# System Patterns

_Обновлено 2026-07-27. Подробное описание устройства — `docs/HOW_IT_WORKS.md`._

## Что изменилось 27-28.07 (устройство, а не детали)

- **сборка данных живёт внутри движка**, не в питоне: `corpus_build.sql` +
  `corpus_merge.sql` + `resolver_build.sql`, связывает `build.sh`;
- **строка корпуса несёт все свои числовые величины** картой `nums`, а не одну
  «денежную». Какую считать — решает вопрос, в момент ответа;
- **сущность выбирает реранкер**, а не близость эмбеддинга метки;
- **вектор 1024** и считает его сам движок (`ai_embed`);
- **подготовка базы** (метаданные → классификация → имена → ссылки → даты → величины)
  признана отдельной сущностью, план — `docs/PREPARE_BASE.md`.

## Разделение ролей — главный принцип

> **Ищет база. Считает база. Модель понимает язык. Код проверяет.**

| Задача | Кто | Почему не другой |
|---|---|---|
| найти строки | инвертированный индекс | модель со схемой промахивалась таблицей |
| посчитать итог | SQL по всему множеству | модель считает по показанным строкам и выдаёт часть за целое |
| «продажи» = «реализация» | модель | языковая задача; эвристика в коде = подгонка под базу |
| числа настоящие | код (гейт) | промт не является гарантией — правило владельца |

## Контракты вместо догадок

Всё, что можно взять из `$metadata`, берётся оттуда. Ни одного имени конкретной
конфигурации в коде — проверено разбором AST.

## 🔴 Надстройки, не переписка (правило владельца 07.08)

**Нельзя трогать то, что работает. Делаем надстройки только.** Если кажется, что
работающий код надо «переписать правильно» — не надо: восстанови рабочее побайтно и
поставь своё РЯДОМ (новый файл/функция, импортирующая примитивы эталона). Два случая
за 07.08 — двухрежимный corpus_build и свой merge в packet_apply — оба откачены;
разбор `docs/HOW_NOT_TO.md §3.39, §3.40`.

| Что | Контракт |
|---|---|
| собственная идентичность | ключ ровно `["Ref_Key"]` |
| табличная часть | ключ содержит `Ref_Key` **и** ещё свойство; владелец найден **по данным** |
| дата записи | `Date` у документов, `Period` у регистров |
| наименование | `Description`, `Code` — если сущность их объявила |
| мусор протокола | `X_Type`, `X_navigationLinkUrl`, `X_Base64Data` — только при объявленной паре `X` |

**Антипример, который был и удалён:** определение табличной части по суффиксу имени.
Давало ложные срабатывания на `*_recordtype` и переворачивало смысл на `*_Turnovers`.

## Границы — по бюджету, не по подобранному числу

Всё, что уходит в модель, ограничено сверху **бюджетом в символах**, а не числом
элементов. Бюджет — свойство контекста модели, он не зависит от базы и не подбирается
под неё. Порядок при этом задан данными, поэтому граница режет хвост, а не смысл.

## Многополевой индекс, а не мешок слов

```sql
CREATE INDEX search_idx ON search_corpus
  USING inverted(doc search_dict, refs search_dict, src_table)
  INCLUDE (src_table, row_key, amount, doc_date);
```

`refs` — только резолвнутые ссылки: можно спросить про контрагента, а не «где-то в
строке». `src_table` без словаря = keyword: фильтр **внутри** индекса.

## Неоднозначность → спросить, а не угадать

Модель может назвать несколько типов записей, если вопрос честно допускает разные
прочтения. Тогда возвращается `kind=clarify` с вариантами и уточняющим вопросом на
языке спрашивающего. **Порога неоднозначности нет и быть не может** — «одинаково ли
подходят» вопрос языковой, а не числовой.

## Что держится кодом, а не договорённостью

| Запрет | Чем держится |
|---|---|
| 1С только читаем | шлюз отвечает 405 на изменяющие методы до всякой авторизации |
| сервис без токена не работает | процесс **не стартует**: выход с кодом 2 |
| бот не пишет в базу | роль СУБД: `INSERT/UPDATE/DELETE/TRUNCATE` = 0 привилегий |
| модель не выдумывает числа | гейт сверяет каждое; не прошло — ответ заменяется структурой |
| подгонка под нашу базу | хук-агент перед коммитом + скрипт после каждой правки |

## Правило работы с движком

Своё писать **только после ответа агента `serenedb-native`, что штатного нет**.
Обычный SQL и приёмы PostgreSQL использованием SereneDB не считаются.

Проверенные исключения, где штатного действительно нет: определение изменившихся строк
(CDC в движке отсутствует), гейт чисел, AST-валидатор SQL, пагинация OData,
`ai_embed` без параметра размерности.

## 🔴🔴 ГЛАВНЫЙ ПРИНЦИП РАЗРАБОТКИ (правило владельца, 2026-07-23)
**Любые правила, ограничения и гарантии, основанные на ПРОМТЕ, — НЕ РАБОТАЮТ.**
Промт (персона/системный промпт) — только для ТОНА и стиля. Любое правило, которое должно ДЕРЖАТЬ
(корректность, «не выдумывай», «не сливай внутреннее», «не ври про действия», запреты/лимиты,
безопасность) — реализуется **детерминированным КОДОМ** (гейт / хук / валидатор / проверка), не текстом.
- Проектируя любое ограничение, сначала отвечай: «чем это ЗАКОДИРОВАНО?». Нет кода → правила нет.
- Числа/факты → кодовый гейт (сверка с источником) — есть (`verify-plugin`).
- Поведение (мета-реплики, ложь о действиях, слив SQL/путей/промпта, инъекции) — сейчас на персоне =
  ВРЕМЕННО, с остаточным риском; цель — кодовый хук (`message_sending`), режущий/заменяющий.
- «Добавил правило в промт» ≠ выполнено. Проверено вживую: персона запрещала — модель нарушала.

## Архитектура (кратко; полностью — `docs/ARCHITECTURE.md`)
Два контура:
- **Холодный** (наполнение): 1С OData (read-only) → GET-only шлюз → ночью ETL→KB-репо (braine) и
  `serene_sync`→витрина SereneDB (аналитика). Обе выгрузки из одного read-only канала.
- **Горячий** (ответ): вопрос → OpenClaw-бот (тон) → `ask_1c` (braine RAG, факты+цитаты) **или** `report_1c`
  (SereneDB, отчёт/график под ro-ролью) → verify-гейт (числа/анти-слив КОДОМ) → ответ клиенту.

Ключевые решения:
- Канал чтения — **штатный OData на IIS** (служба Windows), НЕ встроенный MCP-тулкит
  (тот на idle-обработчике 1С — зависает; `docs/TOOLKIT_TRANSPORT_ROOTCAUSE.md`).
- Read-only — два слоя: пользователь `ai_reader` + шлюз (только GET).
- Мозг — **braine** (клонируемый RAG-шаблон, Open WebUI + pgvector), не своя схема.
- **Конфиг-нейтральность:** код универсален; «что тянуть» — конфиг под бизнес (галочки
  config-ui → `/etc/1c-etl-selected.txt`), не хардкод. Резолв ссылок guid→имя — универсален.

## Структура репозитория
- `docs/` — документация (ARCHITECTURE, RUNBOOK — главные; SERENEDB, OPENCLAW_BOT, PRODUCTION_PLAN).
- `ubuntu/` — код на LXC: `1c-gateway/` (OData-шлюз + dev MCP-прокси), `1c-etl/` (ETL+таймер),
  `1c-config-ui/` (галочки+discovery), **`serenedb/`** (витрина/аналитика: NL→SQL `report_1c` + резолвер +
  ro-роль + тесты), **`openclaw/`** (бот-слой: MCP `ask_1c`, verify-плагин, инстанция/персона, QA).
  У каждого — README + systemd/.
- `windows/` — скрипты стенда (`scripts/backup-1c.ps1`), `fork/` (dev-форк тулкита).
- `memory_bank/` — контекст. `credentials/` — секреты (в `.gitignore`).

## Соглашения
- Коммиты: `тип(область): описание` (feat/docs/fix/chore).
- Каждое изменение → коммит + push в `origin/main`. Значимое → обновлять
  `memory_bank/activeContext.md` и `progress.md`.
- Сервисы на LXC — systemd, `enabled` (zero-touch, переживают ребут).

## Правила (владелец)
- 🔴 1С только читаем; перед любым изменением базы 1С — бэкап (`.dt`/копия).
- На серверах (LXC/Windows) состояние меняем только по явной инструкции владельца.
- Секреты — вне git (`credentials/`, `/etc/*.env` chmod 600).
- Windows-автоматизация — с учётом готчей (BOM, EncodedCommand, COM) из `techContext.md`.
