Замер 2026-07-27 на живой сборке, настройки по умолчанию:

```
 5 000 строк x FLOAT[1536] -> CREATE INDEX за 1 с,   0 МБ
 6 000 строк               -> не завершилось,   +4 473 МБ
10 000 строк               -> не завершилось,  +12 494 МБ
```

Переход **скачкообразный** между 5 и 6 тысячами. `sdb_ivf_posting_size` не двигает
(проверено 128/256/1024). Три гипотезы проверены по исходникам и отвергнуты: размер
обучающей выборки, `kMaxTrainSample`, переключение алгоритма кластеризации.
Причина не найдена.

**HNSW удалён из продукта**, а не «не собран у нас»: каталога `columnstore/` нет,
`kKnownOpclassTypes` = `{included, ivf}`, демки demo4/demo5 не запустятся ни у нас, ни
на их `main`. Строки `hnsw_*` в бинарнике — справочник чужого расширения `vss`,
которое не влинковано, а `LOAD`/`INSTALL` движок запрещает.

**ОПАСНО:** сборка `ivf` НЕ ОТМЕНЯЕТСЯ — `pg_cancel_backend` возвращает успех, работа
продолжается, `SET memory_limit` не помогает. Снимается только рестартом движка.
Каждый неудачный опыт стоит рестарта. Не запускать сборку ivf «на посмотреть».

Отчёт разработчикам: `docs/SERENEDB_IVF_ISSUE.md` (англ.) и `_RU.md`. Ждём ответа.
Канал: https://github.com/serenedb/serenedb/issues

Пока: смысловой поиск идёт полным перебором, 314 мс на 98 тыс. строк, recall 1.0 —
рабочий вариант. Гипотеза владельца на проверку: строить индекс кусками по ~5000 строк
и искать по всем сразу через UNION ALL.
