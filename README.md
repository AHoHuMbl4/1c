# «Второй мозг» на данных 1С

AI-ассистент компании по данным из 1С — **строго на чтение**, ничего в 1С не меняя. Отвечает
в Telegram живым языком на вопросы по данным: кто, что, сколько, когда.

> **Перед началом работы — [`docs/HOW_NOT_TO.md`](docs/HOW_NOT_TO.md).** Каждый пункт
> там оплачен потерянным днём, упавшим сервером или неверным числом у клиента.
>
> **Чем этот продукт обязан быть — [`TARGET.md`](TARGET.md).** Что менялось и чем
> доказано — [`CHANGELOG.md`](CHANGELOG.md).
> Это утверждённый владельцем
> контракт из 21 пункта. При расхождении любого документа с ним прав он.

**Статус: работает на стенде, до продакшена не доведён.** Пишешь боту в Telegram → он
отвечает по реальным данным 1С. На стенде две базы 1С: Бухгалтерия 3.0 (первая) и
УТ 11.4.9 (вторая); боевые ответы идут по **второй** — она же служит проверкой «без
хардкода, на чужой конфигурации».

⚠ **Это держится не настройкой, а процессом, поднятым руками.** Сервис ответов на `:8099`
живёт вне systemd; штатный юнит `1c-serene-ask` настроен на **первую** базу и сейчас
`inactive`. После перезагрузки бот замолчит: юнит поднимется на `:8091`, а мост стучится
в `:8099`. Разбор — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) §6.

## Как это работает

🔴 **PostgreSQL в продукте отсутствует** (`TARGET.md` п. 4 и 16, редакция 25–26.08).
SereneDB — самостоятельный сервер со своим хранилищем (`store.db`, `--server_directory`);
строка «PostgreSQL …» в `SELECT version()` — совместимость протокола для клиентов
(`psql`, Grafana), а не отдельная СУБД в контуре. Пакеты PostgreSQL с серверов контура
удалены 25.08 (подтверждено контрактом). *Прежняя редакция писала «на dev ещё крутится
`postgresql@16-main` (:5432)» и «снос — действие владельца в работе» — это снимок до
вывода; разворачивать PG/pgvector нельзя.* На Windows по контракту стоит только 1С и
агент выгрузки — базы данных там нет.

Всё строится вокруг SereneDB: она и хранит, и ищет. Модель не считает и не ищет —
она нужна только для смысла (п. 19 `TARGET.md`).

Порты на схеме — **первой** базы (шлюз `:6011`, сервис ответов `:8091`). У второй свои:
`:6021` и `:8099`; устройство одинаковое, отличаются только адреса и база движка.

```
Windows (1С)              Ubuntu LXC (весь наш контроль)
┌────────────┐  по IP   ┌───────────────────────────────────────────────────────────────┐
│ 1С:база    │ (роутер  │ OData-шлюз :6011 ── только GET (read-only)                     │
│ └ IIS      │  .1)     │   (у каждой следующей базы 1С — свой: 1c-odata-gateway@<имя>)  │
│   └ OData ─┼─────────►│   └ ТАКТ 1c-serene-pipeline (по готовности, не по часам):      │
│  (ai_reader │          │       синк-дельта из 1С → витрина SereneDB :7890 → корпус +    │
│  read-only) │          │       инвертированный индекс + резолвер + векторы              │
└────────────┘          │  Вопрос: человек → Telegram @бот → OpenClaw (тон)               │
                        │     └ serene_ask :8091 — ВЕСЬ ответ строится здесь:            │
                        │         1. модель понимает вопрос (маленький контекст)         │
                        │         2. ИНДЕКС SereneDB отбирает строки                     │
                        │         3. БАЗА считает суммы/количества по всем строкам       │
                        │         4. модель формулирует фразу из посчитанного            │
                        │         неоднозначно → уточняющий вопрос, а не догадка         │
                        │     → verify-плагин (ГЕЙТ КОДОМ: числа сверяет, внутреннее режет)│
                        │  Наружу временно — только DeepSeek для ответов OpenClaw (п. 16) │
                        │  1c-bot-monitor: алерт в Telegram, если что-то упало            │
                        └───────────────────────────────────────────────────────────────┘
```

⚠ **Слой braine (RAG на OWUI/pgvector) и инструмент `report_1c` (NL→SQL) выведены из контура**
(решение владельца 26.07). PostgreSQL/pgvector с ними — не часть продукта. Графики по
данным вернутся позже — как дополнение ПОСЛЕ ответа, а не как способ его получить.

- **Канал чтения — штатный OData 1С на IIS** (служба Windows): авто-старт, многопоточно, переживает
  ребут. Не встроенный MCP-тулкит — он для прода не годится (`docs/TOOLKIT_TRANSPORT_ROOTCAUSE.md`).
- **Read-only 1С — два слоя:** пользователь-читатель (нет прав записи; по п. 14 создаёт
  инсталлятор) + шлюз (режет всё, кроме GET). Ручное действие при установке одно —
  логин и пароль администратора базы 1С (`TARGET.md` п. 14).
- **Один движок — SereneDB.** Инвертированный индекс на IResearch несёт и словесный поиск (BM25,
  фразы, префикс, опечатки), и вектор. Считает база, по всем строкам, а не по выборке.
  Эмбеддинги текстов — штатный `ai_embed` движка (`TARGET.md` п. 20); модель —
  **`Qwen3-Embedding-8B` @ 1024 в своём контуре** (02.08 съехали с DashScope). Рядом —
  реранкер `Qwen3-Reranker-8B`. *Было ошибочно «@ 1536»; чем опровергнуто:
  `SELECT len(emb) FROM search_corpus` → 1024; 1536 — от выведенного слоя braine.*
- **Свежесть — «как можно быстрее»** (`TARGET.md` п. 17): фиксированного окна нет;
  такт `1c-serene-pipeline` — по готовности. Формулировки «раз в N минут» устарели.
- **Контекст модели не растёт с базой.** Схема базы и перечень колонок в модель не уходят —
  ограничение держится кодом (символьные бюджеты), а не просьбой в промте.
- **OpenClaw** — диалоговая оболочка тона (нативно). Факты — только из инструментов.
  Egress по п. 16 — временно только DeepSeek для ответов OpenClaw; целевое — модели
  внутри контура.
- **Анти-галлюцинации — КОДОМ, не промтом** (правило владельца): гейт `verify-плагин` детерминированно
  сверяет числа ответа с данными и режет внутреннее (SQL/пути). Промт держит только тон.
- **Zero-touch:** настроил один раз → работает само, переживает перезагрузки; мониторинг алертит при сбое.

Полная картина — [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Правила проекта
- 🔴🔴 Вся работа — **только внутри этой папки `1c/`** (в соседние папки воркспейса не смотреть).
  Каждое изменение — коммит + push в `origin/main`.
- 🔴 **1С только читаем** — инвариант. Ни один запрос не меняет данные 1С (2 слоя + read-only роль SereneDB).
- 🔴 **Правила/ограничения — КОДОМ, не промтом** (промт не держит): анти-галлюцинации, анти-слив,
  read-only — детерминированным кодом/гейтом/ролью, персона — только тон.
- 🔴 **Без хардкода.** Настройка, которую человек может заполнить, только зная конкретную базу, —
  такой же дефект, как имя в коде.
- 🔴 **Модель не считает и не ищет** (п. 19 `TARGET.md`). Считает база, отбирает индекс.
- Эмбеддинги — **только Qwen**, с 02.08 в своём контуре (`/etc/1c-embed.env`), ollama не используем.
- На серверах (LXC/Windows) состояние меняем только по явной инструкции владельца.
- Перед любым изменением базы 1С — бэкап (`windows/scripts/backup-1c.ps1`).
- Секреты — в `credentials/` (вне git); на серверах — в `/etc/*.env` (chmod 600).
