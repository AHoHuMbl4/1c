## 1. §2.1 — перепись dup-блока (E4-Д1)

**Вопрос:** снимает ли явная спека два прочтения; реализуемо ли без домыслов
по `:1522-1534`?

**Код сегодня:** `:1524-1534` — один `tmp3_pdoc_dup` (HAVING
`count≠DISTINCT(keyvals)` OR `count≠nrows`) → полный DELETE из
order/chunks/formula/entity.

**v4 §2.1:**
- порядок гейтов зафиксирован: (в) неполный order → mono; иначе collision set +
  `collision_rows`; (б) oversize → mono + quality; иначе (а) V5;
- **mono** = нынешний полный каскад;
- **V5** = сущность остаётся в chunks/formula/entity; из order — только
  коллизионные keyvals; `tmp3_pdoc_tail`;
- гейт покрытия: `collision_rows` до DELETE; после —
  `count(order)+collision_rows==nrows`; форма с `count(DISTINCT tail)` запрещена.

Два прочтения E4-Д1 («оставить каскад + отдельно tail» vs «переписать блок»)
сняты одной фразой keep-in-chunks / partial DELETE. Порядок (в)→(б)→(а) тоже
был в мелких E4 — теперь канон.

Реализация по `:1522-1534`: ветвление вместо единого DELETE-каскада; таблицы
order/chunks/formula/entity уже есть; collision set = keyvals с
`count>1` (тот же смысл, что ветка DISTINCT в HAVING). Домыслов о структуре
диспетчера не требуется.

**Вердикт: ДА** — возражение E4-Д1 снято; реализуемо без домыслов.

## 2. §2.3 — `BEGIN TRANSACTION` + lifecycle маркёра

**Вопрос:** канон доков вместо голого BEGIN; lifecycle = у progress/stage. Ок?

**v4:** одна строка `\gexec`
`BEGIN TRANSACTION; EXECUTE p_doc_tail(…); INSERT …_done …; COMMIT`.

Доки SereneDB (*Starting a Transaction*): канон — `BEGIN TRANSACTION;`.
Multi-Statement: батч — одна (неявная) транзакция; явный BEGIN…COMMIT в той же
строке согласован с главой. Окно «stage есть, маркёра нет» закрыто откатом.

Lifecycle (`fresh` `:1561-1567`, formula `:1445-1452`, post-finalize
`:2211-2216`) — якоря wipe progress/stage реальны; план зеркалит их для
tail/_done. Бамп formula при правке тела tail — дисциплина (как в E1/E2),
fail-closed через `stage_rows=nrows` + error без маркёра.

**Вердикт: ДА** — ок (рекомендация E1 выполнена).

## 4. §3.4 — эталон (возражение E1)

**Вопрос:** снимает ли v4 возражение об эталоне при верности фактов
журнала/замеров (оркестратор) — логическая согласованность с QUALIFY/fold?

**Код QUALIFY/fold:**
- `fold.on_ ⇔ key_cols=['Ref_Key']` (`:1588`, chunk `:1832`, finalize `:2063`);
- монолит пишет в `tmp3_corpus` с QUALIFY внутри INSERT (`:1815-1817`):
  `NOT fold.on_ OR row_number()…=1`;
- при fold.on_ и **уникальных** `(src_table,row_key)` QUALIFY никого не режет →
  count корпуса == nrows витрины — **достижимо без отмены QUALIFY**.

**v4 относительно E1:**
1. убрано «витрина == стейдж монолита» — ловушка термина снята;
2. эталон привязан к `tmp3_corpus` **после** внутреннего QUALIFY (`:1815-1817`),
   не к сырой витрине как подмене корпуса;
3. `74 982 == витрина` сформулировано как **факт данных** (fold не сокращает на
   этой сущности), не как «QUALIFY выключен»;
4. нарратив завершения монолита 19:35:13 / смерть такта позже на merge-гварде /
   два совпавших замера — вне кода; по условию промта принимаю как данные
   оркестратора;
5. «до» `74 785 / 71947efe…` отделён как отпечаток перехода / дрейф, не как
   эталон №0.

Логика: измеренный post-QUALIFY count = nrows витрины **следует** из кода, если
дублей `row_key` нет. Прежнее A2/baseline `74 785` тогда = снимок боевого
корпуса «до», не опровержение post-монолитного `tmp3_corpus`. Противоречия
«эталон обязан быть 74 785 потому что QUALIFY всегда режет» в коде нет —
QUALIFY режет только при коллизии ключа объекта.

Условная ветка E1 §1.1 («если non-fold или уникальные ключи — count=nrows
корректен») — именно этот случай; v4 честно кладёт его на замер, не на
«fold.off».

**Вердикт: ДА** — при принятых фактах замеров возражение E1 об эталоне снято;
с QUALIFY/fold согласовано.
