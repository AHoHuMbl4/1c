## Что извлечь (факты с file:line, цитаты короткие, без догадок)

1. Полный пайплайн каждого файла: вход → шаги → выход; КТО их вызывает и что делает
   с результатом (найди call-site в z20_ask_main_http.py / z21_wiki_choice.py через
   grep по именам функций — только чтобы понять потребителя, сам файл не читать целиком).
2. ВСЕ срезы кандидатов: top-K/LIMIT, alias_top, пороги веса/скора, потолки паспортов
   (WIKI_PASSPORT_N/WIKI_PICK_N и пр.) — точное значение константы + file:line + что
   режется при превышении. Где именно «топ-3» bm25, из-за которого умирает «клиентов».
3. ВСЕ ветки, где пул/кандидат молча выбрасывается или результат становится пустым
   БЕЗ меню — file:line каждого раннего return / return None / [].
4. Нормализация имён при поиске: регистр, пробелы, склейка, стемы, ts_lexize — где
   «реализации ТМЦ» (с пробелом) может разъехаться с системным «РеализацияТМЦ».
   Есть ли уже какая-то норм-функция (в т.ч. `_homonym_norm` — grep по репо
   ubuntu/serenedb/ask/), где она живёт, что делает.
5. Как строится поисковый запрос (tsquery/bm25/websearch? какие слова вопроса
   попадают в запрос, какие отбрасываются — стоп-слова? длина?).
6. Какие таблицы/предства словаря читаются (search_dict, search_dict_syn и т.п.),
   откуда имена берутся и как фильтруются по kind/роду.

## Формат реестра c-lens1-entity.md

- §1 пайплайн z06 и z07 (вход/выход/потребители, file:line);
- §2 таблица «точек смерти»: file:line → механизм (срез/молчаливый throw/пустой
  return) → условие → какому из двух вопросов это угрожает;
- §3 все константы отсечения списком (имя = значение = file:line);
- §4 нормализация имён: что есть сейчас, где точка входа для единой норм-функции;
- §5 факты для дизайна LLM-резолвера: в какой точке ПОЛНЫЙ пул кандидатов ещё
  доступен целиком (до среза), чтобы его можно было отдать резолверу вместо среза.

Только измеримое: каждая строка реестра обязана иметь file:line. Мнений «наверное» —
не писать; если что-то не нашёл — так и написать «не найдено».
