## 1. (б) lifecycle `tmp3_pdoc_tail_done` — v3 §2.3

**Требование D3:** создать IF NOT EXISTS; стирать вместе с progress/stage на
fresh / formula / post-finalize; после правки tail — тот же сброс или отпечаток
в formula; окно «stage есть, маркёра нет» закрыть.

**В v3 §2.3:**
- хвост+маркер атомарны одной строкой `\gexec`
  `BEGIN; EXECUTE p_doc_tail; INSERT …_done; COMMIT` (обрыв откатывает оба);
- lifecycle `tmp3_pdoc_tail` и `_done` = у progress/stage: fresh (`NOT on_`,
  :1561-1567), смена formula (:1445-1452), после успешного finalize (:2211-2216);
- правка тела tail «сопровождается сбросом formula (механизм существующий)»;
- finalize при непустом tail без маркёра → `error()`;
- M2 (§2.5) явно: атомарность + сброс маркёров на fresh/formula.

Сверка с кодом: точки :1445-1452 / :1561-1567 / :2211-2216 — реальные места
wipe progress/stage; план зеркалит их для tail/_done. Formula сейчас
`md5('v8b'||'key_order'||chunk_cells||ncols)` (:1435) — тело tail **не** входит
в отпечаток; «сброс formula» = дисциплина бампа версии (v8b→…), как альтернатива
из D3 («или отпечаток / stamp»). Окна stale-marker→skip tail при усиленном
`stage_rows=nrows` (§2.4) по-прежнему fail-closed, не молчаливая потеря emb.

**Остаток (не блокер векторов):** явного `CREATE TABLE IF NOT EXISTS …_done` в
§2.3 нет (подразумевается); атомарность multi-statement в одном `\gexec` —
на проверке исполнителем по цитированным докам (B3), не дыра спеки.

**Вердикт: ЗАКРЫТО.**

## 4. Новые векторные дыры в v3 (§0.1 / §3.4)

### 4.1 Предусловие `tmp3_build` (§0.1 / §3.4)

Сущности с коллизиями ∈ `tmp3_build` (отметки `search_changed_sources` со
сорванного такта; merge их не потреблял). Логика `tmp3_build` (:1336-1347)

потеря emb.

**Вердикт по 4.1: дыры потери векторов нет.**

### 4.2 Эталон 74 982 + «до» 74 785 (§3.4)

v3: эталон монолита **74 982 / 57ad85de…** с обоснованием замера 02.09
(витрина = стейдж 1:1; QUALIFY не схлопывает; 74 785 = дрейф дат корпусов);
«до»-корпус 74 785 / 71947efe… — отпечаток перехода; multiset без emb;
после merge multiset `search_corpus` == §3.4; `векторов_умрёт=0`; anti-join к
бэкапу → 0 дыр.

Код по-прежнему несёт fold-QUALIFY (`:1815-1817`, finalize `:2112-2113`) при
`key_cols=['Ref_Key']`. Утверждение «не схлопывает» = факт данных на замер
(нет дублей объекта), не отмена QUALIFY. Канон окна в
`takt-baseline.txt` / activeContext всё ещё **74 785 / 71947efe…** (снимок
корпуса «до»).

**Векторная дыра (умеренная, новая относительно D3):** критерии перехода
74 785 → 74 982 не согласованы с жёстким `векторов_умрёт=0` и anti-join C3
(backup LEFT JOIN corpus: ключ пропал **или** `emb IS NULL` → hole).

- Если 74 785 ⊆ 74 982 и на пересечении `content_hash`/`row_key` стабильны —
  бюджет=0 и anti-join=0 достижимы; «до»-отпечаток полезен.
- Если дрейф **с выбытием** ключей — `unmatched_kill` в
  `tmp3_merge_vec_budget` (:637-656) даёт `векторов_умрёт>0` → гейт/приёмка
  стопят (вектора не жгутся молча), но зелёный путь §3.5 противоречив.
  Давление обойти `MERGE_VECTOR_LOSS_BYPASS` (запрещён §8) или ослабить
  anti-join — процессный риск, не дыра кода плана по записи.

План **не** требует доказать ⊆ / стабильность пересечения и **не** сужает
anti-join до «дыры emb у ключей, оставшихся в корпусе». Без одной из двух
фраз приёмка перехода либо ложно-красная, либо провоцирует ослабление гейта.

Неверный эталон 74 982 при реальном fold→74 785: mismatch §3.4 → merge нет —
снова fail-closed (спор корректности эталона — линза D1, не молчаливая
потеря emb).

**Вердикт по 4.2: есть остаточная дыра критериев перехода (не молчаливая
потеря; блокер «зелёной» приёмки при churn ключей).**
