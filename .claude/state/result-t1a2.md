# T1-A2: почему монолит `p_doc` на `document_реализациятмц` ~5 ч / ~1 ядро

Аудит только по репозиторию `/srv/1c` (серверы не трогались). Якоря — `ubuntu/serenedb/corpus_build.sql`, план `.claude/state/plan-takt-fix-v10.md`, живые числа из CHANGELOG / прошлых проб в `.claude/state/result-exec-1c.md` и `result-drev3r-1.md` (как зафиксированные замеры, не повторённые в этой сессии).

---

## 0. Картина одной страницей

1. Чанкование по ячейкам **включается** для широких таблиц (`nrows × ncols > chunk_cells`), затем **снимается dup-гейтом**, если в `tmp3_pdoc_order` есть коллизии `keyvals` (`corpus_build.sql:1522-1534`).
2. У `document_реализациятмц` живой замер: 74 979 строк order, **72 204** distinct keyvals, **2 776** строк с пустым `Ref_Key`+`LineNumber` → один и тот же keyvals `"|"` → сущность уходит в **монолит** (`result-exec-1c.md`; CHANGELOG 02.09; `result-drev3r-1.md` R1).
3. Монолитный `EXECUTE p_doc($tbl)` делает **один** INSERT: полный UNPIVOT всех колонок (~75k×126 ≈ **9.45M ячеек**) + per-cell regex/list + агрегаты + окна → пишет сразу в `tmp3_corpus` (`1576-1817`, диспетчер `2172-2176`).
4. Чанкованный путь режет работу на порции `chunk_rows = floor(chunk_cells/ncols)` (`1454-1469`), тяжёлую сборку текста делает на подмножестве строк, финальный dedup — в `p_doc_finalize` (`2047-2113`). Крупные чанкуемые сущности (321k / 208k / 191k строк корпуса) поэтому укладываются в минуты при том же такте.
5. Узкое место монолита — **объём working set одного statement + стоимость на каждую ячейку**, а не «другая формула текста»: тело `j`/`pieces`/`GROUP BY rid` у монолита и чанка **почти копия**.

## 1. Что делает монолитный `p_doc` и где узкое место

### 1.1 Конвейер (построчно / по ячейкам)

| Шаг | Что | Якорь |
|---|---|---|
| `kc` / `fold` | ключ сущности; `fold.on_ ⇔ key_cols = ['Ref_Key']` | `1578-1588` |
| `src` | `row_number() OVER ()` + **`substr(coalesce(COLUMNS(*)::VARCHAR,''),1,20000)` на ВСЕ колонки** | `1598` |
| `cells` | UNPIVOT всех колонок → ~nrows×ncols строк | `1599` |
| `keyed` | `string_agg(val,'\|' ORDER BY list_position(key_cols,col))` только по ключевым колонкам | `1602-1606` |
| `j` | JOIN `tmp3_cls`; флаги kind/guid/text/num/flag/date; **LEFT JOIN `tmp3_refmap`**; фильтр empty/`own_ref` | `1607-1704` |
| `pieces` | сборка текстового `piece` + `prio`; `corpus_cell_num` до 3 раз на числовую ячейку | `1705-1720` |
| agg | `GROUP BY rid`: `string_agg` doc/refs, `map_from_entries` nums/flags/refs_map/refs_own, `max` даты | `1765-1810` |
| ключ корпуса | `coalesce(row_key, sha1(doc))`; при non-fold и дублях rk — `rk\|\|'#'\|\|sha1(doc)` | `1753-1762` |
| наружный dedup | при `count>1` по `(src_table,row_key)` — суффикс `#N`; QUALIFY одна строка на объект при fold | `1732-1817` |

Итог INSERT — в **`tmp3_corpus`**, не в stage (`1577`).

### 1.2 Выражения с O(n²)-подобным / «дорого на ячейку» поведением

Не классический nested-loop по строкам×строкам витрины, а **стоимость × число ячеек** (линейно по nrows×ncols, с тяжёлой константой) плюс возможные квадратичные эффекты на больших списках/хеш-джойнах.

1. **Полный UNPIVOT после cast всех колонок в VARCHAR** (`1598-1599`).  
   На realiz ≈ 9.45M ячеек в одном statement. Комментарий K1-m: монолит на 638 330×100 давал **>9.7 GiB unspillable** (`1383-1384`). Тот же класс нагрузки.

2. **`regexp_full_match` GUID на каждой ячейке** — дважды по смыслу: флаг `is_guid` (`1611`) и условие JOIN к `tmp3_refmap` (`1671-1674`).  
   CHANGELOG 02.09 прямо: «per-cell regex при threads=4».

3. **`list_position((SELECT key_cols FROM kc), u.col)`** — многократно на ячейку (`1603-1605`, `1609`, `1647`, `1701`). Список короткий, но вызов × миллионы ячеек.

4. **Коррелированный `(SELECT 1 FROM tmp3_datecol d WHERE d.tbl=$1 AND d.col=u.col) AS is_dt`** (`1656`) — на **каждую** ячейку `j`, вместо JOIN один раз.

5. **`EXISTS (SELECT 1 FROM tmp3_src s2 WHERE lower(s2.tbl)=c.decl_entity)`** в WHERE отброса вложенных колонок (`1700-1704`) — при fold и `own_ref`/`own_prop`; на широком документе срабатывает на кандидатах отброса.

6. **`regexp_matches(u.val,'^(https?://|/)')`** для `in_text` (`1612-1613`) — ещё один regex на текстовые ячейки.

7. **`corpus_cell_num(val)`** до трёх раз в CASE куска (`1710-1713`) + снова в `map_from_entries` nums (`1778-1779`). Макрос сам делает `replace`×3 + `try_cast` (`817-819`).

8. **Окна после агрегации** (`1733-1736`, `1753-1755`, `1815-1817`) — partition по ключу на всём результате сущности; для fold QUALIFY оставляет одну строку на объект.

**Анти-джойны** в теле `p_doc` как `NOT EXISTS` по витрине×корпусу — нет. Есть `NOT (… AND EXISTS …)` на отброс колонок (`1699-1704`) и косвенно «пустые ячейки» `u.val <> ''`.

### 1.3 Сравнение с `p_doc_chunk`

**Идентичны (копия логики сборки строки):**  
`kc`/`fold`, JOIN `tmp3_cls`, LEFT JOIN `tmp3_refmap` + тот же GUID-regexp, те же флаги kind/measure/flag/date, тот же WHERE own_ref/own_prop, `pieces`, агрегаты doc/refs/nums/flags/refs_map/refs_own/dt (`1820-2044` зеркалят `1576-1810`).

**Различаются:**

| | Монолит `p_doc` | `p_doc_chunk` |
|---|---|---|
| Источник строк | весь `query_table` сразу (`1598`) | фильтр порции через keyvals (`1871-1882`) |
| Цель INSERT | `tmp3_corpus` | `tmp3_pdoc_stage` (`1821`) |
| Pre-pass keyvals | нет | полный UNPIVOT ключевых колонок **всей** таблицы + `string_agg` (`1843-1870`) **на каждый** EXECUTE порции |
| `row_key` mid/outer `#sha1` / `#N` | внутри statement (`1753-1737`) | **нет** — перенесены в `p_doc_finalize` (`2084-2113`) |
| QUALIFY fold | да (`1815-1817`) | **нет** в chunk; fold-схлопывание только в finalize (`2112-2113`) |
| Параметры | `$1` tbl | `$1` tbl, `$2` lo, `$3` hi |

**ГИПОТЕЗА H1 (главное узкое место монолита):** wall-time доминирует полный UNPIVOT+per-cell regex/list на ~9.45M ячеек в одном working set, а не «особый» SQL только у realiz.  
**Проверка:** `PRAGMA enable_profiling` / `SET profiling_coverage='ALL'` + `EXPLAIN ANALYZE` (или `enable_profiling=json`) на укороченной копии сущности (например 5k строк × те же ncols) vs та же выборка через `p_doc_chunk` на одной порции; сравнить CPU time операторов UNPIVOT / REGEXP / HASH JOIN refmap. На боевой таблице — только после явного слова владельца (сервер).

**ГИПОТЕЗА H2:** коррелированный `is_dt` и тройной `corpus_cell_num` дают заметную долю CPU.  
**Проверка:** тот же профиль; патч-проба на копии: `is_dt` → JOIN `tmp3_datecol`, `corpus_cell_num` один раз в CTE — замер wall на 5k-строчном срезе.

## 2. Почему монолит «однопотен», а чанк быстр

### 2.1 Разница в объёме (доказано кодом + замерами)

- Порог и размер порции — **бюджет ячеек**, не «магия другого алгоритма» (`1387-1406`, `1454-1463`). План v10: на окне `floor(chunk_cells/126)≈4975` строк/порция, ~16 порций (`plan-takt-fix-v10.md` A.1).
- K1-m: одна порция ~2 GiB RSS vs >9.7 GiB на весь монолит (`1383-1384`).
- Чанк обрабатывает тяжёлый `j`/`pieces`/agg на **подмножестве** строк; монолит — на всех сразу.
- Крупные чанкуемые сущности в том же такте прошли за ~6 мин (фон задачи) при **большем** числе строк корпуса — значит узкое место не «nrows вообще», а **монолитный working set × ширина** + снятие чанков у realiz.

### 2.2 Разница в плане / threads

- Доки: `SET threads = N` задаёт число потоков параллельного исполнения запроса ([Configuration › Pragmas › Threads](https://docs.serenedb.com/configuration/pragmas#threads)).
- Пакет v10/CHANGELOG: монолит шёл при **threads=4**, но живой дозор такта — **~1 ядро** (`activeContext`; фон задачи). То есть pragma не равна утилизации.
- В коде `p_doc` нет явного `SET threads`; параллелизм — сессионный/глобальный движка. Замечание в самом SQL: порядок ключей MAP без `ORDER BY` при параллельном исполнении нестабилен (`1773-1777`) — разработчики ожидают параллель, но **не** делают statement обязательно многопоточным.

**ГИПОТЕЗА H3:** один гигантский pipeline (UNPIVOT → hash join refmap → giant aggregate) упирается в memory/spill или в оператор, слабо параллелящийся; чанки дают несколько меньших запросов, каждый лучше заполняет потоки / меньше spill.  
**Проверка:** на стейдже `SELECT current_setting('threads')` во время `p_doc`; profiling CPU per operator; сравнить `vmstat`/RSS монолита vs одной порции chunk (владелец / дозор, не эта сессия).

**Вывод по п.2:** доминирует **объём одного statement**, не «другая семантика текста». Threads в доках есть; факт ~1 ядра при threads=4 — **не опровергает** объёмную гипотезу и **не доказан** в этой сессии как баг движка.

## 3. Как чанковать монолит по батчам документов, не ломая dup-гейт

### 3.1 Что именно ломает dup-гейт / фильтр порций

Dup-гейт (`1524-1530`):

```text
HAVING count(*) <> count(DISTINCT o.keyvals) OR count(*) <> e.nrows
```

Смысл комментария (`1522-1523`): одинаковые keyvals → фильтр порции

```sql
kv.keyvals IN (SELECT o.keyvals FROM tmp3_pdoc_order o
               WHERE o.tbl=$1 AND o.pos BETWEEN $2 AND $3)   -- 1877-1880
```

затянет **все** строки с этим keyvals в **каждую** порцию, где попалась хоть одна позиция коллизии.

Живые числа без dup-gate на realiz: симуляция дала `portion_sum=7 778 379` вместо 74 979 (`result-drev3r-1.md` R2). Пустые ключи: 2 776× keyvals `"|"` (`result-exec-1c.md`).

### 3.2 Что должно быть в батче, чтобы коллизии K1-m/realiz не размножали строки

Инвариант фильтра порции: **каждая физическая строка витрины попадает ровно в один batch**, даже если значения `key_cols` (+surrogate) совпадают.

Это обеспечивается **только** если селектор порции — **уникальная идентичность строки**, а не «значения ключа сортировки»:

| Подход (штатный SQL) | Условие безопасности | Риск |
|---|---|---|
| **A. Фильтр по `pos`**, как задумано в плане («порция = диапазон позиций», `plan-takt-fix-v10.md` A.2): один раз `row_number() OVER (ORDER BY key_cols…)` → `WHERE pos BETWEEN lo AND hi` | `pos` уникален по построению; keyvals для фильтра **не нужны** | Нужна **та же** ORDER BY-формула, что в `tmp3_pdoc_order` (`1496-1516`), иначе сдвиг границ. Дубли ключей сортировки остаются, но не размножаются |
| **B. Уникализировать keyvals**: дописать стабильный разряд (`pos`, или hash прочих колонок / `DataVersion`), хранить в order; фильтр `keyvals IN (…)`) | `count(DISTINCT keyvals)=nrows` → dup-гейт зелёный | Менять только **тег порции**, не `row_key`/`content_hash` корпуса (запрет плана «семантику row_key не менять», v10 условие №1) |
| **C. Батчи по диапазонам непустого `Ref_Key` + отдельный батч всех «пустых»** | Все 2 776 коллизионных строк — **в одном** batch; остальные Ref_Key режутся так, что один Ref_Key не режется пополам *если* нужен атомарный fold на уровне chunk (см. ниже) | Хардкод «пустота» как особый класс; для non-fold регистров — другой ключ (`Recorder`+`LineNumber`) |
| **D. Оставить dup→монолит** (текущее) | Корректность ключей | 5 ч / риск OOM на 10–30× базах |

Для **fold** (`key_cols=['Ref_Key']`, документ): QUALIFY «одна строка на объект» сейчас в **finalize** (`2112-2113`), не в chunk. Значит разные строки одного `Ref_Key` (шапка + хвосты) **могут** лежать в разных порциях stage — finalize схлопнет. Но:

- stage_gate для fold проверяет только `stage_rows > 0`, **не** `stage_rows = nrows` (`2074-2077`);
- при размножении keyvals stage раздувается, finalize всё равно QUALIFY’ит — риск **молчаливого** раздувания CPU/памяти и неоднозначного выбора представителя, если в разные порции попадут **разные** тексты одного ключа в разном порядке.

**Практическое правило батча для документов:**  
либо (A)/(B) — уникальный pos/тег; либо (C) — **все строки с одинаковым collidable keyvals в одном batch**, и лучше **весь один `Ref_Key` целиком** в одном batch (проще рассуждать о fold и приёмке multiset).

**Нельзя:** снимать dup-гейт и оставить фильтр `keyvals IN` как сейчас — это возврат дефекта размножения (R3).

## 4. Что в коде выглядит как потеря / лишняя работа

1. **Двойной полный проход ключевых колонок в каждом `p_doc_chunk`:**  
   `tmp3_pdoc_order` уже материализован (`1474-1520`), но chunk снова UNPIVOT’ит всю таблицу для keyvals (`1843-1870`), затем ещё раз UNPIVOT выбранных строк для текста (`1883`). Зафиксировано как R5 (`result-drev3r-1.md`).

2. **Повторные `string_agg` / list-сборки одной строки:** keyed отдельно; doc/refs отдельно; maps отдельно — необходимо по смыслу, но `corpus_cell_num` и GUID-regexp дублируются внутри одной ячейки (`1710-1713`, `1611`+`1672`).

3. **Монолит не использует уже посчитанный order/chunks:** даже после того как сущность прошла формулу и упала в dup, весь дорогой precompute order для неё **удаляется** (`1531-1534`) — работа на построение order для dup-сущности выброшена (если она успела попасть в chunks до gate).

4. **`COLUMNS(*)::VARCHAR` до UNPIVOT** (`1598` / аналог в chunk `1872`): материализация широкой строки как текста до разборки по колонкам — лишний объём vs UNPIVOT сырых типов.

5. **Диспетчер:** сущности без chunks → один `EXECUTE p_doc` (`2172-2176`); с chunks → N×`p_doc_chunk` + progress + `p_doc_finalize` (`2179-2209`). Realiz после dup — всегда левая ветка.

6. **Не потеря строк корпуса при текущем dup→монолит:** наоборот, монолит — безопасный путь; 74 982→74 785 — ожидаемое fold/QUALIFY (разные строки объекта → одна), не дефект чанка. Дефект — **время**, не п.13 на этом пути.  
   Потеря п.13 вспыхнет, если включить chunk **без** уникального селектора порции (размножение + неоднозначный QUALIFY) или если сменить формулу `row_key`/`sha1(doc)` (запрет v10).

## 5. Варианты «кратно быстрее» (только SQL / штатные средства)

Ограничения владельца: без своих скриптов поверх базы (`HOW_NOT_TO` §0 / TARGET п.20); не менять семантику существующих `row_key`/`content_hash` (v10 условие №1); молчаливая потеря строк = дефект (п.13).

### V1 — Фильтр порции по `pos` (довести план A.2 до кода)

Заменить `keyvals IN (… pos BETWEEN …)` на присоединение/пересчёт `row_number() OVER (ORDER BY …) AS pos` + `WHERE pos BETWEEN $2 AND $3`.  
**Эффект:** realiz снова чанкуется (~16 порций × меньший WS) → ожидаемо минуты вместо часов (как соседние сущности).  
**Риски:** рассинхрон ORDER BY с `tmp3_pdoc_order` → дыры/сдвиги порций (ловятся `chk`/`stage_gate` для non-fold; для fold gate слабее — усилить `stage_rows`/полноту). Dup-гейт можно оставить как диагностику или сузить.  
**Приёмка:** multiset `(content_hash,row_key)` realiz; count корпуса; `portion_sum = nrows` без взрыва.

### V2 — Уникальный тег порции = keyvals∥pos (минимальный дифф к текущему IN)

В `tmp3_pdoc_order` и зеркале chunk писать уникальный ключ фильтра; **корпусный** `row_key` не трогать.  
**Эффект:** dup-гейт зелёный, существующий `IN`-механизм перестаёт размножать.  
**Риски:** легко по ошибке начать использовать тег в `row_key`; раздувание строк order. Нужен замок теста identity.

### V3 — Убрать повторный full-table keyvals из каждой порции

Джойнить к `tmp3_pdoc_order` по уже уникальному id / читать только `pos∈[lo,hi]` без повторного UNPIVOT всей таблицы.  
**Эффект:** ускоряет **уже чанкуемые** сущности (сейчас тоже платят full scan×N порций, R5); для realiz полезен только вместе с V1/V2.  
**Риски:** низкие для ключей; регресс resume/formula при смене выражения order.

### V4 — Дешёвые SQL-микрооптимизации монолита (пока dup держит)

`is_dt` → JOIN; один проход `corpus_cell_num`; GUID-regexp только при `kind='ref'` или после дешёвого length/pattern gate; не кастить все колонки в VARCHAR до UNPIVOT.  
**Эффект:** кратность неизвестна (скорее доли, не 10×), но дешёво проверить на срезе.  
**Риски:** смена набора ячеек в тексте/картах → изменение `doc`/`content_hash`/`sha1(doc)` fallback → rewrite ключей (п.13 / векторы). Только с приёмкой multiset.

### V5 — Отдельный SQL-батч «коллизионный хвост» + чанки по остальным Ref_Key

Все строки с collidable keyvals — один `p_doc`-подобный statement; остальное — chunk по диапазонам уникальных Ref_Key.  
**Эффект:** 72 204 уникальных ключа чанкуются; 2 776 в одном мини-монолите.  
**Риски:** сложнее диспетчер; для fold нужна аккуратная сборка stage+finalize; опасность забыть хвост (потеря строк) — гейт `done_rows = nrows` обязателен и для fold.

## 6. Рекомендуемый порядок (аудит, не исполнение)

1. **V1 или V2** — единственные пути вернуть realiz в cell-chunking без возврата размножения.  
2. Параллельно **V3** — убрать O(порции)×full scan.  
3. **V4** — только с замером профиля и multiset-приёмкой.  
4. Полная row-level дельта (пакет B) — вне scope; не подменяет V1 на текущем монолите.
