## 1. П1 — hash-bump / «≲1 ч»: честность контракта и реалистичность

### Что v2 починил (да)

§0.1 больше не смешивает «минуты» с первым тактом после правки `corpus_build.sql`:
- минуты = (а) проблемный statement после V5; (б) такт №2 при 0 изменений / SKIP_BUILD;
- после выката этапа 2 → hash ≠ `build_sql_hash` → SKIP_BUILD=0 (`build.sh:253-288`);
- приёмка §3.5: такт №1 = полная пересборка по контракту, критерий **≲1 ч**, не «минуты».

Это закрывает главный упрёк C4-П1 на уровне **формулировки** окна выката.

### Где v2 всё ещё врёт / недосказан

**«Полная пересборка всех сущностей» (§0.1) — неверно по коду.**

Смена hash только **заставляет запустить** `corpus_build.sql`. Множество сущностей —
`tmp3_build` (`corpus_build.sql:1004-1007`, `:1336-1347`):

| Условие | Эффект |
|---|---|
| `tmp3_inc.on_` = true (`changed_sources_ok=1` ∧ корпус ∧ refmap) | в build только changed ∪ lag ∪ rename-ветки |
| `tmp3_inc.on_` = false | да, **все** из `tmp3_src` |

Живые якоря репо (не сервер):
- `result-audit-1.md` / `result-tf1-1.md`: на окне типичный `tmp3_build≈30`, не 351;
- текущий такт v10: `pdoc_chunk_entities=6` (`result-exec-1d.md`); «5 крупных чанкуемых ~6 мин» + монолит realiz (`activeContext`, A2).

При **стопнутом apply** (§3.3) и живом `changed_sources_ok=1` hash-bump **не гарантирует**,
что `document_реализациятмц` попадёт в `tmp3_build`. Без неё V5 на приёмке не исполняется,
а `build_sql_hash` после такта всё равно обновится — правка «применилась» формально, по
содержимому корпуса — нет. План этого сценария не специфицирует (FORCE / сброс inc /
явный mark в changed).

### «≲1 ч» — оценка по коду и замерам репо

**Числа, которые есть:**

| Факт | Источник | Что означает |
|---|---|---|
| 5 крупных чанкуемых ~6 мин | activeContext / A2 / план §0.1 | wall пятёрки chunk-path в текущем такте |
| `pdoc_chunk_entities=6` | result-exec-1d | шестая — realiz (монолит), не в «6 мин» |
| stage / merge-контекст **1 441 514** строк | prompt-t1a3 / A3 (corpus×stage) | это **строки `tmp3_corpus` после сборки**, не «351 сущность» и **не wall-time** |
| «сборка завершена 1441514» за N минут в CHANGELOG 02.09 | **нет** | в `CHANGELOG.md` / `result-exec-1c.md` **нет** пары (1441514 ↔ длительность минус монолит) |
| оценка «29 прочих из tmp3_build=30» | result-tf1-1 §4 | **20–60 мин** (при 8 сущностях >50k), до фикса V5 |

**Сборка нижней оценки такта №1 после V5 (та же ~30 сущностей, что живой такт):**

- пятёрка chunk ≈ 6 мин (замер);
- realiz V5 ≈ «как сосед» — **минуты, не доказано замером**, только аналогия A2;
- мелкие/средние из остатка build — неизвестны в репо для *этого* такта; tf1 давал десятки минут на старом пороге;
- merge после этапа 1: ранее ~2 мин до OOM на unmatched — после резки ожидаемо минуты;
- embed при pending≈0: секунды.

**Итого:** ≲1 ч на *этом* окне при scope≈текущего `tmp3_build` — **правдоподобно как ориентир**, но **не выведено из замера «build wall − монолит»** (такого числа в репо нет). Если же «все сущности» читать буквально (inc off → ~351 / полный корпус ~1.66M) — ≲1 ч **не обоснован** имеющимися цифрами; план сам одновременно говорит «десятки минут» и «≲1 ч» без разложения по частям.

### Вердикт П1

Контракт скорости **честнее v1**, но формулировка «всех сущностей» **ложная**; критерий ≲1 ч —
**недозадокументированная ставка**, не бюджет из замера. Нужна правка §0.1/§3.5: scope =
`tmp3_build` по правилам inc + явное предусловие «realiz ∈ tmp3_build»; ≲1 ч — либо разложить
по замерам, либо пометить «ориентир okna / fail→разбор», не SLA без цифр.

## 3. П3 — гейт «хвост > половины nrows»

### Разумность

На okna realiz: ~2 776 / ~74 982 ≈ **3.7%** → V5 проходит, mono не нужен. Порог ловит
катастрофу «хвост ≈ вся таблица» (C4-П3) и пишет `pdoc_tail_oversize` — молчаливого
возврата к 5 ч без следа больше нет. Это **лучше v1**.

### Дыра 40%

Хвост **40%** nrows: гейт молчит → V5 → один `p_doc_tail` на 0.4×nrows×ncols ячеек.
Это тот же класс workload, что монолит (unspillable agg на большом working set), только
без явной диагностики «мы снова в часах». Порог «½» — **произвольная доля строк**, не
связанная с уже существующим бюджетом чанкования.

### Лучше

Привязать гейт к **тому же бюджету ячеек**, что режет порции
(`tmp3_pdoc_cfg.chunk_cells` / `chunk_rows`, `corpus_build.sql:1389-1463`):

```
если tail_rows * ncols > chunk_cells
   (экв. tail_rows > chunk_rows сущности)
→ mono + search_quality('pdoc_tail_oversize', …)
```

Смысл: хвост больше одной «разрешённой» порции = statement того же класса, что монолит.
Дополнительно (не вместо): всегда писать `tail_rows`/`nrows`/`ncols` в quality при любом
V5 — даже при проходе гейта (видимость 40%-кейса в журнале).

Доля ½ как единственный критерий — **слабый генерик**; для п.0 лучше cell-budget.

## 5. Новые провалы v2

### Н1. Сухой такт №0 удваивает wall до «зелёного»

§3.4: отдельный `psql -f corpus_build.sql` + multiset **до** merge; затем §3.5 полный юнит
снова гоняет build+merge (hash уже другой / resume / свежий wipe `tmp3_corpus` при
`tmp3_resume_pdoc.off` — `:1559`).

Если build scope ≈ текущий и без монолита укладывается в ~30–50 мин, №0+№1 ≈ **час+**.
Критерий ≲1 ч написан только на №1; владельцу «до зелёного продукта» не сказано, что
безопасная приёмка стоит **ещё один** прогон сборки.

**Оправдан ли №0?** Да как барьер векторов (C3: mismatch → merge не звать). **Не оправдан**
молчанием в SLA: либо включить №0 в бюджет ожидания («до зелёного ≲2 ч: сухой+юнит»),
либо заменить №0 на прогон M2 на фикстуре + один юнит с pre-merge гейтом multiset
внутри того же `corpus_build`/`build.sh` (один wall).

### Н2. Маркер `tail_done` и вечный блок / раздувание stage

§2.3:
- маркер после успешного tail;
- resume пропускает помеченные (иначе раздувание);
- finalize запрещён без маркёра при непустом tail.

**Не закрыто окно:** `INSERT stage` (tail) успел → краш **до** INSERT маркера.

| Состояние | Поведение по v2 | Дефект |
|---|---|---|
| stage += tail, маркера нет | finalize → `error` (вечный блок сущности) | такт не зелёный без ручной чистки stage |
| resume зовёт tail снова | второй INSERT тех же строк | **раздувание stage** (план сам это называет, но не лечит) |
| маркер есть, finalize упал | resume skip tail — ок | — |

v2 **констатирует** риск раздувания как мотив маркера, но **не специфицирует**
идемпотентный повтор: например `DELETE FROM tmp3_pdoc_stage WHERE src_table=$1 AND … keyvals ∈ tail` **перед** каждым `p_doc_tail`, или один transaction «tail+marker», или
маркер = «хвост уже отражён в stage» проверяемый запросом покрытия, а не отдельной
таблицей с дыркой.

Без этого resume после mid-tail — либо вечный STOP, либо п.13/ложный stage_rows (при
ослаблении гейта). **Провал живучести этапа 2**, переработка §2.3 обязательна.

### Н3 (усиление П1). Приёмка зависит от membership `tmp3_build`

См. §1. При apply-stop и пустом changed списке сухой №0 / такт №1 могут **не** собрать
realiz — multiset §3.4 бессмыслен или сравнивает старое. Предусловие не записано.

### Н4 (мелочь C1). «Стейдж монолита» в §3.4

Монолит пишет в `tmp3_corpus`, не в `tmp3_pdoc_stage` (`:1577` vs `:1821`). Формулировка
«multiset стейджа» остаётся неточной; эталон должен быть с `tmp3_corpus` после finalize.
Не шоу-стоппер, но исполнитель может сверять не ту таблицу.
