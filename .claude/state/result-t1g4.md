- **Во время №0** старый `tmp3_run` (v10) жив до `:2730`. Это прежнее устройство
  файла, не регрессия X3.
- **Merge** (`corpus_merge.sql:81-94`) при `tmp3_run` моложе 6 ч **не** режет по
  возрасту; защита от «чужого» стейджа в этом окне — операционная (план §3.4:
  mismatch → merge не зовём) + прочие гварды merge. Частичный обрыв №0 + случайный
  merge в окне <6 ч — **тот же** принятый класс риска, что и до бампа; v8c его не
  усиливает отдельно от любого fresh-rebuild.
- После успешного конца №0 `tmp3_run` обновляется → штатная свежесть для юнита №1 /
  merge.

**Вердикт по п.2: согласовано. Блокера нет.** (Операционно: эталон §3.4 и бэкап
векторов — до старта №0; merge не звать, пока multiset не зелёный.)

## 3. `memory_limit` / `error()` — позиция и пути обхода

| Вопрос | Ответ |
|---|---|
| Где в файле? | `corpus_merge.sql:8-57` — сразу после `\set ON_ERROR_STOP` / `partial_rebuild`, **до** §0 проверок (`:68+`), unmatched, гвардов, MERGE |
| До первого тяжёлого statement? | **ДА.** Первое чтение корпуса/анти-джойны — после SET |
| `error()` на неизвестную единицу | внутри CASE формулы (`:21-22`), до `\gset`/`SET`; при срабатывании `\gset`/SET не выполняются, `ON_ERROR_STOP` валит файл |
| Путь, где формула не выполняется? | **Нет.** Нет `\if` / early `RETURN` / условного пропуска. Единственный «не выполнить» — не запустить файл / оборвать сессию до строки 10 |

Штатный `current_setting` → `N.N GiB` проходит whitelist (`gib`). Пути обхода SET
в продуктовом запуске `psql -f corpus_merge.sql` нет.
