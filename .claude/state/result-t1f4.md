## 1. §2.1 — явная спека dup-блока; приёмка в продукт?

**Внесена.** Закрывает E4-Д1: два прочтения DELETE-каскада больше невозможны —
V5 и mono разведены поимённо, порядок гейтов одной цепочкой.

**В продукт приёмочного не тянет.** В §2.1 нет имён сущностей, нет md5/чисел окна,
нет эталонов 74 982. Только генерические `nrows` / `collision_rows` / `chunk_cells`
и поведение SQL в `corpus_build.sql`. Имена `document_реализациятмц` /
`accumulationregister_…` живут только в §3.4 (этап 3 «выкат и приёмка»).
§0.2 / §8: приёмка ≠ продукт — соблюдено.

Замок M2 (§2.5) ссылается на форму гейта §2.1, не на эталон окна — ок для п.0.

## 2. §3.5 — векторные критерии; ослабление «вектора не теряются»?

### Что изменилось относительно v3 / E4-дыры П1

| Было (v3 / E4-критика) | Стало (v4) |
|---|---|
| `векторов_умрёт=0` как критерий зелёного | (а) **отчёт**, ожидание ≈ класс законного дрейфа |
| anti-join двусмыслен (ключ vs emb) | (б) дырка **только** живой ключ + `emb IS NULL` → 0; «только ключ» запрещено |
| departed молчали в «0 дыр» или ломали зелёный | (г) departed — **отчёт**, ≈647; сверх — разбор |
| контракт §0.3 «допуск потери = 0» без уточнения | §0.3: «0 дырок **на живых ключах**» ↔ §3.5 |

### Ослабляет ли контракт?

**Нет — сужает приёмку к реальной потере, не к отражению 1С.**

П1 E4 (живой ключ, `emb` умер, такт зелёный) **закрыт**: (б) прямо ловит
`emb IS NULL` на ключе, оставшемся в `search_corpus`, после полного такта incl.
шаг 5. Чтение A («только ключ») запрещено одной фразой.

Нюанс относительно **буквальной** формулы E4 («нет пары … с emb IS NOT NULL» =
дыра и при отсутствии ключа): v4 **намеренно** выносит выбывшие ключи в (г)
отчёт — это вариант (2) из E2, согласованный с фактом дрейфа §3.4 (637+10
выбыло из‑за смены `row_key` при перепроведении). Это не дыра исполнения E4,
а разрешение противоречия «зелёный путь при churn».

### «Законное выбытие» vs TARGET

| Пункт | Чтение |
|---|---|
| п.13 | Полнота = всё, **что есть в 1С**. Ключ ушёл вместе со сменой `row_key`/`doc` в источнике — старый ключ в корпусе **не должен** оставаться; это отражение данных, не молчаливая потеря. Молчаливая потеря = живой ключ без вектора / без строки при наличии в 1С — ловится (б) + гварды. |
| п.17 | Свежесть: отработать изменения, не держать мёртвые отпечатки. |
| §0.3 плана | «row_key/content_hash существующих строк не меняются (v10 №1)» — про **стабильные** строки; дрейф §3.4 как раз фиксирует, что часть ключей **перестала существовать** (sha1(doc) сменился). Согласовано. |
| п.12 | Не про вектора корпуса напрямую; догадок в критерии нет. |
| п.19/20 | Критерии — SQL-сверки оркестратора; продукт по-прежнему SQL в движке. `MERGE_VECTOR_LOSS_BYPASS` запрещён (§8). |

**Вердикт:** законное выбытие при изменении данных в 1С — **допустимо** и **не
ослабляет** «вектора не теряются» в смысле §0.3 v4 (0 дырок на живых ключах).
Ослаблением было бы оставить «только ключ» или снять (б) — этого нет.

Остаток (не блокер F4): `count(emb)≥…` по-прежнему smoke (E4-П1/П2); доказательство
п.13 по векторам держит (б), не пол. Опциональный match `content_hash` из E4
не внесён — для зелёного после шага 5 не обязателен.

## 3. §3.4 — эталон + дрейф-факты; числа только в приёмке?

**ДА.** §3.4 целиком под «Этап 3 — выкат и приёмка». Числа (74 982 / md5,
78 733, дрейф 637/10/554, «до» 74 785) и имена двух сущностей — артефакты
оркестратора этой выкатной приёмки.

§8 явно: «числа §3.4/3.5 — только приёмочные артефакты оркестратора, не в коде».
Этапы 1–2 (§1.x / §2.x) имён и абсолютных эталонов окна не содержат.
п.0 («из коробки», без подгонки под базу в продукте) — **соблюдён**.

Дрейф-абзац — обоснование переопределения §3.5, не инструкция в продукт.
