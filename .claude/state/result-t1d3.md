## 1. Закрытие правок C3 в v2

### 1.1 Pre-merge барьер / сухой такт №0 (§3.4)

**Требование C3:** сверка multiset стейджа ДО первого MERGE; mismatch →
`corpus_merge.sql` не звать; замок 2.5 не заменяет.

**В v2:** §3.4 — такт №0: `psql -f corpus_build.sql` → md5
`(content_hash||'|'||row_key)` по двум сущностям vs эталон монолита;
«**mismatch → merge не зовём**»; M2 обязан был поймать раньше.

**Закрывает 1.1 полностью?** По смыслу — **да**: до боевого merge на окне
есть явный барьер и запрет звать merge при расхождении. Ослабление относительно
буквы C3: сверка идёт по **сухому** прогону, а не по стейджу **того же** юнит-
такта №1 непосредственно перед merge. Между №0 и merge №1 — полная пересборка
юнитом (§3.5). При стопнутом apply (§3.4) и детерминизме ключей это
приемлемо; post-merge в §3.5 ещё раз сверяет multiset уже в `search_corpus`.
Буквального «build→барьер→merge» внутри одного юнит-прогона нет.

**Вердикт: ЗАКРЫТО** (с оговоркой про один прогон между сверкой и merge).

## 2. Новые дыры v2

### (а) Сухой такт №0 → юнит №1 перезаписывает tmp3_corpus

По коду `corpus_build.sql` / `build.sh`:

- `corpus_built_ts` пишет **только** `build.sh` после удачного merge
  (`build.sh:339–342`). Сухой `psql -f corpus_build.sql` её **не трогает**.
- Боевой `search_corpus` / emb сухой прогон **не пишет** (merge не зовётся).
- В конце успешного build: `tmp3_run` обновляется (`:2376`); progress/stage
  сущностей, попавших в `tmp3_corpus`, чистятся (`:2211–2216`).
- Юнит №1: новый `build_sql_hash` ≠ note в `search_quality` → `SKIP_BUILD=0`
  (`build.sh:253–288`) → полная пересборка; при свежем `tmp3_run` (<6 ч) и
  пустом progress режим resume **выключен** (`:1536–1538`, `:1559`) →
  `DELETE FROM tmp3_corpus` целиком → чистый прогон.

Побочные записи сухого прогона (`search_quality` pdoc_*/refmap_*,
`search_pdoc_formula`, `search_refcols`) юнит перезапишет; на вектора не
влияют.

**Риск края:** оборванный №0 (без нового `tmp3_run`) + старый `tmp3_run` старше
6 ч + ненулевой progress → юнит может войти в **resume** на полусборке сухого.
План не требует явной зачистки progress/stage/tail между №0(fail) и №1.

**Вердикт по (а):** успешный №0 **не портит** `corpus_built_ts` / marks успеха /
emb. Дыра только на **аварийном** №0 — дописать «перед №1 при сорванном №0:
сброс progress/stage/tail_done или FORCE полного такта». Для векторов при
fail-closed merge по `tmp3_run` — умеренно.

### (б) Маркер `tmp3_pdoc_tail_done`

План §2.3: таблица по имени `tmp3_*` → как и прочие, **обычная** (переживает
рестарт; см. `corpus_merge.sql:19–21`). Это нужно для resume.

**Не сказано:**
1. сброс при свежем такте (`on_=false`, рядом с `:1561–1567`);
2. сброс при смене формулы (рядом с `:1445–1452`) — formula **не** включает
   текст tail-SQL, правка хвоста формулу **не** сдвинет;
3. сброс после успешного finalize / попадания сущности в `tmp3_corpus`
   (рядом с `:2215–2216`);
4. что делать после правки tail-кода при живом маркере.

Сценарий «правка tail → повтор»: stale `tail_done` → skip `p_doc_tail` →
stage без хвоста → при §2.4 `stage_rows = nrows` → **error**, merge не
зовётся (`tmp3_run` не обновится). Вектора **не** теряются молча, но сущность
**залипает** до ручной зачистки — ровно вопрос C3 «не блокирует ли повтор».

**Вердикт по (б): ДЫРА ПЛАНА.** Обязательная правка v3: lifecycle маркера =
создать IF NOT EXISTS + удалять вместе с progress/stage на fresh/formula/
после finalize в corpus; после смены tail-кода без сдвига formula — тот же
сброс (или включать отпечаток tail в formula / отдельный stamp).

### (в) Такт №2 сразу за №1 / SKIP / таймеры

После зелёного №1: `corpus_built_ts` свежий; apply стопнут → `mart_changed_ts`
не растёт; тот же SQL → `SKIP_BUILD=1` → build+merge не зовутся → DELETE нет.
Это согласовано с кодом и с C3-1.4. §3.6 требует разобрать, если SKIP не
сработал, **до** таймеров.

Порядок в плане: §3.5 → §3.6 → §3.7 (таймеры). §3.4 держит apply стопнутым
«до конца приёмки». Явной фразы «включать оба таймера **только после**
зелёного №2; apply не раньше pipeline / не между №1 и №2» нет — порядок
следует из нумерации и §3.4.

Риск лишнего полного merge: только если apply (или FORCE / смена SQL)
включили **до** №2. Тогда SKIP=0 — полный merge; при эквивалентном multiset
emb не жжётся (`corpus_merge` unless bmap), но критерий «минуты» ломается.

**Вердикт по (в):** для стопнутого apply — **ок**. Порядок включения описан
слабо; одна явная строка в §3.7 закрыла бы вопрос C3.
