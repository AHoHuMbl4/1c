## 1. Эталон §3.4 (D1-дыра №1)

### 1.1 Условная ветка «keyed→sha1, без fold» — что говорит код

В `p_doc` (:1576-1817):

- `fold.on_ ⇔ key_cols = ['Ref_Key']` (:1588);
- после `GROUP BY rid` одна строка на физическую строку витрины;
- `QUALIFY NOT (SELECT on_ FROM fold) OR row_number() … = 1` (:1815-1817):
  при **fold выключен** первое условие истинно → **QUALIFY не отбрасывает
  никого**; при **fold включён** — одна строка на `(src_table, row_key)`.

Следствие: **если** сущность реально non-fold (или все `row_key` уникальны),
multiset финального `tmp3_corpus` на count = nrows витрины корректен. Монолит
пишет сразу в `tmp3_corpus`, не в `tmp3_pdoc_stage` (:1576-1577).

### 1.2 Применима ли эта ветка к `document_реализациятмц`?

**Из кода + артефактов репо — нет оснований принять «без fold / 1:1».**

| Источник | Что говорит |
|---|---|
| A2 (`result-t1a2.md` §4.6), prompt-t1a2 | витрина 74 982 → корпус **74 785**; разрыв = **fold/QUALIFY** |
| C1 (`result-t1c1.md` §4.1) | документ с `key_cols=['Ref_Key']` → QUALIFY схлопывает; эталон корпуса **74 785 / 71947efe…** |
| `takt-baseline.txt` | `74785\|71947efec4bebbc2eac4727b51694523\|…` |
| `activeContext` (~20:30 UTC) | монолит `p_doc('document_реализациятмц')` **ещё идёт** с 14:38 |
| v3 §3.4 | «замер 02.09 20:04-20:52»: витрина==«стейдж» 1:1; A2 опровергнут |

Артефакта замера (SQL/tsv/md5-файл с `57ad85de…`) в `/srv/1c` **нет**. Окно
20:04–20:52 пересекается с незавершённым монолитом — снять финальный
`tmp3_corpus` этой сущности после QUALIFY в это время нельзя было штатно.
«0 строк с `|`» / sha1-форма ключа (см. также `result-drev-2.md`) **не
доказывает** `fold.off`: GUID `Ref_Key` тоже без пайпов; fold смотрит на
`key_cols`, не на наличие `|` в значении. При fold.on_ QUALIFY режет дубли
`row_key` даже если ключ — sha1(doc).

Вывод: рассуждение v3 («построчная → QUALIFY не схлопывает → эталон 74 982»)
**не следует из кода** для этой сущности; оно **противоречит** канону в репо
и прежним аудитам. Живой замер без артефакта и при идущем монолите
опровержением A2 не считается.

### 1.3 Остались ли формулировки, ведущие не к той таблице/числу?

**Да.**

1. §3.4: «витрина = **стейдж монолита** (1:1…)» — монолитный `p_doc` пишет в
   **`tmp3_corpus`** с QUALIFY внутри INSERT; `tmp3_pdoc_stage` на этом пути
   не используется. Термин «стейдж» в проекте (C3) = pre-merge `tmp3_corpus`,
   но фраза «витрина == стейдж» при count витрины **маскирует** возможный
   QUALIFY-разрыв и провоцирует сверять count витрины с эталоном корпуса.
2. §3.4 закрепляет приёмку **74 982 / 57ad85de…** как эталон «финального
   `tmp3_corpus` (после finalize)» — при верном fold-результате ~74 785 это
   ложный FAIL (или давление ослабить QUALIFY).
3. §3.5: multiset в **`search_corpus` == §3.4** — тащит то же 74 982 после
   merge.
4. «до»-корпус 74 785 / 71947efe… как «отпечаток перехода» — полезно, но не
   снимает пункт 2–3: исполнитель обязан зелёным считать **новый** эталон 74 982.

Явное «НЕ сырой stage» / «emb не в multiset» — ок (дыра C1 про emb закрыта).

**Вердикт п.1: НЕ ЗАКРЫТО.** Условная логика non-fold верна; применение к

## 2. Хвост+маркер атомарны + жизненный цикл (D1-дыра №2)

### 2.1 `\gexec` + многооператорная строка

Текущий диспетчер (:2179-2209) гоняет **однооператорные** строки на `\gexec`
при `\set ON_ERROR_STOP on` (:2178). План §2.3 предлагает одну ячейку:

`BEGIN; EXECUTE p_doc_tail(…); INSERT … tail_done …; COMMIT`

Доки SereneDB (Multi-Statement Transactions): несколько statements в одной
подаче = одна (неявная) транзакция; при ошибке предшествующее откатывается.
Явный `BEGIN`…`COMMIT` — штатный путь той же главы. Откат и stage-INSERT, и
маркер — **да**, окна «stage есть, маркера нет» нет.

Оговорки (не блокеры при одной пробе №0):

- в доках канон — `BEGIN TRANSACTION;`, не голый `BEGIN;` — лучше писать как
  в доках;
- в дереве `corpus_build.sql` такого `\gexec`-паттерна ещё нет — один dry-run
  на пустой/фикстурной сущности закрывает клиентский край psql;
- при `ON_ERROR_STOP on` ошибка mid-batch валит файл — согласовано с «неполный
  unmatched/stage не идёт дальше».

### 2.2 Жизненный цикл

v3 §2.3 явно: wipe `tmp3_pdoc_tail` / `_done` симметрично progress/stage —

| Точка | Код-якорь | В плане |
|---|---|---|
| свежий такт `NOT on_` | :1561-1567 | да |
| смена formula | :1445-1452 | да |
| после успешного finalize | :2211-2216 | да |
| атомарность tail+marker | — | да (BEGIN…COMMIT) |
| finalize без маркера при непустом tail | — | error() |

Остаётся **процессный** край (D3): formula **не** хеширует тело tail-SQL;
v3 требует при будущей правке tail сдвигать formula вручную — это сказано,
автоматикой не стало. Для исполнения пакета достаточно (fail-closed через
`stage_rows = nrows` + error без маркера).

**Вердикт п.2: ЗАКРЫТО** (с рекомендацией `BEGIN TRANSACTION` + одна проба
\gexec). Дыра D1-№2 снята.
