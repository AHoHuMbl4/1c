## Провалы найдены

### П1. Окно выката: смена hash `corpus_build.sql` → полная пересборка ВСЕХ сущностей (не оценена)

**Доказательство.** `build.sh:241-279`: SKIP_BUILD=1 только если одновременно корпус непуст, витрина не новее `corpus_built_ts`, **и** `build_sql_hash` = md5(`corpus_build.sql`+`poc_load_entity.py`). Любая правка `corpus_build.sql` (этап 2 плана) ломает равенство → первый такт после выката **обязан** гнать полный `corpus_build.sql` по всему `tmp3_build`, не «только реализациятмц».

**План.** §5.4 обещает «Такт №1 … минуты (реализациятмц чанками+хвостом, как соседние 321k/208k/191k за ~6 мин)». Соседи — уже чанкуемые сущности **внутри текущего** такта; это не оценка «с нуля все сущности после смены SQL». В плане нет слова `build_sql_hash` / SKIP_BUILD / «полный rebuild 351».

**Следствие.** Контракт §0.1 («такт = минуты: первая сборка и регулярный») и приёмка §5.4 смешивают:
- (а) ускорение одной проблемной сущности после V5, и
- (б) wall-time первого такта после выката этапа 2.

(б) = полная пересборка корпуса (~1.66M строк, все крупные сущности снова через chunk-path с pre-pass×N) + merge. Это может быть **десятки минут / час+**, даже если realiz сам стал «как сосед». Сюрприз для владельца и ложный критерий «зелёный за минуты».

**Вердикт:** провал планирования окна выката; пункт §5.4 и контракт скорости требуют переработки (явная оценка полной пересборки + критерий приёмки «после hash-bump»).

### П2. Скорость после этапа 2: «минуты» для realiz — правдоподобно, но не доказано; pre-pass×N план игнорирует

**Счёт порций (код + якорь плана v10).**

| Величина | Откуда | Число |
|---|---|---|
| nrows | план/приёмка | 74 982 |
| ncols | A2 / v10 | ~126 |
| chunk_cells | `plan-takt-fix-v10.md` A.1 (окно) | 626 874 |
| chunk_rows | `floor(chunk_cells/ncols)` = `corpus_build.sql:1456` | **4 975** |
| порций без хвоста | `ceil(74982/4975)` | **16** |
| коллизии | `result-drev3r-1` R1 / A2 | **2 776** с keyvals `"\|"` |
| уникальных после V5 | ≈ 74 982 − 2 776 | ≈ **72 206** → ~15 порций + 1 хвост |

**Pre-pass (A2 «потеря №1» / B1 3e — подтверждено кодом).** В `p_doc_chunk` (`1843-1870`) CTE `raw`/`numbered`/`sort_cells`/`kv` читают **всю** `query_table($1)` и считают keyvals по **каждой** строке; фильтр порции — только в `src_f` (`1877-1880`). Каждый `EXECUTE p_doc_chunk` и (по плану 2.2) каждый `p_doc_tail` платит полный key-UNPIVOT+`string_agg` на 75k строк.

После этапа 2 на realiz: **~16 (или 15+1) полных pre-pass'ов** + тяжёлый UNPIVOT×126 только на отфильтрованных строках.

Доминирует ли pre-pass? На **этой** сущности — скорее нет как единственный блокер «часов»:
- тяжёлая часть по-прежнему ~nrows×ncols ячеек, но **разрезанная** (класс A1/A2: unspillable `string_agg` на меньших группах);
- те же pre-pass×N уже платят соседи 321k/208k/191k и укладываются в ~6 мин (A2 §0.4, план §5.4).

Значит утверждение «realiz станет минутами **относительно текущего 5ч монолита**» **не опровергнуто** кодом для окновского размера. Но план **не считает** 16×full scan и выдаёт «минуты» как факт приёмки. Для контракта «из коробки на невиданной базе» (п.0) сущность с nrows≫75k и ncols≫126 получит O(порции)×full keyvals — R5 (`result-drev3r-1`) остаётся.

**V3 в обязательной части?**
- Для узкой цели «снять 5ч с realiz на okna» — V3 **не обязателен** как единственный блокер (соседи уже минуты без V3).
- Для контракта §0.1 «первая сборка = минуты» на произвольной базе + после hash-bump полной пересборки всех чанкуемых — V3 (материализация keyvals/`pos` один раз, без UNPIVOT всей таблицы на каждый EXECUTE) **должен быть в обязательном контуре или явно сужать контракт**. Сейчас V3 отсутствует и в этапах, и в §8 «чего не делаем» — молчаливый пробел относительно рекомендации A2 §6 («параллельно V3»).

**Вердикт:** провал не «этап 2 бесполезен», а «обещание минут без учёта pre-pass и без V3/сужения контракта». Требует правки плана (цифры + место V3), не косметики.

### П3. Хвост без гейта размера → молчаливый возврат монолита

**Механика плана 2.1–2.2.** Коллизионные keyvals → `tmp3_pdoc_tail`; из order удаляются; `p_doc_tail` = копия chunk с фильтром `keyvals IN (SELECT … FROM tmp3_pdoc_tail)`. Все строки группы в **одном** батче → размножение `IN` между порциями невозможно (это плюс V5).

**Провал.** Если коллизии не «2.7k из 75k», а «почти все строки в 1–2 группах keyvals» (пустой ключ у всей таблицы, массовый одинаковый surrogate и т.п.):
- order после DELETE почти пуст → порции пишут ~0 строк;
- `p_doc_tail` тянет **всю** таблицу одним statement ≈ текущий монолит `p_doc` (те же ~nrows×ncols + unspillable agg);
- плюс зря оплаченные пустые chunk EXECUTE и pre-pass'ы.

План это **допускает молча**: нет порога `tail_rows`, нет fallback (остаться на mono явно / резать хвост по `pos` / STOP с числом в `search_quality`). A2 V5 сам оговаривал риск «забыть хвост»; риск «хвост = вся таблица» не разобран. На okna realiz хвост мал (2776) — но решение позиционируется как **генерик** (план §8, п.0), не как патч одной базы.

**Вердикт:** провал живучести на невиданной базе. Нужен обязательный гейт размера хвоста + видимый fallback/диагностика. Без этого этап 2 не закрывает контракт п.0.

### П4. Эквивалентность фильтра хвоста и NULL keyvals — для realiz ок; дыра в спецификации «DISTINCT keyvals»

**К чему фильтр сейчас.** `1877-1880`: после `GROUP BY rn` в `kv`, фильтр `kv.keyvals IN (SELECT o.keyvals … pos BETWEEN …)`. Селектор — **значение** keyvals строки, не pos. Коллизия `"|"×2776` затягивает все 2776 в каждую порцию, где есть хоть один такой pos (R2: 7.7M).

**Хвост по плану.** Тот же `kv`, фильтр по множеству коллизионных keyvals один раз → в батч попадут все строки с этими значениями (2776 строк, не 2776 групп). Эквивалентность «одна строка витрины → один батч» для коллизий — да, **если** хвост один.

**NULL / пустые ключи (код, не гипотеза).**

```1492:1493:ubuntu/serenedb/corpus_build.sql
|| 'agg AS (SELECT pos, string_agg(CASE WHEN val IS NULL THEN ''∅'' '
|| 'ELSE replace(val::VARCHAR, ''|'', ''\\|'') END, ''|'' ORDER BY sort_ord) AS keyvals '
```

Зеркало в chunk: `1864-1866` — `CASE WHEN val IS NULL THEN '∅'`. Ячейка NULL **не** даёт SQL NULL в `string_agg`; пустые строки дают сегменты `''` → живой keyvals `"|"`, не NULL. `NULL IN (…)` отсечения для этого класса нет.

Риск потери: строка **без** строки в `kv`/`order` (нет key-колонок / `sort_ord`). Исторически ловится dup-гейтом `count(*) <> e.nrows` (`1529-1530`). План, заменяя «снять чанки» на «хвост», обязан сохранить инвариант: строки вне order+хвост → STOP (иначе п.13). В плане 2.4 усилен `done_rows==nrows`, но не сказано явно про `order∪tail` покрытие vs nrows **до** диспетчера.

**Спека `tmp3_pdoc_tail(tbl, keyvals)`.** Если INSERT хвоста пишет **каждую** collизионную строку order (не DISTINCT keyvals), фильтр `IN` всё равно корректен, таблица раздувается. Если DISTINCT — ок. План не фиксирует. Мелочь, но замок M2 должен зафиксировать.

**Вердикт:** для класса `"|"` / `∅` провала эквивалентности нет; пробел спецификации покрытия order∪tail и формы tail — уточнение **с усилением гейта**, само по себе не «НЕТ», но связано с П3.

### П5. Резка unmatched (INSERT) — схема «как сейчас руками» + отсутствие явного wipe

**Сейчас.** `corpus_merge.sql:162-199` — `CREATE OR REPLACE TABLE tmp3_merge_unmatched AS SELECT c.src_table, c.row_key …` (схема = вывод SELECT).

**Потребители** (все совместимы с парой колонок): `edited_delta` `:154-160`, `ent_guard` `:216`, `collapse_rec` `:238`, `delta` `:285`, гейт удаления `:411` — везде `src_table`/`row_key`.

**Риски плана 1.1.**
1. «`CREATE TABLE … (schema как сейчас)` руками» — дрейф типов/NULL vs CTAS при следующем изменении SELECT; образец в том же файле безопаснее: `CREATE OR REPLACE TABLE tmp3_merge_collapse_dead (src_table VARCHAR, dead BIGINT);` + INSERT (`:250-261`).
2. План **не пишет** обязательный `CREATE OR REPLACE`/TRUNCATE перед `\gexec`. `tmp3_*` персистентны (`corpus_merge` комментарий `:19-21`; B3). INSERT без очистки → накопление строк с прошлого такта / прошлой сущности → ложный `уйдёт`, ложный vector/delete гейт.
3. Порядок 1.2 (edited_delta после unmatched) — верный фикс Д5; но edited_delta на **грязном** unmatched усугубляет (2).

**Вердикт:** провал спецификации этапа 1 (wipe + схема из того же SELECT / OR REPLACE empty). Чинится переработкой пунктов 1.1, не «надеемся на исполнителя».

### П6. Дополнительно (усиливает П1–П3, не отдельные шоу-стопперы)

- **Дыры pos после DELETE из order.** План прав: `BETWEEN lo AND hi` по сохранённым pos покрывает оставшиеся уникальные строки; дыры не ломают полноту. Но `p_doc_finalize` chk (`2051-2058`, `2200-2207`) смотрит сумму `(hi-lo+1)==nrows` по **расписанию** chunks, а не число строк order. Полнота stage после хвоста держится только на 2.4 + том, что tail реально вызван. Забыть tail в диспетчере → stage_rows < nrows при усиленном гейте (хорошо) или при fold-слабости (плохо, пока 2.4 не в коде).
- **`memory_limit` в merge (1.3).** B4/A1: не лечит `string_agg`; для anti-join unmatched уместен. План не выдаёт его за защиту монолита — ок. Не провал.
- **Этап 1 alone не даёт «кратно быстрее»** сборку realiz — только переживание merge. См. альтернативы.
