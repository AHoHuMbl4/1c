## Двусмысленности

Читая план как исполнитель этапов 1–2: **большую часть** можно собрать по
ссылкам на строки, но **три места всё ещё требуют домысла**. Без них план
не «исполняемый вслепую».

### Д1. Разветвление dup-гейта (§2.1) vs нынешний DELETE-каскад

Сейчас `:1524-1534` кладёт сущность в `tmp3_pdoc_dup` и **целиком** снимает её
с `order` / `chunks` / `formula` / `entity` → монолит `p_doc`.

V5 требует другого: коллизионные `keyvals` → `tmp3_pdoc_tail`, **остальное
остаётся в чанковании**. План описывает исходы (а)–(г), но **не говорит
явно**:
- при V5 сущность **не** удаляется из `tmp3_pdoc_chunks` / `tmp3_pdoc_formula`;
- из `tmp3_pdoc_order` удаляются **только** строки с `keyvals ∈` коллизионному
  множеству, а не `DELETE … WHERE tbl IN (dup)`.

Два прочтения:
1. «переписать блок 1524–1534 под ветки» (верное);
2. «оставить каскад как был + отдельно наполнить tail» (ломает V5: сущности
   нет в диспетчере порций).

Без одной-двух строк «keep in chunks / partial DELETE order» исполнитель
угадывает структуру.

### Д2. `SET memory_limit` (§1.3) — единицы результата

«Снять `current_setting`, `floor(байты*0.55)`, SET через `\gset`» — ясно про
источник и долю. Неясно **в каком виде** писать SET:
- число байт (`SET memory_limit=123456789`);
- строка с единицей (`'6500MB'` / `'6.5GiB'`), как в `box_tune.sh` и тестах.

В дереве живые примеры — только строковые литералы с суффиксом. Домысел
формата обязателен; неверный формат = тихий no-op или ошибка сессии.

### Д3. Семантика «анти-джойн к бэкапу → 0 дыр» (§3.5)

Бэкап: `(src_table, row_key, content_hash, emb) WHERE emb IS NOT NULL`.
«0 дыр» можно прочесть как:
- **A:** нет ключей бэкапа, отсутствующих в `search_corpus` (ключ жив);
- **B:** нет ключей бэкапа, у которых в живом корпусе нет **непустого** `emb`
  (и/или `content_hash` совпал).

При A такт зелёный, а вектор уже NULL при живом `row_key` — см. «Дыры
приёмки».

### Мелкие (не блокеры сами по себе)

| Место | Два прочтения |
|---|---|
| §1.1 «тело :162-199 дословно» | SELECT-предикаты vs включая обёртку `CREATE OR REPLACE` (очевидно нужен `INSERT…SELECT`, но граница «дословно» спорна) |
| §2.1 (а)+(б) одновременно | сначала оценить размер хвоста → mono; или сначала V5, потом oversize-откат. Порядок гейтов не зафиксирован одной фразой |

## Дыры приёмки

Вопрос 3: путь, где такт «зелёный», а вектора/строки потеряны молча — **да,
вижу**.

### П1. Ключ жив, `emb` умер (главная)

§3.5: `count(emb) ≥ 1 657 724` + `векторов_умрёт = 0` + anti-join к бэкапу.

- `векторов_умрёт` считает только сущности в `tmp3_corpus` (пересборка)
  (`corpus_merge.sql:589-656`). Сущность вне scope build не в бюджете.
- Anti-join при чтении **A** (только ключ): строка из бэкапа есть в
  `search_corpus`, `emb IS NULL` → дыры по ключу нет.
- Глобальный пол `count(emb)` закрывается **новыми** эмбеддингами других
  строк (дрейф витрины 74 785→74 982 уже в плане) или добором `embed_missing`.

Итог: старый вектор на конкретном `(src_table,row_key)` исчез, отчёт зелёный.
Контракт §0.3 «допуск потери = 0» формально не пойман приёмкой, если anti-join
не требует `emb IS NOT NULL` (и лучше — совпадения `content_hash`).

### П2. Полы по всему корпусу, multiset — две сущности

`count(*) ≥ 1 665 427` не ловит обмен: −N в сущности X, +N в Y.
Multiset жёсткий только для `document_реализациятмц` и
`accumulationregister_реализациятмц`. Остальные ~пересобранные сущности
держатся гвардами merge и vector-бюджетом; **непересобранные** — ни
multiset, ни vector-бюджет по ним не смотрят. Молчаливая порча вне scope
маловероятна при стопнутом apply, но приёмка этого не доказывает — только
предполагает.

### П3. Бэкап только `emb IS NOT NULL`

Строки без вектора не в §3.3. Их исчезновение не бьёт anti-join и может
не сдвинуть `count(emb)`. Для контракта «вектора» слабее; для п.13 (строки) —
дыра, если полагаться только на глобальный count.

### П4. Окно DELETE→xfer (признано)

§3.5 сам называет риск mid-merge; откат — бэкап. После **успешного** конца
такта приёмка это не маскирует. Это принятый остаточный риск пакета, не
ложный «зелёный» при живом emb-NULL на месте.

### Что приёмка закрывает хорошо

- №0: mismatch → merge не зовём; эталон финального `tmp3_corpus` (не сырой
  stage); apply стопнут.
- collision_rows-форма гейта (запрет DISTINCT) — правильно против класса «|».
- `векторов_умрёт=0` / `vector_loss_gate=0` на пересобранных — сильный стоп
  при честном чтении бюджета.
- №2 + таймеры только после зелёного — не маскирует SKIP.

## Предложения

Ровно две правки в план (больше не раздувать):

1. **§2.1 — одна явная спецификация переписи `:1524-1534`:**  
   V5 = сущность **остаётся** в `chunks`/`formula`/`entity`; из `order`
   удаляются только коллизионные `keyvals`; mono (неполный order / oversize
   хвоста) = нынешний полный каскад DELETE. Порядок гейтов: (в) неполный
   order → mono; иначе посчитать collision set; (б) oversize → mono; иначе
   (а) V5.

2. **§3.5 — усилить anti-join:** дыра := строка бэкапа, для которой в живом
   корпусе нет пары `(src_table,row_key)` **с `emb IS NOT NULL`** (опционально
   жёстче: `content_hash` совпал с бэкапом). Чтение «только ключ» запретить
   одной фразой. Глобальные полы count оставить как smoke, не как доказательство
   п.13.

§1.3 (формат SET) закрывается одной ремаркой «`SET memory_limit='…'` строкой
с той же единицей, что вернул `current_setting`, масштаб 0.55» — можно
вложить в предложение 1 как подпункт, не раздувая список.

Убирать из плана ничего существенного не стал бы: этапы 1∥2, V5 vs V1,
pre-merge барьер №0 — связаны с диагнозом.
