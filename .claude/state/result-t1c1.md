## 1. Этап 1 — резка unmatched по сущностям (§3 / 1.1–1.2)

### 1.1 Эквивалентность множества строк (UNION INSERT ≡ CTAS :162–199)

**Вердикт: ПРИНЯТЬ** — при двух уточнениях в тексте плана (см. ниже).

Текущий фильтр множества сущностей (`corpus_merge.sql:165–166`):

```text
src_table IN (SELECT DISTINCT src_table FROM tmp3_corpus)
AND src_table NOT IN (SELECT src_table FROM tmp3_merge_rewrite_wave)
```

плюс шесть `NOT EXISTS` к `tmp3_corpus` (`:170–198`; вложенный `EXISTS` по `tmp3_key` — внутри 6-го анти, не седьмой; согласуется с Д3 плана и B3).

Замена `IN (…tmp3_corpus)` → `src_table = $1` при диспетчере ровно по множеству «стейдж ∖ rewrite_wave» даёт то же множество строк: партиции по `src_table` дизъюнктны, анти-предикаты не меняются. Порядок строк в таблице не участвует в семантике (дальше — `count` / `EXISTS` / `JOIN`).

**Правки в план (обязательные уточнения, не смена идеи):**

1. **Список для `\gexec` — не `tmp3_merge_ents`.** Таблица `tmp3_merge_ents` создаётся только на `:811` (фаза записи MERGE), **после** гварда. На момент unmatched готовы: `tmp3_corpus`, `tmp3_merge_ent_counts` (`:123–141`), `tmp3_merge_rewrite_wave` (`:143–148`). Канон диспетчера:

   ```sql
   SELECT DISTINCT src_table FROM tmp3_corpus
   WHERE src_table NOT IN (SELECT src_table FROM tmp3_merge_rewrite_wave)
   ```
   (или то же из `tmp3_merge_ent_counts`). Иначе исполнитель возьмёт «ents» слишком рано или включит wave.

2. **Двойной фильтр rewrite_wave.** Если в теле PREPARE остаётся `NOT IN rewrite_wave` (план: «тело дословно, кроме IN→=$1»), а диспетчер уже исключил wave — избыточно, но безопасно. Опасно обратное: диспетчер шире (все сущности стейджа / корпуса), а `NOT IN wave` вырезан из PREPARE → unmatched посчитается для rewrite_wave, а `ent_guard` ждёт «уйдёт := было» без построчного unmatched (`:204–206`). План обязан явно: **либо** фильтр wave только в диспетчере и `$1` из уже отфильтрованного списка, **либо** wave остаётся в PREPARE. Предпочтительно оба (fail-safe).

3. **`DISTINCT` в диспетчере** — обязателен (двойной EXECUTE одной сущности → дубли `(src_table,row_key)` в unmatched → раздувание «уйдёт»).

### 1.2 INSERT-форма vs CTAS — ссылки ниже по файлу

**Вердикт: ПРИНЯТЬ.**

Читатели `tmp3_merge_unmatched` после `:199` (полный перечень по файлу):

| Якорь | Назначение |
|---|---|
| `:216` | `tmp3_merge_ent_guard` (агрегат «уйдёт») |
| `:238` | `tmp3_merge_collapse_rec` |
| `:285` | `tmp3_merge_delta_rec` |
| `:411–419` | глобальный гейт доли удаления |

Никто не зависит от CTAS vs `CREATE …; INSERT…`. Схема таблицы сейчас выводится как `(src_table, row_key)` — в плане нужна явная DDL этих двух колонок + `CREATE OR REPLACE` (пустая) **до** цикла, иначе повторный прогон допишет к старому содержимому.

Паттерн `PREPARE` + `\gexec` уже есть (`p_collapse_dead` `:252–261`) — образец корректен.

Риск частичного `\gexec` при аварии посередине цикла — тот же класс, что у существующих `\gexec` в merge; на эквивалентность «успешного прогона» не влияет. В плане стоит одной фразой: при ошибке mid-loop unmatched неполный → гвард/STOP (fail-closed), не «тихий догон».

### 1.3 Перенос `edited_delta` после unmatched (Д5 / §1.2)

**Вердикт: ПРИНЯТЬ.**

Сейчас `tmp3_merge_edited_delta` (`:154–160`) читает `tmp3_merge_unmatched` **до** его создания (`:162`). `tmp3_*` обычные и переживают рестарт (`:19–21`) → на повторных прогонах дельта считается по **вчерашнему** unmatched; на свежей базе — «нет таблицы».

Другие читатели `edited_delta`: `:218` (`ent_guard`), `:378` (`search_quality`). Оба идут **после** блока unmatched/delta — перенос delta сразу после заполнения unmatched сохраняет порядок относительно них.

Смысл на **первом** прогоне после фикса: вместо падения / устаревших «правок» — расчёт от свежего unmatched. Это исправление дефекта, не смена контракта гварда.

План «путь без „нет таблицы“» — верен.

Занижение лимита даёт controlled OOM / spill движка, не тихую потерю строк. Условие «без литерала гигабайтов, вывод на месте» согласуется с п.0. На эквивалентность unmatched не влияет.

## 2. Этап 2 — хвост коллизий (§4 / 2.1–2.4)

### 2.1 (а) DELETE order по `(tbl,keyvals)` и покрытие порций `pos BETWEEN`

**Вердикт: ИСПРАВИТЬ.**

Механика уникальной части — **верна**:

- `tmp3_pdoc_chunks` режет диапазоны `1..nrows` (`:1465–1469`), не «плотный список pos».
- Фильтр порции — `keyvals IN (SELECT … FROM tmp3_pdoc_order WHERE pos BETWEEN lo AND hi)` (`:1877–1880`).
- После удаления коллизионных keyvals из order каждая оставшаяся строка имеет **уникальный** keyvals → попадает ровно в одну порцию (ту, чей диапазон содержит её `pos`). Дыры в `pos` не дают двойного покрытия и не исключают оставшиеся строки.

**Но dup-гейт ловит два условия** (`:1524–1530`):

```text
count(*) <> count(DISTINCT keyvals)   -- коллизии
OR count(*) <> e.nrows                -- order неполный vs витрина
```

План описывает только первое («keyvals-группы с коллизиями»). Второе сейчас уводит сущность в монолит (`DELETE` chunks/formula/entity `:1531–1534`). Если при неполном order оставить сущность в chunks + tail только по коллизиям — **потеря строк (п.13)** без монолитного спасения.

**Конкретная правка плана:** явно разветвить:

- коллизии keyvals → `tmp3_pdoc_tail` + DELETE этих keyvals из order + **сохранить** chunks;
- `count(order) <> nrows` (и любые иные поломки order) → **оставить текущий mono-путь** (полное снятие chunks / `p_doc`), не V5.

### 2.2 (б) `p_doc_tail` ≡ chunk-тело → stage → finalize

**Вердикт: ПРИНЯТЬ** при явной оговорке в плане.

- `p_doc_chunk` пишет в `tmp3_pdoc_stage` (`:1821`); mid `#sha1`, outer `#N`, fold `QUALIFY` — только в `p_doc_finalize` (`:2088–2113`). Копия тела chunk с фильтром `keyvals IN (SELECT … FROM tmp3_pdoc_tail WHERE tbl=$1)` совместима с finalize.
- Один батч на все коллизионные keyvals сущности → размножение через `IN` по порциям невозможно по построению (одна порция-хвост).
- Зеркало «три тела» (p_doc / chunk / tail) нужно держать замком M2: монолит пишет в `tmp3_corpus` сразу с mid/outer/QUALIFY (`:1576–1817`); путь chunk+tail — через finalize. Эквивалентность — по **финальному** `tmp3_corpus`, не по сырому stage.

### 2.3 (в) Прогресс / formula / resume и «учёт хвоста в done_rows»

**Вердикт: ИСПРАВИТЬ** (формулировка плана сейчас опасна).

Факт кода:

- `done_rows` в диспетчере (`:2200–2207`) = `sum(hi - lo + 1)` по **ширинам порций**, не по числу строк в order/stage.
- При сохранении chunks на полном `1..nrows` после всех порций `done_rows = nrows` **уже без хвоста**.
- Formula/resume (`:1434–1452`) от метода порядка `key_order` + `chunk_cells`/`ncols` — V5 их не обязан менять: метод порядка тот же.

Если «расширить прогресс, учитывая хвостовые строки в done_rows», прибавив `count(tail)` к уже полному `sum(hi-lo+1)`, равенство `done_rows = nrows` **сломается** (done_rows > nrows) → finalize не вызовется или chk (`:2049–2059`) начнёт врать.

**Конкретная правка:**

- Не включать хвост в формулу `done_rows`.
- Хвост: отдельный `EXECUTE p_doc_tail` **до** `p_doc_finalize` для `tbl ∈ tmp3_pdoc_tail`; полнота хвоста ловится `stage_rows` (см. 2.4), не `done_rows`.
- Formula/resume не трогать — это совместимо с «без смены formula».
- В диспетчере явно указать точку: tail один раз на сущность (не на порцию); при resume — если stage уже содержит хвост / маркер — не дублировать INSERT (иначе размножение на докатке). Сейчас план этого не специфицирует → **добавить**.

### 2.4 (г) stage_gate / `done_rows == nrows`

**Вердикт: ИСПРАВИТЬ.**

Сейчас (`:2070–2077`):

- non-fold: `stage_rows = nrows`;
- fold: только `stage_rows > 0` (слабый гейт — B1/A2 верно).

Усиление «для всех путей `done_rows == nrows`» путает два гейта:

- `done_rows == nrows` уже есть в **диспетчере** перед finalize (`:2206–2207`) и дублируется в `chk` finalize через сумму ширин порций.
- Для fold/V5 нужен именно **`stage_rows = nrows`** в `stage_gate` (все строки витрины дошли в stage до QUALIFY), а не подмена на `done_rows`.

Существующие таблицы достаточны: `tmp3_pdoc_stage`, `tmp3_pdoc_progress.nrows`, `tmp3_entity_rows`, `tmp3_pdoc_chunks`.

**Правка:** в §2.4 писать: для fold усилить `stage_gate` до `stage_rows = nrows` (как non-fold); `done_rows` оставить проверкой покрытия порций. Не смешивать.

### 4.2 Шаг 5 embed и multiset

### 4.3 Совместимость нового прогона при неизменной витрине
