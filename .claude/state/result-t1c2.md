## 1. п.0 (суть) — «сработает на невиданной базе без рук?»

**Вердикт: ИСПРАВИТЬ**

### Что уже в порядке
- §2.1–2.3: хвост определяется генерически — `keyvals`-группы с коллизиями (тот же предикат, что dup-гейт :1524–1530). В коде плана нет имён сущностей, порогов «под реализациятмц», спец-ключей. Имена/md5 в §3.4 — только приёмка на окне, не продукт. Это совместимо с п.0, **если** исполнитель не перенесёт их в SQL.
- §1.1: резка unmatched по `src_table` из стейджа минус `rewrite_wave` — тот же фильтр, что сейчас в WHERE (:165–166). Паттерн уже в файле (`p_collapse_dead` + `\gexec`). Универсально.
- §8 явно запрещает env-флаги и литералы под эту базу.

### Дыра: §1.3 memory_limit — конкретики недостаточно
Формулировка «значение выводится на месте: psql `\gset` от запроса к движку/box_tune, БЕЗ литерала гигабайтов» **не закрывает п.0 для исполнителя**:

1. **`box_tune` — shell**, не SQL. Из `corpus_merge.sql` его не вызвать. Ссылка «/box_tune» двусмысленна: исполнитель может (а) вписать литерал с окны, (b) скопировать `memory_limit_first` из чужого прогона, (c) дернуть shell из SQL-файла.
2. Нет **формулы**, сопоставимой с уже принятым паттерном `tmp3_pdoc_cfg` (:1394–1407): `current_setting('memory_limit')` → байты → доля. План ссылается на cookbook «50–60%», но не фиксирует долю, единицу и место SET/RESET.
3. «`SET threads` вниз только на секцию unmatched» — без правила, до какого числа и как вернуть. На чужой коробке с 2 vCPU «вниз» ≠ на 16.

**Правка (обязательная, вписать в план до исполнения):**
```
В начале corpus_merge.sql (один раз на сессию psql -f):
  SET memory_limit = <доля от текущего current_setting('memory_limit')>;
Формула — зеркало corpus_build.tmp3_pdoc_cfg: разобрать единицы (GiB/GB/MiB/MB),
взять floor(mem_bytes * 0.55) (или иная доля из доков, названная в коммите «Доки:»),
выдать через \gset + SET, БЕЗ чтения /proc и БЕЗ box_tune.sh.
threads: либо не трогать в этом пакете, либо SET threads = greatest(1, current/2)
только вокруг \gexec unmatched с явным RESET после. Никакого литерала «70GB»/«8».
```
Пока этого абзаца нет — риск нарушения п.0 при исполнении высокий.

## 2. Решение владельца №10 (простота) — достаточно ли одного этапа 2?

**Вердикт: ПРИНЯТЬ (оба этапа обязательны; «только этап 2» — отвергнуть)**

Логика плана сходится с кодом и диагнозом Д1–Д5; упрощение «оставить только чанки» **ломает живучесть**.

| Отказ от… | Что остаётся сломанным | Почему |
|---|---|---|
| Только этап 2 (чанки+хвост), без этапа 1 | **Д3**: `tmp3_merge_unmatched` — один CTAS, 6 анти-джойнов на весь корпус (`corpus_merge.sql:162–199`). `MERGE_CHUNK_ROWS` режет запись, не гвард (`build.sh:302–337`, merge :740+). | Сборка станет быстрее, но такт снова умрёт на merge → health fail → no_data (Д6). Пик merge **не** падает от меньшего числа порций p_doc: unmatched считает `search_corpus` ⨯ `tmp3_corpus` целиком. |
| Только этап 1 (резка unmatched), без этапа 2 | **Д1**: монолит p_doc на сущности с коллизиями keyvals — часы, не минуты. Контракт §0.1 плана («такт = минуты») не выполнен. | Живучесть merge чинится; скорость первой сборки/полного пересчёта — нет. |
| Только `SET memory_limit` без резки unmatched | Не доказано планом, что 50–60% хватает на 6 хэш-таблиц 1.66M×1.44M при высокой RSS. | Образец в файле уже entity-wise (`p_collapse_dead`). Это минимальное усложнение того же паттерна, не новый механизм. |

**Вывод по №10:** более простой путь «один этап» — ложный. Два этапа чинят **разные** отказы (OOM merge vs монолит build). Оба нужны для контракта «минуты + из коробки живёт». План обязан **явно** записать этот отказ «только этап 2» в §8 (сейчас подразумевается, не сформулирован) — косметика, не блокер сути.

На 10–30× базах этап 1 остаётся нужен: unmatched растёт с корпусом; этап 2 режет только build. «Полная B» (§6) — следующий пакет, верно отложен.

## 5. п.13 — молчаливая потеря строк

**Вердикт: ИСПРАВИТЬ**

| Место риска | Покрытие в плане | Оценка |
|---|---|---|
| Поры unmatched-диспетчера (пропуск сущности / двойной INSERT) | M1: множество unmatched == старой формуле | Достаточно |
| Порядок edited_delta до unmatched (Д5) | §1.2 + M1 «свежий unmatched» | Достаточно |
| DELETE order для хвоста (уникальная строка ушла и из order, и не в tail) | M2: multiset (content_hash, row_key) чанки+хвост == монолит; stage == nrows | Достаточно **в конце**, если M2 обязателен до выката |
| Хвост не вызван / вызван дважды | §2.3 диспетчер + M2 | Нужна явная проверка в M2: сущности с хвостом и без |
| stage_gate слаб для fold | §2.4: done_rows == nrows для ВСЕХ путей | Хорошо; закрывает находку B1 |
| Промежуточный инвариант после DELETE order | **Нет** | Слабое место |

**Правка:** после построения `tmp3_pdoc_tail` и DELETE из order — SQL-гейт fail-closed:
`count(order) + count(строк витрины с keyvals ∈ tail) == nrows` по сущности
(или эквивалент: `count(DISTINCT pos) оставшихся + сумма размеров коллизионных групп == nrows`).
Иначе ошибка в SELECT хвоста молча оставит дыру до finalize; finalize поймает, но гейт у источника дешевле и ближе к п.13 («видно сразу»).

Также в M2 обязать кейс с **непустыми** коллизиями и кейс с пустым keyvals (`"|"`), плюс дыры pos (см. п.6).

## 6. п.12 — догадки / недоказанные допущения

**Вердикт: ИСПРАВИТЬ**

1. **«Дыры в pos не влияют на полноту» (§2.1).** Логика верна *при текущем устройстве*: chunks строятся по `generate_series(1, nrows)` (:1465–1469) **до** dup-гейта; pos в order — `row_number() OVER (ORDER BY…)` (:1479); после DELETE коллизий оставшиеся строки сохраняют pos; `pos BETWEEN lo AND hi` всё ещё накрывает каждую уникальную строку ровно одной порцией. Это не догадка о данных окна, а следствие нумерации. **Но** план не запирает это замком: M2 обязан явно содержать фикстуру, где после удаления хвоста pos **не сплошной** (дыры), и требовать полное покрытие. Без этого исполнитель может «оптимизировать» перенумерацию pos / пересбор chunks после DELETE и сломать инвариант.

2. **Отказ от V1-pos (§7)** — хорошо обоснован (нестабильный `row_number() OVER ()` в chunk :1844 vs order с ORDER BY). Это анти-догадка, в пользу п.13. **ПРИНЯТЬ**.

3. **Приёмка §3.4** с конкретными md5/именами окна — не догадка в продукте, а эталон замера. Ок, пока не попадёт в код.
