## 1. §2.1 — порядок гейтов / mono·V5 / collision_rows

### Что закрыла дельта (E4-Д1)

| Требование E4 | v4 | Статус |
|---|---|---|
| порядок (в)→collision→(б)→(а) одной фразой | §2.1 явный | **да** |
| V5 = сущность **остаётся** в chunks/formula/entity; из order — только коллизии | §2.1 mono/V5 | **да** |
| mono = нынешний полный каскад DELETE → `p_doc` | §2.1 | **да** |
| покрытие `count(order)+collision_rows` до диспетчера; запрет `count(DISTINCT tail)` | §2.1 + M2 §2.5 | **да** |

Два прочтения E4 (полный wipe + отдельно tail vs частичный DELETE order) сняты:
исполнитель больше не угадывает структуру переписи `:1524-1534`.

### Новые способы wrongly-implement?

**Умеренные остатки (не блокеры круга):**

1. **Решение (б) до мутации order.** Спека сначала «посчитать множество и
   `collision_rows`», затем ветки. Верное чтение: размер хвоста и (б)/(а)
   **до** любого DELETE; partial DELETE order — только на пути V5; mono (б)/(в) —
   полный каскад с целого состояния. Неверное: сначала вырезать коллизии из
   order «для подсчёта», потом обнаружить oversize и пытаться mono на
   полуразрушенном order/chunks. Текст это не запрещает одной фразой «без DELETE
   до ветвления», но порядок гейтов + определения mono/V5 читаются однозначно
   при добросовестном исполнении; M2 (неполный order→mono, oversize→mono,
   покрытие collision_rows) ловит перепутанную ветку на фикстуре.

2. **`tail_rows` vs `collision_rows`.** Для (б) — `tail_rows × ncols`; для
   покрытия — `collision_rows`. Должны быть одним числом (строки order с
   keyvals ∈ коллизиям), не `count(DISTINCT keyvals)`. Подмена DISTINCT
   занижает бюджет → ложный V5 на oversized. Запрет DISTINCT есть у гейта
   покрытия; у (б) — только словом `tail_rows`. Риск исполнителя низок при
   чтении рядом стоящих абзацев; M2 oversize-кейс обязан зафиксировать
   row-count.

3. **Quality «при любом исходе».** На ветке (в) collision set может быть
   пуст/бессмыслен — писать `tail_rows/nrows/ncols` всё равно. Мелочь
   наблюдаемости, не семантика V5.

**Новых классовых дыр wrongly-implement уровня E4-Д1 дельта не открыла.**

**Вердикт §2.1:** спецификация исполняема; остатки — дисциплина порядка DELETE
и row-count для (б), закрываются M2, не новым кругом плана.

## 2. §2.3 — `BEGIN TRANSACTION` в `\gexec`

### Дельта

v3: `BEGIN; …; COMMIT`. v4: канон доков — `BEGIN TRANSACTION; EXECUTE
p_doc_tail; INSERT …_done; COMMIT` одной строкой `\gexec`.

### Доки (Multi-Statement Transactions)

- Несколько statements через `;` в одной подаче = **одна неявная транзакция**;
  ошибка любого → откат предшествующих.
- Явный `BEGIN TRANSACTION;` / `COMMIT;` — штатный путь той же главы.
- `COMMIT` вне активной транзакции — fail (документировано).

### Остался ли риск?

**Да, тот же остаточный, что в E3 — механика первого внедрения, не дыра спеки.**

| Риск | Оценка |
|---|---|
| psql `\gexec` шлёт ячейку целиком (simple query / PQexec) | ожидаемо; иначе паттерн мёртв |
| неявная транзакция батча **+** явный `BEGIN TRANSACTION` | теоретический край вложенности; доки разрешают оба приёма порознь, совместный `\gexec`-прецедент в дереве `corpus_build` **нет** (`:2179+` — однооператорные строки) |
| смягчение | даже `EXECUTE; INSERT _done;` **без** BEGIN уже атомарны по тому же разделу |
| `ON_ERROR_STOP` mid-batch | fail → откат; маркер не пишется — окно D4-Н2 не открывается |

### Чем ловится

- **M2** (§2.5): «resume не раздувает stage (атомарность)» — обязан упасть до
  выката, если multi-stmt/`BEGIN` ведёт себя иначе.
- **Сухой №0**: mismatch multiset / вечный STOP finalize без маркёра → merge не
  зовём (§3.4); боевой корпус не трогается.

**Вердикт §2.3:** окно «stage есть, маркёра нет» закрыто спецификацией;
остаточный риск клиента/`\gexec` — на замках, **не** повод нового круга плана
(та же позиция, что E3 §3).

## 3. §3.4 / §3.5 — эталон, `векторов_умрёт`, дырки

### Дельта относительно v3 / возражений E1·E2

| Было (блокер) | v4 | Оценка |
|---|---|---|
| E1: эталон 74 982 без завершённого монолита / «витрина==стейдж» | монолит 19:35:13 → такт умер на merge-гварде; замеры **20:04 и 20:26:30** совпали; объект = `tmp3_corpus` **после** QUALIFY `:1815-1817`; «==витрина» = факт данных сущности, не отмена QUALIFY; фраза «стейдж монолита» убрана | **логически согласовано с кодом fold** (`fold.on_ ⇔ key_cols=['Ref_Key']`): count корпуса = nrows витрины ⇔ на этой сущности QUALIFY никого не отбросил (уникальность `row_key`). Истина замеров — за оркестратором (сервер не трогался); в репо по-прежнему нет отдельного файла-артефакта md5 — только текст плана. Для исполнения достаточно: №0 сам переснимет |
| E2: `векторов_умрёт=0` + anti-join «только ключ» vs дрейф 74 785→74 982 | (а) `векторов_умрёт` — **отчётное**, ожидание класса ≈647 / 554 законного дрейфа, не критерий зелёного чеклиста; (б) дырка = ключ бэкапа §3.3, **живой** в `search_corpus`, `emb IS NULL` → **0**; чтение «только ключ» запрещено; (г) departed — отчёт ≈647 | **ровно вариант (2) из E2**; конфликт «зелёный приёмки при churn» снят |
| продукт `vector_loss_gate` (tol 0.5%, `:688-714`) | план гейт не отменяет; ~647…1200 / 1 657 724 ≪ 0.5% — путь зелёный без bypass (§8) | согласовано |

«До»-отпечаток 74 785 / `71947efe…` остаётся контролем перехода, не эталоном №0.

### Согласовано ли с «самым вероятным отказом» E3?

E3 §5: первый отказ зелёного прогона — **сухой №0: multiset финального
`tmp3_corpus` после V5+finalize ≠ эталону монолита (74 982 / `57ad85de…`)**.

| Аспект | Согласование |
|---|---|
| предохранитель №0 (mismatch → merge нет) | **на месте** (§3.4) |
| эталон как объект сравнения | усилен двойным замером после completion; ложный FAIL из-за «чужого» 74 785 как эталона V5 — снят |
| M2 раньше №0 | §2.5 по-прежнему обязан поймать класс NULL/`|`/покрытия/fold |
| векторные критерии после №0 | больше не делают законный дрейф ложным красным §3.5 (дыра E2) — отказ «по векторам при живом ключе без emb» остаётся жёстким, как и нужно |

Итого: **самый вероятный отказ первого зелёного пути тот же по месту (№0 /
multiset)**, но теперь это отказ **реализации V5≠монолит** (или срыва
предусловия), а не конфликт приёмки с дрейфом/`векторов_умрёт=0`. Согласовано.

**Вердикт §3.4/3.5:** возражения E1 (логика эталона) и E2 (дыры приёмки) по
дельте закрыты; мой отказ-предохранитель E3 сохранён и очищен от ложных причин.

## 4. Готовность без ещё одного круга

| Источник | Блокер | v4 |

механика `\gexec` — **исполнительские замки**, не пробелы спеки, требующие
волны G.
