## Противоречия отчётов

Проверены кандидаты ТЗ и соседние стыки A1–A4.

### 1. A2 V1/V2 (чанкование монолита) vs A1 (параллелизм с k×122 880)

**Не противоречие — совместимы.**

- A1: порция ~5k строк < 122 880 → **один** row-group scan → штатный multi-thread **внутри одной порции** почти не включается.
- A2: выигрыш чанков — **много коротких** statement’ов с меньшим working set (UNPIVOT/agg), а не один гигантский unspillable `string_agg`/`list`; живой факт того же такта — крупные **чанкуемые** сущности (321k/208k/191k) за ~6 мин при большем nrows, чем у realiz-монолита.

Итог: однопоточность порции не отменяет кратного ускорения серии лёгких порций vs 5 ч монолита. A1 даже рекомендует дробить `string_agg` (топ-2) — то же семейство, что V1/V2.

### 2. A3 «memory_limit 50–60% + threads↓ = защита №1» vs A1 «string_agg/join-память вне BM»

**Дополнение по разным фазам, не лобовое противоречие; риск путаницы приоритетов — да.**

- A3 ранжирует лимит для **OOM на unmatched anti-join** (`corpus_merge.sql:162-199`): JOIN/spill — buffer-managed класс; cookbook OOM прямо советует опустить лимит.
- A1 предупреждает: `string_agg`/`list` **вне** BM → `memory_limit` **не** ловит пик монолитного `p_doc`.

Стыковка: (1) для merge-гварда — A3#1 уместен; (2) для p_doc-монолита — нужен rewrite/чанки (A1#2, A2 V1), а не только pragma. План обязан **не** подавать «снизили memory_limit» как защиту от 5 ч/`string_agg`.

### 3. A4 «MERGE-based partial» vs A3 «NOT MATCHED BY SOURCE на полном target = снос сущности»

**Согласованы.** A4 сам пишет то же (`result-t1a4.md:195-198`): `WHEN NOT MATCHED BY SOURCE THEN DELETE` при partial USING ≡ снос сущности. Штатный путь A4: MERGE upsert стейджа + **DELETE только по кандидатам** (B5 ∪ gone), либо NOT MATCHED BY SOURCE **с предикатом кандидатов**. Доки (`merge_into`): `WHEN MATCHED THEN DELETE` и `WHEN NOT MATCHED BY SOURCE THEN DELETE` оба есть; второе без ограничения source/target опасно ровно как пишут оба отчёта.
