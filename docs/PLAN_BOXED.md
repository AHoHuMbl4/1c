## Условие приёмки

От чистой машины до первого верного ответа бота человек делает **ровно два действия**:

1. создаёт в 1С пользователя с правами только на чтение;
2. при необходимости — создаёт пользователя Windows.

Всё остальное система определяет и делает сама. Любой третий ручной шаг — дефект,
блокирующий продажу. Проверяет агент `boxed-ready`.

## Шаг 1. Перепись базы вместо списка (снимает главный ручной шаг)

**Что делаем.** При подключении система сама выясняет состав:

1. служебный документ OData → перечень всех сущностей;
2. `$metadata` → для каждой: объявленный ключ (в т.ч. составной), типы свойств,
   стандартные служебные свойства;
3. перепись `$count` по каждой сущности, параллельно → кто непуст, кто закрыт правами;
4. профиль базы сохраняется: что нашли, что взяли, что не отдали права.

`serene-entities.txt` **удаляется**, а не остаётся «на всякий случай».

**Стоимость.** Замерено ранее: ~0.1 с на сущность, 4585 сущностей ≈ 8 минут разово,
и это распараллеливается так же, как эмбеддинги в шаге 2 прошлого плана.

**Признак готовности**
- файла со списком нет ни в репозитории, ни на сервере;
- на нашей базе система сама находит 208 непустых сущностей вместо 19;
- в профиле видно, какие 934 сущности закрыты правами и почему.

## Шаг 2. Регистры и составные ключи

**Что делаем.** Пути, которые сейчас не выполняются, должны выполняться на реальных
данных:

1. **составной ключ** — склейка из объявленных свойств (код есть, прогона нет);
2. **регистры сведений** — ключ по измерениям и периоду;
3. **регистры накопления** — ключ по регистратору; движения перечитываются вместе
   с документом;
4. **сущности без Guid** — 497 типов, у них ключ иной формы;
5. **табличные части** — 1840 типов, решить: грузить сразу или по требованию, и решение
   обосновать замером объёма, а не вкусом.

**Признак готовности**
- в витрине есть хотя бы по одной сущности каждого вида, и счёт строк совпадает
  с `$count` из 1С;
- вопрос про остатки или обороты получает верный ответ, сверенный независимым запросом.

## Шаг 3. Отказ вместо тихой деградации

**Что делаем.** Каждый запасной путь получает явное поведение:

| Что недоступно | Сейчас | Должно быть |
|---|---|---|
| `$metadata` | молча переходим на разбор по форме значений | сборка **отказывает**: без типов результат недостоверен |
| модель при выборе колонки денег | молча «наибольшее число» | сущность помечается «сумма не определена», агрегаты по ней не считаются |
| эмбеддер | исключение в середине сборки | явный отказ до начала, с понятным сообщением |

Правило: коробка **не имеет права** тихо перейти на худший путь. Клиент не должен
узнавать об этом по неверной цифре.

**Признак готовности** — прогон с отключённым по очереди каждым внешним сервисом;
в каждом случае понятное сообщение, а не порченые данные.

## Шаг 4. Установка одним действием

**Что делаем.** Всё, что сегодня делается руками помимо двух разрешённых действий,
переносится в установщик:

- генерация токенов (шлюза, сервиса ответов) — сейчас руками;
- заполнение env-файлов и прав на них;
- разворачивание сервисов и таймеров;
- первичная перепись и сборка индекса;
- **самопроверка**: установщик сам задаёт базе контрольный вопрос и сверяет ответ
  с независимым запросом. Не сошлось — установка считается неуспешной.

На стороне Windows автоматизация уже есть (`windows/odata-setup`, 13 шагов). Её надо
свести с Ubuntu-частью в один сценарий и проверить на чистой машине.

**Признак готовности** — установка на чистой машине, где человек сделал только два
разрешённых действия, заканчивается верным ответом бота.

## Шаг 5. Вторая база

Без этого все предыдущие шаги остаются гипотезой: продукт видел один мир.

**Что делаем.** Берём другую типовую конфигурацию — желательно с другим языком
интерфейса — и проходим установку с нуля, считая ручные шаги. Всё, что придётся
подправить, возвращается в шаги 1–4.

**Признак готовности** — на второй базе те же два действия руками и верные ответы
на её собственном золотом наборе.

## Порядок и почему такой

1. **Перепись** — снимает главный ручной шаг и открывает данные, на которых видны
   остальные дефекты.
2. **Регистры и ключи** — без них «инфа должна быть вся» не выполняется, а код остаётся
   непроверенным.
3. **Отказ вместо деградации** — дешевле сделать до второй базы, чем ловить порченые
   данные на ней.
4. **Установщик** — собирает всё в одно действие.
5. **Вторая база** — единственная настоящая проверка.

Каждый шаг завершается прогоном агентов `boxed-ready` и `hardcode-sniper`, а также
золотым набором. Незакрытых хвостов не оставляем.
