# Граница деловых / неделовых данных в витрине (2026-08-21)

Замер и разбор: где в корпусе/витрине лежат данные бизнеса клиента, а где —
общий или служебный объём, который съедает канал, диск и векторизацию.
Критерий обязан работать на незнакомой базе **без списка имён** (девиз 29.07,
`HOW_NOT_TO §3.9`). На okna и klient-1 состояние **не менялось**.

Метки: `[замер]` — прогон; `[код]` — файл:строки; `[доки]` — не использовались
(вопрос не про SQL-средство движка).

## 3. Где граница проходит СЕЙЧАС (три места)

| слой | что решает | файл:строки | фильтр по class? |
|---|---|---|---|
| **контур агента / будущая загрузка** | `force` > `class=service` > `only_binary` | `packet_config.py:180-224` (SQL+вердикт); зеркало `serene_sync.py:152-210` `_service_skip` | да, если таблица class есть |
| **корпус** | все таблицы витрины из `$metadata`, минус `_RecordType`/`_RowType` | `corpus_build.sql:192-198` (`INSERT INTO search_sources`) | **нет** |
| **векторы** | не считать `cls=service` | `build.sh:330-332`, `embed_all.sh:151-154`; мягкий вызов разметки `build.sh:282-283` | да, при пустом class — **никого не режет** |

Итого сегодня: class экономит **векторы** и **повторную** доставку в контуре;
уже лежащая витрина и корпус от class **не чистятся**. Первый полный проход
на базе без успешной разметки платит канал+корпус+векторы за всё.

## 4. Где границу СТОИТ проводить (критерий без хардкода имён)

### 4.1 Что уже есть и должно работать

Разметка моделью по **именам/меткам/колонкам/числу строк** (данные наружу не
идут) → `search_entity_class` → векторы и контур. Это универсально: модель
судит по смыслу, не по словарю языка конфигурации
`[код] classify_entities.py:59-77,149-188`.

На klient-1 это **сломано авторизацией** (401), а не отсутствием идеи. Первый
рубеж восстановления — чтобы 401 не оставлял class пустым на полном первом
эмбеде (сейчас мягкий отказ это допускает).

### 4.2 Структурные признаки (замер на трёх базах, без списков слов)

| признак | как узнать без знания базы | ut_test | postgres | okna / klient-1 | годится ли один? |
|---|---|---|---|---|---|
| **A. `cls` модели** | кэш после classify | 805 service / 697 business | 53 / 178 | okna 97 / 254; klient **0 / 0** | да, когда auth жив |
| **B. участие в `search_changed_sources`** | дельта такта синка | service **0/805** in_changed; business **215/697** | service 0/53, business 0/178 (таблица пуста/не наполнялась) | okna: не снято в этом заходе (§6); klient: class пуст | **сильный на ut_test**; на пустой changed — молчит |
| **C. число пакетов манифеста (`pkgs`)** | происхождение/изменяемость по каналу | н/д (не packet inbox) | н/д | okna: once∩business и once∩service оба есть; klient: адресные pkgs=1, но и `ЦеныНоменклатуры` pkgs=1 | **нет** как единственный: на молодой базе «once» = ещё не догоняли |
| **D. префикс вида OData** (`catalog`/`document`/…) | таксономия платформы, не язык | informationregister: 100 business + 82 service | — | — | **нет** один |
| **E. порог строк** | count | ge50k на ut_test только service (2 шт.) | — | klient: крупные и деловые, и адресные | **нет** один |

### 4.3 Рекомендуемая граница (проверяемая)

1. **Векторы и контур агента** — только через `search_entity_class` (+ force),
   как сейчас. Ошибка class в сторону service дороже (потеря ответа) — правило
   «неразмеченное = business» верное `[код] classify_entities.py:184-187`.
2. **Канал (первый полный проход)** — class должен появиться **до** эмбеда и
   желательно до раздувания контура; мягкий 401 на пустой базе сейчас
   превращает «ещё не размечено» в «векторизуй 15M». Чинить auth / fail-closed
   на первом такте незнакомой базы — отдельное решение владельца (здесь только
   замер ущерба).
3. **Витрина уже загруженного** — не молча удалять (п.13); исключённое видно в
   `search_entity_skipped`. Повторно по каналу service не возить — когда class
   заполнится, `packet_config` уже умеет.
4. **Дополнительный сигнал B** (`never in search_changed_sources` при
   непустой таблице changed) — кандидат на **подтверждение** service или на
   приоритет разметки крупных «неизменяемых», не на замену модели: на
   postgres/ранней базе changed может быть пуст.

Имена вроде «ФИАС» / «адресные» в код **не вносить** — на okna того же блока
нет, на другой конфигурации те же смыслы названы иначе.

`адресныеобъекты` из **корпуса/BM25** было бы жёстче (там 903 вхождения
«казан») — текущий продукт при service как раз **оставляет BM25**, режет
только векторы `[код] classify_entities.py:12-17`.

## 6. Что измерить не удалось и почему

| что | почему |
|---|---|
| Часы передачи адресных порций по каналу | в `manifest.json` есть bytes/chunks/rows, нет длительности приёма по сущности |
| Байты столбца `emb` только по адресным | не снимали block_size/столбцовую статистику store.db; оценка «dim×4×N» без замера диска в документ не кладётся |
| JSON-ответ модели на адресные имена в этой сессии | шлюз `Qwen3.8-27B` — timeout / thinking без `{"items":…}`; на klient исторически 401 |
| `search_changed_sources` × class на okna | повторный SSH во второй половине сессии отклонён runtime-floor |
| Живой `/ask` по городу на klient-1/okna | не запускался: на клиентских базах запрещены изменения; приёмка ask — отдельный выкат/токен |
| Доля адресных в полном `sum(length(doc))` корпуса klient-1 | полный scan 15M строк по length не гоняли; есть сумма по шести таблицам (§2.2) |

## 8. Практический вывод одной фразой

На klient-1 ~27% витрины и ~5,9 ч векторизации ушли в адресный классификатор
не потому что «границы нет», а потому что **граница class не записалась (401),
а код при этом векторизует всё**; корпус class не фильтрует по задумке. Чинить
сначала доставку разметки, не изобретать список имён «адресные».
