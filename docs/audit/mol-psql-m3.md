внутри запроса всё последовательно (кроме будущего ThreadPool).

**Зависимости:** в `/opt/openclaw-mcp/venv` **нет** `psycopg` / `psycopg2` / `asyncpg`

### 2.2 Рантайм: лёгкий vs тяжёлый

Ключевой вывод: **77 кандидатов ≠ 77× запрос.** Почти весь отбор идёт
`IN (...77...)` одним SQL. Рост числа процессов даёт не N кандидатов, а:
арбитр ×`ARBITER_MAX` (умолч. 3), повторные `measures_of`, мелкие O(|cats|) /
O(|указателей not_for|) циклы.

### 2.3 Где ещё «в цикле» (п. 20)

П. 20 запрещает «запускать процесс `psql` (или иной клиент) **в цикле**» там, где
движок делает одним запросом. Уже в ask:

1. `measures_of` / `measure_aliases_of` — десятки одинаковых пар SQL на один `src`
   (`z20:4143+`, 12 сайтов `measures_of` в теле `answer`).
2. `expand_holders` — `SELECT … WHERE target_src = %s` на каждый cat вместо
   `target_src IN (...)`.
3. `z20:2354` — count на каждый текст-указатель not_for.
4. Арбитр — полный повтор пути ×3 (осознанно: «полный ответ» на кандидата;
   транспорт платит трижды).

Смена транспорта **не отменяет** эти пункты; батчи/кэш — пересечение с M2.

## 3. Почему выбран subprocess (история) и что сохранить

Из `z01:306-321` + `HOW_NOT_TO §1.11` / `PLAN_NATIVE_SEARCH`:

| Свойство | Зачем | (а) ThreadPool+psql | (б) psycopg thread-local | (г) батчи |
|---|---|---|---|---|
| SQL в **stdin** (`-f -`), не `-c` | стена argv 131072; 1712 ок / 1713 OSError | да (тот же `psql()`) | **да** (query text в протоколе, лимита argv нет) | да |
| Разбор **CSV** (`--csv` + `csv.reader`) | перевод строки в doc/refs ломал построчный разбор; 4% корпуса | да | нужно **явно** оставить CSV **или** `cursor.fetchall()` (типы надёжнее CSV) | да |
| `ON_ERROR_STOP=1` + check rc | иначе ошибка ≡ «пусто» | да | аналог: не глотать ошибки драйвера | да |

(а) сохраняет оба свойства без правки контракта разбора.
(б) снимает argv-стену по построению; CSV-парсер **не обязан** оставаться — лучше
нативный fetch, но API `psql()` можно временно эмулировать через
`COPY (query) TO STDOUT WITH CSV` / `cursor.copy`, если нужен бит-в-бит тот же разбор.

## 5. Вердикт

### Рекомендуемый транспорт

**Основной: (б) psycopg3 + thread-local соединение**, сохранив сигнатуру `psql(sql)→list[list[str]]` на первом шаге (или сразу `fetchall` с приведением к str — отдельный замок).

**Параллельно и раньше по дешевизне: (г)** — кэш `measures_of` + батч `expand_holders` + (уже в плане) early-clarify, чтобы не платить арбитр×3.

**(а)** — только точечно (arbiter sub-answers **после** (б), одним пулом ≤3), не как главный рычаг.

**(в)** — нет.

### Порядок миграции

1. **Счётчик** в `psql()`: `diag["psql_n"]` / ContextVar на rid — приёмка без догадок.
2. **(г) кэш** `measures_of` / `measure_aliases_of` на `(src,)` в пределах запроса — 1 файл `z08`, замок zone.
3. **(г) батч** `expand_holders` → `target_src IN (...)` — `entity_rank_v2.py:719+`.
4. **Установить psycopg** в `/opt/openclaw-mcp/venv`, зафиксировать в requirements.
5. **(б)** заменить тело `psql` / `_resolver_psql`; smoke SELECT 1 ×30; прогон замков ask.
6. Опционально **(а)** на arbiter loop — замер wall vs baseline.
7. Не трогать смысловой CSV-контракт, пока (б) не сравнен бит-в-бит на корпусной строке с `\n` в `doc`.

### Замер-приёмка (что должно показать)

| # | Замер | Ожидание |
|---|---|---|
| 1 | `SELECT 1` ×30 через новый `psql()` | сумма **≪ 1.05 с** (цель **≲ 100 мс**, т.е. ≲3 мс/вызов) |
| 2 | Тот же лёгкий вопрос: `diag.psql_n` и wall | n не хуже baseline; wall −≈ n×32 мс |
| 3 | Тяжёлый «полный отчёт» / 77 канд.: `psql_n` | до (г): 150–220; после кэша measures: −≥15; после early-clarify без arbiter: **≲100** |
| 4 | Строка корпуса с `\n` в `doc`/`refs` | число колонок и значение `doc` ≡ subprocess+CSV |
| 5 | 2 параллельных HTTP на ThreadingHTTPServer | нет cross-talk; 2 разных thread-local conn |
| 6 | Замки intent/compose/zone | без деградации |
| 7 | Нагрузка: ask пик + живой такт pipeline | нет каскада OOM/lock (особенно если включат (а)) |

### Кратко

> Проблема реальна: **≈1 с** на лёгком и **≈5–9 с** чистого fork-транспорта на тяжёлом.
> Число процессов **не** равно 77×K; оно ≈ **30** / **180±** из-за арбитра и повторов.
> Лечить: **сначала убрать лишние SQL (г), затем убрать fork (б)**.
> psycopg в venv нет, но это **штатный** клиент SereneDB — ставить можно.
> pgbouncer не нужен. Параллель subprocess — слабый рычаг.
