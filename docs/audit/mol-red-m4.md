## Вердикт одной строкой

На «полный отчет» дедлайн **88 с убивает до A**: к отсеву уже **~74 с**, A стоит
**после K6+fork**. Наивная сумма `7.5+51.7+21.5+12` **не сходится** с wall rid
(LLM на этом rid в шагах **нет** — memo; полный fork **не успевает**). Закрыть
смерть главных отчётных вопросов **на этой неделе без L67** может только путь,
который **не ждёт K6**: A2 (fail-closed) или эквивалент «меню до K6»; всё остальное
— ускорение префикса (stock/K6 SQL), чтобы **уже внедрённый A** успел до 88.

### Где «ещё 10–20 с» неучтённого

1. **Главное неучтённое внутри 74 с — сами 21.5 с post-K6.**
   Код между маркерами почти пуст, кроме stock-контура. M1 связывает с
   `stock_question_engaged` (± EXISTS). **Красная проверка:** гипотеза
   правдоподобна (pred всегда + word-loop + при product-kind тяжёлое тело), но
   **не доказана замером** — нет E8. Альтернативы: contention движка (такт),
   расхождение probe≠репо (маловероятно при стабильных 21.2 с в baseline).
2. **1–4 с без маркера** между отсевом и fork (order-by-meaning) — «серая дыра» TRACE.
3. **Холодный LLM +7.5 с** — отдельный бюджет; на прогретом полигоне маскируется memo.
4. Baseline **без** дедлайна: fork до **105 с**, TIME **137 с** → после fork ещё
   **~30 с** (wiki/арбитр/хвост). На rid с B этот хвост **отрезан** — в 88 не входит.

**Итог сверки:** сумма молекул к отсеву **74 ≈ 52+21.5+0.5** сходится.
Наивное `+LLM+полный fork` раздувает на **~10–20 с** за счёт memo и обрыва.
«Потерянные» 10–20 с внутри префикса = **атрибуция молекулы-2 (21.5)**, не третья
невидимая фаза после 88.

## 4. Атаки (≥4)

### Aт1 — Такт `1c-serene-pipeline` vs ask-пики

K6/fork = **full-scan / unnest** по 1.67M; такт = merge/CTAS/embed_bulk на том же
движке. Параллельный ask в окне такта → wall K6/fork **плывёт** (21 с gap может
частично быть contention, не только stock). ThreadPool вокруг SQL (M2/M3 «а»)
умножает пик. **Атака:** снять E1/E2 во время SKIP-такта vs idle — если E2 ×2,
молекулы «кода» преувеличены.

### Aт2 — ThreadingHTTPServer + thread-local psycopg

Один поток = один HTTP = один conn — схема верная. Гонки:

- общий mutable кэш (`_fork_meas_cache`, `_INTENT_MEMO`, emb cache) уже сейчас
  без conn — psycopg их не лечит;
- reset битого conn при `ON_ERROR_STOP`-аналоге;
- orphan после обрыва клиента (speed-s3): поток **держит conn** до дедлайна B;
- вынос conn в global / пул на процесс = классическая гонка.

**Приёмка M3 №5 обязательна** до боя.

### Aт3 — Батчи `IN(77)` / универсальность (п.0)

На okna 77 крупный sales-пул → тяжёлый table scan. На базе с **тысячами** мелких
`src_table` в IN список литералов + план могут деградировать иначе; на крошечной —
наоборот. Фикс «всегда OR по `search_idx`» не обязан быть лучше везде
(`CHECK1_REVIEW_3` — другая кардинальность). **Универсальный фикс** — витрина
агрегатов на такте (`src_table → n_*`), не калибровка под 77 okna.

### Aт4 — A2-меню без K6: устаревание `search_fork_label`

Цепочка:

1. `search_fork_class` пишет **детектор на ask** (живой счёт);
2. `branch_alias.sh` (агент, пачками, `RETRY_H`) пишет **подписи** в
   `search_fork_label`;
3. A2 читает labels **до** K6/not_for/period-live.

Атаки:

- класс есть, подписей нет → пустое/частичное меню или откат в полный путь;
- подписи от **прошлого** класса после смены метаданных/$metadata — ветки-призраки;
- меню без period-`found` показывает источники с **0 строк за «вчера»**;
- K6/not_for отсеяли бы соседа — A2 покажет лишнее (ложный clarify, п.12/21);
- `fork_label` **не** синхронен с корпусом по такту: это словарь смысла веток, не
  снимок данных.

**Контрмеры A2:** fail-closed как у A; требовать покрытие labels на весь пул;
сверять fingerprint с post-K6 A на полигоне; при дырке словаря — не A2, а старый путь.

### Aт5 (доп.) — Параллель arbiter ×3 + такт

M2/M3: N полных `answer` = N× SQL+LLM. На фоне такта — риск OOM/lock SereneDB.
На неделю — **не включать**.
