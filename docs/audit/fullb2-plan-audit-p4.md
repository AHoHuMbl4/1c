## Атака 1: новый сценарий потери emb, который v1 не закрывает

**Сценарии.**

(а) **B4 = горячий путь, не мёртвая ветка.** `repost→bridge` (:602-604) меняется
**вне** `\if :partial_rebuild`. Сегодня `#`-потомки (`guid#sha`) не матчятся
`starts_with(…||'|')` → не входят в `tmp3_merge_repost_delta` → могут оставаться

строки с emb, гейт молчит. На тихом B7 (нет #-repost) ≡ зелёный; первый живой
repost после выката — молчаливая убыль векторов «по плану», без allowlist.

(б) **Обрыв после L-mid.** B5.1 ставит гейт **между** `\gexec` MERGE (:1366) и
DELETE (:1371). `emb_xfer` (:1393) — **после** DELETE. Abort/kill на xfer:
строки уже вычищены anti-join, часть survivor с `emb IS NULL`, L-mid уже пройден.
B5.2 (tx на пачки xfer) сужает окно, но **второго** пост-xfer STOP в v1 нет.
Следующий такт: `old_full` уже с дырами; карта xfer не восстанавливает снятое.

(в) **Retry пакета после STOP в merge.** Apply уже в витрине; маркеры A живы;
`corpus_built_ts` не двигается (ставится только после успешного merge —
`build.sh:429-432`). Следующий полный такт при flip=0 — полный anti-join, тел
B3 мёртвы — **этот** путь v1 держит. Дыра всплывает только если к моменту
retry уже ошибочно `:partial_rebuild=1` / mode=partial (сторож A должен STOP;
если выкат B без A — вне контракта окна).

(г) **«DROP tmp3».** В живом merge — `CREATE OR REPLACE`, не DROP. После fail
merge `tmp3_*` остаются; freshness `tmp3_run` + flock (`build.sh:77-78`) —
следующий такт пересобирает. **Явного** текста в v1 нет; устройство кода
держит, план на это не опирается.

(д) **Гонка тактов.** flock сериализует. Гонка **apply↔merge**: gone-маркер с
`ts > corpus_built_ts` после снятия бюджета, до DELETE — на flip=0 expand не
вычитается (B3.7) → бюджет не маскирует. После flip — классика саботажа
маркеров; v1 откладывает на этап 6 + 6a0, но **не** требует фикстуры «маркер
после budget-read».

**Что v1 закрыл из b4.** 6a0-lite до scp (0.1); не вычитать expand при
`partial_rebuild=0` (B3.7, §9.7); L-mid + tx xfer; запрет 1c≺1a.

**Вердикт: v1 уязвим** — главный незакрытый класс = **B4 на горячем пути** +
дыра **post-DELETE emb_xfer** без второго гейта.

ожидаемая убыль N / quality-ключ»), либо доказать на срезе «есть ли в корпусе

## Атака 4: горячий путь flip=0 — хватает ли B7?

**Что есть.** Замеры 1–4 + wall/tmp + allowlist новых quality-ключей B6;
SKIP не приёмка; расхождение вне allowlist = откат. Partial-тела объявлены
мёртвыми.

**Почему ≡ не доказан.**

1. **B4 меняет горячий путь** (атака 1а) — B7 на тишине не ловит.
2. **«3 сущности»** — срез недостаточен и неуниверсален (атака 2). На базе,
   которую не видели: дефект B может сидеть в 4-й по размеру / в мелкой с
   `#`-ключами. Полный `count(*)/emb` ловит **кардинальность**, не перестановку
   content_hash внутри; multiset трёх — дыра покрытия.
3. **Allowlist** = «только новые ключи замков B6». B4/B2 могут сдвинуть
   **кардинальности существующих** STOP-классов без новых ключей — allowlist
   их не покрывает; B7.3 говорит «≡ базовой», но при живой дельте между
   baseline 0.3 и пост-scp тактом ≡ ломается честно. v1 не требует
   «окно без дельты 1С» или «та же дельта».
4. Открытые Q2/Q5 не влияют на flip=0 **если** тела мёртвы; на ≡ горячего
   unexplained влияют только правки вне `\if` (B4, возможно склейка CTE-имён
   в vec-budget).

**Вердикт: v1 уязвим** — B7 необходим, **недостаточен** для ≡.

**Правка v2.** (1) Полный multiset или `EXCEPT` по всему корпусу (или
data-driven top-K + явный остаток «прочие» одним hash). (2) Базовая линия и
пост-scp — **один** сценарий дельты (ноль или зафиксированный пакет).
(3) Отдельная строка приёмки B4 / allowlist #-repost.
