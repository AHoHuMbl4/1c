# ПЛАН «Speed-Ask» — структурный пакет ускорения ответов v2 (финал)

Дата: 11.09. Статус: **СОГЛАСОВАН** (волны S×4 → план v1 → P×4 → v2 →
контроль K1-K4: правки K1/K4 внесены; вердикт K4 после правок = готов).
Ждёт стоп-точки владельца; внедрение — только после «да».
Источники: speed-s1..s4.md, speedask-plan-p1..p4.md, speedask-check-k1..k4.md.
Скоуп: `ask/*.py` + serene_ask.py + env. НЕ трогаем: вектора, такт, пакет B,
flip, store.db, мост mcp_ask.py (env готов). ВНЕ СКОУПА (отдельный эпизод,
не входит в «закрыто»): агентная модель flash/pro, 30k-промпт агента,
стриминг в Open WebUI.

Цель (W4): простой ≤15с; clarify ≤20с; полный отчёт ≤40с; худший — русский
отказ ≤100с. Обещание по реранку: устранение детерминированных вызовов,

## 0. Протокол приёмки

1. Замки до/после каждого пункта (intent 162/0, compose 92/0, action 48/0,
   zone 99/0, смежные) — деградации нет.
2. **L67 после каждой группы ослаблений** (не один в конце): после A, после
   C (группа), после D — атрибуция wrong сохраняется; wrong не выше L19=3,
   по п.10 для каждого ослабления. B — не ослабление выбора (только обрыв):
   замки + замеры.
3. Stability (обязателен для D): `intent_parse_bench.py 1 58 REPEATS=3
   MEMO=0`, сравнение по `key_of` (7 полей) — не хуже текущего разброса.
4. Тайминги 3 классов живьём через :18801 vs baseline (78с/153с/300с).
5. Инвариант таймаут-цепочки (проверяется в env-комментарии и приёмкой):
   `ASK_DEADLINE_SEC=88 < ASK_TIMEOUT=90 (мост) < requestTimeoutMs=100000
   (шлюз)`. Порядок проверки в рантайме: deadline-чек в начале арбитра →
   ранний clarify; **готовое меню побеждает deadline** — если early-clarify
   сформирован, он возвращается даже при истёкших часах; deadline истёк до
   готовности меню → unavailable.
6. Стоп-точка владельцу после 1-5 зелёных. STOP всего пакета: wrong > 3
   на любом L67, деградация любого замка, timeouts-инвариант нарушен.
