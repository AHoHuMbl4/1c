## Атака 1: потеря emb при B (саботаж маркеров / гонка / обрыв merge)

**Сценарий.** (а) Саботаж или дефект писателей A: в `search_changed_rows` лежат
ложные `op='deleted_gone'` на широком предке; 1c вычитает `gone_expand` из
`unexpected`; anti-join (flip=0) или DELETE gone∪expand (после flip) снимает
строки корпуса с emb — гейт молчит, потому что «объяснено». (б) Гонка: apply
пишет маркеры между build и merge (или после `corpus_built_ts` окна), expand
объясняет то, чего нет в стейдже. (в) Обрыв `\gexec` пачек MERGE
(:1347-1365 уже сегодня) + resume: часть emb=NULL, часть строк уже DELETE —
тихое продолжение без L-mid STOP. (г) 1b сужает unmatched/rewrite-wave по
`mode` так, что при баге R6 (`mode=partial` при `partial_rebuild=0`) сторож A
должен STOP'ить, но если 1a выкатили раньше A/0f — wipe.

**Что план ставит.** R1-комплект 1c: предок=`deleted_gone` ∧ fanout-cap =
COUNT витрины под предком ∧ ⊆ свидетель витрины ∧ cap+⊆ **до** DELETE ∧
фикстуры STOP; `n_seg=0` → expand запрещён; само-объяснение DELETE запрещено;
L-mid (1)(2)(3); 6a0 на flip; сторож A при flip=0.

**Дыры.** 6a0 назван **только** на этапе 6 (flip). Выкат B сам по себе — это
правка `corpus_merge.sql` (формула unexplained / CTE expand / ветки 1b), и она
исполняется на **каждом** полном merge при живых маркерах A. Утверждение
«else = байт-в-байт» не снимает обязанность предусловия-бэкапа emb перед
выкатом merge-SQL (§3.113: право на массовую смену текста/гейтов = 6a0).
Фикстура «expand >K%» противоречит «НЕ константа — R8»: K% не определён.
L-mid требует `count(emb IS NULL) вне маркеров = 0` **или** STOP — нет
протокола, кто и когда меряет после kill -9 на `\gexec`. Нет явного запрета
вычитать `gone_expand` из unexplained при `partial_rebuild=0` / `mode=full`
(если 1c всегда активен — см. атаку 4).

**Вердикт: план уязвим**

**Что добавить в план.** Перед выкатом B: «6a0-lite обязателен (бэкап emb
parquet + сверка count/len=1024), даже при flip=0». В 1c: «при
`:partial_rebuild=0` CTE `gone_expand` **не** вычитается из unexpected
(формула unexplained = текущая); expand-вычитание только в `\if
:partial_rebuild` ветке вместе с DELETE gone∪expand». Убрать «K%» → «STOP
если |expand| > COUNT(mart под предком) ∨ expand ⊈ mart». Приёмка L-mid:
kill после N COMMIT пачек → следующий такт либо STOP quality
`merge_mid_abort_emb_holes`, либо emb-дыры = 0 вне свежих маркеров — замер
числом, не догадкой.

## Атака 2: правило 0 — знание конкретной базы / руки на новой

**Сценарий.** fanout-cap «COUNT строк под предком» на базе без `key_cols`,
без Ref-иерархии, с мешком ключей, с иным регистром имён. Ручной шаг при
установке коробки: выставить mode, прогреть кэш, править cap.

**Что план ставит.** `n_seg=0` / без `key_cols` → expand запрещён, `mode=full`;
cap из витрины, не константа okna; R6 interim `mode='full'` всем при
`partial_rebuild=0` — коробка не зависит от моста до flip.

**Дыры.** «COUNT под предком» не специфицирован: какой SQL-мир (A/B/C), какой
мост, что считается предком при `Recorder` / табличной части. Без этой
формулы исполнитель подставит okna-эвристику — нарушение п.0 по сути.
Фикстура с «K%» — числовое знание базы. Порядок выката «stop timer → scp →
md5» — операция обслуживания (допустима), но в плане B нет явной строки
«на новой базе после install: `\set partial_rebuild 0` в SQL, ноль env, ноль
ручных маркеров» — иначе читатель решит, что flip/маркеры — часть коробки.

**Вердикт: план уязвим** (механика fail-closed верна; спецификация предка/
fanout — нет)

**Что добавить в план.** Одна канон-формула fanout без имён okna: предок =
`key_text` маркера; потомки = строки витрины, чьи key_cols-проекции
`bridge_row_matches` / starts_with по контракту этапа 0; COUNT = `count(*)`
витрины с тем же предикатом; при `len(key_cols)=0` — expand CTE пуст и
grep-замок это требует. Явно: «коробка с B при flip=0 = поведение полного
merge; partial/fanout не активируются установщиком».

## Атака 4: зелёный прод после выката B при flip=0

**Сценарий.** Первый полный такт после scp B: `partial_rebuild=0`, R6 → всем
`mode='full'`, сторож A PASS. Утверждение плана: «else = текущий merge
байт-в-байт». Если 1b/1c меняют CTE unexplained / scope unmatched на **том же**
пути — поведение уже не тождественно; ложный PASS у гейта или новый STOP на
легитимной дельте = красный/дырявый прод.

**Что план ставит.** R6; `\if :partial_rebuild` … else = байт-в-байт; порядок
«0f → A → 1a…» (фактически 0f+A уже выкачаны).

**Дыры.** «Байт-в-байт» — декларация без протокола. 1b («сужение … по mode») и
1c (новая формула unexpected) **не** помечены как мёртвый код при
`partial_rebuild=0`. Живой merge сегодня считает `die_unexplained` без
`gone_expand` (:975-1011). Любое вычитание expand на full-пути меняет гейт.
Порядок в шапке B устарел относительно факта окна — риск «выкатить 0f ещё
раз» / перепутать атомарность с Speed-II.

**Вердикт: план уязвим**

**Что добавить в план.** Жёстко: «при `:partial_rebuild=0` тела 1b/1c
partial-скоупа и `gone_expand`-вычитание **не компилируются в горячий путь**
(`\if` / мёртвая ветка); md5/diff горячего пути unexplained+DELETE ≡ pre-B».
Замер до/после выката B (один снимок, без дельты 1С или с той же дельтой):
(1) `count(*)` / `count(emb IS NOT NULL)` / `count(emb IS NULL)`;
(2) multiset `content_hash‖row_key` по 3 крупным сущностям;
(3) `rehash_gate` / `vector_loss_gate` / классы STOP в `search_quality` —
кардинальность и ключи;
(4) wall merge-секции и список создаваемых `tmp3_merge_*`.
Расхождение любого пункта = STOP выката, не «предсказуемое изменение».
Обновить шапку: «0f+сторож A уже в проде; окно B = только merge-ветвление
1a–1d (+repost bridge)».

## Атака 5: SKIP 103–397 с задушат ветвлением / новыми CTE

**Сценарий.** Новые CTE expand/cap/mode-scope на каждом такте раздувают wall;
SKIP-такты перестают быть «дешёвыми».

**Что план ставит.** Молчание. SKIP в плане B не упомянут.

**Свидетель кода.** `build.sh`: при `SKIP_BUILD=1` **не** зовутся
`corpus_build.sql` и `corpus_merge.sql` — только отметка и хвост. Значит
ветвление merge **не исполняется** на чистом SKIP. Угроза — не SKIP, а
«почти SKIP»: мелкий marker/changed → полный build+merge с тяжёлыми CTE.

**Дыры.** Нет базовой линии merge-wall до выката; нет потолка «CTE expand не
дороже O(|markers|+|mart slice|)»; нет запрета коррелированного EXISTS по
всему корпусу (урок :866, 21 ГиБ tmp). План не требует замер «до» на
живом полном такте.

**Вердикт: план уязвим** (SKIP сам держится устройством build.sh; план этого
не использует и не защищает non-SKIP)

**Что добавить в план.** «SKIP-wall не регрессирует по определению (merge не
зовётся) — не считать его приёмкой B». Обязательный замер **до** scp: wall
фазы merge + пик `.tmp` на одном полном такте; после B — тот же сценарий
(flip=0, mode=full всем); рост >X% (X зафиксировать замером до, не числом
okna в коде) → откат. CTE expand: hash-anti-join / reuse vec-budget, запрет
второго полного скана корпуса (повторить канон FULLB 1c :182-183 в тексте B).

## Атака 7: атомарность 1a / 1c и раздельный выкат

**Сценарий.** Исполнитель выкатывает 1a без 1c (или наоборот) «потому что
меньше дифф».

**Связи.**

- **1a без 1c при flip=0:** else-ветка ≈ noop — риск низкий, если `\if`
  не инвертирован. При ошибочном `\set partial_rebuild 1` без 1c: DELETE
  gone∪expand без cap → §3.113-класс.
- **1c без 1a при flip=0:** если `gone_expand` вычитается из unexplained, а
  DELETE всё ещё полный anti-join — гейт **маскирует** массовое снятие строк,
  объяснённых саботажем/ошибочным expand. Это главный разрыв.
- **1b без 1a:** сужение unmatched по mode при всех `full` может быть noop
  или тихо сузить свидетелей shrink/repost.
- **1d (замки) без 1a/1c:** замки красные или ложно-зелёные — не держат прод.
- **repost→bridge (в 1d):** независим семантически от 1a, но в том же файле
  merge; полуоткат merge ломает сторож A / 0f (уже зафиксировано в RUNBOOK
  §10.9-ter для тройки build+merge+init).

План говорит «артефакты связаны md5 в одном окне (build с mode + merge с A)»
— это про **0f+A**, не про внутренности 1a–1d. Про 1a∥1c атомарность не
сказана.

**Вердикт: план уязвим**

**Что добавить в план.** Атомарные подмножества выката B:

1. **Обязательный минимум одного окна:** `corpus_merge.sql` с **1a+1b+1c+1d
   (вкл. repost→bridge)** одной md5; полуоткат запрещён.
2. `corpus_build.sql` в окне B **не** трогать, если 0f уже в проде (иначе
   тройка снова как §10.9-ter).
3. Явный запрет: «1c не выкатывать раньше 1a; 1a не выкатывать с
   `partial_rebuild=1`».
4. Замки-тесты — в том же коммите/окне, до scp на прод.

Раздельный выкат «только 1a» при гарантированном flip=0 и мёртвой
partial-ветке — допустим **только** если diff доказывает отсутствие изменений
вне `\if :partial_rebuild` и unexplained; иначе нет.

## Атака 8: стоп-точка владельца — чего нет в плане

**Сценарий.** Владелец спрашивает: «можно ли жать выкат? как откатить? что
мерить?» План отвечает «ГОТОВ К ВНЕДРЕНИЮ» без чеклиста B.

**Чего нет.**

1. **Приёмка B** — у пакета A есть нумерованный список замеров (:104-108); у
   B — только отсылки к L-mid/фикстурам 1c и к M* канона FULLB §4 без
   привязки «что обязательно до/после scp на okna при flip=0».
2. **Критерий отката** — нет; §10.9-ter закрывает Speed-II+0f+A (тройка +
   DROP numhint), не ветвление merge 1a–1d.
3. **RUNBOOK** — нужна §10.9-quater (или расширение ter): откат одного
   `corpus_merge.sql` к md5 pre-B; что делать с `search_quality` ключами
   новых замков; запрет BYPASS как «отката».
4. **Предусловие emb** перед B — отсутствует (есть только на flip).
5. **Актуализация порядка** — шапка B всё ещё «после Speed-II-2+0f», хотя
   это уже факт; владелец может одобрить повторный выкат 0f.
6. **Allowlist отличий** такта после B — нет (см. атаку 6).
7. **Стоп при живой дельте:** activeContext ждёт первый пакет с delta для
   проверки writers; план B не говорит «не выкатывать 1c, пока не закрыта
   приёмка A на живой дельте» — гонка двух окон.

**Вердикт: план уязвим**

**Что добавить в план.** Блок «Приёмка пакета B (flip=0)» по образцу A:
замеры атаки 4; L0/L2/L4 фикстуры PASS; grep-замок unexpected↔cap-CTE;
контрольный такт wall; rehash_gate=0 при отсутствии массовой смены текста.
Блок «Откат»: scp pre-B `corpus_merge.sql` (один файл, если build не
трогали) → md5 → один такт; при сомнении emb — сверка с 6a0-lite бэкапом.
Блок «Не стартовать B пока»: приёмка A на живом delta-пакете закрыта ИЛИ
явный override владельца. Строка в RUNBOOK §10.9-quater — тем же коммитом,
что выкат. Статус плана сменить с «ГОТОВ К ВНЕДРЕНИЮ» на «ГОТОВ после
правок красной команды B + одобрения».

## Вердикт: план к внедрению не готов

Держит: п.20 (формулировки B — SQL), fail-closed `n_seg=0`, сам факт R6
interim full, намерение L-mid и R1-cap, запрет self-explain DELETE.

Ломает готовность: отсутствие 6a0 на выкате merge-SQL; возможная активность
1c на full-пути; голое «байт-в-байт» против собственного «Чего НЕ делаем» №5;
неатомарность 1a/1c; нет приёмки/отката/RUNBOOK для B; устаревшая шапка
порядка относительно живого okna.

После правок 1–10 — повторный круг красной команды по **тексту плана**, затем
одобрение владельца, затем код.
