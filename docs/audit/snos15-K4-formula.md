## 2. Новые механизмы: построитель подписей и «новый слой»

### 2.1 Построитель подписей

PLAN W6: обёртка над `wiki_format_passport_lines` / card lines → единая точка для
`mk_opts`, fork-C, wiki-tie, early-A.

**Как форматтер — да**, если контракт жёсткий:

- вход: уже выбранный список кандидатов/осей (кто в меню — решили ступени 2–4);
- выход: только человеческий текст из вики/паспорта;
- **запрещено:** фильтровать, сортировать «лучше», отбрасывать вариант, выбирать
  «главный» label, подставлять src при пустом паспорте как победителя.

**Как выбиратель — станет**, если реализация:

- при отсутствии паспорта молча берёт `search_tables` label / первый src;
- «улучшает» набор options (merge/dedupe по смыслу);
- зовёт LLM «перефразировать варианты».

Требование к правке плана: **явный контракт 0 выбора** + замок «N options in =
N options out, порядок сохранён».

### 2.2 Не создаёт ли PLAN новых сущностей?

## 3. Противоречия формуле внутри плана

### 3.1 Молчаливые выборы, которые PLAN оставляет

| место | компромисс или нарушение? | строгая формулировка |
|---|---|---|
| **мера `totals_of` всем → compose** (P2 §3в) | **нарушение**, если мер >1 и человека не спросили; «модель видит все» ≠ ступень 4 | «при >1 живой мере — только меню с вики-подписями; `totals_of` в compose без выбора запрещён» |
| **intent-слоты z02** | заявленный компромисс MERGE §3.4; по формуле — **нарушение ступени 2** | «интерпретация kind/want/measure/period — из вики (или меню разборов); LLM-слот без вики вне формулы» |
| **билет trusted** | ступень 5 — **ок**, если только после `decision_id` | «trusted без seal_clarify/consume — запрещён» (W1 это почти закрыл) |
| **один wiki-yes** | план: «допустимо как одно прочтение» | спор определения «прочтение». Строго: «pool карточек >1 → всегда меню человеку, даже при одном yes; yes — сигнал для подписи, не лидер». Мягко (текущий дефолт): «прочтение = результат verify, не размер пула» — тогда один yes ок, но это **судья-модель**, не человек |
| **assumed-clarify** | компромисс: догадка+меню | строго: «не применять assumed-окно в SQL до выбора; только показать варианты окон из readings/вики» |
| **expand_pool** | компромисс «техника» | строго: «пул = результат поиска+вики; дописывание классов сущностей кодом — перестановщик прочтений» |
| **equal-tie меню** | дефолт плана **строже** «одно число» | не нарушение формулы выбора; спор п.21 (лишнее меню при тождестве) |

### 3.2 Главный структурный разрыв

Формула: ступень 2 = **интерпретация из вики**.
PLAN итог: `intent-слоты (техника) + wiki-каскад (сущность)`.

Это **два судьи смысла**. Wiki судит src; z02 судит род вопроса. Снос 16 целей
не устраняет второй. Пока §Открытые-3 не закрыт словом владельца в пользу
«слоты вне формулы до отдельного пакета» — пакет **не достигает** «ничего больше».

- п.20: план ask-тракта SQL через штатный путь — вне темы сноса; не ухудшает.

- Риски п.21 после сноса: expand_pool→лишнее меню; equal-tie меню при тождестве;

## 6. «Не точечно, а весь путь» vs 16 целей волнами

### Вариант A — текущий PLAN (снос списком 1…16 / 9 волн)

**Суть:** вырезать известные выбиратели из толстого z20, оставить оболочку и ядро
wiki/SQL/меню.

| плюсы | риски |
|---|---|
| измеримые волны, откат по Δwrong | **точечный список** того, что уже нашли M/P — не доказательство полноты |
| сохраняет HTTP/билеты/compose | между волнами тракт **ещё более** дырявый (полуснос) |
| L67/полигон на каждом шаге | «техники» (z02, expand, totals_of, один yes) переживают пакет по решению плана |
| меньше big-bang | владелец сказал «весь путь» — A выглядит как инвентаризация врагов, не как «оставить только формулу» |

### Вариант B — вырастить тонкий тракт (`z21`+`z17`+`z14`+`z18` + HTTP-оболочка)

**Суть:** новый `answer_formula15`: вопрос → wiki-интерпретация/пул → SQL
aggregate/rows → при >1 меню с вики-подписями → decision_id → compose/gate.
Старый z20 держать за флагом/полигоном до cutover.

| плюсы | риски |
|---|---|
| соответствует «оставить только формулу» буквально | большой объём; долго без ответа на проде |
| нельзя «забыть» R13/R14 — их просто нет в новом пути | перенос edge-cases (period readings, fork detector, currency) легко **вернуть** судьями |
| один cutover-замер вместо 9 полусостояний | п.21: пока тонкий тракт беднее — больше no_data/clarify на живых данных |
| проще доказать «ничего больше» grep-ом по файлу | дубль кода / рассинхрон оболочки HTTP |

**K4 не выбирает за владельца.** Для формулы №15 вариант B ближе к словам
«весь путь»; вариант A ближе к управляемому сносу при живом L67. Смесь без
правки: A **плюс** запрет дефолтов, закрывающих дыры R1/R2/R5/R13/R14 до
объявления пакета «формула достигнута».

## Правки, без которых вердикт не «годен»

1. **Стоп-точка владельца до кодирования** по §Открытые PLAN 1–4; запретить
   исполнять дефолты плана как решения (особенно **один yes** и **equal-tie**).
2. **Явно включить в снос или в стоп-список:** `apply_prior_period`; живые
   stock-эвристики (`stock_breakdown_leader_fallback` / net / engaged как
   ветвитель); путь **`totals_of`→compose при >1 мере** → меню.
3. **Контракт построителя подписей:** 0 выбора; замок N→N; без LLM.
4. **После снятия majority:** спецификация поведения при нестабильном intent
   (меню разборов / honest clarify / запрет first-of-list) — сейчас дыра.
5. **Критерий «пакет закрыл формулу»:** не «16 целей вырезаны», а чеклист
   «в ответе нет шага вне 1–6» + grep остатков R1–R20 = 0 или помечены
   владельцем как периметр.
6. **expand_pool / rerank-порядок:** либо доказать замером, что не меняют
   leader/меню, либо снести/нейтрализовать (shuffle только внутри меню после
   решения «какие варианты»).
7. Зафиксировать в PLAN: **вариант A не равен** «весь путь»; полный match
   формуле либо закрывает R1 отдельным пакетом вики-интерпретации, либо
   владелец явно разрешает z02-слоты как временный суррогат ступени 2.
