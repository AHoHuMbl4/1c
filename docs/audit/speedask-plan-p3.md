## Сверка

### 1. ASK_INTENT_LEAD / ASK_INTENT_SAMPLES — env уже есть

| Что искали | Факт |
|---|---|
| `os.environ` в `z02_intent.py` | **Нет** — z02 читает модульные `INTENT_SAMPLES` / `INTENT_LEAD` |
| Где env | **`z01_infra_trace_llm.py:858–859`**: `ASK_INTENT_SAMPLES` (дефолт `"5"`), `ASK_INTENT_LEAD` (дефолт `"3"`) |
| Ранний выход | **`z02_intent.py:669–671`** уже есть: `while len(samples) < max(1, INTENT_SAMPLES)` + `break` при `min(lead по всем 11 полям) >= INTENT_LEAD` |

**Вывод для плана D шаг 1:** правка кода **не нужна**. Достаточно env на ask-юните: `ASK_INTENT_LEAD=2` (SAMPLES пока 5). Утверждение плана «возможно читает env — проверить; если константа — env-ручка» — закрыто: **ручки уже есть**, дефолты текущие 5/3.

Поля голосования (`_INTENT_FIELDS`, 11 шт., `z01:852–853`):  
`terms, kind, measure, want, period, period2, amount, about, action_class, action_axis, search_form`.

`_field_lead` (`z02:588–596`): `lead = count(лидер) − count(второй)`; при одном значении `lead = count`.

### LEAD=2 при 2:0 — безопасно ли?

**Да для семантики раннего выхода.** После двух **совпавших** сэмплов по всем 11 полям: `lead = 2 − 0 = 2 ≥ LEAD` → break. Unit уже зелёный: `test_intent.py:350–351` («два совпавших прогона третьего не требуют» при lead=2).

Это **не** «консенсус из двух против честного 2:1» — при 2:0 второго кластера нет. Риск «ложного консенсуса» начинается там, где есть **второй голос** (см. атаки).

### Пересчёт потолков: SAMPLES=3, LEAD=2

| Накоплено | Типичный split | lead | Выход при LEAD=2? | При LEAD=3 (сейчас)? |
|---:|---|---:|:---:|:---:|
| 2 | единогласие 2:0 | 2 | **да** (лучший случай) | нет |
| 2 | 1:1 | 0 | нет → 3-й | нет → 3-й |
| 3 | 2:1 | **1** | нет, но **потолок** | нет → 4-й |
| 3 | 1:1:1 | 0 | потолок | нет → 4-й |
| 4 | 3:1 | 2 | **да** (при SAMPLES≥4) | нет → **5-й обязателен** |
| 5 | потолок | majority | — | конец |

**Кейс 3:1 остаётся?** При `SAMPLES=3` **нет**: максимум после трёх — 2:1 или 1:1:1. Кейс «3:1 после четырёх → пятый» живёт только при `SAMPLES≥5` и `LEAD=3`. При `LEAD=2` + `SAMPLES=5` пятый на 3:1 **не нужен** (выход на 4-м) — это и есть экономия шага D1 без резания потолка.

**SAMPLES=3 + LEAD=2 после 2:1 на третьем:**  
код **не** зовёт 4-й (потолок). `_merge_intents` берёт **majority 2:1** (`test_intent.py:353–356`). Лидер 2:1 — да; «дожать до LEAD» — нет.

**SAMPLES=3 + 1:1:1:**  
`_merge_intents` + `_field_lead` order: при равных счётах побеждает **первое встретившееся** (`z02:594`, тест `:360–362` «при трёх разных прогонах берётся первый»). Перезапроса нет. Старый `LEAD=3`+`SAMPLES=5` тоже не «гарантировал разрешение» при 1:1:1:1:1 — лишь давал больше шансов набрать majority / отрыв.

### 3. E — счётчики diag

**Где собирается diag:** пустой/стартовый словарь в `answer` — `z20_ask_main_http.py:1886–1887`:

```text
diag = {terms, preds, kind, parse: разбор, шаги}
```

дальше точечные `diag[…] = …`; наружу — `_diag_pack(diag, …)` (`z01:496–502`, добавляет `tokens` при наличии).

**Уже есть для D без новых ключей:** `diag["parse"]` = `intent.parse` → уже несёт `samples` и `unstable` (`z02:622`). Для приёмки «сколько сэмплов реально» достаточно читать `diag.parse.samples` / TRACE TOKENS — отдельный ключ не обязателен.

**Замки на структуру diag:** жёсткого «набора разрешённых ключей» / `frozenset(diag.keys())` в `test_*.py` **нет**. Тесты проверяют **наличие/значения** конкретных ключей (`diag.get("…")`, `_diag_pack` → `tokens`), не exclusive schema. Добавление `rerank_calls` / `deadline_aborts` / `early_clarify_path` **не ломает** замки, если:

1. не переименовывать/не затирать существующие ключи;  
2. значения — скаляры (int/bool), не раздутые списки;  
3. не класть счётчики в клиентский `text` / `options`.

**Куда вешать (минимально):**

| Ключ | Точка | Замечание |
|---|---|---|
| `rerank_calls` | инкремент в `z07_rrf_vectors.rerank` **или** обёртка с доступом к diag запроса | нужен контекст rid/diag на поток (как `_token_acc`), иначе счётчик в голом `rerank()` не доедет в ответ |
| `deadline_aborts` | чек-пойнт B (вход rerank / цикл арбитра) при истечении | +1 и выход unavailable |
| `early_clarify_path` | возврат раннего clarify (пункт A) | `1` / reason-строка; достаточно флага |

Риск «раздуют ответ»: три скаляра на фоне уже больших `шаги` / пулов — **пренебрежимо**. Не писать journal-таблицы (план верно).

## Атаки (≥3)

### A1. LEAD=2 + честный 2:1 → «консенсус» из двух голосов majority

При `SAMPLES=3` цикл **не может** набрать `lead≥2`, если есть второй кластер: max lead при 2:1 = 1. Merge всё равно отдаёт лидера 2:1. Раньше при `SAMPLES=5`+`LEAD=3` тот же вопрос мог добрать 4–5-й сэмпл и уйти в 3:2 / 4:1 или (реже) сменить лидера. На граничных `kind`/`terms` (класс 18/58) возможен рост **wrong** или flip match↔honest_no, даже если unit lead=2 зелёный.

**Смягчение:** D1 сначала только `LEAD=2` при **SAMPLES=5** (на 3:1 выход на 4-м, пятый ещё доступен при более грязном split); D2=SAMPLES=3 — только после ширины A + L67.

### A2. SAMPLES=3 + LEAD=2 на 1:1:1 → новый honest_no / смена пути

Поведение: **первый** сэмпл по полю, `unstable` помечен, перезапроса нет. Старый потолок 5 тоже мог оставить ничью с победой «раннего» кластера — но реже. На L это выглядит как: раньше majority из 5 совпал с эталоном, теперь «первый из трёх» увёл `kind`/`terms` → другой пул → honest_no вместо match (или наоборот).

**Смягчение:** смотреть в bench долю `parse.unstable` и отдельно кейсы с `distinct==3` на критичных полях; на L — flip-таблица вопрос×вердикт.

### A3. Stability 20×3 маскирует регресс ширины

Приёмка §0.2 зелёная на трёх «спокойных» вопросах при деградации 18/58→25/58 на полной ширине. Ложное «D готов».

**Смягчение:** §0.2 заменить протоколом A (+B); 20×3 не считать достаточным.

### A4. Счётчики diag / «раздуют ответ» (E)

Сами int-ключи безопасны. Реальный риск E — **неверный контекст** `rerank_calls` (глобальный счётчик между параллельными ThreadingHTTPServer-запросами без rid) → ложная приёмка C. Второй риск: класть подробные списки документов реранка в diag.

**Смягчение:** счётчик на запрос (thread-local / diag-объект), только инкремент HTTP-успеха/попытки; без payloads.

### A5. (стык) Путать `diag.parse.samples` с «LEAD сработал»

`samples=3` при LEAD=2 может значить и «единогласия не было до потолка», и «2:1 на третьем». Для гистограммы ранних выходов нужен либо TRACE числа TOKENS intent, либо явный `diag.parse.lead_exit=1` (опционально, не в минимальном E).
