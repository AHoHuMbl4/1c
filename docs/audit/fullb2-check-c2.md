## 5. Стык §2.3 ↔ §3.6 (внутренняя непротиворечивость)

### Что стыкуется

- unexpected ≡ `векторов_умрёт`; разность **множеством**; xfer вычитается;
  full не теряет entity-свидетелей без доказательства (§2.3 хвост = пробел №4).
- partial объясняет смерть через `gone_expand`; full — через прежние
  entity-wide свидетели.

### Конфликт формулировок

**§2.3 (стр. ~84–88):** `NOT EXISTS key_deleted_delta` «заменяется UNION по
mode»; для partial — предикат записан как **`EXISTS (gone_expand …)`**.

**§3.6 (стр. ~125–130):** `die_unexplained_base` уже «partial — замена на
row-level gone_expand по §2.3», **затем** `base EXCEPT gone_expand EXCEPT
xfer_old_keys`.

Риски для исполнителя:

1. **Двойное применение gone:** если base уже выкинул ключи ∈ gone_expand
   (§2.3), EXCEPT снова по gone — для множества безвредно (идемпотентно), но
   провоцирует COUNT-арифметику / «два места правды».
2. **Полярность EXISTS:** в живом unexplained свидетель = *исключение* из
   unexplained (`NOT EXISTS witness`). Голый `EXISTS (gone_expand)` в §2.3
   без рамки «explained IF …» читается двусмысленно (включить в unexplained
   vs объяснить).

### Правка (рекомендация контролёра; код не трогать)

**§2.3** заменить блок про die_unexplained на:

> `die_unexplained` строится в §3.6. Здесь только правило свидетелей
> **до** EXCEPT: mode=full — entity-wide `key_deleted_delta` (и прочие) **как
> сейчас**, не удалять без доказательства покрытия; mode=partial —
> **`key_deleted_delta` не использовать** (orphan-витрина не объясняет
> row-gone). Вычитание `gone_expand` — **только** в §3.6 через EXCEPT, не
> вторым фильтром в base.

**§3.6** уточнить base:

> `die_unexplained_base` = unmatched_emb_rows минус свидетели **без**
> gone_expand (full: включая key_deleted_delta; partial: без него; ch /
> collapse / rewrite / shrink / repost — по режиму как сейчас). Затем
> `die_unexplained_new = base EXCEPT gone_expand EXCEPT xfer_old_keys`.
