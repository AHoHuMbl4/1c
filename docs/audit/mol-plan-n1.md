## Разбор

### 1. Пул A2 «по intent kind из fork_label/alias одним SQL» — **опровергнут**

| Утверждение плана | Факт по коду |
|---|---|
| Кандидаты из `search_fork_label` / `search_entity_alias`, «ОДИН SQL по kind» | У `search_fork_label` **нет колонки kind**. Схема: `(fork_key, src, label, seen_at)` (`corpus_init.sql:343-344`). |
| Таблица даёт **все** ветки продаж для kind=продажи без K6 | **Ни одна**. `fork_key = sha1(src_set¦measure_ctx)` — класс **эквивалентности атомов**, который пишет **детектор на ask** (`corpus_init.sql:323-327`, `z09:_fork_log` / `INSERT INTO search_fork_class`). Это не каталог «все sales-сущности рода». |
| Те же таблицы, что кормят `mk_opts` | Частично: `mk_opts` зовёт `fork_labels_covering(srcs)` **после** того, как `srcs` уже известны (`z20:1092`); alias даёт **hints** (`opts_hints` ← `best_used_for`), не пул веток. Пул A = `arb_pool` после K6/wiki/fork. |
| Покрывает все виды | **Нет.** Подписи пишет `branch_alias.sh` только для классов, уже лежащих в `search_fork_class` и без полной подписи. Классы появляются, когда детектор **уже видел** развилку на живом вопросе — курица/яйцо для A2 до K6/fork. |
| Новая база / п.0: таблица размечается тактом автоматически? | **Нет как «все kinds».** Такт (`wiki_alias.sh` → `branch_alias.sh`, cap/`BRANCH_ALIAS_MAX_SEC`) дописывает подписи **существующим** классам. `search_fork_class` тактом **не** заполняется полным перечнем продаж. Холодная база: class пуст → label пуст → пул A2 пуст. |

Доказательства против «JOIN по fork_key = все ветки»:

- `fork_label_siblings` **снят** (`z09:751-758`): волна-1 раздувала `arb_pool` до сотен подписанных src; шаг 4 больше так не делает.
- `search_entity_alias` + `alias_idx @@ kind` даёт сущности, **похожие** на род (это уже поверхность «смысл/синонимы», `z20:2054-2114`, ~0.6 с) — **не** доказанную неоднозначность источника и не тот же набор, что после K6/`not_for`/wiki.

**Итог:** «все ветки продаж одним SQL по kind» из текущих таблиц **не существует**. Реализуемый суррогат — либо (а) FTS/alias по kind → **ложное меню** на любом >1 hit, либо (б) читать исторические `fork_class`/`fork_label` → **дыры и призраки**, не покрытие.

### 2. Точка вставки и фазы; критерий fingerprint

**Точка «ДО K6»** = непосредственно **перед** `K6R.apply_to_candidates` (`z20:2254`), т.е. после сборки `cands`/`prefer_*` (`2222-2239`), до маркера «K6 v2». План верно указывает порядок относительно K6; номер «2246» в ТЗ — зона каталогов/обёртки, фактический вызов — **2254**.

| Фаза | Обязательна до A2? | Почему |
|---|---|---|
| Разбор intent | **Да** | kind / want / measure / period / allow-lex (`want=list`, rank) — без этого нет гейта allow A |
| Отбор «буквально» + «смысл/синонимы» | **Для пула из cands — да; для «чистого fork_label» — нет, но такой пул невалиден (п.1)** | Если A2 строить из `by`+`extra` (реальный узкий пул до K6) — поверхности уже отработали (`2054`, `2114`). Fork_label сам по себе отбор не заменяет |
| `prefer_entity_for_sales` / stock-фильтры | **Желательно до** | Уже стоят **до** K6 (`2229-2239`); без них пул шумит |
| K6 | **Нет — обходим** | Смысл A2 |
| `not_for` / порядок emb / rerank | **После K6 сейчас** (`2288+`, `2482+`) | A2 их не видит → другой набор веток, чем у A |
| Wiki (`wiki_primary_entity_cascade` ~`2835`) | **Сейчас после K6** | Запрет «wiki уже выбрала» на точке A2 **нечем проверить**, пока wiki не перенесена раньше A2 или не зовётся лёгким префлайтом |
| Fork-детектор | **Нет** | `~2737` / исходы `3486+` — после wiki; для A2 не нужен и не должен запускаться |

**Fingerprint `≡` A/полного пути — структурно часто не сойдётся.**

- A (`3623+`): пул = `arb_pool[:ARBITER_MAX]` после K6 + not_for + order + wiki + doubt/signals.
- A2: любой пул до K6 ≠ этот `arb_pool`.
- `compare_menus` label/hint/src «≡» как у A — **ложный критерий приёмки** для главного кейса (тяжёлый отчёт, где A не успевает).

**Корректная формула приёмки (предложение):**

1. **Негатив (обязателен):** на контрольных Q, где полный путь (без дедлайна) даёт `kind∈{answer,figures}` / единственный src / wiki-lock / sales_canon — A2 **молчит** (`early_a2_path` отсутствует).  
2. **Позитив (где оба дают clarify):** сравнивать **множества `src`**, не порядок и не полный fingerprint≡:
   - `src(A2) ⊆ src_viable` (сущности с непустым `search_tables.label` и, если берём fork_label, непустым label ветки);
   - Jaccard(`src(A2)`, `src(A)`) ≥ порог **или** (слабее, но честнее для нового пути): каждый `src∈A2` проходит тот же allow-lex и **не** отсекается `not_for` на постпроверке офлайн-SQL;
   - текст меню: тот же `mk_opts`/`clarify_say`; `preds` те же, что у clarify-пути A (`preds=None` запрещён — P1).
3. **Тайминг:** меню ≤20 с; diag `early_a2_path=1`.  
4. **L67** группы A2+B+A; замки.

Итого: «A2 валиден, если ветки — реальные сущности с подписями, покрывают составной интент, и A2 не стреляет там, где полный путь ответил бы одним числом» — **да**; «fingerprint ≡ A на всех Q» — **нет**.

## Атаки (≥4)

1. **База без разметки `fork_label` (новая / холод).** Class пуст или labels пусты → при fail-closed «`<2` подписанных → полный путь» A2 молчит — **безопасно**, если так закодировано. Если план прочитает alias по kind и покажет меню из N синонимов — **ложный clarify**. Проверка: на пустом label A2 ≡ no-op.

2. **A2-меню vs wiki-лидер.** Wiki (`z21` / `wiki_primary_entity_cascade`) сейчас **после** K6 (`2835`). A2 до K6 **не видит** `wiki_arbiter_locked`. Атака: составной вопрос, wiki схлопнула бы в один паспорт → A2 всё равно спросит меню. Контрмера: префлайт wiki до A2 **или** не внедрять A2, пока wiki не перенесена / не доказано, что на allow-lex wiki почти никогда не lock (замер, не надежда).

3. **Дрейф подписей между тактами.** `branch_alias` обновляет labels асинхронно (бюджет/cap на такт); `fork_class` — снимок прошлых ask, не корпус. Меню читает **текущую** таблицу в момент запроса (не «кэш такта ask»), но подписи могут отставать от смены $metadata / исчезнувших src. Атака: ветка-призрак или устаревший смысл. Контрмера: требовать `src ∈ search_tables` + непустой label; при дырке — полный путь; не считать fork_label синхронным с данными (M4 At4).

4. **Двойное меню (клиентская несовместимость).** A2 вернул options {X,Y}; полный путь дал бы {Y,Z} или figures. Билеты `seal_clarify` / повтор «вариант 2» привязаны к показанному порядку. Fingerprint≡A не ловит это на тяжёлых Q (A не успевает). Атака: регресс L67 / путаница чипов. Контрмера: негатив «A2 не стреляет, где полный путь ≠ clarify»; на пересечении — сверка **множеств src**, не слепой ≡; diag раздельный `early_a2_path`.

5. **(доп.) Нулевые строки за период.** Без live `preds`-counts A2 показывает источники, которые K6/period отсеяли бы как 0 за «вчера» (M4 At4). При `preds` как у A — `mk_opts` считает live; **нельзя** отключать preds ради скорости.

6. **(доп.) Простой sales-sum с >1 alias hit.** Без A2-2 меню вместо канона/одного числа — п.21.

## Вердикт

**A2 к внедрению по тексту §1 плана — не готов.** Идея «меню до K6 на составных» из M4 (R1) верна как **направление**; спецификация пула и приёмки в MOL_PLAN §1 — **ложные**. Сначала правки плана, потом зонд на `:8092`.

### Правки плана (дословно внести в §1 A2)

1. **Пул:** запретить формулировку «один SQL по kind из `search_fork_label`/`alias` даёт все ветки продаж». Заменить: «пул A2 = пересечение (а) `cands` после буквально+смысл+`prefer_*` до K6 и (б) источников с непустым label (`search_tables` и/или `fork_labels_covering` на этом наборе); **не** расширение через fork_key-siblings; kind-only alias-FTS как единственный источник пула — запрещён».

2. **Точка:** «вставка непосредственно перед `K6R.apply_to_candidates` (`z20:2254`), после `prefer_entity_for_*` / stock-фильтров (`2222-2239`). Intent — да; fork-детектор — нет; wiki — либо префлайт до A2 с теми же wiki-запретами, либо A2 не внедрять до решения по wiki».

3. **Allow:** только составной/отчётный (`want=list` / лексика полного отчёта / «и чего» / rank-ось) — **как `_ec_composite` у A**. Ветку `_ec_src_ambig` на A2 **не** копировать (сигналов ещё нет).

4. **Запреты:** полный список A (п.3 таблица 1–14) **плюс** A2-1…A2-7; явно: «пул из словаря ≠ доказанная неоднозначность; любое сомнение / неполное покрытие labels / ≤1 opts → полный путь».

5. **Приёмка fingerprint:** заменить «fingerprint ≡ A/полного пути» на:  
   (а) негатив — A2 молчит, где полный путь без дедлайна → answer/figures/wiki-lock/canon;  
   (б) на Q, где оба → clarify: сверка **множеств `src`** (+ непустые label/hint; тот же `mk_opts`/`preds`);  
   (в) тайминг ≤20 с; `early_a2_path=1`;  
   (г) L67 группы A2+B+A; замки.

6. **§5 «Не делаем»:** усилить — «A2 в прод без негативной приёмки (п.5а) и без решения по wiki-префлайту — запрещён»; оставить запрет SAMPLES=1 / рост дедлайна.

7. **П.0 / новая база:** явно записать: «`search_fork_label` не размечается тактом для всех kinds; class пишет детектор ask, labels — `branch_alias` пачками; холод → A2 no-op».

8. **Диаг:** `early_a2_path` отдельно от `early_clarify_path` (A после fork).
