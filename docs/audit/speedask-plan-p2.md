## C1 — entity-rerank (z20:2562) в arbiter-подвызовах при focus

### Что делает код сейчас

Блок entity-rerank (`z20:2481–2566`): при `ORDER_BY_MEANING` и `len(cands)>1` зовёт `rerank(question, labels)` и **переставляет** `cands`; ставит `diag["order_by"]="rerank"`. Сигнал `top_by_question` (вектор) **не трогается** (коммент :2540–2542).

Применение focus — **после** этого блока (`:2748+`):

```2804:2806:ubuntu/serenedb/ask/z20_ask_main_http.py
    if focus:
        picked, marks, plan = [focus], {}, {}
        diag["focus_forced"] = focus
```

Арбитр (`:3621–3629`) зовёт `answer(..., focus=c, no_arbiter=True)`.

### Влияет ли порядок пула на выбор / паспорт в подвызове?

| Потребитель `cands` | В подвызове `focus`+`no_arbiter` | Вердикт |
|---|---|---|
| Выбор сущности | `picked=[focus]` | **нет** — сущность уже задана |
| Wiki-каскад | ветка `else` без focus (`:2828+`) | **не зовётся** |
| Fork-детектор (`cands[:ARBITER_MAX×4]`) | гейт `not no_arbiter` (`:2673`) | **не зовётся** |
| Набор соперников из порядка (`order=list(cands)…`) | гейт `not focus and not no_arbiter` (`:3301`) | **не зовётся** |
| Исходы fork A/B/C | гейт `not no_arbiter` (`:3473`) | **не зовётся** |
| Круг арбитра | гейт `not no_arbiter` (`:3613`) | **не зовётся** |
| Паспорт (`src=picked[0]`, мера, ось) | `src` = focus (`:3931`) | **не** берёт порядок пула для сущности |
| `sales_canon_src` / `prefer_entity_for_sales` | работают по **множеству** cands + score регистра (`z11:323–339`), не по rerank-порядку головы | порядок entity-rerank **не** выбирает канон |

Остаточный след порядка: `need |= cands[:ARBITER_MAX*4]` (`:2895`) — какие src попадут в загрузку `par`/`служебные`. При `no_arbiter` этот метаданные-пул **не кормит** rival/fork-решения. На ответный `src` не влияет.

**Wiki** (`wiki_primary_entity_cascade`) параметр `cands` в теле **не использует** — пул вики свой (`wiki_hybrid_pool`).

### Опасен ли C1?

В **скоупе плана** (подвызовы арбитра = `focus` ∧ `no_arbiter`) — **нет**: результат entity-rerank не выбирает сущность и не выбирает поля паспорта. Атака «паспорт берёт другого кандидата» **не держится** для этого скоупа.

⚠️ Расширять guard на «любой `focus` без `no_arbiter`» (кнопка человека) **нельзя молча**: при `focus` и `no_arbiter=False` fork-детектор **всё ещё** читает голову `cands` (`:2673` — только `no_arbiter` гасит). План должен явно писать guard: `if focus and no_arbiter: skip entity-rerank` (или эквивалент S1-P3).

### Что теряется при C1

Только HTTP и перестановка локального `cands` / `diag.order_by` в подвызове. На текст/число/паспорт под-ответа — ничего существенного. Внешний (первый) entity-rerank **обязан остаться** — он кормит rival-порядок внешнего круга (`:3316`).

### Правка дословно (план)

> **C1:** в `answer()`, блок entity-rerank (`z20:2481–2566`) **не выполнять**, если `focus` задан **и** `no_arbiter is True` (подвызов арбитра). Внешний `answer` без `no_arbiter` — блок как сейчас. Не распространять на сырой `focus` без `no_arbiter` без отдельного L-прогона fork.

## C2 — short-circuit N≤1 (`rerank` z07:348)

### Где вставить

Сразу после текущего раннего выхода на пустой вход (`:354–355`), **до** сборки HTTP-body:

```python
def rerank(query, docs):
    if not query or not docs or not RERANK_KEY:
        return []
    if len(docs) <= 1:
        return [0]          # или [] — вызывающие при пустом idx оставляют прежний порядок
    # … HTTP …
```

Предпочтительнее `return [0]`: контракт «успешный порядок индексов» для единственного документа; `[]` тоже безопасен у всех callers (entity / measure / axes / resolve — все ветвят `if idx:`).

### Текущее поведение при 1 кандидате

Обхода **нет**. При `len(docs)==1` всё равно POST; журнал пишет  
`rerank отработал: 1 кандидатов, порядок без изменений` — HTTP уже оплачен (~1–2 с).  
В срезе `ask-units.log` (S1): **8×** таких строк из 31.

**Вывод:** «порядок без изменений» **не** значит «HTTP не нужен уже сейчас» — наоборот, это чистая потеря. C2 убирает сеть; строку stderr при short-circuit **не** писать как «отработал» (иначе счётчик HTTP врёт) — писать отдельно или только инкремент `rerank_short`.

### Правка дословно

> **C2:** в начале `rerank()` после проверки пустого входа: `if len(docs) ≤ 1: return [0]` без HTTP и без строки «rerank отработал». Счётчик: `short_circuits += 1`, не `calls`.

## C3 — кэш по входу в пределах rid

### Вход кэша

Ключ: `(RERANK_MODEL or RERANK_API, query, tuple(docs))`.  
`docs` — уже список строк, ушедших в POST (метки / имена мер / оси). Модель в ключе обязательна: смена env внутри процесса не должна отдавать чужой порядок.

### Где хранить

**ContextVar**, по образцу `_token_acc` / `_rid_ctx` (`z01_infra_trace_llm.py:67,439`):

- `_rerank_cache: ContextVar[dict | None]` — `dict[key → order]`;
- старт: рядом с `_token_acc_start()` / `_rid_enter` на HTTP-входе (`z20:5773`, `answer` при `acc is None`);
- hit/miss внутри `rerank()` до HTTP;
- **запрещено:** модульный глобальный LRU / lru_cache на функцию (дрейф базы между запросами, чужой rid в ThreadingHTTPServer).

Вложенные `answer(focus=…)` идут в **том же** потоке и том же ContextVar (acc стартует только если `None` — `:1821–1822`) → кэш естественно схлопывает внешний B + arbiter×3 с тем же `(question, labels)`.

### Инвалидация

1. Новый HTTP-запрос → `_rid_enter` + новый пустой dict (или `None`→create).  
2. Конец запроса → GC вместе с контекстом потока (не переживает rid).  
3. Внутри rid **не** инвалидировать по времени: корпус read-only на запрос; смена labels mid-request не предусмотрена кодом.  
4. При сбое HTTP (`return []`) — **не** кэшировать провал (иначе повторный caller навсегда без сигнала).

### Атака «кэш скрывает дрейф синонимов внутри долгого запроса»

Внутри одного rid labels читаются из БД на месте вызова; повтор с тем же ключом = те же строки. Дрейф синонимов **между** запросами кэшем rid не маскируется. Реальный риск — **неверный ключ** (забыли `docs` / взяли только `query`) → ложный hit разных пулов. Приёмка: unit «разные docs → miss»; «одинаковые → один HTTP».

### Правка дословно

> **C3:** кэш только ContextVar на время rid; ключ `(model/api, query, tuple(docs))`; miss→HTTP→store; fail→не store; глобальный LRU запрещён. Diag: `rerank.cache_hits`.

## C4 — measure-rerank (z16:619) перед заведомым refuse

### Цепочка

1. `measure_choice` (`z14:30–83`) чисто решает `how`; при `how != 'rerank'` `pick_measure` **уже не** зовёт HTTP (`z16:617–618`).  
2. HTTP только если правила не решили (`how=='rerank'`).  
3. После возврата в `answer` (`z20:4119–4124`):

```4119:4124:ubuntu/serenedb/ask/z20_ask_main_http.py
        if how == "rerank" and (plan.get("compute") in ("sum", "max", "min", "avg")
                                or intent.get("want") == "sum"):
            alts = measures_of(src)
            if len(alts) > 1:
                measure, measure_alts = None, alts
                diag["measure_guess_refused"] = how
```

То есть на sum/max/min/avg при нескольких мерах вердикт **refuse/clarify** сбрасывает результат HTTP. Аналогично rank-ветка `:4101–4108` (`measure_guess_refused=rank_rerank`).

### Заведомые refuse **до** HTTP

Да, на call-site **до** `pick_measure` можно знать:

- `measure_choice(names, word) → how=='rerank'` (дешёво, без сети);
- `plan.compute ∈ {sum,max,min,avg}` ∨ `want==sum`;
- `len(measures_of(src)) > 1`.

Тогда исход после HTTP почти всегда `measure_guess_refused` — HTTP лишний **для refuse**.

### Меняет ли rerank refuse→answer?

**Да, есть путь:** внутри `pick_measure` после HTTP возможна ветка `how='base'` (`z16:627–633`): частный вид → база, возврат `'base'`. Тогда проверка `:4119` (`how == "rerank"`) **не срабатывает**, и сумма **отвечает** базовой мерой, а не уходит в clarify.

Слепой skip HTTP + принудительный refuse **меняет** качество на этих кейсах (answer→clarify).

Также wiki-collapse (`z21:745/751`) зовёт `pick_measure` — C4 должен покрыть оба call-site или жить внутри `pick_measure`.

### Правка дословно

> **C4 (переформулировать):** не «не звать перед refuse», а:  
> (a) в `pick_measure` / call-site: если `measure_choice→rerank` и заранее известно `sum|max|min|avg` + `len(names)>1`, **сначала** попробовать то же base-правило **без** ранжирования (база как единственный префикс ≥2 частных); если base однозначен → `how='base'` без HTTP;  
> (b) иначе при тех же условиях → сразу `(None, names, 'rerank')` + пусть caller ставит `measure_guess_refused` **без** HTTP;  
> (c) не пропускать HTTP, если base-проба неоднозначна и refuse не заведом.  
> Приёмка: `test_gate` measure + L sum-вопросы; сравнить число `measure_guess_refused` до/после.

## Счётчик «rerank отработал» (п.6 плана / §1.E)

### Где считать

**Внутри `rerank()`** (единственная HTTP-точка) — иначе callers разъедутся.

Форма (зеркало `_TokenAcc`):

```python
# z01: ContextVar
_rerank_acc = contextvars.ContextVar("rerank_acc", default=None)

class _RerankAcc:
    __slots__ = ("calls", "cache_hits", "short_circuits", "by_caller")
    # calls = только реальный HTTP
    # by_caller: опционально через kwarg caller=... позже; v1 можно без

def _rerank_acc_start():  # из _rid_enter / рядом с _token_acc_start
    _rerank_acc.set(_RerankAcc())

# в rerank():
#   short → short_circuits += 1; return
#   cache hit → cache_hits += 1; return order
#   HTTP ok → calls += 1; stderr как сейчас
#   HTTP fail → calls += 1 (попытка была) или отдельно fails — зафиксировать в плане

# в _diag_pack:
acc = _rerank_acc.get()
if acc:
    d["rerank"] = {"calls": acc.calls, "cache_hits": acc.cache_hits,
                   "short_circuits": acc.short_circuits}
```

`diag.selection_budget.reranked` **не** заменяет: это размер головы B, не число HTTP.  
Stderr `rerank отработал` оставить для journald; для приёмки C — поле diag (есть rid в ответе/TRACE).

## Атаки (≥4)

### (1) C1 → другой кандидат в паспорте

**Сценарий:** skip entity-rerank в подвызове → другой порядок `cands` → паспорт другой сущности.  
**Разбор:** в скоупе `focus`+`no_arbiter` сущность паспорта = `focus_forced`; порядок пула не выбирает src.  
**Вердикт атаки:** **отклонить** для заявленного скоупа. Оставить в плане явную оговорку guard, чтобы не расширили на `focus` без `no_arbiter`.

### (2) C3 кэш скрывает дрейф синонимов внутри долгого запроса

**Сценарий:** первый вызов закэшировал порядок по старым labels; позже в том же rid aliases/labels обновились.  
**Разбор:** в одном ask labels не пересобираются mid-flight; межзапросный дрейф кэш rid не держит. Риск — только битый ключ.  
**Вердикт:** **слабая**; закрывается контрактом ключа + запретом LRU. Не стоп для C3.

### (3) C4 убирает rerank, который кормил diag/quality / base→answer

**Сценарий:** skip HTTP на sum → нет `'base'` → лишний clarify; или diag без следа «rerank пытался».  
**Разбор:** по коду `how='base'` **меняет** refuse→answer. Слепой C4 — регресс п.21.  
**Вердикт:** **принять** — C4 в текущей формулировке опасен; нужна переформулировка (см. выше).

### (4) Сумма C1–C5 не достигает ≤5 HTTP, а план/S1 обещают

**Сценарий (типовой тяжёлый list/sales):**  
остаются: 1× внешний B + 0…N× resolve A (`RESOLVE_NEAR=12`) + 1× D + 0…1× E/C + grain.  
C1 режет только arbiter-B (×≤3); C2 — только N=1; C3 — повторы; C4 — 0…1; C5 — 0…2.  
При `понятий>0` и нескольких пустых term-группах путь A один может дать несколько HTTP по 12 — **цель ≤5 не выполняется** без A/P4 или раннего clarify (пакет A).  
План §1.C обещает «−20…60с», S1 — «≤5»; §1.E считает приёмку счётчиком, но **не** фиксирует «≤5 обязательно на всех классах».  
**Вердикт:** **принять** как атаку на обещание S1, унаследованное планом. v2: «≤5 — целевой ориентир на cold list **без** resolve-фолбэков; иначе потолок = baseline − (C1…C5)» + не блокировать пакет из-за A.

### (5) C5 «удалить z05 или z17» ломает count-ось

**Сценарий:** исполнитель читает план буквально и вырезает `_pick_kind_axis_col` rerank.  
**Разбор:** это единственный смысловой выбор оси при нескольких matched cats — п.10/12.  
**Вердикт:** **принять** — формулировка C5 в плане дефектна до правки.
