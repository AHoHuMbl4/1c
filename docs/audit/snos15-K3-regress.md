## 2. Недостаточность приёмки

### 2.1. Контрольные 2–3 вопроса ≠ откат-решение

Откат по PLAN: `Δconfident_wrong > 0` **или** контрольный дал wrong/число-вместо-меню.
При 2–3 контролях:

- покрытие **~3/67** вопросов;
- sales-канон держал **до ~9** match — один «вчера продали» не репрезентирует
  неделю/месяц/воскресенье/«вышло»/«наотгружали»;
- register-count **31** — один «кассовыеордера» или «реализациятмц» не ловит
  flip соседнего регистра после смены порядка пула;
- false green: контрольный ушёл в **clarify** (норм), а другой q той же группы —
  в **wrong**.

P3 §0 уже требует kind-разрез jsonl и срезы групп; **PLAN волны** формулируют
только «контроль: …» без обязательного среза N и без порога «сколько clarify
допустимо, пока wrong=0». Для откат-решения после **волн 2, 3, 4, 5, 7**
контрольных вопросов **недостаточно**.

### 2.2. Какие группы L67 гнать после каждой волны (конкретно)

Счёт по `client-gold-okna.tsv` (67 q): sales-маркеры ≈9; stock/склад/петли ≈21;
register «движений/записей» =31; period-маркеры ≈9. Ниже — **обязательный
минимум среза** (не замена полному L67):

## 3. Скрытые wrong (верное число, чужая мера/ось/окно)

### 3.1. Что видит приёмка сейчас

`i2_runner.classify_verdict`: при `kind∈{answer,figures}` решает
**`numbers_match_etalon(nums, etalon)`** (+ `diag.found`/`doubt`).  
**Не сравнивает:** `src_table`, `measure_id`/`measure_name`, `period`/`form_id`,
`axis`, `wiki_verify`, `decision_id`.

Следствие: ответ с чужой мерой/окном при **том же числе** = **match**. P3 цель 3
это уже назвала («wrong скрытый»); PLAN **не вводит** обязательный diag-разбор.

Живой прецедент эпохи (CHANGELOG 02.09): «позавчера» — nums['Сумма']=0 vs
nums['Всего']≈5919; разъехались — попали в wrong. Если бы обе ветки дали 0,
вердикт был бы **match** при разных мерах.

### 3.2. Нужен ли обязательный diag после волн 3 и 7?

**Да — и не только 3/7.**

| после волны | обязательный разбор atom/diag на всех **бывших match** среза | поля |
|---|---|---|
| **2** | sales + named sales-registers | `src_table` vs эталонная эпоха (снимок jsonl до волны); `wiki_pick`/`verify` |
| **3** | sales | `measure_id` / class money\|qty; стоп: answer при `measures_of>1` без `measure_choice` (P3 уже хочет замок) |
| **4** | register-count 31 + sales | `src_table` стабильность vs якорь волны |
| **6–7** | period∩sales | `period` / `form_id` / `assumed`; стоп: answer при ≥2 readings без меню |
| **5** | multi-src sales | нет `arbiter` silent win; не `cand_src[0]` |

Без этого стоп `Δconfident_wrong` **официально зелёный** при нарушении п.10 по
смыслу (чужая величина с тем же числом).

## 5. Скорость: −52 с K6 — где замер врёт

PLAN: «−~52с K6»; контроль волны 4: «wall до wiki заметно ↓ (полигон, было ~52с K6)».

Откуда 52с: MOL (`MOL_PLAN_2026-09-11`, маркер wall «K6 v2» ~z20:2269) —
класс **«полный путь»**, где A2/early-clarify **не** перехватил; цель была
52→≤10 индексом/витриной, не сносом. Анти-двойной счёт: A2 и K6 на **разных**
классах вопросов.

| ловушка замера | почему врёт |
|---|---|
| **Не зафиксирован rid** | «широкий вопрос» / «продажи за квартал» вне L67 — без стабильного текста+URL нельзя сравнить до/после |
| **Класс вопроса** | после сноса канона/K6 тот же текст чаще уходит в **early-clarify A** (меню ≤20с) — выигрыш атрибутируют K6, хотя сработал A2/A-clarify (MOL §0) |
| **«wall до wiki» vs total wall** | K6 сидел **до** wiki; total wall может вырасти (arbiter/fork/wiki LLM), пока префикс ↓ |
| **холодный vs тёплый** | 52с — холодный широкий пул; повтор на полигоне даст другие десятки секунд |
| **полигон :8092 vs прод :8091** | разная нагрузка/DSN/`probe_root`; P3 неясно-8 — не смешивать в одном отчёте |
| **L67 средний wall** | большинство register-count **не** платят 52с K6 — среднее L67 почти не сдвинется; «пакет −52с» по L67 = ложь |
| **Снос ≠ MOL-ускорение** | MERGE §3.3 отменяет ускорение K6; обещать «−52с» как итог пакета = перенос чужой метрики |

**Минимум честного замера (дыра PLAN):** до/после волны 4 на **одном**
зафиксированном rid класса «полный путь» (TRACE/маркер бывшего K6 или
эквивалент «время до входа wiki_cascade»), полигон; отдельно — rid класса
«меню» (ожидание: K6 и так не доминировал). Не использовать Δ среднего L67
как доказательство −52с.

## 6. Откат волны 2 (z11 целиком): восстановит ли поведение?

PLAN: `git revert` пат-спеком волны + выкат. Волна 2 трогает: **z11 целиком**,
call-sites z20, lock, helpers period_empty/fork-empty, bypass z21:671-673,
prefer z10, YoY-clarify, early-clarify `_ec_locks`, `_bootstrap`
sales_canon_post+fork_b, **инверсия замков** (sales_canon → негатив,
wiki stubs).

| риск | почему откат может **не** вернуть прежнее |
|---|---|
| **Соседние волны уже в main** | волна 3 срезает «мёртвые» measure-ветки, завязанные на lock; revert z11 возвращает lock, а тело меры уже другое → **не** эпоха до волны 2 |
| **Один файл `_bootstrap._patch_z20_wiki_primary`** | волны 3/4/9 правят ту же функцию; revert только hunks волны 2 на конфликте/частичном состоянии → рантайм≠диск (P2 §16) |
| **Замки/негативы** | revert кода без revert тестов (или наоборот) → зелёные замки при красном поведении |
| **YoY / `_ec_locks` переписаны** | «оставить A-clarify, убрать опору на lock» — revert должен вернуть **оба** смысла; частичный revert оставляет clarify без канона |
| **P1-упаковка** | если волна = #1+#2+#4+#14a, откат тянет K6+сито; «вернуть только sales» точечно **невозможно** пат-спеком одной волны |
| **Выкат/полигон** | revert в git без `deploy-ask.sh`+рестарт — прод остаётся на сносе; ложный «откат» |

Вывод: откат волны 2 **восстанавливает поведение только если** (а) это
следующий коммит без наложений 3+, (б) в коммит волны входят код+bootstrap+замки
одним пат-спеком, (в) выкат симметричен. Иначе «revert» ≠ эпоха L19.
