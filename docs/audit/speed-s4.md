## Атаки

### A1. Rerank ≤5 → смена сущности → wrong?

**Факт пути (W1):** HTTP `rerank` зовётся не один раз, а из разных мест на один вопрос:

| Caller | Роль |
|---|---|
| `z20_ask_main_http.py` ~2562 | порядок головы сущностей (`RERANK_TOP`, default **60**) |
| `z16_veto_pick_entity.py` ~619 | `pick_measure` при `how=='rerank'` — **на каждую** сущность без словарного выбора |
| `z10_rank.py` / `z17_aggregate_groups.py` | оси группировки / `kind_axis_rerank` |
| `z07_rrf_vectors.py` ~559 | `resolve_near` |

«~30» в срезе — сумма этих циклов (1–2 с × десятки), не «лишний сторож в конце». Сокращение до ≤5 осмысленных вызовов **меняет порядок и состав входа** в каскад: кто в голове 60, какая мера/ось выбрана до паспорта.

**Решение №1 («один судья»):** судья — паспортная верификация z21; rerank — **вход пула/порядка**, не судья. Урезание входа ≠ «убрать лишнего судью». Если урезание выкидывает верную сущность из головы или меняет меру → паспорт верифицирует **другого** лидера → при прохождении паспорта = **wrong** (п.10 хуже отказа); при провале = лишний honest_no/clarify (п.21: отказ/уточнение при наличии данных — дефект, если верный путь был достижим полным rerank).

**Решение №2 («чинить НАЧАЛО»):** чинить **начало** = понимание → пул → выбор → верификация. Слепой cap «≤5 HTTP» на **середине** (меры/оси после уже собранного пула) — классическая починка **дорогого хвоста/середины** скоростью, без доказательства, что начало (полнота пула) не пострадало. Ранний entity-clarify **до** arbiter×N ближе к «началу развилки»; тупое урезание measure/axis-rerank — нет.

**Где wrong реалистичен:**

1. Верная сущность была на позиции 6…N после RRF/смысла; без entity-rerank или с урезанной головой не дошла до wiki/passport → другой src → число другого отчёта.  
2. `pick_measure` без rerank берёт первую/словарную меру там, где раньше rerank отделял «Сумма» от «СуммаВР*» → другое число при том же src.  
3. Ось rank/list («чего продали») меняется → другой grain → L-match ломается или wrong по составу.

**Вердикт A1: ОТКЛОНИТЬ слепой cap.** Допустимо только с явным контрактом: какие из 5 классов вызовов режутся; что остаётся обязательным (минимум 1× entity-head на полный кандидатский набор в бюджете п.19); замер «эталон в голове до/после» на L-корпусе.  
**До выката обязательно:** замки (intent/compose/action/fork/…) **и** полный L-прогон 67 с `wrong ≤ L19` (для ослабления — цель **wrong=0** по п.10 activeContext, не «проба на 3 вопросах»). Скорость без L = не приёмка.

### A2. INTENT_SAMPLES 5→1 — вернём разброс match↔honest_no?

**Да. Это уже измерено и записано в код.**

`z02_intent.py` (докстринг `parse_intent`, замер 04.08):

- при `temperature=0` **18/58** вопросов расходились между прогонами (`kind`, `terms`);
- «товар»/«товаров» → 22/32 общих кандидатов; «выручка»/«продажи» → **5/32**;
- имитация: **1 прогон = 22 % мимо большинства**; до 5 с отрывом 3 → ~8,4 %;
- `ASK_INTENT_SAMPLES=1` в CHANGELOG 04.08 явно = «возвращает прежнее поведение»;
- activeContext до сих пор: «Разброс разбора между прогонами (INTENT_MEMO внутри прогона только)» — **открытый долг**, не закрытый samples=1.

Замок `test_intent.py` (162/0) — **оффлайн форма** (JSON→структура, согласие/отрыв при **подменённой** модели, memo). Он **не** ловит живой разброс 27B. Зелёный 162/0 при samples=1 **не доказательство** стабильности ответов.

**Вердикт A2: samples=1 — ЗАПРЕТ без нового замера модели.** 1–2 допустимы только если:

1. Живой `intent_parse_bench` / эквивалент: **M≥58** вопросов (канон разметки или L-корпус), **N≥5** независимых холодных разборов **без memo** (`ASK_INTENT_MEMO=0`), счётчик идентичности по каноническому отпечатку полей, влияющих на счёт: `kind`, `want`, `measure`, `period`, `amount`, `action_class`, `terms` (нормализованные).  
2. Критерий: доля полного согласия отпечатка ≥ порога, при котором ожидаемый flip L-вердикта < 1 кейса на 67 (практически: **≥95 %** идентичности на M×N, иначе не трогать default).  
3. Два полных L-67 подряд на одном билде: **ноль** вопросов с flip `match↔honest_no` / `match↔wrong` при одинаковом эталоне окна (сверка по `answers.jsonl`, не по усечённой колонке nums — activeContext).  
4. Если оставляют samples=2 — обязан жить `INTENT_LEAD` (не «всегда 2 впустую» и не «всегда 1»).

Без (1)+(3) план с S2=1 **отклонять целиком**.

### A3. Ранний clarify vs п.21; «3 ветки продаж»

**Развести типы (W2 + PLAN_ANSWER_CONTRACT):**

| Что в жалобе WebUI | Это | Авто-развести мерой/периодом? |
|---|---|---|
| «Оптовые продажи / Движения / Реализация ТМЦ» | **entity-clarify** (разные src) | **Нет.** Разные атомы по src → молчаливый выбор = догадка (п.12). Контракт: A только при **тождественном** атоме; иначе B (число лидера + люк) или C/clarify. |
| day_basis / amount_basis / window | fork **B/C** | Числа/подписи кодом; не «ускорить угадыванием одной ветки». |

Ранний clarify **после** того, как в пуле ≥2 живых различных src/подписи и **до** `ARBITER_MAX` полных под-`answer` — это п.21.2 (уточнение при сомнении), не отказ от продукта. Тратить 154 с на arbiter×N, чтобы потом спросить то же меню — дефект **скорости пути**, не требование п.21 «сначала посчитай всё».

**Риск против п.21:** clarify **раньше доказательства**, что ответ единственен (урезанный пул / без fork-scan / эвристика по словам «полный отчёт») → ложный clarify там, где L19 давал **match** → падение доли ответов при наличии данных = дефект п.21. W4/Q4 со ссылкой на вызов#3 (15 с) как на «ранний путь» — **ошибка калибровки** (W2: вызов#3 другой профиль, не early-exit).

«Может, систему можно развести автоматически (мера/период)» для **трёх отчётов продаж** — **нет**: это разные источники, не разные окна одной сущности. Автовыбор одного = п.12.

**Вердикт A3: УСЛОВНО ПРИНЯТЬ** только формулировку: «entity-clarify / fork-C **до** цикла arbiter×N, при том же условии неоднозначности, что сейчас даёт clarify; без новых эвристик по тексту; без silent pick». Приёмка: на золотом «полный отчёт» — `kind=clarify`, opts≥2, **мс < 20k с первого вызова**; на однозначных L-match — **0** новых clarify вместо answer. Полный L-67 обязателен.

### A4. Отмена при обрыве → INTENT_MEMO / качество записи?

**Сейчас:** serene-ask = `ThreadingHTTPServer` без wall-cancel; клиент рвёт `urlopen` — сервер **продолжает** (W1/W2). Orphan жрёт rerank/GPU и портит следующие ask — отмена **нужна для качества следующих ответов**.

**Риски при наивном kill:**

| Состояние | Риск |
|---|---|
| `_INTENT_MEMO` (dict процесса, запись в конце `parse_intent`) | Kill **после** merge, но до/во время `json.dumps` маловероятен; опаснее — **записать неполный/чужой** out при cancel mid-merge, или clear при переполнении во время чужого запроса. Dict **без lock** уже гонка при параллельных ask. |
| `_FACTS_MEMO` (`z20`) | Та же схема: писать только на успешном полном факте. |
| `decision_id` / pending (`z14`, mcp_ask_pending) | Обрыв **до** ответа clarify: билет не выдан — ок. Обрыв **после** выдачи, до выбора клиента — pending должен жить. Cancel не должен `clear_pending` чужой сессии. |
| `ask_choice_memory` (SQL) | Cancel mid-UPDATE → частичная запись выбора; нужен контракт «commit только на завершённом исходе». |
| SQL/соединение SereneDB | Рвать поток mid-query → грязная сессия/слот; cancel = cooperative checkpoints **между** фазами, не `kill -9` воркера с живым psql. |

**Вердикт A4: ПРИНЯТЬ отмену orphan с жёстким контрактом.** Memo/билеты/память выбора — **только после успешного завершения фазы**; cancel до конца parse → **не писать** memo; cancel после clarify-ответа клиенту → не трогать выданные `decision_id`; не разделять один процесс-глобал без синхронизации при параллели. План без этого пункта — **отклонить**.

### A5. Единый протокол приёмки структурного пакета

**Порядок (строго, без перестановок «потом L»):**

1. **Оффлайн-замки ask** (минимум): `test_intent` 162/0, `test_compose` 92/0, `test_action_class`, `test_fork_outcomes` / `test_fork_detector`, `test_decision_id`, релевантные k4/passport/gate — все зелёные на дереве кандидата.  
2. **Контракт отмены** (если S3 cancel в диффе): юнит/проба «обрыв → нет записи memo; следующий ask не видит полуготовое; pending чужой сессии цел».  
3. **Живой intent-stability** (если трогали SAMPLES/LEAD): N×M как в A2, memo=0.  
4. **Полный L-прогон 67** (workers 16, канон TSV выката, сверка `answers.jsonl`):  
   - `wrong ≤ L19.wrong` (при любом ослаблении проверки/отбора — **wrong=0** по правилу activeContext/п.10);  
   - `match` не ниже L19 без поимённого разбора каждого потерянного match (п.21);  
   - нет новых flip-классов на повторном прогоне.  
5. **Живые тайминги WebUI/прямого `/ask`** на 3 классах (W4):  
   - A простой числовой → answer ≤15 с, число = эталон;  
   - B составной → **первый** clarify ≤20 с;  
   - C после `decision_id`/`focus` → отчёт без TimeoutError и без второго clarify.  
6. **Сравнение с L19 baseline** (таблица: match/honest_no/wrong/unresolved + список изменивших вердикт qid).  
7. **Стоп-точка владельца** до выката на прод-ask.

**Критерий отката (любой = STOP + откат билда ask):**

- `wrong` вырос vs L19;  
- любой уверенный wrong на бывшем match;  
- >2 новых ложных clarify на бывших match **или** доля match упала без разбора;  
- intent-identity ниже порога A2;  
- класс B снова >60 с до первого clarify **или** TimeoutError на отчёте после выбора;  
- замок ask красный;  
- затронуты вектора/такт/B (выход за периметр) — откат всего пакета.

### A7. Требования к плану (без них план не принимать)

План структурного ускорения **отклоняется**, если в нём нет **всех** пунктов:

1. **Разделение S1/S2/S3** на независимые диффы с отдельной приёмкой (не один «ускорили всё»).  
2. **S1:** таблица «какой caller режем / что оставляем»; доказательство «эталон сущности в голове до passport» на L-корпусе; явное отрицание «cap ради cap».  
3. **S2:** запрет default=1 без замера A2; если 2 — формула LEAD; memo не выдавать за стабильность.  
4. **S3 clarify:** только entity/fork-C до arbiter×N; ссылка на PLAN_ANSWER_CONTRACT A/B/C; запрет silent pick среди трёх sales-src; метрика «0 ложных clarify на L-match».  
5. **S3 cancel:** контракт memo/pending/SQL; cooperative cancel; запрет kill mid-query без восстановления соединения.  
6. **Протокол приёмки A5** целиком (замки → stability → L67 → тайминги → compare L19 → стоп-точка).  
7. **Периметр A6** явным списком «не трогаем».  
8. **Откат:** однострочный критерий + команда отката выката ask.  
9. **Соответствие решениям №1–2:** rerank/clarify описаны как входы/порядок пути, не как новые сторожи-судьи; плохое качество → правка начала (пул/понимание), не новый post-filter.  
10. **TARGET:** явное утверждение, что ни один пункт не ослабляет п.10/12; любое ослабление проверки сопровождается полным прогоном с **wrong=0**.
