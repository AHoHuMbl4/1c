# СНОС-15 Z2: мера после лидера — число+люк

Линза Z2 волны Z. Код только читался (`ubuntu/serenedb/ask/` на диске +
рантайм-патч `ask/_bootstrap.py` ~:118–224). База/серверы не трогались.
Срез: 11.09.2026.

Два текста владельца, которые сводим:

1. **Контракт начала дня (меры):** «сколько продали» → одно число сразу.
   Второе число — снятие допущения, не вопрос «какое твоё». Меню
   «100к или 500к» — отказ от продукта. Исходы: **A** одно число (разный
   src, одно число) — люк не открывать; **B** числа разные + человеческие
   подписи — ответ лидера + люк с подписью; **C** нет подписей — одно
   число + «есть другое прочтение», ветки не называть.
2. **Формула №15:** вопрос → интерпретация из вики → запрос → варианты с
   описаниями из вики (если прочтений >1) → выбор человека → ответ.

Живой замер (контекст задачи): после выбора сущности бот строит **мерные**
меню («итого? / сумма без НДС? / количество?») на каждом «сколько продали»
→ match 20→8.

## 1. Что в вики-паспорте позволяет найти итоговую меру

### 1.1 Схема карточки / паспорта

| Источник | Поля мер | Порядок | Маркер «итог» |
|---|---|---|---|
| `search_wiki_entity_card` (`wiki_card_build.sql:11–34`) | `measures VARCHAR` = `string_agg(measure \|\| ': ' \|\| aliases, '; ' ORDER BY m.measure)` | **алфавит имени поля** | **нет** |
| `wiki_passport.sql:7–14` | те же `c.measures` (+ wiki body, axes, not_enough_for) | как в карточке | **нет** |
| `search_entity_card.quantities` (`entity_card_build.sql:53–56`) | `string_agg(DISTINCT k … ORDER BY k)` из `map_keys(nums)` | алфавит | **нет** |
| `search_measure_alias` | `measure`, `aliases` | без ранга | **нет** колонки default/primary |

Парсер паспорта в ask (`z21:_wiki_parse_measures_set` :460–468) режет строку
по `;` / `:` в **множество имён** — порядок и «главность» теряются. В
verify-промт меры уходят как плоский текст (`wiki_format_passport_lines`
:547–555).

**Вывод:** из данных карточки **нельзя** надёжно выбрать «итоговую» меру
без доп. правила вне паспорта. Поля/порядка/«Всего»-флага в схеме нет.

### 1.2 Что уже есть рядом (не паспорт, а эвристики)

| Механизм | Где | Что делает | Риск «нового выбирателя» |
|---|---|---|---|
| `_fork_sum_headline_pool` | `z09:173–183` | `*Документа` + имя `Всего` | структурно (суффикс платформы + точное имя), не словарь домена |
| `_fork_headline_measure` | `z09:785–818` | одна головная для атома fork | то же; при неоднозначности → `None` |
| `sales_money_measure` / `sales_qty_measure` | `z11:269–304` | money\|qty по слово-блобам | **да** — словари («сумм/колич/всего…») |
| `measure_class_alts` | `z16:398–410` | сводит к 2 представителям классов | опирается на sales_* → тот же риск |
| `measure_captions` | `z14:86–104` | подпись из alias / split_ident | форматтер, не судья |
| `wiki_menu_captions` | `z21:379–419` | подписи **вариантов src** из passport/card | **не для мер** (ключ = `src`) |

Имя «Всего» в живой УТ часто **есть** как поле nums/alias — это сигнал
данных, не маркер паспорта. Суффикс `*Документа` — свойство метаданных
платформы 1С, не хардкод базы.

### 1.3 Как сейчас выбирается мера ответа (диск, после В3)

Путь в `z20` после фиксации `src` (:3259–3528):

1. `plan.quantity` ∈ names → мера; иначе `pick_measure` (`z16:586–622`).
2. `pick_measure`: `how=rerank` при `len(names)>1` → `(None, fits, 'ask')` —
   **молчаливый победитель снесён**.
3. Пусто → `unresolved_quantity` (`z16:413–432`): `want/compute` ∈ sum|max|min|avg
   и `len(names)>1` → `(None, names)` — **только меню**, даже при равных итогах
   (комментарий «В3 / формула №15»).
4. `measure_class_alts` на rank-sales (:3337–3344, :3450–3454) — ещё одно меню
   из 2 классов.
5. Живые `measure_alts` → **return `kind=clarify`** с `measure_captions`
   (:3479–3492 и дубль :3506–3528). Блок `totals_of` всем именам при >1 мере
   **заблокирован** (:3493–3503).

**Одна мера:** `unresolved_quantity` → `names[0]`; дальше aggregate/compose.
**measure_alts>1:** clarify-меню (живой замер «итого?/сумма?/количество?»).

Патч `_bootstrap._patch_z20_wiki_primary` (:118–224) сейчас трогает
**fork/wiki-лидер / early-clarify**, не ветку меры. Мера — на диске z20/z16.

## 2. Модель исходов A/B/C контракта (1) для МЕР

Контекст: **лидер сущности уже выбран** (wiki-лидер / один verify-yes /
decision_id). Дальше только меры одного `src`.

### 2.1 Желаемое поведение

| Исход | Условие (меры) | Ответ |
|---|---|---|
| **A** | одна живая мера **или** несколько мер с **одинаковым** числом | одно число; люк не открывать |
| **B** | ≥2 живые меры, числа **разные**, у альтернатив есть **человеческие подписи** (alias / passport-текст меры) | число **итоговой** меры + в том же ответе второе число(а) с подписью; `kind≠clarify` |
| **C** | ≥2 меры, числа разные, **подписей нет** | число итоговой + фраза «есть другое прочтение»; ветки/имена полей не называть |

Это **не** меню «какую величину считать?» и не вопрос человеку.

### 2.2 Что уже есть в коде (переиспользовать)

| Кусок | Роль для мерного B/C |
|---|---|
| `totals_of` + `measure_ambiguous` (`z16:567–583`) | разные ли числа (A vs B/C) |
| `measure_captions` / aliases | подписи для B; пустые → C |
| `build_measure_empty_pivot` (`z16:490–564`) | образец «число(а) в тексте ответа без clarify» (мёртвая мера → живые цифры) |
| `kind=figures` + `options` | журнал понимает B-люк (`z20:_journal_clarify_options` :4451–4454); склад уже отдаёт лидер+люк (`z12:stock_breakdown_leader_fallback` :1203–1256) |
| `FORK_OTHER_READING` (`z13:57`, `:648–697`) | готовая формула исхода **C** («число · есть другое прочтение») |
| `compose` + `totals` named placeholders (`z18:823–833`) | модель может назвать несколько величин **после** того, как код уже выбрал лидера; сейчас путь при >1 мере **не доходит** сюда |
| `count_defer_measure_clarify` (`z05:740–756`) | для `want=count` уже гасит measure-меню — правильно для счёта строк |

### 2.3 Чего не хватает

1. **Итоговая мера паспорта** — поля в карточке нет; нужен либо:
   - данные такта (колонка/порядок в `wiki_card_build` / alias), либо
   - **переиспользование** уже существующих структурных сигналов
     (`_fork_sum_headline_pool` / `_fork_headline_measure`) **без** нового
     `sales_money_*`-словаря и без `measure_class_alts` как судьи ответа.
2. **Ветка ответа** вместо clarify в `z20:3436–3528`: при entity-locked +
   sum-вопрос → aggregate(лидер) + figures/options или текст C; **не**
   `kind=clarify` с кнопками мер.
3. **`wiki_menu_captions` не закрывает меры** — он про `src`. Для B
   подписи мер = `measure_captions` (уже есть) или расширение форматтера
   N→N по `measure` id (тот же контракт 0 выбора, что K4 §2.1).
4. **Конфликт с PLAN В3** (`snos15-PLAN.md` :96–98): «при >1 мере ТОЛЬКО
   меню». Это и есть причина match↓. Z2: **пересмотреть В3 для мер** —
   меню формулы оставляем для **сущностных** прочтений, не для мерной
   детализации.

### 2.4 Как не создать новый выбиратель

- Не возвращать `sales_money_measure` / `measure_class_alts` как победителя
  ответа (они уже словари + меню классов).
- Не звать LLM «выбери меру».
- Лидер меры: **данные** (одно headline-имя из nums/метаданных) → иначе
  если headline нет и подписей нет → исход C с count/sum по единственной
  вычислимой величине **или** honest clarify **сущности** (не мер), если
  сущность ещё не зафиксирована.
- Люк = те же `options`/`figures`, что у fork/stock B — без нового API.

## 3. ОСИ: меню при простом счёте

### 3.1 Где строится меню осей

1. `serene_axis.decide_grain` (`serene_axis.py:85–144`) ставит
   `clarify="axis"` когда:
   - `len(kind_hits) > 1`, или
   - `rank_intent` и несколько ref-колонок без однозначного hit.
2. `z20:3535–3599`: `kind_axis_hits(axes, action_axis or kind)` →
   `decide_grain` → при `clarify==axis` → `axis_clarify_options` (`z18:27–51`)
   → `kind=clarify`.
3. Второй вход: rank без group (`z20:4014–4033`) — снова
   `axis_clarify_options`.

### 3.2 Почему «движений в регистре X» может дать меню осей

Цепочка (код, не живой psql):

1. Intent: `want≈count`, `kind≈«движения»`, сущность названа (регистр X).
2. В `z20:3538` **`_axis_word = action_axis or kind`** — при пустом
   `action_axis` в hits уходит **род** «движения».
3. `kind_axis_hits` (`z17:425–466`) ищет оси, чей `target_src`/label
   пересекается стемами с «движения». У регистра часто **несколько**
   refcols → `len(kind_hits)>1` → `clarify=axis`.
4. Страж `count_question_skips_axis` (`z10:9–26`) **должен** снять меню,
   если `want∈{count,list}`, нет measure, нет amount. Но страж **не
   срабатывает**, если:
   - `want` пуст / не count|list (слот z02), или
   - уже выбрана `measure`, или
   - сработал другой путь (rank_intent, entity_form, period-clarify).

Симметрия уже записана в `live_axis_col_for_count` / `wiki_axis_phrase`
(`z05:698–737`, `z21:218–236`): для названной сущности **kind не ось**;
ось — только `action_axis`. Но `decide_grain`-вход в z20 всё ещё кормит
`kind` в hits — **разрыв правила**.

Комментарий замера 01.09 (тот же регистр): distinct по случайной оси
«ВидДеятельности» вместо COUNT строк — ровно этот класс дефекта.

### 3.3 Общее правило «ось только при ранге/группе/по каждому»

| Уже есть | Покрытие |
|---|---|
| `question_wants_breakdown` (`z10:29–41`) | list / amount.value / max\|min |
| `total_question_skips_axis` (`z10:44–63`) | sum / «всего\|итого» / measure proven — **не** axis-clarify |
| `count_question_skips_axis` | count\|list без measure |
| `question_wants_per_axis_breakdown` (`z12:411–413`) | алиас breakdown → тот же breakdown |
| `wiki_axis_phrase`: ось только named `action_axis` | пул вики |

**Отсутствует как единый гейт:** «простой count/sum без явного разреза →
никогда не звать `axis_clarify_options`». Сейчас это размазано по двум
skip-функциям + дыра `kind→hits`. Маркер «по каждому» в коде **не**
отдельный детектор — только через want=list / rank / warehouse breakdown.

## 4. Сведение (1)+(2) без противоречия

```
вопрос
  → вики-интерпретация сущности (формула ступени 2–3)
  → если прочтений сущности >1 после verify → МЕНЮ с wiki_menu_captions
       (формула ступень 4; контракт A/B/C fork для src/окон — как было)
  → если сущность одна (лидер) → запрос в базу
  → мера:
       0/1 живая или числа равны → одно число (контракт A; люк закрыт)
       >1, разные числа, есть подписи → число итоговой + люк (контракт B)
       >1, разные, нет подписей → число + «есть другое прочтение» (C)
  → НЕ clarify-меню мер («какое твоё»)
  → ось: только при явном разрезе/ранге/«по каждому»; простой счёт — COUNT строк
```

Формула №15 «варианты с описаниями» = **прочтения вопроса** (сущность /
окно / именованная ось), не внутренние колонки nums выбранного регистра.

Контракт начала дня про «одно число + люк» = **мерная (и fork-оконная)
детализация после лидера**, не замена сущностного меню.

## 6. Замки / приёмка (для следующей волны)

- «сколько продали» после одного wiki-лидера → `kind∈{answer,figures}`,
  **не** clarify; diag без `measure_ambiguous` как причины меню.
- Две меры, разные totals, aliases есть → текст/options несут второе число
  с подписью (B).
- Две меры без aliases → содержит `FORK_OTHER_READING` / эквивалент, без
  имён полей в options (C).
- Одна мера / равные totals → одно число, options пусты (A).
- «движений в регистре X» → число строк; `axis_clarify_skipped` или отсутствие
  `axis_clarify_options` в ответе.
- Негатив: нет нового call-site `sales_money_measure` на пути ответа меры.
- L67: мерные clarify на sales не должны забирать бывшие match (якорь Δwrong).
