## 1. Атаки на п.0 / no_domain_wordlists / «под okna»

### Aт1 — «полный отчет» как deny-list (запрет)

ТЗ и S сами предупреждают. Любая правка вида
`if "полный отчет" in q: return False` / список отчётных маркеров в
`stock_question_engaged` — **п.0 + замок `test_no_domain_wordlists`**.
Разрез уже в intent (`want=list` / `question_wants_breakdown`) — универсально.
**Требование R:** в диффе S/C **ноль** новых литералов из `DOMAIN_LITERAL`
замка и ноль новых `any(w in q for w in (...))` для маршрутизации.

### Aт2 — S1 через `sales_sum_intent` — ок по форме, не «новый словарь»

`sales_sum_intent` (`z11:21+`) уже живёт в дереве и в базлайне трещотки;
зеркало `balance_path_engaged:385–386` уже режет sales. Повторный вызов —
не новый доменный список. **Принять S1.**

Риск качества (не п.0): ложный False для вопросов, где `sale_q`/`sale_k`
срабатывает, а ответ — остаток («остатки по продажам», смешанные формулировки).
**Контрмера:** позитивный набор stock-замков + 3–5 живых stock-Q на полигоне
до выката; при ложном skip — не расширять лексику, а уточнять уже существующий
`sales_sum_intent` / порядок гейтов (отдельный мини-пакет, не «добавить слова»).

### Aт3 — S3 early-exit «без kind/axis → False без warehouse-loop» — **дыра**

План S §5 шаг 3:

> нет `kind` и нет `action_axis`, и не `state_path`, и не breakdown → False
> **без** warehouse word-loop.

Контратака по коду: `stock_question_engaged` при пустом kind всё ещё может
стать True через `question_mentions_warehouse_axis` (слова вопроса → catalogs
оси места, `z12:395–401`, `190–200`). S3 отрежет **чистые складские** вопросы
без заполненного `kind`/`action_axis` в разборе (LLM иногда оставляет оси
только в тексте).

**Вердикт R:** S3 в предложенной форме — **не внедрять** или сузить:
early-exit только когда **нет** ни kind, ни action_axis, ни breakdown, **и**
нет сигнала `state_path` / `balance_routing` candidate — но **не** пропускать
шаг warehouse, если в вопросе есть кандидаты оси, **либо** оставить warehouse
как сейчас и полагаться на S1+S2. Бюджет −58…−65 **не зависит от S3** (S1+S4
достаточны).

### Aт4 — S4 short-circuit `catalog_kind_total_question` через `sales_sum_intent`

Формально тот же переиспользуемый гейт — ок для п.0. Риск: catalog-count
вопросы с словом «продаж» в тексте (редко) получат False раньше warehouse.
**Приёмка:** кейсы catalog_count / kind-total замков z11; не регресс «сколько
номенклатуры».

### Aт5 — калибровка под rid okna

Ожидания −50,6 / −25,3 сняты на **одной** базе и одном вопросе. П.0 требует
тот же гейт на чужой базе. `sales_sum_intent` + поля intent — универсальны;
EXISTS/corpus timing — нет. **Не** подкручивать пороги/TTL/`n_rows` под okna.
Приёмка: малая база + полигон (как MOL §3 E3d-дух).

## 2. Атаки на п.19 / п.20 и грань ThreadPool

### Aт6 — батч-SQL = да; питон-пулы поверх базы = нет

| Приём | п.20 | R |
|---|---|---|
| Один SQL `IN` / multi-window вместо цикла `psql` | штатно | **да** (P6/P9/P10-SQL) |
| Кэш bool/frozenset результата уже сделанного SQL в рамках одного `answer` | не «свой скрипт над данными» | **да** (S2/C1/C3) |
| ThreadPool вокруг `ds_chat` / rerank (сеть/модель) | вне перечня запрета п.20 | **да** (P1) при изоляции |
| ThreadPool arbiter×N → N× `answer` → N× `psql` | оркестрация существующих путей; нагрузка ×N | **серая**; MOL §5 — **нет на проде этой недели** |
| ThreadPool вокруг `fork_scan` / EXISTS / corp aggregate | явный анти-паттерн HOW_NOT_TO §0 / MOL §5 | **нет** |
| ThreadPool по `by.items()` в counts | нет I/O | бессмысленно (C/P согласны) |

**Грань R (зафиксировать в плане внедрения):**

1. Независимые **не-SQL** подвызовы существующих функций (LLM-сэмплы) —
   ThreadPool допустим.
2. Независимые **готовые** sub-`answer` — только полигон + стоп-точка; merge
   строго по слоту пула; не как замена батч-SQL.
3. Любой тяжёлый путь к `search_corpus` / unnest — **только** один SQL или
   кэш/не-вход, не пул.

п.19 не нарушается S/C (модель не считает). Intent-пул не переносит счёт в
модель. Arbiter×N уже зовёт compose×N — параллель не ухудшает п.19, ухудшает
нагрузку и детерминизм TRACE.

### Aт7 — P «ThreadPool по intent_axis_words» (P4)

N параллельных `entity_form_catalogs_for_kind` = N× SQL/FTS. Это не батч и не
«чистая функция». **Отклонить** в пользу одного SQL/`OR` или просто S1 (на
ложном stock P4 не нужен).

## 3. Гонки diag / ThreadingHTTPServer

### Aт8 — вложенные потоки внутри Handler

Факты кода:

- `ThreadingHTTPServer` (`z20:6239`) — **разные** HTTP = разные `answer` =
  разные замыкания `diag`/`шаги` — уже ок.
- `шаг` (`z20:1844–1849`) — `list.append` + `_trace_write` **без lock**.
- Arbiter сейчас пишет в общий `diag.arb_probe` / `cut` из того же потока.

Если P12 (arbiter pool) или P1 (intent) пишут в общий `diag`/`шаги` из
worker-потоков → перемешанный TRACE, гонки `setdefault`, сломанная приёмка
по `diag.шаги`.

**Требование R:**

- Worker возвращает **кортеж результата**; главный поток один пишет `diag` и
  `шаг`.
- Intent: `samples[i]` по индексу слота; merge только в главном.
- Запрет: общий модульный mutable кэш без ключа rid **между** запросами
  (уже зафиксировано M4); кэш engaged — **на запрос** (`diag[...]` или clear
  на входе `answer`), не процессный LRU «навсегда».

### Aт9 — ключ кэша `id(intent)` (S2/C1)

`id(intent)` ломается при копии/мутации intent после первого вызова; при
одном объекте на запрос обычно стабилен, но хрупок. **Требование:** ключ =
`(question_str, want, kind, action_axis, frozenset(period keys), plan_fp)`
или явная запись `diag["_stock_engaged"]=bool` после первого расчёта
(предпочтительно — один bool в diag, без id()).

## 4. Качество: порядок → сущность → wrong (L67)

### Aт10 — C2 «не гонять фильтры второй раз» — **главная атака на C**

stock#1 (`2232–2237`) и stock#2 (`2270–2286`) **не эквивалентны**:

| | #1 pre-K6 | #2 post-K6 |
|---|---|---|
| noise + goods | да | да |
| named + сужение pool | нет | да |
| `filter_balance_structural` | нет | да |
| входной `cands` | до K6 | **после** `apply_to_candidates` |

K6 (`expand_holders` / live / reorder) **может добавить** src в пул.
Пропуск goods/noise на #2 после expand = продажи/шум снова в `cands` →
другая голова / wiki / wrong figures.

**Вердикт R по C2:**

- Флаг «#1 уже чистил» **не** отменяет noise/goods на **расширенном** множестве.
- Допустимо: если `engaged` и `set(cands) ⊆ set(cands_pre_k6_filtered)` —
  skip; иначе перефильтровать **добавок** (или весь пул одним батч-SQL).
- `filter_balance_structural` и named-ветка — **всегда** остаются в #2 (как
  пишет C), не выкидывать.

Без этой оговорки C2 = регресс качества при выигрыше секунд.

### Aт11 — S1 False → sales-путь; порядок cands меняется vs сегодня

Сегодня на rid ложный stock **режет** sales-регистры как noise и тасует pool.
После S1 filters не бегут → в K6/wiki попадает **другой** порядок/состав, чем
на текущем (бажном) прогоне. Это **желаемое** исправление маршрута, но для
L67 «≡ старому ответу» на этом Q может дать **отличие** — сравнивать надо с
**эталоном продаж**, не с «что выдавал ложный stock».

**Требование:** L67 / fingerprint против sales-канона / gold, не против
текущего wall-88 unavailable.

### Aт12 — параллель меняет порядок merge

P1: tie-break по wall-time → другой kind. P требует merge по слоту — **обязать
в приёмке**. P12: сравнение атомов после shuffle списков → другой winner.
**L67 обязателен** на любой параллели, затрагивающей intent или arbiter.

### Aт13 — анти-двойной счёт бюджета

| Кто | −сек |
|---|---|
| S1 на Z4→Z6 | −50…−51 |
| S1 же гасит stock#2 (C-окно) | −20…−25 **тех же** секунд механизма |
| C2 без S | −15…−22 из 25,3 |
| S4 | −8…−9,5 (отдельная молекула catalog-gate) |

**Нельзя** писать «S −65 + C −24 = −89». Корректно:

- пакет S1+S2+S4 на rid-классе: **≈ −58…−65** (stock#1 + catalog-gate) **плюс**
  схлопывание #2 ≈ ещё **−20…−25** wall до «собраны», если #2 был тем же
  engaged — в сумме к отсеву ближе к **−75…−85** от префикса, но в отчётах
  разделять **молекулы**, не суммировать пересечение дважды в одну строку
  «Σ ролей».
- C2 имеет смысл как **страховка**, пока S1 не влит, или для истинных stock
  (с Ат10).
