## 1. Оценка по парам

Легенда: **(а)** различим · **(б)** тексты слабо/одинаково не разводят · **(в)** объяснение толкает к ошибке.

### 1 · doc ↔ reg «Реализация ТМЦ» → **(а)**

Одинаковое `name: Реализация ТМЦ`, но platform + nef регистра явно: «детали сделки → документ».  
Цитаты: reg BUF «итог продаж / количество проданных / себестоимость»; nef «Не показывает детали конкретной сделки, используйте Реализация ТМЦ (документ)».  
doc BUF: «отгрузки… **списанию стоимости товаров со склада**… выручки».  
Для вопроса «записей в реализациятмц» читатель с platform отличит. Вред склада — в паре №12.

### 2 · Книга Продаж ↔ Книга Покупок → **(а)**

Зеркало: BUF «НДС к **уплате**» vs «НДС к **вычету**»; nef каждой ссылает на сестру. Образец хорошего генератора.

### 3 · Ценовые Группы ↔ Типы Цен → **(а)** (слабо)

Группы: «наценка для ценовой группы / базовая цена»; alias **«прайс-группы»**.  
Типы: «Какие типы цен…», nef «конкретная цена? → установка цен».  
Различимы, но nef групп **не** называет типы/прайс-лист — только «Номера БСО», «Виды Номенклатуры» (шум).

### 4 · Ценовые Группы ↔ Цены Номенклатуры → **(а)**

Цены: alias **«прайс-лист»**, BUF «текущая цена на товар X».  
Группы — наценка категории, не строка прайса. Контраст есть; у групп нет nef «не текущий прайс».

### 5 · Установка Цен ↔ Цены Номенклатуры → **(а)**

Взаимно: установка «история/кто изменил прайс», nef «не текущую цену → Цены Номенклатуры»; цены nef «не историю → Установка Цен». Эталон пары.

### 6 · Номенклатура ↔ Ценовые Группы → **(в)**

i2: «сколько позиций у нас в **прайсе**» → pick `catalog_номенклатура` (2399).  
BUF номенклатуры: «хранение позиций… **установка цен**, единиц…».  
Читатель/судья видит «цены» у справочника позиций → толкает к прайсу; ценовые группы с alias «прайс-группы» рядом, но без «сколько позиций в прайсе». Вред — у A.

### 7 · Номенклатура ↔ Цены Номенклатуры → **(в)**

Тот же BUF «установка цен» у номенклатуры vs настоящий «прайс-лист» у IR.  
Паспорта **различимы** по роли, но формулировка A подменяет прайс справочником артикулов. Счёт в **(в)**.

### 8 · Места Хранения ↔ Складские Операции → **(а)**

Места: «Список складов или локаций»; nef про стоимость/состояние ДА.  
Журнал: «операции на складе / история»; nef «**Каковы остатки на складе? (Это регистры накопления)**». Чётко.

### 9 · Места Хранения ↔ Списание ТМЦ → **(а)**

Списание: «расход материалов / выдача со склада»; nef «остатки? → регистры». Справочник vs акт списания.

### 10 · Складские Операции ↔ Списание ТМЦ → **(а)**

Журнал nef указывает на документ списания для стоимости; списание — конкретный расход. Различимы.

### 11 · Книга Продаж ↔ Реализация ТМЦ (reg) → **(б)**

Обе про «продажи» и суммы.  
Книга: налоговая, НДС к уплате. Реализация: итог продаж, количество, себестоимость.  
При вопросе «вчера сколько продали» (пул i2, clarify) нейтральный читатель без налогового контекста видит два ответа про продажи; **взаимного nef нет** (книга не говорит «не оперативный регистр продаж»; реализация не говорит «не Книга Продаж / не НДС»). Слабый контраст → **(б)**.

### 12 · doc Реализация ↔ Места Хранения → **(в)**

doc BUF дословно толкает склад: «проводок по списанию стоимости товаров **со склада**».  
Места — список складов. На теме «склад/остатки» объяснение A подтверждает ложного кандидата (класс G1/HR).

### 13 · reg Реализация ↔ Места Хранения → **(а)** + дыра

Имена/роли разные (продажи vs справочник складов).  
Но у регистра **нет** doesNotAnswer про остатки/позиции на складе при оси `МестоХранения → catalog_местахранения` — судье не дают маркера «не я» на складском вопросе. Различимость пары есть; покрытие отказа — нет (требование ниже).

### 14 · Виды Номенклатуры ↔ Номенклатура → **(а)**

Взаимный nef: виды = классификация типов; номенклатура = конкретные артикулы. Эталон.

### 15 · Импорт ТМЦ ↔ Реализация ТМЦ (reg) → **(а)**

Импорт: количество/сумма импорта; nef → поступление/доп.затраты. Реализация — продажи. Без пересечения топиков.

## 3. Чего не хватает (требования к генератору, не правка страниц)

Только для слабых/вредных и дыр:

| Пробел | Требование одной фразой |
|---|---|
| doc реализация + «склад» в BUF | **Запрет чужого топика в best_used_for:** не упоминать место хранения / остатки / склад, если сущность не отвечает за остатки; складской побочный эффект проводки — не пример вопроса. |
| номенклатура + «установка цен» / прайс | **best_used_for = вопросы, на которые сущность даёт ЧИСЛО/СПИСОК сама:** «какие артикулы есть»; цены — только у регистра/документа цен. Пример отказа: «сколько позиций в прайсе? → не Номенклатура, а Цены Номенклатуры (строки прайса)». |
| книгапродаж ↔ реализациятмц | **Взаимный контраст однотемных накопителей:** «оперативные продажи/кол-во/себестоимость, НЕ налоговая Книга Продаж (НДС)»; зеркально у книги: «НДС к уплате, НЕ итог реализации ТМЦ». |
| reg реализация на складе (пара 13) | **Тематический doesNotAnswer вне списка соседей пачки:** «не остатки и не список складов — см. регистр остатков / Места Хранения», даже если склад не в kNN-батче. |
| ценовыегруппы nef = БСО | **notEnoughFor только про путаемые ценовые/товарные соседи**, не случайный шум; обязательно: «не текущий прайс-лист (Цены Номенклатуры)», «не тип цены (Типы Цен)». |

## 4. Вывод: 5 требований к объяснениям (любая база)

Проверяемы без знания okna — по тексту паспорта и паре соседей:

1. **Один топик в best_used_for.** Примеры вопросов только про то, что сущность считает/хранит; побочные слова процесса (склад при отгрузке, цена при карточке товара) — запрещены, если есть другая сущность этого топика.
2. **Взаимный doesNotAnswer для одноимённых и однотемных.** Гомонимы (документ/регистр одного stem) и пары «налоговый ↔ оперативный», «история ↔ текущее», «справочник ↔ движения» обязаны ссылать друг друга по имени роли, не только по `src_table`.
3. **Формула отказа: «хранит/отвечает X, НЕ Y (см. Z)».»** Одна короткая строка; Y — человеческий топик вопроса (остатки, прайс, НДС, список складов), Z — кто отвечает.
4. **Запрет подмены меры вопросом чужой сущности.** Если у A нет меры «цена»/«остаток», BUF не должен обещать «установку цен» или «склад»; иначе паспорт вреден даже при различимом имени.
5. **Тематический отказ независимо от состава батча.** doesNotAnswer обязан закрывать частые ложные топики по осям (если есть `МестоХранения` — явно «не остатки склада»; если aliases содержат «прайс*» — кто держит строки прайса). Не ограничиваться соседями kNN-пачки.

Опционально (6): **platform-kind в первой строке смысла** для гомонимов («это документ отгрузки» / «это накопитель итогов») — дублирует поле platform, но уезжает в wiki body, если судья режет platform.
