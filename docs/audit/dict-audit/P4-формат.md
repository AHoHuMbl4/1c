## Вердикт

1. **Схема ответа модели** — жёсткий JSON Schema с `minItems`/`maxItems`
   (aliases 3–8, bestUsedFor 2–4, notEnoughFor 1–5) + те же границы в промте.
   Просить её в `response_format` / guided decoding у vLLM 27B (замер поддержки
   13.09 — канон армии). Пока `openclaw infer model run` **не** пробрасывает
   `response_format` — проект передачи: либо params модели в OpenClaw, либо
   узкий HTTP-вызов в шлюзе, либо фолбэк «схема в промте + пост-валидатор».
2. **Хранение списков** — сегодня массивы модели схлопываются в CSV через
   `_join(..., ',')` (`wiki_alias_parse.py:22–23`). Запятая внутри фразы ломает
   frontmatter (`wiki_build.sql:56–64`) — **30** строк nef / **13** best на okna
   (B1). Рекомендация: **оставить VARCHAR + CSV, сменить разделитель на ` | `**
   (пробел-пайп-пробел) и запретить `|` внутри элементов схемой/валидатором;
   экранирование `\,` — только для Solr-ветки (уже умеет). JSON-массив в колонке
   — запасной путь, дороже по миграции потребителей.
3. **Обрезки:** потолок `_join` **900 → 1600** (запас под NEF 1–5 × ~250 симв.);
   **паспорт 1500 не поднимать** без A/B на verify; **BATCH держать 20**,
   поднимать до 25 только после замера out-токенов при схеме (узкое место —
   `maxTokens: 8192`, не контекст 64k).
4. **Вызов:** `temperature=0`, thinking `off`, `seed` если провайдер принимает —
   всё провести через `alias_infer_gateway` (+ каталог OpenClaw). Сейчас temp/seed
   **не передаются** (`alias_infer_gateway.py:48–61`).
5. **Ретрай:** схема не сошлась → **1 повтор всей пачки** с тем же seed; при
   повторном провале — salvage целых items + `mark_skip` только на хвост/битые
   сущности (не пустышки на успешно разобранные). По-сущностный ретрай — только
   как второй круг для «дыр» пачки, не вместо первого.

## 1. JSON-схема ответа (контракт генерации)

Текущий промт уже просит массивы
(`wiki_alias.sh:182`: `aliases[]`, `bestUsedFor[]`, `notEnoughFor[]`,
`quantities[{name,aliases[]}]`), но **без** min/max и без машинной схемы.

### 1.1. Канон схемы (черновик для `response_format.json_schema`)

```json
{
  "name": "wiki_alias_batch",
  "strict": true,
  "schema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["items"],
    "properties": {
      "items": {
        "type": "array",
        "minItems": 1,
        "maxItems": 30,
        "items": {
          "type": "object",
          "additionalProperties": false,
          "required": [
            "entity", "aliases", "quantities",
            "bestUsedFor", "notEnoughFor"
          ],
          "properties": {
            "entity": {
              "type": "string",
              "minLength": 1,
              "description": "Точный src_table из Input"
            },
            "aliases": {
              "type": "array",
              "minItems": 3,
              "maxItems": 8,
              "items": {
                "type": "string",
                "minLength": 2,
                "maxLength": 48,
                "pattern": "^[^|,]+$"
              }
            },
            "quantities": {
              "type": "array",
              "minItems": 0,
              "maxItems": 30,
              "description": "верхняя граница канона; фактически ≤ числу quantities во Input пачки — потолок batch-select обязан резать ВХОД до того же лимита (иначе truncation = молчаливая потеря, п.13)",
              "items": {
                "type": "object",
                "additionalProperties": false,
                "required": ["name", "aliases"],
                "properties": {
                  "name": { "type": "string", "minLength": 1 },
                  "aliases": {
                    "type": "array",
                    "minItems": 1,
                    "maxItems": 5,
                    "items": {
                      "type": "string",
                      "minLength": 1,
                      "maxLength": 48,
                      "pattern": "^[^|,]+$"
                    }
                  }
                }
              }
            },
            "bestUsedFor": {
              "type": "array",
              "minItems": 2,
              "maxItems": 4,
              "items": {
                "type": "string",
                "minLength": 8,
                "maxLength": 160,
                "pattern": "^[^|]+$"
              }
            },
            "notEnoughFor": {
              "type": "array",
              "minItems": 1,
              "maxItems": 5,
              "items": {
                "type": "string",
                "minLength": 8,
                "maxLength": 220,
                "pattern": "^[^|]+$"
              }
            }
          }
        }
      }
    }
  }
}
```

`pattern` запрещает `|` (будущий разделитель хранения) и `,` в **aliases**
(алиасы — слова/короткие обороты без списков). В BUF/NEF запятые **разрешены**
(«взнос работодателя, НДФЛ…») — их несёт элемент массива целиком, а не CSV.

### 1.2. Как просить схему у модели

| Слой | Статус | Проект |
|---|---|---|
| vLLM guided / `response_format: {type:json_schema,…}` | Поддержка на 27B — замер 13.09 (армия) | Цель: guided decoding |
| `openclaw infer model run` CLI | Флагов `temperature` / `response_format` / `seed` **нет** (`cli/infer.md`) | Не ждать CLI — обойти |
| Каталог `openclaw.json` модели | Есть `maxTokens:8192`, `contextWindow`, thinking kwargs; **нет** temperature | Добавить `temperature: 0` (+ seed, если поле есть у провайдера) |
| `alias_infer_gateway.py` | Только `--model/--thinking/--json/--prompt` | **Проект передачи:** `--temperature`, опц. `--seed`, опц. `--response-format-file`. Прямой `POST /v1/chat/completions` — **запрещён до слова openclaw-native** (правило 26.07: сначала спросить агента о штатной передаче params через каталог/`infer`; HTTP-обход — только после его «штатного нет», отдельной находкой в P7) |

Порядок внедрения (без смены семантики словаря):

1. Пост-валидатор по схеме в `wiki_alias_parse` (фолбэк всегда).
2. Params `temperature=0` в каталоге + проброс в шлюз.
3. Смоук `response_format` на одной пачке 2–3 сущностей (локальный 27B / OR).
4. Включение guided на боевой генерации песочницы `alias_okna_c5`.

### 1.3. Оценка размера ответа при схеме

Грубая верхняя граница **на сущность** (символы ≈ токены×~2 для RU):

| Поле | max | × длина | ≈ символов |
|---|---:|---:|---:|
| aliases | 8 | 48 | 384 + JSON |
| BUF | 4 | 160 | 640 |
| NEF | 5 | 220 | 1100 |
| quantities (типично ≤15 × 5×48) | — | — | ≤3600 худший |

Худший случай **на сущность ~6–7 КБ** JSON → пачка **20** ≈ 120–140 КБ текста ≈
**далеко за 8192 out-токенов**, если у всех богатые quantities. На практике okna
режет раньше (B1: max aliases 256 / best 298 / nef 430 **после** `_join`; CHANGELOG
28.08: обрыв на char **26274** при BATCH=20).

**Следствие:** схема **укорачивает** типовой ответ и делает BATCH=20 безопаснее;
подъём BATCH без подъёма `maxTokens` или без лимита `quantities` — риск регресса
truncation.

Рекомендуемый доп. потолок в схеме: `quantities[].aliases` уже 1–5;
в промте v2 — «не больше имён, чем во Input» (уже есть канон) + не раздувать
aliases меры.

### 2.3. Варианты хранения — сравнение

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **A. Оставить `, ` + запрет запятых в элементах** | Нулевая миграция потребителей | BUF/NEF с перечислениями в скобках придётся уродовать («и» вместо `,`); 30 живых nef уже нарушают | Слабо для NEF |
| **B. Экранирование `\,` везде** | Совместимо с Solr | Надо заменить **все** `str_split(..., ',')` / `split_part` / `_alias_tokens` / reask; легко забыть потребителя | Рабочий, но хрупкий |
| **C. Разделитель ` \| ` + запрет `\|` в элементах** | Редкий в RU-прозе; читаем глазами; схема `pattern` закрывает | Правка ~6–8 call-site split; z02 уже режет по `\|` — топики-примеры останутся шумными (и сейчас шумные) | **Рекомендуется** |
| **D. JSON-массив в VARCHAR** (`["a","b"]`) | Нет двусмысленности; схема = хранение | Миграция 258 строк + все split-потребители → `json`/`unnest`; hybrid inverted на сыром JSON увидит кавычки/`[` — **нужен** generated/текст для индекса или отдельная колонка | Запасной, если C не хватит |
| **E. Настоящий ARRAY/JSON тип колонки** | Штатно для движка | DDL + пересборка индексов `USING inverted(aliases…)` (`corpus_init.sql:463`) — отдельный эпизод | Не в P4 v2 |

### 2.4. Рекомендуемый контракт хранения (C)

1. Модель отдаёт **только массивы** (схема §1).
2. `_join` пишет элементы через `" | "` (не через запятую).
3. Все наивные split (§2.2.A) → split по `" | "` (или `str_split(…, ' | ')` /
   `regexp_split` с тем же литералом).
4. В элементах `|` запрещён валидатором; запятые в BUF/NEF **разрешены**.
5. Solr: при чтении aliases либо (а) split по ` | `, либо (б) продолжить
   escape-aware путь, если когда-нибудь понадобится `,` внутри алиаса — сейчас
   алиасы без запятых по схеме.

### 2.5. Миграция 258 живых строк (okna)

Цель: один раз привести бой / песочницу к новому разделителю **без потери фраз**.

Алгоритм (проект, не код):

1. Снять snap: `CREATE TABLE alias_okna_p4_pre AS SELECT * FROM search_entity_alias;`
   (то же для measures при необходимости).
2. Для каждой колонки `aliases`, `best_used_for`, `not_enough_for`:
   - эвристика «ломанных» строк: есть `(` … `,` … `)` без парности bullet'ов
     (как B1 замер) **или** длина элемента после `,`-split < 2 при наличии скобок;
   - **безопасный путь для «чистых» строк** (нет `,` внутри предполагаемых фраз):
     `replace` последовательности `, ` → ` | ` (типичный `_join`);
   - **ломаные 30+13**: не машинно угадывать — либо перегенерировать сущность
     force-проходом (см. сводку п.3), либо ручной/полуручной fix из snap c1/c5.
3. Меры (`search_measure_alias.aliases`): обычно короткие слова без `,` —

4. После миграции: пересобрать VIEW `wiki_pages` (она на лету), карточку

## 5. Ретраи и валидация пачки

### 5.1. Слои проверки (после ответа)

1. **Транспорт** — exit≠0 / пустой text → как сейчас: `mark_skip`, RETRY_H
   (`wiki_alias.sh:188–196`).
2. **JSON** — parse / salvage (`wiki_alias_parse`).
3. **Схема** (новое) — min/maxItems, pattern, `entity` ∈ Input, `quantities.name` ∈
   allow-list (уже `canon_measure`).
4. **Семантика v2** (соседний эпизод P-промтов) — стоп-слова платформы и т.п.;
   сюда не смешивать.

### 5.2. Политика при провале схемы

```
пачка N сущностей
  → infer (temp=0, seed=S, schema)
  → validate
     OK → MERGE (как сейчас)
     FAIL → infer ещё раз (тот же prompt, тот же seed)  // ровно 1 ретрай
            → validate
               OK → MERGE
               PARTIAL (salvage: k целых items, k < N)
                    → MERGE только валидные k
                    → mark_skip / очередь дыр только для N−k
               FAIL полностью
                    → mark_skip всей пачки (как сейчас), не крутить 3+ раза
```

**Почему сначала пачка целиком, не по одной сущности:**

- Промт заточен на **соседей в одном JSON** (разведение NEF) — одиночный вызов
  теряет контекст путаницы (`wiki_alias.sh:182` «CLOSE IN MEANING»).
- Стоимость/латентность: 20 одиночных вызовов ≫ 1–2 пачечных (A5: минуты на пачку
  local).

**По-сущностно** — только добивка «дыр» после PARTIAL/salvage (сущности без
строки в rows), тем же батч-селектом на следующем круге (уже умеет идемпотентный
отбор пустых). Отдельный «микро-промт на 1 entity» не вводить в P4.

Невалидный item внутри иначе валидной пачки: **отбросить item**, не валить всю
