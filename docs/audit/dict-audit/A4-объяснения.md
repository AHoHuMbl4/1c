## Вердикт

Объяснения судьи в основном **отталкиваются от kind/имени и от отрицаний своими словами**, а не от `bestUsedFor` / тела вики. Поля словаря заполнены почти везде, но: BUF часто **помогает как список вопросов**, иногда **канцелярит или повторяет имя**, и в ключевых местах **врёт** (Номенклатура → «установка цен»). NEF почти всегда **соседский редирект** («смотрите X»), а не тематическое «не я» для размытых вопросов — отсюда `yes` на «прайс»→номенклатура и слабый отсев по остаткам/клиентам. Тело страницы — **английский шаблон** на всех 255 + обрезка.

### На что ссылается why (по топу частот `why_top_by_fit`)

| fit | чаще всего цитирует | редко / почти нет |
|---|---|---|
| **yes** | **platform/kind** + **совпадение name** с вопросом; иногда measures | wiki-excerpt / bestUsedFor / doesNotAnswer — почти не видно |
| **no** | **kind** («это справочник/документ…») + **своя негация** («не содержит продаж/остатков», «unrelated to inventory») | явное поле doesNotAnswer/BUF почти не цитируется дословно |
| **unsure** | measures есть, но **вопрос слишком общий** / сосед-классификатор | — |

Типичные формулы **no** (частоты в топе):

- «This is a catalog, unrelated to the specific register.» (×5)
- «…catalog for report lines / cash flow…, not inventory data.» (×3–4)
- «Номенклатура описывает справочник товаров, но не содержит данных об остатках или складах.» (×3)
- «Справочник 'Праздники'/'Года'/'Нумераторы' не содержит данных о продажах.» (×2 каждый)

Типичные формулы **yes**:

- точное совпадение имени регистра с запросом («допзатратыимпорттмц», «Книга Покупок»)
- «catalog … directly matching … count banks/currencies/warehouses»
- measures перечислены → «allows the count»

### `yes_on_wrong` (все 4)

| вопрос | why (сокр.) |
|---|---|
| сколько позиций у нас в прайсе всего | «Номенклатура … standard entity for storing **price list** items…» (×3 по прогонам) |
| позавчера сколько было продаж | «Entity is 'Книга Продаж' … directly matches … **sales** data» (base24-before) |

Связка с паспортом: у **Номенклатура** BUF буквально содержит «**установка цен**», а NEF **не** говорит «не прайс / не остатки» — только отличие от «Виды Номенклатуры». Судья достраивает «price list» из kind+BUF.

### Clarify / размытые продажи

При clarify на «наторговали / продали / в прошлом месяце всего» why либо:

- **unsure**: «есть мера Всего, но вопрос не уточняет реализацию/закупку/опт»;
- **no** на классификаторы шаблоном «не содержит данных о продажах/торгах»;
- иногда **yes** на «Реализация ТМЦ» при эталоне honest_no (`yes_on_honest_no`) — объяснение сущности верное, исход контура — нет.

Пример unsure: *«Регистр 'Реализация ТМЦ' имеет меру 'Всего', но вопрос не уточняет, о каком именно типе операций…»*

## 2. `best_used_for` (255 страниц ≈ 258 alias)

Все **255** непустые. Стили (эвристика по тексту):

| класс | N | критерий |
|---|---:|---|
| **помогает** (примеры вопросов / конкретный use-case) | **~186–200** | есть «?» или «сколько/какая…», длина ≥60 без канцелярита |
| **повторяет имя** (синоним-список / парафраз title) | **~27–41** | CSV коротких парафраз без вопроса |
| **канцелярит** (герундии «Учет/Формирование/Определение…») | **~13–14** | без askable вопроса |
| **врёт** (смысл чужой темы) | **≥1 явный системный** | Номенклатура → «установка цен»; судья → прайс |

«Врёт» как массовый класс автоматом не ловится: явная ложь точечная, но **дорогая** (см. L67 wrong по прайсу).

## 3. `not_enough_for` / doesNotAnswer — размытые темы

| | |
|---|---:|
| непустых NEF | **254 / 255** (пустой: `Поступление ТМЦИмпорт_ОС`) |
| стиль: topic-neg + sibling | **~95** |
| в основном topic-neg | **~53** |
| в основном «смотрите X» | **~6** |

Упоминания тем в тексте NEF (по всей таблице, грубо):

| тема | страниц с упоминанием в NEF | из них **не** по теме сами (реально могли бы сказать «не я») |
|---|---:|---:|
| остатки/склад | ~15–20 | **~9** |
| цены/прайс | ~14–31* | **~9** |
| клиенты/контрагенты | ~8–12 | **~9** |

\*разброс из‑за слова «цена» внутри ценовых сущностей.

**Вывод по факту текстов:** для размытых «остатки / прайс / клиенты» тематическое «не я» есть у **единиц** чужих карточек (~9 на тему из ~230 не-тематических). Типичный NEF — **разведение с соседом** («не Виды Номенклатуры», «см. Установка Цен»), а не «эта сущность не отвечает на складские остатки / прайс / список клиентов».

Контрпримеры дыр:

- **Номенклатура** NEF: только vs Виды Номенклатуры — **нет** «не прайс / не остатки на складе».
- **Места Хранения** NEF: стоимость актива / состояния ДА — **нет** «не остатки количеств».
- **Контрагенты** NEF: vs Организации — не про «сколько клиентов» vs продажи.

При этом судья в why **сам** пишет «не содержит остатков» для номенклатуры на складских вопросах — то есть негацию **выдумывает**, когда паспорт молчит; а на «прайс» негацию **не** выдумывает и даёт yes.

## 5. Системные дефекты объяснений (5–8)

1. **Why опирается на kind+name, не на BUF/wiki.**  
   Yes-топ: platform + matches name; wiki/bestUsedFor в why почти не встречаются. Поле «объяснение для человека/судьи» в словаре судья использует слабо.

2. **Негация в why — импровизация, не doesNotAnswer.**  
   Частые no: «unrelated to inventory / не содержит продаж» без цитаты паспорта. Когда импровизация совпадает с истиной — ок (`no_on_correct` 218); когда нет — дыра (прайс).

3. **BUF врёт в точке L67-wrong.**  
   Номенклатура: «установка цен» → why: «price list items» → `yes_on_wrong` на «сколько позиций в прайсе». Нужный носитель цен — «Цены Номенклатуры», у номенклатуры NEF об этом молчит.

4. **NEF = маршрутизация к соседу, не тематический veto.**  
   ~9 чужих карточек на тему реально пишут «не остатки/не цены/не клиенты». Размытые вопросы из очереди semantic-verify паспортами почти не закрываются.

5. **Канцелярит / повтор имени в BUF (~15–40 карточек).**  
   «Формирование/Учет/Определение…» и CSV парафразов title не дают судье различить «когда выбирать эту сущность».

6. **Английский шаблон body на 100% страниц.**  
   Судья (промт EN) отвечает why часто по-английски; русские вопросы + EN boilerplate + RU BUF = шум и смешение регистров в одном паспорте.

7. **Clarify/unsure на общих продажах — why честный, контракт меню не из паспорта.**  
   «Есть Всего, но не ясно реализация/закупка» — правильная жалоба; в паспортах нет явного «единственный ответ на „сколько продали“ / иначе меню», поэтому исход уходит в clarify/honest_no при yes на Реализация ТМЦ (`yes_on_honest_no` 37).

8. **doesNotAnswer не спасает dimension vs факт.**  
   Why: «Места Хранения — dimension for balances» при вопросах остатков → yes на справочник складов при honest_no по остаткам. В паспорте складов нет «не остатки количеств» — только чужие темы ДА.

## Метод (коротко)

- Агрегация why: Python по 3× jsonl на окне → `.claude/state/a4-raw/why-summary.json`.  
- Паспорта: SELECT/`wiki_pages` (+ BUF/NEF) → `wiki-pages.jsonl` (255).  
- Классы BUF/NEF — эвристики по тексту + ручной разбор ключевых носителей (Номенклатура, Цены, Контрагенты, Места Хранения).  
- Код проводки: `ubuntu/serenedb/ask/z21_wiki_choice.py` (`WIKI_VERIFY_SYS`, format passport), `wiki_build.sql`, `wiki_passport.sql`.

Критерий следующей правки (из activeContext): wrong не растёт и match не падает — чинить объяснения **точечно** (BUF/NEF номенклатуры↔прайс/остатки, тематические doesNotAnswer), не новым слово-гейтом.
