# S2 — Разбор вопроса = 5× LLM (`ASK_INTENT_SAMPLES`): план снижения до 1–2

**Режим:** только чтение. Код/БД/коммиты не трогались.  
**Дата:** 11.09.2026.  
**Живой факт:** 5× `model TOKENS in=827 out=123–167` за ~10 с (06:42:44–54) → фаза `разбор вопроса 12501` мс (~12,5 с). Модель ask: `qwen3.8-27b` / OpenRouter; `temperature=0`; reasoning/thinking выключены в теле запроса.  
**Источники:** `z02_intent.py:565–686`, `z01_infra_trace_llm.py:521–548,769–862`, `z20_ask_main_http.py:1852–1856`, `test_intent.py:350–376`, `CHANGELOG` 04.08 (устойчивость 18/58→…), `docs/audit/webui-slow-w1.md` §3, `activeContext` «МЕТРИКА» / «Разброс разбора».

## Вердикт

Пять вызовов — **не «магия 5»**, а потолок бюджета согласия: `SAMPLES=5`, `LEAD=3`, цикл уже умеет выйти раньше. На живом срезе потолок **достигнут** → после 4 сэмплов хотя бы одно из 11 полей ещё имело отрыв `< 3` (типично 3:1 → lead=2).  
`temperature=0` **уже стоит** — один сэмпл сам по себе не даёт детерминизма (замер 04.08: 18/58 расходятся).  
Минимальный путь к 2–3 вызовам без правки промта: **ослабить `ASK_INTENT_LEAD` до 2** (env) ± снизить потолок `ASK_INTENT_SAMPLES` до 3; доказательство — уже существующий `intent_parse_bench.py` + счётчик `parse.samples`.

### Зачем 5 сэмплов

Это **консенсус против nondeterminism при temperature=0**, не «усреднение температуры».

Документированный замер в docstring `parse_intent` (`z02:633–651`) и CHANGELOG 04.08:

- 58 вопросов × 3 повтора: **18/58** расходятся по `kind` / `terms` даже при `temperature=0`;
- расклад на 9 прогонах чаще **7:2**, не 50/50;
- имитация: 1 прогон → ~22 % мимо majority; до 5 с отрывом 3 → ~8,4 %; нуля голосованием нет → нужен `_INTENT_MEMO` для повтора в процессе.

Словоформы решают пул: «товар»/«товаров» → 22/32 общих кандидатов; «выручка»/«продажи» → 5/32. Отсюда цена multi-sample — вход в шаги 3–4, не косметика JSON.

### Что такое `INTENT_LEAD`

`_field_lead` (`z02:588–596`): для поля считает частоты значений (`json.dumps` exact-match),  
`lead = count(лидер) − count(второй)` (если второго нет — `lead = count`).

Условие раннего выхода (`z02:670`):

```text
min(lead по ВСЕМ 11 полям) >= INTENT_LEAD
```

То есть выход только когда **каждое** поле набрало отрыв ≥ LEAD. Одно «дрожащее» поле (`search_form`, состав `terms`, синоним `kind`) тянет весь цикл дальше.

**Минимумы при текущих дефолтах:**

| Сэмплов накоплено | Единогласие всех полей | Худший типичный split | lead | Выход при LEAD=3? |
|---:|---|---|---:|---|
| 1 | да | — | 1 | нет |
| 2 | да | — | 2 | нет |
| 3 | да | — | 3 | **да** (лучший случай) |
| 4 | 3:1 на поле | lead=2 | 2 | **нет** → берётся 5-й |
| 5 | потолок | majority / первый при ничьей | — | конец |

**Вывод по живому срезу (ровно 5 вызовов):** это не «LEAD не сработал», а «LEAD=3 не набран к 4-му сэмплу». Ранний выход **уже в коде**; при LEAD=3 лучшее, на что можно рассчитывать без разногласий — **3** вызова, не 1–2. Сценарий 3:1 после четырёх **обязательно** добирает пятый.

Тесты (`test_intent.py:371–376`) проверяют LEAD=**2**: выход на 4-м при серии A,B,A,A (lead=2); без отрыва — все 5.

### Temperature

Уже `0` в `_ds_chat_body` / `ds_chat` (`z01:521–547`). `_one_intent` temperature не переопределяет.  
Вариант «включить temperature=0» **уже сделан**; nondeterminism провайдера/модели остаётся (замер 04.08).

### Почему `out=123–167`

Ответ — JSON разбора по схеме `INTENT_SYS` (не reasoning: `reasoning.enabled=false` при `DS_REASONING_OFF`, `z01:529–532`).  
Разброс 123…167 токенов = разная длина полей (`terms` с альтернативами, `search_form`, даты, `action_*`). `max_tokens=400` — потолок, не факт; факт 123–167 укладывается с запасом.  
Одинаковый `in=827` = один и тот же `INTENT_SYS` (~3,2k символов) + `today=…\n\nQuestion: …` на каждый сэмпл.

### Потребители разбора (влияние на L)

После merge: `same_concept_groups` (SQL стем/синонимы), `_enrich_conversational_business`, затем в `answer`: период/preds → probe/wiki/aggregate.  
Критичные для L-метрики поля: **`kind`, `want`, `measure`, `terms`, `period`, `action_class`/`action_axis`**.  
`search_form` и мелкие вариации `terms` чаще шумят в голосовании, чем меняют эталон match/wrong — но из-за `min(lead)` шумящее поле **дорого по времени**.

### `_INTENT_MEMO` vs «разброс между прогонами»

- Внутри одного процесса ask: повтор того же `(today, question)` — **0 LLM** (тест `test_intent.py:399–402`).
- Между воркерами / рестартом / другим текстом / сменой даты — memo не помогает.
- activeContext долг: «Разброс разбора между прогонами (INTENT_MEMO внутри прогона только)» — про **межпроцессный / межпрогонный** дрейф L19, не про отсутствие multi-sample.

`diag` ответа (`z20:1886+`) сейчас кладёт `terms`/`kind`/…, но **не** `parse.samples` / `parse.unstable` — для замера «сколько сэмплов реально» нужна правка diag или чтение TRACE TOKENS.

## Оценка: дают ли 5 сэмплов консенсус, или LEAD на 2–3?

| Вопрос | Ответ по коду + живому срезу |
|---|---|
| Есть ли ранний выход? | **Да**, `z02:669–671` |
| Когда выход при LEAD=3? | Не раньше **3** единогласных по **всем** 11 полям |
| Почему живой кейс = 5? | К 4-му сэмплу `min(lead) < 3` → обязателен 5-й. Значит было **разногласие** хотя бы на одном поле (часто lead=2 при 3:1 — «консенсус practically есть», порог его не признаёт) |
| Типичный «полезный» консенсус 7:2 | При потолке 5 и LEAD=3 часто **не успевает** оформиться как break: 3:1 после 4 → всё равно 5 вызовов |
| Можно ли выйти раньше минимальной правкой? | **Да, без правки логики:** `ASK_INTENT_LEAD=2` (± `ASK_INTENT_SAMPLES=3`). Одна строка env на юните ask. Поведенческие тесты lead=2 уже зелёные в `test_intent.py` |

Итого: сейчас 5 сэмплов чаще **дожимают порог**, чем «набирают глубокий консенсус». При единогласии всё равно платится минимум 3 вызова (LEAD=3), не 1.

## Стык со stability / L-метрикой

**Факт долга (activeContext):** разброс разбора между прогонами; memo только внутри процесса.

| Изменение | Усилит ли межпрогонный разброс? |
|---|---|
| samples=1 | **Да**, напрямую: каждый прогон И2/WebUI заново бросает монету на 18/58 классе вопросов |
| LEAD=2, samples=5 | Слабо: majority обычно тот же; реже добор «уточняющих» голосов. Memo внутри прогона по-прежнему фиксирует |
| samples=3, LEAD=2 | Компромисс; на патологических 2:2:1 выше шанс «не тот» лидер, чем при 5 |
| Межпроцессный кэш | **Снижает** видимый разброс на повторах; холодный первый раз — как выбранный samples/LEAD |

**Как замерить (без смены эталонов базы):**

1. **Идентичность intent (шаг 1):**  
   `MEMO=0 REPEATS=10 ASK_INTENT_SAMPLES=… ASK_INTENT_LEAD=…`  
   `python3 work/acceptance/intent_parse_bench.py`  
   Метрики: доля вопросов с расхождением между повторами; среднее/гистограмма `parse.samples`; `parse.unstable`.
2. **Счётчик идентичности одной строки:** N раз один вопрос → `json.dumps(intent без parse, sort_keys)` → `identical/N`. Критичные поля отдельно: `kind|want|measure|terms`.
3. **L-метрика:** полный И2 как в activeContext (workers 16, сравнение `answers.jsonl`, не усечённый nums). Смотреть не только 35/3, а **стабильность вердикта** того же вопроса в двух прогонах (match↔wrong / match↔honest_no).
4. **Скорость:** TRACE — число подряд `in=827` до `разбор вопроса`; цель: медиана 2–3, не 5.

Базовый якорь качества шага 1: прогоны `runs/2026-08-04-intent-1-58-*.json` + CHANGELOG (18/58 → снижение multi-sample+memo). Повторить ту же методику на текущей модели `qwen3.8-27b` — цифры 04.08 были на другом стеке; **переносить 8,4 % без перезамера нельзя**.
