Вызов 2 умер в **мосте mcp-ask** на `urllib.urlopen(..., timeout=ASK_TIMEOUT=300)` → `TimeoutError` при живом serene-ask, который продолжал считать. ## 1. Путь составного вопроса

### 1.1 Что увидел человек / gateway

Вопрос: `Сколько продали вчера и чего продали. Полный отчет`.

После вызова 1 агент отдал меню из трёх **сущностей** (подписи из `TABLES.label`, не оси периода):

1. Оптовые продажи  
2. Движения реализации с себестоимостью  
3. Реализация ТМЦ  

Источник в gateway: `clarify_lock … opts=3` + текст уточнения (`gateway-extract.txt`).

### 1.2 Это не исход B

| Исход | Код | `kind` | Что в options |
|---|---|---|---|
| **B** (fork) | `z13_fork_outcomes.py:491-563` `fork_outcome_b` | **`figures`** | люк остальных **веток прочтения** (day_basis / amount_basis / window); число лидера уже в `text` |
| **C** (fork) | `z13:776-932` `fork_outcome_c` | `clarify` / `figures` / `no_data` | ветки fork с подписями оси |
| **Entity clarify** | `z20:3613-3854` (арбитр diverge / mute / `len(picked)>1`) | **`clarify`** | **типы записей** («Оптовые продажи», «Реализация ТМЦ»…) |

Живое меню — третий столбец. Вызов идёт через `clarify_say` (`z20:326-348`) → нумерованные строки из options.

Точка сборки ответа сервиса: `answer()` / `answer_checked()` в `z20_ask_main_http.py` (`answer` ~1808+, вход HTTP `Handler.do_POST` ~6021+, `ThreadingHTTPServer` ~6120).

### 1.3 Где решается clarify по сущностям

Порядок в `answer()` после отбора кандидатов (упрощённо):

1. **Разбор + отбор + порядок/rerank** — всегда до развилок (`z20:1907+`, `2011+`, `2104+`, rerank-голова ~2425–2553).  
2. **Fork-детектор** (`FORK_DETECT`, пул ≤ `ARBITER_MAX*4=16`) — `z20:2673-2734`; при `FORK_OUTCOMES` судья A/B/C — `z20:3473-3610` → `resolve_fork_outcome` / `fork_outcome_*` в `z13`.  
3. Если fork не закрыл вопрос и `len(arb_pool)>1`: **полный под-ответ на каждого кандидата**  
   ```text
   for c in arb_pool[:ARBITER_MAX]:   # default 3
       answer(question, focus=c, no_arbiter=True, …)
   ```
   (`z20:3613-3629`). Это **N полных кругов** (разбор/отбор/счёт/compose) внутри одного ask.  
4. Числа разошлись / соперник mute → `kind=clarify` + `clarify_say` (`z20:3766-3769` и соседние ветки 3714, 3818, 3833).  
5. Дешёвый clarify `len(picked)>1` **только после** блока арбитра (`z20:3841-3854`) — то есть если арбитр уже бегал, «дешёвый» путь уже не спасает.

Для «продали» дополнительно: sales-канон / lift (`z11_sales.py`), wiki-каскад (`z21`) — могут зафиксировать одну сущность (`wiki_arbiter_locked`) и снять fork/arbiter; в этом замере wiki агенту **не дали** (`braine-verify … block side tool=wiki_search` ×несколько до первого ask).

### 1.4 Что такое «полный отчёт» после выбора ветки

После clarify человек/агент обязан вернуть выбор:

- в **репо-мосте**: `decision_id` (одноразовый билет) или текстовый pending (`mcp_ask_pending.apply_pending_before_ask`); сервис — `answer_checked` + `consume_decision` (`z20:5758-5826`);  
- в **старом мосте** (см. §2): снова тот же `question` + `focus=<человеческая подпись>`.

Дальше один проход `answer(..., focus=…, trusted=…)`:

- «сколько» → агрегат (sum/count) по окну «вчера»;  
- «чего продали» / «полный отчёт» → скорее `want=list` / rank×ось номенклатуры (`z11` `sales_rank_*`, `z10_rank` `rank_axes_rerank`, `z18_compose` grain=`group`) — **тяжёлый хвост**: оси → rerank осей → GROUP BY → compose списка.

Именно этот хвост после выбора — главный кандидат на **>300 с** вызова 2 (в срезе serene: непрерывные `rerank` 06:40:28–06:42:22 до обрыва клиента).

Не «цикл по всем трём веткам меню» в одном вызове после выбора: после `focus`/`trusted` арбитр и fork-исходы гасятся (`no_arbiter` / `trusted` в условиях `z20:3473+`, `3613+`). Дороговизна — **один** глубокий отчёт + повторный полный префикс (разбор/отбор/rerank), плюс конкуренция с orphan-потоком предыдущего ask (W1 §0).

## 2. Разбор TimeoutError

### 2.1 Кто бросает

Цепочка:

```text
OpenClaw mcp (requestTimeoutMs=300000)
  → 1c-mcp-ask ask_1c
      → urllib.request.urlopen(ASK_URL+"/ask", timeout=ASK_TIMEOUT)
          → 1c-serene-ask POST /ask  (ThreadingHTTPServer, своего wall-timeout НЕТ)
```

В репо:

- потолок моста: `TIMEOUT = float(os.environ.get("ASK_TIMEOUT", "300"))` — `ubuntu/openclaw/mcp_ask.py:50`;  
- вызов: `urlopen(req, timeout=TIMEOUT)` — `:119`;  
- ловля: `except Exception` → `kind=error TimeoutError` в TRACE — `:543-546` (имя типа `TimeoutError` / `socket.timeout` у urllib3/stdlib).

`I2_ENGINE_TIMEOUT` — **не** runtime serene-ask. Это env прибора `work/gold/i2_runner.py` (умолч. 120 с). К вызову WebUI не относится.

У serene-ask внутреннего `ASK_TIMEOUT` / `wait_for` на весь `/ask` в коде нет: крутит до конца или до исключения модели/БД (`Handler.do_POST` `:6021-6112`).

### 2.2 Два потолка по 300 с

| Слой | Где | Значение в замере |
|---|---|---|
| OpenClaw MCP client | `.openclaw-web/openclaw.json` → срез `web-profile-config.txt`: `requestTimeoutMs: 300000` | 300 с |
| mcp-ask → serene-ask | `ASK_TIMEOUT` default 300 (`mcp_ask.py:50`) | **300080 мс** = сработал **этот** urlopen |

Совпадение потолков: гонка. Здесь победил мост (TRACE `ask_reply 300080 kind=error TimeoutError`). Клиенту уходит `ERROR_REPLY` с `TimeoutError`, не частичный отчёт.

### 2.3 Что с частичной работой

- **Клиент / агент**: ничего полезного — только ошибка сервиса.  
- **serene-ask**: поток `ThreadingHTTPServer` **не отменяется** при обрыве urlopen. W1: после 06:42:23 rerank ещё идут; orphan засоряет stderr и CPU следующего ask (вызовы 3–4).  
- **Билет clarify / pending**: вызов 2 не дошёл до успешного `kind=figures/answer`; погашения выбора нет. Агент на вызове 3 снова получил `clarify` (15 с) — цепочка выбора фактически сброшена с точки зрения UX.

## 3. Ранний clarify за 10–20 с? (стык с W1)

### 3.1 Что обещает код

| Путь | Когда clarify | Цена до ответа |
|---|---|---|
| Fork C | после `fork_detector_scan` по пулу | отбор+rerank+SQL fork; **без** N×`answer` арбитра |
| Arbiter diverge | после `ARBITER_MAX` полных под-ответов | **максимум** (×3 круга) |
| `len(picked)>1` | **после** блока арбитра | «дешёвый» только если арбитр не бегал |

**Нет** ветки вида: «три разных label в голове кандидатов → сразу меню, без разбора/отбора/реранков».  
Для составного sales-вопроса вызов 1 (154 с) с высокой вероятностью прошёл **префикс W1 + (fork и/или arbiter×N)** и только потом `clarify`. Детальных TRACE вызова 1 в срезе нет (W1 §0) — реконструкция по коду.

### 3.2 Вызов 3 = 15272 мс clarify

Доказывает: clarify **может** уложиться ~15 с на тёплом/узком проходе (меньше кандидатов, `focus`/кэш embed, без arbiter×3).  
**Не** доказывает ранний выход «до фаз 12–14 с ×3 + 30 rerank»: у вызова 3 в срезе нет TRACE фаз; у вызова 4 как раз видны разбор 12,5 с и хвост rerank — и это **после** повторного clarify, на пути к отчёту.

Итог по вопросу «можно ли сейчас early clarify»: **нет, не на этом коде**; вызов 3 — другой профиль, не перенос clarify перед отбором.

## 5. Где умер вызов 2 и что сократить

### 5.1 Точка смерти

```text
mcp_ask._ask → urlopen(ASK_URL/ask, timeout=300)
  ↑ ровно здесь: TRACE ask_reply 300080 kind=error TimeoutError
serene-ask в это время ещё жив (rerank до 06:42:22), ответа HTTP клиенту уже нет
```

Не `I2_ENGINE_TIMEOUT`. Не отдельный raise внутри serene-ask с именем TimeoutError на весь запрос (таких нет). OpenClaw `requestTimeoutMs` совпадает по величине, но TRACE ошибки пишет **мост**.

### 5.2 Рекомендации (файл:строка), без правок в этом заходе

**A. Уложить «полный отчёт» в бюджет <300 с (или честно поднять оба потолка вместе)**

1. **Не гонять arbiter×N до entity-clarify**, если уже видно ≥2 живых кандидата с разными числами/подписями — перенести логику уровня `z20:3841-3854` **перед** циклом `z20:3621-3629` (или после fork C без под-ответов). Цель: clarify вызова 1 за десятки секунд, не 154 с.  
2. **После `trusted`/`focus`**: не повторять полный cold-отбор 16+ сущностей и десятки rerank; узкий путь «одна src + период + list/rank» (сейчас `hold_settled_entity` / `trusted` гасят fork, но префикс parse+search всё равно тяжёлый — `z20:1907+` до focus-ветки).  
3. **Составной вопрос**: один SQL group (сколько + чего) вместо list+отдельного compose-хвоста; или два явных ask с общим `focus` (агентный контракт), без второго полного поиска сущности. Точки: `z11_sales.py` rank/list, `z18_compose.py` grain=group, `z10_rank.py:170+`.  
4. **Потолки**: `ASK_TIMEOUT` (`mcp_ask.py:50`) и `requestTimeoutMs` (openclaw-web mcp) поднимать **парой**; иначе снова гонка. Либо оставить 300 с и резать работу (предпочтительно по TARGET: ответ быстрее, не «дольше ждать»).  
5. **Отмена orphan**: при обрыве клиента не оставлять serene-ask считать минутами (сейчас `ThreadingHTTPServer` `:6120` без cancellation) — иначе вызов 3/4 деградируют.

**B. Поведение агента после ошибки**

6. После `TimeoutError` / `[SERVICE ERROR]` — **повтор с тем же `focus`/`decision_id`**, не новый clarify. Стык: docstring/`decision_id` в репо-мосте `mcp_ask.py:485-502`; на проде сверить, что выкачан мост с билетами (локальный `/opt/openclaw-mcp/mcp_ask.py` в этом LXC — старая схема focus-only, 305 строк; okna TRACE `ask_reply` похож на новый мост — сверить md5 на окне).  
7. Не жечь ходы на `wiki_*`, если verify их режет до ask (`gateway-extract`: block side tool=wiki_search).

**C. Замер, который закрыл бы дыры среза**

8. На успешном и на timeout-ask: одна строка TRACE в конце `answer_checked` с `fork_outcome`, `arb_pool`, `trusted`, `sec`, `focus` (сейчас вызов 1 в срезе слепой — W1). Без этого arbiter×3 vs fork C для вызова 1 остаётся реконструкцией.

## 6. Краткая схема эпизода

```text
Владелец: «сколько + чего + полный отчет»
    │
    ├─ ask#1 154с → entity clarify (3 src)     ← дорого: префикс+развилка/арбитр
    ├─ выбор человека / агента
    ├─ ask#2 ≥300с → TimeoutError в mcp urlopen ← serene ещё rerank'ает
    ├─ ask#3 15с  → снова clarify               ← лишний круг
    └─ ask#4 …    → снова полный префикс         ← лог обрезан
```

**Сжать:** clarify раньше и дешевле; после выбора — узкий отчёт без повторного поиска сущности и без orphan-нагрузки; потолки MCP/моста не разъезжать; агенту — ретрай с билетом, не второе меню.
