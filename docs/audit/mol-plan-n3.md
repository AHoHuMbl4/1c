## 1. 4a — второй `fork_detector_scan` на исходах A/B

### Два места в коде

| # | Файл:строки | Пул | Что пишет |
|---|---|---|---|
| **Ранний** | `z20:2675–2736` → `fork_detector_scan` `:2702` | `cands[:max(ARBITER_MAX*4, 16)]` + prefer_*/event_filter → `_fork_pool` | `diag.fork` + **`_fork_early`** `{rows,cls,rel,pool}` |
| **Исходы** | `z20:3479–3554` → снова `fork_detector_scan` `:3508` | **`arb_pool` целиком** (+ merge `_fork_early.pool` при `_ef_early`) | перезаписывает `diag.fork`, **не читает** `_fork_early.rows/cls` |

Реализация детекции: `z09:404+` → readings → `fork_scan_readings` / `fork_scan`
(`z09:242–365`). Исходы A/B/C — `resolve_fork_outcome` (`z13:286+`) **после**
второго скана (`z20:3554+`).

### Что отличает «повтор нужен» от «повтор зря»

Сейчас условия входа **разные**, reuse **нет**:

- Ранний: `FORK_DETECT ∧ ¬no_arbiter ∧ len(cands)>1 ∧ ¬_skip_stock_fork`.
- Исходы: `FORK_OUTCOMES ∧ FORK_DETECT ∧ ¬no_arbiter ∧ ¬trusted ∧ ¬wiki_arbiter_locked ∧ (len(arb_pool)>1 ∨ _window_fork ∨ _ef_early)`.

Комментарий у второго скана (`z20:3496–3498`) — канон риска: **исход B обязан
судиться по `arb_pool`, не по `cands[:16]`** (регресс B8-01: ранний пул тянул
посторонние классы; `arb_pool[:3]` резал эталонные пары).

Честное условие reuse (из M2 №2, не из текста плана):

| Повтор **зря** | Повтор **нужен** |
|---|---|
| `_fork_early` заполнен и множество `arb_pool` ≡ (или ⊆ с тем же `rel`) `_fork_early.pool`; preds/readings/intent не менялись | пул разъехался (wiki/writer_pair/prefer_*/event/sales-canon); `_ef_early` дописал ранний пул к `arb_pool`; раннего скана не было (`_skip_stock_fork`, `len(cands)≤1`) |

Формулировка плана «не гонять на исходах **A/B**» **неточна**: исход узнаётся
**после** классов; нельзя «пропустить скан, потому что A», не имея `_cls`.
Правильнее: *reuse `_fork_early`, когда пул совместим; иначе один скан на
outcome-пуле (и тогда ранний можно не дублировать)*.

### Риск пропуска нужного повтора

1. **B8-01**: reuse раннего пула → чужие классы / неверное B или C.
2. Между сканами пул **меняется** (wiki lock, writer_pair, prefer_entity_for_*).
3. Ложный A по ранней голове → пропуск исхода B по полному `arb_pool`.
4. `_ef_early` **специально** расширяет `_out_pool` — там второй скан часто
   обязателен.

**Вердикт 4a:** идея M2 верна (−5…12 с, когда оба срабатывают); текст плана
нужно заменить на *reuse при совместимом пуле / один скан на outcome-пуле*.
Без этого — риск регресса B. Атомарно откатывается.

## 2. 4b — кэш `measures_of` в запросе

### Где повторные вызовы (M3: 2 SQL без кэша)

`measures_of` (`z08:147–177`): **каждый зов** = 2×`psql` —
`unnest(map_keys(nums))` по `src_table` + `search_measure_alias`. Кэша нет.

В `z20` — **≥12 сайтов** после выбора `src` (мера / totals / clarify / stock
fallback: `:4143`, `:4163`, `:4185`, `:4224`, `:4231`, `:4245`, `:4260`,
`:4327`, `:4365`, `:4469`, `:4569`, `:4575`, …). M3: лёгкий 3–5 зовов
(=6–10 SQL), тяжёлый 6–10 (=12–20) **на один** проход; арбитр ×N умножает.

Контраст уже в коде:

- `_measures_by_src` (`z09:105–126`) — **один** unnest корпуса + TTL процесса
  `ASK_FORK_MEAS_TTL` (600 с) — другой слой, не request-cache `measures_of`.
- `measures_of_many` (`z17:407`) — батч nums для holder-пути; обычный
  `measures_of` его не зовёт.

### Ключ кэша

В пределах одного rid: **`(src_table,)`** (строка сущности). Опционально
общий dict на ContextVar `_rid_get()` (`z01:71–100`) или поле `diag`/локал
`answer()` — главное: **не процессный TTL** (иначе дрейф между HTTP).

### Инвалидация внутри rid

Состав величин сущности в ask **не меняется** (корпус read-only для
`serene_ro`). Внутри rid инвалидация **не нужна**. Под-`answer` арбитра
должен **наследовать** тот же кэш (общий rid / общий dict), иначе выигрыш
съедается ×N. Не путать с `_fork_meas_cache` (процессный, полный корпус).

**Вердикт 4b:** дешёвый, атомарный, совпадает с M3 (г). Ожидание: −10…30
вызовов/проход → **−0.3…1 с** транспорта (+ меньше unnest SQL). Не путать с
выигрышем K6.

## 3. 4c — stock-фильтр через индекс (стык с N2)

### Что в коде сейчас

Post-K6 (`z20:2270–2286`): снова `stock_question_engaged` + фильтры.
Тяжёлое тело — не «тот же corp-агрегат K6», а:

1. **pred** `stock_question_engaged` ×3 (word-loop catalogs) — M1;
2. `registers_for_kind_axes` (`z12:457–466`): `EXISTS (SELECT 1 FROM
   search_corpus c WHERE c.src_table = r.src_table AND nums…)` —
   коррелированный зонд корпуса, **не** `FROM search_idx … @@`.

§3 плана: corp-агрегат/live/unnest K6 → `search_idx` (keyword `src_table`,
`corpus_init.sql:420`) или materialized-агрегаты.

### Тот же механизм или свой?

| | §3 (K6) | 4c (stock) |
|---|---|---|
| Цель SQL | `GROUP BY`/FILTER по пулу IN(≈77) | EXISTS «есть nums» + pred |
| Индекс `search_idx` | да, если переписать `FROM index` | **сам EXISTS не тот же запрос** |
| Общий фикс | витрина/`n_rows`/`n_with_nums` по `src_table` | **да**: stock читает тот же агрегат вместо EXISTS (M1: «антисем / n_with_nums из F1») |

Итого: **не клон SQL п.3**, а **потребитель того же артефакта** (F1/витрина).
N2/N4 уже бьют: M4 ставил stock-**skip** до K6 после E8; план спрятал в 4c
после п.3 — ранняя полигонная экономия −10…21 с без L67 теряется как шаг.

### Запасной вариант, если индекс не покрывает word-loop EXISTS

1. **Кэш pred** `stock_question_engaged(q,intent)` на rid + не звать pred
   внутри фильтров (M1/M4) — не зависит от индекса.
2. **Skip тела** на `sales_sum` / report-lex (M4 R2) — если E8 подтвердил
   ложный engage.
3. **Витрина** `src_table → n_with_nums` с такта сборки / reuse F1 features —
   покрывает EXISTS без `@@`.
4. Если только `search_idx` keyword — для коррелированного EXISTS по
   `r.src_table` план может остаться table-scan → **не обещать 4c ≡ п.3**.

**Вердикт 4c:** направление ок при явной связке «артефакт п.3 → stock»;
как написано — дыра (N2). Атомарность: да, если отдельный коммит; эффект
−15…21 с — **гипотеза** до E8.

## 4. 4d — fork readings батч-SQL

### Форма батча по коду `z09`

Сейчас (`fork_scan_readings` `:319–365`):

```
for rd in readings:          # до ~4–8 после calendar×currency
    preds_w = period_preds(rd)
    [опц. split catalog_ / dated_ — ASK_ENTITY_FORM]
    fork_scan(...)           # 2 SQL: count/folders GROUP BY; unnest sums
    [опц. currency_patch_fork_scan]
    → cells (src, window_fp, status)
```

Целевая форма (M2 №3, штатно п.20): **один** (или два: dated‖cat)
SQL с ключом окна в SELECT/`GROUP BY` (`src_table`, `window_fp` /
`from`/`to`/`day_basis`…), вместо N×`fork_scan`. Пул ThreadPool вокруг
SQL — план §5 запрещает; согласовано.

### Риск изменения порядка / результатов

1. Порядок `cells` / итерация `merged_rows` → `fork_classes_windowed`
   (`:368+`) — смена порядка src в классе / meta-лидера day_basis/amount_basis
   (`:390–399`).
2. Ветвление `ASK_ENTITY_FORM` (catalog без date-pred) нельзя слить в один
   WHERE с dated без смены семантики.
3. `currency_patch_fork_scan` сейчас **после** каждого окна — батч обязан
   сохранить ту же семантику патча.
4. Эквивалентность: те же `status=no_live_cells` / `computed` на каждую
   пару (src, window_fp).

Приёмка: эталонные исходы B/C + `счёт_мс` fork −≥40% (M4 шаг 5).

**Вердикт 4d:** сильный рычаг (−6…10 из ~12 с), атомарный; риск качества —
порядок/meta, не «просто быстрее». Нужен замок fork + сверка cells.

## 5. 4e — psycopg3 «последним, отдельным решением»

### Правильно ли вынесено последним?

**Да.** M3: сначала (г) число SQL (кэш measures, батчи), затем (б)
транспорт. После §1 (A2 режет путь) + §3 (K6 SQL) + 4a/4b/4d число
подпроцессов и wall SQL падают; чистый транспорт 150–220×35 мс (=6–9 с)
на «оставшихся» вызовах может стать **≲2–3 с** (ориентир M3 после кэша:
≲100 вызовов ×35 мс ≈ 3.5 с; после early-clarify без arbiter — ещё меньше).

### Сто́ит ли вообще, если транспорт <2 с?

| Если после 4a–4d | 4e |
|---|---|
| `psql_n` ≲40 и SQL уже ≤ цели W4 | **опционально**: −1…1.5 с, цена — deps/venv/типы; отдельное решение владельца оправдано |
| `psql_n` всё ещё ≳100 (арбитр×N на полном пути) | **да**: −3…6 с чистого fork-транспорта; W4 полный отчёт может упереться именно сюда |
| Лечить **52 с K6** транспортом | **нет** (M4/M1: <2% фазы K6) — план правильно не ставит 4e до п.3 |

Вынос «отдельным решением» — верно: не блокирует 4a–4d; приёмка своя.

### Что перенести из `mol-psql-m3` в план как конкретику

1. **`threading.local()`** conn на поток; `connect(DSN)` lazy; **не** шарить
   между потоками.
2. Сигнатура `psql(sql)→list[list[str]]` на первом шаге **или** сразу
   `fetchall` + приведение к str — **замок** на строке корпуса с `\n` в
   `doc`/`refs` (CSV≡native).
3. Второй local для `_resolver_psql` / `RESOLVER_DSN`.
4. `psycopg[binary]` в `/opt/openclaw-mcp/venv` + requirements.
5. Приёмка: `SELECT 1`×30 ≪1.05 с (≲100 мс); 2 параллельных HTTP без
   cross-talk; `diag.psql_n`; замки zone.
6. Счётчик вызовов **до** смены транспорта (M3 шаг 1 миграции).

**Вердикт 4e:** порядок верный; конкретика M3 в план **не перенесена** —
дыра для стоп-точки. Конфликт с `ThreadingHTTPServer` — только при общей
conn; thread-local = штатно (`z20:6239`).

## 7. Атаки (≥3)

### Ат1 — кэш 4b скрывает дрейф внутри запроса

Если ключ кривой (забыли `src`, закэшировали глобально по процессу, или
arbiter-дочерний `answer` с другим focus читает чужой src) — мера/totals
могут быть от **другой** сущности при том же rid. Процессный TTL как у
`_fork_meas_cache` усугубит дрейф **между** HTTP после пересборки корпуса.

**Контр:** ключ `(rid, src_table)`; lifetime = rid; arbiter шарит dict;
приёмка: смена focus → miss; два HTTP → два dict.

### Ат2 — батч 4d меняет выдачу fork-детектора

Смена порядка GROUP BY / слияние окон / ошибка в entity_form split → другие
классы → A↔B↔C. B8-01 уже доказал чувствительность к пулу.

**Контр:** побитовая сверка `cells`/`classes` на эталонах; L67 fork; не
менять `fork_classes_windowed` meta-правила day_basis.

### Ат3 — 4e «конфликтует» с `ThreadingHTTPServer`

Ложная атака, если conn **thread-local** (M3: 1 conn/поток = норма для
`ThreadingHTTPServer` `:6239`). Реальный конфликт: **общая** conn /
пул без замка → cross-talk, сломанный state, гонки типов.

**Контр:** явный запрет shared conn в плане; замер «2 HTTP параллельно»;
reset при ошибке протокола.

### Доп. (коротко)

- **4a без условия пула** → регресс B (см. §1).
- **4c = «тот же индекс»** без витрины → EXISTS всё ещё table-scan; ложный
  «закрыли 21 с».
