# I0v2 — План: транспорт LLM (локальная 27B + нативная схема) + семантический verify

Дата: 13.09.2026 (v2 — после красной проверки `I1-проверка-плана.md`, 5 атакующих).
Контракт неизменен: один путь (вопрос → вики → SQL → меню при >1 прочтении → выбор →
ответ), TARGET.md п.0, никаких гейтов по словам, люков, «вторых чисел», подгонок.

## 0. Диагноз (уточнён проверкой)

1. **Флип verify — главный недолеченный узел**: один и тот же вход даёт то yes→число,
   то no→no_data (подтверждено по токенам in=671, out 229 vs 237). Причина НЕ в нехватке
   данных: паспорт уже несёт aliases/bestUsedFor в теле (255/255 страниц, замер) —
   вердикт нестабилен сам по себе (z02:644: 18/58 при temp=0).
2. Щель degraded: непроверенный модельный пик уходит в ответ (z21:1139-1140 `pass`).
3. Дыра пула «прайс»: object-ветка (wiki_card_hybrid.sql:247-256) режет носителя
   informationregister_ценыноменклатуры до судьи; послабление = +1 карточка (замер).
4. Наблюдаемость: fit/why вердиктов не сохраняются ни в diag, ни в jsonl прогона —
   калибровка слепа.
5. Метрика приёмки слепа к 16 honest_no с числовым эталоном и 6 меню-ловушкам
   (classify_verdict до сверки с эталоном) — очередь отдельного эпизода (J).

## 1. Транспорт: остаёмся на ds_chat, модель — локальная 27B владельца

Решение по llm-task (5/5 проверяющих): НЕ переезжаем. llm-task — optional Lobster-крючок
(«not currently reliable» в доке сборки), +0.42 с на вызов (+18-30% на наших коротких),
причины ошибок наружу не выходят, usage нет, нужен операторский токен шлюза на LAN.
Пилот снят: :18801 — боевой канал (Open WebUI клиента), а 20 вопросов на флип-узле
ничего не докажут.

Нативное берём там, где оно реально проверено людьми — у провайдера модели:

1. **Модель: локальная 27B** (владелец поднял; адрес:порт — по его подтверждению).
   Переключение: /etc/1c-serene-ask-postgres.env + /etc/1c-serene-ask.env (DEEPSEEK_BASE/
   DEEPSEEK_MODEL/ключ) → рестарт юнита (он остановлен с 12.09 15:37) → health →
   контрольные вопросы → замер латентности против OpenRouter-среза.
   Кредиты OpenRouter (остаток 5.90/35) перестают расходоваться; 402-блокер исчезает.
2. **Нативная схема ответа**: проба response_format/guided_json (json_schema) на нашем
   vLLM — если поддерживается, включаем для вердикт-вызовов (pick/verify/intent):
   жёсткое ограничение генерации при декодировании, строже любого пост-валидатора.
   Пробы локальные — бесплатны.
3. **Валидатор-фолбэк свой** (один модуль, замок): enum/minItems/additionalProperties,
   невалид → повтор ×1 → degraded-семантика (см. П5). Только как фолбэк, не второй путь.

Не делаем: переноса свободнотекстовых вызовов (compose/REFUSE), правки tools.allow
шлюза, операторских токенов, maxConcurrent, цепочки дедлайнов (88 код / 90 мост живы).

## 2. Правки (порядок по проверяющим: наблюдаемость первой)

- **П2 (первый пакет, поведение не меняет): наблюдаемость.**
  diag-verdicts (fit+why, санитизация в одну строку) внутри wiki_verify_candidates
  (z21:957-967); i2_runner пишет diag в jsonl (правка :830-858, выкат в work/gold);
  живой дамп паспорта «что реально видит судья» (первые 1500 симв, 3-5 страниц).
  Замок: diag несёт wiki_verdicts; TRACE-строка без перевода строк.
- **П2b: согласие verify на sole-yes (лечит флип).** При ровно одном yes и всех
  остальных no — повторный вызов verify (тот же вход). Совпало (тот же лидер) → лидер;
  разошлось → clarify-меню по yes+unsure пулу (п.21: данные есть — спросить).
  По образцу INTENT_SAMPLES (z02) — существующий паттерн проекта, не новый выбирающий
  механизм, не слова в коде. Стоимость: +1 вызов только на sole-yes (на локальной
  модели бесплатно по деньгам); латентность замерить.
- **П5: непроверенный пик не уходит в ответ.** degraded при pick=leader → пик не
  утверждается; исход пересобирается по пулу (меню при >1 кандидате, при 1 — повтор ×1
  → no_data). Меню не роняем (п.21). Замок уровня try_wiki_hybrid_entity_pick.
- **П4: носитель alias'а доходит до судьи.** Колонка-провенанс src_kind в конец пула
  (позиционных потребителей не ломать: z21:342-361); освобождение ТОЛЬКО struct_alias
  от object-ветки (не struct_named по стемам, не parent-фильтр want_agg — его назначение
  измерено). Замер не «раздувание меню», а «кто вытеснен из топ-8» (LIMIT 8).
  Требует живого эмбеддера (kNN) — только после снятия блокеров §4.
- **П1 (пересмотрен): не «+колонки»** (посылка опровергнута: поля уже в теле 255/255).
  Решение по факту дампа из П2: если смысловые поля тонут в свалке текста —
  структурированные строки паспорта (about:/askedAs:) как A/B против текущего вида,
  с прогоном до/после. Без положительного замера — не выкатывать.
- **П3 (последним): топики отдельной колонкой.** Новая колонка topics в
  search_entity_alias (VARCHAR[]/JSON), наполняет ГЕНЕРАТОР (1c-wiki-alias) из
  метаданных базы — на чужой базе свой словарь, ничего в коде. not_enough_for (текст)
  НЕ трогать: коллизионный круг (2 SQL, ILIKE, 38 пар) живёт на нём. Паспорт судьи
  дополняется topics-строкой; форматтер не меняет подписи меню (там санизация уже
  режет эти поля). Замки: эмиссия топиков, коллизионный круг зелёный на новом поле.

## 3. Приёмка

- База «до»: после П2 — снятие контрольного среза (20-30 вопросов полигона, diag
  сохранён) — до любых поведенческих правок.
- Поимённая приёмка: «склад позиций» ≠ число 79705; «прайс» → 2389 или меню с
  ценовым носителем (не 2399 номенклатуры). Список новых wrong поимённо пуст.
- Парные прогоны (флип-шум отличаем от эффекта): минимум 2 повтора одного среза.
- L67 полный — один раз в конце (не жечь на П4: там контрольные + меню-замер).
- Критерий: wrong ≤ 2 (поимённо те же классы, не другие), match ≥ 32, молчаливых 0.
- **Стоп-точка владельца перед выкатом прода — обязательна.**
