# G1 — МЕХАНИКА: как нерелевантный лидер дошёл до числа

Дата: 12.09.2026. Код: HEAD `057b148` (= md5 ask на okna).  
Источник прогона-проблемы: `/tmp/i2-onepath-final/i2-answers.jsonl` (engine, 2× `confident_wrong`).  
Живые SELECT / повтор `/ask` :8091 на окне okna (`gpu-erw:2202`). Код не менялся.

## Вердикт

Число на размытом вопросе получается не одним багом, а **дырой между слоями**:

1. INTENT кладёт место/роль (`склад`, `прайс`) в `search_form` / `kind`, а **`terms` оставляет пустым** — по правилам разбора (значения ≠ род).
2. Гибридный пул всё равно находит посторонних кандидатов (kNN + alias + object-фильтр).
3. Verify — **единственный судья темы**, и он LLM-ный: в i2 сказал `yes` «Реализация ТМЦ»; при повторе 12.09 по тому же вопросу сказал `no` всем → `no_data`.
4. Утверждение лидера (`wiki_outcome_from_verify`) смотрит только на счётчик `yes`/`no` (+ оси/омонимы), **без сигнала «паспорт покрывает топик вопроса»**.
5. SQL-ступень `unmatched` **не срабатывает при `terms=[]`**, а пустой `match` считает **всю** выбранную таблицу → число.

Отсутствующий сигнал в решении лидера: **topic-coverage** (согласованность топика вопроса с `bestUsedFor` / `doesNotAnswer` / осями паспорта), удерживаемый кодом — не только `fit=yes` модели.

## 1. INTENT: какие термы

|---|---|---|---|---|---|---|
| …на складе позиций… | `[]` | позиции | count | **object** | `""` | позиции на складе |
| …в прайсе всего | `[]` | позиции | count | **object** | `""` | позиции в прайсе |

Почему `terms=[]` — не сбой, а контракт промта:

```783:789:ubuntu/serenedb/ask/z01_infra_trace_llm.py
Rules:
- "terms" holds only VALUES that should literally appear in a record: names of parties,
  goods, places, document numbers. NEVER put the KIND of records there — that goes to
  "kind". A record need not contain the word naming its own kind.
- A word for a ROLE of a party (supplier, customer, employee, payer) names a kind of
  party, not a particular one. It belongs to "kind" or nowhere — a role word in "terms"
```

«Склад»/«прайс» остаются в `search_form` (вход пула), но **не становятся row-filter**.  
Код ещё вычищает kind/measure из terms, если база знает их родом (`z02_intent.py:454–484`).

Диаг `/ask`: `понятий=0`, `terms: []`, `preds: []`.

## 2. Гибридный пул: кто попал и почему

Точка: `wiki_hybrid_pool` → SQL `wiki_card_hybrid.sql` → `filter_pool_by_named_type`  
(`z21_wiki_choice.py:323–362`, `:1098–1114`; SQL `:197–273`).

### 2.1. «Склад» (живой пул с diag)


Слои SQL:

- **kNN / kNN_raw** (`wiki_card_hybrid.sql:27–55`) — по `search_form` «позиции на складе» и сырому вопросу; «позиции» тянет товарно-учётных соседей, в т.ч. регистр продаж.
- **struct_alias** (`:138–150`) — bm25 по `aliases @@ question`; у `catalog_местахранения` aliases: «склады,…» (`search_entity_alias`, SELECT).
- **struct_register / struct_catalog** — требуют `action_axis <> ''`; у нас ось пуста → **не сработали**.
- **filtered при `action_class=object`** (`:253–255`): оставляются `catalog_%` **и** `accumulationregister_%` — поэтому «Реализация ТМЦ» **законно** проходит структурный фильтр object-вопроса.

Alias bm25 по слову `склад` (SELECT): `catalog_местахранения` 4.18, журнал/документы склада — рядом; **реализациятмц в alias-топе по «склад» нет** → в пул её несёт в основном **вектор**, не словарь.

## 3. Verify: вердикты и паспорта

Вызов: `wiki_verify_candidates` → LLM `WIKI_VERIFY_SYS` → `wiki_outcome_from_verify`  
(`z21_wiki_choice.py:50–57`, `:934–968`, `:871–931`).

В паспорт модели уходит `doesNotAnswer` = поле `search_entity_alias.not_enough_for`  
(`wiki_passport_enrich` `:639–681`, формат `:684–710`).

### Живые паспорта (SELECT)

**Реализация ТМЦ** — bestUsedFor: итоги продаж / кол-во проданных / себестоимость;  
notEnoughFor: детали сделки / экспорт / услуги.  
**Склада / остатков / «позиций на складе» в doesNotAnswer нет.**

**Места Хранения** — bestUsedFor: список складов; notEnoughFor: стоимость/состояние ДА.  
**Не заявляет «сколько позиций на остатках».**

**Номенклатура** — aliases про позиции; bestUsedFor про хранение позиций и «установка цен»;  
notEnoughFor про виды номенклатуры. **«Прайс-лист» как сущность не отмечен чужим.**

**Цены Номенклатуры** — aliases: «прайс-лист»; bestUsedFor: текущая цена.  
В пуле «прайс» при object **не участвует** (см. §2.2).

### Вердикты

|---|---|---|
| склад (i2) | (в jsonl diag нет; ответ = лидер реализациятмц) | был ровно один `yes` на регистр продаж |
| склад (повтор) | **0 / 7 / 0** | `outcome=none` → `no_data` |
| прайс | **1 / 7 / 0** | лидер `catalog_номенклатура` |

Verify **не детерминирован** на границе «размытый топик»: один и тот же пул «склад» в i2 утвердил продажи, сегодня отверг всех. Паспортного маркера «этот регистр не отвечает про склад» модели не дали.

## 5. Почему unmatched на z20 не остановил

```2104:2117:ubuntu/serenedb/ask/z20_ask_main_http.py
    # Row-filter после меню: unmatched → no_data (не выбиратель сущности).
    exprs, kinds = probe(intent.get("terms") or [])
    ...
    n_groups = len(intent.get("terms") or [])
    matched_groups = matched_group_count(kinds)
    if n_groups > 0 and matched_groups < n_groups:
        diag["unmatched_terms"] = ...
        return {..., "kind": "no_data", ...}
```

Факт diag (прайс / поставщики / …): `terms: []`, `match_by: {}`, `min_should_match: 0`, **`unmatched_terms` отсутствует**.

Следствия:

1. При `n_groups=0` ветка no_data **недостижима** — контроль выключен.
2. `probe` / `tables_of` со пустым match не режут строки: счёт идёт по всей `src_table`.
3. Даже если бы «склад» попал в terms: в индексе `ts_phrase('склад')` = **24** строки (местахранения 3, настройки 20, …), в **`accumulationregister_реализациятмц` — 0**. Unmatched смотрит **глобальное** наличие понятия, не «есть ли оно в выбранном src». Глобально «склад» нашёлся бы → unmatched всё равно пропустил бы; резал бы уже `rows_of` с match. Но terms пуст → match пуст → **полный count 79705**.

Живой corpus-probe:

| Условие | count |
|---|---|
| idx `склад` phrase | 24 (не в реализациятмц) |
| реализациятмц ∧ склад | **0** |
| idx `прайс` phrase / like | **0** всюду |
| leaves номенклатуры | **2399** (= ответ) |
| distinct номенклатура в ценах | 1892 (≠ эталон 2389; эталон ближе к каталогу, чем к IR) |

Итог по (5): unmatched не «нашёл склад в строках лидера» — он **вообще не вызывался как стоп**, потому что INTENT не положил склад/прайс в terms.

Диаг прайса: `счёт.where = src_table = 'catalog_номенклатура'` без doc-фильтра; `found: 2403`, `n_rows: 2399` (минус 4 папки).

## 6. Где путь можно было честно закончить no_data / меню

По порядку тракта (файл:строка):

| # | Место | Что уже есть | Чего не хватает для честного стопа |
|---|---|---|---|
| A | INTENT `terms` vs `search_form` (`z01` RULES; `z02:445–452`) | место/роль в search_form | топик-слово не становится ни terms, ни отдельным coverage-якорем |
| B | SQL filtered object (`wiki_card_hybrid.sql:253–255`) | IR «прайс-лист» в alias | **informationregister_ценыноменклатуры вырезан** до судьи → verify не видит верную карточку |
| C | Пул «склад» содержит и местахранения, и реализациятмц | gap≈0 | нет меню «остатки vs продажи vs список складов» — идём в LLM-verify |
| D | `wiki_format_passport_lines` + `doesNotAnswer` (`z21:684–710`) | notEnoughFor из alias | у продаж нет маркера «не остатки/склад»; у номенклатуры нет «не прайс-лист» |
| E | `wiki_outcome_from_verify` (`z21:871–914`) | ровно один `yes` → лидер | **нет topic-coverage / trait-gate**; sole yes = ответ |
| F | `wiki_leader_post_verify` (`z21:1253–1283`) | меры и оси | при пустых measure/axis — noop |
| G | unmatched (`z20:2104–2117`) | no_data если terms не в индексе | при `terms=[]` молчит; не проверяет hit **в src** |
| H | SQL aggregate при пустом match (`z20` счёт / `rows_of`) | число по всей таблице | молчаливый полный count = ответ клиенту |

Для i2 «склад→число»: критичны **E** (verify yes на продажах) + **G/H** (пустой match → 79705).  
Для «прайс→2399»: критичны **B** (верный IR вырезан) + **E** (yes на номенклатуре) + **G/H**.  
Для «поставщиков/сотрудников»: alias прямо отождествляет роль со справочником → verify yes; это тот же класс «размытый kind → один справочник», без уточнения «все контрагенты ≠ поставщики».

## 8. Вывод: какой сигнал отсутствует

В решении лидера **нет кодового сигнала topic-coverage**:

- вопрос несёт топик в `search_form` / `kind` («склад», «прайс», роль «поставщик»);
- паспорт несёт `bestUsedFor` / `not_enough_for` / aliases;
- между ними стоит только LLM `fit=yes|no`, а `wiki_outcome_from_verify` принимает единственный `yes` как истину;
- post-verify и unmatched **не смотрят на топик**, когда нет меры/оси/terms.

Побочный усилитель на «прайс»: фильтр `action_class=object` **исключает informationregister**, хотя alias «прайс-лист» указывает на `informationregister_ценыноменклатуры` — верный кандидат не доходит до судьи.

Контракт: п.12 — догадка (sole yes без покрытия топика); п.21 — не резать уверенные ответы, где сущность названа и паспорт согласован (регистры «сколько записей в X» и т.п.). Правило должно опираться на **паспортный coverage-сигнал / структурный допуск носителя топика**, а не на чёрный список вопросов.
