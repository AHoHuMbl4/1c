  nef — только история цен.

Один (а) склад→реализацию не ловит.

(`entity_card_build.sql`): позитивный поиск по чужим топикам давал переток.

### 1.2 Положительная поверхность паспорта

Уже в verify-макете: `name`, wiki body, `platform`, `axes`, `measures`,
`distinct` (traits vs соседи пула), плюс в БД `label` / `aliases` /
`best_used_for`.

### 1.3 Точки решения лидера

```
wiki_verify_candidates
  → wiki_outcome_from_verify   # sole yes + все no → leader; tie → clarify
  → (cascade) wiki_leader_post_verify  # меры + action_axis
  → z20: нет picked → kind=no_data (без manual-fallback)
```

Вставка темы логична **после** V4 sole-yes и **рядом с** post-verify:
модель уже сказала «fit=yes», код обязан проверить, что паспорт тему
несёт. Homonym-guard и axis_reject остаются выше/рядом без изменения порога
V4.

### 1.4 Почему (в) один не сработает

1. `WIKI_VERIFY_SYS` уже описывает `doesNotAnswer`; на проде модель всё равно
   дала sole-yes реализации на «склад».
2. Хук `check-prompt-rules` **режет императивы** (`must` / `always` /
   «обязан») в `*_SYS` — усиление «модель обязана ставить fit=no» в промт
   **нельзя** вписать как правило.
3. Правило владельца: запреты держит код, не текст для модели.

Допустимо лишь уточнить **описание** поля (как в `rm4`), без долженствований.

## 3. Общее правило (без слов домена в коде)

### 3.1 Формулировка

> Sole-yes лидер утверждается только если каждый **дискриминативный** стем
> темы вопроса, для которого в **текущем verify-пуле** есть хотя бы один
> носитель на положительной поверхности паспорта, подтверждён положительной
> поверхностью **этого** лидера. Иначе исход пересобирается: среди
> паспортов пула с максимальным покрытием этих стемов — один → лидер,
> несколько → clarify-меню, ноль → `none`/`no_data`.
>
> Дополнительно: стем темы, который есть в `not_enough_for` лидера и **нет**
> на его положительной поверхности, — голос «doesNotAnswer» → лидер не
> утверждается (тот же пересчёт).

Положительная поверхность (один concat, как в hybrid/measure SQL):

`label | aliases | best_used_for | axes | measures`  
(+ опционально wiki body ≤ бюджета; traits/`distinct` — только подсказки
модели, в гейт не обязательны).

Отрицательная: только `not_enough_for`.

Стемы: `ts_lexize(STEM_DICT, …)` + `length(x) ≥ 3`, словарь
`search_dict_stem` — тот же приём, что `wiki_measure_carried` /
`kind_axis_hits` (п.20: работа в SQL, не свой стеммер).

### 3.2 Что считать дискриминативным стемом (без хардкода «склад/прайс»)

Из стемов вопроса:

1. Отбросить стемы с **глобальным** DF = 0 (нет ни у одной сущности) —
   служебные/мусор (`нас`, …).
2. Отбросить стемы с DF выше порога **высокочастотных** (замер на окне:
   ~39 стемов с DF>30 при 1015 типах; кандидаты порога **DF_MAX=25…30** —
   режет `скольк`/`всег`/`как`, не режет `склад`(10), `праис`(4),
   `прода`(5)).
3. Из оставшихся оставить только **pool-relevant**: хотя бы один паспорт
   текущего пула несёт стем на положительной поверхности.
4. Стемы, целиком покрытые уже разобранным `intent.period` /
   календарными readings (если стем входит в нормализованный текст
   выбранного окна) — вне темы сущности (иначе «за месяц» валит продажи).

Порог DF_MAX — константа окружения с дефолтом после замера на матчевой
выборке (не список доменных слов).

### 3.3 Решение (псевдологика)

Пусть `S` — pool-relevant дискриминативные стемы; `score(p) = |{s∈S: p несёт s}|`.

После `wiki_outcome_from_verify` при `outcome=leader`:

1. Если `S` пуст → **fail-open** (оставить лидера; нечего подтверждать).
2. Если `score(leader) < max_p score(p)` по пулу **или** `score(leader)==0`
   при непустом `S` → лидер **не** утверждается.
3. То же при nef-hit: ∃s∈S в nef лидера и не в positive.
4. Пересчёт: `C = {p in pool: score(p) == max score}`.
   - `|C|=1` и (опционально) verify-fit ∈ {yes,unsure} **или** max>0 →
     новый leader (diag: `wiki_topic_repick`);
   - `|C|≥2` → clarify по `C` (меню; п.21: данные есть — спросить);
   - `|C|=0` → `none` → `no_data`.

Не повышать до лидера паспорт с `fit=no`, если есть другой с yes/unsure и
тем же score — сначала класс verify; topic-gate **сужает**, не переворачивает
«no» в «yes» без нужды. Исключение для «прайс»: если sole-yes номенклатура
сброшена, а `ценыноменклатуры` в пуле с max score и был unsure/yes — берём;
если был `no`, а score уникален и >0 — допустим promote с diag
`wiki_topic_override_fit` (узкий люк; закрыть замком + L67). Альтернатива
безопаснее: только clarify по `C`, без silent override fit=no.

**Рекомендация первой красной:** demote + clarify/leader только из
`fit∈{yes,unsure}∩C`; если пересечение пусто, а `C` непусто — clarify по `C`
(меню честнее ложного числа и лучше голого no_data при живом прайсе).

### 3.4 Живой SELECT-зонд (окна), подтверждающий направление

| вопрос / кандидат | ключевые стемы (DF) | несёт лидер? |
|---|---|---|
| склад… / реализациятмц | `склад`(10), `позиц`(22) | нет / нет → demote |
| прайс… / номенклатура | `праис`(4), `позиц`(22) | нет / да → demote по `праис` |
| прайс… / ценыноменклатуры | `праис`(4) | **да** → может стать repick |
| продали за месяц / реализация | `прода`(5), `месяц`(13) | да / нет; `месяц` убрать периодом |
| контрагентов / контрагенты | `контрагент`(24) | да → keep |
| валют / валюты | `валют`(68>DF_MAX) | S пуст → fail-open keep |

Bag-overlap (`list_has_any` всего вопроса) **недостаточен**: у реализации
`overlap_pos=true` из‑за `всег`↔«Всего» в measures — только **per-stem**.

```python
def wiki_leader_topic_gate(leader, passports, question, intent, diag):
    stems = wiki_topic_stems(question, intent, passports)
    if not stems:
        return {"ok": True, "reason": "no_topic_stems"}
    scores = {p["src_table"]: wiki_passport_topic_score(p, stems)
              for p in passports}
    lead = scores.get(leader, 0)
    best = max(scores.values()) if scores else 0
    if wiki_nef_blocks(leader, stems, passports):
        diag["wiki_nef_hit"] = leader
        return {"ok": False, "candidates": _argmax(scores), "reason": "nef"}
    if lead == 0 or lead < best:
        diag["wiki_topic_reject"] = leader
        diag["wiki_topic_score"] = scores
        return {"ok": False, "candidates": _argmax(scores), "reason": "topic"}
    return {"ok": True}
```

В cascade при `not ok`: если `len(candidates)==1` → подменить leader +
post_verify снова; если `≥2` → clarify; если `0` → none.

Один round-trip SQL на гейт (VALUES стемов × JOIN alias/card), без цикла
`psql` по сущностям.
