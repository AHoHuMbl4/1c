
Почему ровно 5 и одинаковый `in=827`:

- лидер по полям не набрал `INTENT_LEAD` → цикл дошёл до потолка 5;
- тело одно и то же: `INTENT_SYS` (~3239 символов ≈ ~800 tok) + `today=…\n\nQuestion: …` → **prompt_tokens=827**;

Это **не** JSON-retry (retry — только вторая попытка внутри `_one_intent` при невалидном объекте, с другим `in`).  
Это **не** fork (fork — SQL `fork_detector_scan`, без TOKENS).

## 6. ТОП-3 причины 2,5 минут

1. **Реранкер в цикле (десятки HTTP ×1–2 с)** — главный кандидат на «минуты». Один вопрос тянет entity-rerank + measure-rerank + axis-rerank; в срезе ~30 строк `rerank отработал` на ~3 минуты окна 06:40–06:43.  
2. **`ASK_INTENT_SAMPLES=5` без раннего LEAD** — стабильные **~12,5 с** на каждом холодном вопросе (5× одинаковый `in=827`). Само по себе не даёт 2,5 мин, но обязательный налог на каждый ask.  
3. **Параллельные ask + живой хвост после TimeoutError** — ThreadingHTTPServer + `ASK_TIMEOUT=300`: вызов 2 жрёт процесс/GPU-rerank/LLM, пока вызов 1/3/4 делят тот же инстанс; journal перемешан, вызов 1 на 153 с без своего TRACE в срезе.

Не узкое место: буквальный SQL (~0,1 с) и смысл (~1,6 с) — цифры «12–14 с» у них были артефактом cumulative TRACE.
