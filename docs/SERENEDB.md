# SereneDB — движок аналитики/отчётов над 1С

Аналитический слой «второго мозга»: превращает вопрос на естественном языке в точный отчёт/график по
данным 1С. **Общий, без хардкода — переносится на любую 1С-базу и локаль.** 1С только читаем (через OData).

- Установка движка SereneDB: `ubuntu/serenedb/README.md`.
- **Развёртывание на новом сервере / подключение новой 1С-базы: `docs/RUNBOOK_DEPLOY.md` §10.**
- Бот-слой (Telegram, гейт анти-галлюцинаций): `docs/OPENCLAW_BOT.md`.
- План доведения до продакшена и что осталось: `docs/PRODUCTION_PLAN.md`.

## Что это
SereneDB (Apache-2.0, single-node, **PostgreSQL-протокол**, форк DuckDB + собственный поисковый движок
**IResearch**) — позиционируется как «поиск уровня Elasticsearch + аналитика уровня ClickHouse в одной
Postgres-совместимой БД». Полнотекст + вектор + колоночный OLAP. У нас держит **производную витрину**, пересобираемую из 1С в любой
момент. Источник истины — 1С; даже полная потеря витрины = ре-синк, данные не теряются. Поэтому строить на
ней аналитику — низкий риск (это НЕ система-оф-рекорд).

## Пайплайн (сквозной, общий)
```
1С ─OData(GET,read-only)─► ЗАГРУЗЧИК ─► витрина SereneDB ─► NL→SQL ─► ВАЛИДАТОР ─► выполнение(serene_ro) ─► отчёт+график ─► бот
     poc_load_entity.py      catalog_*/document_*   serene_report.py   allow-list(AST)      + caveat подмены      report_1c(MCP)
```
1. **Загрузчик** (`poc_load_entity.py`) — ЛЮБАЯ сущность 1С через OData → таблица `catalog_*`/`document_*`
   с сырыми колонками (union полей, авто-типы). Инварианты, общие для любой базы:
   стабильная пагинация `$orderby=Ref_Key` (иначе страницы OData перекрываются → дубли/потери); дедуп
   «одна строка на объект 1С» (`QUALIFY row_number() PARTITION BY ref_key`); исключение строк-папок
   (`IsFolder` — узлы иерархии справочника, не бизнес-строки).
2. **Схема для LLM** (`get_schema`) — интроспекция `duckdb_columns()` + **размеры таблиц** (`[строк: N]`,
   чтобы LLM отличал населённую таблицу от почти пустой при похожих именах) + **примеры значений**.
3. **Резолвер** (`resolve_hints`) — фаззи-термин вопроса → ТОЧНОЕ значение колонки-измерения. Два
   **язык-нейтральных** слоя (без стоп-слов/стемминга под язык): лексический (подстрока+`jaro_winkler`) и
   семантический (эмбеддинги Qwen `text-embedding-v4`@1536 → `resolver_index`, косинус, порог 0.70).
4. **gen_sql** (DeepSeek, `temperature=0`, промт язык-нейтральный) — вопрос+схема+подсказки → один SELECT.
5. **Валидатор** (`validate`) — см. «Безопасность».
6. **Выполнение** под ролью `serene_ro` → результат + `sql` (прозрачность трактовки) + `caveat` при
   подмене метрики. График — `render_chart` (PNG).
7. **Бот** — инструмент `report_1c` (MCP `1c-mcp-reports`, :6015); гейт `verify-plugin` сверяет числа.

## Выбор сущностей (имена — из реальности, не из головы)
- `serene-entities.txt` — активный список; **собственный у serene** (версионируется в git, деплоится с
  кодом). НЕ `/etc/1c-etl-selected.txt` (тот — у braine/ETL; разные системы, совпадать не обязаны).
- `serene_select.py` тянет служебный документ OData и пишет список из РЕАЛЬНЫХ имён; `--review` — picker:
  кандидаты закомментированы по убыванию строк, владелец отбирает бизнес-сущности (авто-дискавери на 1С
  неизбежно включает и платформенные справочники — метаданные/классификаторы; отделить их алгоритмически
  без хардкода нельзя, поэтому финальный отбор — за человеком).
- `serene_sync._preflight` каждый прогон сверяет весь список с живым OData: несуществующее имя → **громко**
  (прогон помечается failed) + подсказка ближайшего реального, а не молчаливый 404.

## Безопасность (защита в глубину)
- **Валидатор = ALLOW-LIST через AST** (`json_serialize_sql`): пропускается ТОЛЬКО одиночный SELECT/WITH,
  читающий ИСКЛЮЧИТЕЛЬНО таблицы витрины (+ свои CTE). DML/DDL/несколько-операторов → `error` парсера →
  reject. Табличные функции (`read_csv`/`glob`/…) и объекты вне схемы (`resolver_index`, `pg_settings`,
  системные каталоги) → reject *by construction*. Плюс лимит длины SQL (анти-DoS) и тонкий денайлист
  скалярных служебных функций (`current_setting`). Общий контроль **без списков имён** — на любую базу.
  (Денайлисты `FORBIDDEN`/`FS_ACCESS`/`INTERNAL_OBJECTS` остаются как fallback, если AST недоступен.)
- **Роли БД** (защита в глубину под валидатором):
  - `serene_ro` — read-only: SELECT работает, любая запись → `permission denied` (проверено `test_ro_role`).
  - `serene_resolver` — читает служебный `resolver_index` (positive control); у `serene_ro` доступ к нему
    ОТОЗВАН, поэтому LLM-SELECT не дотянется к внутреннему индексу даже в обход валидатора.
- **1С read-only** — только OData GET (гарантия на стороне 1С/шлюза, см. RUNBOOK §6).
- ⚠ **Движковый лимит доступа к ФС недостижим** на текущей SereneDB (один общий DuckDB-инстанс, FS-настройки
  `enable_external_access`/`allowed_directories` — GLOBAL-only, ломают загрузчик; подтверждено исходником
  SereneDB). Поэтому доступ к файлам держит ТОЛЬКО валидатор (allow-list). Это пробел модели SereneDB →
  вопрос фаундерам (ниже).

## Достоверность (инвариант)
Отчёт/график достоверен **по построению**: числа считает наш SQL из реальных данных, не LLM. LLM только
(а) понимает вопрос, (б) оживляет текст. Класс риска аналитики — не «выдумал число», а **«понял вопрос не
так»** и **«подмена метрики»**; страховка:
- **Прозрачность трактовки** — рядом с ответом виден `sql` (владельцу в логе), метрика/разрез/фильтры.
- **Подмена метрики** закрыта общим кодом: `measure_caveat` (типовой — числовая свёртка ТЕКСТ-реквизита,
  напр. `SUM(CAST(номер_счёта AS ...))`, по типам из интроспекции) + `metric_critic` (LLM-проход: «есть ли
  реальная колонка-величина под запрос?»). Не блок, а **предупреждение клиенту**.
- **Гейт бота** (`verify-plugin`) сверяет числовые токены исходящего с эталоном инструмента.

### ❗❗ Главное уточнение (2026-07-26): запрос идёт ОТ ИМЕНИ ИНДЕКСА

Рецепты выше показывали поиск «`FROM таблица WHERE col @@ …`». **Так не работает.** Проверено на
обычной таблице, на VIEW и на VIEW над `read_parquet` — везде движок отвечает:

```
ERROR: TSQUERY expression evaluated outside an `@@` match against an inverted-indexed column.
```

Сообщение вводит в заблуждение: оно указывает на колонку, а проблема — в источнике в `FROM`.
**Рабочая форма — обращаться к имени индекса:**

```sql
CREATE INDEX my_idx ON t USING inverted(doc my_dict, emb ivf (metric='cosine'))
                       INCLUDE (src, amount, dt);

SELECT count(*)              FROM my_idx WHERE doc @@ ts_phrase('СБЕРБАНК');   -- ✅
SELECT bm25(my_idx.tableoid) FROM my_idx WHERE doc @@ ts_phrase('СБЕРБАНК');   -- ✅ ранг
SELECT count(*)              FROM t      WHERE doc @@ ts_phrase('СБЕРБАНК');   -- ❌ ошибка выше
```

Отсюда же: «индекс на VIEW обязателен» — **неверно**. Индекс на обычной таблице работает; в прошлый
раз дело было в форме запроса, а не в типе объекта.

### ❗ Словарь: полный DDL и обязательный `case='lower'`

```sql
CREATE TEXT SEARCH DICTIONARY d (
  template='text', locale='ru_RU.UTF-8', case='lower',
  stemming=false, accent=false, frequency=true, position=true, norm=true);
```

`template` обязателен и принимает `'text'`; `locale` обязательна при `template='text'`.
Без `case='lower'` поиск **регистрозависим** — замерено на одном корпусе:
`СБЕРБАНК` 56 / `Сбербанк` **4** / `сбербанк` **0**; с `case='lower'` — 62 во всех вариантах.

Цена `stemming=false` (держим ради языконезависимости): `LIKE '%СБЕРБАНК%'` даёт 70 против 62 —
разница на словоформах (`СБЕРБАНКА`) и составных (`ПРОМСБЕРБАНК`).

## 🔌 «Данные в Postgres — поиск от SereneDB»: как это делается (проверено 2026-07-25)

Источник — не интуиция, а их собственный тест
`tests/sqllogic/sdb/pg/duckdb_postgres/inverted_index_pgscan.test_slow` + прогон на нашей сборке 26.07.3.

**Рабочий рецепт (три шага):**
```sql
ATTACH 'host=… dbname=… user=… password=…' AS pgp (TYPE postgres);
CREATE VIEW v AS SELECT id, name, city, amount FROM pgp.public.banks;   -- VIEW, не таблица!
CREATE INDEX v_idx ON v USING inverted(id, name ru_dict) INCLUDE (city, amount);
```
Ключевое: **индекс строится на VIEW**. Если строить его прямо на `pgp.public.banks`, SereneDB
транслирует DDL в Postgres и там появляется обычный `btree` — никакого поиска.

**Что работает сегодня** (проверено на наших данных, кириллица):

| Операция | Результат |
|---|---|
| `CREATE INDEX` на VIEW | ✅ 100 мс — IResearch забирает строки в момент создания |
| `count(*)` + `@@ ts_phrase('СБЕРБАНК')` | ✅ 2 — обслуживается индексом, источник не трогается |
| `bm25(v_idx.tableoid)` | ✅ ранг считается |
| Проекция `INCLUDE`-колонок (`SELECT city, amount`) | ✅ отдаются из колоночного хранилища индекса |
| **Агрегация** по `INCLUDE`-колонке (`SUM(amount)`) | ✅ 1212 — тоже из индекса |
| `SELECT` колонки, которой нет ни в индексе, ни в `INCLUDE` | ❌ documented error: *«materialising real columns from this view-backed inverted index is not yet supported»* |

**Почему так:** материализация произвольных колонок источника требует, чтобы источник был в
fast-path-реестре (`server/connector/view_fast_path.cpp`). Сейчас там `read_parquet`, `read_csv`,
`read_json`, `read_ndjson`, `read_json_objects` (+ алиасы). `postgres_scan` — **явный TODO** в коде;
в их тесте зафиксирован ожидаемый провал, который «перевернут», когда поддержка появится.

**Правило проектирования, которое из этого следует:**
> Всё, что нужно вернуть пользователю или агрегировать, должно быть **либо проиндексировано, либо в
> `INCLUDE`**. Тогда данные физически остаются в Postgres, а поиск и аналитику даёт SereneDB.

**Чем это ценно нам:** это прямой ответ на требование «данные всегда свежие» — витрину можно не
копировать ночью, а держать в Postgres и переиндексировать. Ограничение — набор колонок фиксируется
на этапе `CREATE INDEX` (при изменении состава нужен пересоздать индекс).

### Проверено на объёме и по свежести (50 000 строк, наша сборка)

| Проверка | Результат |
|---|---|
| Текстовый индекс над PG-view, 50 тыс. строк | **423 мс** на постройку |
| Поиск `@@ ts_phrase('КАЗАНЬ')` через индекс | 16 666 за **4 мс** |
| Тот же ответ живым чтением VIEW (`LIKE`) | 16 666 за **21.9 мс** — цифры совпали |
| **Векторный `ivf` над PG-view** | ✅ **работает**, 224 мс на 50 тыс.; поиск 4.25 мс |
| **Гибрид: текст + вектор в ОДНОМ индексе над PG-view** | ✅ 457 мс; фильтр по тексту 2.7 мс; текст + ранжирование вектором 4.4 мс |

⚠ **Тип денежных колонок:** `NUMERIC`/`DECIMAL` **не индексируется** (`unsupported type DECIMAL(14,2)`).
В PostgreSQL деньги обычно `numeric` → приводить в VIEW: `amount::DOUBLE AS amount`.

⚠ **Тип вектора:** колонка обязана быть **фиксированной** `FLOAT[N]`. PG-массив `real[]` приходит как
переменный `FLOAT[]` → ошибка `Column 'emb' must be ARRAY(FLOAT, N)`. Лечится приведением в самом VIEW:
`SELECT …, emb::FLOAT[8] AS emb FROM …`.

⚠ **`ivf` приближённый:** в замере кандидатный набор был 6 304 из 50 000 — это нормальная работа IVF
(обходятся не все кластеры). Для точного топ-K нужен замер recall на наших данных.

### 🔴 Свежесть: индекс — это СНИМОК

Главный факт, который решает судьбу схемы. Проверено прямым экспериментом:

| Шаг | Результат |
|---|---|
| Построили индекс (в источнике 2 подходящие строки) | индекс: **2** |
| В Postgres сделали INSERT + UPDATE + DELETE (стало 3) | — |
| Чтение **VIEW напрямую** | **3** ✅ всегда живое |
| Чтение **через индекс** | **2** ❌ устарело |
| `DROP INDEX` + `CREATE INDEX` | **3** ✅ |

**Индекс не отслеживает изменения источника.** Но пересборка дёшева (**0.4–0.5 с на 50 тыс. строк**),
поэтому свежесть регулируется частотой пересборки, а не ночным копированием. Практический вывод:

> Живые SQL-агрегации по VIEW — всегда свежие. Поиск (BM25/вектор) — свежий настолько, насколько часто
> пересобирается индекс. При 50 тыс. строк это меньше секунды, то есть можно хоть каждую минуту.

Ещё замечено: `ATTACH` **сохраняется между сессиями** (повторный ATTACH → «database already exists»),
но, по их recovery-тесту, не переживает рестарт сервера — после рестарта нужен повторный `ATTACH`.


## ⏱ Свежесть: как узнавать об изменениях в 1С (замерено 2026-07-25)

Вопрос владельца: «можно скрипт или вебхук от 1С?». Разложено по степени вторжения в 1С.

### Вариант A — опрос `DataVersion` (НИЧЕГО в 1С не меняем) ✅ рекомендуемый первым

У каждого объекта 1С есть служебное поле **`DataVersion`** (версия объекта, меняется при каждой записи —
платформа использует его для оптимистичных блокировок). Оно отдаётся штатным OData, и его можно тянуть
проекцией — без самих данных:

```
GET /Catalog_X?$select=Ref_Key,DataVersion&$format=json
```

**Замеры на стенде (сущность 2779 строк, прогретая сессия):**

| Запрос | Время | Объём |
|---|---|---|
| `$count` | 0.11 с | ~0 |
| `$select=Ref_Key,DataVersion` | **0.12–0.20 с** | 238 КБ (в 11 раз меньше полной) |
| Полная выгрузка | 0.44 с | 2687 КБ |
| **Опрос ВСЕХ 22 сущностей витрины через `$count`** | **3.7 с** | — |

Ключевое наблюдение: **проекция стоит почти столько же, сколько `$count`** — время съедает round-trip к
сессии 1С, а не объём. Значит нет смысла в «дешёвом сторожке» на `$count`: можно сразу тянуть точную
проекцию. Полный точный скан наших сущностей ≈ **5 с**, то есть опрос **раз в минуту** — незаметная нагрузка.

Что это даёт: диф по `(Ref_Key, DataVersion)` ловит **вставки, изменения И удаления** точно, после чего
дотягиваются только изменившиеся объекты → пишутся в Postgres → пересборка индекса (0.4 с на 50 тыс.).
**Инвариант «1С только читаем» сохраняется полностью** — это обычные GET.

✅ **ПРОВЕРЕНО ЖИВОЙ ЗАПИСЬЮ (2026-07-25, с разрешения владельца, под `admin` через COM).**
Контролируемый обратимый тест на одном элементе справочника (перед этим — бэкап базы 767 МБ):

| Шаг | Имя элемента | `DataVersion` |
|---|---|---|
| исходное состояние | Прочие затраты | `AAAAAQAAAAs=` |
| **запись БЕЗ изменений** | Прочие затраты | `AAAABQAAAAA=` ← **изменилась** |
| реальное изменение имени | Прочие затраты ZZТЕСТ | `AAAABgAAAAA=` |
| возврат имени как было | Прочие затраты | `AAAABwAAAAA=` |

**Вывод: `DataVersion` меняется при КАЖДОЙ записи объекта — механизм обнаружения изменений работает.**
Значение из COM (`ВерсияДанных`) и из OData (`DataVersion`) совпадает — это одно и то же поле.

⚠ **Важный нюанс:** версия меняется **от самого факта записи**, даже если содержимое не изменилось.
Значит если в 1С работает регламентное задание, перезаписывающее объекты, мы получим «ложные»
изменения — лишние дотягивания, но НЕ неверные данные (мы всё равно грузим строку целиком).
При необходимости лечится сравнением содержимого после дотягивания.

ℹ️ Версия только растёт и **не возвращается** при откате данных: имя восстановлено точно, но версия
у этого элемента теперь `AAAABwAAAAA=` вместо `AAAAAQAAAAs=`. Для конвейера безвредно — он один раз
перечитает этот элемент.

⚠ **Масштабирование:** проекция линейна по числу строк (~88 байт на объект). Для сущности в 1 млн строк
это ~90 МБ на скан — раз в минуту уже тяжело. Тогда: крупные документы опрашивать реже либо окном по дате.

### Вариант B — вебхук из 1С (push) — требует решения владельца

Настоящий вебхук = **HTTP-сервис + подписка на события** внутри 1С. Это **изменение конфигурации и
запись в базу**, то есть прямой конфликт с нашим инвариантом. Цивилизованный способ — **расширение
конфигурации** (не снимает типовую с поддержки), но это всё равно установка кода в базу клиента.
Плюс: задержка почти нулевая. Минус: сопровождение при обновлениях 1С, согласование с их администратором.

### Вариант C — план обмена (штатная регистрация изменений)
Родной механизм 1С: платформа сама регистрирует изменённые объекты. Точно и дёшево читать, но требует
конфигурации/расширения и **пишет регистрационные записи в базу** — тот же конфликт с инвариантом.

### Вывод
Начинать с **A**: он ничего не меняет в 1С, даёт свежесть порядка минуты и уже замерен. К **B/C** идти
только если бизнес потребует секундной реакции — и это будет отдельное согласованное решение владельца,
с явной записью, что инвариант «только читаем» сужается.


### ✅ Решение владельца: опрос раз в 10 минут

Принято 2026-07-25. Следствия:

- **Вебхук/расширение/план обмена НЕ нужны** — вариант A закрывает требование. Инвариант
  «1С только читаем» остаётся нетронутым, в базу клиента ничего не ставится.
- Нагрузка опроса: 3.7 с раз в 10 мин = **0.6% времени**. Запас по масштабу большой: даже сущность
  на 1 млн строк (~90 МБ проекции) при таком такте — примерно 150 КБ/с в среднем.
- Сквозная задержка «ввели в 1С → видно боту»: **до ~10 минут** (обнаружение) + секунды на дотягивание
  изменённых объектов + 0.4 с на пересборку индекса.

#### ⚠ Но одним таймером не обойтись: замер текущего синка

`1c-serene-sync` сейчас делает **полную** перезагрузку всех сущностей + **полную** пересборку резолвера:

| Метрика последнего прогона | Значение |
|---|---|
| Длительность | **3 мин 31 с** |
| CPU | всего 20 с → остальное **ожидание сети** (OData + DashScope) |
| Резолвер | пересобирается целиком: 624 значения эмбеддятся заново |

Поставить это на 10 минут нельзя: система будет занята **35% времени**, постоянно дёргать OData и
переплачивать за эмбеддинги, которые не менялись.

#### Что нужно изменить (дельта-синк)

| Шаг | Сейчас | Нужно |
|---|---|---|
| 1. Обнаружение | нет | опрос `(Ref_Key, DataVersion)` по сущностям — 3.7 с |
| 2. Нет изменений | полная перезагрузка | **выход сразу** (типовой случай ≈ 4 с) |
| 3. Есть изменения | тянутся все строки | дотянуть **только изменившиеся** `Ref_Key` |
| 4. Витрина | таблица пересоздаётся | upsert изменённых строк |
| 5. Резолвер | все 624 значения заново | эмбеддить **только новые** значения |

Итог: типовой прогон превращается из 211 секунд в ~4 секунды, а расход на эмбеддинги — из «каждые
10 минут заново» в «только за новые значения».

#### Побочная находка: резолвер эмбеддит мусор
В журнале синка видно, что в семантический индекс попадают служебные поля:
`catalog_статьизатрат.DataVersion` (штампы версий вида `AAAAAQAAAAA=`) и
`catalog_банки.Страна_navigationLinkUrl` (URL-ссылки). Это трата эмбеддингов и шум в поиске.
Отсекать **без хардкода** — по данным, а не по именам колонок: значение должно содержать буквы
какого-либо алфавита и не быть технической строкой (GUID/base64/URL по структуре). Отдельная правка.

## Backup/restore
- Первичное восстановление — **ре-синк из 1С** (`serene_sync`), т.к. витрина производная.
- Быстрый restore без ре-пула/ре-эмбеддинга — **оффлайн-снапшот** `/var/lib/serenedb`
  (`serenedb_backup.sh`, ротация). Проверено round-trip. `pg_dump` не годится (SereneDB не полноценный PG).

## Тесты (гейты; гоняются перед деплоем/после синка)
`test_validate` (allow-list), `test_integrity` (grain / витрина⊆OData / resolver / нет фантомных строк),
`test_caveat` (подмена метрики), `test_ro_role` (read-only + positive control), `test_e2e` (реальный
`run_report`: ground-truth **из БД** + danger-wiring). Все — схемо-агностичны (таблицы/числа из данных, не
вшиты). Запуск — в окружении reports (env как у `probe.sh`). Плюс агент-харнесс (5 классов провокаций).

## Открытые вопросы фаундерам SereneDB (контакт владельца)
