# Как это работает и почему именно так

Документ объясняет устройство: что делает каждый слой, какое решение за ним стоит и
чем оно подтверждено. Стадия по каждому пункту контракта —
[`TARGET_STATUS.md`](TARGET_STATUS.md); `STATE_2026-07-26.md` — исторический снимок на
26.07, за состоянием туда не ходить.
Целевая схема размещения данных — [`TARGET_ARCHITECTURE.md`](TARGET_ARCHITECTURE.md).

🔴 **Числа в этом файле принадлежат разным базам, и база названа не везде.** На стенде их
две: первая (Бухгалтерия, база движка `postgres`) и **боевая** вторая (УТ 11.4.9,
`ut_test`) — по ней идут все ответы бота. [замер 01.08] корпус: `postgres` 103 808 строк,
`ut_test` 623 565; резолвер: 115 151 и 188 068. Встретив здесь число без имени базы,
сверяйтесь с `MAP.md §5`, а не с той базой, что под рукой.

## Главный принцип

> **Ищет база. Считает база. Модель понимает язык. Код проверяет.**

Каждая из четырёх ролей выбрана потому, что остальные её выполняют хуже:

| Задача | Кто делает | Почему не другой |
|---|---|---|
| найти строки | инвертированный индекс SereneDB | модель, получив схему, промахивалась таблицей; поиск ищет по содержимому |
| посчитать итог | SQL по всему множеству | модель, считая по показанным строкам, выдаёт часть за целое |
| понять «продажи» = «реализация» | модель | это языковая задача; эвристика в коде превращается в подгонку под базу |
| проверить, что цифры настоящие | код (гейт) | промт не является гарантией — правило владельца |

## Путь вопроса

```
   вопрос
     │
 1.  ├─► НАМЕРЕНИЕ (модель)         что за слова искать, о чём вопрос,
     │                              какие условия (период, порог суммы)
     │                              видит ТОЛЬКО текст вопроса
     │
 2.  ├─► РАЗВЕДКА (один SQL)        каждое слово проверяется четырьмя способами
     │                              сразу: точная фраза / фраза с окном /
     │                              опечатки / подстрока — и выбирается самый
     │                              строгий, который что-то нашёл
     │
 3.  ├─► ГДЕ НАШЛОСЬ (SQL)          группировка по источникам ПО ВСЕМУ множеству
     │                              совпадений, а не по первым сорока строкам
     │
 4.  ├─► КАКАЯ СУЩНОСТЬ (модель)    список названий + сколько где совпало +
     │                              чем источник отличается от остальных +
     │                              структурные факты из метаданных.
     │                              Данных и схемы модель не видит.
     │                              Неоднозначно → СПРАШИВАЕТ человека
     │
 5.  ├─► ИТОГ (SQL)                 count / sum / min / max / avg по всему
     │                              множеству, без LIMIT
     │
 6.  ├─► ФОРМУЛИРОВКА (модель)      вопрос + до 25 строк + посчитанные величины;
     │                              цифры обязана КОПИРОВАТЬ, не вычислять
     │
 7.  └─► ГЕЙТ (код)                 каждое число из ответа ищется в данных;
                                    чужое → ответ заменяется структурой величин
```

### 1. Намерение

Модель получает только текст вопроса — ни схемы, ни данных. Возвращает: слова для
поиска с вариантами написания, «о чём вопрос» (для сопоставления с названиями
сущностей), что хотят (сумму, количество, список) и условия — период, порог суммы.

### 2. Разведка одним запросом

Каждое слово проверяется четырьмя способами, все в **одном** SQL через `UNION ALL`:

| Способ | Зачем |
|---|---|
| `ts_phrase` | точное совпадение через анализатор (регистр не важен) |
| `ts_phrase` с окном | имя в данных разорвано: «Общество с ограниченной ответственностью "Ромашка"». Окно = число слов в самой фразе, не константа |
| `ts_levenshtein` | опечатки и словоформы. Расстояние выводится из длины слова: при фиксированном 2 трёхбуквенное `tax` совпадало с 2978 строками из 97 тысяч |
| `ts_like` | склеенные имена: «поступления» внутри «ПоступлениеТоваровУслуг» |

Берётся **самый строгий способ, который дал ненулевой результат**. Условие собирается
штатным булевым запросом движка `ts_compound(must, must_not, should, k)` — один запрос
вместо цикла подбора (замерено: 6,9 мс против 42,5 мс).

### 3. Где нашлось

`GROUP BY src_table` по всему множеству совпадений. Раньше источники считались по
сорока строкам, отобранным по рангу, и BM25 штрафом за длину вытеснял документы
целиком: 74 строки из четырёх таблиц документов не попадали в кандидаты вовсе.

### 4. Выбор сущности

Модели даётся список названий — **и ничего больше из данных**. Рядом с каждым:

- **сколько совпадений** — снимает неоднозначность «Банки» на 1 запись против
  «Классификатор Банков» на 680;
- **чем источник отличается** (significant terms по полю ссылок): у реализации это
  «оптовый склад, расчёты по авансам», у поступления на счёт — «счёт банка, средства
  полученные от покупателей». Термы, общие для всех кандидатов, отсеиваются — они
  ничего не различают;
- **структурный факт из метаданных**: «это строки внутри такой-то записи». У табличной
  части объявленный ключ составной — ссылка на владельца плюс номер строки; сам
  владелец найден по данным. Ни одного имени конкретной базы.

**Порядок списка — по смыслу вопроса**, потому что модель тяготеет к началу, а число
совпадений врёт: значение чаще встречается в чужой сущности.

#### 🔴 Модель формулирует ПАРАМЕТРЫ подсчёта, а не только номер (с 30.07)

Замысел владельца 30.07: «сначала сформулировать, какие именно параметры вытягивать для
подсчёта, а потом уже из них включается калькулятор».

В том же вызове модель отдаёт JSON: **тип**, **имя величины дословно из списка данных** и
**что считать** (`count|sum|max|min|avg`). Прежде она отдавала только номер типа, а величину
потом угадывал реранкер по похожести ИМЁН — **уже не видя вопроса**. Отсюда [замер 30.07]
«на какую сумму мы закупили» при верно выбранной сущности давало 70 902 572,21 (`Сумма` строк,
без НДС) вместо 73 181 157,68 (`СуммаДокумента`).

**Имя величины проверяется по данным**, а не принимается на слово: его обязана содержать
`measures_of(сущность)`. Выдуманное имя до калькулятора не доходит физически — запрет держится
кодом, а не просьбой в промте.

**Если модель величину назвать не смогла, а вопрос про величину — догадка НЕ принимается**,
вопрос уходит человеку (п. 12: догадка — ошибка). [замер] «Сколько НДС мы заплатили
поставщикам?» прежде молча брал `КОплате` и отвечал 13 777 225,30 вместо 11 036 086,09.

Побочная находка того же замера: **невозможность сформулировать параметры сама является
признаком неверной сущности** — «НДС» нельзя назвать величиной регистра расчётов, потому что
её там нет.

#### 🔴 Объявленный ключ — не величина (с 30.07)

[замер 30.07] `SurrogateKey` попал в карту величин у **656 сущностей**, `LineNumber` — у **359**.
Последствие видно в ответе: на «сколько штук мы закупили» система отвечала «закуплено 1 позиция,
единица измерения — штука. **Считано по величине „SurrogateKey"**». Складывать ключ бессмысленно:
это тождество строки, а не измерение.

🔴 **Признак «величина» отделён от признака «число в тексте» — и это оплачено ошибкой.**
Первая попытка исключила ключи из общего флага `is_num`, то есть сразу и из величин, и из ТЕКСТА
строки. Слияние отказало: **«дублей ключа 1368»**. У обёрток регистров объявленный ключ
`{Recorder, Recorder_Type}` строки не различает — их различал номер строки в тексте; без него
тексты совпали. Защита остановила перенос, корпус остался цел. Теперь в тексте число остаётся
(оно про тождество строки), в карту величин не идёт (там только складываемое). Разбор —
`HOW_NOT_TO §3.31`.

Отсекается **двумя правилами**, оба без списка слов о конкретной базе:

1. **колонка входит в объявленный ключ** (`$metadata` → `tmp3_key.key_cols`) — тот же источник,
   что `Ref_Key`. Убрало `SurrogateKey` полностью: 656 → **0**;
2. **`LineNumber`/`SurrogateKey` как имена ПЛАТФОРМЫ.** Первое правило не ловит их у обёрток
   регистров, где ключ объявлен как `{Recorder, Recorder_Type}` — [замер] так уцелели **95 из
   359**. Эти имена порождает сама платформа 1С, одинаково на любой конфигурации и языке; это тот
   же класс факта, что `Ref_Key` и `DataVersion` (последний отсекался и раньше).

Проверка после правки: корпус **623 565** без изменений, партнёров **164**, сумма приобретений
**73 181 158** — ничего не сдвинулось.

#### 🔴 Страница вики описывает сущность В ОТЛИЧИЕ ОТ СОСЕДЕЙ (с 30.07)

Первая версия описывала каждую сущность **в одиночку**, и этого не хватило: [замер 30.07] у
«Подтверждения оплаты НДС в бюджет» в «не годится» стояло «налоговая декларация, конкретный
платёж» — верно, но соседей не отделяет. А сущностей со словом «НДС» в базе **восемнадцать**, и
бот отвечал не из той: **8 654 378,11** вместо 11 036 086,09.

Поэтому пачка для агента набирается **по близости смысла** к первой неописанной сущности — тем же
вектором названия, что лежит в `search_tables.emb`. Ни списка тем, ни слов о конкретной базе:
соседей определяет сама база. Агента просят назвать в `notEnoughFor` **соседей поимённо** и
сказать, какой из них отвечает вместо этой.

Что получилось [замер 30.07] у «НДС записи книги покупок»:

> не годится: НДС к уплате с продаж — **НДСЗаписи Книги Продаж**; предъявленный покупателям —
> **НДСПредъявленный**; фактическая уплата в бюджет — **Подтверждение Оплаты НДСВБюджет**;
> **НДС в конкретном документе приобретения — Приобретение Товаров Услуг_Товары**

Последняя строка уводит от книги покупок к строкам приобретений, то есть к эталонному источнику —
ровно туда, где бот ошибался.

#### Вики OpenClaw — основа для выбора сущности (с 30.07)

Замысел владельца 30.07: «нельзя надеяться на ллм, у него мало контекста чтобы правильно
сделать; Wiki тут поможет». Довод подтверждён замером: переход на модель посильнее
(`v4 pro` вместо `flash`) выбор сущности **не** починил — плохих исходов 11 против 11. Из

отвечает на «на какую сумму мы продали»: это знание о конкретной базе.

**Что где лежит.**

| Слой | Где | Чем наполняется |
|---|---|---|
| человеческие слова к сущности | таблица `search_entity_alias` в базе | `wiki_alias.sh` — **штатным агентом OpenClaw** (`openclaw agent --json`), один раз на сущность, идемпотентно |
| страницы вики | хранилище `memory-wiki` | `wiki_build.sql` собирает текст **в базе**, `wiki_publish.sh` пишет файлы и зовёт `openclaw wiki compile` |

## Промты: только задача, запреты держит код

Указание владельца 31.07: «запреты и правила у нас на уровне кода, а не в промтах».
Промты переписаны начисто, 8 154 → 3 767 символов у сервиса и 9 416 → 3 867 у персоны.

Что чем держится, чтобы не возвращать это в промт:

| Требование | Держится |
|---|---|
| в ответе нет числа, которого нет в данных | гейт: величины подставляет код `_fill_figures`, остальные числа сверяются |

| бот не отвечает без обращения к данным | **частично** (прежняя редакция говорила «типизированные хуки плагина, у них есть block/cancel» — это сильнее, чем есть): хук `before_agent_finalize` возвращает не `block`, а `{action:'revise', retry:{maxAttempts:1}}` — модель гоняется ещё **один** раз, и если второй проход снова отвечает без обращения к данным, ответ уходит. ## Подтверждение выбора сущности

Ответ не выпускается, пока собственное знание базы не подтвердит, **та ли это сущность**.
Правило нужно потому, что гейт исходящего этот класс ошибок не ловит **по построению**:
число посчитано базой честно, просто не по тому источнику — для гейта оно обосновано.

Подтверждением считается любое из трёх, и все три — из данных:

1. человек выбрал сущность сам (`focus`) — спорить не с чем;
2. сущность — вершина по вектору самого вопроса (считает база);
3. слова вопроса совпали с её алиасами (сравнение **по основам**, штатным словарём
   `search_dict_stem`, а не подстрокой).

Не подтверждена — система спрашивает, а не угадывает (п. 12, п. 21). Соперников для вопроса
подбирает **движок**: `SELECT src_table, tfidf(alias_idx.tableoid) FROM alias_idx WHERE
aliases @@ <вопрос> ORDER BY 2 DESC`. Шапка документа и его табличная часть считаются одной
семьёй — это одно прочтение, а не два, поэтому в списке остаётся один представитель.

🔴 **Жёсткая форма правила** (`ASK_ALIAS_VETO=1`): подтверждает только **лидер**
ранжирования. Это решение владельца 30.07 — «когда вопросу отвечает несколько разных
объектов, всегда переспрашивать». Числового порога в ней нет намеренно: согласие определяет
база. Выключена, пока замер не покажет, что алиасы подсказывают верно — на первой их версии
жёсткая форма меняла верные ответы на бессмысленные вопросы (`HOW_NOT_TO §1.25`).

🔴 **Три раза это правило было мертво и это было не видно** (`HOW_NOT_TO §1.24`): не выдано
право `SELECT` роли `serene_ro`; проверка стояла после арбитра, который возвращает ответ
раньше; внутри лежал `KeyError`. Отсюда требование к замеру: правило, которое ничего не
запретило ни разу, — подозрительно, и нужен отдельный замер, что оно **срабатывает**.

**Почему шаг в такте, а не руками.** Замечание владельца: «дословно как в базе — это ты
делаешь, а должна система при любой базе вообще». Первую вики я собрал своим скриптом из `/tmp`
для одной базы — на чужой базе её бы не появилось, а по п. 14 ручной шаг при установке = дефект.
Теперь шаги живут в репозитории и вызываются `build.sh` после переписи полноты.

**Чего на страницах НЕТ:** счётов, сумм, диапазонов дат. Страница попадает в промт при поиске, а
«249 документов» — готовый ответ; устарев, он стал бы неверным ответом в обход базы (п. 19).
Сколько сейчас подошло — считает база на каждом вопросе.

**Универсальность.** Ни в SQL, ни в скриптах нет имён сущностей, величин или слов конкретной
базы. Тип сущности — префикс имени от платформы 1С (`Catalog_`, `Document_`), берётся как есть и
**не переводится**: перевод был бы привязкой к языку. Каркас страницы по-английски, данные — на
языке базы. Модель просят отвечать «на том же языке, что название», поэтому на английской базе
выйдут английские слова без правки кода.

**Две ловушки, найденные замером 30.07:**

1. **алиасы обязаны быть в ТЕЛЕ страницы, не только во frontmatter** — поиск ищет по тексту: с
   алиасами только в заголовке запрос «сколько мы заработали» не находил ничего, хотя ровно эти

**Где именно работает вики — поправка владельца 30.07.** «wiki нужно только для
ПЕРЕФРАЗИРОВАНИЯ, а не для точного поиска. вопрос — перефразирование по wiki, поиск через нашу

Порядок вписан в инструкции бота (эталон — `ubuntu/openclaw/instance/AGENTS.md`; исполняется копия из рабочей папки, см. оговорку о персоне) и держится мостом

#### 🔴 Где какое правило стоит: движок не выпускает, сервис выбирает

Проверено замером 30.07, после указания владельца ставить правила штатными механизмами.

| Задача | Средство движка | Замер |
|---|---|---|
| заставить модель сходить за данными | `before_agent_finalize` → `{action:"revise", retry}` | ход **честно отменяется** («requested one more pass, attempt=1/3» в журнале шлюза), но модель указание **проигнорировала** и повторила прежний ответ |
| то же, жёстко | `agents.defaults.models.<ref>.params.extra_body.tool_choice = "required"` | 🔴 **петля**: пять вызовов подряд, шесть минут вместо тридцати секунд, прогон кончился ошибкой. Модель обязана звать инструмент на КАЖДОМ шаге и не может остановиться, чтобы ответить. Откачено |
| не выпустить неподтверждённое наружу | `after_tool_call` + `message_sending`/`reply_payload_sending` | **работает гарантированно**, от желания модели не зависит |
| повторить ход ПОСЛЕ вызова инструмента | — | **штатного средства нет**: движок отказывает, потому что MCP-инструмент по построению не replay-safe |

🔴 **У механизма `revise` два свойства, которых наше описание не знало, и оба объясняют
провал лучше, чем «модель проигнорировала».**

1. **Движок сам приписывает к нашей причине текст, обратный ей по смыслу.** Перед отправкой
   модели он добавляет префикс: *«Before accepting the previous final answer, apply this
   revision request… **Do not repeat completed work or rerun tools unless the request
   explicitly requires it**»* — то есть буквально просит НЕ звать инструменты повторно,
   тогда как наша причина требует ровно обратного («сходи за данными»).
2. **После любого не-replay-safe инструмента `revise` отклоняется молча.** Если в ходе уже
   вызывался инструмент вне жёсткого списка replay-safe (`read`, `search`, `grep`,
   `web_fetch`, `memory_get`, …), движок финализирует ответ и пишет в журнал
   «requested revision after potential side effects; finalizing». [замер] в живом журнале
   шлюза это случилось **23 раза** (против 98 «requested one more pass»).

Попасть в список replay-safe MCP-инструмент не может в принципе: `declaredReplaySafe` у
движка умеет только **запретить** (`=== false`), а разрешить — нет. Поэтому вывод «штатного
средства повторить ход после вызова инструмента нет» остаётся верным, но держится на этом,
а не на своеволии модели.

**Правило разделения, которое из этого следует:**

- **что можно запретить на выходе — запрещает движок** (плагин `braine-verify`): число без опоры
  не доходит до человека; уточнение сервиса доходит дословно;
- **что нужно решить до ответа — решает сервис** (`serene_ask`): какую сущность и величину брать,
  и отвечать ли вообще. Движок умеет не выпустить, но не умеет выбрать.

Решение владельца 30.07 по этому конкретному случаю: «правило в сервисе». Принято ПОСЛЕ того, как
оба штатных средства были проверены и оказались недостаточны, — а не вместо проверки.

Включение хуков обязательно: `plugins.entries.braine-verify.hooks.allowConversationAccess: true`,
иначе движок **молча** не зарегистрирует их у неbundled-плагина.

#### Три слоя знания о сущности — и все три из данных базы

Знание о сущности строилось за 30.07 в три захода, и каждый закрывал свой класс ошибок. Все три
нужны одновременно; ни один не заменяет другой.

🔴 **Слой строит такт КАЖДОЙ базы отдельно, и на базе, где такт после 30.07 не проходил, его
просто нет.** [замер 01.08] `select count(*) from search_entity_alias`: `ut_test` — 697,
`postgres` — **0**; таблицы `wiki_pages` в `postgres` нет вовсе, а все 698 страниц в
хранилище бота — 697 из `ut_test` плюс сводный `index.md`, который создаёт сам движок. Отсюда два практических следствия: на первой базе бот
выбирает сущность БЕЗ этого слоя, и регрессия первой базы («8/8») про него ничего не
говорит — переносить выводы о качестве выбора сущности с одной базы на другую нельзя.

| Слой | Что отвечает | Чем был вызван |
|---|---|---|
| **словарь** (`aliases`) | какими словами человек называет эту запись | модель видела только техническое имя: «Реализация Товаров Услуг» против вопроса «сколько продали» |
| **разграничение** (`notEnoughFor` с именами соседей) | чем эта запись отличается от похожих | [замер] сущностей со словом «НДС» в базе **18**; описанные поодиночке страницы друг о друге молчали, и вопрос уходил не в ту |
| **связь со значением** | по какой ВЕЛИЧИНЕ её будут искать | [замер] у строк приобретений есть `СуммаНДС`, но в алиасах стояло «что купили» — вопрос «сколько НДС заплатили поставщикам» уходил в регистр «уплаченный НДС» и давал 2 719 573,23 вместо 11 036 086,09 |

Третий слой — самый неочевидный: **название говорит, ЧЕМ запись является, а спрашивают про
ЗНАЧЕНИЕ**. Не «покажи строки приходной накладной», а «сколько НДС мы заплатили». Пока страница
описывала только «что купили», вопрос уходил туда, где нужное слово стояло в НАЗВАНИИ, хотя самой
величины там не было.

**Универсальность.** В коде нет ни «НДС», ни «количества»: агенту показываются величины сущности
**из её же данных**, и он связывает их со словами на языке базы. [замер 30.07] после правки у
строк приобретений появился алиас «сколько НДС заплатили поставщикам», у строк реализаций —
«сколько НДС в отгрузке». На английской конфигурации `VATAmount` даст «VAT» тем же механизмом.

**Как чинить дальше — по факту ошибки, а не подряд.** `WIKI_ALIAS_WORD` разводит конкретное
спорное слово: прогнали приёмку, увидели, где спуталось, развели ровно этих. Полное разведение
всех столкновений идёт ~3 часа и не окупается, пока не известно, где болит.

#### Арбитр: выбор между ГОТОВЫМИ ответами (с 30.07)

Когда сомнение **найдено** (модель назвала больше одной сущности, либо вершина по вектору
вопроса расходится с её выбором и не из той же семьи), по каждому кандидату собирается
**полный ответ** тем же кодом, и модель-арбитр выбирает **номер** готового ответа. Числа в них
уже посчитаны базой — арбитр не считает и не ищет (п. 19).

От арбитра принимается **только номер**; всё прочее считается «не выбрал», и тогда спрашиваем
человека. Пересказать ответ он не может: его текст в выдачу не попадает никогда.

🔴 **Арбитр не запускается там, где сомнения нет.** [замер 30.07] когда соперник придумывался
всегда, сломались вопросы, отвечавшие верно: механизм для спорных случаев, применённый ко
всем, портит бесспорные (`HOW_NOT_TO §1.16`).

Контекст предыдущего разговора приходит полем `context` (его ведёт OpenClaw) и используется
**только арбитром** — в отбор данных не попадает.

**Если вопрос неоднозначен, система спрашивает.** Модель может назвать несколько типов,
когда вопрос честно допускает разные прочтения и ответы различались бы. Тогда
возвращается `kind=clarify` с вариантами и уточняющим вопросом, сформулированным
моделью на языке спрашивающего. Порога тут нет и быть не может: «одинаково ли
подходят» — вопрос языковой, а не числовой.

**Уточнение бывает и на втором рубеже — когда сущность одна, а вопрос о соседнем.**
Строки могут отвечать не ровно на заданный вопрос, а на близкий: другое направление той
же связи, другой период, другая роль того же лица. Прежде такое падало в отказ. Сейчас
модель кладёт в ответ то, что данные **показывают**, и задаёт один короткий вопрос,
который позволил бы ответить точно; возвращается тот же `kind=clarify`, но с полем
`question` и с посчитанными итогами.

[замер 28.07] «Что покупало ООО Ромашка?» — её собственных закупок в базе нет, а наши
реализации в её адрес есть: 3 документа на 1 236 800 руб. Система отвечала «данных нет» —
формально верно, по делу бесполезно. Стало: числа названы, вопрос задан. Оба приёмочных
набора после этого дают 8 из 8.

Три правила этого рубежа держатся кодом, а не просьбой в промте:

- **уточнение возвращается только после гейта** — числа в нём проверены базой наравне с
  обычным ответом, «спросить» не является лазейкой мимо проверки;
- **вопрос не задаётся при пустых данных**: переспрашивание допустимо вместо молчания,
  но не вместо работы;
- **величины отдаются с именами из данных**: когда вопрос не назвал величину, `sum` не
  посчитан, и выдать `sum: 0` значило бы соврать нулём.

Порядок трёх рубежей и есть п. 21 `TARGET.md`: **ответ → уточняющий вопрос → отказ**.
Отказ — последнее средство, а не первое.

**Как это будет показано человеку — решение владельца 28.07: кнопками, и рядом всегда
«свой вариант» свободным текстом.** Это меняет контракт ответа, а не только его вид: к
вопросу нужны готовые короткие варианты, а сейчас второй рубеж возвращает `question` и
пустой `options`. Варианты обязаны браться **из данных** — на первом рубеже так уже есть
(названия и отличительные реквизиты из `search_tables`), на втором ещё нет. Свободный
ввод не отменяется ни при каком числе кнопок: список — подсказка, а не ограничение,
иначе кнопки станут новой отсечкой правильности. Ни одного варианта в коде: кнопка,
которую пришлось бы править под конкретную конфигурацию, — такой же хардкод, как имя
таблицы. Работа записана в `docs/PRODUCTION_PLAN.md`.

### 3-квинт. Уточнение → выбор → верный ответ

Порядок п. 21 (ответ → уточнение → отказ) замкнут в рабочий цикл: когда вопрос
неоднозначен, система отдаёт `kind=clarify` со списком сущностей (`options`); бот
показывает их кнопками; выбор человека возвращается в `/ask` полем `focus`, и по нему
считается ответ — сущность больше не гадается.

Пример — «обороты по счёту 62». «62» это и номер формы статистики, и счёт. Судить по
числу нельзя, поэтому система предлагает выбор (форма / регистр бухучёта). Человек
выбирает регистр — и получает верное число: 147 движений, 23 742 200 (сходится с 1С).
Универсально для любого счёта (41 → 20 500 500), без хардкода: признак кода структурный
(цифра в терме), базовая величина «Сумма» узнаётся как префикс частных («СуммаВРDr»).

Решение владельца 28.07: «если после уточнения даётся верный ответ, это ок» — уточнение
не тупик, а шаг к ответу.

### 3-тер. Резолвер: слово человека → значение в базе

Когда слово вопроса записано в данных иначе — сокращение, искажение, транслитерация — и
не находится ни точно, ни по опечатке, ни подстрокой, включается **резолвер**: он
сопоставляет слово с конкретными значениями базы (`resolver_index`, 115 тыс. значений с
векторами). Близость считает база (`emb <=> vec`), верное из близких выбирает реранкер —
порога близости нет, как и везде.

Резолвер читается ОТДЕЛЬНОЙ ролью `serene_resolver`: та роль, которой исполняется SQL
модели (`serene_ro`), к нему доступа не имеет — SQL от модели не должен дотягиваться до
служебных эмбеддингов.

Две гарды держат его честным:
- **от мусора:** вектор всегда отдаёт ближайшее, поэтому у значения, которого в базе нет,
  находится случайное. Разрешённое значение обязано делить с словом буквенный триграмм
  («Питер»/«Петербург» делят «тер»); «SanDisk»/«5920» не делят — отвергается.
- **от «всё вместо ничего»:** если ни одно значение из вопроса не найдено ни поиском, ни
  резолвером — честный отказ, а не агрегат по всей сущности. «продали SanDisk» (нет в
  данных) отвечает «нет данных», а не «12 млн по всем продажам».

Резолвер — фоллбэк: срабатывает только когда буквальный поиск дал ноль. Модель и так
расширяет известные ей синонимы, а `ts_like` берёт подстроки; резолвер закрывает зазор —
искажённые базоспецифичные значения, которых модель не знает.

**Резолвер ПОДКЛЮЧЁН к ответу** — с 28.07. В отборе он штатный фоллбэк для групп без
буквального совпадения (`resolve_values` → `ts_phrase` по разрешённым значениям), результат
виден клиенту полем `diag.resolved`. *Ниже в этом файле стояло «строится, но в ответ ПОКА
НЕ подключён» — это опровергнуто кодом (`serene_ask.py`, фоллбэк в отборе и `diag.resolved`)
и записью в `CHANGELOG` от 28.07.*

⚠ **`resolver_clipped` — вектор посчитан по обрезанному началу значения.** Вход эмбеддера
режется на `EMBED_MAXLEN` = 20 000 символов, и счётчик считает, скольких значений это
коснулось: [замер 01.08] `ut_test` — **4** из 188 068, `postgres` — 3 из 115 151. По этим
значениям смысловой поиск идёт по началу строки, а не по всей; текстовый путь не страдает.
Счётчик заведён как исполнение п. 13 (потеря видна запросом), но ни в одном документе до
сих пор не был назван.

### 3-бис. Связь сущностей: шапка ↔ табличная часть

Бот отвечает по одной сущности за вопрос, но табличные части (товары документа, движения
регистра) он подтягивает СТРУКТУРНО. Имя контрагента стоит в шапке, в строках товаров его
нет — поэтому по словам вопроса они не совпадают. Решение: сущности-совпадения тянут за
собой свои табличные части (связь `parent` посчитана при сборке по составному ключу), а
отбор в них идёт ПО ШАПКЕ — «строки, чей владелец попал в совпадения».

Так «какие товары продали ООО Ромашка» отвечает товарами и количествами, а не суммами
документов, а «сколько штук продано» даёт 499 штук — количество лежит в табличной части,
и модель видит его среди величин кандидата (`quantities recorded here: …`, имена из данных).

Чего это ещё НЕ покрывает: вопросы, где значение измерения надо сначала распознать —
«обороты по счёту 62» (понять, что 62 это счёт, развернуть в 62.01/62.02, просуммировать
регистр). Это работа резолвера — он **подключён к ответу с 28.07** (см. §3-тер), но
разворачивание вида «62 → 62.01/62.02» поверх него ещё не сделано.

*Было ошибочно: «он строится, но в ответ пока не подключён». **Чем опровергнуто:** код
`serene_ask.py` — резолвер стоит фоллбэком в отборе, результат уходит в `diag.resolved`;
`CHANGELOG` 28.07 «резолвер подключён к ответу». Строка противоречила и коду, и §3-тер
этого же файла.*

### 3-секст. Честный отказ при сбоях и старение данных (п. 18)

Любой обрыв по дороге — модель молчит, база/движок недоступны, эмбеддер не отвечает —
доходит до обработчика как исключение и превращается в **HTTP 503 с понятным сообщением**
(«модель не отвечает» / «база недоступна»), а НЕ в ответ по частичным данным. `answer`
либо возвращает результат целиком, либо падает — среднего нет. Внутренности (`psql`, стек)
в ответ не утекают, только в журнал.

1С недоступна не роняет корпус: сборка защищена (проверки до такта, сущность-пустышка,
удаление >10%), и корпус остаётся консистентным — бот отвечает последним ЦЕЛЫМ состоянием.
Чтобы старение не было слепым, каждый ответ несёт возраст данных, а при сильном отставании
(1С лежит, такт падает) — явную приписку «данные могли устареть».

### 4-бис. Числа в ответ ставит КОД, а не модель

Решение владельца 28.07: «нужен просто калькулятор для чисел, а не сложные системы».

Модель не пишет посчитанных чисел вообще. Она оставляет **места** — `{total}`, `{count}`,
`{max}`, `{min}`, `{avg}`, `{date_min}`, `{date_max}`, а при нескольких величинах
`{total:ИМЯ}` — и код ставит туда то, что посчитала база.

Почему это лучше проверки: прежде неверное число было **возможно** и лишь отлавливалось
гейтом, а всякая проверка ошибается в обе стороны — за один день она уронила верные
ответы дважды. Теперь неверное число **невозможно по устройству**. Это то же правило
проекта, что и везде: запреты держатся кодом, а не промтом.

Что модель по-прежнему пишет сама — значения, скопированные из ОДНОЙ строки: номер
документа, ИНН, дата конкретной записи. Это цитата, а не арифметика, и её проверяет
прежний гейт по тексту строк. Граница простая: **посчитанное по нескольким строкам —
место, прочитанное из одной строки — цитата.**

🔴 Подстановка сама по себе не защищает от нуля. Если вопрос не назвал величину, итог
считать не по чему, и место `{total}` заполнилось бы нулём — [замер] так и вышло:
«Общая сумма поступлений — 0 руб.» при настоящих 2 088 800. Поэтому без выбранной
величины безымянное место **не заполняется**: формулировка отвергается, отказ называет
доступные имена величин, и вторая попытка адресует величину по имени.

### 5. Итог считается в базе

`count/sum/min/max/avg` по **всему** подходящему множеству, без `LIMIT`. Это ключевое
отличие от чанкового RAG, который суммирует попавшее в выборку и выдаёт часть за целое.
`LIMIT` влияет только на то, что покажут модели, но не на цифру.

Рядом с суммой считается `count(amount)` — сколько строк реально имеют величину.
Иначе среднее по 31 строке подавалось как среднее по 1344.

### 6. Формулировка

Модель получает вопрос, до 25 строк и посчитанные величины. Каждая строка приходит
**целиком**, а не одной подсветкой: `ts_highlight` по устройству отдаёт фрагменты
вокруг совпавших слов (замерено: 144 символа при длине строки 398), и реквизит,
оказавшийся дальше от совпадения, до модели не доходил — ИНН на 367-й позиции терялся
у 12 контрагентов из 13.

### 7. Гейт

Каждое число из текста ответа ищется в данных и в посчитанных величинах. Проверяются:

- **разряды** во всех записях — пробел, неразрывный пробел, запятая, точка, апостроф;
- **даты** — покомпонентно, не строкой;
- **числа прописью** — частным случаем: величина посчитана, а в тексте нет ни одной цифры (работает при `want` = сумма или количество, на списках — нет);
- **структурная проверка подстановки** — место (`{total}` и т. п.), которому нечего подставить, валит формулировку. Это единственное, что осталось от прежней ролевой сверки, и оно структурное, а не числовое.

⚠ У гейта есть и белый список **наших собственных порогов**: число, которое человек назвал в вопросе («больше 500000»), проходит, не встречаясь в данных.

*Было ошибочно: «**роли**: сумма, названная итогом, сверяется именно с итогом». **Чем
опровергнуто:** сверка ролей на основном пути **убрана вместе с `claims`** — промт велит
оставлять `claims` пустыми, они игнорируются, `check_claims` зовётся только из ветки ответа
о полноте, `claims_in_text` не вызывается вовсе. Роли теперь держатся не проверкой, а
подстановкой: место `{total}` заполняет код (решение владельца 28.07), поэтому число не из
той роли стало невозможно по построению — гейт по тексту сверяет число с данными без роли.
Описание было верно для прежнего гейта.*

Не прошло — ответ модели **заменяется структурой посчитанных величин**, а не нашей
прозой: свой текст был бы на одном языке независимо от языка вопроса.

### 8. Отдельная ветка ответа: «что не загрузилось» (`about=coverage`)

Вопрос про **полноту** («всё ли загрузилось», «чего не хватает») идёт не по общему пути, а
своей веткой — этим и закрыта часть п. 13 контракта («бот отвечает, что не загрузилось»).
Раньше эта ветка не была описана здесь вовсе, хотя живёт в коде и в бою.

| Шаг | Чем сделан |
|---|---|
| распознать намерение | модель, разбирая вопрос, ставит `about = coverage` |
| собрать ответ | отдельная функция `_coverage_answer` — берёт **перепись полноты** (таблица `search_coverage`), а не корпус |
| подсказка модели | своя, `COVERAGE_SYS` — не та, что у обычного ответа |
| бюджет | свой: `ASK_COVERAGE_TOP` = 15 записей |
| проверка чисел | ⚠ **НЕ тот же гейт.** Здесь зовётся только `check_claims` — он сверяет те роли, что модель объявила сама; `gate()`, который на основном пути проверяет **каждое** число текста, в этой ветке не вызывается. Число, названное мимо `claims`, тут не проверяется ничем |

Замысел и замер этой ветки — `PLAN_P13_COMPLETENESS.md §«Шаг 3»`: ответ строится из
переписи, а не из корпуса, поэтому «не загрузилось» называется причиной, а не молчанием.

## Как данные попадают в поиск

```
1С ──OData GET──► перепись (что есть, что непусто, что закрыто правами)
                        │
                        ▼
                  загрузка постранично, порядок по ОБЪЯВЛЕННОМУ ключу
                  сверка с $count; дедуп по объявленному ключу
                        │
                        ▼
                  витрина: копия таблиц как есть
                        │
                        ▼
                  сборка корпуса: строка = один документ поиска
                        │
                        ▼
                  индекс: поля по отдельности в ОДНОМ индексе
```

### Перепись вместо списка руками

Состав данных определяет система: служебный документ OData даёт все сущности,
`$metadata` — объявленные ключи и типы, параллельный `$count` — что непусто.
Различаются **пусто** и **закрыто правами**: раньше это выглядело одинаково, и клиент
не знал, что часть его данных недоступна.

### Ключи — контракт платформы, не догадка

| Что | Контракт |
|---|---|
| собственная идентичность | ключ ровно `["Ref_Key"]` |
| табличная часть | ключ содержит `Ref_Key` **и** ещё свойство; `Ref_Key` там — ссылка на владельца |
| владелец табличной части | найден **по данным**: та сущность, где это значение есть |
| дата записи | `Date` у документов, `Period` у регистров — объявляет платформа |
| наименование | `Description`, `Code` — если сущность их объявила |
| мусор протокола | `X_Type`, `X_navigationLinkUrl`, `X_Base64Data` — только при объявленной паре `X` |

Ни одного имени конкретной конфигурации. Проверено разбором AST: неанглийские литералы
в исполняемом коде — только сообщения журнала.

### Строка корпуса

```
реализациятоваровуслуг | Контрагент: ООО Ромашка | Склад: Основной | Сумма: 791800
```

Ссылки на другие объекты **резолвятся в имена** — иначе поиск по имени контрагента не
нашёл бы документ, где лежит только GUID. Карта имён строится по сущностям с
собственной идентичностью.

### Индекс — поля по отдельности

```sql
CREATE INDEX search_idx ON search_corpus
  USING inverted(doc search_dict, refs search_dict, src_table)
  INCLUDE (src_table, row_key, amount, doc_date);
```

| Поле | Что даёт |
|---|---|
| `doc` | широкий запрос по всей строке |
| `refs` | только ссылки: спросить про контрагента, а не «где-то в строке» |
| `src_table` | **без словаря = keyword**: точное совпадение и фильтр **внутри** индекса |

Это шаблон самого движка. Раньше всё склеивалось в одну колонку — 45 реквизитов
превращались в мешок слов, где «Контрагент: Ромашка» и «Склад: Ромашка» неразличимы.

### Инкремент

Пересчитывается только изменившееся: отпечаток строки сравнивается с сохранённым.
Отпечаток считается по **всему**, что уходит в индекс — иначе изменение одних ссылок
не пересчитывалось бы, а прогон отчитывался успешным.

## Что держится кодом, а не договорённостью

Правило владельца: **правила и ограничения — кодом, не промтом.**

| Запрет | Чем держится |
|---|---|
| 1С только читаем | шлюз отвечает 405 на POST/PUT/PATCH/DELETE до всякой авторизации; пользователь 1С — только чтение |
| выход за пределы базы OData | путь проверяется в сыром и раскодированном виде, `..` → 403 |
| сервис не работает без токена | процесс **не стартует**: нет токена — выход с кодом 2 |
| бот не пишет в базу | роль СУБД без права записи: `INSERT/UPDATE/DELETE/TRUNCATE` = 0 привилегий |
| модель не выдумывает числа | гейт сверяет каждое число; не прошло — ответ заменяется |
| подгонка под нашу базу | хук-агент перед коммитом и проверка после каждой правки |

### Разметка сущностей — зачем и что именно уходит

Языковая модель один раз на сущность решает, о таком **спрашивают** или это **служебное**
(технические замеры, объекты «Удалить…», журналы обмена, настройки интерфейса). Ответ
кэшируется в таблице `search_entity_class` и переживает такты; повторно спрашиваем только
про новые сущности, и не больше `CLASSIFY_MAX_PER_RUN` за прогон.

🔴 **Это очерёдность, а не отбор.** Ни одна строка не выбрасывается: текстовый индекс
(BM25) строится по всему корпусу, а векторы считаются сначала не-служебным сущностям,
а служебным — **не считаются вовсе** (решение владельца 29.07: «да, не нужны они в
векторе»). [замер 29.07, УТ] это 41% корпуса.

Полнота (п. 13) не страдает, и это обеспечено двумя вещами, а не обещанием: служебные
сущности лежат в корпусе и **в текстовом индексе**, то есть находятся по словам (не
находятся только «по смыслу»); а отсутствие вектора **названо причиной** в переписи —
`cov_noemb_service` («по решению») отдельно от `cov_noemb_pending` («ещё в очереди»).

**Почему решает модель, а не список слов.** Список вроде «замеры», «удалить», «служебный»
был бы привязкой к языку и к конфигурации: на другой базе те же понятия названы иначе.
[замер 29.07, УТ 11.4.9] из 632 683 строк корпуса 265 916 (42%) — служебные; крупнейшие
`ЗамерыВремени` (97 834) и «Удалить…» (52 153 + 17 311).

Схема базы и образцы значений в модель не уходят — в отличие от пути предыдущего
поколения (NL→SQL), где на каждый вопрос отправлялось 464 292 символа со схемой и
живыми значениями из каждой текстовой колонки.
