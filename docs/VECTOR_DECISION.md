## 0. Что было неверно в первой версии

Три ревизора независимо нашли одни и те же ошибки. Все подтверждены моей проверкой.

| Утверждение v1 | Чем опровергнуто |
|---|---|
| «Причина 30 ГБ — метрика» | 30 ГБ это пик памяти при ПОСТРОЕНИИ на 10 000 строк, где самих векторов **61 МБ**. Квантизация превратила бы 61 МБ в 15 МБ. Разрыв в 600 раз |
| «Квантизация даёт 4×/8×/32× сжатия» | Сырые векторы хранятся в индексе **всегда** (`store_values = true` для ivf, они нужны для переранжирования). Коды пишутся СВЕРХУ: `sq8` даёт не −75%, а **+25%** к объёму |
| «Каждый подквантайзер pq = 1 байт» | `kPqNbits = 4` — четыре бита. Строка `pq` занижена вдвое |
| «Потолок размерности 8192» | Выведено из функции, которая **нигде не вызывается**. Над цитируемой константой стоит комментарий `// there is no strict limit for floating points`, который я не привёл |
| «При d ≥ 32 включается другой алгоритм» | Условие конъюнктивное: нужно **и** `d ≥ 32`, **и** `k ≥ 512` (для угловых метрик 4096). У нас k ≈ 10–97. Ветка та же |
| «`kMaxTrainSample` = 24,6 ГБ» | Ограничено числом строк: при 10 000 строк выборка ≤ 576 векторов ≈ 3,5 МБ |

**Отдельно про метод.** В блок кода я вставил собственные пояснения
(`// l — длина в БАЙТАХ`), которые читаются как часть исходника, и обрезал настоящий
соседний комментарий. Так делать нельзя: цитата должна быть цитатой.

**Причина 30 ГБ остаётся НЕИЗВЕСТНОЙ.** Это открытый вопрос, а не закрытый.

## 1. Что установлено точно: с косинусом квантизация недоступна

**[замер]** Собственная справка нашей сборки (получена ошибкой валидации):

```
quant (string: sq8|sq4|pq|rabitq|none, default none;
       sq8|sq4|pq|rabitq need l2|ip)
```

**По умолчанию квантизации НЕТ.** Мы строили индекс с `metric='cosine'` — а с косинусом
наша сборка запрещает сжатие вообще:

```
metric='cosine', quant='sq8'    -> ERROR: ivf quantization supports only metric 'l2' or 'ip'
metric='cosine', quant='rabitq' -> ERROR: то же
metric='cosine', quant='none'   -> CREATE INDEX
metric='ip',     quant='sq8'    -> CREATE INDEX
```

То есть из всех сочетаний мы выбрали единственное, при котором векторы ложатся в индекс
несжатыми: 1536 чисел × 4 байта = 6 КБ на строку.

**[вывод]** Это ограничение сборки, и оно реально. Но объяснением расхода памяти при
построении оно **не является** — см. §0.

**[замер]** Полная матрица, снятая ревизорами (4 метрики × 5 квантизаторов): `l2` и `ip`
пропускают все квантизаторы; `cosine` **и `l1`** — только `none`.

### Расхождение с публичным репозиторием

**[код]** В `main` (`server/catalog/index.cpp:343-347`) умолчание уже `sq8`, и косинус
с квантизацией разрешён. Наша сборка на этом месте отстаёт. Значит часть лечения придёт
с обновлением, но обходной путь есть сейчас.

## 2. Что реально доступно на нашей сборке

**[замер]** Проверено на `FLOAT[2048]` (только валидация опций, индексы не собирались):

| Опции | Результат |
|---|---|
| `metric='ip', quant='pq'` | создаётся |
| `metric='ip', quant='rabitq'` | создаётся |
| `metric='ip', quant='rabitq', rabitq_bits=4` | создаётся |
| `metric='ip', quant='sq4'` | создаётся |
| `metric='l2', quant='rabitq'` | создаётся |
| `metric='cosine', quant='rabitq'` | **отказ** |

Запрет держится на МЕТРИКЕ, не на квантизаторе: `ip` и `l2` пускают любое сжатие.

### Сколько это даёт — и чего НЕ даёт

**[код]** Сырые векторы хранятся в индексе **при любом квантизаторе**:
`entry.store_values = true` безусловно для ivf (`index.cpp:583`), и они нужны для
переранжирования. Коды квантайзера пишутся **дополнительно**, а не вместо.

**Поэтому колонка ниже — это размер КОДОВ, а не итоговый размер индекса.**
`sq8` не уменьшает индекс на 75%, а увеличивает примерно на 25%.

**[код]** `pq_m` подбирается так, чтобы на подквантайзер приходилось около двух
измерений (`kTargetDsub = 2`, `index.cpp:367-377`); каждый кодируется **четырьмя
битами** (`kPqNbits = 4`, `quantizer.cpp:71`), упаковка PQ4-FastScan.

| Режим | Байт КОДОВ на вектор (d=2048) | Метка |
|---|---|---|
| `none` | 0 (кодов нет) | **[код]** |
| `sq8` | 2 048 | **[код]** |
| `sq4` | 1 024 | **[код]** |
| `pq` (умолчание ≈ d/2) | 512 | **[код]** |
| `rabitq`, 1 бит | ~256 | **[вывод]** — исходников faiss в репозитории нет |

### Настоящий довод за квантизацию — не объём, а точность

**[замер]** Справка движка по `sdb_rerank_factor`:

> …pool re-scored with **exact distances** for a quantized IVF vector-similarity query…
> **Unquantized (quant = 'none') indexes never rerank, regardless of this setting.**

То есть при `quant='none'` точного пересчёта кандидатов **нет вообще** — выдача
остаётся приближённой без уточнения. Это и есть главная причина брать квантизацию,
а не экономия места.

**[замер]** Опция, прямо управляющая объёмом хранения, в справке отдельная:
`compression (bool, default true; false stores the index vectors uncompressed)`.

**[код]** `rabitq` округляет размерность вверх до степени двойки —
`RotatedDim(d) = std::bit_ceil(d)` (`quantizer.cpp:81`). Практическое следствие:
**2048 — точное попадание, паддинга ноль; 2560 округлится до 4096, то есть 37% памяти
уйдёт в нули.** Это аргумент в пользу 2048 при выборе размерности.

## 3. Потолка размерности в пути ivf нет вовсе

**[код]** `libs/iresearch/include/iresearch/utils/vector.hpp:58,90`:

```cpp
inline constexpr size_t kMaxDimF32 = 1 << 15;      // = 32768
...
const auto l = data.size() - 1;                     // l — длина в БАЙТАХ
case Type::F32:
  if (l <= kMaxDimF32 && l % 4 == 0) {
    return {t, l / 4};                              // байты -> элементы
  }
```

Чтение кода само по себе верно: `l` — длина в байтах, деление на 4 даёт элементы.
**Но вывод «потолок 8 192» неверен по двум причинам:**

**[код]** Прямо над константой стоит комментарий, который в версии 1 я не привёл:

```
// there is no strict limit for floating points
inline constexpr size_t kMaxDimF32 = 1 << 15;
```

**[код]** Функция `irs::vector::Info()` **не вызывается нигде** — ни в `server/`, ни в
`libs/`, ни в тестах. Поиск даёт единственное вхождение: само определение.

**[замер]** Проверка на живом движке: валидация опций `ivf` принимает
d = 8192, 8193, 16384, 32768, 65536 и 100 000 без единого возражения про размерность;
`array_cosine_similarity` реально считает на `FLOAT[16384]` и `FLOAT[65536]`.
Единственный наблюдаемый предел — **100 000** у самого типа `ARRAY`.

**[код]** Структурная граница, о которой стоило сказать вместо мнимой: размерность
передаётся как `uint16_t` (`column_info.hpp:47`, `clustering.cpp:147`) → **65 535**.

**[вывод]** 2048 и 2560 проходят с большим запасом. Вывод версии 1 был случайно верен
при неверном обосновании.

## 5. Мы вышли за пределы протестированного

**[код]** Покрытие `ivf` в тестах и демках движка:

| Что | Значение |
|---|---|
| Максимум `d` в тестах **на объёме** | **8** при 50 000 строк |
| Единственный тест с `d > 8` | `d = 384` на **четырёх** строках |
| Тестов `ivf` с `d > 128` на любом объёме | **ноль** |
| Наш случай | 1536 × 10 000 — в **38 раз** больше максимума |

**[код]** Версия 1 объясняла это переключением алгоритма кластеризации при `d >= 32`.
**Объяснение неверно.** Условие конъюнктивное:

```cpp
SuperKMeansGate(d, k, min_k) { return d >= kSuperKMeansMinD && k >= min_k; }
```

где `min_k` = 512, а для угловых метрик 4096 (`clustering.cpp:42-44, 86-88`). Число
кластеров при наших настройках (`sdb_ivf_posting_size = 1024`, `sample_factor = 0`)
получается **k ≈ 10** на 10 тыс. строк и **≈ 97** на 98 тыс. Это на два порядка ниже
порога — ветка **та же самая**, что в тестах на `FLOAT[8]`.

**[код]** Константа `kMaxTrainSample = 4 194 304` (`centroids.cpp:51`) в версии 1 была
пересчитана в 24,6 ГБ. Она **недостижима**: следующей строкой стоит
`sample_size = min(sample_size, rows)`. При 10 тыс. строк обучающая выборка ≤ 576
векторов ≈ 3,5 МБ.

**[вывод]** Вывод «замер на d=8 не переносится на 1536» остаётся верным — но по
неизвестной причине, а не по этим двум.

**[код]** Почему сборка не отменяется: во всём пути построения `ivf` **нет ни одной
точки проверки прерывания** — проверено поиском по коду. `pg_cancel_backend` возвращает
успех, потому что сигнал доставлен, а читать его некому.

## 6. `ai_embed`: остаётся внешним

**[код]** Тело запроса содержит ровно два поля — `model` и `input`
(`provider_openai.cpp:130-141`). Секрет принимает три ключа: `api_key`, `base_url`,
`embeddings_path` (`embedding.cpp:64`). Параметра размерности нет нигде.

**[замер]** Наш эмбеддер без явного `dimensions` отдаёт **1024**.

**[вывод] ⚠ ЭТОТ ВЫВОД БЫЛ НЕВЕРЕН — исправлено 27.07 по замечанию владельца.**

Прежняя формулировка: «задать нужную размерность через `ai_embed` невозможно, поэтому
держим внешний эмбеддер». Посылка верна, вывод из неё не следует.

**[код]** `ai_embed` возвращает `FLOAT[]` — массив **без фиксированной длины**. В демке
движка стоит `ai_embed(abstract, 'gemini-embedding-001', 'gemini')::FLOAT[3072]`
(`demo5/bootstrap.sql:5-33`, `SERENE_CAPS_3.md §14`). То есть размерность — свойство
**модели и эндпоинта**, а не параметр функции; колонка объявляется под то, что модель
отдаёт. Параметра `dimensions` нет потому, что он и не нужен, а не потому, что чего-то
не хватает.

Наш блокер («у нас индекс `FLOAT[1536]`, а без параметра DashScope отдаёт 1024») был
**круговым**: 1536 мы взяли по образцу прежнего слоя braine, а не из замера. Ранее
проведённое исследование по выбору эмбеддера дало ответ **«подходит любой»** — движок
хранит и индексирует `FLOAT[N]` при любом N (потолок структурный, 65 535, см. §3).

**Действующий вывод: `ai_embed` пригоден.** Размерность выбирается объявлением колонки
под выбранную модель. Что это даёт:
- уходит ~120 строк своего кода: четыре реализации HTTP-похода, пул на 16 потоков,
  ручной батчинг, ретраи, очередь `inflight`;
- уходит **тихая потеря данных**: сейчас непосчитанная пачка увеличивает
  `failed_batches` и видна только в журнале; у `ai_embed` пропуск даёт `NULL`, и
  недосчитанное ловится `count(*) FILTER (WHERE emb IS NULL)`;
- эмбеддинг считается **там же, где лежат данные**, внутри `MERGE`, а не через
  перекачку корпуса в Python и обратно.

Оговорка, которая остаётся: `ai_embed` — сетевой вызов **внутри** запроса, синхронный.
Как он группирует вызовы при `INSERT ... SELECT` — из исходников не выяснено, поэтому
скорость сборки надо **замерить**, а не предполагать.

### Переход 1536 → 1024 бессмысленен

**[код]** Все буферы, зависящие от размерности, зависят **линейно**. Единственный
квадратичный член — матрица поворота `4·d²`: 9,4 МБ против 4,2 МБ. Экономия 5 МБ на
фоне 30 ГБ.

**[вывод]** 30 ГБ → 20 ГБ, 40 минут → 27. Задача не решается, только откладывается.

## 7. Что делать

### Первое: найти причину, а не перебирать квантизаторы

Причина 30 ГБ неизвестна. Перебор квантизаторов её не найдёт: они **добавляют** работу
к тому же пути, который уже съел память, и ожидать меньшего пика оснований нет.

**Порядок — от дешёвого к дорогому, только на изолированной копии:**

1. **одна** сборка на **1 000** строк с профилированием памяти по фазам (обучение
   центроидов / присвоение кластеров / кодирование). Тысяча строк, а не десять тысяч;
2. по профилю понять, какая фаза растёт — и только тогда выбирать рычаг;
3. рычаги известны и зафиксированы: `sdb_ivf_sample_factor`, `sdb_ivf_posting_size`,
   `compression`, `quant`.

**[код]** Почему изолированная копия обязательна: в пути построения `ivf` **нет ни
одной точки проверки прерывания** (поиск по `formats/ivf/*` не даёт ни одного
`cancel`/`interrupt`). `pg_cancel_backend` возвращает успех, читать сигнал некому.
Снимается только рестартом движка.

### Если дойдёт до конфигурации: `ip` вместо `cosine`

**[код+замер]** Математика подтверждена и кодом, и замером: `ComputeDistance<InnerProduct>`
— чистое скалярное произведение, `ComputeDistance<Cosine>` — то же, делённое на нормы;
обе «больше — лучше», знак не инвертируется. Более того, движок **сам** делает эту
подмену при квантизации: `EffectiveQuantMetric(Cosine) = InnerProduct`
(`column_info.hpp:80-83`), а писатель нормирует строки (`ivf_writer.cpp:89`).
Ревизор сверил top-20 обоими способами — совпало **20 из 20, позиция в позицию**.

**Но рекомендация неполна без трёх вещей:**

1. **[код]** Оператор `<=>` привязан к `VectorMetric::Cosine`
   (`functions/vector.cpp:394-410`), а планировщик требует совпадения метрики индекса
   и запроса (`iresearch_plan.cpp:594-596`). С индексом на `ip` запрос с `<=>`
   **не выдаст ошибки — молча пойдёт полным сканом**. Нужен `<#>` или `inner_product`;
2. **[код]** Меняется и ЗНАЧЕНИЕ скора: `<=>` даёт `1 − cos`, `<#>` даёт `−ip`.
   Любой порог вида «сходство > 0.8» после перехода начнёт работать неверно;
3. **[код]** При `cosine` движок нормирует сам; при `ip` — **нет**. Вся корректность
   ложится на нашу нормировку. В сборке есть `l2_normalize`, то есть делать это можно
   в SQL, а не в Python.

### Чего пока не знаем честно

Все проверки режимов выше — **валидация опций, а не сборка**. Обучающая выборка
хранится несжатой независимо от квантизатора, и именно она может оказаться главным
потребителем памяти. Сжатие уменьшает **хранение**, а про **построение** у нас цифр нет.

### Запасной вариант, который надо померить первым

**[замер]** Точный перебор работает и он быстрее нашего нынешнего варианта. На
97 965 × 1536, воспроизведено тремя ревизорами независимо:

| Форма запроса | Время |
|---|---|
| `ORDER BY emb <=> q` | 262–338 мс |
| `ORDER BY emb <#> q` (нормированные) | 291–337 мс |
| `ORDER BY array_cosine_similarity(emb, q) DESC` — наш нынешний | 397–511 мс |

**[вывод]** Обе формы исполняет движок; версия 1 ошибочно противопоставляла «движок
против Python». Разница между ними — в биндинге и плане, а не в том, кто считает.

**[вывод]** Для нашего объёма это рабочий вариант с recall ровно 1.0, и он гибридится
с текстовым фильтром в одном запросе. Прежде чем городить ANN — надо померить, хватает
ли его.

## 9. Ответ разработчиков SereneDB и что он изменил (27.07)

**Их ответ дословно по сути:** есть замер на **1,5 млн строк с векторами по 1536**.
Грузили **сразу с индексом, а не создавали индекс после** («так медленнее, но из-за
бизнес-требований делали именно так»). Скорость загрузки ~400 строк/с, помимо вектора
были ещё текстовые колонки. Итоговый индекс ~15 ГБ.

**Это меняет диагноз.** Дело не в размерности и не в объёме — дело в ПОРЯДКЕ:

| Порядок | Результат |
|---|---|
| заполнить таблицу → `CREATE INDEX` (наш) | ломается на **6 000** строк |
| `CREATE INDEX` на пустой → `INSERT` (вендор) | 1,5 млн строк × 1536 у них; **98 тыс. у нас вошли** |

**[замер 27.07]** Вставка в уже созданный `ivf`-индекс на нашей машине:

```
+ 5 000 строк -> 1 с  ( 5 000 строк/с), +423 МБ
+10 000 строк -> 2 с  ( 5 000 строк/с), +649 МБ
+30 000 строк -> 3 с  (10 000 строк/с), +232 МБ
```

Семьдесят тысяч строк за двенадцать секунд — там, где `CREATE INDEX` не осиливал шесть
тысяч. Все 97 965 строк корпуса вошли в таблицу с живым индексом.

Это ровно то, на что указывал один из агентов ещё до ответа вендора: **во всех тестах
движка порядок именно такой** — `CREATE TABLE` → `CREATE INDEX` → `INSERT` →
`VACUUM (REFRESH_TABLE)`. Наш порядок оказался нетестируемой веткой.

### Что осталось нерешённым

**Работа не исчезла, а сместилась на публикацию.** `VACUUM (REFRESH_TABLE)` после
вставки 98 тысяч строк одним куском повис и съел 34 ГБ. То есть кластеризация делается
при публикации, и проблема та же — вся работа разом.

**Гипотеза на проверку:** публиковать порциями — вставил ~5 000, опубликовал, дальше.
Тогда движок никогда не получает всё сразу. У вендора это, судя по описанию, выходило
само собой: они грузили потоком со скоростью 400 строк/с, и публикация размазывалась.

Совпадает с гипотезой владельца про куски: **не давать движку делать всю работу
одним куском** — с двух разных сторон одно и то же решение.

### Практический вывод для сборщика корпуса

Если порционная публикация подтвердится, менять надо не размерность вектора и не
метрику, а **порядок в `serene_search_build.py`**: создавать индекс на пустой таблице
один раз и наполнять вставками с периодической публикацией, вместо нынешнего
`DROP INDEX` + `CREATE INDEX` поверх готового корпуса.

## 10. Замеры 27.07: главное было во ВТОРОЙ цифре разработчиков

### 10.0 Что я пропустил в их ответе

Из ответа разработчиков я вынес только **порядок** (индекс на пустой таблице, данные
после) и на этом остановился. Владелец указал на пропущенное:

> «Сама загрузка при этом была порядка **400 строк в секунду**.»

Наша вставка шла **5 000–10 000 строк/с** — в 12–25 раз быстрее. Одинаковую работу с
такой разницей в скорости не делают. Значит наша вставка ту работу **не делает, а
откладывает**, и отложенное копится до момента публикации. Скорость была не деталью
их рассказа, а диагнозом нашей.

Обратная сторона той же цифры: 400 строк/с для наших 97 965 строк — это **четыре
минуты**. Темп, за который разработчики извинялись («так медленнее»), нас полностью
устраивает.

### 10.1 Одна большая транзакция — рост без полки

`INSERT INTO v SELECT ... FROM read_parquet(...)` на все 97 965 строк, индекс уже
создан на пустой таблице, опции `segment_docs_max = 5000, compaction_interval = 0`:

| Время | RSS |
|---|---|
| старт | 13,5 ГБ |
| +3,5 мин | 17,7 ГБ |
| +5 мин | 21,3 ГБ |
| +6 мин | 22,7 ГБ |
| остановлено | 23,9 ГБ |

Рост строго линейный, **25 МБ/с, полки нет**. Шаг между отсчётами одинаков до десятых —
значит расход привязан к потоку строк, а не к запечатыванию сегментов (тогда была бы
пила). `SELECT count(*) FROM v` всё это время возвращал **0**: одна транзакция, до
коммита не опубликовано ничего.

**Вывод: `segment_docs_max` в одной большой транзакции работу не ограничивает.**
Гипотеза «резать на сегменты» — проверена и не подтвердилась в этой форме.

### 10.2 Штатные рычаги (из наших же аудитов, не из моей головы)

Опции индекса, `server/connector/inverted_index_options_util.h:42-76`
(`SERENE_CAPS_3.md §3.3`, `SERENE_CAPS_1.md §2.4`):

| Опция | Умолчание | Что делает |
|---|---|---|
| `refresh_interval` | 1000 мс | **фоновая публикация** — записи становятся видимы поиску сами |
| `compaction_interval` | 1000 мс | фоновое слияние сегментов |
| `segment_docs_max` | 0 = ∞ | документов на сегмент |
| `segment_memory_max` | 256 МБ | памяти на сегмент |
| `compaction_max_segments` | 10 | сколько сегментов сливать за раз |

Замер по `sdb_metrics` на боевом `search_idx`: 97 965 документов лежат в **одном
сегменте**. При старте движок пишет в лог `Search maintenance: per-index
refresh/compaction loops` — фоновый цикл существует и работает всегда.

### 10.3 Ошибка предыдущего прогона: я отбирал работу у движка

`VACUUM (REFRESH_*)` — не уборка мусора, а **публикация** (`SERENE_CAPS_1.md §15`,
`SERENE_CAPS_3.md` п. 22). Вызвав `VACUUM (REFRESH_TABLE)` на всей таблице разом, я
потребовал одним куском ту работу, которую фоновый цикл делает порциями каждую
секунду. Отсюда 34 ГБ и смерть движка.

**Разработчики про `VACUUM` не упоминали вообще.** В их сценарии публикацией занимался
фоновый цикл, а темп вставки был таким, что цикл успевал. 400 строк/с — вероятно, не
предел их железа, а тот темп, при котором маintenance не отстаёт.

### 10.4 Ловушка WAL: опыты с `ivf` минируют боевой инстанс

Незавершённая работа с `ivf` попадает в WAL и **проигрывается при каждом старте**.
27.07 боевой движок из-за этого три часа крутился в петле OOM-рестартов: RSS рос
~19 МБ/с до OOM, рестарт, снова, — сам бы не вышел.

Лечение (проверено): остановить, убедиться `strings`, что имён боевых таблиц в WAL
нет, снять полную копию `store.db` + WAL, отвести WAL в сторону, стартовать. Движок
поднялся за **10 секунд**, данные целы: корпус 97 965, все с эмбеддингом,
226 сущностей, резолвер 60 552, `search_idx` на месте.

🔴 **Правило: любые опыты с `ivf` — только на отдельном `--server_directory`.**
Опытный движок поднимается второй копией на другом порту, боевой не затрагивается.

### 10.5 Порционная заливка без ручного `VACUUM` — и настоящий диагноз

Форма, в которой работали разработчики: порции отдельными транзакциями, публикацию
делает фоновый цикл, ручного `VACUUM` нет вовсе. Индекс создан на пустой таблице,
порции по 2 000 строк.

| Порция | Всего строк | Время | Темп | RSS |
|---|---|---|---|---|
| 1 | 2 000 | 1 с | 2 000 строк/с | 0,9 ГБ |
| 2 | 4 000 | 1 с | 2 000 строк/с | 0,9 ГБ |
| 3 | 6 000 | 1 с | 2 000 строк/с | 0,9 ГБ |
| 4 | **встала** | не завершилась | — | **22,8 ГБ** |

`count(*)` остановился на **6 000** и не двигался; память выросла с 0,9 до 22,8 ГБ.

🔴 **Это ровно тот порог 5-6 тысяч строк, который мы намерили в самом первом опыте**
с `CREATE INDEX` поверх заполненной таблицы (1 000 и 5 000 — секунда; 6 000 — виснет).
Число совпало с точностью до порции.

**Вывод: дело не в том, что мы делали.** Проверены и отвергнуты замером три гипотезы,
включая обе мои сегодняшние:

| Гипотеза | Проверка | Итог |
|---|---|---|
| порядок: индекс до данных, а не после | вставка в готовый индекс | **не помогает** — та же стена на 6 000 |
| размер транзакции: лить порциями, а не одним куском | порции по 2 000 отдельными транзакциями | **не помогает** — стена там же |
| сегментирование: `segment_docs_max = 5000` | одна транзакция с опцией | **не помогает** — линейный рост без полки |
| ручной `VACUUM` отбирает работу у фонового цикла | заливка вообще без `VACUUM` | **не помогает** — стена наступает раньше, чем понадобился бы `VACUUM` |

Остаётся **жёсткая стена около 6 000 строк при 1536 измерениях**, не обходимая ни
порядком, ни размером порции, ни опциями сегмента, ни отказом от ручной публикации.
`sdb_ivf_posting_size` (128/256/1024) её тоже не двигает — замерено ранее.

### 10.6 Что теперь спросить у разработчиков

Их замер — 1,5 млн строк × 1536, то есть они эту стену **прошли**. Значит различие в
условиях, а не в объёме. Что у них отличалось по их же словам: «помимо вектора были
ещё текстовые колонки». Наши опытные таблицы — только `row_key VARCHAR` + `emb`.

Спросить конкретно:
1. Какая метрика и `quant` были в их индексе? Мы везде брали `metric='cosine'`,
   а квантизация с `cosine` запрещена движком — возможно, их путь шёл через `l2`/`ip`
   с квантизацией и потому не упирался в память.
2. Какие значения `sdb_ivf_posting_size` и `sdb_ivf_sample_factor` стояли?
3. Воспроизводится ли у них останов на ~6 000 строк на таблице из двух колонок
   (`VARCHAR` + `FLOAT[1536]`, `metric='cosine'`, умолчания)? Это минимальный
   воспроизводящий пример, и он у нас стабилен.
