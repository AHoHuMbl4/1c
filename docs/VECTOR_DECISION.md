# Векторный поиск в SereneDB 26.07.3: что доступно и почему было 30 ГБ

Составлено 2026-07-27 по итогам четырёх независимых расследований (два агента по
размерности, два по HNSW) плюс независимая проверка владельца. Каждое утверждение
ниже помечено: **[замер]** — проверено запуском на нашей сборке; **[код]** — прочитано
в исходниках; **[вывод]** — рассуждение поверх первых двух.

---

## 1. Главное: причина 30 ГБ найдена, и это не размерность

**[замер]** Собственная справка нашей сборки (получена ошибкой валидации):

```
quant (string: sq8|sq4|pq|rabitq|none, default none;
       sq8|sq4|pq|rabitq need l2|ip)
```

**По умолчанию квантизации НЕТ.** Мы строили индекс с `metric='cosine'` — а с косинусом
наша сборка запрещает сжатие вообще:

```
metric='cosine', quant='sq8'    -> ERROR: ivf quantization supports only metric 'l2' or 'ip'
metric='cosine', quant='rabitq' -> ERROR: то же
metric='cosine', quant='none'   -> CREATE INDEX
metric='ip',     quant='sq8'    -> CREATE INDEX
```

То есть из всех сочетаний мы выбрали единственное, при котором векторы ложатся в индекс
несжатыми: 1536 чисел × 4 байта = 6 КБ на строку.

**[вывод]** Тридцать гигабайт — следствие выбора МЕТРИКИ, а не размерности вектора.

### Расхождение с публичным репозиторием

**[код]** В `main` (`server/catalog/index.cpp:343-347`) умолчание уже `sq8`, и косинус
с квантизацией разрешён. Наша сборка на этом месте отстаёт. Значит часть лечения придёт
с обновлением, но обходной путь есть сейчас.

## 2. Что реально доступно на нашей сборке

**[замер]** Проверено на `FLOAT[2048]` (только валидация опций, индексы не собирались):

| Опции | Результат |
|---|---|
| `metric='ip', quant='pq'` | создаётся |
| `metric='ip', quant='rabitq'` | создаётся |
| `metric='ip', quant='rabitq', rabitq_bits=4` | создаётся |
| `metric='ip', quant='sq4'` | создаётся |
| `metric='l2', quant='rabitq'` | создаётся |
| `metric='cosine', quant='rabitq'` | **отказ** |

Запрет держится на МЕТРИКЕ, не на квантизаторе: `ip` и `l2` пускают любое сжатие.

### Сколько это даёт

**[код]** `pq_m` по умолчанию подбирается так, чтобы на подквантайзер приходилось около
двух измерений (`kTargetDsub = 2`, `index.cpp:367-377`), каждый кодируется байтом.

| Режим | Байт на вектор (d=2048) | Сжатие |
|---|---|---|
| `none` — то, что строили мы | 8 192 | 1× |
| `sq8` | 2 048 | 4× |
| `sq4` | 1 024 | 8× |
| `pq` (умолчание ≈ d/2) | ~1 024 | 8× |
| `rabitq`, 1 бит | ~256 | 32× |

**[код]** `rabitq` округляет размерность вверх до степени двойки —
`RotatedDim(d) = std::bit_ceil(d)` (`quantizer.cpp:81`). Практическое следствие:
**2048 — точное попадание, паддинга ноль; 2560 округлится до 4096, то есть 37% памяти
уйдёт в нули.** Это аргумент в пользу 2048 при выборе размерности.

## 3. Потолок размерности — 8 192, а не 32 768

**[код]** `libs/iresearch/include/iresearch/utils/vector.hpp:58,90`:

```cpp
inline constexpr size_t kMaxDimF32 = 1 << 15;      // = 32768
...
const auto l = data.size() - 1;                     // l — длина в БАЙТАХ
case Type::F32:
  if (l <= kMaxDimF32 && l % 4 == 0) {
    return {t, l / 4};                              // байты -> элементы
  }
```

`kMaxDimF32` сравнивается с длиной буфера **в байтах**, число измерений получается
делением на 4. Потолок — **8 192 измерения**.

`l % 4 == 0` — не «байтовое выравнивание», а условие «длина кратна размеру float»,
иначе буфер не является массивом `float`.

**[замер]** Тип колонки при этом допускает и больше: `FLOAT[1024]`, `[1536]`, `[2048]`,
`[3072]` создаются; жёсткий предел типа — 100 000 (`ARRAY type size must be at most`).
Ограничение 8 192 относится к сериализованному значению вектора, а не к DDL.

**[вывод]** 2048 и 2560 проходят с запасом. Заложиться на 16 000 было бы нельзя.

## 4. HNSW: его удалили из продукта

**[код]** Проверено двумя независимыми агентами по репозиторию того же дня, что и наша
сборка (коммит `722c929`, 26.07.2026):

- список опклассов захардкожен двумя значениями:
  `server/catalog/index.cpp:110-113` — `{kIncludedKind, kIVFKind}`;
- каталога `libs/iresearch/include/iresearch/columnstore/` **не существует**, хотя
  `scripts/perf/sweep_hnsw.sh:16` ссылается на удалённый `columnstore/hnsw.cpp`;
- фикстура каталога `resources/tests/catalog/hnsw_column_config.bin` осталась сиротой;
- из faiss берутся только кластеризация и квантайзеры, `IndexHNSW` не подключён;
- в 1653 тестах `sqllogic` слова `hnsw` нет вообще;
- плана `IRESEARCH_ANN_SCAN`, обещанного демкой, в коде нет.

**[вывод]** HNSW **был и был заменён на IVF**. Демки `demo4` (100 тыс. × 1536) и
`demo5` (5 тыс. × 3072) — устаревшая витрина: они **не запустятся ни у нас, ни на их
собственном `main`**, упадут на `CREATE INDEX`.

### Девять строк в бинарнике объяснены

**[замер]** Пять уникальных строк (`hnsw_ef_search`, `hnsw_index_scan`,
`pragma_hnsw_index_info`, `hnsw_compact_index`, `hnsw_enable_experimental_persistence`)
лежат в таблице автозагрузки расширений DuckDB — справочник «эта функция живёт в
расширении `vss`». Соседи по той же таблице: `httpfs`, `spatial`.

```
INSTALL vss;
ERROR: INSTALL is not supported by SereneDB: extensions are compiled into
       the server binary and cannot be installed at runtime.

SET hnsw_ef_search=100;
ERROR: ...it exists in the vss extension. This feature relies on the "vss"
       extension which is not built into this SereneDB binary.
```

**[замер]** Ни `SET`, ни `LOAD`, ни `INSTALL`, ни `PRAGMA` его не включают. Ни флага
сборки (`CMakeLists` — 7 опций, ни одной про ANN), ни редакции, ни лицензионного
ограничения (чистая Apache 2.0) за этим нет.

**[вывод]** Это чужой HNSW (расширение `vss` поверх usearch), и он тоже недоступен.
Собственный HNSW SereneDB — удалён из продукта.

## 5. Мы вышли за пределы протестированного

**[код]** Покрытие `ivf` в тестах и демках движка:

| Что | Значение |
|---|---|
| Максимум `d` в тестах **на объёме** | **8** при 50 000 строк |
| Единственный тест с `d > 8` | `d = 384` на **четырёх** строках |
| Тестов `ivf` с `d > 128` на любом объёме | **ноль** |
| Наш случай | 1536 × 10 000 — в **38 раз** больше максимума |

**[код]** Почему наш успешный замер обманул: при `d >= 32` включается другой алгоритм
кластеризации (`kSuperKMeansMinD = 32`, `clustering.cpp:42-44`). Замер «50 тыс. строк за
224 мс» был на `FLOAT[8]` — **ниже порога**, то есть по другой ветке кода. Про 1536 он
не говорит ничего.

**[код]** Оба агента независимо указали на одну константу:
`kMaxTrainSample = 4 194 304` (`centroids.cpp:51`) — предохранитель по **числу
векторов, слепой к размерности**. В байтах: 134 МБ при `d=8` и **24,6 ГБ** при 1536.

**[код]** Почему сборка не отменяется: во всём пути построения `ivf` **нет ни одной
точки проверки прерывания** — проверено поиском по коду. `pg_cancel_backend` возвращает
успех, потому что сигнал доставлен, а читать его некому.

## 6. `ai_embed`: остаётся внешним

**[код]** Тело запроса содержит ровно два поля — `model` и `input`
(`provider_openai.cpp:130-141`). Секрет принимает три ключа: `api_key`, `base_url`,
`embeddings_path` (`embedding.cpp:64`). Параметра размерности нет нигде.

**[замер]** Наш эмбеддер без явного `dimensions` отдаёт **1024**.

**[вывод]** Задать нужную размерность через `ai_embed` невозможно. Плюс он синхронный
внутри запроса и только текстовый. **Держим внешний эмбеддер; движок хранит и
индексирует готовый вектор.** Это согласуется с независимой проверкой владельца.

### Переход 1536 → 1024 бессмысленен

**[код]** Все буферы, зависящие от размерности, зависят **линейно**. Единственный
квадратичный член — матрица поворота `4·d²`: 9,4 МБ против 4,2 МБ. Экономия 5 МБ на
фоне 30 ГБ.

**[вывод]** 30 ГБ → 20 ГБ, 40 минут → 27. Задача не решается, только откладывается.

## 7. Что делать

### Решение по конфигурации

**Нормировать векторы и брать `metric='ip'`.** На нормированных векторах скалярное
произведение даёт ровно тот же порядок, что косинус — то же ранжирование, — но
открывает все квантизаторы. Косинус оставляет только несжатый режим.

Порядок проверки, **только на копии инстанса** (сборка не отменяется):

1. собрать `ivf` на 10 000 строк в трёх вариантах: `ip/none`, `ip/sq8`, `ip/rabitq`;
2. замерить **пик памяти при построении** и время;
3. замерить recall против точного перебора на золотом наборе;
4. только после этого решать про полный корпус.

### Чего пока не знаем честно

Все проверки режимов выше — **валидация опций, а не сборка**. Обучающая выборка
хранится несжатой независимо от квантизатора, и именно она может оказаться главным
потребителем памяти. Сжатие уменьшает **хранение**, а про **построение** у нас цифр нет.

### Запасной вариант, который надо померить первым

**[замер]** Точный перебор силами движка работает: оператор `<=>` и функции расстояния
штатные, считает движок, не Python — векторизованно и без перегона данных по сети.
На 97 965 × 1536 это **314 мс** против 462 мс у нашего варианта с
`array_cosine_similarity`.

**[вывод]** Для нашего объёма это рабочий вариант с recall ровно 1.0, и он гибридится
с текстовым фильтром в одном запросе. Прежде чем городить ANN — надо померить, хватает
ли его.

## 8. Вопросы разработчикам SereneDB

Канал указывает сам движок в тексте ошибки:
`https://github.com/serenedb/serenedb/issues`. Версия: `PostgreSQL 18.3 (SereneDB 26.07.3)`.

1. HNSW удалён окончательно или будет возвращён? Демки `examples/demo4` и `demo5` на
   вашем же `main` падают с `Unknown built-in opclass 'hnsw'` — это баг витрины или
   существует непубличная сборка?
2. Какая конфигурация `ivf` рекомендована для ~100 тыс. строк × 1536, косинус?
   Конкретно: `quant`, `pq_m`, `rabitq_bits`, `sdb_ivf_posting_size`,
   `sdb_ivf_sample_factor`, `sdb_nprobe`, `sdb_rerank_factor`. Сколько ОЗУ и времени
   занимает построение, какой recall@10?
3. В 26.07.3 квантизация запрещена с `metric='cosine'`, а в `main` уже разрешена и
   `sq8` стал умолчанием. В каком релизе это доехало и можно ли получить сборку с этим
   поведением?
4. Есть ли регрессионное покрытие боевых размерностей? В `tests/sqllogic/` максимум —
   `FLOAT[384]` на четырёх строках, всё остальное `d <= 8`.
5. `kMaxTrainSample` задан в числе векторов, а не в байтах — при `d=1536` это 24,6 ГБ.
   Это осознанное решение?
6. Построение `ivf` не прерывается: `pg_cancel_backend` возвращает успех, работа
   продолжается, снимается только рестартом. Точек проверки отмены в коде нет.
7. Мелкий дефект: `CREATE INDEX ... USING secondary (col unknown_opclass)` молча
   создаёт индекс **без колонок** вместо ошибки, тогда как `USING inverted` в том же
   случае корректно ругается.
