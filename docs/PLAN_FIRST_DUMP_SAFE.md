## Простыми словами

### Чистка 100 ГБ у клиента — наш канал не сбросила

Админ удалил «файлы транзакций» на диске 1С. Это **не** наши пакеты и
**не** откат данных 1С. На Ubuntu по-прежнему `seq=2`: лог установщика и
`$metadata`. Полной выгрузки в витрине не было ни до чистки, ни после:
агент 1.0.2 пакет с данными шлёт только когда обойдёт все 9151 сущность.

Ночная работа **до нас не доехала**. Оборваться мог сам обход на Windows:

- процесс агента **жив** — продолжает список с того места, уже прочитанное
  ещё в оперативке;
- процесс **упал** — оперативка пустая, следующий запуск читает контур
  с первой сущности. Это и есть «всё заново». По релею нового запуска
  нет (нет повторного `GET /config` после 20:09 UTC) — либо тот же
  процесс ещё висит, либо демон не поднялся. Без Windows не различить.

### Как сделать, чтобы диск так не разрастался

Два разных диска. Путать их нельзя.

**Диск 1С (те ~100 ГБ).** Это **мы**. До нашей первой полной выгрузки
такого не было (слово владельца 13.08). Файлы лежат не в `C:\1c\packet`,
а у 1С/SQL — от этого вывод «не мы» делать нельзя.

Как именно наш обход раздул диск — см. документацию ниже: техжурнал
(гигабайты в час на наши CALL), `tempdb` от нашего `$orderby`/`COUNT`,
`.ldf` если обработчики на GET ещё и писали. Recovery model и чужой
`logcfg.xml` мы не трогаем (п. «контур не ломаем»), но нагрузку, которая
их крутит, даём мы. Выкинуть деловые сущности нельзя. Отсечь «служебное»
на чистом юните по снимку нельзя (§2.3).

Что меняем у себя в 1.1.2, чтобы **наш** обход так больше не делал:

1. **Выгрузить из оперативки** после каждой сущности (уже 1.1.1).
2. **Меньше лишних GET** (`$inlinecount`, `/$count`, второй `ProbeVersions`) —
   меньше тяжёлых `COUNT`/`ORDER BY`, меньше `tempdb` и меньше событий ТЖ.
3. **Слать пачками и после `applied` стирать свои файлы.** Упал 1С —
   не читаем заново уже отправленное (повторный полный обход снова
   раздует их диск).
4. Пауза между пачками — окно сжать журнал / `tempdb` у клиента.

Итого: чинить надо **наш** обход. Какой файл 1С вырос — уточняет, какую
часть обхода резать в первую очередь, не снимает с нас причину.

**Наш диск (`C:\1c\packet`).** У 1.0.2 ночью он почти пустой (чанки
ещё не писались). У 1.1.1 чанки уже на диске по ходу обхода, пакет
уезжает только в конце — очередь может вырасти на размер выгрузки.
У 1.1.2: пачка уехала → `applied` → каталог пакета удаляется. Это
«высылал пачками и удалял».

### Оперативка у 1.0.2 — да, это RAM, и она забивается

«Прогресс только в памяти» = **оперативная память процесса агента**,
не диск.

`[код]` 1.0.2 (`6b9712d`): все прочитанные сущности копятся в списке
`results` (строки + CSV) до одного `SendPackage` в конце. `FlushEntity`
нет. Пик RAM ≈ вся выгрузка с начала такта. ERP на 9151 сущность это
может быть **много гигабайт оперативки**. Кончилась RAM — процесс убит,
ночь сгорела, на диске пусто, до нас ничего не уехало. На `klient-1`
пик RAM не снимали (Windows недоступна) — забилась ли в ту ночь,
не знаем; по коду путь такой.

`[код]` 1.1.1: после каждой сущности `FlushEntity` — чанки на диск,
строки из RAM выбрасываются. Пик = **одна** сущность (крупный справочник
всё ещё может быть тяжёлым). Пакет по-прежнему уезжает только в конце
контура.

**Требование владельца 13.08: из оперативки выгружать.** У 1.0.2 этого нет.
У 1.1.1 уже есть (`FlushEntity`). 1.1.2 это **не откатывает**: после каждой
сущности чанки на диск, строки из RAM выбрасываются. Плюс пачки на провод
и удаление очереди после `applied`.

## Что говорит документация 1С и SQL `[док]` (поиск 13.08)

Живых файлов, которые удалил админ, по-прежнему нет. Ниже — не замер
на `klient-1`, а открытые источники: **какой файл** наш обход раздул.
Вину это не снимает: до выгрузки такого не было (владелец 13.08).
Цепочка «каждый GET пишет строку в `.ldf`» с доками не сходится — это
про механизм, не про «не мы».

### Что OData GET делает по документации 1С

- GET — чтение. Запись — POST/PATCH/PUT/DELETE
  ([Infostart, практика OData](https://infostart.ru/1c/articles/719982/),
  [официальная страница REST](https://v8.1c.ru/platforma/rest-interfeys/)).
- При чтении через REST платформа всё равно **проверяет права и зовёт
  обработчики событий** (кроме проверки заполнения)
  ([v8.1c.ru, REST интерфейс](https://v8.1c.ru/platforma/rest-interfeys/)).
  Обработчик *может* писать — это не то же самое, что «каждый GET пишет
  строку в базу».
- Журнал регистрации штатно фиксирует **изменение** данных
  (`_$Data$_.Update` / `New` / `Delete` / `Post`), не каждое чтение списка
  ([события ЖР](https://www.mista.ru/topic/743373)). ЖР лежит в файлах
  `1Cv8Log` (`.lgf`/`.lgp`/`.lgd`), это **не** `.ldf` SQL.

### Что реально разрастается на диске (ранг по документам)

| Кандидат | Как растёт | Тянет ли на ~100 ГБ за ночь | Наше отношение |
|---|---|---|---|
| **Техжурнал** (`logcfg.xml`) | Текстовые файлы. Нагруженный сервер, полный набор событий — **гигабайты в час** ([Хабр/OTUS](https://habr.com/ru/companies/otus/articles/1018102/), [bit-erp: «десятки и сотни гигабайт за час»](https://support.bit-erp.ru/article/ru/1368-kak-sobrat-logi-tehnologicheskogo-zhurnala.html)). Снимается удалением `logcfg.xml` | **Да, лучшее совпадение** с «съело 100 ГБ за ночь» как файлы | Установщик `logcfg.xml` **не кладёт**. Чужой ТЖ на машине клиента уже писал 10.08. Снимать — только слово владельца |
| **`tempdb` SQL** | Не журнал транзакций основной базы. Растёт от **одного** тяжёлого запроса (сортировка/хэш миллионов строк на диск). Живой разбор: 313 млн строк → терабайты ([Infostart](https://infostart.ru/1c/articles/1880561/)) | **Да**, если `$orderby` / `$inlinecount` / `/$count` по огромному регистру | Наш `FetchAll` как раз так делает. Убрать COUNT и не читать сущность дважды — меньше шансов. Это код агента |
| **`.ldf` основной базы** | Журнал транзакций SQL. Пишет **изменения**, не SELECT ([SQL Server](https://stackoverflow.com/questions/5516358/are-ad-hoc-read-only-queries-stored-in-sql-server-transaction-log)). В Full recovery без бэкапа лога файл не усекается и растёт от любой записи ([HelpF.pro](https://helpf.pro/faq8/view/624.html); типичные 100+ ГБ `.ldf` при базе 18 ГБ — [Хабр Q&A](https://qna.habr.com/q/1259458)) | Только если ночью **были записи**. Само чтение OData `.ldf` не наполняет | Чужой SQL. Бэкап лога / Simple recovery — руки клиента |
| **ЗамерыВремени (APDEX)** | Пишет регистр, если константа оценки включена; пакетами ([курсы-по-1С](https://xn----1-bedvffifm4g.xn--p1ai/news/2021-12-03-performance-evaluation/)) | Строки регистра, не 100 ГБ сами | В контуре `.7` регистр есть; гасить константу всей базы — запрет плана |
| **Ключи доступа RLS** | В БСП ключи **обновляются при записи** объекта, не при чтении списка ([Infostart](https://infostart.ru/1c/articles/1698732/)) | Не от нашего GET | Не наш рычаг |
| **Журнал регистрации** | Файлы, не `.ldf`. При уровне «Информация» — гигабайты за месяцы, скачки по 25 ГБ бывают ([mista](https://mista.ru/topic/817605)) | 100 ГБ за одну ночь — слабо, если только не путают с ТЖ | Не кладём, не настраиваем |
| **`sessionMaxAge="20"`** | Официально: **время простоя** сеанса в секундах, умолчание 20 ([документация 1ci.com](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.22_Administrator_Guide/Appendix_3._Description_and_location_of_internal_files/3.19._default.vrd/3.19.3.__ws_/)). Пока страницы OData идут без паузы 20 с, сеанс жив | На 100 ГБ не тянет | Поднять всё равно дёшево (HTTP-таймаут агента 600 с) |

Слово админа «файлы транзакций» в речи 1С-ников чаще значит `.ldf`. Без списка
удалённого это может быть и техжурнал, и `tempdb`. **Спросить админа, какой
путь чистил** — единственный способ закрыть причину, не рассуждением.

### Что в первой редакции плана было неверно или слишком смело

1. **П.4 §0 («каждый GET пишет в `.ldf`») помечен `[код]` — это ошибка маркировки,
   и поиск 13.08 её усиливает.** SELECT в журнал транзакций SQL не пишется.
   REST GET — чтение; права и обработчики платформа зовёт, но это не «каждый
   GET = строка в `.ldf`». 100 ГБ за ночь лучше стыкуется с техжурналом
   (гигабайты в час) и `tempdb` от тяжёлого `ORDER BY`/`COUNT`. Без пути,
   который чистил админ, источник не закрыт.
2. **§2.3 в заявленном виде невозможен.** 06.08 уже замерено: структурного признака
   «служебное» в `$metadata` нет (129 служебных с человеческим текстом, 57 деловых
   без). Три признака `serene_sync._service_skip`: `only_binary` в бутстрепе **уже
   применяется**; `search_entity_class` и `search_entity_force` — не из снимка, на
   чистом юните их нет. «Отсечь служебное по снимку теми же тремя признаками» —
   ложно. Хардкод имён (`ЗамерыВремени`) — запрет п. 9, сам план его повторяет.
3. **`sessionMaxAge=20` → 100 ГБ.** Поле в vrd есть; официально это **idle**
   (простой 20 с), не «убивать сеанс каждые 20 с пока идёт выгрузка»
   ([1ci.com](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Administrator_Guides/1C_Enterprise_8.3.22_Administrator_Guide/Appendix_3._Description_and_location_of_internal_files/3.19._default.vrd/3.19.3.__ws_/)).
   На гигабайты не тянет.
4. **«7,9 ГБ свободно»** относилось к диску очереди агента, не обязательно к тому
   же тому, что SQL. Вывод «очередь не 100 ГБ» всё равно верен: 1.0.2 чанки ещё
   не писал.
5. **IIS-HttpLogging.** В `IisOptional`. Если обязательные роли уже включены —
   optional **не** ставятся (`EnsureIis` return 0). Дописываются только вместе с
   недостающими обязательными. Не источник 100 ГБ; пункт плана — мелкий.
6. **Порции отправки не уменьшают `.ldf` сами.** Без бэкапа лога у клиента журнал
   SQL всё равно растёт. Порции дают чекпоинт (не терять часы RAM при «сервак
   встал») и окно для shrink. Это план в одном месте признаёт — держать явно.

### Что в плане остаётся верным как направление

- Не резать деловой контур и не прятать сущности в `/agent/config`.
- Чекпоинт / порции **отправки** лечат потерю работы 1.0.2 при падении 1С —
  независимо от природы 100 ГБ.
- Убрать `$inlinecount` **и** запасной `CountOf`, не звать повторный
  `ProbeVersions` (взять `DataVersion` из строк `FetchAll`) — меньше HTTP на
  ту же полноту. Это код, golden CSV не обязан меняться.
- Поднять `sessionMaxAge` — дёшево и по коду установщика; эффект на диск скромный.

`[замер]` релей `1c-gate.timpul.ru`: с IP клиента `79.134.209.186` последнее

`[код]` это не очередь агента и не файлы установщика:

| Куда не оно | Почему |
|---|---|

Цепочка чтения (это код, не гипотеза про диск):

1. Установщик, шаг 12: дефолтный состав OData — `all` (справочники, документы

   Разметки «служебное» (`search_entity_class` / `force`) ещё нет — слой

   с `$inlinecount=allpages`; если счётчика нет — ещё `/$count`; дальше
   страницы по 10 000) и, если есть `DataVersion`, ещё `ProbeVersions`
   (второй полный проход ключей — тоже с `$inlinecount`). В приёмник до
   конца обхода — ни одного запроса.

`[док]` откуда 100 ГБ — см. раздел «Что говорит документация». SELECT в
`.ldf` не пишется. Лучшие совпадения: техжурнал (гигабайты в час) и
`tempdb` от нашего `$orderby`/`COUNT`. `.ldf` — только если ночью были
записи плюс Full recovery без бэкапа лога. Путь, который чистил админ,
неизвестен.

`sessionMaxAge="20"` в `default.vrd` — `[код]` поле есть; официально это
**простой** сеанса, не «убивать каждые 20 с во время выгрузки».

Чистка «файлов транзакций» данные 1С и наш канал не откатывает (разбор
простыми словами — выше). Прогресс ночного обхода агент 1.0.2 держит
только в **оперативке процесса** (список `results` до `SendPackage`,
`FlushEntity` нет): если процесс жив и 1С снова отвечает — такт
продолжается; если упал — RAM сбросилась, полный обход с первой сущности.
По релею нового такта не видно.

## 1. Инвариант (не пересматривать без слова владельца)

- **Полнота.** Всё деловое, что есть в составе OData и доступно читателю,
  доезжает в витрину. Молчаливая потеря — дефект (п. 13). Не приехало —
  видно в `search_entity_skipped` / секции `skipped` пакета, с причиной.
- **Не «похудеть контуром». ** Нельзя решить диск, выкинув из первой
  выгрузки справочники, документы или деловые регистры. Резать контур
  порциями **со стороны сервера, пряча сущности из `/agent/config`**, —
  запрещённый путь: половина ERP может так и не попасть в список.
- **Служебное платформы** — как решение владельца 06.08, не шире: отсев
  по трём признакам (`only_binary` / `search_entity_class` / `force`),
  исключённое с видимой причиной. Регистр, который 1С дописывает **из‑за
  нашего же чтения** (`ЗамерыВремени`), конечного снимка не имеет: чем
  дольше читаем, тем он больше. Это не «их данные для ответа бота».
- **Без хардкода имён** (п. 9). Ни списка «не читать ЗамерыВремени»,
  ни порога «если ERP». Признак — из `$metadata` или из уже существующих
  таблиц разметки, не из словаря русской конфигурации.
- **Это мы.** До нашей выгрузки диск так не рос (владелец 13.08). Файлы
  не в нашей папке — не аргумент «не мы». Какой файл 1С/SQL — про механизм,
  не про вину.
- **Чужой контур не ломаем.** Recovery model SQL, константа «оценка
  производительности» на всю базу — не наши ручки. Нагрузку, которая их
  крутит, даём мы — её и режем.

`manifest_version` не меняется: пакет по-прежнему неделимая единица apply,
`seq` с разрывами уже норма контракта. Уточнение совместимое: первая
заливка может ехать несколькими `seq`, пока `full_done` ложь; apply и так
мержит сущность по `op=full`, не по `kind` пакета.

## 2. Два слоя правки (третий снят проверкой)

Ни один не выкидывает деловые данные. Слой «служебное из снимка» (§2.3)
проверкой 13.08 закрыт как неисполнимый — не пункт работ.

### 2.1 Установщик 1.2.3 — меньше служебных записей 1С на наши GET

| Что | Зачем | Где |
|---|---|---|
| `sessionMaxAge` в `default.vrd`: **20 → часы** (это **idle**, не «убивать сеанс каждые 20 с во время работы»; не короче `HttpTimeout` агента 600 с) | длинный простой между пачками не роняет сеанс; на 100 ГБ не лечит | `Steps.cs` шаблон vrd и запись `standardOdata` |
| Если в `bin\conf\logcfg.xml` лежит техжурнал — **отложить в `.bak-<дата>` и снять** | только по явному слову владельца: инвазивно, и что ТЖ = те 100 ГБ — не доказано (на машине клиента `logcfg.xml` уже писал 10.08, не наш файл) | новый шаг, до автозапуска агента |
| Не дописывать роль IIS `HttpLogging` даже когда ставим недостающие обязательные | сейчас optional едут только пакетом с missing required (`EnsureIis`); если IIS уже полный — HttpLogging и так не включается. Не источник 100 ГБ | `Steps.cs` `IisOptional` |

Не делать: менять SQL recovery, гасить оценку производительности всей базы,
резать состав OData с `all` на «только справочники».

### 2.2 Агент 1.1.2 — та же полнота, меньше GET и с чекпоинтом

**Меньше походов в 1С на ту же сущность (полнота та же):**

- На полном чтении не слать `$inlinecount=allpages` **и не звать запасной
  `CountOf` (`/$count`)**, если счётчика в ответе нет. Конец сущности —
  короткая страница; эта логика в `FetchAll` уже есть. `COUNT` миллионной
  таблицы ради числа в первом ответе не нужен. То же в `ProbeVersions`
  (там `$inlinecount` тоже стоит).
- После `FetchAll` не звать `ProbeVersions`, если `DataVersion` уже в
  прочитанных строках (`FetchAll` без `$select` — поле приезжает). Сейчас
  на `firstRun` первая проба пропускается, а вторая после полного чтения
  всё равно идёт: версионированная сущность сканируется дважды.
- **Усилитель нагрузки на умирающем сервере** (дополнение 13.08, проверка
  по коду `FetchAll`/`ProbeVersions`): любая ошибка страницы — включая
  таймаут 600 с — уменьшает страницу вчетверо и **перечитывает сущность
  с нуля** (до 4 заходов: 10000 → 2500 → 625 → 250), каждый заход — снова
  `COUNT`/`ORDER BY` с первой строки. Ровно в ночь, когда 1С встал, агент
  на каждой сущности мог до 4 раз повторять самые тяжёлые запросы —
  положительная обратная связь: серверу плохо → таймаут → перечитать →
  серверу хуже. В 1.1.2: при сетевых/5xx ошибках — пауза с нарастанием
  **до** повтора, и повтор со страницы меньшего размера без сброса уже
  прочитанного там, где ключ сортировки это позволяет; минимум — пауза.

**Первая заливка порциями, контур полный:**

- `/agent/config` по-прежнему отдаёт **весь** контур (9151, не «первые 500»).
- Прочитали пачку сущностей → пакет уехал (`seq+1`) → индекс на диске для
  этих сущностей → следующая пачка. Граница пачки — не имя базы, а наша
  машина: объём очереди / число чанков, те же пределы, что уже держат
  приёмник (размер чанка, карантин), плюс явный потолок «отправить, не
  дожидаясь конца контура».
- `full_done` ставится только когда каждая сущность контура либо имеет
  индекс (доехала и applied), либо стоит в `skipped` с причиной.
- После сбоя: нет индекса — читаем; индекс есть и версии совпали — не
  читаем заново. Это не пропуск, это «не делать одну работу дважды».
  `firstRun` перестаёт значить «FetchAll всего, игнорируя индекс».

После `applied` каталог пакета в очереди удаляется — свои файлы не живут
до конца ERP. Пауза между пакетами даёт окно сжать `.ldf` у клиента.
Без бэкапа лога у них рост журнала 1С всё равно будет; мы его не режем.
Чего не будет: 100 ГБ за одну ночь без точки возврата и повторный полный
обход (он раздует их диск второй раз) после «сервак встал».

Агент 1.1.1 уже сбрасывает чанки сущности на диск сразу (`FlushEntity`) —
оперативка больше не держит всю ERP. 1.1.2 добавляет **отправку** до конца
контура, **удаление** очереди после подтверждения и **возобновление** по
индексу.

### 2.3 Бутстреп контура — служебное до первого чтения

**Проверка 13.08: этот слой в заявленном виде сделать нельзя.**
`only_binary` из снимка бутстреп уже режет. `search_entity_class` и
`search_entity_force` в снимке `$metadata` не живут — их нет, пока слой
не собран. Структурного признака «служебное» в `$metadata` нет
(`[замер 06.08]`). Список имён вроде `ЗамерыВремени` — хардкод (п. 9).

Что остаётся без новой разметки и без хардкода: **не обещать отсев
служебного на чистом юните**. Служебные регистры в первом full будут,
пока владелец не даст другой механизм (например, классификатор по
именам EntitySet **до** чтения строк — это отдельное решение, сейчас
его нет). Слой 2.1/2.2 от этого не зависит.

Деловые сущности без «человеческого текста» по 06.08 **грузятся** —
это правило не переворачиваем.

## 3. Порядок работ

1. Агент: убрать лишние GET (`$inlinecount`, запасной `CountOf`, повторный
   `ProbeVersions`) — полнота та же, меньше походов в 1С. Проба: golden
   CSV не меняется.
2. Агент: порционная отправка + `full_done` только по покрытию контура.
   Проба: два пакета `op=full` подряд, после «сбоя» (удалить очередь,
   оставить индекс) второй прогон не перечитывает уже индексированное.
3. Установщик: `sessionMaxAge`; снятие чужого `logcfg.xml` — только если
   владелец явно согласен (инвазивно, источник 100 ГБ не доказан); не
   дописывать `IIS-HttpLogging` к missing required. Проба на стенде: vrd
   содержит новое значение.
4. `packet_config`: **не делать** «служебное из снимка» — см. §2.3.
   Открытый вопрос владельцу, если служебное всё же надо не читать
   первым full.
5. Сборка на стенде (`build.cmd`), golden, живой смоук. Дисты — по слову
   владельца, комплекты (токен/серт) не трогать (`refresh-dist.sh` /
   `upload-dist.sh`).

`klient-1` на 1.0.2 этим не лечится, пока нет захода на Windows. Живой
такт не останавливаем из этого плана.

## 4. Приёмка (что считается сделанным)

- Golden-проба CSV агента — байт-в-байт как эталон `poc_load_entity`
  (порции и отказ от `$inlinecount` формат не меняют).
- Контур тестовой базы после первой заливки: каждая сущность либо таблица
  в витрине, либо строка в `search_entity_skipped` с причиной. Нет третьего
  состояния «просто не читали».
- `default.vrd` — `sessionMaxAge` не 20. Снятие `logcfg.xml` — только если
  слой 2.1 это включил по слову владельца.
- `test_packet_config` / `test_packet_server` / `test_packet_apply` зелёные.
  Бутстреп по-прежнему: все наборы минус `only_binary` (как сейчас).
- Живой замер «`.ldf` / техжурнал / `1Cv8Log` — что именно выросло» — на
  стенде с SQL, не рассуждением. Пока замера нет, причина 100 ГБ не закрыта;
  слои 2.1/2.2 от этого не ждут: меньше GET и чекпоинт полезны сами по себе.
