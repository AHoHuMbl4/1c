# Дельта-синк: свежие данные без изменений в 1С

Система обновления витрины **раз в 10 минут** вместо ночной полной перезагрузки. Инвариант
«1С только читаем» сохраняется полностью — никаких вебхуков, расширений и планов обмена.

Решение владельца (2026-07-25): такт **10 минут**. Все числа ниже — замеры на стенде, не оценки.

---

## 1. Как узнаём, что изменилось

У каждого **объекта** 1С есть служебное поле `DataVersion` — платформа меняет его при каждой записи.
Штатный OData отдаёт его проекцией, без самих данных:

```
GET /Catalog_X?$select=Ref_Key,DataVersion&$format=json
```

Диф пар `(Ref_Key, DataVersion)` против сохранённого состояния даёт **вставки, изменения и удаления**.

### ✅ Проверено живой записью (2026-07-25, с разрешения владельца)

| Шаг | Имя элемента | `DataVersion` |
|---|---|---|
| исходное | Прочие затраты | `AAAAAQAAAAs=` |
| **запись БЕЗ изменений** | Прочие затраты | `AAAABQAAAAA=` ← изменилась |
| изменили имя | Прочие затраты ZZТЕСТ | `AAAABgAAAAA=` |
| вернули как было | Прочие затраты | `AAAABwAAAAA=` |

**Механизм работает.** Значение из COM (`ВерсияДанных`) и из OData (`DataVersion`) — одно и то же поле.

⚠ Версия меняется **от самого факта записи**, даже если содержимое не изменилось. Регламентные задания
1С, перезаписывающие объекты, дадут «ложные» изменения — лишние дотягивания, но **не неверные данные**.

## 2. 🌍 Язык и имена: что сломается на чужой базе, а что нет

Главный вопрос: **мы заранее не знаем ни конфигурацию, ни язык, ни имена.** Разобрано по фактам —
источник: `$metadata` нашей базы (19.7 МБ, **4585 типов сущностей, все имена кириллические**).

| Элемент | Зависит от языка/имён? | Доказательство |
|---|---|---|
| **Имена сущностей** (`Catalog_КлассификаторБанков`) | Да — но мы их **не знаем и не хардкодим**: `serene_select.py` берёт список из ЖИВОГО OData | 4585 имён обнаружены автоматически |
| **Стандартные поля** (`Ref_Key`, `DataVersion`, `DeletionMark`, `IsFolder`, `Description`, `Code`, `Predefined`) | **НЕТ. Всегда английские и фиксированные** — даже в полностью русской конфигурации | в `$metadata` все 4585 типов именуют их одинаково |
| **Пользовательские реквизиты** (`Город`, `ИНН`, `СВИФТБИК`) | Да — но мы их не знаем и не хардкодим: берём интроспекцией схемы | витрина держит кириллические колонки и работает |
| **Кириллица в URL OData** | Нет проблем | все запросы к `Catalog_СтатьиЗатрат` проходят через шлюз |
| **Локаль словаря полнотекста** | **НЕТ** — проверено замером | `ru_RU`, `en_US` и нейтральная `C` дали **одинаковые 37**, и заглавными, и строчными |
| **COM-квирки с кириллицей** | Да — но это **только разовый `setup-1c-odata.exe`**, где уже есть RU/EN-фолбэк | в дельта-синке COM не используется вообще |

### Вывод
Дельта-синк опирается **только на платформенный контракт** (`Ref_Key`, `DataVersion`) — ровно как уже
опирается загрузчик (`$orderby=Ref_Key`, `IsFolder`). Это не хардкод, а контракт платформы, одинаковый
на любом языке. Всё, что зависит от конкретной базы, добывается из неё же в рантайме.

### Про полнотекст отдельно
Словарь создаём с `stemming = false` — тогда поведение язык-нейтрально (подтверждено таблицей выше:
локаль не влияет). Стемминг включать нельзя: он language-specific и нарушил бы правило «без языкового
хардкода» — то самое, из-за которого мы убирали `RU_STOP`/`_stem` из резолвера.

## 3. ⚠ Ограничение: `DataVersion` есть не у всего

Из `$metadata` (4585 типов):

| Поле | У скольких типов |
|---|---|
| `Ref_Key` | 2969 (64%) |
| **`DataVersion`** | **1129 (24%)** |
| `DeletionMark` | 1129 (24%) |
| `Description` | 666 (14%) |
| `IsFolder` | 71 (1%) |

`DataVersion` есть у **объектов** (справочники, документы, планы счетов) и **нет у регистров**
(накопления/сведений/бухгалтерии) и табличных частей — у них другая природа (наборы записей).

**Что это значит:** дельта по `DataVersion` покрывает справочники и документы — то есть весь наш
нынешний состав витрины (22 сущности, все объекты). Для **регистров** нужен отдельный подход:
- регистры, подчинённые регистратору, меняются вместе со своим документом → отслеживать документы
  и перечитывать движения изменившихся;
- независимые регистры сведений — перечитывать окном по периоду либо целиком (они обычно невелики).

Это станет актуально на Фазе 7, когда появятся реальные обороты.

## 4. Алгоритм

```
каждые 10 минут:
  1. по каждой сущности из serene-entities.txt:
        GET ?$select=Ref_Key,DataVersion         (3.7 с на все 22 сущности)
  2. сравнить с сохранённым состоянием:
        новые Ref_Key            -> вставка
        изменившийся DataVersion -> обновление
        пропавшие Ref_Key        -> удаление
  3. если изменений НЕТ  -> выход (~4 с)          <- типовой случай
  4. если есть:
        дотянуть ТОЛЬКО изменившиеся объекты ($filter по Ref_Key)
        upsert в витрину
        эмбеддить ТОЛЬКО новые значения-измерения
        (при схеме «данные в Postgres» — пересобрать индекс: 0.4 с на 50 тыс.)
```

Состояние `(сущность, Ref_Key, DataVersion)` хранится рядом с витриной — это служебная таблица,
недоступная отчётной роли (как `resolver_index`).

## 5. Что меняется по сравнению с сегодняшним синком

| | Сейчас | Станет |
|---|---|---|
| Такт | ночь, 03:40 | **каждые 10 минут** |
| Обнаружение изменений | нет | проекция `(Ref_Key, DataVersion)` |
| Типовой прогон | **3 мин 31 с** (замер) | **~4 с** (только опрос) |
| Загрузка | все строки всех сущностей | только изменившиеся объекты |
| Резолвер | пересборка целиком, 624 значения | эмбеддинг только новых значений |
| Нагрузка на 1С | всплеск раз в сутки | 3.7 с раз в 10 минут = **0.6% времени** |

Сквозная задержка «ввели в 1С → видно боту»: **до 10 минут** + секунды на дельту.

## 6. Побочная правка: резолвер эмбеддит служебное

В журнале синка видно:
```
catalog_статьизатрат.DataVersion: 13 значений          <- штампы версий AAAAAQAAAAs=
catalog_банки.Страна_navigationLinkUrl: 1 значений     <- URL-ссылки
```
Это трата эмбеддингов и шум в семантическом поиске. Отсекать **без хардкода** — по структуре значения
(содержит ли буквы какого-либо алфавита; не GUID/base64/URL по форме), а не по именам колонок.

## 7. Открытые вопросы

1. **Регистры** (§3) — отдельная стратегия, актуальна на Фазе 7.
2. **Масштаб проекции:** ~88 байт на объект. Для сущности в 1 млн строк это ~90 МБ на скан; при такте
   10 минут приемлемо, но для очень больших документов имеет смысл окно по дате.
3. **Ложные срабатывания** от регламентных заданий 1С (§1) — при необходимости гасить сравнением
   содержимого после дотягивания.
