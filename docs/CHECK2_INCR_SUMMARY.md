# CHECK2_INCR_SUMMARY — сведение трёх независимых проверок

Источники: `CHECK2_INCR_1.md` = **[1]**, `CHECK2_INCR_2.md` = **[2]**, `CHECK2_INCR_3.md` = **[3]**.
Каждый агент делал два прохода, друг друга не видел. Все замеры — живой движок
**PostgreSQL 18.3 (SereneDB 26.07.3)**, `127.0.0.1:7890`, только `SELECT` и каталожные функции;
DDL/DML не выполнял ни один из троих (это ограничивает выводы, см. раздел 5).

Пометки сохранены: **[замер]** — время на живом движке, **[код]** — файл:строка / тест,
**[вывод]** — дословный вывод команды, **[рассуждение]** — вывод без замера.
Атрибуция пересчитана по текстам, а не по памяти.

## 1. Ответ одной страницей

**Что делать вместо нынешней фазы.** Всю фазу «прочитать 97 965 строк в Python → склеить `doc`/`refs`
→ SHA1 → залить staging → сравнить» заменить **одним SQL-запросом в одном соединении**:

1. текст запроса (`UNION ALL` по всем таблицам витрины) **генерирует сам движок** одним `string_agg`
   по `duckdb_tables()`/`duckdb_columns()` — [1] §2.3 [замер 0.27 с], [2] §2, [3] §2. Python не обходит
   таблицы; в psql это выполняется в один процесс через `\gexec` — [1] Д2 [вывод].
2. строка `doc` собирается в SQL без перечисления колонок — три разных механизма, см. раздел 3;
   [1] §2.1, [2] §2, [3] §2 (каждый нашёл свой).
3. `refs` (разрешённые имена ссылок) — **обычный `LEFT JOIN` на карту `Ref_Key → Description`**,
   собранную из базы в том же запросе: [1] §7.2-7.3 [замер 141 мс на карту], [2] §7 [вывод],
   [3] §7 + §2.3 [замер 101,7 мс на карту].
4. отпечаток — `sha1()` прямо в SQL, данные наружу не идут: [1] §3, [2] §3, [3] §3.
5. применение и список изменившихся ключей — один
   `MERGE INTO search_corpus USING (<этот запрос>) … WHEN NOT MATCHED BY SOURCE THEN DELETE
   RETURNING merge_action, t.src_table, t.row_key`: [1] §4.3, [2] §4, [3] §4 (все трое, но **никто не
   исполнил** — DML был под запретом).
6. поверх — «ранний выход»: контрольные суммы таблиц за ~0,7–0,9 с, и если ничего не менялось, такт
   на этом кончается: [1] Д1 [замер 0,918 с], [2] §2.4 [замер 0,711 с]. ([3] этого не предлагал.)

**Требование про переименование не только сохраняется, но усиливается** — все трое сходятся
независимо: имя контрагента приходит из JOIN на текущее содержимое справочника, поэтому оно
актуально по построению, а не «если отпечаток изменился»: [1] §7.3, [2] §3/§7, [3] §7.

**Сколько выиграем (только измеренное).**

| фаза | сейчас | штатно |
|---|---|---|
| `count(*)` по таблицам | 233 процесса `psql`; [2] замерил тот же цикл целиком — **11,9 с** | один сгенерированный `UNION ALL`: **0,266 с** / 235 табл. [1], **0,214 с** / 305 табл. [3] |
| состав колонок | 233 процесса | один `duckdb_columns()`, 4002 строки: **0,041 с** [2]; подтверждено [1] и [3] [вывод] |
| чтение + `doc`/`refs` + SHA1 | ~258 с (86 % такта), ~233 процесса | **4,4 с** [1] / **18,1 с** [2] / **4,2 с** = 1,14+2,93+0,10 [3] — расхождение разобрано в разделе 4 |
| staging + ~490 `INSERT` | ~490 процессов | 0 — строки не покидают движок [1] §5, [2] §5, [3] §5 |
| поиск изменившихся | 233 процесса | 0 доп. запросов — `MERGE … RETURNING` [1,2,3] |
| **такт при нуле изменений** | ~258 с | **0,85 с** [2] §2.4 / **0,92 с** [1] Д1 |

Итог по числу процессов: **~1 190 → 1–2** (все трое: [1] «~4 процесса», [2] «≈2», [3] «≈1 190 раз по
числу процессов»). Требование «свежесть ≤ 20 минут» выполняется с запасом в любом из вариантов.

**Чего этот ответ НЕ покрывает:** стоимость самого `MERGE` на 97 965 строк — не измерил никто
([1] п.2, [2] п.1, [3] п.1 в «не выяснил»); стоимость эмбеддинга изменившихся строк остаётся вне SQL
(`ai_embed` не годится — [1] Д7: в сборке есть, но без параметра `dimensions`, наш провайдер отдаёт
1024, индекс на 1536).

**Отношение к TARGET.md п.20 (запрет своих скриптов к базе).** Предложенное решение убирает из Python
всю работу с данными: обход таблиц, склейку, хеширование, батчи. Остаётся «взять текст, сгенерированный
движком, и отдать его движку» — с `\gexec` это один `psql -f` [1] Д2. Считать ли и это «своим скриптом
для работы с базой» — **решение владельца, ни один из трёх агентов такого вывода не делал** [рассуждение
сводки].

## 2. Закрытые вопросы

Здесь только то, что подтвердилось независимо более чем одним агентом (или подтверждено кодом движка).

### 2.1. Путь «корпус = VIEW + индекс на VIEW» — ЗАКРЫТ, отрицательно

Это главный вопрос, и он закрыт тремя независимыми линиями доказательств.

**Индекс над VIEW существует и штатен** — [1] §1.1 (`examples/demo6/bootstrap.sql`, 9 тестов
`inverted_index_view*`), [2] §1 (тот же demo6 + `cookbook/search/indexing-views.test`),
[3] §1 (`inverted_index_view.test:30-36,121-125`). Все трое.

**Но он СНИМОК на момент `CREATE INDEX`** — три РАЗНЫХ доказательства:
- [2] и [3] — прямой комментарий в исходнике: `server/connector/duckdb_catalog.cpp:874`
  `// View-backed indexes are STATIC -- captured at CREATE INDEX, no DML refresh.`
  [2] добавляет второе место: `server/search/wal_recovery.cpp:112-119`.
- [2] и [3] — тест-«гвоздь» `inverted_index_view_include.test:189-207`:
  `# … This is the documented behaviour today; pinning it so it doesn't silently change.`
- [1] — поведенческий тест `inverted_index_view_attached.test:137-152`: источник видит 5 строк,
  индекс — по-прежнему 2 постинга; удалённая строка материализуется как NULL (строки 158-160).
- [3] — ещё два подтверждения: `inverted_index_view.test:110`, `inverted_index_partial.test:381`
  («Partial indexes on views are static»), плюс формулировка контракта `the index pins what it indexed`
  ([1] и [3] цитируют её независимо, из разных файлов).

**`VACUUM (REFRESH_*)` это не чинит** — [1] §1.3 (`duckdb_vacuum_function.cpp:431`:
`search->VacuumRefresh(); // commit pending inserts + reclaim files`), [2] §1 (обход целей идёт
**по таблицам**, `duckdb_vacuum_function.cpp:264-290`, индекс над вьюхой в обход вообще не попадает),
[3] §1 (`vacuum_global.test:41` «REFRESH_ALL publishes pending writes»). Все трое, разными путями.
Ловушка, которую стоит знать: в `pg_class.reloptions` есть `refresh_interval=1000` — это интервал
видимости уже закоммиченных сегментов iresearch, а не перечитывание источника ([1] Д5,
`server/catalog/persistence/index.h:48` → `server/search/search_table.cpp:115`). Только [1].

**Обходных путей нет:** MATERIALIZED VIEW в движке отсутствует — [1] Д4 (`grep "CREATE MATERIALIZED"`
по `server/` и `tests/` пусто), [2] §2.1 (ноль совпадений по всем 1653 тестам), [3] §2.1(д)
(в бинарнике только `relkind='m'` и `Cannot drop MATERIALIZED VIEW yet`). Все трое.
Штатного «перестроить индекс над VIEW по источнику» нет, остаётся `DROP INDEX`+`CREATE INDEX`
— [1] §1.4 (официальный кукбук `indexing-external-data.test` делает ровно это), [1] Д5 (`REINDEX`
только в аварийном контексте).

**Дополнительные гвозди в этот путь:**
- у generic-вьюхи (UNION ALL/JOIN) читать неиндексированные колонки нельзя — всё нужное обязано быть
  в `INCLUDE`: [1] §1.5 + Д6, [2] §1 (`inverted_index_store_pk.test:82`), [3] §1 + §2.2(к). Все трое.
- `postgres_scan` в fast-path НЕ входит (`view_fast_path.cpp:140` — `// TODO: … postgres_scan`), то есть
  для целевой архитектуры «PG на Windows + attach» ограничение остаётся: [1] Д6, [3] §2.2(к). Двое.
- во вьюхе негде взять `emb FLOAT[1536]` — [2] §1 прямо, [1] §1.5 (только через `LEFT JOIN` на кэш).

**Формулировка закрытия:** корпус остаётся **таблицей** с инвертированным индексом на ней. Это
подтверждено и с положительной стороны: [1] Д8 цитирует `examples/demo2/README.md` — «the index updates
transactionally with the table … the inverted index is just another secondary index»; [3] §«что уже
штатно» и [1] §«что трогать не надо» приходят к тому же. Единственный остающийся аргумент «за» —
неизмеренная стоимость `DROP`+`CREATE` каждый такт (см. раздел 4.4 и 5).

### 2.2. Штатного CDC нет — закрыто

Ни журнала изменений, ни changefeed, ни версии строки. [1] §4.1 (полный список 34 функций `duckdb_*`,

Побочно: `xmin`/`ctid` к строкам не привязаны — [1] §4.1, [2] §4, [3] §4 [вывод]
`ERROR: Referenced column "xmin" not found in FROM clause!`. Все трое.
Заглушки, на которые нельзя ловиться: `pg_stat_user_tables` в сборке есть, но отдаёт нули даже для

### 2.3. `rowid` не годится как детектор изменений — закрыто

Стабилен при in-place UPDATE (`merge_returning_rowid.test`) — [1] §4.2, [2] §4, [3] §4. Все трое,
и все трое делают один вывод: это ключ строки, а не версия. [1] добавляет обратную сторону:
при обновлении индексированной или LIST-колонки идёт delete+insert и **rowid двигается**
(`upsert_returning_rowid.test:4-5`) — только [1].

### 2.4. `MERGE … RETURNING merge_action` — механизм есть, значение известно, исполнение НЕ проверено

Все трое цитируют один и тот же docs-тест `merge_into/index.test` (~строки 104-145) и сходятся:
возвращается `VARCHAR` со значениями `INSERT`/`UPDATE`/`DELETE` плюс любые колонки, включая ветку
`WHEN NOT MATCHED BY SOURCE THEN DELETE` — то есть gone-очистка встроена в тот же оператор.
Наличие в 26.07.3: [2] и [3] независимо — строки бинарника `Unsupported merge action for RETURNING`,
`MergeActionType`, `MergeActionCondition`, `WHEN NOT MATCHED BY SOURCE`; [1] — иначе, через
`EXPLAIN MERGE … RETURNING merge_action, t.row_key` на нашей базе: план строится, колонка признаётся.
**Ни один не исполнил MERGE** — все трое ставят это первым пунктом «не выяснил».
Запрет `MERGE` на search-backed таблицах нас не касается (наш `search_corpus` — обычная таблица):
[1] §4.4 (`duckdb_catalog.cpp:824-838`), [3] §4 (строка бинарника + `search_table_scan_10k.test:202`).
Двое. Согласованность индекса при merge оговорена тестом `dml/merge.test:2` — [1] и [3].
Ограничение, которое нашёл только [2]: `RETURNING is not implemented for Postgres yet` — для
ATTACH-нутых PG-таблиц `RETURNING` не работает; для нативного корпуса неважно, **но важно для целевой
архитектуры «PG на Windows + attach»**.

### 2.5. Массовая вставка — 490 `INSERT` не нужны вовсе

`INSERT … SELECT` / `MERGE … USING (<подзапрос>)` внутри базы — все трое ([1] §5, [2] §5, [3] §5),

### 2.6. Каталог одним запросом — закрыто

`duckdb_columns()` без фильтра отдаёт все 4002 колонки базы: [1] §6.1, [2] §6 [замер 0,041 с],

## 3. Как это выглядит в SQL

### 3.1. Что НЕ работает (проверено вживую, чтобы не повторяли)

- `concat_ws(' | ', *)` → `ERROR: STAR expression is only allowed as the root element…` — [1] §2.2, [2] §2.
- `concat_ws(' | ', COLUMNS(*))` **размножает выражение по колонкам**, а не склеивает: 14 отдельных
  колонок вместо одной строки — [1] §2.2 [вывод], [2] §2 [вывод]. Оба на этом основании отвергли путь
  `COLUMNS(*)` целиком — **и это оказалось преждевременно**, см. 3.2(в).
- `query_table(t.table_name)` в LATERAL → `ERROR: … only supports literals as parameters` — [2] §2, [3] §2.
- `query((SELECT '…'))` → `ERROR: Table function cannot contain subqueries` — [2] §7, [3] §2.2(е).
  Динамического `EXECUTE` в движке нет — [1] §2.3. То есть имя таблицы обязано быть литералом, и
  генерация текста `UNION ALL` неизбежна; но её делает движок, а не Python — все трое.
- `json_extract_string(j, '$.a')` и `'$."'||k||'"'` возвращают **пусто**, рабочая форма — голое имя ключа
  `json_extract_string(j, 'a')` — [3] §2 [вывод] и [2] §2.7 [вывод]. Двое, независимо.
- `json_each(r.jj)` рядом с источником в `FROM` → `Failed to bind column reference "jj"`, нужен явный
  `LATERAL` — только [1] §7.3.
- `btrim` в сборке нет (`Did you mean "trim"?`); `struct_values(t)::VARCHAR[]` падает
  (`Unimplemented type for cast`) — [1] §7.3 и [2] §2 соответственно.

### 3.2. Три механизма сборки строки — сравнение

**(а) `to_json` + `json_each` в `LATERAL` + `string_agg` — нашёл [1]** (§2.1, §7.3):
```sql
SELECT r.row_key, string_agg(x.key || ': ' || COALESCE(m.nm, trim(x.value::VARCHAR,'"')), ' | ' ORDER BY x.key)
FROM rows_j r, LATERAL (SELECT key, value FROM json_each(r.jj)) x
LEFT JOIN refmap m ON m.k = trim(x.value::VARCHAR,'"') AND x.key LIKE '%\_Key' ESCAPE '\'
GROUP BY r.row_key;
```

**(б) `to_json` + `json_keys` + `list_transform` / `unnest … WITH ORDINALITY` — нашли [2] и [3]**
(независимо; [2] §2, [3] §2):
```sql
SELECT array_to_string(list_transform(json_keys(j), k -> k || ': ' || coalesce(json_extract_string(j,k),'')), ' | ')
FROM (SELECT to_json(t) AS j FROM <t> t) s;
```
[2] показал парную форму через `unnest(json_keys(j)) WITH ORDINALITY AS u(k,i)` — она нужна, когда
значения надо ДЖОЙНИТЬ (резолвинг ссылок), и сохраняет исходный порядок через `ORDER BY i`.

**(в) `UNPIVOT` + `COLUMNS(*)::VARCHAR` — нашёл только [3]** (§2.1(а)), из кукбука движка
`cookbook/sql_features/query_and_query_table_functions.test:38-73`:
```sql
SELECT col, val FROM (SELECT COLUMNS(*)::VARCHAR FROM <t>) UNPIVOT (val FOR col IN (COLUMNS(*)));
```
Явный каст обязателен, иначе `ERROR: Cannot unpivot columns of types VARCHAR and BOOLEAN`.
Там же `alias(COLUMNS(*))` даёт имена колонок — то, чего, по мнению [1] и [2], у `COLUMNS(*)` нет.

**Сравнение (все цифры — со ссылкой на агента):**

| критерий | (а) `json_each` [1] | (б) `json_keys`+`list_transform` [2],[3] | (в) `UNPIVOT` [3] |
|---|---|---|---|
| 23 878 строк, `doc` | 900 мс; `doc`+`sha1` **815 мс** [1] | **1 199 мс** [3] | **181 мс** без `ORDER BY`; 401 мс с ним [3] |
| вся база, `doc`+отпечаток | **4,4 с** — но это ВМЕСТЕ с `refs` и с `ORDER BY` [1] | **1,64 с** без `refs` [3]; **18,1 с** с `refs` и `ORDER BY` [2] | **1,139 с** без `refs`, без `ORDER BY`; **5,59 с** с `ORDER BY` [3] |
| зависимость от порядка колонок | порядок ключей JSON; [1] явно сортирует `ORDER BY x.key` — от каталога не зависит | [2] сохраняет исходный порядок через `WITH ORDINALITY`+`ORDER BY i`; [3] сортирует по имени | порядок = список `IN`, раскрываемый из порядка колонок каталога; **тестом движка не зафиксирован** [3] «не выяснил» п.3 |
| BOOLEAN | `false` [1] [вывод] | `false` [2] [вывод] | `false` [3] [вывод] |
| NULL | не описано [1] | `coalesce(...,'')` → пустая строка, ключ остаётся [3] [вывод] | строка с NULL **отбрасывается** по умолчанию (= наша семантика «пустой реквизит в текст не идёт»), либо `UNPIVOT INCLUDE NULLS` [3] [вывод] |
| устойчивость | значения приходят закавыченными, нужен `trim(…,'"')` [1]; `LATERAL` обязателен | безопасно только потому, что в витрине нет колонок с точками/кавычками/пробелами — проверено [2] §2.7 [вывод] `0` | требует явного каста; чувствителен к `ALTER TABLE ADD COLUMN` (отпечатки поедут — это правильно, но разом) [3] |

**Что брать.** Механизм (б) в форме [2] — **отбросить**: он же дал 18,1 с, и [3] независимо измерил
его как более медленный, чем (в) (1,64 против 1,14). Между (а) и (в) **данных для выбора не хватает**:
единственное сравнение «яблоки к яблокам» на всей базе даёт 4,4 с [1] против 4,2 с (1,14+2,93+0,10) [3]
— разница в пределах разброса, при этом (а) считает `sha1`, а (в) в замере считал `md5`, у (в) не
подтверждена детерминированность порядка колонок, а у (а) не измерена сборка `refs` отдельно от `doc`.
**Решается одним A/B-замером** на ОДНОЙ и той же формуле `doc` (см. раздел 6, шаг 2).
Заметка по атрибуции: `to_json` для детекции ссылочных колонок по форме значения удобнее в любом случае
— так делает [3] даже в варианте (в) (§2.4 п.1).

### 3.3. Разрешение ссылок — три разных критерия «это ссылка»

- **по имени колонки**: `kv.k LIKE '%\_Key'` — [1] §7.3. Диагностика: на 50 строках
  `pairs=3564, key_cols=1260, resolved=318`.
- **по значению, без фильтра колонок**: `LEFT JOIN refmap ON m.g = kv.v` — [2] §3/§7. Предупреждение
  самого [2]: в `HAVING` карты надо добавить «объявленный ключ = ровно `Ref_Key`», иначе в карту полезут
  табличные части — «тот же дефект, что уже ловили в Python-коде».
- **по форме значения (regexp GUID) + исключение нулевого GUID** — [3] §7. 17 ссылочных колонок нашлись
  сами за 3,6 мс; полное разрешение на документ-таблице — 62,9 мс; по всей базе — 2 927 мс,
  63 524 строки с непустыми `refs` на 186 таблицах [замер].

Все три формы дают одно и то же свойство и все трое явно это отмечают: **переименование меняет текст
корпуса на следующем же такте, потому что это результат JOIN, а не сохранённая строка**.
Вариант «джойнить `refmap` не при сборке, а на выдаче» (`FROM search_idx JOIN refmap …`,
`cookbook/search/search-with-joins.test:47-58`) нашёл только [3] §2.2(ж) — и сам же его ограничил:
это чинит только **отображение**, а не находимость, потому что термы индекса и эмбеддинг строятся по
сохранённому тексту. То есть это дополнение, а не замена.

### 3.4. Ранний выход по контрольным суммам — [1] и [2], независимо

```sql
SELECT '<t>' AS t, count(*) AS n, bit_xor(hash(to_json(x)::VARCHAR)) AS ck,
       sum(hash(to_json(x)::VARCHAR)::HUGEINT) AS s FROM "<t>" x  UNION ALL …
```
[1] Д1: `count + sum(hash)` по 233 таблицам — **917,5 мс** [замер].
[2] §2.4: `count + bit_xor` по 226 таблицам — **687 мс**; `count + bit_xor + sum` — **711 мс** [замер].
Оба помечают это как **нашу конструкцию поверх штатных агрегатов**, штатной контрольной суммы таблицы
в движке нет; оба независимо предупреждают, что `bit_xor` гасит пары одинаковых значений, а `sum`
теоретически компенсируем.
Оба независимо вывели одно и то же правило, сохраняющее требование про переименования:
**если изменилась хотя бы одна таблица, участвующая в карте ссылок → пересчитывать по всей базе**
(дайджест самого документа при переименовании не меняется); иначе — только по изменившимся таблицам
([2] замерил такую точечную пересборку: 0,381 с на таблице 11 688 строк).
[3] этого механизма не предлагал — значит у него нет и независимого подтверждения цифр.

### 3.5. Найденное и отклонённое (по одному агенту каждое, но полезно знать)

- **Генерируемая колонка** `doc_hash TEXT GENERATED ALWAYS AS (sha1(doc||chr(0)||refs)) STORED` —
  [2] §2.2 (`cookbook/search/computed-values.test:6`, `dml/merge.test:112`, строки бинарника).
  Ограничение оттуда же: `Lambda functions are currently not supported in generated columns` — сборку
  `doc` через `list_transform(… k -> …)` в генерируемую колонку положить нельзя, только хеш от готовых.
- **Индекс по выражению** `USING inverted(id, (first||' '||last))` с backfill — [2] §2.3. Нашу задачу
  не решает: `cannot use subquery in index expressions`, значит «Контрагент: ООО Ромашка» выражением
  не собрать. [2] честно называет это «случаем, где штатного механизма ровно под нашу задачу нет».
- **`CREATE TABLE … WITH (storage='search')`** — [2] §2.5. Не подходит: отложенная видимость записей и
  `RejectIfSearchTable` в `BindCreateIndex` — свой инвертированный индекс со словарями не построить.
- **ES-путь `es_bulk`/`es_refresh`** — [2] §2.6. Отклонён: отдельный мир схемы `es`, без наших словарей,
  `INCLUDE` и `MERGE`.
- **`CREATE MACRO … AS TABLE` + `query(…)`** как способ убрать генерацию 76 КБ текста из Python —
  [3] §2.2(е). Не проверено (DDL).
- **`postgres_query(dsn, sql)`** есть в каталоге — [3] §2.2(л). Даёт третий вариант для архитектуры
  «PG на Windows»: считать отпечатки на стороне Windows и гнать по сети только пары (ключ, хеш).
  На реальном соединении не проверено.
- **`ai_embed` прямо в `INSERT … SELECT`** (`examples/demo5/bootstrap.sql:5-37`) — [1] Д7. Заблокирован
  размерностью: в сборке `ai_embed(VARCHAR,VARCHAR,VARCHAR)`, параметра `dimensions` нет.
- **`VACUUM (REFRESH_INDEX) search_idx` сохранить** — [3] §2.2(з): 30 из 34 рецептов кукбука вызывают
  `REFRESH_*` сразу после записи; у нас это уже сделано (`serene_search_build.py:915`) и при укрупнении
  транзакции терять нельзя.

## 4. Расхождения

### 4.1. Время сборки `doc`+отпечатка по всей базе: 4,4 с [1] / 18,1 с [2] / 1,139 с [3]

**Мерили РАЗНОЕ.** Разбор по трём осям:

| | [1] = 4,418 с | [2] = 18,1 с | [3] = 1,139 с |
|---|---|---|---|
| строк | 96 931 | 97 965 | 97 965 |
| таблиц | 233 (исключены таблицы с векторной колонкой и `search%`) | 233 | 226 |
| механизм | `to_json`+`json_each`+`string_agg` | `to_json`+`unnest(json_keys)` + `json_extract_string` на каждый ключ | `UNPIVOT`+`COLUMNS(*)::VARCHAR` |
| резолвинг ссылок включён | **да**, `LEFT JOIN refmap` внутри | **да**, `LEFT JOIN` карты внутри | **нет** — отдельно 2,93 с |
| `ORDER BY` в `string_agg` | да (`ORDER BY k`) | да (`ORDER BY i`) | **нет** |
| хеш | `sha1` | `sha1` | `md5` |
| выгрузка наружу | нет (агрегат) | нет (агрегат); с выгрузкой — 20,4 с | нет (агрегат) |

**Сопоставимые величины:** «весь тяжёлый такт, включая `refs`» — **4,4 с [1]** против
**4,2 с [3]** (1,139 `doc` + 2,927 `refs` + 0,102 `refmap`). Расхождение практически отсутствует.
«`doc` без `refs`, без сортировки» — 1,139 с [3] против 1,644 с [3] у JSON-варианта (замерено одним
агентом на одном стенде, это самое чистое сравнение механизмов).
**18,1 с [2] — выброс.** Причина замером не установлена: [2] сам пишет в «не выяснил» п.5, что
`EXPLAIN ANALYZE` не снимал и распределение 18,1 с между `to_json`, `unnest`, JOIN и `sha1` не
разбирал. Два фактора, которые видны из текстов и оба присутствуют именно у [2]:
(1) `json_extract_string(j,k)` вызывается по одному разу на каждый ключ строки, тогда как `json_each`
[1] и `UNPIVOT` [3] разворачивают строку за один проход; (2) сортировка в `string_agg`, за которую [3]
независимо измерил цену ×3,4 (1,139 → 5,593 с). **Это объяснение [рассуждение сводки], а не замер** —
подтверждать одним `EXPLAIN ANALYZE` (чистый SELECT, запрета не нарушает).
**Разрешается так:** к планированию берётся 4,2–4,4 с как измеренная стоимость полного такта с
резолвингом ([1] и [3] независимо), 18,1 с — стоимость конкретной, отвергнутой реализации.

### 4.2. `pg_class.reltuples`: «быстрый счётчик» [2] против «врёт» [1] и [3]

**Факты не противоречат друг другу, противоречат выводы.**
- [1] §6.2(б): `sum(reltuples)` за 0,069 с; `search_corpus` → 99 009 при `count(*)`=97 965; на малых
  справочниках совпадает точно. Вывод: **предфильтр «пусто/непусто», не источник истины**.
- [2] §6 и §2.1: 0,089 с; сверка со всеми точными счётчиками — `всего=235, совпало=232, разошлось=3`,
  и разошлись **ровно те, куда пишут**: `search_meta`, `search_corpus` (99 009/97 965 — «мёртвые» строки
  после MERGE не вычтены), `search_idx`. Вывод: **на витрине (только чтение) точно**.
- [3] §6: то же расхождение 99 009/97 965, и **найдена причина в коде** —
  `server/pg/pg_catalog/pg_class.cpp:160-176`: «reltuples is read from the store table's row-group
  metadata (DataTable::GetTotalRows), never a count(*) query: pg_catalog must not scan data».
  Считаются в том числе строки, вытесненные обновлениями/удалениями.

**Чем разрешается.** Цитата из [3] объясняет наблюдение [2]: `reltuples` = число строк в row-группах
хранилища, поэтому оно точно ровно там, где не было UPDATE/DELETE. То есть «сошлось на 232 из 235» —
не свойство `reltuples`, а свойство текущего наполнения витрины.
**Но для задачи это не спасает**, и здесь решает третий аргумент, который привёл только [1] (Д10 п.2):
**число строк — плохой детектор изменений в принципе: правка поля не меняет `count(*)`.**
Плюс [3] §2.1(в): дешёвого сигнала «в этой таблице писали» через row-group-метаданные у нас нет вовсе
(`pragma_storage_info` пуст).
**Решение:** обнаруживать изменения `reltuples`'ом **нельзя** — ни в версии [2], ни в какой другой.
Для точного счёта брать сгенерированный `UNION ALL` (0,214–0,266 с, [1] и [3] независимо) — цена
0,2 с за истину против 0,09 с за оценку не стоит обсуждения. `reltuples` оставить как предфильтр
«таблица пустая/непустая», если он вообще понадобится. Для «что изменилось» — дайджесты (3.4).
Отдельно фиксирую: **зависимость витрины от ETL не проверена никем** — если ETL начнёт делать UPDATE/
DELETE по витрине, точность [2] исчезнет; это ещё одна причина не строить на этом логику.

### 4.3. Нужен ли разовый полный пересчёт эмбеддингов: ДА [2] против НЕТ [1] и [3]

**Это НЕ противоречие: спорят о разных вещах.** Разбор:

**Равенство хеш-функции — подтверждено ТРОИМИ, спора нет.**
[1] Д9: `sha1('Контрагент: ООО Ромашка | Сумма: 100')` в SQL и `hashlib.sha1` — совпало побайтово
(включая кириллицу). [3] §2.1(б): то же на другой строке — совпало. [2] §3: совпало на `'abc'`.
Вывод общий: **перенос вычисления хеша в SQL сам по себе ничего не инвалидирует.**

**Равенство ВХОДНОГО ТЕКСТА — не выполняется, и это тоже говорят ВСЕ ТРОЕ**, просто [1] и [3] написали
это не в выводе, а в оговорке и в «не выяснил»:
- [2] §2.7 — **конкретная измеренная причина**: `BOOLEAN` в `to_json` рендерится как `true`/`false`,
  а нынешний `psql --csv` даёт `t`/`f` [вывод].
- [3] «не выяснил» п.4 — **другая конкретная причина**, дословно: «Совпадёт ли отпечаток в SQL с текущим
  продовым `doc` — **нет, наверняка не совпадёт**: продовый `doc` строится не из всех колонок, а из
  отфильтрованных по `$metadata` (`serene_search_build.py:430-460`)».
- [1] «не выяснил» п.1 — **третья порция причин**: отбрасывание машинных токенов, `TEXT_CLIP`, отдельные
  `amount`/`doc_date`, порядок колонок из каталога; и все замеры [1] дали `changed = 96931`, то есть
  100 % расхождение именно из-за формата.
- Оговорки в выводах [1] и [3] стоят прямо: «при условии побайтово того же `doc`» [1] §3, «при условии,
  что формула склейки `doc` воспроизведена ровно» [3] §2.1(б).

**От выбора механизма зависит следующее.** Наблюдение по BOOLEAN, найденное [2], **не различает три
механизма**: `false` даёт и `to_json` ([1] §2.1 [вывод] `DeletionMark: false`), и `json_extract_string`
([2] §2 [вывод] `DeletionMark: false`), и `UNPIVOT` с кастом `::VARCHAR` ([3] §2.1(а) [вывод]
`DeletionMark | false`). То есть **ни один из трёх путей не воспроизводит нынешний `t`/`f` сам по себе**;
это чинится явным `CASE`, и [2] прямо это предлагает. От механизма реально зависит другое:
порядок колонок (у [1] сортировка по имени, у [2] исходный порядок через `WITH ORDINALITY`, у [3] —
порядок каталога), обработка NULL (у [3] `UNPIVOT` отбрасывает — это совпадает с нынешней семантикой;
у [2] `coalesce(…,'')` оставляет пустой ключ), и наличие/отсутствие фильтра колонок по `$metadata`.

**Разрешение:** утверждение «переход без пересчёта» **истинно для хеш-функции и ложно для текста в том
виде, в каком его сегодня строит SQL у всех троих**. Полный пересчёт эмбеддингов **не является
неизбежной ценой перехода** — он становится не нужен, если в SQL воспроизвести продовую формулу `doc`
целиком: фильтр колонок по `$metadata`, `TEXT_CLIP`, рендер BOOLEAN, порядок. Стоимость этого
воспроизведения **никем не оценена** ([3] «не выяснил» п.4 прямо: «стоимость варианта не оценена»).
Решение — бинарное и требует одного замера (раздел 6, шаг 3): либо формула воспроизводится и
эмбеддинги живут, либо принимается разовая полная переэмбеддировка 97 965 строк. Выбирать «удобную»
версию здесь нельзя: цена ошибки — молчаливая переэмбеддировка боевого корпуса.

### 4.4. Дополнительно найденные расхождения

**(г) Приемлемость `DROP INDEX`+`CREATE INDEX` каждый такт.**
[1] §1.5 — «при 98 тыс. строк это по нашему же замеру порядка 1 с (`docs/SERENEDB.md:256`:

**(д) Размер карты ссылок: 141 таблица [1] против 112 [3], при одинаковых 38 515 парах.**

с его же §7.4. Правильное число для карты — **112** ([3], прямой `[вывод]`; критерий совпадает с

[1] проверял уникальность **ключей** (38 515/38 515). Это разные проверки, обе верны.

## 6. Порядок работ

Корпус боевой: 97 965 строк, бот на нём отвечает. Каждый шаг — с проверкой, что не сломалось.
Шаги 1-3 не трогают боевые данные вообще.

**Шаг 0. Зафиксировать точку возврата.** Снять текущие `(src_table, row_key, doc_hash)` целиком и
текущее время полного такта. Проверка: контрольные запросы бота отвечают как раньше.

**Шаг 1 (только чтение, безопасно). Убрать процессы, не трогая логику.**
Заменить 233 `count(*)` на один сгенерированный `UNION ALL` (0,214–0,266 с [1,3]) и 233 вызова
`duckdb_columns()` — на один (0,041 с [2]); генерацию текста выполнять в движке, прогон — через
`\gexec` в одном процессе [1] Д2. Логика сборки `doc` пока прежняя, питоновская.
*Проверка:* число таблиц и суммарное число строк совпало с прежним циклом до строки; корпус не
менялся; такт стал короче ровно на время запуска процессов.
*Риск:* нулевой — это чтение каталога. Ловушка: разные критерии выборки таблиц дают 226/233/235/305
(разд. 4.4(е)) — критерий зафиксировать один раз.

**Шаг 2 (только чтение). A/B двух механизмов сборки на ОДНОЙ формуле.**
Реализовать продовую формулу `doc` дважды: `to_json`+`json_each` [1] и `UNPIVOT`+`COLUMNS(*)::VARCHAR`
[3], с одинаковым `sha1`, одинаковым порядком и одинаковой обработкой NULL/BOOLEAN. Снять время на
всей базе и `EXPLAIN ANALYZE` (закрывает разд. 4.1 и пп. 5-6 раздела 5).
*Проверка:* оба варианта дают побитово одинаковый `doc` на 1 000 случайных строк; `UNPIVOT` даёт тот же
отпечаток в 5 прогонах подряд ([3] «что проверить» п.3).
*Решение шага:* берётся более быстрый **из тех, что дали одинаковый текст**; при равенстве — [1]-форма,
как не зависящая от неподтверждённой детерминированности `UNPIVOT`.

**Шаг 3 (только чтение). Сверка отпечатков с боевым корпусом — точка принятия решения.**
Посчитать `sha1` по SQL-формуле и сравнить с `search_corpus.doc_hash` построчно

*Исход А:* совпадение ~100 % → переход без переэмбеддировки.
*Исход Б:* расхождение → перечислить причины (BOOLEAN `t/f` [2] §2.7, фильтр колонок по `$metadata`

*Исход В:* формулу воспроизвести не удаётся → **отдельное решение владельца** о разовой полной

**Шаг 4 (первая запись, на КОПИИ корпуса). Один `MERGE` вместо staging.**
`MERGE INTO <копия> USING (<запрос шага 2>) … WHEN NOT MATCHED BY SOURCE THEN DELETE
RETURNING merge_action, t.src_table, t.row_key` (форма — [2] «что проверить» п.2, [3] п.4).
*Проверка:* (а) `merge_action` реально приходит и содержит `INSERT`/`UPDATE`/`DELETE`; (б) время при

нельзя потерять — [3] §2.2(з).

**Шаг 6. Ранний выход по дайджестам (опционально, после шага 5).**

## 7. Побочные находки

1. **`duckdb_indexes().sql` врёт про состав индекса** — отдаёт `USING inverted ()`, пустые скобки
   ([2] §2.9, [3] §2.2(н), двое независимо). Практический вывод [3]: проверять «индекс тот, что нужен»
   по каталогу **нельзя**; наша таблица `search_meta` с полным DDL — вынужденный обход дефекта
   интроспекции, а не самодеятельность. Не удалять.
2. **`refresh_interval=1000` в `pg_class.reloptions` — ловушка** ([1] Д5). При беглом чтении выглядит
   как «индекс сам обновляется раз в секунду». На деле это интервал видимости уже закоммиченных
   сегментов iresearch (`index.h:48` → `search_table.cpp:115`). Ровно та ошибка, которая могла бы
   «доказать» несуществующую свежесть индекса над VIEW.
3. **`pg_stat_user_tables` — заглушка** ([2] §2.1): нули даже для `search_corpus`, куда пишет каждый
   такт. Любая логика «сколько строк вставлено/обновлено» на PG-счётчиках работать не будет.
4. **`pragma_storage_info` / `pragma_metadata_info` на наших таблицах пусты** ([3] §2.1(в)) — таблицы
   SereneDB лежат не в duckdb-storage. Дешёвого сигнала «в этой таблице писали» через row-group-
   метаданные нет.
5. **`json_extract_string` с JSONPath молча возвращает пусто** — и `'$.a'`, и `'$."'||k||'"'`
   ([3] §2, [2] §2.7, двое). Не ошибка, а пустой результат — молчаливая потеря данных, если не заметить.
   Рабочая форма — голое имя ключа. Родственное: `json_extract_string(v,'$')` на скалярном JSON тоже
   пусто, снимать кавычки надо `trim(v::VARCHAR,'"')` ([1] §7.3).
6. **`btrim` в сборке нет** (`Did you mean "trim"?`), **`struct_values(t)::VARCHAR[]` падает**
   (`Unimplemented type for cast`), **`xxhash`/`crc32`/`digest`/`farm_fingerprint` нет** —
   [1] §7.3/§3, [2] §2/§3, [3] §3.
7. **`UNPIVOT` без явного каста падает** — `Cannot unpivot columns of types VARCHAR and BOOLEAN`
   ([3] §2.1(а)). Рабочая форма — `SELECT COLUMNS(*)::VARCHAR` во внутреннем подзапросе.
8. **Аргумент `read_csv`/`read_parquet` обязан быть строковым литералом**, иначе
   `Deprecated implicit conversion of unbound identifiers to strings in table function arguments`
   ([3] §5).
9. **`RETURNING` не реализован для ATTACH-нутых Postgres-таблиц** (строка бинарника, [2] §4).
   Для нативного корпуса неважно, **но это прямой риск для целевой архитектуры «PG на Windows +
   attach»** — там `MERGE … RETURNING` работать не будет.
10. **Триггеры и MERGE взаимно исключаются**: `MERGE INTO is not supported on tables with triggers`
    ([1] Д3). Даже если триггерный аппарат когда-нибудь откроют для наших таблиц, он отключит MERGE.
11. **Поиск можно JOIN-ить с обычными таблицами прямо от имени индекса**
    (`cookbook/search/search-with-joins.test:47-58`, [3] §2.2(ж)) — `FROM products_idx p JOIN orders o
    …`, с `GROUP BY` и агрегатами. К теме такта не относится, но это готовый штатный механизм для
    выдачи (с оговоркой [3]: правит отображение, не находимость).
12. **`ai_embed` существует и штатно вызывается прямо в `INSERT … SELECT`**
    (`examples/demo5/bootstrap.sql:5-37`, [1] Д7), но в нашей сборке у неё три VARCHAR-аргумента без
    `dimensions`. Если размерность индекса когда-нибудь сменится на то, что отдаёт провайдер, весь такт
    становится одним запросом без единого выхода в Python. Держать как цель, не как задачу.
