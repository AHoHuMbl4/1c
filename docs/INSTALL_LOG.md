### ✅ Windows: PostgreSQL 17.6 — УСТАНОВЛЕН (после долгой диагностики)
Цель была померить, сколько ресурсов съест СУБД рядом с 1С.

| Шаг | Итог |
|---|---|
| Скачивание бинарников (315 МБ) | ✅ 7 с, скорость ~5 МБ/с |
| Распаковка (848 МБ) | ✅ 109 с |
| `psql.exe --version` | ✅ работает |
| `postgres.exe` / `initdb.exe` | ❌ `0xC0000142` |
| То же под служебным аккаунтом `pgsvc` | ❌ та же ошибка |
| Штатный установщик EDB (348 МБ) в тихом режиме | ❌ exit=1 за 16 с, **лога не создал** |

**Причина:** серверные бинари PostgreSQL отказываются работать под администратором и пересоздают
себя с ограниченным токеном; в неинтерактивной SSH-сессии это не проходит. Установщик, судя по всему,
тоже требует интерактивного сеанса.

**Ещё две попытки обойти без RDP (обе неудачные):**
- **Установщик через планировщик задач от SYSTEM** — впервые *запустился* и создал лог (значит дело
  было в оконной станции), но упал на `The database cluster initialisation failed`. В
  `installation_summary.log` видно причину выбора аккаунта: запуск от SYSTEM заставил установщик взять
  `NT AUTHORITY\NetworkService`.
- **То же с явным `--serviceaccount postgres --servicepassword ...`** — тот же отказ на инициализации.

**Итоговая причина:** `initdb.exe` и `postgres.exe` не стартуют **в сессии 0** в принципе (та же
`0xC0000142`), тогда как `psql.exe` там работает. Это те бинари, что пересоздают себя с ограниченным
токеном. **Это не приговор PostgreSQL на Windows** — с консоли он ставится штатно. Ограничение именно
headless-подхода: нужен интерактивный сеанс.

### 🎯 НАСТОЯЩАЯ ПРИЧИНА (найдена не сразу — все версии выше были ошибочными)

Дело оказалось **не в PostgreSQL, не в сеансе и не в правах**. Диагностика по шагам:

1. Загрузил каждую DLL из `bin` по отдельности → нашёл виновника:
   `icuuc67.dll` — ошибка **193 (ERROR_BAD_EXE_FORMAT)**, остальные 15 падали каскадом
   с ошибкой 126 («модуль не найден»), потому что зависят от неё.
2. Разобрал PE-заголовок: файл целый, `MZ`/`PE` на месте, machine = x64. Не порча и не битность.
3. Загрузил с флагом `DONT_RESOLVE_DLL_REFERENCES` → **загрузилась** ⇒ проблема в зависимостях.
4. Проверил зависимости ICU — библиотеки MSVC:
   `msvcp140.dll`, `vcruntime140_1.dll`, `msvcp140_1/2.dll`, `concrt140.dll` → **ошибка 193**,
   хотя физически лежат в `System32` с правильной версией 14.44.
5. Проверил по полному пути — та же ошибка ⇒ **системный VC++ runtime был нерабочим**.

**Причина:** мой ранний `vc_redist.x64.exe /install /quiet /norestart` отчитался `exit=0`,
но оставил runtime в нерабочем состоянии (файлы разложены, но не активированы — нужен был перезапуск).

**Решение — одна команда:**
```
vc_redist.x64.exe /repair /quiet /norestart
```
После неё: `msvcp140.dll` грузится, `initdb --version` → `initdb (PostgreSQL) 17.6`.

**Урок:** `/norestart` у VC++ redist может оставить систему в состоянии «файлы есть, версия правильная,
но ничего не грузится». Признак — ошибка **193 на заведомо валидной x64-библиотеке**.
После установки runtime обязательно проверять загрузку, а не доверять `exit=0`.

### ⛔ SereneDB на Windows — невозможно нативно
Проверено по репозиторию, не по догадкам: CI собирает и публикует только `linux-amd64`,
`linux-arm64` и Docker-образы. `windows-latest` в workflow относится к `serene-ui` (клиенту), не к
серверу. CONTRIBUTING: единственный тулчейн — clang-21 + Ninja.

Варианты запуска на Windows: WSL2, Docker Desktop (сам поверх WSL2), Hyper-V.
**WSL на стенде не установлен** — требуется `wsl --install` и перезагрузка.

### 📊 ЗАМЕР: PostgreSQL на Windows рядом с 1С (эксперимент завершён)

**Топология стенда (важно для трактовки цифр):** LXC и Windows **не связаны напрямую** — с LXC виден
только порт 80 (проброс на роутере для OData). Порты 22/135/445/3389/5432 закрыты. Поэтому связь
SereneDB → PostgreSQL пришлось делать SSH-туннелем через рабочую станцию по VPN. **Все сетевые тайминги
ниже завышены** этим обходом; на реальном клиенте обе машины в одной сети.

#### Ресурсы на Windows (замер локальный, без сети — потому достоверный)

| Состояние | postgres RAM | CPU | RAM свободно |
|---|---|---|---|
| В покое | **73 МБ** (6 процессов) | 3.5% | 6 из 8 ГБ |
| После заливки 200 тыс. строк | 119 МБ | 2% | 6 ГБ |
| Под нагрузкой (2 потока аналитики) | **128 МБ** | **81.5%** | 5.7 ГБ |

**Влияние на 1С — главный вопрос:**

| | Задержка OData |
|---|---|
| 1С при простаивающем Postgres | **77 мс** (74/64/91/78) |
| 1С при Postgres, грузящем CPU на 81% | **83 мс** (89/75/99/68) |

**+8% к задержке 1С при загрузке процессора на 81%.** То есть на 2-ядерной машине с 8 ГБ
PostgreSQL с 200 тыс. строк соседствует с 1С практически незаметно.
30 аналитических запросов по 200 тыс. строк локально — **3.1 с**.

#### Два режима работы SereneDB с данными на Windows

| Режим | Что происходит с данными | Замер (через медленный туннель) |
|---|---|---|
| **Живое чтение** (`ATTACH`, без индекса) | остаются на Windows | count 200k — 5.4 с; group by city + sum — 4.5 с; числовой фильтр — 2.4 с |
| **Индекс над VIEW** | втягиваются в SereneDB | постройка — 15.0 с; поиск по тексту — 258 мс; по городу — 154 мс |

**Сверка корректности:** «свыше 500 тыс» = **91 076** в обоих режимах, цифра в цифру.
Поиск по городу через индекс = 40 000, столько же в источнике.

Поиск по индексу быстрее живого чтения **в 10–20 раз** — но ценой копирования данных к себе.

#### ⚠ Найдено: NUMERIC нельзя индексировать
```
ERROR: Column 'amount' has unsupported type DECIMAL(14,2) and can not be indexed
```
Денежные колонки в PostgreSQL обычно `numeric` — инвертированный индекс их не берёт.
Лечится приведением **в самом VIEW**: `SELECT ..., amount::DOUBLE AS amount FROM ...`.
Это надо закладывать в генератор представлений.

#### Вывод
Опасение «СУБД рядом с 1С задушит машину» **не подтвердилось**: +8% к задержке 1С при пиковой
загрузке CPU, 128 МБ памяти. Но напомню про главное ограничение — **SereneDB под Windows не собирается**,
поэтому схема «всё у клиента» всё равно требует Linux-машины; PostgreSQL на Windows решает только
задачу «данные остаются у клиента», и то частично (индекс копирует к себе то, что индексирует).

## Грабли окружения (повторяются, держать под рукой)

### PowerShell
- **`$args` — автоматическая переменная.** Назвал так параметр функции → всё сломалось.
  Аналогично `R` — это алиас `Invoke-History`, функцию с таким именем не вызвать.
- **Кириллические члены COM не резолвятся напрямую:** `$obj.Наименование` возвращает пусто,
  `$ib.Справочники` — NULL. Работают английские псевдонимы (`$obj.Description`) и `InvokeMember`
  для обоих языков. Динамические члены менеджеров (`Справочники.X`) не резолвятся вообще —
  обход через запрос + `ПолучитьОбъект()`.
- **Длинные скрипты — только `-EncodedCommand`** (base64 от UTF-16LE), иначе ломается кириллица.
  Совсем длинные — файлом через `scp`, обязательно **UTF-8 с BOM**.
- **Заголовок `Range` в `Invoke-WebRequest`** задать нельзя — использовать `curl.exe` (есть в Windows 10+).

### 1С через COM
- **COM-коннектор 32-битный** (платформа x86) → запускать
  `C:\Windows\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`, иначе `Class not registered`.
- **Платёжные документы молча не делают проводок**, если в строке `РасшифровкаПлатежа` не заполнить
  `КурсВзаиморасчетов`, `КратностьВзаиморасчетов`, `СуммаВзаиморасчетов`. Документ при этом
  записывается и помечается проведённым, ошибок нет, а движений ноль.
- **У банковских документов два разных «счёта»:** `СчетОрганизации` — ссылка на справочник
  банковских счетов, `СчетБанк` — счёт учёта из плана счетов.
- **Безопасный режим** (`ОбщегоНазначения.ВыполнитьВБезопасномРежиме`) удобен для экспериментов —
  всё откатывается; но **сохранить через него ничего нельзя** (БСП оборачивает в транзакцию и
  блокирует фиксацию). Запись — только прямыми COM-вызовами.

### OData 1С
- **Стандартные поля именуются по-английски** даже в русской конфигурации: `Ref_Key`, `DataVersion`,
  `Posted`, `Date`, `Description`, `IsFolder`. Пользовательские реквизиты — на языке конфигурации.
- **Служебный документ отдаётся в XML**, не в JSON (нужен `$format=json` или парсить XML).
- **Ключ у каждого типа объявлен в `$metadata`** и он разный: `Ref_Key`, `Ref_Key + LineNumber`,
  `Recorder + Recorder_Type`, встречается и кириллический (`Организация_Key`).
