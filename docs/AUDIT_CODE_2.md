Дата: 2026-07-27. Сборка движка: **26.07.3** (`PostgreSQL 18.3 (SereneDB 26.07.3)`),
инстанс `192.168.56.42:7890`, корпус `search_corpus` 97 965 строк, индекс `search_idx`.
Источники: `/srv/data/cursor/cursor/1/serenedb-src` (ветка `main`), три каталога
возможностей (`docs/SERENE_CAPS_1..3.md`), живой инстанс (только `SELECT`/`EXPLAIN`).

Критерий владельца: обычный SQL, приёмы PostgreSQL и наш код штатным механизмом **не**
считаются. Ниже засчитано только то, что является механизмом именно этого движка.

Все замеры — psql `\timing` на живом инстансе, повторный прогон (первое значение

## 1. `serene_search_build.py:865-880` — индекс сносится и строится заново каждый прогон

```python
ddl("DROP INDEX IF EXISTS %s;" % INDEX)
...
ddl("CREATE INDEX %s ON %s USING inverted(doc %s, refs %s, src_table) "
    "INCLUDE (src_table, row_key, amount, doc_date);" ...)
```

**Сейчас:** свой код. Строки корпуса уже записаны штатной `MERGE INTO` (`_flush`,
строка 723) — и в комментарии к ней сами же цитируем `dml/merge.test:2`: «the index
forces the commit-time append/delete path for every merge action». То есть движок уже
привёл индекс в согласованное состояние. После этого мы индекс **уничтожаем** и строим
с нуля.

**Штатно:** индекс инвертированного типа обновляется транзакционно вместе с таблицей
(`examples/demo2/README.md:8`, `tests/sqllogic/sdb/pg/dml/merge.test:46-57` — те же
merge-действия против таблицы **с** inverted-индексом). Видимость свежих сегментов —
не пересборкой, а публикацией:

```sql
VACUUM (REFRESH_INDEX) search_idx;   -- tests/.../index/vacuum_options.test:67-80
```
(либо ждать `refresh_interval`, у нас 1000 мс — подтверждено `pg_class.reloptions`).

**Выигрыш:**
* *правильность/доступность* — сейчас между `DROP INDEX` и концом `CREATE INDEX`
  индекса не существует, и **любой запрос `serene_ask` в это окно падает**
  (`FROM search_idx` → relation does not exist → `RuntimeError` → HTTP 500). Окно = всё
  время построения индекса, каждый такт сборки;
* *скорость* — по нашим же замерам (`docs/SERENEDB.md:219`) 50 тыс. строк = 423 мс,
  2696 строк = 150 мс; на текущих 98 тыс. это ~1 с **каждого** прогона, и растёт
  линейно с базой, тогда как инкремент стоит ровно столько, сколько изменившихся строк.

**Проверено на инстансе:** частично (факт транзакционного ведения индекса — по тестам
движка и по тому, что MERGE уже используется; DDL на сервере не выполнялся — запрещено).
**Важность: блокирует** (регулярное окно 500-ошибок на живом сервисе).

## 2. `serene_search_build.py:879-880` — `amount` и `doc_date` только в `INCLUDE`

```python
USING inverted(doc %s, refs %s, src_table) INCLUDE (src_table, row_key, amount, doc_date)
```

**Сейчас:** числовая и датовая колонки — «пассажиры». Предикаты по ним
(`serene_ask.py:224-231`) исполняются как residual-фильтр над сканом.

**Проверено EXPLAIN на инстансе:**
```
EXPLAIN SELECT count(*) FROM search_idx WHERE doc @@ ts_phrase('договор') AND amount > 1000;
  IRESEARCH_SCAN
    Index Filter: Term(doc)          <- в постинги
    Column Filter: amount > 1000     <- residual, поверх скана
```
Для сравнения `WHERE src_table = '...'` (колонка есть в списке ключей) даёт
`Index Filter: Term(src_table)` — фильтр уходит в постинги.

**Штатно:** колонка может быть **и** ключом, **и** в `INCLUDE` одновременно — тогда есть
и пушдаун, и быстрая проекция (`index/inverted_index_indexed_vs_included.test:1-20`,
`index/inverted_index_include_pushdown.test:1`):
```sql
CREATE INDEX search_idx ON search_corpus
USING inverted(doc search_dict, refs search_dict, src_table, amount, doc_date)
INCLUDE (src_table, row_key, amount, doc_date);
-- и тогда запрос:
WHERE amount @@ ts_gt(1000)            -- или ts_between(lo, hi, true, true)
WHERE doc_date @@ ts_ge(TIMESTAMP '2025-12-01')
```

**Выигрыш:** *скорость на масштабе*. На 98 тыс. строк разница мала (`amount > 1000`
= 1.18 мс), потому что residual-фильтр всё равно идёт по columnstore индекса. Ценность
растёт вместе с корпусом: сейчас условие по сумме/дате читает все документы, прошедшие
текстовый фильтр, а не пересечение постингов.
**Проверено на инстансе:** да (EXPLAIN обоих вариантов).
**Важность: ухудшает** (на нашем объёме — не блокер).

## 3. `serene_search_build.py:879` — нет `WITH (optimize_top_k = ...)`, WAND выключен

**Сейчас:** индекс создаётся без опций (`pg_class.reloptions` живого `search_idx`
содержит только 10 числовых умолчаний, `optimize_top_k` отсутствует — проверено).
Наш горячий запрос (`serene_ask.rows_of`, строки 371-376) имеет ровно ту форму, под
которую механизм и сделан: `WHERE <фильтр> ORDER BY bm25(idx.tableoid) DESC LIMIT 40`.

**Штатно:**
```sql
CREATE INDEX search_idx ON search_corpus USING inverted (...)
  WITH (optimize_top_k = 'bm25(1.2, 0.75)');
```
`index/inverted_index_optimize_top_k.test:1-20`, `index/inverted_index_wand.test:1-17`;
скорер в `ORDER BY` обязан совпасть со записанным; `EXPLAIN` тогда печатает
`Top: k, optimized`; глобальный выключатель `SET sdb_disable_top_k_optimization = true`
(есть в `duckdb_settings()` нашей сборки).

**Выигрыш:** *скорость*. Сейчас `ORDER BY bm25 DESC LIMIT 40` по `ts_phrase('договор')`
(3918 документов) = **2.68 мс**; отсечение по block-max начинает окупаться на широких
запросах и больших корпусах. На нашем объёме выигрыш не измерить без пересборки индекса
(DDL запрещён) — поэтому внедрять с замером до/после.
**Важность: косметика сейчас, ухудшает на масштабе.**
**Проверено на инстансе:** частично (отсутствие опции и наличие выключателя — да; эффект — нет).

⚠ Оговорка: `optimize_top_k` жёстко связывает индекс с одним скорером. Пока `ASK_SCORER`
переключается окружением (A/B), включение WAND обесценит все варианты, кроме записанного.

## 4. `serene_ask.py:920-922`, `:956-959`, `:969-973` — косинус скалярной функцией вместо оператора движка

```python
"ORDER BY array_cosine_similarity(emb, %s) DESC LIMIT %d"
```

**Сейчас:** обычная скалярная функция DuckDB `array_cosine_similarity(...) DESC`.

**Штатно:** оператор дистанции движка `<=>` (cosine), именно он распознаётся
планировщиком как ANN-форма (`IRESEARCH_ANN_SCAN`, `examples/demo4/demo.sql:56-60`,
`site_docs/sql/indexes/inverted/vector-search.test`):
```sql
SELECT src_table FROM search_corpus ORDER BY emb <=> '[...]'::FLOAT[1536] LIMIT 40;
```

**Выигрыш:** *скорость* — замерено на нашем корпусе, одинаковая форма запроса, по два
прогона: `array_cosine_similarity(...) DESC` = **394 / 415 мс**, `emb <=> ...` =
**298 / 282 мс** → **в 1.4 раза быстрее** при том же результате. Плюс *задел*: как только
появится ivf-колонка, ровно эта форма превращается в ANN-скан, а форма со скалярной
функцией — нет (проверено `EXPLAIN`: сейчас обе дают `SEQ_SCAN` + `TOP_N`).
**Проверено на инстансе: да.**
**Важность: ухудшает** (полсекунды на каждый вопрос, где слова не нашлись).

Тот же дефект в `serene_report.py:220` (`_semantic_into`) и в `docs`-примерах резолвера.

## 5. `serene_ask.py:277` — нижний регистр слова считается в Python

```python
("part", "ts_like(%s)" % lit("%" + alt.lower() + "%"))
```

**Сейчас:** свой код. Комментарий в функции верен (`ts_like`/`ts_starts_with` — терминные
функции, анализатор их не трогает), но нормализацию мы делаем питоновским `.lower()`, а
индексная сторона нормализована **словарём** (`case='lower', accent=false`). Правила
расходятся: словарь снимает диакритику и приводит регистр по своим правилам, `.lower()`
Python — по своим. Для базы с диакритикой (`Café`, `Ångström`, турецкое `İ`) термы в
индексе и наш шаблон не совпадут, и подстрочный поиск молча вернёт 0.

**Штатно:** нормализовать тем же словарём, прямо в SQL:
```sql
WHERE doc @@ ts_like('%' || ts_lexize('search_dict','Ромашка')[1] || '%')
```
`ts_lexize(dict, text) -> VARCHAR[]` — `site_docs/.../inverted/text-analysis.test:12`.

**Выигрыш:** *правильность* (одно правило нормализации вместо двух), минус одна языковая
догадка в коде.
**Проверено на инстансе: да** — запрос выше отрабатывает (29 строк, 5.6 мс).
**Важность: ухудшает** (на кириллице не проявляется, на латинице с диакритикой — тихо теряем).

## 6. `serene_ask.py` — поле `refs` построено, но в поиске не используется

**Сейчас:** `serene_search_build.py:879` индексирует `refs` отдельным полем, и комментарий
прямо объясняет зачем: «спросить „контрагент Ромашка“ и не получить „склад Ромашка“, плюс
можно поднять вес поля (^)». В `serene_ask.py` **нет ни одного** `refs @@ ...` — весь
поиск идёт только `doc @@ ...` (строки 279, 318, 325, 335). `refs` читается лишь в
`signal_terms` (`ts_dict_agg(refs)`).

**Штатно:** мультиполевой запрос по одному индексу и буст поддерева:
```sql
-- проверено на инстансе:
SELECT count(*) FROM search_idx WHERE doc @@ ts_phrase('ромашка')
                                   OR refs @@ ts_phrase('ромашка');          -- 29, 5.0 мс
SELECT count(*) FROM search_idx WHERE refs @@ ts_phrase('ромашка');           -- 29, 3.2 мс
SELECT row_key, bm25(search_idx.tableoid) s FROM search_idx
 WHERE refs @@ (ts_phrase('ромашка') ^ 3.0) ORDER BY s DESC LIMIT 3;          -- работает
```
Оператор `^` — `cookbook/search/boosting.test:46`, `index/boost_score.test:1-60`.

**Выигрыш:** *правильность выбора сущности* — ровно та задача, ради которой поле и
заведено; сейчас затраты на его построение мы несём, а пользы не берём.
**Проверено на инстансе: да.**
**Важность: ухудшает.**

## 9. `serene_report.py:192-203` — резолвер терминов на `LIKE '%…%'` + `jaro_winkler`

```python

conds.append(f"jaro_winkler_similarity(lower(\"{c}\"), '{wq}') > {min_sim}")
```

**Сейчас:** обычный SQL (`LIKE`) + скалярная функция DuckDB, полным сканом, **по каждой**

```sql
-- фаззи по терму (проверено на нашем индексе):

WHERE value @@ ts_ngram('казань', 0.6)
WHERE value @@ ts_like('%казан%')                   -- 12.1 мс
-- рецепт «исправление опечаток» целиком:
SELECT unnest(ts_dict_agg(value))  AS suggestion,
       unnest(ts_dict_score(value)) AS similarity,
       unnest(ts_dict_count(value)) AS n
FROM resolver_idx WHERE value @@ ts_levenshtein('казань', 2)

```

(**в 37 раз**), `ts_levenshtein('ромашка',2)` = **5.5 мс**, и оба дают тот же ответ

в витрине **2297** колонок типа char.
**Проверено на инстансе: да** (замер механизма; отдельный индекс над `resolver_index` не
создавался — DDL запрещён).

## 10. `serene_report.py:169-189` (`dim_columns`) и `:122-154` (`get_schema`) — профиль колонок по одному запросу на колонку

`index/inverted_index_summarize.test:34-40`, `site_docs/.../SUMMARIZE`.

**Выигрыш:** *скорость*. Замерено: `SUMMARIZE catalog_классификаторбанков` (23 колонки) =

для той же таблицы — 23 отдельных `count(DISTINCT)` + 23 выборки образцов ≈ **1.8 с**
(46 × 40 мс) → **>150×** на таблицу. Для справки: `approx_count_distinct("Город")` = 380
за 2.5 мс против `count(DISTINCT)` = 395 за 0.94 мс (на этом объёме точный дешевле —

**Проверено на инстансе: да.**
**Важность: блокирует** (путь `report_1c` в текущем виде не укладывается ни в какой таймаут

1. **`ai_embed()` вместо питоновского эмбеддера (п.16).** Механизм в сборке есть,

2. **`sparse_ngram` (п.17).** Механизм штатный и точно есть в сборке, но выигрыш над
   текущими 12 мс `ts_like` не измерен, а цена (второй набор постингов над всем текстом)
   известна. Чего не хватило: права создать словарь и индекс для замера. Внедрять только

5. **`serene_ask.probe` (244-305) — лестница «точно → слоп → фаззи → подстрока» со
