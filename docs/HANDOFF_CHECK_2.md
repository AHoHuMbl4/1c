# 1. Понятно ли, что делать первым действием?

## Место найдено, формулировка дословная

Первое действие названо **трижды**, тремя документами, и все три согласованы между собой:

`CLAUDE.md:150-153`
> **Первое действие: Шаг 0 — резервная копия корпуса** со всеми колонками, включая `emb`
> и `refs`. Учти: `search_corpus_bak` копией **не является**.

`memory_bank/activeContext.md:33-34` — тот же текст.

> `CREATE TABLE search_corpus_backup_<дата> AS SELECT * FROM search_corpus` — со всеми
> колонками, включая `emb` и `refs`; проверить: число строк совпало, `count(emb)` совпал,
> `refs` не пуст; записать коммит, на который откатываемся.

Точка входа найдена без труда. Согласованность трёх документов — сильная сторона пакета.

## 🔴 Но шаг уже выполнен, и об этом не сказано нигде

```
$ psql ... -c "SELECT table_name FROM information_schema.tables WHERE table_schema='public' ..."
search_corpus_backup_20260727     ← артефакт Шага 0, уже существует
tmp_prod_corpus                   ← артефакт Шага 1/3, уже существует
tmp_refmap                        ← артефакт Шага 1/3, уже существует
```

Копия не заготовка, а **настоящая и полная**:

```
$ psql ... -c "SELECT count(*) n, count(emb) e, count(refs) r FROM search_corpus_backup_20260727;"
 n=97965 | e=97965 | r=97965

$ psql ... -c "SELECT count(*) FROM search_corpus c
               JOIN search_corpus_backup_20260727 b USING(src_table,row_key)
               WHERE c.doc_hash <> b.doc_hash;"
 0
```

То есть все три критерия «готово, если» из Шага 0 выполнены: строки совпали, `emb`
заполнен у всех, `refs` не пуст, содержимое побайтово тождественно боевому корпусу.
Схема копии полная — 8 колонок, включая `refs` и `emb`.

`tmp_prod_corpus` — 97 965 строк, **схема один-в-один со `search_corpus`**; это уже не
Шаг 0, а прогон Шага 1 или Шага 3. `tmp_refmap` — 39 376 строк, колонки `g`, `nm`
(карта GUID → имя).

**Чем это плохо для исполнителя.** Он выполнит `CREATE TABLE search_corpus_backup_20260727
AS SELECT * FROM search_corpus` и получит ошибку «таблица существует». Дальше у него два
пути, и оба плохие: либо он решит, что копия чужая и ненадёжная, и начнёт разбираться
(потеря времени), либо — что хуже — сочтёт себя вправе её пересоздать. Пересоздание
безобидно **сегодня**, потому что копия и корпус тождественны, но если корпус к тому
моменту уже будет частично переписан новой формулой, `DROP` + `CREATE` уничтожит
единственную точку отката. Документ, который называет первым действием то, что уже
сделано, **сам создаёт эту развилку**.

## Чего ещё не хватает, чтобы выполнить шаг без вопросов

1. **Нет строки подключения.** Ни один из шести документов не показывает, чем ходить в
   базу. `SERVER_HANDOFF §8` приводит SQL-инварианты голым текстом, без `psql` и без DSN.
   Порт `7890` упомянут в `§2` в описании службы, имя базы и роль — нигде. Вывести можно
   из `/etc/1c-serene-sync.env`, но документ на этот файл в таком качестве не указывает.

2. **🔴 Не сказано, что роль в переменной окружения зависит от того, какой файл прочитан.**
   Это не мелочь, а ровно та ловушка, которая каждую ночь роняет сборку. Проверено:

   ```

   /etc/1c-mcp-reports.env   : SERENEDB_DSN=host=127.0.0.1 port=7890 user=serene_ro dbname=postgres

   Исполнитель, который по привычке сделает `. /etc/1c-mcp-reports.env` и запустит

3. **Не сказано, где выполнять.** `SERVER_HANDOFF §3` описывает установку Claude Code на

   а не с машины разработки. Мелочь, но исполнитель без человека рядом на таких мелочах и
   спотыкается.

**Оценка:** первое действие названо ясно, но **выполнить его по документу нельзя** —
не хватает способа подключиться и предупреждения про роль, а сам шаг уже сделан.

## 4.7 «Гибридный индекс BM25 + вектор» — а индекс один, и он не векторный

Описание юнита: «пересборка **гибридного** поискового индекса (**BM25 + вектор**)».
Инвариант `§8` при этом ожидает ровно одну строку `search_idx`.

**Факт:**
```
$ psql ... -c "SELECT index_name, table_name FROM duckdb_indexes();"
 search_idx | search_corpus     ← один, и только он
$ psql ... -c "SELECT k, v FROM search_meta;"
 index_ddl | CREATE INDEX search_idx ON search_corpus USING inverted(doc search_dict,
             refs search_dict, src_table) INCLUDE (src_table, row_key, amount, doc_date);
```

Индекс **только инвертированный**. Векторного индекса нет вообще — это следствие
блокировки `ivf` (`§5`, поиск идёт перебором). Документы это знают, но **имя юнита
продолжает утверждать обратное**, и `§2` цитирует юниты без оговорки. Исполнитель,
увидевший «BM25 + вектор» и одну строку в `duckdb_indexes()`, решит, что векторный индекс
пропал, и пойдёт его создавать — то есть **прямо в запрещённую зону `ivf`**.

Это самое опасное умолчание после 4.1: оно не просто вводит в заблуждение, а **толкает
именно к тому действию, которое `CLAUDE.md:124-126` запрещает красным**.

## 4.8 Дефект №1 из §6 задевает и `refs`, не только `doc`

Разобрано в 3.5. `serene_ask.py:119` режет по `\n` весь вывод `psql`; переводы строки
есть в 4 009 значениях `doc` **и в 2 361 значении `refs`**. Документ считает только `doc`.

# Вердикт

**Стартовать завтра по этим документам без человека рядом — можно.** Пакет достоверен
там, где это важнее всего: службы описаны верно (8 из 9, пропущен один упавший),
все четыре дефекта `§6` воспроизведены замером, эталоны `§8` совпали до последней цифры,
код на сервере побайтово совпадает с репозиторием, опасных команд, готовых к исполнению,
в документах нет.

**Но перед стартом обязательны правки 1-6.** Три из них не «неточности», а прямые
ловушки для исполнителя, работающего в одиночку:

- он начнёт с работы, которая **уже сделана** (Шаг 0), и в худшем случае снесёт копию,
  которая и есть точка отката;
- он увидит «BM25 + вектор» в имени юнита при одном инвертированном индексе и пойдёт
  создавать `ivf` — то самое, что уже клало движок в петлю OOM на три часа;
- он получит `permission denied for schema public` на первом же `CREATE`, узнает в этом
  дефект из `§6` и уйдёт чинить не свою ошибку.

Ни одна из этих трёх ловушек не требует нового исследования — все три закрываются
абзацем текста. Правки 7-15 можно делать по ходу.

Отдельно стоит отметить, чего в документах **нет**, и это заслуга: ни одной готовой
разрушительной команды, предупреждения стоят перед опасным, а не после, отвергнутые
версии сохранены с разбором (`CHECK2_INCR_SUMMARY_V2 §0`), и признание «версия 1 негодна»
стоит в шапке файла первой строкой — ровно как требует `HOW_NOT_TO §4.1`. Уроки из
`HOW_NOT_TO` применены к самим документам. Не применён только один — §4.4, «одна цифра в
двух документах разная»: 226 против 235 и 19 против 20 живут в пакете до сих пор.
