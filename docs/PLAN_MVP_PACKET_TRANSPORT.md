# План MVP: пакетная доставка данных Windows → Ubuntu (без VPN)

Заведён 2026-08-06 по решению владельца (обсуждение, код не писался).  
Связано: `TARGET.md` п. 14 / 16 / 17 · `windows/odata-setup/` · `work/installer-exe/PLAN.md` ·
`ubuntu/serenedb/serene_sync.py` · `ubuntu/serenedb/poc_load_entity.py` ·
`memory_bank/owner-memory/project-architecture-pg-windows-attach.md`.

**Статус:** план. Реализации ещё нет.

---

## 0. Зачем

Между Windows (1С) и Ubuntu **не будет защищённого VPN**. Постоянный открытый HTTP к
OData по незащищённой сети неприемлем: перехват = логин + тело ответов 1С.

При этом:

- доступ к Windows у нас **разовый** (после установки править по SSH нельзя рассчитывать);
- подготовка базы, корпус, индекс, ответы — ещё плывут и должны жить **на Ubuntu**;
- обновление данных уже устроено **по изменениям** (`DataVersion`), не «раз в N минут
  перечитать всё».

Отсюда MVP: Windows тонкий (1С + канал + агент посылок), Ubuntu толстый (всё остальное),
транспорт — **шифрованные пакеты** с догрузкой, без VPN.

⚠ Это **не** целевая схема TARGET п. 4/16 (PG на Windows + `postgres_attach`). Та схема
остаётся «потом, когда Windows-часть застынет». Для MVP сознательно: копия/витрина на
Ubuntu, Windows — источник.

---

## 1. Целевая картина MVP

```
Windows (ставится один раз, дальше почти не трогаем):
  1С + IIS + OData + ai_reader
  агент: localhost → 1С → diff по DataVersion → zstd → AEAD → чанки → Ubuntu

Ubuntu (всё, что ещё меняется в продукте):
  приёмник → расшифровка → витрина SereneDB → корпус/индекс → бот
```

| Слой | MVP | Потом (контракт) |
|---|---|---|
| Windows | 1С + OData + тонкий агент пакетов | PG рядом с 1С + постоянный канал / attach |
| Ubuntu | полная витрина + вся подготовка | индекс/поиск/бот; сырьё может остаться у клиента |
| Свежесть | дельта-пакеты по `DataVersion` | п. 17 как сейчас по смыслу |
| VPN | нет | не обязателен, если пакеты/TLS закрывают транзит |

План доводок exe: `work/installer-exe/PLAN.md` (Фаза 1 отмечена сделанной 30.07).

### Механика обновления (боевой код на Ubuntu)

Такт `pipeline.sh`: `serene_sync.py` → `build.sh`. Не «будильник на полную перечитку».

Для сущностей с `Ref_Key` + `DataVersion`:

1. проба `$select=Ref_Key,DataVersion`;
2. сверка с витриной: другая версия / новый ключ → changed; ключ пропал → gone;
3. дотягивание только изменённых объектов (`Сущность(guid'…')`);
4. merge: delete по `Ref_Key` + insert (документ целиком с ТЧ);
5. ноль изменений → витрину не трогаем; список `search_changed_sources` может быть пуст;
6. сборка корпуса идёт **только по изменившимся таблицам**, если список достоверен.

Ускорения уже в коде: тихий владелец → ТЧ не читаем; полная загрузка без изменения
содержимого (`EXCEPT ALL`) ≠ изменение; перепись схемы раз в час; служебные источники
в `search_entity_skipped`.

**Следствие для пакетов:** после первой полной заливки регулярные посылки — **дельта**,
не снова вся база. Логика та же; меняется транспорт и место индекса версий.

| Сейчас | MVP (вариант B) |

Без локального индекса версий на Windows пришлось бы каждый такт слать через интернет

## 4. Криптография

**Цель:** перехват по дороге бесполезен; подмена пакета ловится; на Windows нет ключа
расшифровки.

```
Ubuntu:  пара X25519 (private — только здесь)
Windows: public key (кладётся при установке)

На каждый пакет:
  file_key = random 256 bit
  payload  = zstd(данные)
  body     = AES-256-GCM(file_key, payload)   // либо age (ChaCha20-Poly1305)
  header   = seal(file_key → ubuntu_pubkey)
             + package_id, seq, kind, chunk list, hashes
```

| Требование | Как |
|---|---|
| Перехват бесполезен | AEAD + ключ расшифровки только у Ubuntu |
| Подмена ловится | GCM / Poly1305 |
| Windows не читает чужие/свои уехавшие пакеты | нет private key |
| Пакет от нашего агента | токен или mTLS на HTTPS заливки (отдельно от шифра тела) |
| Пароль в ini / ZipCrypto / «AES-CBC + свой HMAC» | **запрещено** |

Готовые коробки: **`age`** или libsodium / AES-256-GCM + обёртка ключа на X25519.  
Ротация: новый pubkey Ubuntu → Windows подхватывает; старым ключом ещё принимают период.

## 6. Формат передачи: манифест + чанки

**Не** один незарезюмируемый multi-GB файл.  
**Не** миллион файлов по одной строке.

```
package_id/
  manifest.json.enc     — meta, список чанков, хеши, сущности, kind=full|delta, seq
  chunk-00001.enc
  chunk-00002.enc
  ...
```

| Параметр | Значение |
|---|---|
| Размер чанка | 16–32 МБ для `full`; мелкая `delta` может быть одним чанком |
| Логическая нарезка | по сущностям внутри пакета |
| Commit на Ubuntu | только когда **все** чанки на месте и AEAD/хеши сошлись |
| Повтор `package_id` | идемпотентно (no-op, если уже `applied`) |
| Обрыв | Ubuntu отдаёт `missing[]`, Windows догружает только их |

Протокол:

```
Windows:  PUT chunk → Ubuntu inbox (карантин)
Windows:  GET  /inbox/status?package_id= → {received, missing, applied}
Windows:  GET  /agent/config → {config_version, список сущностей, параметры, pubkey}
Ubuntu:   все чанки OK → decrypt → apply → build → applied=true
Windows:  локальную очередь чанков удалять только после applied=true
```

🔴 **Топология (вопрос владельца 06.08): Windows только ИНИЦИИРУЕТ исходящие HTTPS.**
Белый IP / открытый порт нужен **только Ubuntu**; Windows может быть за серым IP, NAT,
динамическим адресом — входящих правил в его firewall нет вовсе, Ubuntu к Windows не
подключается никогда. Обратный канал (конфиг, ротация pubkey) агент забирает **опросом**
`GET /agent/config` раз в такт, а не толчком от Ubuntu. Следствие: endpoint Ubuntu —
единственная видимая снаружи точка, на нём обязательны TLS + аутентификация + лимиты
на карантин (§13, К8).

**Endpoint приёмника (владелец, 06.08): `https://1c-gate.timpul.ru`** — домен с TLS;
агенту при установке пишется этот URL и pubkey Ubuntu.

> ⚠️ **[замер 06.08] Допущение «белый IP только у Ubuntu» неверно.** У Ubuntu-LXC
> белого IP нет: `eth0` = `192.168.56.42/24`, исходящий NAT `167.235.37.94`, входящий
> UDP снаружи не транслируется (проба 0 из 3). Белый IP есть у FreeBSD
> `201.34.130.46` — поднят WireGuard-мост `10.77.0.0/24` (Ubuntu — инициатор,
> FreeBSD слушает `:51820/udp`; `ubuntu/wireguard/README.md`). Для Windows за NAT
> узлом встречи может служить FreeBSD; домен `1c-gate.timpul.ru` и схема приёма
> остаются решением владельца — замер меняет только представление о том, где
> реально терминируется входящий канал.

🔴 Индекс версий на Windows обновляется **только после applied=true**, как и очередь
чанков (§13, К2).

## 7. Фазы работы

### Фаза 0 — установка Windows (уже есть)

`setup-1c-odata.exe`: IIS, публикация, OData, состав, проверка.  
Позже дополнить: агент, pubkey Ubuntu, URL приёмника, тестовая посылка.

### Фаза 1 — первая полная заливка (один раз)

1. Windows: полная выгрузка сущностей (тот же контур отбора, что у синка).
2. zstd → AEAD → пакет `kind=full` (манифест + чанки).
3. Ubuntu: расшифровка → витрина → полная сборка (`build.sh`).
4. Windows: сохранить локальный индекс версий по всем сущностям.

### Фаза 2 — регулярные такты

Триггер по готовности (как сейчас pipeline), не «всегда полный dump».

На Windows — та же логика, что `serene_sync` / `load_entity_delta`, но против
**локального** индекса версий и с чтением 1С с **localhost**:

1. проба `Ref_Key` + `DataVersion`;
2. diff;
3. дотянуть changed; gone — список ключей на удаление;
4. владелец тихий → ТЧ не читать;
5. дельта неприменима → полная сущность + сравнение содержимого (как сейчас);
6. ноль изменений → пакет не слать (или пустой манифест — лучше не слать).

Ubuntu: apply merge → `search_changed_sources` → сборка только по изменившимся.

Свежесть по смыслу п. 17: цена такта ∝ числу изменений, не размеру базы.

## 10. Ограничения (честно)

- Проба версий всё равно читает все ключи сущности из 1С каждый такт — на **localhost**
  терпимо; через интернет без локального индекса — нет.
- Сущности без `DataVersion` (часть регистров и т.п.) — редкая полная пересылка или
  отдельный отпечаток на Windows (тяжелее).
- Ложные срабатывания `DataVersion` (регламентная перезапись в 1С) — лишний трафик,
  не неверные данные (как сейчас).
- Потеря индекса версий на Windows → нужен `full` resync.
- Данные клиента физически на Ubuntu — периметр/договорённость с клиентом не снимается
  шифрованием транзита.
- TARGET п. 4/16 этим планом **не закрываются** — откладываются явно.

## 12. Одной строкой

## 13. Сверка с боевым кодом (06.08, разбор по `serene_sync` / `poc_load_entity`)

План сверен с кодом построчно (`serene_sync.py` 546 строк, `poc_load_entity.py` 885,
`odata_census.py`, `build.sh`, `corpus_build.sql`). Вывод: разрез «producer на Windows /
apply + сборка на Ubuntu» ложится на существующие границы — вся OData-часть (~1,6 тыс.
строк чистого stdlib-Python) отделяется от записи в витрину; `DataVersion` сравнивается
как непрозрачный токен на равенство. Схема рабочая. Ниже — что в плане отсутствовало.

### Блокирующие пробелы (без них не заработает)

- **Б1. `$metadata` читает не только синк — его читает сборка корпуса.**
  `corpus_build.sql:35` тянет `$metadata` прямо с шлюза (`read_text`, 16,6 МБ XML;
  HTTP-секрет создаёт `build.sh`). При «Ubuntu до 1С не ходит» сборка теряет источник
  схемы: классификация колонок, имена, ссылки, `written_by`. Решение: `$metadata` едет
  в пакете (при `full` и при изменении отпечатка), `corpus_build` переключается на
  чтение из витрины. Это шаг №0, а не деталь.
- **Б2. Контур отбора сущностей — на двух сторонах.** `only_binary` вычислим на
  Windows из `$metadata`, но `search_entity_class` пишет модель на Ubuntu
  (`classify_entities.py`), `search_entity_force` — слово владельца в базе Ubuntu.
  Агент обязан получать итоговый список «что грузить» конфигом через `GET
  /agent/config` (см. §6) — иначе разметка задублируется (второе место истины) или
  застынет навсегда.
- **Б3. Контрактные таблицы синка пишет apply на Ubuntu.** Сейчас синк пишет
  `base_profile`, `search_entity_skipped`, `search_changed_sources`,
  `search_quality(mart_changed_ts)` — публичный контракт со сборкой и ботом (экономия
  пересборки, видимость исключённого по п. 13 TARGET). В §8 приёмник назван, а эта
  обязанность — нет. Без `search_changed_sources` сборка не поймёт, что изменилось.

### Подводные камни

- **К1. Защита от ложных изменений останется на Ubuntu.** «Полная загрузка без
  изменения содержимого ≠ изменение» сейчас делает движок (сравнение содержимого
  против текущей таблицы, `poc_load_entity.py:840-844`). На Windows его нет → каждая
  полная загрузка объявит витрину изменённой → холостая пересборка корпуса 780 с ×
  каждый такт (ровно это чинили 05–06.08). Цена — не трафик (§10), а пересборка.
  Лечение: **контент-хеш в локальном индексе версий** поверх `DataVersion`; он же
  закрывает сущности без `DataVersion` (1018 источников, 573 с такта): «частое чтение
  + редкая отправка» вместо «редкой полной пересылки».
- **К2. Атомарность «индекс версий ↔ applied=true».** Индекс обновляется только после
  `applied=true` (как очередь чанков). Обрыв между «витрина применила» и «индекс
  сохранён» → рассинхрон с нулевым diff: агент никогда не догонит пропавшее.
- **К3. Проверка «одна версия на Ref_Key».** Сейчас дельта отвергается при mix версий
  в витрине (`poc_load_entity.py:610-616`). На Windows проверять не против чего:
  инвариант держит локальный индекс, а apply на Ubuntu перепроверяет и требует full
  resync сущности при нарушении.
- **К4. «Тихий владелец» и порядок.** Решение «не читать табличную часть» принимается
  по дельте владельца внутри такта. Владелец и его части едут в одном пакете (или
  apply гарантирует владельца раньше) — иначе корпус соберётся по новому документу
  со старой ТЧ.
- **К5. Скрытый контракт формата — самое молчаливое.** `_cell`: булевы как JSON
  `true/false` (не Python `True/False`), дата-время с пробелом вместо `T`, `safe_col`,
  CSV all-varchar. От этого зависят `row_key` всех строк корпуса. При порте на C#
  разъедется без единой ошибки → массовый ложный «изменилось» + переэмбеддинг корпуса
  (деньги эмбеддера). Лечение: **golden-проба** — эталонные ответы OData → CSV
  Python-версии, вывод агента сверяется побайтно. Шаг плана до E2E.
- **К6. Самонастройку страниц переносить как есть.** «Прочитали без `orderby`, данных
  больше страницы → сначала с `orderby`», уменьшение страницы вчетверо при отказе 1С —
  вылизано замерами (`ETL_PAGE`). «Упрощение» при порте вернёт уже оплаченные дефекты.
- **К7. Атомарность apply.** §6 описывает commit по полноте чанков, но не
  транзакционность применения: падение apply посередине пакета оставит витрину в
  полусостоянии. Нужен откат по пакету + карантин битого + повторная доставка.
- **К8. Endpoint в интернете.** TLS с пином сертификата, auth на самом status API,
  лимиты размера и частоты на карантин — иначе диск забивается чужими «чанками».
- **К9. Побазовость.** `package_id`/манифест несут идентичность базы с первой версии
  (принцип проекта: у каждой базы свой контур целиком).
- **К10. `manifest_version` с первого дня и «тупой агент».** Доступ к Windows разовый,
  а формат будет меняться (Б1–Б3). Всё, что можно обновлять, живёт на Ubuntu; агент —
  минимум логики, максимум по конфигу; приёмник принимает старые версии манифеста или
  честно отказывает с ошибкой, видимой в мониторинге. Главный эксплуатационный пункт
