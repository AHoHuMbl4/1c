## 1. Краткий вердикт

Таймаут **curl `-m 120`** и HTTP-клиент ask **`ds_chat_post(..., timeout=120)`** совпадают по потолку. Когда wall >120 с, типичнее всего **один или несколько последовательных вызовов LLM** упираются в 120 с (очередь GPU, холодный мультисэмплинг разбора, редко — тяжёлый compose), а не SQL/embed/реранкер.

На **дороге clarify (исход C)** — текущий исход С4 после `5174b8c`/`2c18fc6` — compose/гейт **не вызываются**. Узкое место смещается в **разбор намерения (×N)** + **выбор сущности** + **два прохода детектора развилки** (~5–10 с SQL суммарно, остальное — LLM и реранк).

На **дороге answer (исход B, старые прогоны)** — полный пайплайн с compose (~9k prompt tokens) давал **~21 с** wall при нормальной GPU (`k6-dead.txt`); под нагрузкой или с retry гейта — кратно больше.

## 3. Путь вопроса по коду (последовательность, таймауты, LLM)

Точка входа: `answer()` в `z20_ask_main_http.py` (~1977+).

### 3.1. Общая лестница

```
POST /ask
  → parse_intent()                    [z02, до первого шаг()]
  → apply_period_leader / preds       [z03/z04, SQL+meta]
  → шаг «разбор вопроса»
  → отбор буквально / смысл / vector  [z06/z07, embed+BM25]
  → K6 v2 rank pool                    [z10, опционально]
  → fork_detector_scan #1              [z09, SQL fork_scan]
  → try_entity_form / event clarify    [z05, SQL если ASK_ENTITY_FORM]
  → pick_entity + arb_pool             [z16, LLM]
  → fork_detector_scan #2 + outcomes   [z09/z13]
      ├─ A/B unique → ответ без compose (atom)
      ├─ B defer → rank → aggregate → compose → gate
      └─ C → fork_outcome_c → clarify_say [без LLM] → seal_clarify
  → (если не вышли) aggregate → compose → gate [z08/z18]
  → (legacy clarify) clarify_text()    [z07, LLM max_tokens=120 — не на fork C]
```

### 3.2. Вызовы LLM (`ds_chat`), лимиты и таймауты

| Вызов | Где | Условие | `max_tokens` | HTTP timeout |
|---|---|---|---:|---:|
| `_one_intent` | z02 | каждый семпл разбора | **400** (`ASK_INTENT_MAX_TOKENS`) | **120 с** |
| retry intent JSON | z02 | если первый ответ не JSON | 400 | 120 с |
| `pick_entity` | z16 | ≥2 кандидата | **120** | 120 с |
| `compose` | z18 | answer/figures | **800** | 120 с |
| compose **retry** | z20 | гейт отверг | 800 | 120 с |
| `arbitrate` | z01 | ≥2 готовых ответа | **8** | 120 с |
| `clarify_text` | z07 | legacy clarify | 120 | 120 с |
| `refuse_text` | z07 | отказ | 60 | 120 с |
| rank hint | z10 | K6 measure hint | 80 | 120 с |

**Мультисэмплинг разбора:** `ASK_INTENT_SAMPLES=5`, `ASK_INTENT_LEAD=3` — цикл до 5 вызовов `_one_intent`, каждый до **2×** ds_chat при bad JSON (`z02_intent.py:661–664`). **Холодный потолок:** до **10** LLM-вызовов только на intent.

**Память:** `ASK_INTENT_MEMO=512` — повтор того же текста в тот же день **без** intent-LLM (до `2c18fc6` мемо давало ложный «быстрый» разбор — отдельный инцидент).

**Embed:** `EMB_TIMEOUT` + retry; типично **0,04 с** (`LATENCY_AUDIT_2026-08-26.md`).

**Rerank:** `timeout=30`, `ASK_RERANK_TOP=60` — на С4 в k6-dead **60/67** кандидатов.

**Не LLM:** `fork_scan` — 2 SQL на проход (`z09_fork_detector.py:233–307`); при нескольких readings — `fork_scan_readings` умножает окна.

### 3.3. Сколько LLM на типичных дорогах С4

| Дорога | Исход | LLM calls (норма) | LLM calls (холод, intent×5) |
|---|---|---:|---:|
| **Clarify C** (29.08+) | fork C | **1–2** (intent с lead + pick) | **до 11** (5–10 intent + pick) |
| **Answer B** (complement defer) | figures/answer | **3–4** (+ compose) | **до 12** |
| **Answer** (k6-dead) | answer+gate | **5** (3+1+1) | **до 13** (+ retry gate) |

На clarify C **`clarify_say`** (`z20:342–364`) формирует текст из options **кодом**; `clarify_text` (LLM) на этой ветке **не зовётся**.

### 3.4. Что удлиняет путь именно для complement/count «позиций»

1. **Широкий пул K6:** «позиций» + «продаётся» → **~80–95** кандидатов, rerank **60**, K6 v2 SQL (`k6-dead`: 82 канд.).
2. **Два fork_scan:** ранний (pool ≤16–64) + исходы по **arb_pool** (3+ src) — см. `z20:2827–2886`, `3649–3708`.
3. **MTD period readings:** `period_leader=mtd` → preds на месяц; при `ASK_ENTITY_FORM=0` каталог в fork получает date-pred → **`no_live_cells`** → лишние классы / исход C (`C4_K6_BREAKDOWN` §2.2).
4. **Complement SQL** (если `ASK_ENTITY_FORM=1`): `entity_form_compute("complement")` — каталог + DISTINCT по sales (`z05:1073–1081`); не вызывается на текущем clarify C без флага.

### 3.5. Почему curl «ровно» >120 с

- Клиенты приёмки: `curl -m 120` (`work/acceptance/probe-okna-ask.sh`, `ubuntu/serenedb/golden.sh`).
- Сервер: `urllib.request.urlopen(..., timeout=120)` в `ds_chat_post` (`z01:538`).
- Один зависший/очередной chat completion **≈120 с** → curl обрывается **без тела**; в журнале может не быть финального `ask … 200`.

При **нормальной** GPU и clarify C ожидаемый порядок — **15–40 с** (см. декомпозицию F1 и audit clarify GAP 12–23 с на других вопросах), не 120+.

## 5. Топ-3 причины по влиянию (механизмы, не «подогнать слова»)

### 1. Очередь / потолок LLM 120 с (главный кандидат для >120 s)

- Жёсткий **`timeout=120`** на каждый `ds_chat` = потолок **curl -m 120**.
- Холодный intent: до **10** последовательных вызовов × ~4 с (audit) = **~40 с** в норме; при конкуренции GPU (тест владельца на том же `Qwen3.8-27B`) каждый вызов растягивается → **сумма или один вызов ≈120 с**.
- **Мерить:** `TRACE … model TOKENS` с `rid`; `diag.tokens.calls`; метки vLLM queue time.

### 2. Мультисэмплинг разбора намерения (`INTENT_SAMPLES` / `INTENT_LEAD`)

- Контракт п.3: согласие полей через несколько прогонов (`z02:625–664`).
- На «позиций» / «продаётся» разбор нестабилен (`kind` «базы» vs «позиции» в bench `work/k6-rank-v2/dumps/positions5.json`) → чаще **3–5** семплов.
- **Мерить:** `diag.parse.samples`, `diag.parse.unstable`; отдельный `шаг` вокруг `parse_intent` (audit §7.1).

### 3. Двойной детектор развилки + широкий K6-пул (SQL + Python, усилитель latency)

- Два вызова `fork_detector_scan` на пути к исходам (`z20:2850`, `3669`).
- Пул **O(arb_pool × readings × measures)**; SQL `cost_ms` **0,5–2,5 с** каждый, wall fork **3–8 с** (audit + k6-dead).
- Само по себе **не объясняет 120 с**, но **удлиняет окно**, пока GPU занята, и добавляет работу до/после LLM.
- **Мерить:** `diag.fork.cost_ms` обоих проходов; `diag.fork.pool`; число `period_readings`.

**Не в топ-3:** embed (0,04 с), rerank (0,12 с), буквальный отбор (0,03 с) — подтверждено audit 26.08.
