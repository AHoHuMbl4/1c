## 3. Незамеченные расхождения, где сводка молча взяла одну сторону

**(A) `NULL` в механизме (а) — пропущено, и это существенно.**
В таблице 3.2 стоит «NULL: не описано [1]», а в 4.3 разбор NULL идёт только для (б) и (в).
[мой замер] на живом движке, одна строка `(1 AS id, TRUE, FALSE, NULL::VARCHAR, 'y')`:

```
(а) json_each : bf: false | bt: true | id: 1 | n: null | s: y     <- в текст попадает слово "null"
(б) json_keys : id: 1 | bt: true | bf: false | n:  | s: y         <- пустое значение, ключ остаётся
(в) UNPIVOT   : id: 1 | bt: true | bf: false | s: y               <- ключ выброшен
```
То есть механизм (а) **пишет в `doc` литерал `null`** — мусорный терм в инвертированном индексе и
в эмбеддинге на каждый пустой реквизит. Это довод против (а), которого в сводке нет вовсе.
Вывод сводки «ни один из трёх не воспроизводит `t`/`f`» — **подтверждаю**: все три дали `true/false`.

**(B) Множество строк у [1] и у [3] — разное, а сводка сравнивает как одно.**
Разд. 4.1: «4,4 с [1] против 4,2 с [3] … расхождение практически отсутствует». Но у [1] 96 931
строка, у [3] — 97 965. [мой замер]: `SELECT count(*), count(DISTINCT src_table) FROM search_corpus`
→ **97965 | 226**. То есть корпус собран ровно из **226** таблиц и содержит 97 965 строк —
множество [3] совпадает с боевым, множество [1] (233 таблицы, 96 931 строка) **не совпадает**
ни по таблицам, ни по строкам. Сводка выбрала сторону «эти цифры сопоставимы» без основания.

**(C) «Такт при нуле изменений 0,85 с [2]» противоречит собственному разд. 4.2 сводки.**
0,85 с у [2] = 0,089 (`reltuples`) + 0,041 (`duckdb_columns`) + 0,711 (дайджесты). А в 4.2 сводка
сама постановляет: «обнаруживать изменения `reltuples`'ом нельзя — ни в версии [2], ни в какой
другой», и точный счёт берётся сгенерированным `UNION ALL` (0,214–0,266 с). С этой заменой цифра
становится ≈ 1,0 с, а не 0,85 с. Внутреннее противоречие, не отмеченное.

**(D) Решающий фактор скорости — `ORDER BY`, а не механизм.** Сводка сравнивает механизмы,
не выравнивая политику сортировки (у (а) сортировка есть, у (в) в лучшем замере нет), и на этом
строит вывод. Разрешено моим замером, разд. 4.

### 4.2. `sha1` движка = `hashlib.sha1`, включая кириллицу и `chr(0)`
[мой замер] (движок ⟷ python3):
```
sha1('Контрагент: ООО Ромашка | Сумма: 100') = 21a373c088fa55aff8c340c389c72a76014fb7aa  (совпало)
sha1('Контрагент: ООО Ромашка')              = 54958b51121e123c13d899ef5b75eace06c829fa  (совпало)
sha1('Ёжик'||chr(0)||'тест')                 = c2909b4bec1d71778b7a9b79af16ff669e1557cc  (совпало)
```
Последняя строка закрывает и склейку `doc || chr(0) || refs` — сводка её не проверяла отдельно.
**Утверждение сводки верно.**

### 4.3. `pg_class.reltuples` против `count(*)`

### 4.4. Три механизма сборки строки — выполнил все три
**Одна таблица `catalog_поляформстатистики` (23 878 строк, 20 колонок, 5 BOOLEAN), `doc` + `sha1`,

## 6. Годен ли раздел «Порядок работ»

Как каркас — да: шаги 1–3 действительно только чтение, у каждого есть проверка, точка принятия
решения (шаг 3) названа явно, дайджесты правильно поставлены последними и с блокирующим
сценарием (б). Но как руководство по **боевому** корпусу есть четыре дыры:

1. **Шаг 0 не даёт точки возврата.** Снимаются `(src_table, row_key, doc_hash)`. Не снимается
   `emb`. [мой замер]: в корпусе 97 965 строк и **у всех 97 965 заполнен `emb`**; существующий
   `search_corpus_bak` **не годится как бэкап — в нём нет колонки `refs`** (колонки:
   `src_table,row_key,doc,doc_hash,amount,doc_date,emb`). Значит откат после исхода В (полная
   переэмбеддировка) невозможен, а это единственный необратимый и платный исход всего плана.
   Требование: шаг 0 обязан сохранять `emb` вместе с ключами и `doc_hash`.
2. **Шаг 4 внутренне невыполним как написан.** Проверка (в) — «после MERGE + `VACUUM
   (REFRESH_INDEX)` запрос `FROM search_idx` находит новые строки» — относится к боевому
   `search_idx ON search_corpus`, а MERGE по плану идёт в **копию**, у которой индекса нет;
   создать его нельзя, `CREATE INDEX` отложен до шага 7. Либо проверка (в) переносится в шаг 5,
   либо в шаг 4 явно включается создание индекса на копии (с ценой и окном).
   Плюс не сказано, что копия корпуса — это ~98 тыс. × `FLOAT[1536]` дискового объёма.
3. **Шаг 7 — единственный шаг, способный уронить ответы бота, и у него нет ни отката, ни
   оговорки о простое.** `DROP INDEX search_idx; CREATE INDEX …` на боевой таблице: между DROP и
   завершением CREATE поиск не работает, а поведение в этот момент сама же сводка держит в
   непроверенном (разд. 5, п.8). Должно быть: делать на копии таблицы, а не на боевом индексе;
   если на боевом — с явной остановкой бота и заранее сохранённым DDL из `search_meta`
   (`duckdb_indexes().sql` состав индекса не отдаёт — проверено, см. 4.5).
4. **Шаг 1 содержит непроверяемый критерий**: «такт стал короче ровно на время запуска процессов»
   — это прогноз, а не проверка. Проверяемое здесь: совпадение множества таблиц и суммы строк
   (оно в шаге и есть) — этого достаточно, прогноз убрать.

Отдельно: в шаге 2 не задана политика `ORDER BY`, хотя по моему замеру она стоит дороже выбора
механизма (×3,2–4). Её надо фиксировать вместе с формулой `doc`, иначе A/B меряет не то.
