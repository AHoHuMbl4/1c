## 1. Что было сломано

**Два разных дефекта, найдены один за другим 14.08.**

### 1.1 Падение apply по памяти (закрыто, `1e3e487`)

Буфер читателя CSV = 16 × `maximum_line_size` (доки: Data import and export ›
Csv › Overview › Parameters) и берётся **на каждый** `read_csv` в `UNION ALL`.
Предел строки прижимался к размеру файла, поэтому сущность из 18 чанков по 32 МБ
просила 16 × 32 МБ × 18 = **9,2 ГБ** при `memory_limit` 9,3 ГиБ — apply падал
каждые 2 минуты. Мельче резать чанки бесполезно: общий буфер = 16 × объём
сущности и от нарезки не зависит.

Починено: предел считается по факту — самой длинной строке в файлах
(`_longest_raw_line`, проход `bytes.split`, 0,027 с на 27 МБ), ×8 запас на
записи с переводами строк внутри кавычек, пол 1 МиБ. Для klient-1: предел
32 МБ → 1 МиБ, буфер 9,2 ГБ → 288 МиБ.

### 1.2 Молчаливая потеря строк (закрыто в коде, `1e42ba1`)

`_full_sql` дедуплицировал `QUALIFY row_number() OVER (PARTITION BY ключ) = 1`
по ключу из `$metadata`. **Ключ — заявка источника об исходной сущности, а не
свойство строки:**

```xml
AccumulationRegister_X            Key = (Recorder, Recorder_Type)   ← одна запись на ДОКУМЕНТ
                                  Property RecordSet = Collection(..._RowType)
AccumulationRegister_X_RecordType Key = (Recorder, LineNumber, Recorder_Type)
Document_X                        Key = (Ref_Key)                   ← строки табчасти внутри
```

Агент разворачивает вложенный список в плоские строки (`Flatten.Rows`,
`PacketAgent.cs:807-858`) — это верно, — но кладёт в манифест **родительский**
ключ (`res.Key = _meta.DeclaredKey(e)`, строки ~2314 и ~2371). После разворота
он строку не различает, и дедуп оставлял **одну строку на документ**.

Доки о прежней форме говорят прямо: без `ORDER BY` выбранная строка *«is not
defined and can be any row»* — то есть оставалась ещё и произвольная.

Починено: дедуп по **полной строке** (`SELECT DISTINCT *`) — снимает ровно то,
ради чего заводился (полные повторы от перекрытия страниц 1С и переотправки
чанка). Добавлены два счётчика в журнал: `_check_key_identifies` (сколько строк
делят ключ) и `_check_rows_landed` («прислано N, легло M, снято повторов K»).

## 3. Что осталось — по шагам

### Шаг 1. okna: переприменить порции (главное)

🔴 **Из 1С ничего перечитывать не нужно.** Все 35 порций лежат на приёмнике
целыми — 393 МБ, с чанками (`000002-353d4a59/chunk-00001.csv.zst.age` и т.д.).
Агент прислал всё; потерял строки **apply**. Значит их надо применить заново
исправленным кодом.

Приёмник берёт в работу пакет, у которого в `<pkg>/state.json` стоит `verified`
и `seq > last_applied_seq` базы, и применяет **по порядку seq**
(`_iter_verified`, сортировка по `(base, seq)`). Сейчас у всех 35 стоит
`applied`, `last_applied_seq: 35`. Сброс пометок прогонит всю историю заново —
полные заливки, дельты, удаления в том же порядке — и даст состояние, какое
было бы, будь приёмник исправен с самого начала.

**Перед сбросом остановить сборку корпуса**, иначе она соберётся по
полуприменённой витрине: `1c-serene-pipeline@postgres.timer` тикает каждые
2 минуты.

```bash
ssh root@167.233.249.110

systemctl stop 1c-serene-pipeline@postgres.timer

cd /var/lib/1c-packet/inbox/okna-1
tar czf /root/okna-state-$(date +%Y%m%d-%H%M%S).tgz state.json */state.json

python3 - <<'EOF'
import json, glob
base = '/var/lib/1c-packet/inbox/okna-1'
n = 0
for p in sorted(glob.glob(base + '/0000*/state.json')):
    d = json.load(open(p))
    if d.get('state') == 'applied':
        d['state'] = 'verified'
        json.dump(d, open(p, 'w'))
        n += 1
st = json.load(open(base + '/state.json'))
for v in st.get('packages', {}).values():
    if v.get('state') == 'applied':
        v['state'] = 'verified'
st['last_applied_seq'] = 0
json.dump(st, open(base + '/state.json', 'w'))
print('переведено в verified:', n)
EOF

systemctl start 1c-packet-apply
journalctl -u 1c-packet-apply -f
```

Один заход apply применяет **все** накопленные пакеты подряд (`main` идёт по
списку `_iter_verified`), так что прогон непрерывный, а не по одному в 2 минуты.
Оценка — 20–40 минут на 393 МБ.

**Чего ждать в журнале:** строки `прислано N, легло M, снято полных повторов K`
и `объявленный ключ … НЕ различает строки` — это новые счётчики, так и надо.

**Риск, который надо знать:** новый дедуп оставляет обе версии `Ref_Key`, если
они пришли в одной порции (перекрытие страниц 1С). Инвариант «одна версия на
Ref_Key» (К3) это ловит и ставит пакет в **карантин** — раньше старый код такие
строки молча схлопывал. Если увидите `QUARANTINE base=okna-1 pkg=… code=mix_versions`
— данные не потеряны, пакет просто не применён; разбираться отдельно.

**Откат дешёвый:** пакеты на диске неизменны, состояние — в бэкапе; повторять
можно сколько угодно.

## 4. Мои ошибки в этой работе

Записаны, чтобы не повторять.

1. **Дважды предложил заход на Windows, когда он исчерпан и не нужен.** Сначала
   для okna («удалить `EntityIndex`»), и это было прямым нарушением известного
   ограничения владельца — один шанс, доступ закрыт. Хуже того, предложение было
   **не нужно по существу**: порции лежат на приёмнике, и данные восстанавливаются
   переприменением. Правильный вопрос — «где данные сейчас», а не «как заставить
   агента прислать снова».
2. **Сначала лечил не ту причину.** Увидев подсказку движка «Reducing the number
   of threads», выставил `PACKET_APPLY_THREADS=4`. Не помогло: сменилась лишь
   формулировка ошибки. Подсказка называет ходовые рычаги, а не вашу причину.
   `SET threads` у движка **глобален** — на klient-1 значение 4 живёт до
   рестарта движка.
3. **Дефект нашёлся случайно.** Чинил падение по памяти и заглянул в счёт строк.
   Полгода никто не сверял «прислано против легло» — потому потеря и была не
   молчаливой, а невидимой. Отсюда `_check_rows_landed`: у каждого шага, где
   строк может стать меньше, должен быть свой счёт до и после.
4. **Тест закреплял дефект.** Проверка «дедуп по уцелевшей части ключа
   (LineNumber)» ожидала выброшенную строку как правильное поведение. Тест на
   одном файле проходил и при неверной формуле — проверять надо на рабочем
   числе элементов.
5. **Перебирал ключи по релею и мог схватить бан.** fail2ban оказался ни при чём
   (`unban` вернул 0), но три отказа подряд — плохая практика; сначала выяснять
   пользователя по докам, потом стучаться.

## 5. Окружение: что мешает и как обходили

- **Дев не видит релей `89.23.101.22`** — ни 22, ни 443. `mtr`: пакеты умирают
  за краем Hetzner (`213.239.224.98`); до okna тот же путь доходит целиком.
  Встречное направление тоже закрыто (с юнита порт 22 дева недоступен).
  `fail2ban` на релее — один джейл `sshd`, `unban` вернул 0. Похоже на
  фильтрацию Hetzner↔Timeweb, вопрос к хостеру. **Юнит klient-1 достижим только
  через релей**, поэтому фикс туда выкатывали заплаткой через сессию владельца.
- **Приём заплатки на изолированную машину:** `git diff` → `gzip -9` → `base64`
  → here-doc в сессии владельца → `patch -p1`. 8 КБ вместо 35 КБ файла, и
  сжатие снимает риск поехавших пробелов в контексте diff.
- **Сессии среды не пишут на прод-машины** (запись файлов и запуск юнитов
  блокируются рубежом среды) — все изменения на юнитах делает владелец
  командой в своей сессии.
- **`SERENEDB_DSN` в `/etc/1c-packet.env` записан без кавычек.** systemd читает
  верно, а `. /etc/1c-packet.env` в bash разбирает строку как четыре
  присваивания: переменной достаётся `host=127.0.0.1`, и psql уходит в 5432.
  Поэтому DSN передаётся строкой прямо в команде.
