# Самопроверка контура ответов ИЗ ДАННЫХ — базовое число слепого пятна

План: [`PLAN_ANSWER_CONTRACT.md`](PLAN_ANSWER_CONTRACT.md) §4 (состязательная
самопроверка) и замок 17 (§10: «слепое пятно — число, рост метрики — брак»),
фаза 4 [`PLAN_AUTONOMY.md`](PLAN_AUTONOMY.md) (приёмочный набор строится из базы).
Мерило — TARGET.md пп. 10, 15, 19, 20.

Слепое пятно — деловая сущность, которую конвейер не может выбрать никогда:
ни одна поверхность отбора не доносит её до кандидатов ни одним её собственным
словом. Такая сущность не видна ни в одном ответе, и никакая правка шага 4
(выбора) этого не изменит — чинить надо поверхность, словарь или разметку.

## Метод: два яруса

### Ярус 1 — поверхности напрямую, без модели (основная метрика)

Прибор: `work/acceptance/selftest_surfaces.py`. Для каждой деловой сущности
(`search_tables` минус `search_entity_class.cls='service'`) берутся её слова
из самой базы — метка (`label`) и ВСЕ человеческие алиасы
(`search_entity_alias.aliases`); значений данных в словах нет (п. 19). Каждое
слово прогоняется через продуктовые функции `serene_ask.py` — те же, что зовёт
бой (`meaning_candidates` + шаг 2), с боевым порогом `MEANING_TOP` (= 50):

| Поверхность | Функция продукта | Что проверяется |
|---|---|---|
| `alias` | `alias_hits` | словарь синонимов (`alias_idx`, ts-запрос) |
| `card` | `card_hits` | слова карточки (название, синонимы, величины, реквизиты) |
| `literal` | `probe` → `match_expr` → `tables_of` | буквальное совпадение слова со строками корпуса сущности |
| `vector` | `near_tables` | место сущности в ПОЛНОМ векторном порядке карточек; достижима, если не дальше боевого порога |

Правила замера:

- табличная часть засчитывается за свой документ (`search_tables.parent`) — как
  в `candidate_surfaces_bench.py`;
- первое попадание закрывает сущность (достигнутая дальше не проверяется);
  недостижимость доказывается полным перебором всех слов на всех поверхностях;
- эмбеддер спрашивается один раз на прогон (`embed_model_live`); лёг — векторная
  фаза пропускается целиком, и это видно в отчёте (`vector_live: false`):
  у боя в этот час та же картина;
- вектор сущности (`has_emb`) проверяется по отметке переписи
  `emb_model_<таблица>` и `emb IS NOT NULL` — по данным, а не по живости сервиса.

🔴 Честная граница: в бою вход поверхностей богаче (разбор модели даёт
словоформы, смысловая поверхность спрашивается всем вопросом). Поэтому число
яруса 1 — ВЕРХНЯЯ оценка слепого пятна: недостижимое своими же словами
недостижимо наверняка, достигнутое здесь в бою может быть потеряно позже
(разбор, шаг 4) — это уже предмет яруса 2.

Классы причин промаха: `нет алиаса` (словарь сущности пуст, слово одно —
метка), `буквально пусто` (лексика пуста, вектор не измерен), `нет вектора`
(`emb IS NULL`), `вектор рядом` (место ≤ 3× порога), `вектор далеко`.
Отдельно считается `service`-подозрение: сущность размечена service, но имеет
человеческие алиасы — то есть исключена из контура при том, что «о таком
спрашивают».

Детерминизм (замок): на неизменной базе два прогона дают байт-в-байт одинаковый
per-entity файл — проверено повторным прогоном postgres (diff пуст). Файлы:
`work/acceptance/runs/selftest-<база>-surfaces.jsonl` (строка на сущность) и
`…-report.json` (метрика, расклад классов, поимённые промахи).

Контроль прибора (замок «откат на 5 рукотворных случаях»): прогон `--only` по
заведомо достижимым сущностям — postgres: `catalog_контрагенты`,
`document_реализациятоваровуслуг`, `catalog_номенклатура`, `catalog_банки`,
`catalog_валюты` — 5 из 5 подтверждены; ut_test: `document_реализациятоваровуслуг`,
`catalog_номенклатура`, `catalog_склады`, `document_поступлениетоваровнасклад`,
`catalog_партнеры` — 5 из 5 (у `catalog_номенклатура` первой сработала
поверхность `alias`, у остальных `card`). Контроль пишет в
`…-surfaces-probe.*`, полный снимок не затирается. Побочный замер контроля:
два несуществующих в витрине имени (`document_поступлениетоваровуслуг` и
`accumulationregister_продажи` — в УТ 11.4.9 этой витрины их нет) прибор честно
пропустил, а не «подтвердил».

### Ярус 2 — живой путь через /ask (стратифицированная выборка)

Приборы готовы: `selftest_generate.py` (детерминированный список вопросов из
меток/алиасов/величин базы), `selftest_sample_tier2.py` (каждая 10-я сущность

`selftest_run.py` (последовательный прогон через живой `/ask`, один вызов на
вопрос, без ретраев; пути списка/результата — `SELFTEST_LIST`/`SELFTEST_OUT`),
`selftest_check.py` (достижимость по `diag.focus`/вариантам + сверка атома

детерминированно ~10 % (двойной прогон sampler'а — diff пуст). Прогон —
на замороженном коде с живым эмбеддером и реранкером: мерить живой путь по
движущемуся коду или с мёртвым смысловым контуром нельзя — число протухнет.

## Базовое число (замер 15.08)

Замер снят в ТРЁХ конфигурациях. Сначала эмбеддер дева был мёртв (адреса на
несуществующий хост — activeContext 13.08), днём 15.08 дев переключён на живой
хост `lr0r1k1g-*` (владелец; ключи эмбеддера обновлены следом — первые были от
мёртвого хоста, `embed_check` при этом врал 0, потому что судил по `/health`
без авторизации; прибор починен живым вызовом, разбор — `HOW_NOT_TO §3.78`).
Поэтому у postgres три числа, у каждого — своя конфигурация:

| База | Конфигурация | Деловых | Недостижимо | Доля |
|---|---|---|---|---|
| postgres | без словаря, без вектора | 178 | 43 | **24,2 %** |
| postgres | с вектором, без словаря | 178 | 0 | **0 %** |
| postgres | со словарём и вектором | 178 | 0 | **0 %** |
| ut_test | со словарём, без вектора | 697 | 134 | **19,2 %** |
| ut_test | со словарём и вектором | 697 | 0 | **0 %** |

Ход замера и его честность:

- «без словаря, без вектора» (postgres): словарь синонимов на базе был пуст
  целиком (`search_entity_alias` — 0 строк), эмбеддер мёртв. Класс всех 43
  промахов — «нет алиаса», доносила практически одна `card` (135 из 178).
- «с вектором, без словаря» (postgres): снято ДОСЧЁТОМ, а не прогоном — живой
  прогон стартовал до построения словаря, но прочитал его уже построенным.
  Досчёт (`selftest_vector_probe.py`): векторная фаза по единственному слову
  (метке) для 43 промахов первого прогона, чья лексика от словаря не зависит
  (доказано чтением `wiki_alias.sh`: пишет только в `search_entity_alias`/
  `search_measure_alias`). Результат: вектор достал **все 43, из них 41 —
  местом 1** в полном порядке из 231 карточки. Вектор карточки по одной метке
  сильнее всего лексического ряда этой базы.
- «со словарём и вектором» (postgres): живой прогон после построения словаря
  (178/178 алиасов сущностей, 230/230 слов величин — окно 3, коммит `7aaaf26`).
  0 недостижимых; поверхности: `alias` 144, `card` 137, `literal` 46,
  `vector` 2 (сущности, которых не донесла ни одна лексическая поверхность).
- «со словарём и вектором» (ut_test): живой прогон 15.08, 31 мин (векторная
  фаза перебирает все слова лексических промахов — это и есть цена).
  0 недостижимых; поверхности: `alias` 208, `card` 541, `literal` 174,
  `vector` 58. Слепое пятно контура с живым эмбеддером на обеих дев-базах —
  **0**. Механика закрытия 134 прежних промахов ВАЖНА и неочевидна: вектор
  (kNN) закрыл 58, а остальные 76 закрылись ЛЕКСИЧЕСКИМИ поверхностями —
  потому что с живым эмбеддером ожил резолвер (`resolve_values` внутри
  `probe`): слитное слово вне корпуса («Соглашения СКлиентами») разрешается в
  реальные значения записей, и уже они дают выражения для `literal`/`card`/
  `alias`. В первом прогоне (эмбеддер мёртв) резолвер молчал, `probe` отдавал
  пустой список выражений, и лексические поверхности по таким словам не
  спрашивались вовсе. То есть зависимость от эмбеддера у контура двойная:
  смысловая поверхность И резолвер внутри буквального отбора. Из 18
  самостоятельных промахов 16 закрыл резолвер через `literal`, 1 — `card`
  (по алиасу «функция контакта» — тоже через выражения резолвера),
  1 (`catalog_группырассылокиоповещений`) — kNN-вектор.

⚠ В прогонах с вектором реранкер НЕ участвовал: `RERANK_API_KEY` на деве
протух (от мёртвого хоста, 401) — владельцу сообщено. На число яруса 1 это не
влияет: поверхность `near_tables` — чистый kNN, реранк в приборе не зовётся
(ошибка деградирует молча, порядок остаётся). Для яруса 2 ключ обязателен.

### ut_test: разбор

Словарь синонимов здесь построен (697 записей — ровно на деловые сущности), и
все 134 промаха алиасы **имеют** — класс «буквально пусто». Механика промаха
видна в коде боя: выражения для всех лексических поверхностей строит `probe`,
а он отсекает слово с нулём совпадений в корпусе. Слова, которого нет ни в
одной строке корпуса, до `alias_idx` запрос просто не доходит — словарь есть,
но не спрашивается. При мёртвом эмбеддере запасного пути нет.

- **116 из 134 промахов — табчасти** (`document_чекккм_товары`,
  `document_счетфактура*_документыоснования` и т.п.); у 113 родитель достижим —
  риск ограничен величинами, живущими только в табчасти. У трёх
  (`document_распределениедоходовпонаправлениямдеятельности_{доходы,расходы}`,
  и родитель тоже) — недостижимо всё семейство.
- **18 самостоятельных промахов** — это и есть адреса настоящего пятна:
  `catalog_соглашениясклиентами` («Соглашения СКлиентами»),
  `accumulationregister_расчетысклиентамиплан{оплат,отгрузок}`,
  `accumulationregister_расчетыспоставщикамиплан{оплат,поставок}`,
  `informationregister_заданиякраспределениюрасчетовс{клиентами,поставщиками}`,
  `informationregister_номенклатураконтрагентовбэд`,
  `informationregister_графикначисленийкредитовидепозитов`,
  `informationregister_процентныеставкифинансовыхинструментов`,
  `catalog_{группырассылокиоповещений,роликонтактныхлицвсделкахипроектах,
  ролипартнероввсделкахипроектах}` и 5 констант. Общий признак: слитные
  платформенные слова в метке («СКлиентами», «ВСделках») — так не пишет ни
  человек, ни строки корпуса; алиасы, судя по нулю лексики, повторяют ту же
  орфографию. Это вход для словаря развилок/вики-агента: человеческое написание
  («с клиентами», «в сделках») закроет класс без правки кода.
- `service`-подозрений нет: ни одна service-размеченная сущность алиасов не
  имеет (805 служебных на ut_test, 53 на postgres).

### postgres: разбор (конфигурация «без словаря, без вектора» — ЗАКРЫТА 15.08)

На момент первого замера словарь синонимов на этой базе был **пуст целиком**

метка, и класс всех 43 промахов — «нет алиаса». Доносила практически одна
поверхность `card` (135 из 178; `literal` добавлял 10). Оба предсказанных

закрыли пятно целиком — 0 недостижимых в обеих новых конфигурациях.

Поимённо (все 43 — в `selftest-postgres-surfaces-novector.jsonl`, слепок
первого замера):

- **`document_поступлениетоваровуслуг` (+ его табчасть `_товары`)** — главный
  промах: первичный документ, метка «Поступление Товаров Услуг» не совпала
  буквально ни с одной строкой корпуса и не нашлась в карточках других
  сущностей. Родитель недостижим лексически — при мёртвом векторе вопрос
  «сколько поступлений товаров» на этой базе отвечается чужой сущностью.
- **12 табчастей** (`document_реализациятоваровуслуг_товары`,
  `document_*_расшифровкаплатежа` и др.): метка табчасти
  («… Товары», «… Расшифровка Платежа») ни с чем не совпадает. У 11 из 12
  родитель достижим — риск ограничен величинами, живущими только в табчасти;
  у `_поступлениетоваровуслуг_товары` недостижим и родитель.
- Остальные 30 — узкие справочники и регистры сведений
  (`catalog_классификаторбанков`, `informationregister_настройкиучетаусн`,
  `accumulationregister_книгаучетадоходовирасходов` и т.п.): одна метка,
  буквальных совпадений в корпусе нет.
