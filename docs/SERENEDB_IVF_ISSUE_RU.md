# Сборка IVF-индекса на векторах 1536: резкий порог между 5 000 и 6 000 строк

Отчёт составлен 2026-07-27. Все числа ниже — замеры на живой сборке, не оценки.
Скрипт воспроизведения в конце проверен запуском.


## Что мы делаем

Строим IVF-индекс над колонкой `FLOAT[1536]` (эмбеддинги текста, косинус). В таблице
нет ничего, кроме ключа и вектора:

```sql
CREATE TABLE t (row_key VARCHAR, emb FLOAT[1536]);
CREATE INDEX t_idx ON t USING inverted(row_key, emb ivf (metric = 'cosine'));
```

`quant` не указан, то есть остаётся `none` — в 26.07.3 квантизация с косинусом всё
равно отвергается:

```
metric='cosine', quant='sq8' -> ERROR: ivf quantization supports only metric 'l2' or 'ip'
```

---

## Что наблюдается: резкий порог, а не постепенный рост

Форма таблицы и настройки одинаковы, отличается только число строк. В колонке памяти —
прирост общесистемной занятой памяти за время сборки.

| Строк | Результат | Время | Прирост памяти |
|---|---|---|---|
| 1 000 | `CREATE INDEX` | **1 с** | **0 МБ** |
| 5 000 | `CREATE INDEX` | **1 с** | **0 МБ** |
| 6 000 | не завершилось | 90 с (таймаут) | +4 473 МБ |
| 7 000 | не завершилось | 91 с (таймаут) | +4 324 МБ |
| 8 000 | не завершилось | 90 с (таймаут) | +5 653 МБ |
| 10 000 | не завершилось | 400 с (таймаут) | +12 494 МБ |
| 20 000 | не завершилось | 400 с (таймаут) | +13 476 МБ |

**Переход между 5 000 и 6 000 строк — скачкообразный.** Ниже него сборка мгновенна и
не выделяет измеримой памяти; выше — не завершается, а память растёт неограниченно.
Оставленная работать дольше, одна сборка дошла до ~30 ГБ.

Для масштаба: 10 000 × 1536 × 4 байта = **61 МБ векторных данных**. Пик памяти
превышает объём полезных данных примерно **на два порядка**.

### `sdb_ivf_posting_size` порог не двигает

На 10 000 строк изменение размера постинг-листа не меняет ничего:

| `sdb_ivf_posting_size` | Результат | Прирост памяти |
|---|---|---|
| 128 | не завершилось (90 с) | +4 529 МБ |
| 256 | не завершилось (90 с) | +4 255 МБ |
| 1024 (по умолчанию) | не завершилось (400 с) | +12 494 МБ |

## Гипотезы, которые мы проверили по исходникам и отвергли

Мы читали `libs/iresearch/include/iresearch/formats/ivf/` в публичном `main`
(коммит `722c929` от 26.07.2026 — то же поколение, что наша сборка), пытаясь найти
объяснение. Три кандидата не подтвердились:

**1. Размер обучающей выборки.** При `sample_factor = 0` адаптивная формула даёт
`(строки / posting_size) * kTrainPointsPerLeaf` = `(10000 / 1024) * 64` ≈ **625
векторов** ≈ 3,7 МБ. Слишком мало, и растёт плавно по обе стороны порога.

**2. `kMaxTrainSample`.** Ограничение в 4 194 304 тут же ограничивается ещё раз
следующей строкой `sample_size = min(sample_size, rows)`, поэтому при таких объёмах
недостижимо.

**3. Переключение алгоритма кластеризации.** `SuperKMeansGate(d, k, min_k)` требует
**и** `d >= 32`, **и** `k >= min_k` (512, для угловых метрик 4096). При
`posting_size = 1024` число кластеров — порядка десяти. Гейт не срабатывает ни по одну
сторону порога, то есть в обоих случаях работает один и тот же путь `RunLloyd`.

**Причину в коде мы найти не смогли.** Это и есть главный вопрос.

## Две сопутствующие проблемы, найденные по ходу

### Сборка не отменяется

`pg_cancel_backend()` возвращает `t`, клиент `psql` можно убить, а серверная работа
**продолжается** и продолжает выделять память. Остановить можно только рестартом
движка. Точек проверки прерывания в пути построения IVF мы не нашли ни одной
(`centroids.cpp`, `clustering.cpp`, `ivf_writer.cpp`, `quantizer.cpp`).

Это делает цену ошибки высокой: случайная сборка на чуть большей таблице выводит
инстанс из строя до рестарта.

### `SET memory_limit` её тоже не останавливает

Мы ставили `memory_limit = '4GB'` и `'6GB'` на сессию как предохранитель перед
сборкой. Сборка всё равно ушла за 12 ГБ. Похоже, память, выделяемая при построении
IVF, не проходит через учёт движка.

## Воспроизведение

Проверено на 26.07.3 — выражение генерации вектора возвращает 1536.

```sql
-- строится за ~1 секунду, измеримого роста памяти нет
CREATE TABLE t5 AS
  SELECT i::VARCHAR AS k,
         array_transform(range(1536), x -> random()::FLOAT)::FLOAT[1536] AS emb
  FROM range(5000) s(i);
CREATE INDEX t5_idx ON t5 USING inverted(k, emb ivf (metric = 'cosine'));

-- тот же оператор, 6000 строк: не завершается, память растёт неограниченно
CREATE TABLE t6 AS
  SELECT i::VARCHAR AS k,
         array_transform(range(1536), x -> random()::FLOAT)::FLOAT[1536] AS emb
  FROM range(6000) s(i);
CREATE INDEX t6_idx ON t6 USING inverted(k, emb ivf (metric = 'cosine'));
-- для восстановления потребуется рестарт движка
```

## Вопросы

1. **Ожидаемо ли такое поведение при `d = 1536` с настройками по умолчанию, или это
   дефект?** В `tests/sqllogic` максимальная размерность, прогоняемая на объёме, —
   `FLOAT[8]` (50 000 строк); единственный тест выше — `FLOAT[384]` на четырёх
   строках. Есть ли у вас замеры IVF на боевых размерностях: время построения, пиковая
   память, размер на диске, recall?

2. **Какую конфигурацию вы рекомендуете для ~100 000 строк × 1536, косинус?**
   Конкретно: `quant`, `pq_m`, `sdb_ivf_posting_size`, `sdb_ivf_sample_factor`,
   `sdb_nprobe`, `sdb_rerank_factor`.

3. **Квантизация и косинус.** 26.07.3 отвергает `quant` с `metric='cosine'`, тогда как
   в `main` умолчанием уже стал `sq8` и косинус разрешён
   (`server/catalog/index.cpp:343-347`). В каком релизе это доступно?

4. **Планируется ли прерываемость сборки IVF**, и должна ли её память учитываться в
   `memory_limit`?

5. **Поможет ли разбиение данных?** Раз 5 000 строк собираются мгновенно, является ли
   поддерживаемым приёмом построение нескольких небольших IVF-индексов по разделам с
   последующим совместным поиском (`UNION ALL` по top-k каждого раздела), или есть
   причины, по которым это ухудшит recall или скорость?

## Два несвязанных наблюдения, если пригодятся

**`examples/demo4` и `demo5` не запускаются.** Обе используют опкласс `hnsw`:

```sql
embedding hnsw (metric = 'cosine', m = 32, ef_construction = 64)
```

который падает на нашей сборке и, насколько мы видим, на текущем `main` тоже:

```
ERROR: Unknown built-in opclass 'hnsw' on 'embedding' (known: included, ivf)
```

`kKnownOpclassTypes` в `server/catalog/index.cpp:110-113` содержит ровно
`{included, ivf}`; каталога `columnstore/` нет, хотя `scripts/perf/sweep_hnsw.sh:16`
до сих пор ссылается на `columnstore/hnsw.cpp`. Это единственные две демки,
покрывающие боевые размерности (1536 и 3072), то есть ровно то, к чему новый
пользователь обращается первым делом.

**Неизвестный опкласс молча проглатывается `USING secondary`.**

```sql
CREATE INDEX i ON t USING secondary (v bogus_opclass);
-- выполняется успешно; duckdb_indexes() затем показывает:
--   CREATE INDEX i ON public.t USING secondary ();      <- без колонок
```

Тот же DDL через `USING inverted` корректно выдаёт ошибку. Мы наткнулись на это при
тестировании, и это стоило времени, прежде чем заметили, что индекс без колонок.
