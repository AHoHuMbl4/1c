# K6 — ранг сущности: почему «клиенты» → справочник, а не продажи

База: **okna** (gpu-erw:2202, SereneDB `127.0.0.1:7890`, ask `:8091`).  
Дата замера: **27.08.2026**. `serene_ask.py` **не правили** (К5).

Контроль: «сколько клиентов реально покупают?» → эталон SQL **141**
(`COUNT DISTINCT` покупателя за 12 мес на `accumulationregister_реализациятмц`).
Бой отвечает `clarify` по мерам справочника `catalog_контрагенты`
(дней отсрочки / кредитный лимит / 353). Разбор обрыва: [`C4_K6_BREAKDOWN.md`](C4_K6_BREAKDOWN.md).
Флаг `ASK_ENTITY_FORM` оркестратором на `:8092` **закрыт** как гипотеза
(Q1 тот же мусор; Q2 хуже — догадка, п. 12).

Доки SereneDB (обязательный заход):  
[Ranking / Top-K](https://docs.serenedb.com/sql/indexes/inverted/ranking#top-k-queries-and-wand-pruning) —  
`@@` отбирает, scorer в `ORDER BY` ранжирует;  
[Relevance Tuning — Blend in a business signal](https://docs.serenedb.com/cookbook/search/boosting#blend-in-a-business-signal) —  
BM25 (или иной scorer) — обычное число, в `ORDER BY` можно умножать на
бизнес-сигнал (popularity и т.п.).

## 0. Сводка

| вопрос | факт |
|---|---|
| Чем выбирается источник? | Пул (буквально + смысл/синонимы) → эвристики prefer_* → порядок (эмбед+реранкер) → **модель** `pick_entity` → арбитр. Форма F (`distinct_axis`) за флагом, до модели режется гейтом. |
| Есть ли в ранге «сущность отвечает данными»? | **Нет** для `want=count`. Есть только отсев `nums` при `want=sum` и поздний `no_live_cells` в fork по **датному** окну. |
| Почему побеждает справочник? | Лексика: kind=`клиенты`, aliases «клиенты» → `catalog_контрагенты`; у карточек нет продаж, но модель этого не видит как «не отвечает». |
| Мера | `answer_fit` — live DISTINCT оси kind-catalog на регистре vs счёт карточек (считает база, без списка слов). |

## 2. Признак «отвечает ли сущность» — факт

### 2.1. Код

- Ранг пула: буквальные совпадения, tfidf/bm25/RRF по aliases/карточке, cosine по emb, реранкер по **label**. Это лексика/смысл имени.
- Единственный близкий отсев по данным — `with_value` при **sum** (есть ключи `nums`). Для **count** его нет.
- `fork_scan` / `no_live_cells` — про пустой счёт в текущем WHERE (часто дата). Без периода карточки справочника «живы».
- В `pick_entity` в промпт идут matching records и имена величин; **не** идёт «DISTINCT оси kind за окно = N» vs «карточек = M».

Комментарий в коде (~12709): признак «есть спрошенное поле» **уже пробовали и убрали** по замеру 30.07 — но то был stem полей, не live axis fit.

### 2.2. Живой diag okna (`:8091`, user=`k6-diag`)

### 2.3. SQL на том же инстансе

| сигнал | значение |
|---|---|
| карточки контрагентов | **353** |
| DISTINCT Контрагент на `реализациятмц` за 12 мес | **141** |
| `doc_date` у каталога | 357 NULL / 0 дат |
| `doc_date` у регистра | 0 NULL / 77901 дат |
| `nums` каталога | `ТОК_ДнейОтсрочки`, `ТОК_КредитныйЛимит` (= варианты clarify) |
| `nums` регистра | Количество, Всего, … |
| `search_refcols` → каталог | в т.ч. `accumulationregister_реализациятмц\|Контрагент` |
| aliases каталога | «…, клиенты, …»; best_used_for — лимит/отсрочка |
| aliases регистра | продажи/реализация; не «клиенты» |

**Вывод:** ранг чисто лексический/смысловой по именам. Признака «эта сущность даёт атом, отвечающий на вопрос» в выборе нет — справочник побеждает, потому что похож на «клиенты», а не потому что в нём есть покупки.

## 3. Мера `answer_fit` (без списка слов)

Модуль: [`ubuntu/serenedb/entity_answer_fit.py`](../ubuntu/serenedb/entity_answer_fit.py).

Идея = business signal из доков SereneDB (Relevance Tuning): к лексическому порядку добавить сигнал **из данных**.

При `want∈{count,''}` и `kind` → catalog `C` (те же основы label/aliases/best_used_for, что `entity_form_catalogs_for_kind`):

| src | fit | условие (всё в SQL) |
|---|---:|---|
| `C` | 1 | есть карточки (`NOT IsFolder`) |
| `H` = `accumulationregister_*`, ось `search_refcols.target_src=C`, не книга НДС | 2 | `0 < COUNT(DISTINCT refs_map[axis]) < N_cards` в окне (явный period или rolling year) |
| `H` | 1 | distinct == cards |
| иначе | 0 | |

Перестановка: больший fit раньше (стабильно).  
Проверка автономии: на чужой базе нужны только `search_refcols`, корпус с `refs_map`/`flags`/`doc_date` — **имён okna в коде нет**.

На Q1: `fit(реализациятмц)=2`, `fit(контрагенты)=1` → регистр выше справочника.

Напряжение с «сколько у нас всего клиентов?» (эталон 353): оба атома живы и **различны** (353≠141). Мера поднимает регистр и там тоже. По п. 12 честный исход при двух атомах — **clarify** «все карточки / участники движений», а не угадывание. Золото «всего» сейчас ждёт справочник — это конфликт двух эталонов при одной структуре; чинить словом «всего» в коде нельзя. В патче: либо clarify двух атомов, либо ужесточить гейт F/`has_movement` (не считать «движение в пуле» из полного literal dump при пустых terms — на Q1 351 сущность).

## 4. Прибор — числа до / после

Скрипт: [`work/entity-choice/k6_entity_rank_bench.py`](../work/entity-choice/k6_entity_rank_bench.py).  
Набор: `ubuntu/serenedb/ab-gold-okna.tsv` (23). Эталон — `src_table` из SQL.  
«До» = порядок `alias_idx` + expand держателей kind.  
«После» = `reorder_by_answer_fit` при form эталона count/distinct.  
Модель не зовётся. Прогон: okna 27.08, today=2026-08-27.

| | эталон-лидер | в тройке | не найден |
|---|---:|---:|---:|
| **до** | **2** / 23 | **2** / 23 | **15** / 23 |
| **после** | **1** / 23 | **2** / 23 | **15** / 23 |

Почему «после» лидеров меньше: alias-поверхность на «продали*» часто **пуста** (miss=15) — боевой путь там `prefer_entity_for_sales`, не словарь; мера K6 на sum не переставляет. Сдвиг по сути — на count/distinct:

| вопрос | etalon | place до→после | fit |
|---|---|---|---|
| сколько клиентов реально покупают? | `accumulationregister_реализациятмц` | **5 → 1** | 2 |
| сколько у нас всего клиентов? | `catalog_контрагенты` | **1 → 2** | регистр 2, каталог 1 |
| сколько позиций совсем не продаётся…? | регистр (DISTINCT в SQL) | ∅ → ∅ | kind угадан криво («базы») — отдельный дефект Q2/F |

Числа не подгонялись: лидер 2→1 — честный итог набора; выигрыш K6 виден в строке «покупают».
