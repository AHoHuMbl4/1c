# Что мешает работать «из коробки» на чужой базе

Заведён 29.07 по итогам независимой проверки агентами. Здесь только то, что **ломает
работу на незнакомой базе**, а не то, что можно улучшить. Каждый пункт — с местом в коде
и с тем, как проявится у клиента.

Девиз владельца: **автономность, универсальность, непривязанность к базе.** Проверка
перед правкой: *может ли этот код узнать нужное, ничего не зная о конкретной базе?*

---

## 1. 🔴 Резолвер молча мёртв на не-кириллической базе

**Место:** `ubuntu/serenedb/serene_ask.py`, функции `_ngrams` / `_shares_chars`
(`re.sub(r"[^0-9a-zа-яё]", "", s)`).

**Что произойдёт.** Класс символов перечисляет латиницу и кириллицу. На греческой,
японской, турецкой конфигурации **все буквы вырезаются**, строки становятся пустыми,
`_shares_chars` всегда даёт «нет совпадения», и `resolve_values` возвращает пустоту.
Резолвер (слово человека → значение базы) перестаёт работать — **без единой ошибки в
журнале**.

Проверено кодом: `('Αθήνα','Αθηνών')` → False, `('東京','東京商事')` → False, при этом
`('Питер','Санкт-Петербург')` → True. Докстрока рядом утверждает «работает на любом
языке» — **это неверно**.

**Как чинить:** посимвольный `ch.isalnum()` вместо перечисления алфавитов. Unicode знает
про буквы всех языков, а список — только про два.

## 2. 🔴 Словарь индекса привязан к русской локали умолчанием

**Место:** `ubuntu/serenedb/build.sh` (`DICT_LOCALE="${SEARCH_DICT_LOCALE:-ru_RU.utf8}"`)
и `corpus_init.sql` (`CREATE TEXT SEARCH DICTIONARY … locale = :'dict_locale'`).

**Что произойдёт.** Разбор на слова и приведение регистра пойдут по русским правилам на
любой базе. Для турецкой (`İ`/`ı`), греческой, японской это даёт неверную токенизацию и
неверную регистронезависимость — **молча**, поиск просто хуже находит.

Отдельно: это ровно «настройка, которую человек может заполнить, только зная конкретную
базу» — то, что в `CLAUDE.md` названо таким же дефектом, как имя в коде.

**Как чинить:** язык базы спросить у источника (`$metadata`, сама 1С), а не задавать
умолчанием.

---

## 3. 🔴 Остатки рукописного списка сущностей

**Место:** `ubuntu/serenedb/serene_select.py`, `serene-entities.txt`,
`serene_sync.py` (константа `SELECTED_FILE` и фильтр `_selectable`), `test_integrity.py`.

**Что произойдёт.** Список сущностей витрины, который человек заполняет, зная конкретную
базу. Синк его уже **не читает** (идёт от переписи `base_profile`), но файл, пикер,
константа и тест на него остались в продукте — то есть при установке у клиента это
выглядит как обязательный шаг настройки.

Там же — фильтр по русским подстрокам «присоединенныефайлы» и «удалить»: на англоязычной
конфигурации (`AttachedFiles`, `Delete…`) он не сработает.

**Как чинить:** убрать из продукта вместе с файлом.

## Найдено тогда же, но НЕ блокирует коробочность

| Место | Что | Почему не блокирует |
|---|---|---|
| `serene_ask.py`, приписка о старении и три сообщения об отказе | русский текст уходит клиенту | ухудшает, но система работает; рядом в том же файле от русских умолчаний уже сознательно отказались (`NO_DATA_TEXT` пуст) |
| `serene_ask.py`, признак «кода»: цифры, без точки, ≤12 символов; поиск держателей через `код + "."` | предполагает точку разделителем субсчёта и длину до 12 | на базе с разделителем `-` или `/` ветка уточнения не найдёт держателей |
| `serene_ask.py`, `ts_levenshtein(alt, min(2, len(alt)//4))` | расстояние опечатки от длины в символах | для иероглифических языков всегда 0 — нечёткий поиск выключен молча |
| `corpus_init.sql`, `resolver_build.sql` | `FLOAT[1024]` литералом при настраиваемом `EMBED_DIM` | не привязка к базе, а рассинхрон: проверка размерности смотрит только на `search_corpus` |

## Проверено и привязкой НЕ является

Чтобы не искали заново: `Ref_Key`, `DataVersion`, `LineNumber`, `Recorder`,
`Description`, `Code`, `Date`, `Period`, `PredefinedDataName`, суффиксы `_Type`,
`_RecordType`, `_RowType`, `%_Base64Data`, типы `Edm.*`, нулевой GUID — это имена
**платформы и протокола**, одинаковые при любом языке конфигурации, и все берутся только
при наличии в `$metadata` с запасным путём. `current_database()` вместо имени базы,
разбор регистра букв через `\p{Lu}`/`\p{Ll}`, разбиение чисел по разрядам в гейте — тоже
чисто.

## 🔴 Целевая схема «PostgreSQL на Windows + attach» НЕ реализована

**Записано по указанию владельца 30.07: «отдельная работа, но запиши что надо».**

Решение владельца 26.07 (`memory_bank/owner-memory/project-architecture-pg-windows-attach.md`,
подтверждено п. 16 `TARGET.md`): сырые данные 1С живут в PostgreSQL на Windows рядом с 1С;
SereneDB на Ubuntu присоединяет их (`ATTACH TYPE postgres, READ_ONLY`), строит `VIEW`
(NUMERIC→DOUBLE) и держит **только корпус и индекс**. Дословно из решения: «сырых
таблиц-копий в SereneDB быть не должно».

**Как сейчас** [замер 30.07, `ut_test`]:

| Что | Значение |
|---|---|
| таблиц витрины ВНУТРИ SereneDB | **1 620** |
| присоединённых баз | **`postgres`** — это наша же вторая база SereneDB, не Windows |

То есть сырые копии лежат именно там, где их быть не должно, а Windows-PG в контуре ответа не
участвует вовсе. Загрузчик пишет прямо в SereneDB на Ubuntu.

**Чем это плохо, кроме расхождения с решением:**

- **вес.** Полная копия сырых данных клиента на нашем сервере — это то, чего владелец
  сознательно избегал (периметр, п. 16);
- **два места правды.** При переходе на attach придётся заново решать, где строится витрина, и
  все замеры производительности сборки снимались НЕ на attach-таблицах;
- **индекс на attach-таблицу транслируется в btree** (`docs/SERENEDB.md`), поэтому обязателен
  `VIEW` — а значит переход задевает и сборку корпуса, и индекс, не только загрузчик.

**Что нужно сделать (не в этой работе):**

1. поднять PostgreSQL на Windows рядом с 1С — открытый вопрос коробки, две попытки без RDP
   неудачны (`docs/INSTALL_LOG.md`), владелец знает про конфликт с правилом двух ручных
   действий и выбрал сознательно;
2. переключить загрузчик на запись в PG-на-Windows по сети;
3. в SereneDB: `ATTACH … READ_ONLY` → `CREATE VIEW` с приведением типов → сборка корпуса и
   индекса **по VIEW**;
4. удалить локальные копии витрины из SereneDB и **перемерить такт** — прежние замеры к
   attach-схеме не относятся;
5. проверить, что перепись полноты (`coverage_build.sql`) считает по VIEW, а не по копиям.

## 🔴 Бот подключён к ВЫВЕДЕННОМУ слою braine и не может отвечать по данным

[замер 30.07] инструмент бота `ask_1c` (MCP `second-brain`, `:6014`) обращается к
`BRAINE_URL = http://127.0.0.1:8090` — это слой **braine**, который `README.md` объявляет
выведенным из контура. Порт `:8090` не слушает вовсе.

| Порт | Что там | Состояние |
|---|---|---|
| `:6014` | MCP-мост `ask_1c` | отвечает (401 без токена) |
| `:8090` | braine, к которому мост обращается | **не слушает** |
| `:8091` | отвечающий сервис ПЕРВОЙ базы | остановлен |
| `:8099` | отвечающий сервис ВТОРОЙ базы (`ut_test`) | работает, но к боту **не подключён** |

Проверено вживую: на вопрос «сколько мы заработали» бот отвечает «не удаётся получить данные из
системы — сервер 1С не отвечает».

**Почему это важно сверх самой поломки.** Это второй раз тот же класс, что записан в
`HOW_NOT_TO §2.14`: вывод компонента из контура не закончен, пока не убраны его **связки**.
Тогда выведенный `nightly-eval` продолжал будить владельца ночью; теперь выведенный braine
остался единственным источником данных для бота.

**Что нужно сделать (отдельная работа):**

1. переключить `mcp_braine.py` (или его окружение) с `BRAINE_URL` на отвечающий сервис
   `serene_ask` — и сделать адрес настройкой, чтобы бот мог смотреть на нужную базу;
2. решить, какая база у бота основная, — это решение владельца (сейчас работает `ut_test`);
3. только после этого проверять сквозной путь «вопрос → перефразирование по вики → поиск →
   уточнение → ответ»: до этого шаг перефразирования проверяется лишь по частям.
