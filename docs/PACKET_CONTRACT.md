# Контракт пакета: пакетный транспорт Windows → Ubuntu

Заведён 2026-08-06. Шаг 1 порядка реализации [`PLAN_MVP_PACKET_TRANSPORT.md`](PLAN_MVP_PACKET_TRANSPORT.md) §9.
**Версия контракта: `manifest_version = 1`.** Несовместимые изменения = новая версия,
совместимые (новое необязательное поле) — без смены версии.

Связано: `ubuntu/packet/` (реализация), `ubuntu/serenedb/poc_load_entity.py` (формат CSV —
источник истины), `work/installer-exe/` (ТЗ агента Windows). С 07.08 установщик и агент
Windows — трек разработки (решение владельца: снято с Cursor).

---

## 1. Термины и идентичность

- **`base_id`** — идентичность базы 1С (К9: побазовость с первой версии). Задаёт Ubuntu
  при установке агента, в манифесте и в URL всегда. Строка `[a-z0-9_-]+`.
- **`package_id`** — `<base_id>/<seq>-<rand8>` (полная форма, в манифесте); `seq` —
  монотонный номер пакета базы (растёт только на отправленных пакетах; разрывы допустимы —
  обрывы и «ноль изменений»), `rand8` — 8 hex, защита от повторного использования `seq`
  после сброса агента. В URL передаётся **короткая форма** `<seq>-<rand8>` (`base_id` —
  отдельным сегментом пути); приёмник сверяет `manifest.package_id == base_id + "/" +
  короткая форма`.
- **Пакет** — манифест + чанки. Неделимая единица применения (К7).

## 2. Формат на диске (карантин приёмника)

```
inbox/<base_id>/<package_id>/
  manifest.json.age        — манифест, зашифрован age
  <chunk-name>.csv.zst.age — чанки: CSV → zstd → age
```

**Режимы приёма (приёмник определяет по магии файла):** `age-encryption.org/` — age;
байты `28 B5 2F FD` — zstd без age; иначе 409 `bad_format`. Приёмник принимает оба
одновременно — это совместимость протокола, а не режим работы: 🔴 **с 07.08 агент
всегда шлёт age** (решение владельца «делаем как надо, с шифрованием»; пилотная
оговорка 06.08 отменена, не доехав до боя). Снятие/возврат age не меняют ни манифест,
ни имена чанков, ни `manifest_version`.

Имя чанка: `chunk-NNNNN` (5 цифр, от 00001). Служебные чанки: `metadata` (`$metadata`
XML), `gone` (ключи на удаление), `index` (отпечаток индекса версий — контрольный,
не для применения). Данные сущностей — только `chunk-NNNNN`.

## 3. Криптография

- **Два фактора канала (с 06.08): mTLS на релее** (клиентский сертификат от CA
  `1c-packet-ca`, `CN=<base_id>`, HAProxy `verify required`) **+ Bearer-токен** на
  приёмнике. Ключ сертификата по сети не передаётся вообще.
- Шифрование тела пакета: **age v1** (https://age-encryption.org), получатель **X25519**,
  passphrase-получатели запрещены. Каждый файл пакета — отдельный age-файл.
  ⚠ **С 07.08 age обязателен с первого пакета** (решение владельца «делаем как надо,
  с шифрованием»; пилотная оговорка 06.08 отменена, не доехав до боя): тело пакета
  нечитаемо и на релее после TLS-терминации, и в карантине на диске.
- Private key (identity) — только на Ubuntu, `/etc/1c-packet-age-<base>.key`
  (640 root:1c-secrets, как все секреты). Public key (recipient) уезжает в конфиг агента
  при установке; ротация — через `GET /agent/config` (принимаются оба ключа на
  grace-период, список живых identity — у приёмника).
- Свой envelope-формат, ZipCrypto, AES-CBC + свой MAC, пароль в ini — запрещены
  (анти-паттерны плана §11).
- Реализация: штатный `age` CLI обеими сторонами (Ubuntu — пакет ОС; Windows — exe
  рядом с агентом). Своя криптография не пишется.

## 4. Сжатие

- **zstd**, уровень 3 (в коридоре плана 1–3), порядок: **compress → encrypt**.
- Каждый чанк — самостоятельный zstd-фрейм: догрузке и проверке не нужны соседи.
- Ubuntu: `/usr/bin/zstd` (есть). Windows: `zstd.exe` рядом с агентом.

## 5. Манифест (JSON до шифрования)

```json
{
  "manifest_version": 1,
  "package_id": "ut/000041-a1b2c3d4",
  "base_id": "ut",
  "seq": 41,
  "kind": "full | delta | meta",
  "created_utc": "2026-08-06T10:00:00Z",
  "agent_version": "1.0.0",
  "entities": [
    {"name": "Catalog_Контрагенты", "op": "delta", "rows": 120,
     "chunks": ["chunk-00003"],
     "version_fingerprint": "sha256:…", "content_fingerprint": "sha256:…"}
  ],
  "gone": {"entities": ["Catalog_Контрагенты"], "chunks": ["gone"]},
  "skipped": [{"entity": "InformationRegister_…", "error": "…: HTTP 401"}],
  "metadata": {"included": true, "fingerprint": "sha256:…", "chunks": ["metadata"]},
  "chunks": [
    {"name": "chunk-00003", "entity": "Catalog_Контрагенты",
     "rows": 120, "bytes_plain": 34567, "bytes_enc": 8912,
     "sha256_plain": "…", "sha256_enc": "…"}
  ]
}
```

- `kind=full` — первая заливка (или resync): все сущности контура + `metadata` обязателен.
- `kind=delta` — изменённые сущности (`op`: `delta` | `full_entity` | `gone_only`),
  `gone` при наличии удалённых ключей; `metadata` — только если отпечаток изменился.
- `kind=meta` — только `$metadata` (схема изменилась без изменений данных).
- `skipped` (опционально, с 09.08) — сущности контура, которые агент НЕ смог
  прочитать (вне состава OData, RLS базы запрещает, сбой 1С): `[{"entity", "error"}]`.
  Приёмник не отвергает; apply пишет каждую в журнал (`SKIPPED entity=…`). Агент
  шлёт уведомление один раз при ИЗМЕНЕНИИ набора (отпечаток в state.json
  `skipped_fp`); в обычных пакетах поле идёт всегда, когда есть пропуски.
  Индекс пропущенной сущности не трогается — каждый такт пробует снова.
  **С 09.08 (вечер) `error` машиночитаем: `<причина>: <текст>`**, причины
  (ресерч `docs/research/rls_odata_research.docx` 4.4): `not_published`
  (нет в составе OData), `no_read_right` (нет роли «Чтение» — 401 код 20 и
  с allowedOnly), `rls_filtered` (сущность прочитана ЧАСТИЧНО: после отказа
  RLS агент дочитал разрешённое подмножество с `allowedOnly=true`),
  `auth_failed` (401 без OData-тела — фатал для такта), `infra_blocked` (403
  IIS/прокси), `rls_error` (500 от RLS-шаблона). `rls_filtered` — единственная
  причина, при которой данные сущности ЕСТЬ в пакете, но урезаны RLS базы.
- Ноль изменений → **пакет не шлётся** (план §7).
- `key` в записи сущности — объявленный ключ из `$metadata` (для `full`/`full_entity`
  apply строит по нему QUALIFY-дедуп, как `poc_load_entity.load_entity`).
- `version_fingerprint` — отпечаток пары `(Ref_Key, DataVersion)` сущности после такта;
  сверяется с локальным индексом агента. `content_fingerprint` — отпечаток содержимого
  (К1: защита от ложных изменений). **Формулы (зафиксированы 06.08 агентом
  `windows/packet-agent/src/PacketAgent.cs`, непрозрачны для приёмника):**
  - `version_fingerprint` = `"sha256:" + sha256( UTF-8( "Ref_Key\tDataVersion\n" … ) )`,
    строки конкатенируются в порядке сортировки `Ref_Key` (ordinal), отсутствующая
    `DataVersion` → пустая строка;
  - `content_fingerprint` = `"sha256:" + sha256( CSV-байты полного прочтения )` —
    заголовок и строки ровно в том виде, в каком агент их пишет (§7), порядок строк —
    порядок чтения `fetch_all` (при постраничности — `$orderby` по объявленному
    ключу, что делает порядок стабильным).

## 6. Чанкование

- Размер чанка до распаковки: цель **16–32 МБ** (`full`); мелкая `delta` — один чанк.
- Граница — по сущностям: чанк никогда не смешивает сущности (apply читает каждый
  чанк как CSV одной сущности); сущность больше 32 МБ — серия чанков `chunk-NNNNN`
  подряд с полем `entity_part: "i/n"` в записи `chunks`. Разрез — по строкам,
  **заголовок CSV повторяется в каждой части** (apply склеивает части `UNION ALL`,
  читая каждую с `header=true`).
- `gone.csv`: колонки `entity,ref_key`, тот же CSV-контракт (§7).

## 7. Формат данных в чанках (CSV)

🔴 **Байт-в-байт контракт `poc_load_entity.py`** (К5 — самое молчаливое место):

- header — имена колонок после `safe_col`; все значения — текст (витрина all-varchar);
- булевы — `true`/`false` (как в JSON 1С, не `True/False`);
- дата-время — `YYYY-MM-DD HH:MM:SS` (пробел, не `T`);
- диалект — Python `csv` по умолчанию: quote `"`, удвоение кавычек, `\r\n`;
- кодировка — UTF-8.
- Соответствие проверяется **golden-пробой**: сохранённые ответы OData → CSV
  Python-версии (эталон), вывод агента сверяется побайтно. До зелёной пробы агент в бой
  не выкатывается.

## 8. HTTP-протокол (endpoint `https://1c-gate.timpul.ru`)

Аутентификация — **два фактора** (решение владельца 06.08):

1. **mTLS на релее (HAProxy)**: клиентский сертификат агента, выдан нашим CA
   `1c-packet-ca`, `CN = <base_id>`. Ключ сертификата по сети не передаётся (в отличие
   от токена, который релей видит в каждом запросе). Без сертификата релей запрос не
   пропускает. HAProxy передаёт CN заголовком `X-SSL-Client-CN`; приёмник при наличии
   заголовка сверяет его с `base_id` пути (расход — 403).
2. **Bearer-токен базы** (как было): `Authorization: Bearer <token>` — вторая проверка
   на приёмнике; выдаётся при установке, отзывается перевыпуском комплекта.

Выпуск комплекта новой базы (частый процесс «новый бизнес») — одна команда:
`work/packet/onboard-base.sh <base_id>`, процедура и ловушки —
[PACKET_ONBOARDING.md](PACKET_ONBOARDING.md).

Только TLS. Только эти пути — остальное 404.
`<package_id>` в путях — короткая форма `<seq>-<rand8>` (§1).

```
PUT  /v1/package/<base_id>/<package_id>/manifest      body = manifest.json.age
PUT  /v1/package/<base_id>/<package_id>/chunk/<name>  body = <name>.csv.zst.age
GET  /v1/package/<base_id>/<package_id>/status
     → {"state": "receiving|verified|applied|rejected|quarantined",
        "received": [...], "missing": [...], "error": null|"…"}
GET  /v1/agent/config?base_id=…&config_version=…&agent_version=…
     → {"config_version": N, "entities": ["…"], "params": {"page_size": 10000,
        "tact_seconds": 1200, "chunk_mb": 32}, "recipient_pubkey": "age1…"}
     (304-подобно: config_version без изменений → {"config_version": N} только)
GET  /health → {"status":"packet-server-ok"} — без авторизации (сторож)
```

- Порядок заливки: манифест → чанки в любом порядке с повторами.
- **Идемпотентность:** повтор `PUT` чанка с тем же `sha256_enc` — no-op; повтор манифеста
  — no-op; повтор `package_id` в `applied` — весь пакет no-op.
- **Догрузка:** обрыв → агент спрашивает `status`, шлёт только `missing`.
- **Применение:** все чанки на месте → verify (age + sha256 + zstd) синхронно в `status` →
  состояние `verified`; перевод `verified → applied` выполняет apply-компонент.
  🔴 **DDL в SereneDB не транзакционен** (`[замер 06.08]`: `CREATE TABLE` коммитится
  немедленно, `ROLLBACK` его не откатывает — WARNING движка; доки — Transactions).
  Поэтому атомарность пакета (К7) держится **идемпотентностью + маркером в конце**:
  все операции apply повторяемы без вреда (full — `CREATE OR REPLACE`, delta —
  `DELETE` по ключам + `INSERT`, gone — `DELETE`), контрактные таблицы и отметка
  `applied` пишутся ПОСЛЕДНИМИ одной DML-транзакцией; обрыв посередине → пакет остаётся
  `verified` и apply повторяет его целиком при следующем заходе. Сбой → `quarantined`
  + `error`, витрина не тронута. Агент по `quarantined` не повторяет тот же пакет —
  ждёт решения (новый `seq`).
- **seq:** `seq <= last_applied` → `rejected(stale_seq)`. Разрывы — норма.
- **`manifest_version`:** неизвестная версия → `rejected(version_unsupported)` с
  максимальной поддерживаемой в `error`. Агент старой версии продолжает работать, пока
  приёмник принимает его версию (К10).
- **Лимиты приёмника (К8):** чанк ≤ 64 МБ, чанков в пакете ≤ 4096, карантин ≤ 20 ГБ на
  базу, пакетов в приёме ≤ 8 на базу; превышение — `429`/`rejected(limit_*)` и метрика.

## 9. Что apply пишет в витрину (Б3 — контракт с ботом и сборкой)

- merge сущностей: `delete по Ref_Key + insert` (документ целиком с ТЧ) — тот же SQL,
  что у `load_entity_delta` / `load_entity`;
- `gone` — delete по ключам;
- `metadata` → **файл** `<PACKET_META_DIR>/<base_id>/$metadata` (умолчание
  `/var/lib/serenedb/packet-meta`, атомарная запись, читаем процессом движка).
  Б1 закрыт БЕЗ правки боевой сборки (решение владельца 06.08): `corpus_build`
  читает снимок своим прежним `read_text(:'gate' || '/$metadata')` — в пакетном
  контуре `build.sh` получает `ETL_ODATA_BASE=<PACKET_META_DIR>/<base_id>`, и путь
  сходится на файле снимка. Таблица для снимка не заводится;
- контрактные таблицы: `search_changed_sources` (список изменённых — пустой допустим),
  `base_profile` (строки/счётчики из манифеста), `search_quality.mart_changed_ts`;
- инвариант «одна версия на Ref_Key» проверяется при apply (К3): нарушение → пакет
  в карантин с требованием `full_entity` resync;
- ⚠ атомарность — не rollback (DDL в движке не транзакционен, §8), а идемпотентный
  повтор + маркер `applied` последней транзакцией.

## 10. Конфиг агента (обратный канал, Б2)

Источник истины отбора — Ubuntu (`search_entity_class` модели + `search_entity_force`
владельца + `only_binary` из снимка `$metadata` — того же файла §9). Отдельный
**config-builder** на Ubuntu считает контур теми же тремя признаками, что
`serene_sync._service_skip`, пишет `search_entity_skipped` с причинами (п. 13 TARGET:
исключённое видно) и раскладывает итоговый конфиг в файл базы приёмника
(`config_version` растёт при изменении `entities`/`params`; `params` уже записанные
не затираются). Агент получает **итоговый список сущностей** и параметры такта через
`GET /agent/config`; применяет новый конфиг со следующего такта; сам ничего не
исключает и не добавляет.

**Бутстреп чистого юнита (вариант А, решение владельца 10.08).** Контурный
запрос отбирает из переписи `base_profile` (rows>0), но на новом юните перепись
пуста до первых данных, а данные идут только по контуру — круг (вскрыт первым
реальным прогоном юнита 10.08: ни один юнит до этого не доезжал до контура).
Разрыв: перепись пуста и есть снимок `$metadata` → первый контур = все наборы
сущностей (EntitySet) снимка, к которым применяются те же три признака
(на практике — only_binary; class/force таблиц на чистом юните ещё нет).
Ни переписи, ни снимка — прежний отказ. Дополнение о полноте (п. 13): сущность
из прошлого контура не выбывает молча (ещё пустая, rows=0) — выбывает только по
явной причине (force/class/only_binary).

**Первая сборка слоя — по данным, не по снимку.** До первых данных такт
пайплайна обрывается штатным сторожем «после такта корпус ПУСТ», поэтому сборку
и таймер свежести включает отметка `.first-data`, которую apply кладёт при
первом пакете с данными (path-юнит `1c-serene-firstbuild@<base>`).

## 11. Отклонённые варианты (с причиной)

- Один multi-GB файл на initial dump — невозобновляем (план §6).
- Свой envelope вместо age — своя криптография; age — готовая коробка обеих сторон.
- Шифрование пакета целиком одним файлом после сборки — теряется пофайловая догрузка.
- Пасphrase-получатель age — пароль в конфиге Windows (анти-паттерн).
- Вычисление отбора сущностей на Windows — второе место истины (Б2).
