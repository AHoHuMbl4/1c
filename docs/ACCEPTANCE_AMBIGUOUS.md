# Приёмочный набор неоднозначных вопросов (Э3)

Набор проверяет **поведение на неоднозначном вопросе** — то, что в [`TARGET.md`](../TARGET.md)
отнесено к п. **12**, **18** и **21**, но до сих пор **не имело отдельной приёмки**
([`PLAN_TO_TARGET.md`](PLAN_TO_TARGET.md), Э3).

Файл набора: [`ubuntu/serenedb/ab-acceptance-ambiguous.tsv`](../ubuntu/serenedb/ab-acceptance-ambiguous.tsv).

🔴 Набор проверяет **контракт**, а не текущие возможности кода. Вопросы не подгонялись
под то, что система умеет сейчас.

---

## 1. Критерии приёмки (из TARGET.md)

### п. 12 — «Отказ и уточнение — не ошибка. Догадка — ошибка.»

| Поведение | Приёмка |
|---|---|
| Вопрос допускает **несколько равноправных прочтений** | `kind=clarify` с вариантами или формулировкой, **что именно уточнить** — не число «наугад» |
| **Недостаточно контекста** для одного верного ответа | уточняющий вопрос, а не выбор «самого правдоподобного» |
| **Данных нет** | честный отказ (`no_data`), без правдоподобной цифры |
| **Выбор наугад** между правдоподобными вариантами | **провал** — даже если число случайно близко |

### п. 18 — «При отказах — честный отказ, а не ответ на неполных данных.»

| Поведение | Приёмка |
|---|---|
| Неоднозначность **не снята** | **нет** `answer`/`figures` с итогом по одному из прочтений без уточнения |
| Частично собранные данные | **не** подаются как полный ответ |
| Сервис недоступен | `unavailable` с причиной — не «ответ из того, что успели» |
| Живой сервис | `unavailable` при рабочем `/health` — **провал** по п. 18 |

### п. 21 — «Задача проекта — отдать ответ. Правильный.»

| Поведение | Приёмка |
|---|---|
| Порядок | **ответ** → **уточняющий вопрос** → **отказ** |
| Данные **есть**, прочтение **одно** после уточнения | `no_data` или молчание — **дефект**, не осторожность |
| Данные **есть**, прочтений **несколько** | сначала `clarify`; ответ числом без уточнения — **дефект по п. 12** |
| Данных **нет** | `no_data` — **не дефект** |
| Догадка | **запрещена** (п. 12 сохраняется) |

**Сводка для скорера:** на строках режима `clarify` верно = `kind=clarify` (+ игла в `options`,
если задана). На строках `kind` с `SELECT 0` верно = `kind=no_data` без итоговых чисел в `text`.
Любой `answer`/`figures` с числом там, где ожидается уточнение или отсутствие данных, — провал.

## 3. Каталог вопросов

Формулировки — словами человека. «Игла» — подстрока, которую `ab_scorer` ищет в тексте
варианта `clarify` (человеческая формулировка уточнения, не имя поля метаданных).

### 3.1. Непонятый период → уточнение

| № | Вопрос | Ожидание | Уточнение (игла / смысл) |
|---:|---|---|---|
| 1 | Сколько мы продали за год? | уточнение | «за какой год?» — в базе несколько лет с разной выручкой |
| 2 | Какая выручка за квартал? | уточнение | «за какой квартал?» (и год, если нужно) |
| 3 | Сколько закупили весной? | уточнение | «какой год?» — «весна» без года неоднозначна |

**Провал:** одна сумма «за год» без указания, какой; `no_data` при наличии продаж.

### 3.2. Две сущности с похожим именем → уточнение

| № | Вопрос | Ожидание | Уточнение |
|---:|---|---|---|
| 4 | Какой ИНН у контрагента Алмаз? | уточнение | «какой именно Алмаз?» — в демо-базе ut_test два контрагента с этим словом в имени |
| 5 | Сколько мы продали контрагенту Сатурн? | уточнение | «какой Сатурн?» — несколько одноимённых контрагентов |
| 6 | Покажи заказы ПАНГЕЯ | уточнение | «какая ПАНГЕЯ?» — несколько юрлиц с похожим названием |

**Провал:** один ИНН/сумма без вопроса «какой из…»; `no_data`, если совпадения по имени есть.

### 3.3. Мера не задана → уточнение

| № | Вопрос | Ожидание | Уточнение |
|---:|---|---|---|
| 7 | Сколько мы закупили товаров? | уточнение | «в рублях или в штуках?» |
| 8 | Топ-5 товаров по продажам | уточнение | «по деньгам или по количеству?» |
| 9 | На какую сумму? | уточнение | «о чём речь?» — предмет вопроса не назван |

**Провал:** число без названной меры; топ без указания, по чему ранжировали.

*Допустимо по контракту:* `answer`/`figures`, если ответ **явно называет** выбранную меру
(как в [`ACCEPTANCE_UT.md`](ACCEPTANCE_UT.md) №1, №29). Скорер на этих строках ждёт
именно `clarify` — так фиксируется дефект «ответил, не уточнив».

### 3.4. Лицо/место не задано → уточнение

| № | Вопрос | Ожидание | Уточнение |
|---:|---|---|---|
| 10 | Сколько товара на складе? | уточнение | «на каком складе?» — складов несколько |
| 11 | Сколько осталось на складе? | уточнение | «на каком складе?» |
| 12 | Сколько лежит на всех складах вместе? | уточнение | «какой товар / какая номенклатура?» — предмет не назван |

**Провал:** остаток по одному складу без вопроса; сумма «по всем» без перечня товаров, если
товар не задан.

### 3.5. Слова/данных нет → нет данных

| № | Вопрос | Ожидание | Почему |
|---:|---|---|---|
| 13 | Сколько велосипедов мы продали? | нет данных | в корпусе ut_test нет продаж велосипедов |
| 14 | Сколько анкет заполнено? | нет данных | сущность анкет в базе пуста |
| 15 | Какая выручка за 2022 год? | нет данных | документы заканчиваются 2019 годом; 2022 вне корпуса |

**Провал:** любое ненулевое число продаж/выручки; `no_data` без пояснения границы (для №15
желательно назвать последнюю дату данных — проверяется вручную по тексту, скорер — только
`kind=no_data` без итогов в `text`).

### 3.6. Вопрос не про данные 1С

| № | Вопрос | Ожидание | Почему |
|---:|---|---|---|
| 16 | Как у нас дела? | уточнение | нет одного числового смысла — «о чём спросить: продажи, остатки…?» |
| 17 | Кто сейчас президент России? | нет данных | в 1С нет таких сведений |
| 18 | Напиши стих про наш склад | нет данных | запрос не про учётные данные |

**Провал:** выдуманный KPI или «ответ» из общих знаний; для №16 — число без уточнения темы.

## 4. Как гонять

Тот же скорер, что и золотые наборы — [`ubuntu/serenedb/ab_scorer.py`](../ubuntu/serenedb/ab_scorer.py).
Прямой `curl` на `/ask` **не** заменяет прогон через бота ([`ACCEPTANCE_UT.md`](ACCEPTANCE_UT.md) §0).

### 4.1. Сервис `/ask` (smoke / okna / ut_test)

```bash
cd /srv/1c/ubuntu/serenedb
AB_GOLD_FILE=/srv/1c/ubuntu/serenedb/ab-acceptance-ambiguous.tsv \
AB_BASE=ut_test \
AB_GOLD_MODE=smoke \
ASK_URL=http://127.0.0.1:8099/ask \
python3 ab_scorer.py
```

Для контура okna — свой DSN и порт; **набор ut_test на okna не переносится** (другая база).
На okna нужен отдельный файл с теми же *видами* неоднозначности и SQL эталона по корпусу okna.

### 4.2. Через бота (полная цепочка, п. 21)

Как [`run_acceptance.py`](../work/acceptance/run_acceptance.py) для `ACCEPTANCE_UT.md` — отдельный
прогонщик по этому документу **пока не подключён**; оркестратор может снять живой прогон
и сверить `kind` + текст уточнения по таблице §3.

## 5. Как читать результат `ab_scorer`

| Вывод скорера | Значение |
|---|---|
| `clarify:…=ok` | уточнение вместо догадки — **верно** для строк `clarify` |
| `kind:…=ok` | `no_data` без итогов в тексте — **верно** для строк `kind` |
| `kind не тот` / `лишний clarify` | ответил числом или отказался, где нужно было уточнить — **провал п. 12/21** |
| `число/итоги в no_data` | в `no_data` протекло число — **провал п. 12** |
| `подстрока clarify не найдена` | `clarify` есть, но формулировка не про нужную ось — **частичный провал**; смотреть `options` вручную |
| `эталон не посчитан` | SQL не выполнился — инфраструктура, не поведение бота |

Счёт: **N/N** — все строки прошли. Для приёмки Э3 важна **доля clarify+no_data там, где
ожидается**, и **ноль** случаев «число наугад».

### 9.2. Что это значит

- Класс «лишний clarify» — это ровно К4-2 (`docs/K4_CLARIFY_VS_NODATA.md`,
  проект патча A+B готов, не применён): мусорный measure-clarify на вопросах,
  у которых предмета нет в базе вовсе.
- Класс «подстрока не найдена» — clarify выходит, но не называет человеческую ось
  (валюта вместо рублей, не «какой склад»). Чинится подписями clarify, не kind.
- №8/№12 (no_data вместо clarify по складам): на okna нет баланс-источников
  (`search_meta.balance_registers` пуст), no_data честен по правилу «именованный
  товар без ТМЦ-остатков»; набор ждёт clarify — конфликт набора с правилом стока
  22.08, разбор за владельцем набора, не подгонка кода.
- №5 «Топ-5 товаров» → answer: по контракту ответ лучше уточнения, провал набора
