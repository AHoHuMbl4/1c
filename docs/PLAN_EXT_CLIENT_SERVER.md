Итого: скрипт не умеет клиент-серверную форму подключения ни в COM, ни в
конфигураторе, а установщик даже не передаёт ему сервер и имя базы. «КОРП» в
комментарии — непроверенная гипотеза; реальная причина пропуска — неумение.

### А.1 Правки `Steps.cs` (вызывающая сторона)

1. **Снять пропуск** `if (!bref.IsFile)` целиком.
2. **Передавать форму базы** окружением: `OC1C_EXT_IB_KIND=file|server`;
   для file — как сейчас `OC1C_EXT_BASE=bref.Dir`; для server — два новых
   `OC1C_EXT_SRVR=bref.Srvr`, `OC1C_EXT_REF=bref.Name`. Никакого разбора
   строк подключения в скрипте — форма выбирается по `IB_KIND` (девиз:
   не разбирать текст, когда структура известна).
3. **Порядок шагов**: шаг 14 — ДО запуска агента (сейчас 21:52:04 агент,
   21:52:15 шаг 14). Причина не фатальная (агент дочитывает пропуски каждым
   тактом), но первый проход должен идти уже с правами — иначе первая полная
   заливка гарантированно неполная, а это самые дорогие часы чтения.
4. **Честный фейл**: убрать «~15 %». После шага — измерение: проба N=20
   случайных сущностей `$metadata` под читателем; в лог и в ИТОГ — число
   отказов 401 «до» и «после». Если «после» не лучше «до» — шаг ЖЁЛТЫЙ в
   ИТОГЕ с числом, а не тихий `return true`. Порог не выдумывать: любое
   `после > 0` называется числом.
5. `detail` шага обязан попадать в ИТОГ всегда (сейчас при пропуске виден
   только в строке шага).

### А.2 Правки `ai-ext.ps1`

1. **Подключения** — по `OC1C_EXT_IB_KIND`:
   - COM (стр. 101): file → `File="…"`; server → `Srvr="…";Ref="…"` (+Usr/Pwd).
   - Конфигуратор (4 вызова): file → `/F$BASE`; server → `/S"$SRVR\$REF"`.
     Форма аргумента одна, собирается в одном месте (функция), не в четырёх.
2. **Занятость базы.** На клиент-серверной конфигуратор может не войти из-за
   сеансов. Расширение назначения AddOn данных не меняет, поэтому
   `/UpdateDBCfg -Extension` обычно проходит динамически; но вход конфигуратора
   может упереться в блокировку. Обработка: код выхода + разбор `/Out`-лога;
   при «база занята» — до 3 повторов с паузой 60 с; не вышло — честный жёлтый
   фейл с текстом лога. Сеансы НЕ рубить: чужой прод.
3. **Профили безопасности кластера** — та самая «КОРП»-гипотеза. Проверяется,
   а не предполагается: если `/LoadConfigFromFiles -Extension` вернул отказ
   с текстом про профиль безопасности — в лог ровно эту причину и жёлтый фейл
   («кластер запрещает расширения профилем безопасности — нужно разрешение в
   консоли кластера»), это ЕДИНСТВЕННЫЙ случай, когда пропуск честен.
4. **Снятие БезопасныйРежим/предупреждений** (COM-блок после загрузки) — тем же
   `IB_KIND`-подключением; логика не меняется.
5. **vrd**: на клиент-серверной публикация та же (IIS на той же машине) —
   изменений не ждём, но проба «/hs/ отвечает» обязательна как и сейчас.
6. **Контрольные пробы до/после** (уже есть в скрипте) — оставить, они и есть
   измеритель п. А.1.4.

### А.3 Проверка (без неё не выкатывать)

1. **Стенд с клиент-серверной базой обязателен.** У нас проверено только на
   файловых — из-за этого и весь дефект. Нужен сервер 1С на стенде
   (192.168.56.1, платформа 8.3.27.1786 есть; нужна установка сервера и
   создание базы — **шаг владельца**, сессии стенд недоступен).
2. Прогоны: (а) чистая установка на клиент-серверную базу — шаг 14 зелёный,
   пробы «после» = 0 отказов; (б) повторный прогон — идемпотентность
   (расширение уже стоит → «уже установлено», не ошибка); (в) файловая база —
   регресс, поведение прежнее; (г) отказ из-за профиля безопасности — жёлтый
   фейл с точной причиной (эмулировать включением профиля на стенде).
3. Golden-набор установщика дополнить случаем «клиент-серверная база»:
   сейчас все 4 golden — файловые, потому дефект и прожил до прода.
4. `--check` (dry-run) обязан печатать, ЧТО сделал бы шаг 14 на этой базе,
   включая форму подключения.
