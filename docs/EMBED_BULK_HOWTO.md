# Массовая векторизация корпуса: как правильно

Записано 21.08 по итогам разового прогона на klient-1 (15,1 млн строк, 6 × RTX A6000).
Всё, что ниже, — либо цитата доков, либо **замер**. Догадок здесь нет: каждая догадка,
которую я проверял на живых картах, стоила денег и почти всегда оказывалась неверной.

## 0. Главное в одну строку

Скорость упирается **не в карты**. По очереди упирается в: число одновременных HTTP-вызовов
(= `threads` движка), в единственного писателя базы, в полные проходы по корпусу и в память
клиентской машины. Карты насыщаются раньше, чем кажется, и добавлять их имеет смысл только
после того, как сняты первые четыре ограничения.

## 1. Что говорят доки (и это подтвердилось)

| факт | раздел |
|---|---|
| «Each `ai_embed` call is a network request to the provider» — считать один раз при записи | `sql/functions/ai#performance` |
| «each SereneDB thread can make at most one HTTP request at a time»; для множества мелких сетевых запросов ставить `threads` в 2–5× от числа ядер | `cookbook/performance/how_to_tune_workloads#querying-remote-files` |
| «for a query to run on k threads, it needs to scan at least k × 122 880 rows» — параллельность берётся из групп строк | там же, `#the-effect-of-row-groups-on-parallelism` |
| размер группы задаётся **только** при `ATTACH ... (ROW_GROUP_SIZE N)` | `sql/statements/attach/duckdb#options` |
| форма записи: колонка типизирована `FLOAT[N]`, вектор кладётся `UPDATE ... SET emb = ai_embed(...)` | `quick-start#generate-embeddings` |
| «An ART index does not affect the performance of join, aggregation, and sorting queries» — индекс не ускорит обратную запись | `cookbook/performance/indexing` |
| штатного «векторайзера» нет; генерируемые колонки для `ai_embed` не описаны | проверено поиском по докам |

## 2. Где доки расходятся с нашей сборкой 26.07.3

🔴 **`ai_embed(...)::FLOAT[1024]` падает, если оператор отдаёт больше ~16–32 строк.**
`Vector::SetSize out of range - trying to set size to 2097152 for vector with capacity 16384`
(2 097 152 = 2048 × 1024 — полный блок обработки). Воспроизводится и в `CREATE TABLE AS`,
и в `UPDATE ... SET emb = ...` в типизированную колонку, на всех картах, детерминированно.
Форма из блога SereneDB (одним оператором на весь набор) на этой сборке **неприменима**.

Отсюда: **оператор берёт 16 строк** — ровно то значение, которое стоит в штатном
`ubuntu/serenedb/embed_missing.sh` (`EMBED_BATCH_ROWS=16`). Это не про ограничение
провайдера, а про предел движка. Комментарии в `embed_missing.sh` и `embed_all.sh`,
объяснявшие пачку и параллельность ограничениями облачного провайдера, исправлены
21.08 — с разбором, чем прежняя версия была неверна.

## 3. Порядок ограничений, по замерам

| что снимали | было | стало |
|---|---|---|
| исходный путь (штатный такт, `threads=4`) | **15,2 строк/с** | — |
| подняли `threads`, дали каждому потоку свою рабочую базу | 15,2 | **240** |
| убрали выбор порции отдельным проходом по корпусу (список работы строится один раз) | — | снялись 100 % CPU и своп |
| оператор 8 → 16 строк | 185 | **354** |
| установившийся режим за ночь, конец в конец | — | **168 строк/с**, 5,4 млн строк за 9 часов |

### 3.1. Одновременные запросы = `threads`
Замер: 42 потока-процесса в фазе счёта, а в полёте **ровно 18** — столько, сколько
`threads`. Ни разу не больше. Это буквально то, что написано в доках.

### 3.2. У базы один писатель
Несколько пишущих операторов в **одну** базу выстраиваются в очередь, и наружу идёт один
запрос за раз. Замер: 18 воркеров штатного скрипта → 15,2 строк/с, в полёте 1 активный
запрос (13,1 строк/с × 8 строк ÷ 4,9 с латентности = ровно один).
**Лечение:** своя присоединённая база на каждый поток (`ATTACH '/var/lib/serenedb/wN.db'`).

### 3.3. Полные проходы по корпусу — самое дорогое
`search_corpus` — 15,1 млн строк с колонкой `doc`. Любой `SELECT ... WHERE emb IS NULL ...`
и любой `UPDATE search_corpus ... FROM ...` читает её целиком (замер: 0,7–1,5 ГБ/с чтения,
CPU 100 %, своп 4,9 ГБ).
**Правило: один проход на построение списка и один на запись результата — за круг**, а не
на каждую порцию и не на каждый поток. Замер до правила: поток закрывал 50 000 строк за
8 754 с (5,7 строк/с), хотя счёт шёл 359 строк/с — то есть **70 % времени карты ждали**.

### 3.4. Круг должен быть ДЛИННЫМ
Проверено ошибкой: укоротил круг с 900 000 до 180 000 строк, чтобы сократить хвост, где
быстрые потоки ждут отстающего. Стало **133,7 строк/с вместо 270–375**. Причина: запись в
корпус стоит полного прохода и делается раз в круг — короткий круг платит за неё впятеро
чаще, и это дороже хвоста (хвост стоил 300–500 с на круг из 3300).

### 3.5. Память клиента — жёсткий потолок
Каждая строка тащит вектор `FLOAT[1024]` = 4 КБ. 42 потока со своими таблицами раздули
движок до **14 ГБ из 15**, свободной памяти не осталось, скорость упала до **2,4 строк/с**.
Движок память сам не возвращает — нужен рестарт `serenedb` (после него 14 ГБ → 3 ГБ).
**Правило:** число потоков × размер доли × 4 КБ должно оставлять машине запас.
На 15 ГБ рабочими оказались 18 потоков × 50 000 строк.

### 3.6. Сетевой отказ — это «приходи позже», а не конец работы
Провайдер (Cloudflare перед сервисом) периодически отдаёт `HTTP 404` с HTML-страницей.
Если поток на этом заканчивает работу, его карта простаивает до конца круга: замер — из
18 потоков живы 9, работали 3 карты из 6, владелец видел «одна карта стоит, нагрузка
рваная, не выше 50 %». **Порцию надо переспрашивать** (в штатном `embed_missing.sh` это
сделано раундами).

## 4. Про сами карты (замеры на реальных строках корпуса)

- одна карта насыщается на **3 одновременных запросах**: 1 поток — 16 строк/с, 2 — 19,6,
  3 — 19,4, дальше ровно;
- **две копии сервиса на одной карте бесполезны**: 44,2 против 45,7 строк/с — разница в
  шуме, а VRAM вторая копия ест вдвое (15 ГБ). Одна копия на карту;
- 🔴 **сервис считает пачку по САМОЙ ДЛИННОЙ строке в ней**: 8 коротких (3 200 симв.) —
  0,72 с; 7 коротких + 1 длинная (22 800) — **17,6 с**; 8 длинных (160 000) — 12,5 с.
  Поэтому строки идут **полосами по длине**, иначе одна длинная отравляет всю пачку;
- считать надо **в символах, а не в строках**: потолок 6 карт — около 66 000 симв/с
  (11 000 на карту). Корпус — 12,48 млрд символов, отсюда и берётся срок;
- RTX A6000 = **0,6 от A100** по факту (11 000 против 18 400 симв/с) при цене втрое ниже,
  то есть вдвое выгоднее на единицу работы. L40 по деньгам примерно как A100.

## 5. Рабочая конфигурация (та, что дала 5,4 млн строк за ночь)

```
EMBED_BATCH_ROWS=16        # предел движка на FLOAT[1024] в одном операторе
EMBED_THREADS=24           # 3 × ядер; = число одновременных запросов
EMBED_STREAMS_PER_CARD=3   # карта насыщается на трёх
EMBED_POOL_PER_STREAM=50000
EMBED_HTTP_TIMEOUT=600     # SET GLOBAL, иначе длинные полосы валятся по таймауту
```
Плюс: `SET GLOBAL threads` и `SET GLOBAL http_timeout` — **обязательно `GLOBAL`**
(`http_timeout` по умолчанию LOCAL и из чужой сессии не виден), **каждое отдельным
оператором** («parameter is global and cannot be set inside a transaction») и **на
простое** — на занятом пуле значение не применяется.

## 6. Грабли обвязки, на которых я потерял больше всего

1. **Скрипт читал `/etc/1c-embed.env` ПОСЛЕ переменных юнита** — значения из файла молча
   перекрывали `--setenv`. Полдня я объяснял «потолок 18 запросов» свойствами движка,
   а это была моя переменная из файла.
2. **`trap` при остановке возвращал `threads` в старое значение** — и следующий запуск
   стартовал с чужой настройкой.
3. **Считать скорость по `count(emb)` в корпусе нельзя** — запись идёт раз в круг, счётчик
   стоит часами. Мерить надо прирост в рабочих таблицах.
4. **«Соединений в полёте» ≠ «активных запросов»**: keep-alive держит сокет открытым.
   Проверять надо арифметикой (строк/с ÷ размер пачки × латентность).
5. **`count(*) WHERE emb IS NULL AND NOT EXISTS(...)`** на 26.07.3 кладёт `emb` в CTE
   (`Projections: emb, src_table`) и на 15 млн строк OOM'ится. Форма в
   `embed_missing.sh` `left()`: сначала `(SELECT src_table FROM … WHERE emb IS NULL)`,
   антисоединение снаружи. Не глушить stderr у этого count. Замок
   `test_embed_left_count.py`. Доки: partial-reading / avoid unnecessary columns.
6. **curl 200 ≠ ai_embed жив.** TEMPORARY SECRET переживает смену `EMBED_HOST`:
   curl бьёт в env, движок — в `duckdb_secrets().base_url`. Сторож
   `embed_secrets_base_url_check`. Не класть путь в `base_url` (double-path →
   JSON 404).

## 7. Чего делать НЕ надо

- не гнать оператор больше 16 строк — упадёт на `Vector::SetSize`;
- не поднимать `threads` «побольше» — упрётся в память и станет в сто раз хуже;
- не укорачивать круг — платить за проход по корпусу чаще выйдет дороже;
- не строить индекс ради обратной записи — доки прямо говорят, что на join он не влияет;
- не ставить две копии модели на карту — это не даёт ничего и съедает VRAM;
- не смешивать длинные и короткие строки в одной пачке.

## 8. Как узнать прогресс пересчёта

**Во время раунда** `embed_missing.sh` переносит векторы в корпус только в конце
(`transfer` после всех part-таблиц). Счётчик `count(emb)` в `search_corpus` стоит
часами — это не поломка, а устройство раунда (§6.3).

**Живой прирост** — сумма строк в рабочих таблицах `emb_<база>_<таблица>_part_<N>`.
Перечень этих таблиц скрипт спрашивает у движка (`duckdb_tables()` с фильтром
`current_database()`), а сумму берёт одним `query_table(<список>, true)` — номера не
перебираются и число воркеров подсчёт не ограничивает (24.08, находка снайпера по
п. 20 TARGET.md). Каталог или сумма недоступны — в выводе стоят `parts_incomplete`
и `parts_incomplete_reason`, числа не занижаются молча.
Инструмент: `ubuntu/serenedb/embed_progress.sh` (два снимка с интервалом дают
скорость):

```bash
# один снимок
./embed_progress.sh search_corpus

# скорость за 60 с (меряет прирост в part-таблицах)
./embed_progress.sh search_corpus 60
```

Если полный `left()`-count по корпусу недоступен под нагрузкой (типично >120 с на
klient-1 при живом `embed_all`), задайте объём очереди вручную один раз:
`EMBED_SCOPE_TOTAL=<деловые строки без вектора на старте раунда>`. После первого
удавшегося полного count значение запоминается в `/tmp/embed_progress_<база>_<таблица>.json`.

**Что не работает под нагрузкой** ([замер 23.08 klient-1]):

| способ | результат |
|---|---|
| `count(*) FILTER (WHERE emb IS NULL)` по всему корпусу | >300 с, не ответил |
| лёгкий `left()` по одной крупной сущности (643k строк) | 105 с |
| `duckdb_tables()` / `sdb_metrics` | >120 с, очередь за embed |
| `search_quality.cov_noemb_pending` | устаревает до следующего `coverage_build.sql` |
| `SET statement_timeout` | не enforced движком 26.07.3 |

**Штатный механизм:** partial reading / projection pushdown — считать только
`src_table`, не проецировать `FLOAT[1024]` ([partial-reading](https://docs.serenedb.com/data_import_and_export/parquet/overview#partial-reading));
форма как `left()` в `embed_missing.sh`, замок `test_embed_left_count.py`.
