# Ф6.5 — чеклист включения env-флагов в бой okna `:8091`

Подготовка к утреннему ходу: модель в момент составления выключена владельцем —
этот документ и прибор `ubuntu/serenedb/f6_rollout_measure.sh` только описывают
и меряют. Включение флага — снаружи (env юнита / процесса), не скриптом.

Источник плана: `docs/PLAN_UPGRADE_NATIVE.md` §Ф6 п.5. Фактура чисел:
`docs/F6_HYBRID_FACTS.md`, `docs/F6_FRESHNESS_FACTS.md`, `docs/F6_SYNONYMS_FACTS.md`,
записи в `CHANGELOG.md` / `docs/PLAN_UPGRADE_NATIVE.md` §Ф6 (23–24.08).

Контур до боя уже пройден для перечисленных ниже флагов на стейджинге `:8092`
(кроме оси календаря — см. §0). Дальше — только бой `:8091`, затем klient-1
тем же прибором.

---

## §0. Порядок по риску (не по алфавиту)

Критерий: сначала флаг с **минимальным влиянием на текст ответа** и **дешёвым
откатом** (одна строка env + рестарт). Последним — флаг, который шире всего
меняет отбор кандидатов.

| № | Флаг | Почему здесь | Влияние на `/ask` | Откат |
|---|---|---|---|---|
| 0 | `ASK_SQL_RRF` | **уже в бою** с 23.08 | пятая ветвь ANN корпуса + SQL-RRF | снять строку env (уже не нужен как шаг включения) |
| 1 | `ASK_HEALTH_NATIVE_FRESHNESS` | только `/health`; путь ответа не читает эти поля | нет | убрать `=1` / восстановить bak env |
| 2 | `ASK_RESOLVER_IVF` | меняет путь резолвера при готовом IVF; без индекса — прежний exact | да (имена/значения) | убрать `=1` |
| 3 | `ASK_SOLR_SYNONYMS` (+ `ASK_SOLR_SYNONYMS_DICT`) | query-side `ts_lexize` рядом со стеммом; шире всех влияет на поверхности | да (поиск/кандидаты) | убрать `=1`; alias-джойны остаются |
| — | `ASK_CALENDAR_AXIS` | **включать нечего**: на okna `search_meta` без `calendar_*` (пакетный контур не отдаёт `$metadata`); `calendar_axis_open()` = false → no-op. Включение бессмысленно до починки контура / выката карты корпуса | фактически нет | не применимо на okna сейчас |

Хвост после шагов 1–3: перемер латентности `ASK_SQL_RRF` на **свободном GPU**
(открытый хвост Ф6.1: +16 с при GPU 100 % на klient-1). Число «нормы»
латентности — **снимается в момент включения/перемера**, не из бракованных
прогонов под очередью эмбеддера.

## §1. Общий ритуал на каждом шаге

Инструмент замера (сам флаг не ставит):

```bash
# ДО (флаг снаружи ещё 0 / отсутствует)
F6_FLAG=ASK_HEALTH_NATIVE_FRESHNESS F6_PHASE=before \
  ASK_URL=http://127.0.0.1:8091/ask \
  bash ubuntu/serenedb/f6_rollout_measure.sh

# включение снаружи: строка в env юнита/процесса + рестарт; бэкап env до правки
# ПОСЛЕ
F6_FLAG=ASK_HEALTH_NATIVE_FRESHNESS F6_PHASE=after \
  ASK_URL=http://127.0.0.1:8091/ask \
  bash ubuntu/serenedb/f6_rollout_measure.sh

# таблица сравнения
F6_FLAG=ASK_HEALTH_NATIVE_FRESHNESS F6_PHASE=compare \
  bash ubuntu/serenedb/f6_rollout_measure.sh
```

Что снимает один `before`/`after`: готовность (`/health` + живой `/ask`),
`AB_PROBE=okna` (`ubuntu/serenedb/ab_scorer.py` + `ab-probe-okna.tsv`),
`ubuntu/serenedb/golden.sh` + `golden-questions.txt`, латентность одного `/ask`,
тело `/health`. Пустой успех при недоступной модели/базе скрипт не выдаёт
(ненулевой код + сообщение).

Перед любым живым прогоном: модель и эмбеддер отвечают (урок брака замера —
`docs/HOW_NOT_TO.md` / план §Ф6: готовность после рестарта доказывается живым
`/ask`, не одним `/health`).

Откат env (образец Ф6.1 23.08): восстановить
`/etc/1c-serene-ask-<база>.env.bak-pre-…` (или снять строку флага) →
`systemctl restart 1c-serene-ask@<база>` (бой) либо перезапуск процесса
`serene_ask_probe.py` на `:8092` без флага. Повтор `F6_PHASE=after` (или
нового `before` на откате) тем же прибором — подтверждение, что ответы
вернулись к снимку ДО.

## §2. Шаг 0 — `ASK_SQL_RRF` (уже включён; не «включать», а зафиксировать)

| | |
|---|---|
| Статус | бой `:8091` с 23.08 (`PLAN_UPGRADE_NATIVE` §Ф6.1) |
| ДО (история) | флаг 0: **12/24**, **60,17 с**; флаг 1: **12/24**, **76,31 с**; **VERDICT_DIFFS 0** |
| Провал тогда | смена вердикта на вопросе; сбои обращения; брак замера (рестарт посреди набора / выгруженная модель) |
| Сейчас | перемер латентности на свободном GPU — **снимается в момент перемера**; порог «норма» = медиана ДО под тем же контуром GPU ± договорённый запас (пока не снят — в отчёт не писать «ок по латентности») |
| Откат | снять `ASK_SQL_RRF=1` из env + рестарт; bak `env.bak-pre-f61-*` (23.08) |

## §3. Шаг 1 — `ASK_HEALTH_NATIVE_FRESHNESS` (первый к включению в бой)

| | |
|---|---|
| Что включаем | `ASK_HEALTH_NATIVE_FRESHNESS=1` (+ при нужде `ASK_HEALTH_SEARCH_IDX`, умолч. `search_idx`) |
| Почему первым | `/health` дополняется полями `sdb_metrics`; `/ask` не меняется |
| ДО | `f6_rollout_measure.sh` phase=before на `:8091`; зафиксировать HTTP `/health`, наличие/отсутствие native-полей, AB_PROBE **8/8** (базлайн боя 24.08: **~55,98 с**, маркер `0err/8`) |
| ПОСЛЕ | тот же прибор; эталон стейджинга 24.08: `/health` **200** за **~0,13 с**, поля buffered/failed_commits/refresh_pending/refresh_active отвечают; AB_PROBE **8/8**, **0 сбоев** |
| Провал | `/health` ≠ 200; AB_PROBE errs>0 или hits < hits_ДО; любой сдвиг вердикта probe (для этого флага ожидаем **0** сдвигов на `/ask`) |
| Числа, которых ещё нет на бое | точная мс `/health` и native-поля на `:8091` — **снимаются в момент включения** |
| Откат | убрать флаг / восстановить bak → рестарт → phase=after на откате = снимку ДО по probe |

Фактура: `docs/F6_FRESHNESS_FACTS.md`; стейджинг — CHANGELOG 24.08.

## §4. Шаг 2 — `ASK_RESOLVER_IVF`

| | |
|---|---|
| Что включаем | `ASK_RESOLVER_IVF=1` (`ASK_RESOLVER_IVF_IDX` / `resolver_ivf_idx`) |
| Почему вторым | меняет резолвер, но при неготовом IVF код остаётся на exact; откат — одна строка |
| ДО | phase=before; AB_PROBE 8/8; по возможности построчный diff `AB_CONTOUR=okna` (`ab-gold-okna.tsv`) — **снимается в момент**, если гоняют полный набор |
| ПОСЛЕ | эталон `:8092` 24.08: `_resolver_ivf_ready()`=True, IVF `<#>` отвечает, AB_PROBE **8/8**, **44,19 с** (латентность тогда под нагрузкой GPU — не норма) |
| Провал | errs>0; hits < hits_ДО; построчный VERDICT_DIFF против снимка ДО на полном gold — любая новая FAIL-строка при том же GPU/модели |
| Откат | `ASK_RESOLVER_IVF=0` / снять строку → рестарт → повтор замера |

Замок оффлайн: `ubuntu/serenedb/test_resolver_ivf.py`.

## §5. Шаг 3 — `ASK_SOLR_SYNONYMS`

| | |
|---|---|
| Что включаем | `ASK_SOLR_SYNONYMS=1` и имя `ASK_SOLR_SYNONYMS_DICT` (на okna словарь **`search_dict_syn`**: **221** правило / **23 305** байт из 254 алиасов — уже в базе) |
| Почему последним из рабочих | шире всего меняет query-side разбор; alias-слой ещё не снят |
| ДО | phase=before на бое без флага; полный gold-diff желателен |
| ПОСЛЕ | эталон `:8092` с флагом: AB_PROBE **8/8**, **0 сбоев**, средняя **69,02 с** (рост отнесён к очереди эмбеддера, не к словарю — CHANGELOG 24.08); `ts_lexize('search_dict_syn','окно')` → `{окно}` |
| Провал | errs>0; hits < hits_ДО; новые FAIL на `ab-gold-okna.tsv` vs ДО; отсутствие словаря / пустой `ts_lexize` на контрольном токене |
| Латентность | сравнимая цифра — **только на свободном GPU**; иначе в отчёт «латентность загрязнена», не «провал флага» |
| Откат | снять `ASK_SOLR_SYNONYMS` → рестарт; самодельные alias-джойны остаются |

Фактура: `docs/F6_SYNONYMS_FACTS.md`.

## §6. `ASK_CALENDAR_AXIS` — не шаг боя okna

На okna ключи `calendar_*` в `search_meta` пусты (пакетный контур / `$metadata`).
Флаг на `:8092` уже ставили: ось no-op, AB_PROBE 8/8 без эффекта оси
(CHANGELOG 24.08). Набор `ubuntu/serenedb/ab-calendar-axis-okna.tsv` — для
базы **с** картой, не как ворота включения на пустой meta.

Включать в бой okna **нечего**, пока контур не начнёт отдавать метаданные и
такт не заполнит карту. После появления ключей — отдельный ритуал с
`AB_CALENDAR_AXIS=okna` и тем же `f6_rollout_measure.sh` (расширение phase —
по факту данных).

## §8. Сводка порогов (коротко)

| Метрика | Провал |
|---|---|
| готовность | нет JSON `/ask` или `/health` не 200 → стоп, замер бракован |
| AB_PROBE | errs>0 или hits < hits_ДО |
| golden | скрипт/прибор вернул ненулевой код; пустой набор не считается успехом |
| построчный gold | новая FAIL-строка vs ДО при живой модели |
| латентность | без свободного GPU — не вердикт; с ним — регресс vs ДО того же шага сверх запаса, **снимаемого при before** |
