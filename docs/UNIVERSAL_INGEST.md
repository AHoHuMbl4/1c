# Универсальный приём данных: любая база, вся информация, из коробки

Требование владельца (2026-07-25): это **коробочный продукт для бизнеса**. Значит:
- **работает из коробки** — никакой ручной настройки под конкретную базу;
- **базы у всех разные** — конфигурация, язык, имена заранее неизвестны;
- **информация должна быть вся** — не выбранное подмножество.

Документ фиксирует, что в прежнем подходе этому противоречило, и как строится правильный.

## 1. Что было неверно (признано 2026-07-25)

### Ошибка 1: сущности отбирал человек
`serene-entities.txt` — **22 сущности, отобранные вручную** из 4585. Обосновывалось тем, что
авто-дискавери не отличает бизнес-сущности от платформенных «без хардкода».

Для коробки это неверно дважды: ручной шаг ломает «из коробки», а вопрос про данные вне этих 22
останется без ответа — при требовании «инфа должна быть вся».

**Правильно:** не выбирать вообще. Берём **всё, что непусто и доступно на чтение**. Задача «какая
таблица нужна» решается не отбором при загрузке, а **поиском по метаданным в момент вопроса** (§4).
Отделять «бизнес» от «платформы» не требуется: пустая сущность и так не попадёт в ответ.

### Ошибка 2: `Ref_Key` считался универсальным контрактом
Загрузчик предполагает `$orderby=Ref_Key` и дедуп по `ref_key`. Я защищал это как «контракт платформы,
а не хардкод». **Разбор `$metadata` (4585 типов) это опроверг:**

| Объявленный ключ | Типов | Что это |
|---|---|---|
| `Ref_Key` + `LineNumber` | **1840** | табличные части |
| `Ref_Key` | 1129 | объекты (справочники, документы) |
| `Recorder` + `Recorder_Type` | 191 | регистры по регистратору |
| `Recorder` + `LineNumber` + `Recorder_Type` | 101 | движения |
| **`Организация_Key`** | 42 | ← **ключ КИРИЛЛИЦЕЙ** |
| `Recorder_Key` | 41 | |

**Предположение `Ref_Key` неверно для 76% типов.** Ключи бывают составными, а их имена — на языке
конфигурации. То же с полем версии: оно объявлено лишь у **1129 из 4585** типов (24%).

**Правильно:** ничего не предполагать. **Все 4585 типов объявляют свой ключ в `$metadata`** — читаем
оттуда в рантайме.

## 2. Принцип

> Ни одно имя поля, сущности или ключа не живёт в коде. Всё берётся из `$metadata` конкретной базы
> при подключении и хранится как её профиль.

Что читаем для каждой сущности:
- **ключ** (`<Key><PropertyRef .../></Key>`) — возможно составной, на любом языке;
- **состав и типы свойств** — для схемы витрины и типизации;
- **наличие служебных свойств** (версия записи, пометка удаления, признак группы) — **по факту наличия**,
  а не по предположению;
- **навигационные свойства** — для резолва ссылок.

Человек при установке задаёт только **адрес OData, логин и пароль читателя**.

## 3. Приём данных: берём всё

```
При подключении базы (разово):
  1. служебный документ OData  -> список ВСЕХ сущностей
  2. $metadata                 -> для каждой: ключ, свойства, типы
  3. перепись: $count по каждой -> кто непуст, кто закрыт правами
  4. первичная загрузка всего непустого

Дальше регулярно:
  дельта по изменившемуся (§5)
```

Замеренные на стенде обстоятельства:
- перепись 4585 сущностей ≈ 0.1 с на сущность → **~8 минут разово**;
- часть сущностей отдаёт **«Доступ запрещен» (код 20)** под читателем — это законно (права 1С поверх
  состава OData). Такие пропускаем и **явно показываем в профиле базы**, а не замалчиваем;
- пагинация и дедуп используют **объявленный ключ**, а не `Ref_Key`.

## 4. Как LLM работает с базой неизвестного размера

Число сущностей — величина **неизвестная и разная**: у нас 4585, у другого клиента будет своё.
Значит решение не должно зависеть от порядка величины. Ключевая мысль: **LLM никогда не видит схему
целиком** — ни всю, ни «сокращённую по нашему усмотрению».

### 4.1 Профиль базы строится сам (`SUMMARIZE`)

Движок умеет профилировать **любую** таблицу, ничего о ней не зная:

```sql
SUMMARIZE TABLE <любая_таблица>;
-- column_name, column_type, min, max, approx_unique, avg, std, q25, q50, q75, count, null_percentage
```

Замеры на нашей витрине:

| Что | Значение |
|---|---|
| Профиль таблицы 2696 строк | **17.8 мс** |
| Профиль ВСЕЙ витрины (12 таблиц, 354 колонки) | **0.56 с** |
| Размер профиля | одна строка на колонку — сотни байт на таблицу |

Профиль растёт **линейно по числу колонок**, а не по числу строк. Для базы любого размера это минуты
разово плюс инкремент. И он не содержит ни одного нашего предположения об именах.

Пример разделения без единого имени в коде (доля уникальных значений):

| Колонка | Уникальных | Класс |
|---|---|---|
| `Ref_Key` / `DataVersion` / `Code` | 99–103% | идентификаторы, для поиска бесполезны |
| `Description` | 103% | наименование — искать по нему нужно |
| **`Город`** | **14.1%** | **измерение** — то, что нужно резолверу |
| `IsFolder`, `Телефоны`, `ИНН` | 0–1 значение | мусор, не грузить в индексы |

### 4.2 Три независимых сигнала выбора таблицы

Контекст LLM перестаёт зависеть от размера базы, потому что таблицы выбираются **до** обращения к модели:

1. **Значение из вопроса.** Если человек назвал «Казань», это значение само указывает на таблицу и
   колонку — у нас уже есть `resolver_index (таблица, колонка, значение)`. Сигнал не зависит от того,
   1000 сущностей в базе или 100 000.
2. **Поиск по профилю.** Имена сущностей и колонок, типы, примеры значений, размеры — индексируются
   тем же инвертированным индексом (BM25 + вектор), что и данные. По вопросу достаются только
   релевантные таблицы.
3. **Догрузка по требованию.** Если модели мало — она запрашивает `DESCRIBE`/`SUMMARIZE` конкретной
   таблицы отдельным вызовом (как агент исследует незнакомый код). Схема раскрывается постепенно,
   а не целиком.

Итог: **в контекст попадает не «вся схема» и не «наш отбор», а выборка под конкретный вопрос.**

### 4.3 Честно: что проверено, а что нет

✅ Проверено: `SUMMARIZE` работает на кириллических таблицах, стоит 17.8 мс, разделяет колонки по
кардинальности; полнотекст и вектор поверх метаданных технически доступны (§6).

❌ Не проверено и требует реальной базы: **качество автоклассификации колонок**. Первая быстрая
эвристика на стенде **ошиблась** — брала `min` как образец формы значения, а у текстовых колонок это
пустая строка, из-за чего `Город` (настоящее измерение) попал в «прочее». Правильно брать несколько
случайных значений, а не `min`.

Проверить это на нашем стенде **нельзя**: **332 из 354 колонок содержат 0–1 различное значение** —
база пуста. Классификатор настраивается и валидируется только на базе с реальными данными
(та же Фаза 7, `PRODUCTION_PLAN.md`).

## 5. Свежесть

Такт — **10 минут** (решение владельца). Механизм зависит от того, что объявляет тип:

| Что объявлено в `$metadata` | Как ловим изменения |
|---|---|
| поле версии записи (1129 типов) | проекция `$select=<ключ>,<версия>` и диф — **проверено живой записью**, §6 |
| ключ по регистратору (292 типа) | движения меняются вместе с документом → перечитываем движения изменившихся документов |
| прочее (независимые регистры сведений и т.п.) | окно по периоду либо полное сравнение — обычно невелики |

Стоимость на стенде: проекция ключ+версия ≈ 0.12–0.20 с на сущность; при отсутствии изменений прогон
заканчивается за секунды.

## 6. Проверенные факты (замеры, не оценки)

| Факт | Значение |
|---|---|
| Поле версии меняется при **каждой** записи объекта | подтверждено контролируемой записью: `AAAAAQAAAAs=` → `AAAABQAAAAA=` → `AAAABgAAAAA=` |
| …меняется даже при записи **без изменений** | да → возможны лишние дотягивания, но не неверные данные |
| Служебные поля в русской конфигурации именуются по-английски | да, но **это не повод их предполагать** — ключ берём из `$metadata` |
| Локаль словаря полнотекста | **не влияет**: `ru_RU`, `en_US`, `C` → одинаковые 37, заглавными и строчными |
| Стемминг | держим **выключенным** — language-specific |
| Полнотекст по кириллице | совпал с эталоном `LIKE` до строки |
| Индекс над данными в Postgres | работает через VIEW; 50 тыс. строк — 423 мс |

## 8. Честные риски

1. **Объём первичной загрузки.** «Вся информация» на реальной ERP — часы первой выгрузки и заметный
   объём хранения. Это цена требования; принять осознанно и измерить на реальной базе.
2. **Права.** Часть данных читатель не увидит (законно). Продукт обязан это показывать в профиле базы.
3. **Табличные части** (1840 типов, ключ `Ref_Key + LineNumber`) — самая массовая группа; решить,
   грузить сразу или по требованию.
4. **Регистры** — отдельная стратегия (§5), проверяется на Фазе 7, когда появятся реальные обороты.
