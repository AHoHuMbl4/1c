# Как работает система — только смысл

Версия без ссылок на код: что происходит и зачем. Точная разводка по файлам и
строкам — в `HOW_IT_REALLY_WORKS.md`; этот документ — понимание, не карта.

## Одним абзацем

Данные из 1С только читаются и складываются в базу-витрину SereneDB. Фоновый
конвейер по таймеру превращает витрину в поисковый слой: тексты строк, их
вектора, словари синонимов, карточки сущностей. Когда человек спрашивает бота,
модель разбирает вопрос, поиск находит в слое нужные таблицы и меры, база
считает числа SQL-агрегатами, модель пишет текст вокруг уже посчитанных чисел,
гейт проверяет ответ, и бот отдаёт его человеку. Модель никогда не считает и не
ищет сама: она разбирает, выбирает и формулирует.

## Контур 1 — данные (фоновый, без человека)

1. **Выгрузка из 1С.** 1С только читаем, записи нет физически. Два пути
   доставки, работают взаимоисключающе: пакетный агент на Windows-машине
   клиента шлёт готовые пачки CSV по HTTPS, либо OData-шлюз отдаёт данные по
   HTTP на запросы конвейера.
2. **Витрина.** Всё ложится в таблицы SereneDB — по таблице на вид документа,
   справочника, регистра. Имена таблиц — имена сущностей 1С.
3. **Такт конвейера.** Таймер systemd запускает пересборку раз в минуту.
   Движок сам, SQL-скриптами: собирает текстовые представления строк в единый
   корпус, считает вектора текстов (эмбеддер на GPU), строит полнотекстовый
   индекс, компилирует словари синонимов, строит карточки сущностей и резолвер
   значений («Сбербанк» → конкретный элемент справочника). Вектора — числовые
   отпечатки смысла текстов; по ним поиск и находит «про продажи», даже когда
   слов «продажа» в тексте нет.
4. **Результат** — поисковый слой: корпус текстов + вектора + индекс + словари
   + резолвер + карточки. В момент ответа система ходит только в этот слой,
   к 1С — никогда.

## Контур 2 — путь вопроса (реальное время)

1. **Канал.** Человек пишет боту в Telegram или в веб-чат. Бот — OpenClaw,
   персона ассистента 1С.
2. **Мост.** Бот зовёт инструмент `ask_1c` (MCP). Мост проверяет токен,
   смотрит, нет ли отложенного контекста с прошлого обмена (меню, уточнение),
   и шлёт вопрос HTTP-сервису `ask`.
3. **Разбор вопроса.** Языковая модель (Qwen) превращает вопрос в
   структурированное намерение: что спрашивают (мера: сумма, количество,
   список), о каких сущностях, нет ли отказа/пустяка. Выход — JSON, не проза.
4. **Период.** «Вчера», «за август», «с начала года» — разбирает код по
   календарю, без модели. Спорные прочтения периода («этот месяц» на границе)
   дают варианты-топ readings.
5. **Поиск.** Вопрос превращается в вектор (эмбеддер), ищется по корпусу
   комбинацией: полнотекстовый поиск (bm25), векторный поиск, словари
   синонимов, резолвер значений. Кандидаты дожимаются реранкером (модель на
   GPU, сортирует «насколько документ про то, что спросили»). На выходе —
   короткий список таблиц-кандидатов с колонками-мерами.
6. **Выбор, что считать.** Если прочтение вопроса одно — идём считать. Если
   прочтений несколько («выручка» как отгрузки или как оплаты) — бот
   показывает меню-уточнение; каждый выбор получает «билет», и следующим
   сообщением человек выбирает вариант. Модель помогает на развилках: выбор
   сущности, выбор оси для рейтингов. Есть ранние тупики: остатки по
   складам, которых нет в базе, — честный отказ без поиска.
7. **Счёт.** Числа считает только база: SQL-агрегаты (sum, count, группировки)
   поверх витрины. Никаких вычислений в модели или в коде моста.
8. **Текст ответа.** Модель пишет прозу, видя имена слотов («SUM_реализация»),
   но НЕ видя чисел. Числа в готовый текст подставляет код. Затем гейт
   проверяет: все ли числа из базы попали в текст, нет ли выдуманных цифр, не
   утёк ли служебный текст, отвечен ли вопрос. Провал гейта — один повтор
   генерации.
9. **Обратно.** Сервис отдаёт JSON (вид ответа, текст, числа, опции меню) —
   мост форматирует строку — бот отдаёт человеку. Если было меню, мост
   запоминает pending, чтобы следующий ответ человека свёлся с билетом.

## Каналы и чипы подсказок

**Два канала человека:** Telegram-бот и веб-чат (Open WebUI, персона
«Ассистент 1С»). Внутри оба идут одним путём — вопрос попадает в тот же
инструмент `ask_1c`, разница только в подаче.

**Меню-уточнение в канале.** Когда у вопроса несколько прочтений, ответ — не
вопрос «что вы имели в виду?», а готовые варианты:

- в Telegram — кнопки под сообщением (нажал — выбор улетел, кнопки снялись);
- в вебе — **чипы**: кликабельные подписи вариантов под ответом
  («Общая выручка по компании», «С учётом оплат картой и долгов клиентов»).

**Как чип сводится к выбору.** Чип — это просто текст варианта; настоящий
«выбор» — одноразовый билет, выданный вместе с меню. Клик по чипу плагин веба
сводит к билету (по подписи, её началу, номеру или уникальному слову). Если
плагин не сработал — то же самое делает мост по отложенному контексту. Человек
может и не нажимать: написать вариант словами или номером — сведётся тем же
механизмом. Билет просрочен или неверен — сервис не падает: выдаёт меню заново
со свежими билетами.

**Подсказки веба — отдельная история.** Веб ещё и сам генерирует
чипы-продолжения диалога («follow-up»: что ещё можно спросить) — это отдельный
вызов модели самого интерфейса, живёт своей жизнью и нашими кнопками не
является. Статичные подсказки для живых вариантов не годятся: варианты у нас
каждый раз из данных.

**Клик — не память.** Нажатие чипа доказывает выбор только в этом обмене.
Запомнить выбор на будущее («всегда считай выручку так») — только явное слово
человека; система ведёт такую память по базе и пользователю отдельно.

## Особые случаи

- **Продажи/деньги:** кандидаты-регистры накопления получают приоритет,
  выбран канонический регистр продаж; мера «сколько» без слова денег — не
  подменяет молча сумму на количество: это развилка или вопрос.
- **Рейтинги/сравнения:** модель выбирает ось (по товарам, по клиентам),
  потом детерминированный расчёт; простой случай может уйти без генерации
  прозы — готовой таблицей.
- **Отказ:** отказ при живых данных — дефект; честный отказ — только когда
  данных в базе правда нет, и это видно из слоя.
- **Молчаливая потеря данных** — дефект: если что-то не вошло в ответ, об этом
  сказано в тексте ответа.

## Разделение труда (главный принцип)

| Кто | Что делает | Чего никогда не делает |
|---|---|---|
| База (SereneDB) | хранит витрину, ищет, считает все числа | — |
| Модель (LLM) | разбирает вопрос, выбирает на развилках, пишет текст | не считает, не ищет, не видит схему и числа при генерации |
| Эмбеддер/реранкер (GPU) | вектора текстов и вопроса, дожим кандидатов | — |
| Код (ask, мост) | период, подстановка чисел, гейты, билеты, формат | не заменяет правила модели своей логикой «на месте» |
| 1С | источник, только чтение | не изменяется никогда |

## Инфраструктура — по смыслу

- **Окно (боевой контур okna)** — LXD-контейнер на GPU-хосте Hetzner: внутри
  SereneDB, сервис ask, мост, бот.
- **GPU-хосты** — эмбеддер и реранкер на одном, вторая модель — на другом;
  внутренняя сеть, трафик не ходит через интернет.
- **LLM** — Qwen: словари синонимов и служебные разборы ходят через OpenRouter,
  дешёвые и короткие вызовы; принцип «1 задача = 1 вызов».
- **Секреты** — только в env-файлах на серверах; в git их нет.

## Чем проверяется качество

- **Живая проба здоровья** `/health`: корпус на месте, разрывов нет — 200.
- **Прогоны по эталонам:** список вопросов с правильными ответами гоняется
  против живого сервиса; доля совпадений и виды ошибок — в журнале исходов.
- **Гейты разработки:** коммит не пройдёт без обновления документов, графа
  зависимостей и замеров; выкат — без пройденной золотой пробы.
- **Живые пробы приёмки** — настоящими сообщениями в бота, не синтетикой.

## Инварианты (то, что не пересматривается)

1. 1С только читаем — двумя слоями защиты.
2. Числа считает только база; модель — слова и выбор.
3. Схема базы в модель не уходит; график — после ответа, не вместо.
4. Отказ при живых данных — дефект; догадка — тоже ошибка.
5. Молчаливая потеря данных — дефект.
6. Коробочность: на незнакомой базе всё работает без правки кода и без знания
   её конкретики — всё, что можно, система узнаёт сама из метаданных.
7. Один путь: любое поведение — общий механизм, без точечных заплаток под
   конкретные вопросы.
