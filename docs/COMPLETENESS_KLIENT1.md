## 2. Причины пропусков

`k1-skipped.txt` причин не несёт (одна колонка). Классификация — из журнала
агента `k1-agent28.log` (хвост такта 16.08 17:55 – 17.08 08:31 UTC) и из замера
15.08 по тем двум сёстрам, которых в этом хвосте уже нет.

Покрытие журнала: это **хвост**, не полный обход. Первая строка обрезана;
полная сущность восстанавливается из скобок —
`InformationRegister_ЗаданияКРасчетуДлительностиДоВыпускаПоЭтапамПроизводства`
(`[no_read_right]`). Дальше журнал идёт по `InformationRegister_*` до
`InformationRegister_РеестрДокументов` и обрывается на отправке порции
(17.08 08:31, «чанков 35»). Документы, справочники, константы, журналы и
начало регистров в этот хвост не попали.

Машиночитаемые теги — `windows/packet-agent/src/PacketAgent.cs:2130-2179`:
`[no_read_right]` (HTTP 401, код 20, нет роли «Чтение»), `[not_published]`,
`[rls_filtered]` (частично, данные отданы), без скобок — сбой 1С/сети/памяти.

| Причина | Уникальных сущностей | Где измерено |
|---|---:|---|
| `[no_read_right]` / HTTP 401 код 20 | **761** | `k1-agent28.log`: 760 полных строк + 1 обрезанная первая |
| 1С не отвечает (после 3 сужений страницы) | **7** | тот же журнал, без скобок. Имена: `ЗаданияКРасчетуСебестоимости`, `КодировкиФайлов`, `КонтрольОтправкиФайловВ1СДокументооборот`, `НаличиеФайлов`, `НомераОтсканированныхФайлов`, `ОбъектыКОбновлениюПечатныхФорм`, `РеестрДокументов` (все — `InformationRegister_*`, все в `skipped`) |
| «Время ожидания операции истекло» | **2** | тот же журнал: `InformationRegister_ОбъектыИнтегрированныеС1СДокументооборотом`, `InformationRegister_ОбъектыПроблемСостоянияСистемы` |
| память (`System.OutOfMemoryException`) | **1** | не в этом хвосте; замер 15.08, CHANGELOG: `AccumulationRegister_СебестоимостьТоваров_RecordType` (читал 6,7 ч, 638 330 строк, выбросил). Сестра основной таблицы, основная доехала — см. §3 |
| 1С не отвечает (вне хвоста) | **1** | замер 15.08: `AccumulationRegister_ПрочиеАктивыПассивы_RecordType`. Тоже сестра, основная доехала — §3 |
| `[rls_filtered]` (частично, **доехали**) | **5** | журнал; все пять входят в 38 дочитанных, не в потерю |
| `[not_published]` / `[infra_blocked]` / `[rls_error]` | **0** | в этом хвосте нет |

Итого классифицировано журналом этого хвоста: **770** пропусков
(761 + 7 + 2). Плюс две сестры из замера 15.08, которых хвост уже не содержит.
Остальные `6298 − 770 = 5528` в этом файле журнала не названы: агент обошёл их
раньше (контур сортируется `StringComparer.Ordinal`, документы и справочники
стоят до `InformationRegister`). По механике шага 14 установщика (роль
`AIReadAll` на клиент-серверной базе не загружена) это тот же
`no_read_right`; поэлементно из данного хвоста не подтверждается, и в таблицу
«сколько 401 из 6298» это число не подставляется.

В планах встречается **6228** как «стоило шага 14». Это оценка прав без
вычета таймаутов и дочитки; в описи держимся файлов: снимок закрытых **6298**,
текущий остаток **6260**.

## 5. Что доедет само

Без действий с нашей стороны и без захода на Windows:

- **Дельты** — каждый час. Всё, что открыто читателю, пополняется.
- **Пустые 1372** — агент перечитывает каждым тактом (`flatAll.Count == 0 →
  return`, пакет не шлётся; появятся строки — приедут). Список
  [`empty.txt`](completeness-klient1/empty.txt).
- **Закрытые** — после открытия прав заходом админа (~полгода, одна команда
  из части А установщика). Агент пробует их каждый такт; механика проверена
  на 38 дочитанных (§1.1). До того дня закрытые домены §4 отвечают по
  регистрам (Б.3).

Сверка контура живёт в приёмнике: `ubuntu/packet/packet_apply.py`,
`_check_contour_arrived` (с 16.08 в коде; на юнитах клиентских копий — выкат
назначает оркестратор, коммит `a8dfbf6`). Расхождение «контур минус витрина»
