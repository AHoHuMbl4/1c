## 1. Что установлено твёрдо

Ниже — только то, что подтверждено **несколькими независимыми проверками**.

### 1.1 Путь «корпус = представление» закрыт

**[код: `[2]`, `[3]`, подтвердили Р1 и Р3 самостоятельно]**
Индекс поверх `VIEW` **заморожен на момент `CREATE INDEX`**:
`server/connector/duckdb_catalog.cpp:874` — «View-backed indexes are STATIC — captured
at CREATE INDEX, no DML refresh». Тест-«пин»: после `INSERT` в базовую таблицу индекс
новых строк не отдаёт. `VACUUM (REFRESH_*)` не помогает — он публикует отложенные
записи, а источник не перечитывает. MATERIALIZED VIEW в движке нет.

⚠ **Оговорка Р2:** строки `STATIC` в бинарнике 26.07.3 нет (grep дал 0). Цитаты — из
исходников того же поколения, не из нашей сборки. Вывод считаем верным, но это
**вывод по исходникам**, а не замер на нашем движке.

**Следствие: корпус остаётся таблицей.** Оптимизируется не хранение, а сборка.

### 1.2 Сборка текста целиком в SQL — работает

**[замер: все три агента, все три ревизора]** Собрать строку из всех колонок таблицы,
**не перечисляя их**, можно. Лучший механизм — `UNPIVOT (val FOR col IN (COLUMNS(*)))`
над `SELECT COLUMNS(*)::VARCHAR`:

| Механизм | Р1 (23 878 строк) | Р2 (та же таблица) | Р3 (вся база) |
|---|---|---|---|
| `UNPIVOT` + `COLUMNS(*)` | **285 мс** | **119–210 мс** | **1,18–1,95 с** |
| `json_keys` + `list_transform` | 1 130 мс | 705–1 024 мс | — |
| `to_json` + `json_each` | 1 408 мс | 1 005–1 468 мс | 2,6–3,2 с |

**`UNPIVOT` выигрывает у всех трёх ревизоров**, и он же:
- **[замер Р1]** обращается с пустыми значениями **как боевой код** — выбрасывает пару,
  а не пишет `null`;
- **[замер Р1, Р2]** даёт одинаковый отпечаток в пяти прогонах подряд.

### 1.3 Отпечаток можно считать в базе

**[замер: все три ревизора]** `sha1()` движка **побайтово совпадает** с `hashlib.sha1` —
проверено на кириллице и на боевой склейке через `chr(0)`.

**Следствие: разовый пересчёт всех 98 тысяч эмбеддингов НЕ требуется**, если текст
собирается тем же составом полей. Опасение `[2]` про `true/false` против `t/f` касается
только формул на `to_json`; при `UNPIVOT` вопрос снимается, но **состав полей обязан
быть сверен построчно перед переключением**.

### 1.4 `pg_class.reltuples` как детектор изменений негоден

**[замер: все три ревизора]** Расходится ровно там, где были правки: 99 009 против
97 965. **[код `[3]`]** причина — `pg_class.cpp:160-176`, читается из метаданных
row-group, а не считается.
**[вывод `[1]`]** решающее: правка поля вообще не меняет `count(*)`.
Точный счёт по всем таблицам стоит **0,107 с** (Р1) — экономить не на чем.

### 1.5 Журнала изменений в движке нет

**[замер: все три агента]** Ни CDC, ни версий строк, ни `xmin`/`ctid`.
Триггеры в бинарнике есть, но для таблиц SereneDB запрещены. Значит обнаружение
изменений — только сравнением отпечатков.

## 2. Что обязано войти в любое решение

Это ограничения, а не пожелания. Каждое найдено ревизором и каждое, будучи нарушенным,
даёт **молчаливую** порчу данных.

1. **Ссылка определяется по ФОРМЕ ЗНАЧЕНИЯ, а не по имени колонки.**
   Иначе теряется `Контрагент` и ещё 25 колонок в 34 таблицах (Р1). Боевой код уже
   делает верно — `serene_search_build.py:676`.

2. **`doc` и `refs` — разные поля, отпечаток от обоих.**
   Формулы `[1]` и `[2]` их сливают; это меняет структуру корпуса и ломает пофилдовый
   поиск (Р2).

3. **Тождество строки — объявленный ключ, а НЕ `rowid`.**
   `[2]` и `[3]` мерили по `rowid`, а он двигается при удалении и вставке (Р1).
   Боевой код берёт `Ref_Key` и составной ключ из `$metadata`.

4. **В `MERGE` обязано остаться `t.doc_hash <> s.doc_hash`.**
   Без него обновляется всё подряд — то есть **молчаливый пересчёт всех эмбеддингов**
   (Р2).

5. **Никакого `VACUUM (REFRESH_TABLE)` на корпусе.**
   Записано в нашем же коде (`serene_search_build.py:911-915`): на таблице с вектором
   это дало 34 ГБ и смерть движка. Только `REFRESH_INDEX`.

6. **Настоящая резервная копия перед работой.**
   `search_corpus_bak` **копией не является** — в ней нет `refs` (Р3). Копия обязана
   содержать `emb` (заполнен у всех 97 965 строк) и `refs`.

## 3. Что осталось нерешённым

- **Цена `ORDER BY` при сборке.** Р1 намерил ×1,2, Р2 и Р3 — ×3,2–4. Расхождение между
  ревизорами не разрешено. Нужен ли детерминированный порядок колонок вообще —
  **решается замером на нашей базе**, а не выбором.
- **Статичность VIEW-индекса на НАШЕЙ сборке** — вывод по исходникам, не замер (Р2).
- **`RETURNING merge_action` и `NOT MATCHED BY SOURCE`** — не выполнялись ни разу.
- **Фильтр колонок по `$metadata`** — как перенести в SQL, не выяснил никто.
- **1 034 строки расхождения** в замере `[1]` — никем не разобраны.
- **Число таблиц** в замерах гуляет: 226 / 233 / 235 / 305. Р3 показал, что 305 —
  это вместе с системными схемами.

## 4. Порядок работ

Версия 1 признана негодной как руководство всеми тремя ревизорами: шаг 4 неисполним
(проверка требует индекса, вынесенного в шаг 7), откатов нет у шагов 1, 2 и 4, шаг 0 не
задаёт артефакт, шаг 7 идёт по боевому индексу без отката и окна простоя.

**Переписано:**

### Шаг 0. Настоящая копия и точка отката
- `CREATE TABLE search_corpus_backup_<дата> AS SELECT * FROM search_corpus` — **со всеми
  колонками, включая `emb` и `refs`**;
- проверить: число строк совпало, `count(emb)` совпал, `refs` не пуст;
- записать коммит, на который откатываемся.
**Готово, если:** копия читается и по ней воспроизводятся контрольные ответы.

### Шаг 1. Сверка состава полей — ДО любых изменений
Собрать текст новой формулой (`UNPIVOT`) для **всех** 97 965 строк во временную таблицу
и сравнить отпечатки со `search_corpus.doc_hash` построчно.
**Готово, если:** расхождений ноль. Есть расхождения — разобрать каждое; это и есть
ответ на вопрос, нужен ли разовый пересчёт эмбеддингов.
**Откат:** удалить временную таблицу, ничего больше не тронуто.

### Шаг 2. Критерий ссылки и ключ строки
Сверить, что SQL-формула распознаёт **те же** ссылочные колонки, что боевой код
(по форме значения), и берёт **тот же** ключ строки (объявленный, не `rowid`).
**Готово, если:** множество разрешённых ссылок совпало с нынешним по всем 226 сущностям.
**Откат:** не требуется, шаг только читает.

### Шаг 3. Замер на копии
На копии из шага 0 прогнать полную сборку новой формулой. Замерить: время, число
запусков процесса, объём данных, покинувших движок (это проверка п. 20 `TARGET.md`).
**Готово, если:** содержимое совпало с боевым корпусом построчно.
**Откат:** удалить копию.

### Шаг 4. Переключение сборщика
Заменить фазу в `serene_search_build.py`. `MERGE` — с условием по отпечатку.
**Готово, если:** такт при нуле изменений уложился в единицы секунд, приёмочный набор
8 из 8, инварианты `1С == витрина == корпус == индекс`.
**Откат:** вернуть прежнюю версию файла из git, корпус не тронут.

### Шаг 5. Индекс — отдельно и в окно простоя
Только если состав индекса меняется. `REFRESH_INDEX`, не `REFRESH_TABLE`.
**Откат:** пересоздать индекс прежним DDL из `search_meta`.
