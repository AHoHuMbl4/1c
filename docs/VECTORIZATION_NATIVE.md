# Как сейчас работает векторизация (нативная, в SereneDB)

Состояние на 20.09.2026, всё проверено на живом контуре okna.

## Механизм — функция движка

Вектора считает **сам движок** функцией `ai_embed(text, model, secret_name)`:
она вызывается прямо в SQL, превращает текст в `FLOAT[]` и сама делает
сетевой запрос к провайдеру эмбеддингов. Никакого внешнего кода
«вычитать → послать → записать» в тракте нет — это запрещено (п. 20
контракта) и не нужно. Источник по функции — доки SereneDB, раздел
Sql › Functions › AI Functions.

## Провайдер — секрет движка, OpenAI-совместимый протокол

Эндпоинт и ключ движок берёт из собственного секрета:

```sql
CREATE SECRET … ( TYPE openai,
  api_key '…', base_url '…', embeddings_path '…' );
```

`TYPE openai` — это протокол (любой OpenAI-совместимый сервис), не вендор.
Секреты ставит такт (`embed_secrets_install.sh/.sql`): по одному на каждую
пару «адрес × ключ» из env (`EMBED_HOSTS`, `EMBED_API_KEYS`), воркеры
досчёта раскладываются по секретам по кругу.

Живой конфиг ок на 20.09: адрес `http://10.3.1.11:8000` (GPU-хост во
внутренней сети), модель **Qwen3-Embedding-4B**, размерность **1024**.

## Что и когда векторизуется

Только недостающее. Раунд досчёта (`embed_missing.sh` → `embed_missing.sql`):

1. отобрать строки цели `WHERE emb IS NULL`;
2. построить план пачек — по числу строк и байтовому бюджету текста;
3. **один массовый оператор на раунд**:

```sql
INSERT INTO :part
SELECT ключи, ai_embed(txt, :'model', :'secret')::FLOAT[1024]
FROM :todo;
```

Массовый нативный вызов — решение владельца; порочный дефект старой сборки
26.07.3 (падение при >16–32 строках в операторе) на живой 26.08.1 не
воспроизводится — 64 и 512 строк в одном операторе проверены живьём.
4. перенести вектора в целевую таблицу `UPDATE … FROM` по ключу, убрать
временные таблицы.

Порядок целей в такте: метки → резолвер значений (`resolver_index`) →
документы корпуса (`search_corpus.doc`) → карточки.

Строки, которым вектор невозможен (NULL/пустой текст/длиннее 20 000
символов), не теряются молча — раунд отчитывает их отдельным счётчиком
«вектор_невозможен».

## Скорость — переподписка исполнителей

`ai_embed` занимает исполнителя движка на всё время сетевого запроса.
Поэтому в конфиге движка пул поднят выше числа ядер (34 исполнителя при
6 ядрах): замер 29.07 показал, что без этого наружу уходило ровно 5–6
запросов при любом числе параллельных сессий — узким местом был не psql,
а исполнители. Работа сетевая, не счётная, переподписка безопасна.

## Где лежат вектора

Колонки `emb FLOAT[1024]` в таблицах поискового слоя: `search_corpus`
(1 678 919 векторов из 1 686 622 строк на 20.09), `resolver_index`
(2 150 079), карточки сущностей. Облачный слепок всех векторов —
S3-бакет `1c-data`, префикс `okna-vectors-20260920` (5 файлов parquet,
восстановление — обновлением по ключу).

## Вопрос пользователя в момент ответа

Текст вопроса векторизуется тем же эмбеддером (тот же адрес, модель,
размерность), но **не через движок** — сервис ответов зовет эмбеддер
прямым HTTP-вызовом (нативный режим для ask выключен флагом по умолчанию).

## Поиск по вектору

ANN-индекс `ivf` в нашей сборке не используется (решение владельца —
заблокирован); поиск идёт прямым сравнением векторов в смеси с bm25,
кандидаты дожимаются отдельным реранкером (Qwen3-Reranker-8B на GPU).
