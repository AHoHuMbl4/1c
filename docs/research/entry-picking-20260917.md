# Ресёрч: выбор правильной сущности и числовой колонки (17.09)

Заказ владельца: 4 независимых агента, один промт без фокусов («поищи в интернете,
где — реши сам»), проблема описана просто: одноимённые объекты 1С (документ vs регистр)
и «мёртвая» колонка («Сумма»≡0 при живой «Всего») → человек получает «0,00, продаж
не было». Полные отчёты: `.claude/state/res1..4-findings.md` (со ссылками на источники).
Исполнители — cursor-agent (субагенты Kimi были недоступны: 402), искали встроенным
веб-поиском.

## Пересечения (найдено независимо; сила сигнала = число агентов)

| Находка | Кто | Уверенность |
|---|---|---|
| Вид объекта из префикса OData EntitySet (`Document_*` / `AccumulationRegister_*` / `Catalog_*`) — гомоним различим по типу, бесплатно | 4/4 | офиц. доки 1С |
| Доктрина платформы: агрегат за период → ресурсы регистра; документ — регистратор | 4/4 | офиц. доки + сообщество |
| Профиль данных: мёртвая колонка видна по zero-variance/non-zero массе, универсально | 4/4 | профилирование/DQ |
| Пробы кандидатов до ответа (execution probing): SUM=0 у соседа ≠ 0 — расхождение, не «продаж нет» | 3/4 | академич. работы |
| Именованная мера (semantic layer) — модель резолвит метрику, не сырую колонку | 4/4 | доки dbt/Looker/Cube/SAP |
| Неоднозначность → меню, не молчаливый выбор | 4/4 | AmbiSQL/CLEAR/PowerBI/SAP |
| Feedback loop: выбор человека → правка определения меры | 1/4 | Databricks Genie |

## Чего в 1С НЕТ (подтверждено живой проверкой на окне 17.09)

- OData-аннотаций мер: `$metadata` источника (890 КБ, 819 EntitySet) — 0 `Annotation`;
  стандартный REST 1С — OData 3.0-происхождение, vocabulary v4 не отдаёт.
- Ролей полей (ресурс/измерение/реквизит) наружу через OData — нет; свойства плоские.
- Готового продукта «ИИ для 1С», раскрывающего механику выбора колонки, — рынок не дал.

## Живая проверка (окно, read-only)

- Префикс вида объекта доходит: имена таблиц корпуса и ключ словаря `src_table`
  (`accumulationregister_реализациятмц`, `document_реализациятмц`, `catalog_…`).
- Боевой словарь: алиас «выручка» висит на «Сумма» (мёртвая) регистра; живая «Всего»
  держит «итого/сумма всего». Слой сущности прав («выручка» → регистр), дефект в слое мер.
- Аномалия: `ASK_SOLR_SYNONYMS_DICT=search_dict_syn` — таблицы нет (только bak 27.08).

## Что вошло в дизайн v18 (design-b.md §1b)

1. Дайджесты опций (числа/счётчики/превью/диапазоны в кнопках clarify; мёртрые — «0 · не
   ведётся») — из probing+меню-консенсуса и решения владельца 16.09.
2. Kind-подписи опций + kind-prior ранжирования (период-агрегат → регистр выше документа,
   правило по ВИДУ объекта, не по имени — п.0).
3. LLM-арбитр опций (подсветка рекомендуемой опции, не молчаливый выбор; fail-soft;
   llm_pick/human_pick в журнал) — решение владельца 17.09 «ставим».

## Оговорки (все четыре агента)

- Ноль бывает правдой: сравнивать кандидатов на том же окне, не банить ноль безусловно
  (в дизайне: константа ≠0 — живая; п.21).
- «Максимальная SUM = правильная мера» — опасно (двойной счёт, валюта); профиль —
  ранжирование/алерт, не истина.
- URL из отчётов поштучно не перепроверялись (квота поиска); опора — на пересечения.
