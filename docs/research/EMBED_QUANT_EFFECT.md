# Квантизация эмбеддера: ускорение пересчёта против потери качества

Собрано по публичным источникам (10.09.2026) под вопрос владельца: поможет ли квантизация
ускорить массовый пересчёт векторов и что она делает с качеством поиска.
Наш случай: Qwen3-Embedding-4B, bfloat16, dim 1024 (MRL-усечение из 2560), одна GPU,
русские документы 1С, метрика — retrieval (поиск нужного документа).

**Ни одно число ниже не наш замер.** Это чужие опубликованные бенчмарки и таблицы из
карточек моделей. Помечено, где это заявление вендора, а где измерение.

Две несовместимые вещи, которые часто путают, — разведены по разделам:

- **(A) квантизация весов модели** (`int8`/`int4`/`fp8`/`GPTQ`/`AWQ`/`GGUF`) — ускоряет и
  удешевляет *вычисление* вектора. Это наш вопрос: пересчёт корпуса.
- **(B) квантизация векторов на выходе** (binary/scalar/PQ) — ускоряет *поиск и хранение*.
  Нам не подходит: в БД колонка `FLOAT[1024]`. Данные приведены одной таблицей, §B.

Что из этого следует по числам:

- **int8/fp8 — почти бесплатно**: −0.09…−0.36% на всех трёх семействах метрик у Gemma.
- **int4 по весам — цена 0.5–1.3%**: у Qwen3-Embedding-4B именно retrieval/STS проседают
  сильнее среднего (−1.14% / −1.29%), у Gemma код — сильнее всего (−1.12%).
- **Размерность и язык влияют на потери**: «большая модель устойчивее к квантизации» на этих
  данных не подтверждается — 8B потерял по среднему больше, чем 4B (−0.81% против −0.72%),
  хотя разница в пределах одного бенчмарка. А вот **мультиязычный** вариант BitEmbed потерял
  в 4 раза больше английского (−2.19%).
  Наш корпус русский — это прямой повод не переносить английские/китайские числа на себя.
- **Все замеры Qwen3-Embedding сделаны на китайском C-MTEB**, не на русском и не на MTEB
  Multilingual. Русских замеров квантизованного Qwen3-Embedding не публиковал никто (см. ниже).
- **QAT vs PTQ** — принципиальная разница. У EmbeddingGemma это QAT-чекпойнты (модель
  обучали с учётом квантизации, [§Quantization-Aware Training](https://arxiv.org/abs/2509.20354)),
  в карточке прямо сказано: «QAT models are evaluated after quantization».
  У Qwen3-Embedding-4B QAT нет — на карточке только GPTQ W4A16, то есть честная PTQ.
- **Post-hoc квантизация проигрывает обученной под низкую точность.** BitEmbed (Qwen3-0.6B,
  MMTEB eng v2): 4-битные *векторы* после post-hoc — 66.31, те же 4 бита у обученной модели —
  67.45; 1 бит — 63.71 против 64.43. То есть «сжать готовую модель» всегда хуже,
  чем «обучить сжатой».

### A2. Скорость: чем квантизация весов реально ускоряет, а чем нет

| Что | Заявленный выигрыш | Условие | Источник |
|---|---|---|---|
| fp16 + FlashAttention-2 + распаковка входа (GPU) | **2.92× (fp16), 3.87× (fp16+FA2)** к fp32 PyTorch, «при отсутствии потери качества»; рекомендуется как основная GPU-конфигурация | GPU, архитектура с поддержкой FA2 | [sbert.net](https://sbert.net/docs/sentence_transformer/usage/efficiency.html) |
| int8-веса (ONNX dynamic / OpenVINO static) | 3.23× / 5.29× | **CPU**. На GPU int8-веса в бенчмарке ST не побеждают fp16 | там же |
| fp16/bf16 на CPU | **0.01×** (деградация в сотню раз, эмуляция) | CPU | там же |
| vLLM FP8 W8A8 | до **1.6×** throughput, 2× экономии памяти, «minimal impact on accuracy» | W8A8 нужен cc ≥ 8.9 (Ada/Hopper/Blackwell); на Turing/Ampere — только W8A16 weight-only (Marlin) | [vLLM docs, FP8 W8A8](https://github.com/vllm-project/vllm/blob/main/docs/features/quantization/llm_compressor/fp8.md) |
| vLLM INT8 W8A8 | ускорение + экономия памяти | Turing…Hopper; **не поддерживается на cc ≥ 10.0 (Blackwell)** | [vLLM docs, INT8 W8A8](https://github.com/vllm-project/vllm/blob/main/docs/features/quantization/llm_compressor/int8_w8a8.md) |
| vLLM INT4 W4A16 | «memory savings and inference acceleration» — но позиционируется для **низкого QPS** (латентность), не для throughput | Ampere+ | [vLLM docs, INT4 W4A16](https://github.com/vllm-project/vllm/blob/main/docs/features/quantization/llm_compressor/int4.md) |
| BitEmbed (ternary веса) | ~2× токенов/с на CPU | CPU, нужна переобученная модель | [arXiv:2606.25674](https://arxiv.org/abs/2606.25674) |

Ключевое для нас: **на GPU квантизация весов — это в первую очередь экономия VRAM,
а не ускорение.** Единственный документированный GPU-выигрыш от весовой квантизации,
который удалось найти, — FP8 W8A8 «до 1.6×» (и это про LLM, не про эмбеддер), причём он
требует Ada/Hopper. Документированные кратные ускорения (3–5×) — это CPU и/или
квантизация выходных векторов. Ускорения эмбеддера на GPU, документированные числом, —
это bf16/fp16 + FlashAttention + батчи, при нулевой потере качества.

| mxbai-embed-large-v1 | float32 → binary | 54.39 → 52.46 | 96.45% (с rescoring; без — 92.5%) | там же |

- Скорость поиска по векторам (CPU, точный перебор, USearch/Faiss): **int8 3.66×, binary 24.76×**
  (мин. 2.99× / 15.05×) — там же. С rescoring ×4–5 int8-векторы держат ~99% качества.
- [arXiv:2505.00105](https://arxiv.org/abs/2505.00105) (MTEB, bge-small/nomic): float8 — 4×
  сжатие при потере **<0.3%** и лучше int8; int8 — **1.5–3.5%** и требует калибровки;
  binary — **7–11%**; float4 — неприемлемо. Модели большей размерности устойчивее.
- [arXiv:2511.13057](https://arxiv.org/abs/2511.13057) (BEIR SciFact): int8 — ~1–2% nDCG@10
  при 4× сжатии, binary — катастрофа.
- [CoRECT, arXiv:2510.19340](https://arxiv.org/abs/2510.19340): «необучаемое» сжатие векторов
  даёт статистически незначимую потерю даже на 100 млн пассажей, но выбор метода зависит
  от модели — единого безопасного пресета нет.
- Позиция TEI (мейнтейнер, issue #219): квантизация векторов — «client-side», TEI всегда
  отдаёт float32 ([issue](https://github.com/huggingface/text-embeddings-inference/issues/219)).
- «ECCLM» из задания не существует как название — поиск по нему пуст; похожие по смыслу
  бенчмарки PQ/OPQ встречаются только как сжатие векторов (CoRECT, Zilliz/Qdrant обзоры).

## ВЕРДИКТ-МАТЕРИАЛ

При каких условиях квантизация безопасна для retrieval — по совокупности источников:

1. **int8/fp8-веса — безопасно** (−0.1…−0.4% на всех опубликованных замерах), при условии,
   что это не weight-only на GPU без аппаратной поддержки: FP8 W8A8 требует Ada/Hopper,
   INT8 W8A8 не работает на Blackwell (cc ≥ 10), на Ampere/Turing остаётся W8A16 — то есть
   скорость почти не меняется, экономится только память.
2. **int4-веса — на границе приемлемого** для «терять точность нельзя»: 0.5–1.3%,
   причём именно retrieval и STS проседают сильнее среднего, а на английском/китайском
   поведение разное. Для русского корпуса цифра неизвестна и, судя по мультиязычному
   BitEmbed (−2.19%), может быть в 2–4 раза хуже английской.
3. **QAT-чекпойнт vs PTQ решает больше, чем битность.** Gemma с QAT: int4 = −0.87%.
   Qwen3-Embedding-4B без QAT, честная PTQ int4 = −0.72% на китайском. Если Qwen не выпускал
   QAT-версию — считать, что мы в худшем из двух режимов.
4. **Квантизация — это про память, а не про скорость на GPU.** Единственные числа ускорения
   от весовой квантизации, которые удалось найти: до 1.6× (vLLM FP8, LLM, не эмбеддер) и
   2× на CPU (BitEmbed). Кратные 3–5× — это CPU или квантизация векторов.
   На одной GPU безопаснее и быстрее сначала выжать bf16/fp16 + FlashAttention + батчи
   (2.9–3.9× без потери качества).
5. **Смешивать в одном индексе векторы от bf16-модели и от int4-модели нельзя** — это два
   разных пространства; квантизация меняет все векторы чуть-чуть, поэтому пересчитывать надо
   **весь корпус**, а не досчитывать дельтами. (Это следствие, а не чужой замер.)
6. **Порог решения — свой замер на своём корпусе.** Ни одного замера квантизованного
   Qwen3-Embedding на русском нет. Минимальный честный тест: gold-набор запросов →
   до/после сравнить recall@10 / nDCG@10, а не косинус (косинус всегда «почти тот же» —
   в [issue llama.cpp #26282](https://github.com/ggml-org/llama.cpp/issues/26282) L2-дрейф
   0.026 соседствует с явной жалобой на падение качества).
7. **Если выбирать компромисс по битам** — порядок предпочтения по опубликованным потерям:
   bf16/fp16 (0) → fp8/int8 (−0.1…−0.4%) → Q8_0 GGUF (−0.26…−0.36%) → int4 QAT (−0.5…−0.9%)
   → int4 PTQ (−0.7…−1.3%) → ternary только с переобучением (−0.5% eng, −2.2% multilingual).
8. **Что действительно дёшево и без риска потерять точность** (по числу из тех же источников):
   усечение MRL-размерности уже сделано (1024/2560); остаются fp16/bf16 + FA2 + батчи,
   `torch.compile`, а из квантизации — только int8 как «память + чуть-чуть скорости».

## ЧТО НЕ НАШЛОСЬ

1. **Замера Qwen3-Embedding-4B в int8/fp8 (W8A8) не существует** в публичном доступе —
   только GPTQ W4A16 (C-MTEB) и GGUF-кванты без таблиц качества.
2. **Русскоязычных (и вообще мультиязычных) замеров квантизованного Qwen3-Embedding нет.**
   Все доступные числа — C-MTEB (китайский) или английский MTEB.
3. **Замеров GGUF Q4_K_M vs F16 для Qwen3-Embedding нет**, хотя Ollama именно так и
   раздаёт модель по умолчанию. Никакого подтверждения, что −0.7% (GPTQ) переносится на Q4_K_M.
4. **GPU-throughput (векторов/сек) для квантизованного эмбеддера — публикаций нет.**
   Есть только CPU-числа (ST 3.2–5.3×, BitEmbed 2×) и FP8 «до 1.6×» для LLM.
5. **Теоретических работ именно про PTQ энкодеров-эмбеддеров** (аналог AWQ/GPTQ-статей, но
   для би-энкодеров) не нашлось; AWQ и GPTQ написаны про декодеры и про латентность генерации.
   Из близкого — только BitEmbed (QAT, требует дообучения).
6. **Официальной позиции Qwen по квантизации их эмбеддера нет** — ни рекомендаций, ни
   предупреждений, ни QAT-чекпойнта.
7. **llama.cpp: рекомендаций по выбору кванта для эмбеддеров в документации нет.** Есть
   незавершённый PR #22562 с инструментом `llama-semantic-bench` (метрика Bhattacharyya,
   заявленная цель — «найти semantic cliff F16 vs Q4_K_M vs Q2_K»), но чисел в нём нет —
   это заготовка, а не замер.
8. **«ECCLM»** (из формулировки задачи) как название статьи/бенчмарка не существует;
   PQ/OPQ-бенчмарки есть только в контексте сжатия векторов, не модели.
9. **Единого безопасного пресета квантизации эмбеддера нет** — CoRECT прямо это фиксирует:
   оптимальный метод сжатия зависит от модели, и его надо подбирать замером.
