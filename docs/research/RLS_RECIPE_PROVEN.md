# Рецепт RLS «читать всё без полных прав» — ДОКАЗАН НА СТЕНДЕ (замер 09.08)

Источник механики: глубокий ресерч `docs/research/rls_odata_research.docx`
(текстовая копия — `RLS_ODATA_RESEARCH.txt`), бриф — `RLS_DEEP_RESEARCH_BRIEF.md`.
Здесь — только то, что проверено замером на живой базе (ut_demo, платформа 8.3.27.1786,
RLS включён: `ОграничиватьДоступНаУровнеЗаписей = Истина`, стандартный вариант).

## Рецепт (ступень 1 каскада)

1. Читатель (пользователь ИБ + элемент справочника «Пользователи») с ролями чтения —
   как уже делает установщик (387 ролей по префиксам, без полных прав).
2. **Профиль читателя содержит ВСЕ используемые в базе виды доступа
   со значением «Все разрешены, без исключений» (`ВсеРазрешены = Истина`).**
   Набор видов читается запросом из базы (`ПрофилиГруппДоступа.ВидыДоступа`,
   различные `ВидДоступа`) — ни одного имени в коде. На стенде: 17 видов.
   Практическое наблюдение: при обычной записи профиля БСП сама заполняет
   табличную часть всеми видами (со значением по умолчанию Истина) — но это
   замер одной базы, код обязан выставить явно.
3. **Читатель состоит только в группах с таким профилем** — ни одной чужой группы
   с ограничениями (агрегат МИНИМУМ(ВсеРазрешеныБезИсключений) берётся по всем
   группам пользователя; пользователь вообще без групп получает «всё запрещено»).

## Замер «до/после» (сеанс читателя, запрос «способом все» = семантика OData без allowedOnly)

До: `InformationRegister_ЦеныНоменклатурыПоставщиков` — HTTP 401 через OData,
не читается даже штатным демо-менеджером закупок (NRE в RLS-шаблоне);
`ЖурналФискальныхОпераций`, `ЗаданияКРаспределениюРасчетов*` — 401 (лог агента ночи 09.08).

После применения рецепта (ai_reader, 387 ролей чтения, профиль «Только просмотр»
с 17 видами «все разрешены», единственная группа «Чтение (AI)»):

| Проба | Результат |
|---|---|
| Справочник.Номенклатура ПЕРВЫЕ 1 | УСПЕХ (контроль, как и раньше) |
| РС.ЦеныНоменклатурыПоставщиков ПЕРВЫЕ 1 | **УСПЕХ** (был 401) |
| РС.ЖурналФискальныхОпераций ПЕРВЫЕ 1 | **УСПЕХ** (был 401) |
| РС.ЗаданияКРаспределениюРасчетовСКлиентами ПЕРВЫЕ 1 | **УСПЕХ** (был 401) |
| ЦеныПоставщиков строк «все» vs «разрешенные» | **2385 = 2385** — полнота числом |
| РС.ЗаданияКЗакрытиюМесяца | отказ (см. остаток) |

## Остаток (ожидаемый, из ресерча)

`ЗаданияКЗакрытиюМесяца` читателю недоступен и после рецепта (админом читается,
81 строка — отказ именно правовой). Это граница рецепта: спецвиды доступа
«Условие»/«Объект»/«ПравоЧтения» и ручные шаблоны, не проверяющие отключённые
виды, механизмом не отключаются. Такие объекты — в манифест skipped с
классифицированной причиной (ступень 4 каскада, всегда активна), при жёстком
контракте полноты — ступени 2-3 (расширение с ролью / привилегированный канал —
решение за владельцем, не реализовано).

## Что это меняет в продукте

- Установщик: после создания профиля/группы/членства — выставить всем видам
  профиля `ВсеРазрешены = Истина` и проконтролировать, что читатель не в чужих
  группах. Контрольная проба: ранее закрытая сущность читается (запрос
  «способом все» / OData без allowedOnly → 200 = строгое доказательство).
- Агент: `allowedOnly=true` — фолбэк чтения + классификация причин skip
  (`not_published` / `no_read_right` / `rls_filtered` / `access_data_stale` /
  `auth_failed` / `infra_blocked`) по кодам OData (ресерч 4.1, 4.4).
- Гигиена данных доступа (ЗаполнениеДанныхДляОграниченияДоступа +
  ОбновлениеДоступаНаУровнеЗаписей через COM) — опциональный шаг для чужих
  пользователей базы; нашему читателю не нужна (ветка RLS исключается
  препроцессором до исполнения — NRE в ней невозможна).

## Квирки COM-канала, вскрытые этим замером

См. `docs/HOW_NOT_TO.md` (свежий раздел про PowerShell↔V83.COMConnector):
строки из выборок приходят пустыми, коллекции маршалятся как Object[],
ошибки 1С — как NullReferenceException; сравнения строк — только на сервере
параметрами запроса.
