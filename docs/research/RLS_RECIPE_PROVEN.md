# Рецепт RLS «читать всё без полных прав» — ДОКАЗАН НА СТЕНДЕ (замер 09.08)

Источник механики: глубокий ресерч `docs/research/rls_odata_research.docx`
(текстовая копия — `RLS_ODATA_RESEARCH.txt`), бриф — `RLS_DEEP_RESEARCH_BRIEF.md`.
Здесь — только то, что проверено замером на живой базе (ut_demo, платформа 8.3.27.1786,
RLS включён: `ОграничиватьДоступНаУровнеЗаписей = Истина`, стандартный вариант).

## Рецепт (ступень 1 каскада)

1. Читатель (пользователь ИБ + элемент справочника «Пользователи») с ролями чтения —
   как уже делает установщик (387 ролей по префиксам, без полных прав).
2. **Профиль читателя содержит ВСЕ используемые в базе виды доступа
   со значением «Все разрешены, без исключений» (`ВсеРазрешены = Истина`).**
   Набор видов читается запросом из базы (`ПрофилиГруппДоступа.ВидыДоступа`,
   различные `ВидДоступа`) — ни одного имени в коде. На стенде: 17 видов.
   Практическое наблюдение: при обычной записи профиля БСП сама заполняет
   табличную часть всеми видами (со значением по умолчанию Истина) — но это
   замер одной базы, код обязан выставить явно.
3. **Читатель состоит только в группах с таким профилем** — ни одной чужой группы
   с ограничениями (агрегат МИНИМУМ(ВсеРазрешеныБезИсключений) берётся по всем
   группам пользователя; пользователь вообще без групп получает «всё запрещено»).

## Замер «до/после» (сеанс читателя, запрос «способом все» = семантика OData без allowedOnly)

До: `InformationRegister_ЦеныНоменклатурыПоставщиков` — HTTP 401 через OData,
не читается даже штатным демо-менеджером закупок (NRE в RLS-шаблоне);
`ЖурналФискальныхОпераций`, `ЗаданияКРаспределениюРасчетов*` — 401 (лог агента ночи 09.08).

После применения рецепта (ai_reader, 387 ролей чтения, профиль «Только просмотр»
с 17 видами «все разрешены», единственная группа «Чтение (AI)»):

## Остаток (ожидаемый, из ресерча)

`ЗаданияКЗакрытиюМесяца` читателю недоступен и после рецепта (админом читается,
81 строка — отказ именно правовой). Это граница рецепта: спецвиды доступа
«Условие»/«Объект»/«ПравоЧтения» и ручные шаблоны, не проверяющие отключённые
виды, механизмом не отключаются. Такие объекты — в манифест skipped с
классифицированной причиной (ступень 4 каскада, всегда активна), при жёстком
контракте полноты — ступени 2-3 (расширение с ролью / привилегированный канал).
Ступень 2 с 10.08 **реализована** (решение владельца 10.08) — раздел ниже.

## Ступень 2 каскада: расширение с ролью чтения — РЕАЛИЗОВАНО (замер 10.08)

Закрывает объекты, у которых в конфигурации нет НИ ОДНОЙ штатной читающей роли
(замер на ЗУП 3.1: 693 объекта из 4359 контура = 16 %, все покрывающие роли
пишущие; охота по ролям с контролем механики — `work/acceptance/probe-rights.ps1`).
Механика: расширение конфигурации `AIReadOnly` с собственной ролью `AIReadAll`
(Read+View на все объекты, без шаблонов RLS = «ГДЕ Истина») + HTTP-сервис
`AISetup` для самоназначения роли читателю. Генератор/установщик —
`windows/odata-setup/src/ai-ext.ps1` (вшит ресурсом в exe, шаг 14 установщика).

**Замеры.** ut_demo (УТ 11, 1791 объект, compat 8.3.12): загрузка и применение
EXIT=0. ЗУП 3.1 (2247 объектов, compat 8.3.24, у владельца): `LOAD-EXIT=0`,
`UPDATEDB-EXIT=0`, endpoint отвечает `read=Да; write=Нет`, контрольная константа
OData 401 → **200**. Универсальность: один и тот же код без правок — обе базы;
всё снимается с живой базы (состав объектов — COM, UUID — ConfigDumpInfoOnly,
шаблоны типов — частичный дамп по объекту класса, compat/язык — дамп корня).

**Форматные требования, доказанные перебором (каждая ошибка — свой замер):**

1. **`/LoadConfigFromFiles -Extension` только хранит расширение; применяет его
   `/UpdateDBCfg -Extension <имя>`** — без этого HTTP-сервис расширения даёт 404
   при правильном vrd, а ошибка применения видна только в ЖР. Это была главная
   ловушка: «загрузилось» ≠ «применилось».
2. Роль расширения даёт права только на **заимствованные** объекты — заимствуем
   все объекты 14 разделов данных (заглушки `ObjectBelonging=Adopted`).
3. `ExtendedConfigurationObject` **контролируется**: при /UpdateDBCfg сверяется
   с реальным UUID объекта основной конфигурации. Реальные UUID всех объектов
   даёт `/DumpConfigToFiles <dir> -ConfigDumpInfoOnly` (27 с на УТ, один файл
   ConfigDumpInfo.xml) — полный дамп не нужен.
4. Набор `GeneratedType` в `InternalInfo` заглушки проверяется строго по классу
   («отсутствует один или более типов объекта»), но TypeId/ValueId могут быть
   свежими GUID. Табличные части в набор не входят. Шаблоны снимаем частичным
   дампом (`-listFile`, по одному объекту класса) — никаких таблиц в коде.
5. Особые классы: у `Constant` нет элемента `ChildObjects`; у `ExchangePlan`
   в `InternalInfo` нужен `<xr:ThisNode>`.
6. Язык заимствуется как объект (`Adopted` + реальный UUID, имя из
   `DefaultLanguage` основной конфигурации).
7. `ConfigurationExtensionCompatibilityMode` расширения ≤ режима совместимости
   основной конфигурации (читаем из дампа корня: `Configuration` в -listFile).
8. **Права от роли расширения действуют только при `БезопасныйРежим=Ложь`** —
   при включённом ПравоДоступа возвращает Ложь, OData 401. Снятие через COM:
   сначала `ЗащитаОтОпасныхДействий.ПредупреждатьОбОпасныхДействиях=Ложь`, потом
   `БезопасныйРежим=Ложь`, потом `Записать()` — в другом порядке запись требует
   интерактивного подтверждения и падает. Изнутри сеанса с расширением снять
   безопасный режим нельзя («Изменение расширения недоступно в безопасном
   режиме») — только снаружи (COM).
9. Публикация HTTP-сервисов расширений: в default.vrd элемент
   `<httpServices publishByDefault="true" publishExtensionsByDefault="true"/>`
   + рецикл пула. Явный `<service>` не нужен. Ручная правка vrd затирается
   при переопубликации из конфигуратора — установщик прописывает её сам.
10. Роль назначается читателю из HTTP-сервиса расширения (сеанс с применённым
    расширением): COM-сеанс расширение не применяет, его роли в метаданных
    COM не видны.

**Границы.** Клиент-сервер без лицензий КОРП: платформа (8.3.11+) запрещает
расширение прав ролями расширений без профиля безопасности — путь закрыт,
установщик пропускает шаг с предупреждением. Эксплуатационный риск: после
обновления основной конфигурации расширение может молчаливо потерять
применимость → нужен мониторинг (переустановка шагом 14 повторным прогоном
установщика идемпотентна).

## Что это меняет в продукте

- Установщик: после создания профиля/группы/членства — выставить всем видам
  профиля `ВсеРазрешены = Истина` и проконтролировать, что читатель не в чужих
  группах. Контрольная проба: ранее закрытая сущность читается (запрос
  «способом все» / OData без allowedOnly → 200 = строгое доказательство).
- Агент: `allowedOnly=true` — фолбэк чтения + классификация причин skip
  (`not_published` / `no_read_right` / `rls_filtered` / `access_data_stale` /
  `auth_failed` / `infra_blocked`) по кодам OData (ресерч 4.1, 4.4).
- Гигиена данных доступа (ЗаполнениеДанныхДляОграниченияДоступа +
  ОбновлениеДоступаНаУровнеЗаписей через COM) — опциональный шаг для чужих
  пользователей базы; нашему читателю не нужна (ветка RLS исключается
  препроцессором до исполнения — NRE в ней невозможна).

## Квирки COM-канала, вскрытые этим замером

См. `docs/HOW_NOT_TO.md` (свежий раздел про PowerShell↔V83.COMConnector):
строки из выборок приходят пустыми, коллекции маршалятся как Object[],
