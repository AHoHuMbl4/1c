## 1. Резюме для владельца

**1. Кто мы на рынке.** Густой рынок заменителей (дешёвый чат+1С, enterprise-агенты, заказная ИИ под ключ, MCP для разработчиков). Пуст **пересечённый** сегмент нашего контракта — «пустой в третьем слое» (mr1): коробка ∧ on-prem ∧ любая база без хардкода ∧ витрина/индекс вне 1С ∧ модель не считает и не ищет ∧ канал сотрудника (Telegram/веб), не IDE. Наивная обёртка (схема/сэмплы в LLM, модель складывает, только облако) проваливается на жёстком контракте; обёртка с local LLM, узкими tools или готовыми отчётами на типовой базе может удовлетворить пилот. Вендор 1С учётный ask не занял (Напарник — код; Аналитика — BI; ITILIUM RAG — база знаний сервиса, не live ERP).

**2. Кому и за что (гипотеза ICP, не замер).** Ядро — операционка УТ/КА (продажи·склад·деньги), собственник/финдир сам покупает, частые ad-hoc цифры и дорогая ошибка; производство — тот же приоритет при тех же сущностях. Второй контур — mid с требованием «данные не в чужом облаке». Не наша война: микро/Фреш, «ChatGPT за 3 тыс.», запись в 1С, ЗУП.

**Сейчас = качество ответа и стабильный контур, не установщик и не продажи.**

**3. Что делать первым.** По живому плану (`activeContext`, срез 10.09): **полная B → план фиксов → L20** (независимая приёмка / вторая база). Инсталлятор (TARGET п.14) — **за горизонтом** зелёного ответа, в конце. До «0 уверенных ложных чисел» на согласованном наборе — только R&D / дружеские пилоты, не коммерция и не франчайзи-реселл. Пока нет доказуемого преимущества на чужой базе, установки «за день до верного ответа» и живого бота после ребута — плагин+MCP+Claude выигрывает по умолчанию (красная команда, mr4).

### 2.3. Выводы рынка (mr1 + уточнения mr8)

1. Обёртка бьёт **скоростью и ценой входа**; для SMB на типовой УНФ/УТ демо «бот про продажи» часто достаточно как ожидания.
2. **Наивная** обёртка (схема/сэмплы в LLM, модель складывает, только облако) **проваливается** на жёстком нашем контракте. Обёртка с local LLM, узкими tools или готовыми отчётами на типовой базе **может удовлетворить пилот** и не провалиться по периметру/числам в узком контуре.
3. Мир сходится к **governed route**, не к сырому Text-to-SQL — это подтверждает ставку п.19, а не «ещё один разъём».
4. Пуст **пересечённый** TARGET-сегмент (пустой в третьем слое); **заменители густые**. Давление: enterprise/Custom справа, дешёвый SaaS слева, OSS data-MCP снизу. Ближе всех по обещанию — СИНИМЕКС, но проект.

## 4. Наши преимущества и недостатки

*Источник: mr3. Приёмка — с поправкой оркестратора (не README).*

### 4.1. Таблица аргументов (сильные строки)

| Аргумент | Покупателю | У обёртки | Вердикт |
|---|---|---|---|
| **Модель не считает и не ищет** (п.19) | Число из учёта, не «оценка модели» | Модель ищет и складывает в контексте (у наивной обёртки) | **Мы лучше** — видно на числовом вопросе + сверка SQL |
| **Контекст не растёт с базой** (п.19) | На ERP не взрывается счёт/шум | Схема/сэмплы/tool-результаты в LLM | **Мы лучше** — слабо видно в питче; на малой типовой базе дифференциация слабее |
| **Гейт чисел кодом** (п.12/18/21) | Ошибочное число не должно дойти | «Не выдумывай» в промте | **Мы лучше** — иногда больше уточнений (фича контракта) |
| **Полнота видима** (п.13) | Знает, на чём отвечает бот | Дыры OData невидимы бизнесу | **Мы лучше** |
| **1С read-only, два слоя** | Страх «ИИ провёл документ» закрыт механизмом | MCP с записью опасен | **Мы лучше / паритет** с аккуратной обёрткой |
| **Целевой on-prem** (п.16) | Проще ИБ/152-ФЗ | Часто Claude/GPT наружу; часть конкурентов уже local LLM | **Мы лучше по цели**; сейчас честно: DeepSeek ещё наружу (временно по TARGET) |
| **Без хардкода, любая база** (п.9) | Коробка без проекта «подпилить» | Часто заточка/маппинги / skills | **По контракту лучше**; снаружи спорно, пока нет инсталлятора и чужой-базы A/B |

Остальное сжато (mr3): единый SereneDB и инкремент свежести — сильны инженерно / по дизайну, покупателю почти невидимы; бизнес-контракт «ошибки запрещены» сильнее позиционированием, но **доказуемость = приёмка**, не текст TARGET.

### 4.2. Приёмка: спор входов vs поправка

| Источник | Утверждение |
|---|---|
| **mr3 / mr4** (по README) | «Приёмка <50% верных» / «меньше половины» — как оружие против «без ошибок» |

**Интерпретация:** honest_no при отсутствии/неоднозначности данных — поведение по п.12/18, не «провал как wrong». Три wrong из 67 — дыра относительно п.3/10 («ошибки запрещены»). **Вердикт для продажи:** продавать нельзя, только R&D-пилоты, пока не 0 уверенных ложных чисел на согласованном наборе.

### 4.3. Слабые стороны (сжато, mr3 + mr4)

- Нет инсталлятора (п.14 в конце) → time-to-value проигрыш обёртке на порядки (недели/**месяцы** инженерии vs часы у конкурента, mr4).
- Эксплуатация: станция ответов вне systemd / порт ≠ юнит (README) → после ребута бот молчит (K8).
- Сложность контура vs 1–2 компонента у обёртки; SereneDB — малоизвестный вендор (риск найма/lock).
- CAPEX GPU/Ubuntu; временный egress LLM бьёт по ИБ-питчу.
- Zero-touch заявлен, держится руками — расхождение обещания и факта.

## 5. Позиционирование

*УТП — из mr3 «3 отличи»; таблица TARGET→сообщение — mr2 §6 (см. §7). Против кого — mr1 слои.*

### 5.1. Формулировки УТП (простым языком)

1. **«Цифры из 1С-учёта, не из нейросети.»** Считает база; модель понимает вопрос и формулирует ответ; сверка кодом.  
   → Против: Цифровой сотрудник, 1eska, любой «чат + OData + GPT».

2. **«На большой базе не скармливаем схему модели — ответ не дорожает с каждой таблицей.»**  
   → Против: MCP-обёртки и Text-to-SQL, которые «умнеют» за счёт контекста.

3. **«Бизнес-ИИ с правом молчать: лучше спросить или отказать, чем угадать; дыры в данных видны вам.»**  
   → Против: «всегда что-то скажет» ассистенты и мягкий стандарт «перепроверьте сами».

Дополнительный акцент для mid+ (mr2): **«Контур клиента; наружу — только то, что вы явно разрешили»** — с честной оговоркой текущего временного DeepSeek (TARGET п.16).

### 5.2. Против кого играем

| Играем | Не играем (сейчас) |
|---|---|
| Дешёвые обёртки — **качеством цифр и периметром** на mid-market | Ценовая война SMB / Infostart .cfe |
| MCP/Codex / data-MCP для бизнеса — **каналом сотрудника + гейтом**, не IDE | Рынок «AI for 1C developers» (Напарник, Unica) |
| Enterprise / Custom SI — **коробкой и п.9** vs skills/проект | Тендеры на год без чемпиона |

## 6. Риски и kill-критерии

*Источник: mr4.*

### 6.1. Сценарии поражения (сжато)

| ID | Сценарий | Суть |
|---|---|---|
| **A** | 1С вшивает ассистента в типовые | Поражение по каналу сбыта; мы страдаем сильнее MCP из‑за TCO |
| **B** | Рынок нормализует «обёртки + перепроверь» | Премия за детерминизм обесценивается культурно |
| **C** | Приёмка не выходит на прод вовремя | Пилот уходит Claude+MCP на 20 вопросах директора |
| **D** | CapEx железа/сопровождения | SMB отказывается до A/B по точности |
| **E** | Уход ключевых людей / остановка SereneDB | Bus-factor ≈ 1–2 = стратегическое поражение |

Почему конкурент выигрывает «по умолчанию» (mr4 §1): скорость, простота фразы, цена входа, смена модели одной строкой, экосистема MCP, найм, быстрые итерации промта. Наши козыри либо невидимы в демо, либо ещё не доведены до порогов ниже.

### 6.2. Kill-критерии K1–K10

| # | Утверждение (MUST) | Как проверить | Порог «ещё в игре» |
|---|---|---|---|
| **K1** | На **чужой** базе верных ответов больше, чем у плагин+MCP+Claude | Слепой A/B, N≥50, эталоны из 1С/SQL, без подгонки | Наш % − конкурент ≥ **+15 п.п.**; галлюцинированных чисел = **0** |
| **K2** | «Не врёт» доказуемо за один визит | 10 вопросов директора + 5 ловушек; запись | ≥9/10 верных или честный clarify; **0** уверенных ложных чисел; **ловушки → clarify/отказ, не догадка** |
| **K3** | Установка до первого ответа сравнима по восприятию | Чистая машина; секундомер; п.14 | **≤ 1 рабочий день до первого верного ответа по живым данным**; ручное действие одно (логин/пароль админа 1С) |
| **K4** | TCO 12 мес. не отпугивает до сравнения качества | Смета vs API+плагин | Наш TCO ≤ **1.5×** MCP-стека *или* доказанная экономия ошибок ≥ разницы |
| **K5** | Свежесть не хуже «живого OData» в восприятии | Изменить документ → вопрос боту; **p50/p95** задержки | p50 **≤ 15 мин** на пилотном размере; иначе явный флаг в ответе |
| **K6** | On-prem: ничего чувствительного наружу | Инвентарь egress + tcpdump/прокси | **0** фактов/сумм за периметр; вызовы поимённо |
| **K7** | Не единичная точка отказа по людям | Второй инженер по runbook | Подъём ответа **≤ 2 дня** без автора |
| **K8** | Продукт переживает ребут как прод | `reboot` стенда без ручного nohup | Бот отвечает **сам**; юниты = фактический порт/база |
| **K9** | Приёмка из базы клиента (п.15) | Генератор из `$metadata`+данных; агенты без контекста | Набор на клиенте; доля верных ≥ K1 **до** подкрутки |
| **K10** | Отказ при наличии данных не убивает ценность (п.21) | Где данные есть: answer vs ложный отказ | Правильных answer ≥ конкурента; лишние отказы поимённо |

**Kill switch (mr4):** если через **~90 дней после момента «готово к продаже»** (не от сегодняшней даты; при текущем хвосте работ этот момент — **после L20**) **не выполнены одновременно K1, K2, K3 и K8** — преимущества п.19/SereneDB/гейтов считаются не монетизируемыми; рациональный исход — упростить стек или сменить категорию.

## 7. Приоритеты до продажи

Связка: **дыры mr3** + **жёсткие K mr4** + живой план (`activeContext`, срез 10.09, **вне mr1–mr4**): полная B → план фиксов → L20; инсталлятор п.14 — в конце.

Две шкалы в таблице: **критичность для kill-switch** ≠ **порядок по календарю**.

| Критичность | Календарь | Что закрыть | Откуда |
|---|---|---|---|
| **P0** | **1-й** | Качество ответа: match/wrong → продакшен; 0 уверенных ложных чисел; путь к K1/K2 | mr3 дыра 1; mr4 K1, K2; L19 база 35/28/3 |
| **P0** | **2-й** (после полной B) | План фиксов → **L20** + **K9** (генератор набора из `$metadata` клиента) в одном ряду | activeContext; mr4 K9; TARGET п.15 |
| **P0** | **до первого внешнего пилота** | systemd / zero-touch: бот жив после ребута → **K8** | mr3 дыра 2; mr4 K8 |
| **P0** | **последний** (TARGET п.14 «в конце») | Инсталлятор + один ручной шаг → **K3** | mr3 дыра 2; mr4 K3 |
| **P1** | пакет **перед mid+**, не блокер тёплых МСП-пилотов | ИБ-питч: roadmap **on-prem LLM**, egress → K6; «почему SereneDB» + runbook → K7 | mr3 дыра 3; mr4 K6, K7 |
| **P2** | после пилотной экономики | TCO-пакет и свежесть с флагом → K4, K5; разбор ложных отказов → K10 | mr4; TARGET п.21 |

**Порядок «не сломать продажу раньше времени»:**

1. **Сейчас (`activeContext`):** полная B → план фиксов → качество ответа / стабильный контур.  
2. **Затем:** L20 + заготовка K9 (генератор набора с клиентской базы).  
3. **До любого внешнего пилота с ожиданием uptime:** K8 (ребут).  
4. **Перед масштабом канала / реселлом:** инсталлятор п.14 (K3) — последний по календарю.  
5. **Перед mid+ с жёстким ИБ:** on-prem LLM (K6) и честный периметр / «почему SereneDB».  
6. **Не открывать** outbound-квоту, коммерческий чек 50+ и enterprise-тендеры, пока (1)–(3) не дали кейсов.

**Итог одной фразой:** пуст пересечённый TARGET-сегмент (пустой в третьем слое); заменители густые — рынок покупает быстрые обёртки и заказной SI. Выигрыш возможен только если теологию п.19 превратить в **числа на чужой базе** (K1/K2), **за день до первого верного ответа** (K3) и **живой после ребута** (K8) — раньше, чем пилот уйдёт к Claude+MCP.
