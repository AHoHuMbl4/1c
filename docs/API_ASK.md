# Контракт `/ask` — для фронта

Всё ниже **вычитано из `ubuntu/serenedb/serene_ask.py`**, а не написано по памяти. Если
код разойдётся с этим файлом — прав код, и файл надо поправить в том же заходе.

Заведён 29.07, когда владелец взял на себя фронт (веб на Flutter, с прицелом на
приложение).

---

## 0. Два ограничения, которые лучше знать ДО начала

### 🔴 0.1 Сервис слушает только loopback и не отдаёт CORS-заголовков

`serene_ask` поднимается на `127.0.0.1:8091` и не имеет ни `do_OPTIONS`, ни
`Access-Control-Allow-*`. Значит **Flutter Web не может обратиться к нему напрямую**:
браузер пошлёт предварительный `OPTIONS` (из-за заголовка `Authorization`) и получит 404.

### 🔴 0.2 Токен `/ask` нельзя класть в браузер

Токен даёт полный доступ к ответам по данным 1С. В веб-приложении любой ключ виден в
исходниках вкладки — это раздача витрины кому угодно. То же правило, по которому у нас
секреты лежат только в `/etc/*.env` с правами 600.

**Отсюда вывод для фронта:** между Flutter и `serene_ask` нужен **свой тонкий бэкенд**
(прокси): он держит токен, ставит CORS-заголовки, и он же потом обслужит мобильное
приложение. Прямое обращение из браузера — тупик по обеим причинам сразу.

Это не «доделка на потом»: без прокси веб-версия не заработает вовсе, а с токеном в
браузере — заработает и одновременно откроет данные наружу.

## 1. Адреса

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | жив ли сервис. `200 {"status":"serene-ask-ok","corpus_rows":N}` или `503 {"status":"degraded","error":"…"}` |
| `POST` | `/ask` | задать вопрос |

Протокол `HTTP/1.1`, тело — JSON в UTF-8. Любой другой путь — `404`.

## 2. Запрос

```
POST /ask
Authorization: Bearer <ASK_TOKEN>
Content-Type: application/json

{ "question": "Сколько мы продали за декабрь?", "focus": null }
```

| Поле | Обязательно | Смысл |
|---|---|---|
| `question` | да | вопрос человека. Пустой → `400 {"error":"empty question"}` |
| `focus` | нет | имя сущности, **выбранной человеком после уточнения** (см. §4) |

Без верного заголовка — `401 {"error":"unauthorized"}`. Кривой JSON — `400 {"error":"bad json"}`.

## 3. Ответ: разбирать по полю `kind`

| `kind` | Код | Что показывать |
|---|---|---|
| `answer` | 200 | готовый ответ в `text` |
| `figures` | 200 | ответ с числами в `text` |
| `clarify` | 200 | **уточняющий вопрос**: `text` + `options` (см. §4) |
| `no_data` | 200 | данных нет — честный отказ, `text` объясняет |
| `unavailable` | **503** | сбой: `text` — человеческое сообщение, `retry: true` |

Общие поля: `text` (строка для человека), `sources` (список названий сущностей, откуда
взят ответ), `partial` (не `null` — часть данных не дошла, показать оговорку), `diag`
(служебное; **пользователю не показывать**).

🔴 **`partial` обещан видимым клиенту — и до 02.08 через бота он не доходил вовсе**: мост
`ubuntu/openclaw/mcp_ask.py` брал из ответа только `kind`, `text`, `options` и `measure`,
поэтому оговорка «учтено не всё» терялась на переходе к боту. Молчаливая потеря — дефект
по п. 13 контракта. Сейчас мост дописывает боту блок `PARTIAL` с числами (что и насколько
отсечено) и заданием сказать об этом одной фразой. Своего фронта это не касается: он
читает `partial` из ответа `/ask` напрямую, как и раньше.

## 4. Уточнение — главный сценарий фронта

Когда вопрос допускает несколько толкований, система **не гадает** (п. 12 контракта), а
спрашивает. Приходит `kind: "clarify"` и массив `options`:

```json
{ "kind": "clarify",
  "text": "Уточните, о чём речь…",
  "options": [
    { "src": "document_реализациятоваровуслуг", "label": "Реализация товаров и услуг",
      "distinct_by": "продажа, отгрузка", "found": 311 },
    { "src": "document_поступлениетоваровуслуг", "label": "Поступление товаров и услуг",
      "distinct_by": "закупка",             "found": 180 }
  ] }
```

| Поле | Для чего |
|---|---|
| `label` | **надпись на кнопке** — человеческое название |
| `src` | вернуть в поле `focus` следующего запроса |
| `distinct_by` | чем этот вариант отличается от других — подпись под кнопкой |
| `found` | сколько записей нашлось — помогает выбрать |

**Как обрабатывать:** показать `text`, под ним кнопки по `label`, **плюс поле «свой
вариант»** (решение владельца 28.07). Нажали кнопку → повторить тот же `question`, но с
`focus: <src>` выбранного варианта. Ответ придёт уже без уточнения.

Бэкенд к этому готов; кнопок нет только в боте.

## 5. Свежесть данных

В `diag.data_age_sec` — сколько секунд назад закончился последний успешный такт. Если
данные сильно отстали, сервис **сам** дописывает предупреждение в `text` и ставит
`stale: true`. Фронту достаточно показать `text` как есть; отдельно `stale` можно
использовать для значка.

## 6. Чего в ответе НЕТ и не будет

- SQL, имён таблиц в `text`, путей, стека ошибок — это режется на стороне сервиса;
- графиков: по решению владельца график строится **после** ответа, а не вместо него;
- `diag` — для отладки, показывать его человеку нельзя.

## 7. Что можно потрогать прямо сейчас

```bash
# токен лежит в /etc/1c-serene-ask.env, в командную строку его не пишем
curl -s http://127.0.0.1:8091/health

TOK=$(grep -oE '^ASK_TOKEN=.*' /etc/1c-serene-ask.env | cut -d= -f2-)
H=$(mktemp); chmod 600 "$H"; printf 'header = "Authorization: Bearer %s"\n' "$TOK" > "$H"
curl -s -K "$H" -H 'Content-Type: application/json' \
     -d '{"question":"Сколько всего мы продали?"}' http://127.0.0.1:8091/ask
rm -f "$H"
```

## 8. Граница между сессиями

Фронт живёт **вне** `ubuntu/serenedb/`. Этот каталог раскладывается в рабочий на каждом
такте (`deploy.sh`), поэтому правки там из параллельной сессии попадут в идущую сборку.
Если фронту понадобится изменение контракта — менять `serene_ask.py` должен тот, кто
ведёт сборку, и с замером по `docs/REGRESSION_BASE1.md`.

## Вход: `focus` и `measure` — ответы на уточняющие вопросы

Уточнение задаётся **в два шага**, и на каждый есть свой вход. Оба необязательны; без них
сервис спрашивает, а не гадает (п. 12, указание владельца 30.07: «лучше 1, 2, 3 раза
уточнить, если непонятно, чем дать не то»).

| Поле запроса | Что означает | Откуда берётся |
|---|---|---|
| `focus` | человек выбрал СУЩНОСТЬ | `options[].src` из ответа `kind=clarify` |
| `measure` | человек выбрал ВЕЛИЧИНУ | `options[].measure` из ответа `kind=clarify` |
| `context` | предыдущий разговор | ведёт OpenClaw; используется **только арбитром**, в отбор данных не попадает |

Ответ `kind=clarify` про величину отличается от уточнения про сущность тем, что у его
`options` заполнено поле `measure`, а `src` у всех одинаков.

**Ответ называет величину.** У `kind=answer` появилось поле `measure`, а в текст дописано
«Считано по величине «ИМЯ».», если модель не назвала её сама. Дописывает КОД: имя приходит
из данных, забыть его нельзя.

[замер 30.07] цепочка на живой базе, эталон из живой 1С — **73 181 157,68**:

| Шаг | Запрос | Ответ |
|---|---|---|
| 1 | `{"question": "На какую сумму мы закупили товаров и услуг?"}` | `clarify`, варианты — сущности |
| 2 | `+ "focus": "document_приобретениетоваровуслуг"` | `clarify`, варианты — четыре величины со словом «сумма» (три вызова из трёх — один и тот же состав) |
| 3 | `+ "measure": "СуммаДокумента"` | `answer`, **73 181 157,68**, три вызова из трёх |

До этой правки шаг 2 отвечал молча и давал **71 045 277,59** — сущность верная, величина
нет.
