# Целевая схема: поиск делает SereneDB, модель ничего не грузит

Зафиксировано владельцем 2026-07-25. Это **целевая** архитектура; отличия от текущей — в §5.

> **Дополнение владельца 2026-07-26 (решение): сырые данные живут в PostgreSQL на Windows.**
> SereneDB на Ubuntu держит только поисковый корпус и индекс, сырые таблицы читает через
> `ATTACH (TYPE postgres, READ_ONLY)` + `CREATE VIEW` (индекс строится на VIEW — на
> attach-таблицу он транслируется в btree, см. `SERENEDB.md`). Загрузчик остаётся на Ubuntu
> и пишет из OData в PG-на-Windows по сети. Копия текста, который индексируется, физически
> есть в корпусе/индексе на Ubuntu — это свойство полнотекстового индекса, не выбор схемы.

## 0.0 🔴 Инвариант масштаба: контекст модели НЕ РАСТЁТ с размером базы

Замерено 2026-07-26 на нашей базе — и это причина, по которой инвариант записан:

| Путь | Что уходит в модель на один вопрос | От чего зависит | На базе x100 |
|---|---|---|---|
| `ask_1c` (`serene_ask.py`) | вопрос + до 25 найденных строк | **ни от чего** | столько же |
| `report_1c` (`serene_report.py`) | **464 292 символа ≈ 155 000 токенов**: вся схема витрины (233 таблицы, 3 462 колонки) + по 5 ЖИВЫХ значений из каждой из 2 294 текстовых колонок | числа таблиц и колонок | **~15 млн токенов** — не влезет ни в одну модель |

`report_1c` — путь предыдущего поколения (NL→SQL: модель получает схему и пишет запрос).
Он не чинится настройкой: даже без живых значений схема растёт вместе с базой. Плюс на
сборку контекста уходит ~2 500 запросов к БД на каждый вопрос (на базе x100 — 250 000).

**Правило:** всё, что уходит в модель, обязано быть ограничено сверху и не зависеть от
числа таблиц, строк и колонок. Живые значения данных клиента наружу не уходят вообще.
Проверяет агент `context-and-scale` (`.claude/agents/context-and-scale.md`).

Открытое решение владельца: убрать `report_1c` из контура, перенеся график и табличный
вывод на `ask_1c` (величины для них уже посчитаны в базе функцией `aggregate()`).

Секреты — в `/etc/1c-*.env` (chmod 600), в git не попадают.

**Индекс** (замер 2026-07-26): текстовый `USING inverted(doc search_dict) INCLUDE (src_table,
row_key, amount, doc_date)` — 5 с, <0.5 ГБ на 96 931 строке. Векторная часть (`ivf`) в индекс
**не включена**: её сборка на 96 931×1536 требует >34 ГБ и убивается OOM хоста (три замера;
`sdb_ivf_sample_factor=0.05` и `segment_memory_max=64МБ` траекторию не меняют — вопрос к движку
открыт). Векторный поиск работает полным сканом `array_cosine_similarity` по таблице — он
используется только как запасной путь, когда слова вопроса не нашлись вовсе.

Словарь: `template='text', case='lower', stemming=false, accent=false, frequency, position,
norm` — морфологии нет, регистр и диакритика снимаются для любого алфавита; локаль — параметр
`DICT_LOCALE`. Словоформы и опечатки ловит `ts_levenshtein` (расстояние от длины слова).

## 1. Две машины, три роли

```
        WINDOWS                              UBUNTU                          ТЕЛЕФОН
┌────────────────────┐            ┌──────────────────────────────┐        ┌──────────┐
│  1С + её база      │            │  SereneDB                    │        │          │
│  (источник истины) │  только    │   • хранит данные            │        │ Telegram │
│                    │  чтение    │   • ИЩЕТ (BM25 + вектор)     │ ◄────► │          │
│  OData ────────────┼───────────►│   • считает агрегаты         │        └──────────┘
│                    │            │                              │             ▲
└────────────────────┘            │  OpenClaw                    │             │
   данные не уходят               │   • говорит с человеком      │─────────────┘
   никуда, кроме                  │   • формулирует ответ        │
   Ubuntu-сервера                 └──────────────────────────────┘
```

| Где | Что делает | Чего НЕ делает |
|---|---|---|
| **Windows** | держит 1С и её базу; отдаёт данные по OData только на чтение | ничего не считает, ничего не ищет |
| **SereneDB** (Ubuntu) | хранит данные, **ищет по ним**, считает суммы и группировки | не разговаривает с человеком |
| **OpenClaw** (Ubuntu) | принимает вопрос из Telegram, формулирует ответ живым языком | **не получает ни схему, ни сырые данные** |

## 2. Главный принцип

> **Ищет база, а не модель.**
> Модель получает вопрос и готовый результат. Схему таблиц, список колонок и выгрузки данных
> в модель не отдаём никогда.

Почему это правильно, а не просто экономно:
- **Стоимость.** Сейчас в модель уходит 140 000 символов схемы на *каждый* вопрос. При 19 таблицах.
  Одна таблица документа 1С — 35 000 символов, потому что в ней сотни реквизитов.
- **Качество.** Именно из-за размера и невнятности модель на вопрос «выручка по месяцам» выбрала
  не ту таблицу и вернула пустой ответ. Поиск по индексу такой ошибки не делает — он ищет по
  реальному содержимому.
- **Масштаб.** Схема растёт с базой, а индекс — нет: поиск возвращает единицы строк независимо от
  того, 19 таблиц в базе или 5 000.
- **Приватность.** Чем меньше уходит в облачную модель, тем меньше поверхность утечки.

## 3. Как проходит вопрос

```
человек в Telegram
      │
      ▼
  OpenClaw ──── передаёт ТОЛЬКО текст вопроса ───►  SereneDB
                                                       │
                                    ┌──────────────────┴──────────────────┐
                                    │ 1. ПОИСК по индексу                 │
                                    │    • BM25 по тексту                 │
                                    │    • вектор по смыслу               │
                                    │    • ЧИСЛА: диапазоны, «свыше N»    │
                                    │    • даты: периоды                  │
                                    │    → какие строки/таблицы подходят  │
                                    │ 2. СЧЁТ прямо в базе                │
                                    │    • суммы, группировки, топ-N      │
                                    │    • из колонок индекса (INCLUDE)   │
                                    └──────────────────┬──────────────────┘
                                                       │  готовый результат
                                                       ▼   (несколько строк)
  OpenClaw ◄─────────────────────────────────────── таблица чисел
      │
      │  формулирует по-человечески + график
      ▼
  ответ в Telegram  ──►  гейт сверяет каждое число с результатом
```

Модель видит: **вопрос** и **несколько строк результата**. Больше ничего.

## 4. Как данные попадают в SereneDB

```
Раз при подключении базы:
   спрашиваем у 1С: какие сущности есть, какой у каждой ключ, какие колонки
   → грузим всё непустое и доступное
   → строим индекс: текст (BM25) + вектор + нужные колонки для счёта (INCLUDE)

Дальше раз в 10 минут:
   спрашиваем «что изменилось» (лёгкий запрос: ключ + версия)
   → тянем только изменившееся
   → обновляем данные и пересобираем индекс (0.4 с на 50 тыс. строк — замерено)
```

Ручной настройки нет: адрес OData, логин и пароль читателя — всё.

## 5. Чем это отличается от того, что работает сейчас

| | Сейчас | Целевая схема |
|---|---|---|
| Кто ищет | **модель** (ей дают всю схему, она пишет SQL) | **SereneDB** (индекс BM25 + вектор) |
| Что уходит в модель | вся схема, 140 000 символов на вопрос | вопрос + несколько строк результата |
| Что грузим из 1С | 22 сущности, отобранные руками | всё непустое и доступное |
| Свежесть | ночь, полная перезагрузка (3 мин 31 с) | раз в 10 минут, только изменения |
| Промах по таблице | случается («выручка» → пустой ответ) | ищем по содержимому, а не по названиям |

## 6. Что уже проверено на стенде, а что нет

**Проверено замерами:**
- гибридный индекс BM25 + вектор в одном индексе — работает, в т.ч. по кириллице;
- поиск по индексу совпал с эталоном `LIKE` до строки (37 = 37), но **в 5 раз быстрее**;
- **агрегация прямо из индекса** (`SUM` по колонке `INCLUDE`) — работает;
- **числовой поиск в том же индексе** — диапазоны, `BETWEEN`, топ-N по числу, агрегация по диапазону
  и связка «текст И число» в одном запросе; сверено с эталоном по таблице;
- индекс над данными в Postgres — работает через VIEW; 50 тыс. строк — 423 мс;
- профиль любой таблицы (`SUMMARIZE`) — 17.8 мс, показывает типы, кардинальность, диапазоны;
- аналитика end-to-end на реальных данных: «продажи по месяцам» и «топ контрагентов» совпали
  с эталонным SQL до рубля.

**Реализовано и проверено 2026-07-26** (`BENCH_BRAINE_VS_SERENE.md`):
- связка **«вопрос → поиск по индексу → результат»** работает: `serene_ask.py`, сервис
  `1c-serene-ask`. Модель схему не видит — только вопрос (на шаге намерения) и найденные
  строки (на шаге формулировки);
- агрегация собирается **кодом**: намерение (порог, период, «сумма/список») извлекается
  отдельным вызовом, дальше условие накладывается предикатом по `INCLUDE`-колонкам, а
  `count`/`sum` считаются в базе по всему подходящему множеству;
- выбор сущности — без имён в коде: сила текстового совпадения × близость вопроса к
  **названию сущности из `$metadata`**;
- braine выведен из контура, освободилось 972 МБ.

**Не проверено / предстоит:**
- поведение на базе с тысячами сущностей;
- постраничный вывод длинных списков (сейчас топ-N строк, счёт — по всему множеству);
- локальный эмбеддер: сейчас 0.8 с каждого ответа уходит в облако за вектором вопроса.

## 7. Что это меняет в коде

| Компонент | Судьба |
|---|---|
| `get_schema()` — сборка всей схемы в промт | **уходит** |
| `gen_sql()` — модель пишет SQL по схеме | **заменяется**: поиск в базе + сборка запроса кодом |
| `resolver_index` (значение → таблица/колонка) | остаётся, становится одним из сигналов поиска |
| валидатор SQL, ro-роль, гейт чисел | остаются без изменений |
| загрузчик | переписывается под «всё + ключи из метаданных» (`UNIVERSAL_INGEST.md`) |
