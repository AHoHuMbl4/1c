# ДЕК1 — замер идеи «разбор вопроса отдельным слоем»

Дата подготовки: 2026-08-26.  
Источник провалов: живой прогон `/tmp/scorer-k2.log` (okna, `:18092`, средняя **28.47 с**, 21/25 OK).  
Код ответа (`ubuntu/serenedb/serene_ask.py`) — только чтение. Стенд не вызывался.

## Зачем

Идея владельца: слой над ботом разбирает язык на точечные, полностью определённые
подвопросы, ядро считает, слой собирает ответ. Замер проверяет предпосылку:
**умеет ли ядро отвечать на уже точечный вопрос.** Если нет — новый этаж повторит
ошибку.

| F3a − F3b | разность | **1049991.33** | то же для помесячного сравнения |
| F4a | число | **141** | атом «активные покупатели» |

### Как читать итог

1. **Контроли C1/C2 FAIL** → стенд/токен/выкат; разложение не судить.
2. **Атомы F2a/F2b/F3a/F3b OK, а исходные F2/F3 в логе FAIL** → предпосылка идеи
   подтверждена: ломается составной/сравнительный язык, не счёт на фиксированном окне.
3. **F1c и/или F1a−F1b ≠ 1891** → ядро ошибается и на точечном «позиции без продаж»;
   слой разбора **не** лечит это.
4. **F4a ≠ 141 или clarify** → ядро не тянет даже явное «клиенты с продажей за 12 мес.»;
   слой лишь повторит отказ/ошибку.
5. Любой атом с непустым `partial` — см. §4 п.13: без проброса пометки сборка запрещена.

## 4. Ограничения проекта

### п. 19 TARGET — модель не считает и не ищет

| Делает разбирающий слой | Обязана делать база / ядро `/ask` |
|---|---|
| Смысл: относительные слова → абсолютные даты; «лучше/хуже» → два окна; «реально» → явное определение окна | Отбор строк индексом, суммы, count distinct, разности множеств (каталог − продававшиеся) |
| Сборка **фразы** из уже посчитанных чисел («эта неделя хуже на …») | Любая арифметика над данными: в т.ч. `A−B` для доказательства — **детерминированным кодом** после ответов ядра, не «в уме» у LLM |
| Не ищет сущности и не подбирает строки корпуса | Поиск и агрегат — только SereneDB через ядро |

Если слой сам вычитает миллионы в промте — это нарушение п. 19. Допустимо: skill/плагин
зовёт `/ask` (или `ask_1c`) на атомы, а разность считает маленький детерминированный
шаг (как scorer), либо одним атомом, который ядро уже умеет.

### п. 13 — молчаливая потеря данных

У ядра пометка частичности уходит наружу полем `partial` ответа (`serene_ask.py`,
исходы `answer`/`figures`/`clarify`/`no_data`). При сборке из N подвопросов:

- если **хотя бы один** атом вернул непустой `partial`, `unavailable`, обрезание
  кандидатов или `kind` ∈ {clarify, no_data, unavailable} — итоговый ответ человеку
  **обязан** нести ту же пометку (объединение причин), а не «гладкий» текст из остальных
  чисел;
- молча отбросить атом с `partial` и ответить по оставшимся = дефект п. 13 / п. 18.

Скрипт пишет `partial` каждого атома в jsonl — оркестратор сверяет проброс.

### Латентность (~28 с × N)

Три последовательных атома ≈ **1.5 мин** при текущей средней. Варианты без отрицания
факта:

1. **Параллель независимых атомов** (F2a∥F2b, F3a∥F3b, F1a∥F1b) — стена ≈ max, не сумма.
2. **Декомпозировать только составные** (сравнение, «не продаётся»=разность, «реально»);
   простые «сколько продали за …» — один вызов, как сейчас.
3. Не раздувать согласие `parse_intent` на каждом атоме, если даты/мера уже абсолютны
   (см. двойной разбор ниже) — иначе каждый подвопрос снова платит за LLM-разбор.

Идея «всегда 3 вызова» для любого вопроса — неприемлема по UX; селективная декомпозиция
обязательна.

### Двойной разбор — что забрать слою целиком

Сейчас в ядре уже есть разбор намерения и календарная ось со словарём относительных форм:

| Место | Файл:строка | Что делает |
|---|---|---|
| `parse_intent` | `ubuntu/serenedb/serene_ask.py:1289` | текст → структура отбора (LLM, без данных) |
| вызов в основном пути | `serene_ask.py:11999` | `intent = parse_intent(question, today)` |
| `period_readings` | `serene_ask.py:1592` | MTD/WTD vs полный месяц/неделя по форме границ |
| `period_relative_forms` / `period_form_from_question` | `serene_ask.py:1727`, `:1759` | словарь относительных фраз из `search_meta` |
| `apply_period_leader` | `serene_ask.py:1772` | лидер окна (в т.ч. prev_week) |
| `calendar_axis_open` / `expand_readings_calendar_axis` | `serene_ask.py:1880`, `:1936` | ось calendar_days vs working_days |
| подключение оси в пути ответа | `serene_ask.py:12004–12007` | `apply_period_leader` → `expand_readings_calendar_axis` |

**Слой обязан забрать себе целиком (чтобы смысл не жил в двух местах):**

1. Разрешение **относительных** периодов («вчера», «эта неделя», «в этом месяце») в
   **абсолютные** `from`/`to` (и явную меру/срез) — то, что сейчас делают
   `period_relative_forms` + лидер окна + (частично) `parse_intent.period`.
2. Разбор **сравнений и составных** («лучше/хуже», «больше чем», «совсем не …») в список
   атомов — этого в ядре как отдельного контракта нет; сейчас ядро пытается ответить на
   весь вопрос целиком и на F2–F4 из лога срывается.
3. Толкование **размытых квалификаторов** («реально покупают») → либо явное определение
   окна, либо clarify **до** похода в ядро.

**В ядре после появления слоя должно остаться:** счёт и поиск по уже абсолютному
запросу (даты цифрами, мера названа). Иначе «прошлая неделя» снова разберётся и в skill,
и в `period_form_from_question` — два смысла, два окна, п. 3/12.

Практическое следствие замера: атомы в скрипте уже с ISO-датами; если они OK, а
оригиналы FAIL — аргумент вынести относительный календарь наверх. Если атомы тоже FAIL —
чинить ядро, слой не строить.

## 5. Штатный механизм OpenClaw (установленная сборка)

Доки: `/usr/lib/node_modules/openclaw/docs` (не `/opt/openclaw-engine`).

**Подходит как основной контур идеи — Skill (SKILL.md):**

- раздел [Skills](file:///usr/lib/node_modules/openclaw/docs/tools/skills.md)
  (`/tools/skills`): skill учит агента *когда и как* звать инструменты; грузится из
  workspace `skills/`, без своего HTTP-велосипеда;
- создание: [Creating skills](file:///usr/lib/node_modules/openclaw/docs/tools/creating-skills.md)
  (`/tools/creating-skills`).

Смысл укладки: skill описывает «сложный/сравнительный вопрос → разложить на абсолютные
атомы → для каждого вызвать уже существующий MCP/`ask_1c` → собрать фразу; числа не
считать в модели». Это ровно «слой поверх бота» без второго пайплайна данных.

**Дополнительно, если нужен типизированный инструмент «вернуть план атомов»:**

- [Tool plugins](file:///usr/lib/node_modules/openclaw/docs/plugins/tool-plugins.md)
  (`/plugins/tool-plugins`) — `defineToolPlugin` регистрирует tool у агента;
- общий каркас: [Building plugins](file:///usr/lib/node_modules/openclaw/docs/plugins/building-plugins.md).

Плагин не должен сам ходить в SereneDB и считать (п. 20 TARGET). Максимум — схема
подвопросов; счёт — через текущий мост к `/ask`.

**Не выбирать своим велосипедом:** отдельный Python-сервис «декомпозитор» вне OpenClaw;
хуки Gateway полезны для перехвата, но не заменяют skill как место смысла
([Plugin hooks](file:///usr/lib/node_modules/openclaw/docs/plugins/hooks.md)).
