## §0. Решения владельца (зафиксированы 22.08.2026, пересмотру этим планом не подлежат)

1. 🔴 **Полный отказ от PostgreSQL как компонента — везде, не только на Windows.**
   Продукт целиком на собственной БД SereneDB. Windows-слой «PostgreSQL + attach»
   выводится (отменяет решение 26.07 — `owner-memory/project-architecture-pg-windows-attach.md`
   обновить); на Ubuntu — подтвердить и вычистить любые остатки.
   **Факт [замер 22.08]:** наш инстанс УЖЕ является собственным сервером SereneDB, а
   не PostgreSQL: `current_setting('data_directory')` пуст и `pg_extension` пуст (у
   настоящего PG оба непременно заполнены); хранилище — `store.db`, запуск —
   `--server_directory`. Строка «PostgreSQL 18.3 (SereneDB…)» — совместимость
   протокола, не Postgres. **PG-протокол остаётся как интерфейс клиентов**
   (`psql`, Grafana, OWUI) — это протокол SereneDB, отказ его не касается.
2. 🔴 **Максимально нативные средства SereneDB** вместо самодельных слоёв
   (синонимы, слияние рангов, свежесть индекса, бэкапы — см. §2 и Ф6).
3. 🔴 **Переход эмбеддера на Qwen3-Embedding-4B.**
4. (Ранее, в связке) IVF и полный векторный поиск — включаются после доказательства,
   что новая версия движка чинит сборку индекса (ворота Ф1).

Шлюз OData на Windows (:6011, IIS) **остаётся** — отказ касается только БД-слоя.
1С и её собственную СУБД не трогаем (читаем OData, п. 2 TARGET).

## §2. Целевое состояние (одним взглядом)

- Движок: актуальный стабильный релиз (**≥ v26.07.5**; точный номер пиновать в Ф0 с
  GitHub Releases — страница доков грузит список скриптом).
- БД-слой один — SereneDB; на Windows БД нет вообще.
- Эмбеддер: Qwen3-Embedding-4B (размерность 2560; вариант MRL-обрезки — только по замеру, Ф4).
- Метрика векторов: **нормированные векторы + `metric='ip'`** (открывает `sq8`/`rabitq`;
  для нормированных ip ≡ косинусу) — при условии замера нормированности в Ф0.
- IVF-индексы: resolver_index, метки сущностей, корпус okna, корпус klient-1.
- Путь ответа: гибрид (BM25 + вектор + фильтры) штатным Hybrid Search / RRF в SQL.
- Синонимы: словарь `solr_synonyms`, наполняемый нашим генератором wiki-alias
  (+ кэш «моста на лету»); самодельные alias-джойны сняты.
- Свежесть: штатные `REFRESH_*`/интроспекция в `/health`.
- Бэкапы: `EXPORT DATABASE` / `IMPORT DATABASE` + копия store.db на апгрейдах.

### Ф4 — Эмбеддер Qwen3-Embedding-4B [решение владельца 22.08]

1. Развёртывание 4B на эмбеддер-хосте (тот же сервис и эндпоинт, что сейчас; вес,
   прогрев, `/health` отвечает именем модели). Единое место конфигурации —
   `/etc/1c-embed.env` (модель, адрес, размерность, ключ); секреты движка —
   `qwen_<база>` (урок §3.17). Никаких побазовых расхождений.
2. **Решение о метрике здесь, до пересчёта:** выход нормирован (замер Ф0) → пишем
   нормированные, целимся в `ip`; нет → нормировка при записи. Операторы в коде
   (`<=>`/`<#>`) меняются одним заходом с индексами Ф5.
3. Порядок пересчёта — от дешёвого к дорогому (защита «отметка модели на таблице»
   уже в коде, смешение невозможно):
   а) метки сущностей + alias + resolver_index (тысячи строк, минуты) — смысловая
      поверхность возвращается сразу;
   б) корпус okna (~1,5 млн) — фоновая докатка, ставка в отчёт;
   в) **klient-1 — только новой моделью** (это и есть отложенный досчёт; ожидаемая
      ставка 4B кратно выше — замерить, пересчитать срок из 19–35 суток).
4. Такт: дельта-эмбеддинг новой моделью с первого дня; бюджет такта ≤ 20 мин — замер.
5. MRL-обрезка размерности (2560 → 1536/1024) — **только как замер** recall на golden;
   в бой лишь при неотличимом качестве и с записью в `PLAN_VECTOR_CHECKS.md`.
6. Приёмка модели: скорер 25 **построчно ×3** (разброс прибора ±1); реплей резолвера
   RU↔RO + диакритика; двуязычные вопросы. Критерий отката: устойчивая просадка
   смысловых строк (не суммы).
7. Старые векторы держать до прохождения приёмки; удаление — Ф7.

**Ворота 4:** обе базы на 4B во всех смысловых таблицах; приёмка пройдена; klient-1
докатывается новой моделью с замеренной ставкой.

### Ф6 — Нативизация: гибрид в пути ответа, синонимы, свежесть

1. **Гибридная поверхность строк** 🟡 **Ф6.1 код+замер 23.08**: ANN по корпусу как четвёртая поверхность
   кандидатов; слияние — штатным RRF **в SQL** (доки: Inverted › Ranking › Combining
   ranked queries; Hybrid Search › Score fusion); python-RRF снимается после замера
   эквивалентности. **Статус (23.08, вечер):** `ASK_SQL_RRF` в коде, стейджинг
   okna `:8092` — паритет 12/24=12/24, DIFFS 0. Бой `:8091` **на паузе, флаг 0**:
   приёмка отложена до конца пересчёта klient-1. Причина — не код: замер с флагом
   дал 11/24 при 68,24 с против базлайна 12/24 при 32,66 с, но 27B в это время
   делил GPU с пересчётом (util 100%), а контрольный прогон снять не удалось —
   Qwen3.8-27B `:8000` выгружен, ask отдавал 503 `unavailable`. Условие повтора:
   живой 27B, свободный GPU, базлайн и замер подряд **без рестарта между ними**
   (гонка рестарта уже дала ложный красный 5/24 — `HOW_NOT_TO §3.35`).
2. **Резолвер значений** («Питер → Санкт-Петербург», румынская диакритика) — на IVF.
3. **Синонимы natively**: словарь `solr_synonyms`, наполняемый генератором wiki-alias
   (двунаправленные классы: «остатки, склад, stoc, depozit …»; односторонние — по
   смыслу); кэш «моста на лету» компилируется туда же с пометкой источника.
   Применение — сначала query-side (`ts_lexize`, как STEM_DICT), чтобы не пересобирать
   основной индекс; самодельные alias-джойны снимаются после замера. Обновление
   словаря = пересоздание словаря (SYNONYMS — inline строка) — процедура в такт.
4. **Свежесть**: `/health` переводится на штатную интроспекцию/`REFRESH_*`; самодельные
   `merge_pending`-эвристики остаются вторым рубежом до замера, потом снимаются.
5. Включение — **env-флагом, поэтапно**: dev :8097 → okna :8092 → okna бой → klient-1.
   На каждом шаге: скорер построчный diff, golden двуязычный, замки, проба протоколом.
   Канон-ветки остаются детекторами сомнения (страховка скорера) — их судьба решается
   универсальным путём (v6), не этим планом.
6. 🔴 Красная линия всей фазы: в диффах ни одного имени сущности/счёта/языкового
   списка в коде — снайпер хардкода по новым строкам = брак. Все слова живут в данных
   (словарь) или приходят из метаданных.

**Ворота 6:** гибрид в бою на обеих базах; скорер не ниже базлайна, смысловые строки
выросли; латентность ответа в норме; сняты python-RRF и alias-джойны (или записано,
почему остаются).

## §4. Сквозные правила (весь план)

- **Протокол факта:** каждый замер = rid + code_md5 (кода, который отвечал!) + порт +
  текст вопроса + q_len; строка без этого в отчёт не принимается.
- **Гранты:** каждая новая таблица/словарь/индекс → GRANT в `corpus_init.sql` +
  проверка в precheck (урок search_meta). 🔴 Выкат обновлённого `corpus_init` на УЖЕ
  развёрнутые базы — частью каждой фазы, не «потом» (klient-1 разошёлся с init именно
  так).
- **Отдельные имена** для временного: `<метка>_<база>_<таблица>` (§3.16); секреты
  `qwen_<база>`, `odg_<база>` (§3.17).
- **Деньги:** после ворот 0 ни одна строка не эмбеддится старой моделью.
- **Такт ≤ 20 мин** (п. 17) — замер в каждой фазе, где такт трогается.
- **REGRESSION_BASE1** — после последней правки каждой боевой фазы.
- **Двуязычная приёмка** (рус+рум) везде, где меняется путь ответа.
- **Коммиты** — пат-спеком (в папке несколько сессий), код+доки одним коммитом,
  `Доки:`/`Числа:` в сообщении по гейтам.

### §7-бис. Сцепка с параллельными работами (мост на лету, скиллы-композиторы)

**Мост на лету** (модель достраивает словарь при промахе) — остаётся нужным и после
плана: лучшие эмбеддинги и гибрид закрывают часть смысловых промахов, но
концептуальные скачки («остатки товаров ↔ бухгалтерский счёт учёта товаров») не
решаются похожестью — их решает мировое знание модели над структурным шорт-листом.
Что план меняет в идее:
1) шорт-лист моста становится лучше (гибридная поверхность Ф6.1 поднимает кандидатов,
   которых kNN-меток не видел);
2) 🔴 **точка приземления кэша меняется**: подтверждённая связка пишется не в
   «таблицу + джойны», а в данные словаря (alias-таблица как источник → из неё
   генерится `solr_synonyms`, Ф6.3) — связка становится токен-эквивалентностью для
   всех будущих запросов, включая индексные;
3) частота вызовов моста со временем падает ещё быстрее (словарь+гибрид закрывают
   больше первыми ступенями). Зависимости моста: карта паспортов (v6 Ф4-пункт) —
   без неё шорт-лист не из чего строить; от фаз этого плана мост не зависит и может
   делаться параллельно, с переключением кэша на словарь при готовности Ф6.3.

**Скиллы-композиторы** (составные вопросы: сравнение периодов, доли, план-факт) —
полностью ортогональны плану: слой НАД `/ask`, зависят только от контракта атома
(figures/atom + rid), который уже существует. План даёт им точнее и быстрее атомы
(гибрид, синонимы), но ни одна фаза их не заменяет: «динамика по месяцам» закрывается
формой «серия» в атомарном пути (работа v6, не этого плана), настоящие многоатомные
вопросы — только скиллом. Могут идти параллельно всем фазам.
- **Гейт чисел и путь ответа** — не трогаются этим планом нигде, кроме подмены
  поверхности кандидатов (Ф6.1), которая проходит полную приёмку.
