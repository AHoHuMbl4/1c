# Замер: braine (RAG) против SereneDB (гибридный поиск) на одних данных

Дата: 2026-07-26. Повод — вопрос владельца: нужен ли braine как прослойка, или OpenClaw может
ходить в SereneDB напрямую.

Условия уравнены намеренно: перед прогоном запущен ETL, чтобы у braine были **те же** свежие данные
(17 сущностей, 176 записей). Эталон для каждого вопроса считается отдельным SQL по витрине —
он не зависит ни от одной из сравниваемых систем.

---

## 1. Что обнаружено до начала сравнения

### 1.1 ❗ braine лежал: боевая авария (исправлено)

`POST /ask` отвечал **500** на 4 вопроса из 6. Причина в логе `api.service`:

```
httpx.HTTPStatusError: Client error '400 Bad Request'
  for url 'https://api.deepseek.com/v1/chat/completions'
```

`/opt/smart-bot/.env` содержал `DEEPSEEK_MODEL=deepseek-chat` — модель отключена поставщиком
**2026-07-24 15:59 UTC**. Тот же сбой я чинил ранее в `serene_report.py`, но у braine **свой** клиент
модели и свой конфиг, поэтому он остался сломанным.

Проверено прямым вызовом API до правки:

| Модель | Ответ API |
|---|---|
| `deepseek-chat` (была в конфиге) | **HTTP 400** |
| `deepseek-v4-flash` | **HTTP 200** |

Исправлено: `DEEPSEEK_MODEL=deepseek-v4-flash` (бэкап `.env` сохранён), `api.service` перезапущен,
500 больше не воспроизводится.

> **Вывод для продукта:** имя модели живёт в **двух** независимых местах. Это конфигурационный долг:
> одна замена у поставщика роняет половину системы. Кандидат на единый источник настройки.

### 1.2 Исправление в нашей же документации: как вообще искать в SereneDB

В `SERENEDB.md` рецепт поиска был записан неточно, из-за чего поиск сперва не работал вообще.
**Запрос идёт от имени ИНДЕКСА, а не таблицы:**

```sql
-- НЕ работает: ERROR: TSQUERY expression evaluated outside an `@@` match…
SELECT count(*) FROM bench_corpus WHERE doc @@ ts_phrase('СБЕРБАНК');

-- Работает:
SELECT count(*) FROM bench_idx     WHERE doc @@ ts_phrase('СБЕРБАНК');
```

Ошибка движка при неверной форме вводит в заблуждение — она указывает на колонку, а не на источник
в `FROM`. Проверено: форма с таблицей не работает ни на обычной таблице, ни на VIEW, ни на VIEW над
`read_parquet`; форма с индексом работает везде.

### 1.3 Словарь: `case='lower'` обязателен

Полный рабочий DDL словаря:

```sql
CREATE TEXT SEARCH DICTIONARY d (
  template='text', locale='ru_RU.UTF-8', case='lower',
  stemming=false, accent=false, frequency=true, position=true, norm=true);
```

Без `case='lower'` поиск регистрозависим — замерено на одном и том же корпусе:

| Запрос | без `case='lower'` | с `case='lower'` |
|---|---|---|
| `СБЕРБАНК` | 56 | 62 |
| `Сбербанк` | **4** | 62 |
| `сбербанк` | **0** | 62 |

Для бота это критично: человек пишет как хочет.

`stemming=false` держим осознанно (см. `UNIVERSAL_INGEST.md` — стемминг language-specific).
Цена этого решения замерена: `LIKE '%СБЕРБАНК%'` даёт 70 против 62 у индекса; разница — словоформы
и составные слова (`СБЕРБАНКА`, `ПРОМСБЕРБАНК`). Компенсировать нужно не стеммингом, а ngram/фаззи.

## 2. Что и как измерялось

**Корпус для поиска строится из витрины кодом, без имён-констант:**
- колонки классифицируются **по структуре значений** (GUID / число / дата / текст / машинный токен);
- ссылки резолвятся общей картой `GUID → наименование`, собранной из всех справочных таблиц;
- машинные значения (base64-версии записи, URL) в поиск не идут — распознаются **по форме**;
- число для агрегатов — колонка с наибольшим максимумом; дата — первая временная колонка.

**Стоимость постройки** (2886 строк витрины, 21 таблица):

| Этап | Время |
|---|---|
| Обход витрины + карта ссылок (2882 пары) | 32 с |
| Сборка текстов корпуса | 60 с |
| Эмбеддинги Qwen v4 @1536, батч 10 | **459 с** (7.6 мин) |
| **Постройка гибридного индекса** (текст + вектор + INCLUDE) | **0.79 с** |

Эмбеддинги — 98% времени. Индекс практически бесплатен.

## 3. Результаты

Шесть вопросов, одни и те же данные, эталон — независимый SQL.

| Вопрос | Эталон (правда) | SereneDB | braine |
|---|---|---|---|
| Что покупало ООО Ромашка? | 3 док / 1 236 800 | нашёл **3 из 3** | «нет данных» |
| На какую сумму продали ООО Северный Ветер? | **3 615 700** | **3 615 700 — точно** | **647 300 — неверно** |
| Какие продажи больше 500 000? | 11 док / 9 101 800 | **11 / 9 101 800 — точно** | «нет данных» |
| Какие банки в Казани? | 37 банков | **37 из 37, без ложных** | «нет данных» |
| Продажи за декабрь 2025 | 6 док / 2 456 400 | нашёл **5 из 6** | **2 документа — неверно** |
| Поступления от ООО ТехноСнаб | 2 док / 2 088 800 | нашёл **2 из 2** | **1 док / 556 400 — неверно** |

**Итог по правильности:**

| | SereneDB | braine |
|---|---|---|
| Точный ответ | **4** | 0 |
| Нашёл почти всё (5 из 6) | 1 | 0 |
| Отказ «нет данных» | 0 | 3 |
| **Уверенный НЕВЕРНЫЙ ответ** | **0** | **3** |

### 3.1 ❗ Главная находка: braine отвечает уверенно и неправильно

Три ответа из шести — неверные, **со ссылками на источники**:

- «На какую сумму продали Северный Ветер?» → ответил **647 300**. Правда — **3 615 700**.
  Нашёл 1 документ из 6 и просуммировал только его.
- «Поступления от ТехноСнаб» → «было **одно** поступление на 556 400». Правда — **2 документа
  на 2 088 800**.
- «Продажи за декабрь 2025» → «зафиксированы **две** реализации». Правда — **6 документов**.

Это свойство поиска по нарезанным кускам текста: достали один кусок — модель уверенно отвечает по
нему. Гейт точности здесь не спасает: он ловит «нет контекста», но не «контекст неполный».
Для бизнес-ответа неполная сумма хуже отказа — по ней принимают решения.

SereneDB на тех же вопросах не ошибся ни разу: он либо возвращает все строки, либо часть, но
**не выдаёт часть за целое** — сумма считается по всему найденному множеству прямо в базе.

### 3.2 Скорость

| | SereneDB | braine |
|---|---|---|
| Полнотекст (BM25) | **34–47 мс** | — |
| Вектор по 2886 строкам | **51–67 мс** | — |
| Эмбеддинг вопроса (облако DashScope) | 790–890 мс | — |
| Агрегация прямо из индекса | **55 мс** | — |
| **Ответ целиком** | **≈0.9 с** | **6.0–30.3 с** |

Узкое место SereneDB — не поиск (это десятки миллисекунд), а **поход за эмбеддингом вопроса в
облако**: 0.8 с из 0.9 с. Локальный эмбеддер убирает и задержку, и утечку текста вопроса наружу.

### 3.3 Ресурсы

| Контур | Память |
|---|---|
| **braine** — 5 сервисов | **974 МБ** (open-webui 813, api 81, oikb 48, kb-poll 21, rerank 11) |
| **SereneDB** — 1 сервис | **225 МБ** |

Плюс у braine промежуточный git-репозиторий базы знаний и отдельный ETL.

### 3.4 Свежесть

До прогона braine не знал про данные вообще: его база знаний обновляется цепочкой
`ETL (03:00) → git push → kb-poll → oikb → индекс`. Отставание — **сутки**.
SereneDB читает витрину напрямую.

### 3.5 Чего поиск сам по себе НЕ может (и что с этим делать)

Честно про два вопроса, где recall был неполным:

- **«продажи больше 500 000»** — текстом и вектором это не ищется в принципе: в тексте строки нет
  слов «больше 500000». Но **числовой предикат по индексу дал точный ответ** (11 док / 9 101 800,
  55 мс). Значит нужен шаг «понять намерение» — распознать порог и применить его как условие.
  Это ровно то, что в `TARGET_ARCHITECTURE.md` названо «собирать запрос кодом».
- **«за декабрь 2025» (5 из 6)** — та же причина: период надо накладывать как условие по дате,
  а не искать словом «декабрь».

Вывод: **поиск закрывает «про что», условие по числу/дате закрывает «сколько и когда»**. Обе части
уже работают и обе — в базе. Не хватает связки: разбора намерения вопроса.

## 4. Дефекты, найденные в моей же реализации корпуса

Фиксирую честно — это были ошибки метода, а не движка:

1. **Карта ссылок брала `DataVersion` как «наименование».** Правило «текстовая колонка с высокой
   уникальностью» выбирало служебную версию записи (она уникальна в каждой строке). В результате
   документы содержали `Контрагент: AAAABgAAAAA=` вместо имени — и **не находились по имени
   контрагента вообще**. Исправлено структурным фильтром машинных токенов.
2. **Фильтр машинных значений требовал цифру в base64.** `AAAABgAAAAA=` цифр не содержит и проходил
   насквозь. Признак `заканчивается на '='` достаточен и языконезависим.
3. **Эталонный SQL с `LIKE` регистрозависим** — `'%Казан%'` не находил `Г. КАЗАНЬ`. Эталон обязан
   быть регистронезависимым, иначе меряешь не то.

## 5. Вывод по исходному вопросу владельца

> «Стоит ли оставить braine как прослойку, или можно напрямую OpenClaw → SereneDB?»

**По замерам — braine как слой поиска себя не оправдывает.** На одних и тех же данных он дал
0 точных ответов и 3 уверенно неверных, работает в 7–30 раз медленнее, ест в 4 раза больше памяти
и отстаёт от данных на сутки. SereneDB на тех же вопросах — 4 точных ответа, ни одного неверного,
и считает суммы прямо в базе.

**Но снимать его прямо сейчас нельзя** — не потому что он лучше, а потому что в нём осталось то,
чего в новом контуре ещё нет:

| Что даёт braine сегодня | Состояние в контуре SereneDB |
|---|---|
| разбор намерения вопроса (какая сущность, какой период) | **нет** — это и есть недостающая связка (§3.5) |
| оформление ответа со ссылками на источник | частично: строка витрины сама и есть источник |
| гейт «не отвечать без контекста» | есть свой — сверка чисел с результатом запроса |
| диалог, уточнения, память разговора | это уровень OpenClaw, а не braine |

**Порядок действий, который следует из замеров:**

1. **Сделать разбор намерения** — числовые пороги и периоды как условия запроса. Обе половины уже
   работают по отдельности и замерены; нужна сборка.
2. **Прогнать оба контура на расширенном наборе вопросов** — этот замер на 6 вопросах показателен,
   но мал.
3. **Перевести OpenClaw на прямой вызов SereneDB**, braine оставить включённым для сравнения.
4. **Погасить сервисы braine, не удаляя** — освободится ~974 МБ и сутки задержки.

Отдельно: **имя модели живёт в двух конфигах** (§1.1). Это чинить независимо от судьбы braine.
