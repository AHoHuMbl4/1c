## 2. Находки — по мере теста

### 🔴 Н-1. Имя базы SereneDB было зашито как `'postgres'`
**Найдено до загрузки данных**, при подготовке изоляции.
`corpus_build.sql` (×2) и `coverage_build.sql` фильтровали источники по
`database_name = 'postgres'` — имени нашей базы на ЭТОМ стенде. На установке, где база
названа иначе, отбор дал бы **ноль источников**, и корпус собрался бы пустым **молча**.
Починка: `current_database()`. [замер] в `ut_test` возвращает `ut_test`, в рабочей —
`postgres`.

### 🔴 Н-2. Замок сборки не зависел от базы
`build.sh` брал `flock` по фиксированному пути `/var/lock/1c-serene-build.lock`. Два
конвейера над **разными базами 1С** (у клиента их бывает несколько) блокировали бы друг
друга: второй молча уходил бы, и его данные не обновлялись **никогда**. Починка: имя
замка из `dbname` в DSN — из того же источника, что и сама база, без отдельной настройки.

### Н-3. Публикация OData создаётся с выключенным OData
`webinst -publish -iis` отработал с кодом 0, но записал `standardOdata enable="false"` —
эндпоинт отдавал **404**. Это не наш дефект, а поведение утилиты платформы, но для
инсталлятора (п. 14) существенно: **после публикации надо проверять `enable="true"`**,
иначе установка выглядит успешной, а данных нет. Записано для п. 14.

### 🔴 Н-4. `duckdb_tables()` видит ВСЕ базы движка — утечка между базами
[замер] из `ut_test` он показал 1 605 своих таблиц **и 302 чужих**. Четыре наших запроса
не фильтровали по базе, поэтому источник считался существующим, потому что таблица с
таким именем есть в ДРУГОЙ базе — и `query_table()` падал: «Table
catalog_внешниекомпоненты does not exist». Починено фильтром `database_name =
current_database()` в `corpus_build` (×2), `corpus_precheck`, `corpus_init`.
**На одной базе эффекта нет** — там всё и так в текущей базе, поэтому дефект был скрыт.

### 🔴 Н-5. Наша обрезка значения создавала БИТУЮ КОДИРОВКУ и роняла всю сущность
Самая важная находка теста.

[замер] `catalog_правилаинтеграциис1сдокументооборотом`: исходное значение соединяется с
картой ссылок нормально, а **после нашей же `substr(…,1,20000)`** соединение падает —
`Invalid unicode (byte sequence mismatch) detected in value construction`. То есть дефект
**наш**, а не данных: на первой базе он просто не стрелял, потому что там не оказалось
таких значений.

Хуже последствие: с `ON_ERROR_STOP on` вместе с одной сущностью падал **весь такт** —
1 500 здоровых сущностей не доезжали из-за одной.

**Две починки, обе универсальные:**
1. **Соединение с картой ссылок — только по GUID-образным значениям.** Ссылкой может быть
   ТОЛЬКО GUID, значит сужение не теряет ни одной связи; GUID по определению ASCII, и
   битые байты до хеша не доходят. Побочно снимается лишняя работа: раньше движок хешировал
   ВСЕ ячейки (миллионы) против 39 тыс. записей карты.
2. **Перебор вариантов вместо падения** (указание владельца): не собралось полной сборкой —
   пробуем `p_doc_plain`, намеренно простой вариант (текст из пар «колонка: значение», без
   ссылок, величин и дат). Качество ниже, но сущность остаётся в поиске. Что не собралось
   и им — уходит числом в `search_quality.build_failed`, то есть **видно**, а не проглочено.

### 🔴 Н-6. Замок, рабочие таблицы и СЕКРЕТЫ назывались одинаково во всех базах (29.07)

Три дефекта одного класса — «общее имя на все базы». Ни один не виден, если гонять базы
по очереди; все три вылезли, когда две базы пошли рядом.

| Что | Чем кончилось | Замер |
|---|---|---|
| замок брал имя базы **разбором строки DSN** | в окружении конвейера `dbname=` не задан — libpq подставляет базу по умолчанию, разбор дал `default` против `postgres`. Два такта по ОДНОЙ базе, общие `tmp3_*`, **66 дублей ключа** | корпус цел: остановила защита `corpus_merge` |
| рабочие таблицы досчёта векторов | перенос мог взять таблицу чужой базы (чужой вектор на нашей строке), уборка — снести чужую оплаченную работу | из `postgres` было видно **5** рабочих таблиц `ut_test`; после починки 0 |
| **секреты движка общие на инстанс** | упавшая сборка второй базы трапом снесла `odg`/`qwen`, и такт ПЕРВОЙ базы получил `ai_embed: secret 'qwen' not found` | было 16 строк без вектора → осталось 16; после починки 17 → **0** |

Починка по указанию владельца — **отдельные имена, а не фильтр**: `emb_<база>_<таблица>`,
`odg_<база>`, `qwen_<база>`, имя базы спрашиваем у движка (`current_database()`).
Разбор — `HOW_NOT_TO §3.14`, `§3.16`, `§3.17`.

### 🔴 Н-7. `Edm.Stream`/`Edm.Binary` валят ВЕСЬ ответ OData, а не одно поле (29.07)

При загрузке с нуля одна сущность из 1 588 ответила `HTTP 500` устойчиво — при `$top`
1000, 100, 10 и даже 1, — тогда как `$count` честно отдавал **37**. Причина: поля
хранилища значения (`ИсточникДанных` `Edm.Stream`, `ИсточникДанных_Base64Data`
`Edm.Binary`). Исключил их через `$select` — пришли все 37 строк, код 200.

**Но наличие такого поля отказа НЕ гарантирует:** [замер] `Catalog_ШаблоныПоясненийДляФНС`
имеет ровно те же два типа, 35 строк, отдаётся 200. Типов с такими полями **470 из 2 795**
на УТ и **961 из 4 585** на первой базе — это размер подверженности, а не число поломок.

Отсюда починка — **перебор, а не сужение всем подряд**: как обычно → повтор → без
неотдаваемых полей → честный отказ с числом в переписи. Сузить все 961 значило бы
выбросить колонки там, где всё работает, сменить схему таблиц витрины и переписать ключи
строк корпуса (`ловушка 22`). Подробности — `techContext` ловушка 27.

## 2-бис. Пересборка второй базы С НУЛЯ (29.07)

По указанию владельца: «делаешь бэкап, куда-то складываешь файл, сносишь старую и начисто
делаешь новую». Это и есть приёмка автономности, а не обвязка вокруг неё.

1. **бэкап** — `serenedb_backup.sh` → `/root/backups/serenedb/serenedb-20260729-044937.tar.gz`,
   **2,6 ГБ**; проверено, что внутри `engine_duckdb/store.db`, где лежат все базы;
2. **снос** — `DROP DATABASE ut_test`;
3. **чистая** — `CREATE DATABASE ut_test`, 0 таблиц;
4. **конвейер без единой ручной правки по ходу.**

| Этап | Замер |
|---|---|
| синк с нуля | **1 588 сущностей, 769 842 строки, 80 минут**, ошибок 1 (та самая Н-7) |
| медиана на сущность | 0,13 с; **71% времени — восемь сущностей** |
| самая дорогая | `Document_ПланПродаж`: 169 строк за 156 с — **одна страница, один запрос** |
| разброс скорости | от 1 до 902 строк/с при одинаковом размере страницы |

**Вывод про скорость:** одинаковая страница, одна сеть, один наш код, разброс в 150 раз —
время уходит **внутри 1С на отрисовку OData**, не у нас. Верхняя оценка нашей доли: на
быстрых сущностях мы даём 900 строк/с вместе с записью CSV и слиянием, значит наши
накладные — доли секунды на сущность. И это **разовая цена подключения базы**: дальше
работает дельта по `DataVersion`, обычный такт первой базы — 150-180 с.

Что можно ускорить (не сделано, записано): `$select` только нужных колонок; страничность
по ключу вместо `$skip` (сейчас доходит до `$skip=97000` — платформа обязана пройти 97
тысяч записей, чтобы начать отдавать, и стоимость всей выгрузки растёт квадратично);
загрузка нескольких сущностей параллельно.
