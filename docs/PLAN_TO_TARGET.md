## 1. Потоки и что в них можно делать одновременно

Пять потоков. Внутри потока — строго по порядку, между потоками —
одновременно, с одной оговоркой ниже.

| Поток | О чём | Правит | Кто ведёт |
|---|---|---|---|
| **И** | Измерение: наборы, замеры, статус | документы, `ab_scorer.py`, gold-наборы | оркестратор + агент |
| **С** | Словарь и данные поиска | `wiki_alias*`, `*_load.sql`, `build.sh` | агент + прогон оркестратором |
| **К** | Классы неверных ответов | **`serene_ask.py`** | агенты, по одному за раз |
| **В** | Ворота Ф6: флаги в бой | env боевых юнитов, документы | оркестратор |
| **Э** | Эксплуатация и недостающие замеры | документы, юниты, `*.sh` | агенты |

🔴 **Оговорка о параллельности.** `ubuntu/serenedb/serene_ask.py` — один файл на
15 851 строку. Два агента, правящие его одновременно, затирают друг друга —
это уже случалось. Поэтому:

- в потоке **К** одновременно работает **ровно один** агент;
- потоки **И, С, В, Э** идут параллельно с **К** и между собой, потому что
  правят другие файлы;
- если задача из другого потока всё же требует правки `serene_ask.py`, она
  ждёт освобождения потока К.

Проверять пересечение до запуска — по карте зон `docs/CODE_MAP_ASK.md`
(20 зон, якоря, замок `test_code_map.py`). Две задачи в разных зонах —
всё равно один файл, всё равно очередь.

## 2. Задачи

### Этап 0 — наглядная схема пайплайна (делается первым)

**Ш0. `docs/PIPELINE.md` — как всё происходит, стрелками.**
Одна страница, которую можно понять взглядом, без чтения кода. Не пересказ
аудита, а именно схема: узлы и стрелки от 1С до сообщения человеку.

Что в ней обязано быть:

- **путь данных**: 1С на Windows → выгрузка → приёмник → витрина в SereneDB →
  корпус → индекс и векторы → словари;
- **путь вопроса**: человек → бот → мост → `/ask` → разбор → отбор → счёт →
  формулировка → проверка → ответ человеку;
- на каждой стрелке подписано, **что именно едет** (файлы пакета, строки
  витрины, вектор вопроса, число);
- у каждого узла — **что запускает** (таймер, вопрос, такт) и **где код**;
- отдельно показаны **развилки**: где путь может свернуть в уточнение,
  в отказ, в «нет данных»;
- отдельно — **где зовётся языковая модель** (это важно для п. 19);
- условные обозначения: сплошная стрелка — данные, пунктир — управление.

Источник — только факты аудита (`docs/HOW_IT_REALLY_WORKS.md`,
`docs/audit/level2/*`) и код. Догадок нет; чего не удалось установить —
в раздел «белые пятна» схемы.

Зачем первым: дальше работают несколько потоков сразу, и схема — общий язык,
по которому видно, какой поток какой участок трогает.
Параллельно: со всем. Исполнитель: агент.

### Поток И — измерение (вход во всё остальное)

**И0. Утилита эталонов из живой 1С + генератор приёмочного набора.** 🔴
новый первый шаг [решение владельца 26.08]
Прецедент: 31.07 эталоны набора 58 сверялись с живой 1С по OData скриптом
`etalon_1c.py` — сверка поймала **1 неверный эталон из 17** (склады:
группы посчитаны записями). Скрипт не закоммичен и **утерян** — в дереве
отсутствует. И0 восстанавливает его как постоянный инструмент, а не
одноразовый.

Что делает:
1. **Эталон из 1С по OData** (через шлюз `odata_gateway`; Ubuntu в 1С
   напрямую не ходит — `PLAN_MVP_PACKET_TRANSPORT.md`). Эталон двойной:
   независимый счёт из 1С и из корпуса; расхождение — не «пометить и
   пойти дальше», а **независимое прочтение вопроса агентом без контекста
   кода** (буква п. 15: «проверку ведут агенты без контекста») — иначе
   оба SQL разделяют одну интерпретацию автора (прецедент 30.07:
   «Всего» vs «СуммаДокумента»).
2. **Лаг свежести учитывается конструктивно**: эталон из 1С считается на
   «сейчас», корпус — на момент последнего такта (порога свежести нет —
   п. 17 с 26.08 «как можно быстрее», но лаг между тактом и «сейчас»
   существует всегда). Для стабильных
   срезов (справочники, закрытые периоды) — сверка всегда; для
   относительных («вчера», «этот месяц») — сверка сразу после такта либо
   пометка «данные уехали за лаг», а не FAIL. 1С по OData историческое
   состояние не отдаёт, проводки задним числом — это ограничение физики.
3. **Генератор вопросов**: покрытие сущностей — из `$metadata` базы;
   покрытие формулировок — из `ask_journal` (339 clarify на okna —
   готовый источник живых формулировок; шаблон «Сколько X за Y?» проверяет
   только классы, которые мы и так умеем).
4. Выход: `client-gold.tsv` (вопрос, эталон, источник эталона, статус
   сверки) + сам инструмент в git, с замком.

Правило верификации эталонов (из сверки 31.07): эталон правится **только
по факту 1С, с записью, никогда — по ответу системы**.

Доказательство: инструмент в git; прогон на ut_test/klient-1; таблица
расхождений эталон↔1С с разбором каждого.

(`1c-odata-gateway@<имя>`, только GET): для всех живых баз он уже поднят,
иначе не шёл бы сам синк. Проверка «шлюз отвечает» — первый шаг задачи.
Обходного пути нет и не нужно: база без шлюза — мёртвый стенд, сверять там

читается файл `$metadata`, а не живая 1С, поэтому под разрешённый остаток п. 20
(«поход в 1С по OData») он не подпадает — это работа с данными вне движка.
Цель: чтение метаданных пакета силами движка одним запросом (штатная загрузка
JSON) либо честный вынос шага из такта в поход OData. Промежуточных состояний
«остаётся как есть» нет. Зависит от: ничего. Параллельно: с К, В.

**Э7. Долг такта: выгрузка wiki — SELECT → свой Python → `.md`-файлы + чистка.**
[решение владельца 26.08] Та же природа, что Э6: данные обрабатываются вне
движка, побочные файлы живут на диске. Цель: дамп wiki средствами движка
(`COPY TO`) либо пересмотр формата хранения так, чтобы внешняя обработка
исчезла целиком, а не переименовалась. Зависит от: проверки по докам SereneDB,
что штатное средство покрывает формат потребителя. Параллельно: с К, В.

### Этап финальный — пересобрать схему по факту

**ШФ. `docs/PIPELINE.md` заново, после всех работ.**
К концу плана пайплайн изменится: словарь синонимов наполняется тактом,
флаги Ф6 стоят в бою, часть развилок закрыта, часть узлов исчезнет
(например, мёртвый шаблон юнита из Э5). Схема, нарисованная в начале,
к этому моменту начнёт врать — а устаревшая схема хуже отсутствующей.

Поэтому в конце схема строится заново от кода, и рядом кладётся короткий
раздел «что изменилось против первой версии»: какие стрелки появились,
какие исчезли, какие развилки закрыты. Это же будет доказательством
проделанной работы, понятным без чтения замеров.

Зависит от: всех потоков. Исполнитель: агент, проверка — оркестратор.

## 3bis. Контрольные точки (go/no-go) [добавлено 26.08]

План — не только список задач: в трёх точках принимается явное решение
«продолжаем или пересматриваем».

**ЧП1 — после И0 + первого прохода И2.**
- go: `client-gold.tsv` построен, 100 % эталонов сверены с 1С, каждое
  расхождение эталон↔1С разобрано (независимым прочтением, не догадкой);
- no-go: расхождение эталон↔1С > 20 % → стоп И2/И3 на старом наборе,
  пересмотр генератора и эталонов, повторный И0; объём потока К и срок
  называются только после валидного И2.

**ЧП2 — после С2 + К1 + К2.**
- go: полный скорер не ниже базы (21/25), оба K6 закрыты, rank живьём
  сходится с золотом;
- no-go: скорер ниже базы → откат С1/С2 (бок-таблицы для того и есть),
  разбор до выката.

**ЧП3 — после В2 (выкат Ф6 по чеклисту Ф6.5).**
- go: флаги в бою, скорер не ниже базы, латентность в норме Ф6.1;
- no-go: регресс → откат флагов по тому же чеклисту, разбор.

**Отдельно — сценарий «честное число хуже подогнанного».** Если И2 на
независимом наборе покажет значительно хуже 21/25 — это не регрессия
системы, а снятие подгонки под рабочий набор. Действия: признать факт
записью в `TARGET_STATUS.md` (стадии п. 2, 3, 10, 21 не повышать до
устранения), поток К перестраивается — сначала классы из И2, потом
известные; срок называется заново. Это прямое применение правила
приоритета из шапки: между «быстро закрыть жёлтый» и «получить честное
число» выбирается число.

**Готовность к финальной приёмке (п. 11)** определяется самим
[`TARGET.md`](../TARGET.md), а не новым списком порогов: все 21 пункт 🟢
или 🟡 с обоснованием остатка, п. 3/10/15 закрыты, приёмка на базе
клиента пройдена независимыми агентами. Численные цели для
`client-gold.tsv` и разброса называются **после** И2/И3 — до валидного
замера любой порог был бы выдумкой.

## 4. Чем доказывается «сделано»

Одинаково для каждой задачи:

- живой замер с числом, а не чтение кода;
- прогон замков с числами PASS/FAIL;
- полный скорер + `check_deploy_gate` перед любым выкатом в бой;
- запись в `CHANGELOG.md` с меткой `[замер]` / `[код]` / `[решение]`;
- обновление `docs/TARGET_STATUS.md`, если сдвинулась стадия пункта.

Задача без своего числа считается незаконченной, каким бы зелёным ни
выглядел код.

🔴 **Три правила против подгонки [26.08, решение владельца]** — постоянные,
действуют на все потоки, а не только на этот план:

1. **Починка доказана, только если её дельта превышает разброс.** Пока
   детерминированность не измерена (И3), система даёт ±1 на одиночном
   прогоне — и «починили» неотличимо от «повезло». Дельта в пределах
   разброса И3 — это шум, а не починка; задача не закрывается.
2. **Эталон правится только по факту 1С, отдельным коммитом от кода, с
   записью.** Никогда — по ответу системы. Держится гейтом И5, а не
   дисциплиной.
3. **Каждое принятое правило против подгонки получает механическое
   воплощение (гейт или замок) в том же шаге, иначе оно считается
   отсутствующим.** Задел на будущее: любое новое правило вида «не делать
   X» без остановки — это ноль исполнений (замер 03.08), поэтому правило
   принимается только вместе с его механизмом.
