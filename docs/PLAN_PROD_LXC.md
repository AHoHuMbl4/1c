# План: прод-контур — свой LXC на компанию

Заведён 2026-08-08. Решение владельца 08.08: **для прода у каждой компании — свой
чистый LXC**, никаких пересечений между компаниями. Этот сервер (`lxc-claude-1c`)
остаётся контуром разработки: тестовый стенд, стейдж. Прод — отдельные чистые LXC
без дев-хлама.

Статус: **план, не замер**. Реализация — по этапам §6.

Связано: [`PACKET_CONTRACT.md`](PACKET_CONTRACT.md) (транспорт, К9 «побазовость»),
[`PLAN_MVP_PACKET_TRANSPORT.md`](PLAN_MVP_PACKET_TRANSPORT.md), `ubuntu/packet/`
(приёмник/apply/kit), `work/packet/setup-receiver.sh` (идемпотентный установщик
приёмника — основа provisioning-а).

---

## 0. Принципы

1. **Изоляция: blast radius = одна компания.** Свой процесс приёмника, своя
   SereneDB, свой диск карантина, свой бот. Сбой, баг apply или переполнение диска
   одной компании не трогает остальных.
2. **Минимум ручной работы.** Заведение компании — одна команда + передать
   комплект клиенту. Всё остальное — скрипты, идемпотентные, с проверкой результата.
3. **Чистые LXC.** В прод-контейнере нет репозитория `/srv/1c`, хуков, гейтов,
   дев-скриптов, стендов — только код приёмника/apply, SereneDB, бот и секреты в
   `/etc` (как и сейчас: `640 root:<группа>`, не в git).
4. **Один код на всех.** Стейдж (несколько баз на этом хосте) и прод (одна база в
   LXC) работают на одном и том же коде и одном образе. Разница — только конфиг.
5. **Контракт не трогаем.** `manifest_version=1`, криптография (age + mTLS +
   Bearer), релей, универсальный установщик Windows — без изменений (правило
   «не трогать то, что работает», `HOW_NOT_TO §3.40`).

## 1. Архитектура прода

```
Windows компании (серый IP допустим)
  │  HTTPS, mTLS (CN=<base_id>) + Bearer, тело — zstd+age
  ▼
HAProxy на FreeBSD, 1c-gate.timpul.ru  ← единая точка входа, единый CA 1c-packet-ca
  │  маршрутизация по CN клиентского сертификата → backend компании
  ▼
LXC компании <base_id>:
  1c-packet-server (:6090) → карантин inbox/<base_id>/
  1c-packet-apply.timer    → merge в SereneDB этого же LXC
  SereneDB (витрина компании)
  бот компании (OpenClaw-слой; заводится, когда дойдёт бот-трек)
```

- **Маршрутизация на релее:** ACL по `ssl_c_s_dn(cn)` → backend `<base_id>`
  (адрес LXC). Альтернатива — поддомен на компанию; CN-маршрутизация не требует
  новых DNS-записей и новых сертификатов релея, поэтому она основная. Решение
  фиксируется на этапе 2 (§6) живой проверкой на стейдже.
- Белый IP нужен только нашей стороне — уже так; у компании может быть серый.
- Туннель LXC↔релей: по той же схеме, что сейчас (SSH reverse-туннель) или
  по WireGuard (`ubuntu/wireguard/` уже есть в проекте) — выбор на этапе 2,
  критерий: меньше ручных шагов при заведении компании.

## 2. Состав LXC компании (минимальный)

- SereneDB (та же сборка, что на стейдже; отдельный кластер внутри LXC).
- `/opt/1c-packet/`: `packet_server.py`, `packet_apply.py`, `packet_crypto.py`,
  `age`, `zstd` (официальные релизы, как на стейдже).
- Юниты: `1c-packet-server.service`, `1c-packet-apply.{service,timer}` —
  как на стейдже, без изменений.
- `/etc/1c-packet.env` (PACKET_ROOT, PACKET_LISTEN, PACKET_BASES, SERENEDB_DSN
  этой компании), `/etc/1c-packet-bases.json` — **одна запись** (эта компания),
  `/etc/1c-packet-age-<base>.key` — identity только этой компании.
- Бот-слой — по готовности бот-трека, отдельным шагом, тем же приёмом
  «образ + конфиг».

Чего в LXC **нет**: git-репозитория, хуков/гейтов, стендов, дев-скриптов,
доступов разработки.

## 3. Доработки до прода (обязательные)

1. **Per-base DSN в apply** (находка 08.08, замер чтением кода): сейчас
   `packet_apply.py` берёт один `SERENEDB_DSN` на все базы, а таблицы витрины
   именуются только по сущности — две базы в одной СУБД сольют одноимённые
   таблицы. Делается: запись базы в `PACKET_BASES` несёт `dbname` (или полный
   DSN), apply берёт его на базу, умолчание — прежний env (совместимость
   стейджа). Тогда один код работает и на стейдже (несколько баз на хосте),
   и в проде (одна база в LXC). Пробы apply дополняются случаем «две базы →
   две СУБД».
2. **Provisioning LXC** = обобщение `work/packet/setup-receiver.sh` (он уже
   идемпотентен) на цель «внутри свежего контейнера».
3. **Образ LXC**: чистая ОС + пакеты + код + юниты, **без секретов и без баз** —
   секреты и запись базы добавляет `new-company.sh` (§4).

`packet_kit.py` уже создаёт комплект на произвольный `base_id` (identity, токен,
сертификат CN, `packet-setup.json`, `client.pfx`) — используется как есть.

## 4. Автоматизация (минимум ручной работы)

- **`build-image.sh`** — сборка/обновление базового образа LXC. Прогон — по
  требованию (новая версия кода), результат — версионированный образ.
- **`new-company.sh <base_id>`** — единственная команда заведения компании:
  клон образа → старт → `packet_kit` (identity/токен/сертификат CN) → раскладка
  `/etc` внутри LXC → регистрация backend на релее (готовый фрагмент конфига
  HAProxy + reload, или печать фрагмента, если API у релея нет) → smoke:
  `/health` приёмника через домен с сертификатом компании → печать пути к
  комплекту клиента (`packet-setup.json` + `client.pfx`).
  **Ручная работа: передать комплект клиенту. Всё.**
- **`rollout.sh`** — обновление кода по всем LXC: копирование `/opt/1c-packet`,
  `systemctl restart`, проверка `/health` каждой компании; не ответил — стоп
  и доклад, следующие не трогаем.
- **`remove-company.sh <base_id>`** — остановка LXC, снятие backend на релее
  (отзыв доступа), архив данных (куда — решает владелец), удаление LXC.

## 5. Надёжность

- Изоляция процессов/БД/диска — по построению (§0.1).
- Карантин и идемпотентный apply — уже есть, остаются побазовыми без изменений.
- Отзыв компании = снятие backend на релее + удаление записи базы: пакеты
  перестают проходить на первом факторе (mTLS) и на втором (токен).
- Бэкапы: снапшот LXC средствами хоста + штатная выгрузка SereneDB внутри LXC
  (по расписанию, на компанию).
- Мониторинг (минимум): `/health` приёмника каждой компании + свежесть
  `last_applied_seq` (пакет не пришёл больше N тактов — сигнал, а не молчание).

## 6. Этапы

1. **Per-base DSN + пробы** — на этом сервере (стейдж), код apply + тесты.
2. **Образ + `new-company.sh`** — здесь же: вторая тестовая база заводится в
   своём LXC одной командой; живая проверка маршрутизации релея по CN
   (два комплекта → два LXC → оба отвечают через домен).
3. **Перенос `ut` в свой LXC** — когда этап 2 доказан замером; стейдж-контур
   при этом остаётся для разработки.
4. **Прод-хост**: чистая машина, только образ + LXC компаний; этот сервер
   окончательно становится dev/stage.

## 7. Открытые вопросы (решает владелец по ходу)

- Где физически живёт прод-хост (этот же hypervisor или отдельный).
- CN-маршрутизация vs поддомены — фиксируется на этапе 2.
- SSH-туннель vs WireGuard для LXC↔релей — на этапе 2, критерий §1.
- Ресурсные лимиты LXC (RAM/CPU/диск на компанию). Первый замер на стейдже
  `[08.08]`: SereneDB 4,7 ГБ RSS, приёмник 26 МБ, apply всплесками, CPU боевого
  контура между тактами ~0 — стартовая норма **2–4 ГБ RAM, 1–2 vCPU, 20–30 ГБ
  диска на компанию**; уточняется замером на реальных базах после этапа 2.
- Бот-слой: один бот на компанию в её LXC или общий фронт — когда дойдёт
  бот-трек.
- Почтовый приёмник (`ubuntu/mail/`, 08.08): в проде живёт в LXC компании
  (тогда почтовый сервер компании шлёт на адрес этого LXC — нужен маршрут
  пакетов 25/tcp из её сети, чего текущая схема «только исходящие» не даёт)
  или на стороне Windows рядом с агентом пакетов (тогда это не Postfix, а
  компонент установщика — трек владельца). На стейдже ставится как есть.

## 8. Этап «первый боевой юнит» — сервер 201.34.140.106 (08.08, в работе)

Решение владельца 08.08: первый юнит — не LXC на этом хосте, а **отдельный
сервер `201.34.140.106`** (hostname `medteh`, Ubuntu 26.04, 4 vCPU, 7,9 ГБ RAM,
77 ГБ диска). Схема «юнит на компанию» та же, что в §1, только вместо LXC —
выделенная машина; для следующих компаний такие же.

**Сеть [замер 08.08]:** у юнита два интерфейса — внешний `201.34.140.106` (eth0,
управление по SSH deploy-ключом `/home/claudedev/.ssh/id_ed25519_deploy`, доступ
уже работает) и внутренний `10.1.1.5` (eth1); релей — `10.1.1.4` в той же
внутренней сети (пингуется с юнита; на :443 ведёт себя как mTLS-релей — без
клиентского сертификата обрыв рукопожатия; это новый релей Ubuntu
`89.23.101.22`, на который переключён DNS `1c-gate.timpul.ru` 08.08 — 8.8.8.8 /
1.1.1.1 / Яндекс уже отдают его, dns.google и локальный кэш ещё догоняют).
Внутренняя сеть связывает только релей и юнит (с дев-сервера `10.1.1.5`
недоступен — замерено). **Следствие: SSH-туннель и WireGuard для юнита не
нужны** — HAProxy ходит в приёмник напрямую `http://10.1.1.5:6090`. Открытый
вопрос §7 про транспорт закрыт для этой схемы. Порт 6090 на юните открывается
только для `10.1.1.4`.

**Принцип переноса (указание владельца): только переносим, ничего не
переписываем.** Файлы копируются побайтно; меняются только значения в `/etc`
(адрес прослушивания, DSN, запись базы). Новых скриптов на юните не появляется.

**Опись боевого контура [замер 08.08 по живому стенду] — что переносится:**

| Слой | Файлы (источник на деве) |
|---|---|
| Движок | `/opt/serenedb-dist/serenedb-26.07.3-linux-amd64` → `/usr/local/bin/serened`, `/etc/serenedb/serened.conf`, юнит `serenedb.service`, юзер `serenedb` (uid 999), `/var/lib/serenedb` (чистый кластер), `/var/lib/serenedb/packet-meta/<base>` |
| Приёмник | `/opt/1c-packet/` (5 py + `bin/age`, `bin/age-keygen`, zstd), юниты `1c-packet-server.service`, `1c-packet-apply.service/.timer`, `/etc/1c-packet.env`, `/etc/1c-packet-bases.json` (одна запись), `/etc/1c-packet-age-<base>.key` |
| Доступ к БД | `psql` (пакет ОС), пароль роли postgres в env приёмника (как сейчас через `1c-serene-sync.env` + `1c-packet.env`) |
| Сборка слоя | снимок `/opt/1c-mcp-reports/` (раскладка `deploy.sh`), шаблон `1c-serene-pipeline@.service/.timer`, `/etc/1c-mcp-reports.env`, `/etc/1c-embed.env`, `/etc/1c-serene-pipeline-<base>.env` (DSN с явным dbname, `ETL_ODATA_BASE=/var/lib/serenedb/packet-meta/<base>`, свой `CSV_DIR`) |

**Не переносится (дев-хлам и выведенное):** репозиторий `/srv/1c`, хуки/гейты,
OData-шлюз и `serene_sync` (юнит к 1С не подключается — данные приезжают
пакетами), ETL/config-ui, `1c-mcp-reports` (report_1c), braine-остатки,
OpenClaw/бот-слой (отдельный этап), приборы `work/`, SSH-туннель `1c-gate-tunnel`.

**Единственная правка значений:** `PACKET_LISTEN=0.0.0.0:6090` (вместо
`127.0.0.1:6090`) — приёмник слушает все интерфейсы, а доступ режет файрвол:
ufw пускает на 6090 **только с релея `10.1.1.4`** (плюс ssh 22). Так конфиг
одинаков для любой копии, независимо от её внутреннего адреса. Код не трогается.

Первичный порядок сборки эталона (как делался 08.08, для воспроизводимости):

1. ОС: пакеты (`postgresql-client` ради `psql`, остальное по факту нехватки),
   юзер `serenedb`, каталоги — шаги те же, что в `setup-receiver.sh`, только
   без части «CA + комплект» (CA один, живёт на деве).
2. Движок: dist → `/usr/local/bin/serened`, conf, юнит, чистый кластер, роли
   `serene_ro`/`serene_resolver` тем же `setup.sh` (он идемпотентен).
3. Приёмник + сборка: rsync `/opt/1c-packet`, `/opt/1c-mcp-reports`, юнитов,
   `/etc`-файлов с правкой значений.
4. Комплект базы: генерируется на деве `packet_kit.py` (CA здесь), на юнит
   уезжают identity + одна запись `bases.json`; установщику — dist/zip как в
   `PACKET_ONBOARDING.md`.
5. Релей: backend по CN → `10.1.1.5:6090` (задание FreeBSD-сессии) + файрвол
   на юните (6090 только для 10.1.1.4).
6. Приёмка: чистый Windows-стенд → установщик → smoke `kind=meta` → первая
   полная выгрузка → `verified→applied` на юните → сборка слоя → контроль
   числа объектов витрины. Данные не переносим — наполняются пакетами с нуля.
