## 2. Занят или залип

**Вердикт: залип (не выполняет работу), а не «занят долгой операцией».**

Доказательства против «идёт сборка / пересчёт / тяжёлый SQL»:

1. Все 38 потоков спят, %CPU = 0 на двух выборках с паузой 3 с.
2. Счётчики CPU процесса за 15 с почти не двигаются.
3. WAL и mtime каталога данных не растут; последняя запись WAL — **~13 ч** до замера (24.08 15:25 → 25.08 ~04:20).
4. RSS не растёт (нет раздувания буферов под активную работу).
5. TCP-сессии копятся и висят ESTAB, но даже `SELECT 1` / handshake с `connect_timeout=3` не обслуживается.

Признак «порт слушает + unit active» **не** означает живость query path: accept/listen жив, исполнение запросов — нет.

## 4. Пул и memory_limit снаружи клиента

- В conf зафиксированы `--cpu_threads=160` / `--io_threads=16` (с 29.07).
- `SET threads` / `SET memory_limit` — глобальные SQL-настройки (ловушка проекта; CHANGELOG 23.08: прогоны `.test_*.sql` с `threads=2` / `memory_limit=1GB`, затем подъём до 160 / 46.5 GiB).
- Текущие `SHOW threads` / `SHOW memory_limit` **снять нельзя**: клиент не получает ответ.
- Следов «сейчас conf=2» нет; conf на диске = 160. Гипотеза «осталось threads=2 и поэтому SELECT 1 таймаутится» **слабо согласуется** с CPU=0 (при живом пуле даже узкий SELECT дал бы хоть какой-то utime).

## 5. Версии причины

### A. Query path движка мёртв / deadlock внутри serened (наиболее вероятно)

- Подтверждает: CPU≈0, WAL freeze, ESTAB копятся, `SELECT 1` timeout, journal текущего pid пуст, MemoryPeak 18.6 GiB в прошлом (был тяжёлый эпизод, сейчас процесс «тихий»).
- Опровергнуть извне без клиента/стека нельзя (`/proc/PID/stack` и `io` закрыты для claudedev).

### B. Незавершённая операция с хвостом в WAL, процесс «застыл» mid-flight

- Подтверждает: ненулевой `store.db.wal` (115 706), mtime 24.08 15:25 совпадает с окном, после которого клиенты перестали получать ответы (старейшие видимые stuck psql ~15:37 UTC 24.08).
- Ослабляет: при активном checkpoint/flush ожидались бы I/O и рост/сдвиг WAL — за 8 с и на горизонте часов роста нет.

### C. Исчерпание/шторм клиентских сессий (ask × сотни psql)

- Подтверждает: 56+232 psql только от ask + ~47 claudedev ≈ масштаб ESTAB.
- Не объясняет одно: при живом движке часть сессий или хотя бы `SELECT 1` сдвигали бы CPU; сейчас — нет. Скорее **вторичный** эффект после A/B.

### D. Глобально малые `threads`/`memory_limit` после тестовых SET

- Подтверждает исторически: CHANGELOG 23.08, conf сам по себе memory_limit не задаёт.
- Опровергает как **текущую** причину молчания: idle CPU и полный отказ handshake/query не выглядят как «медленно при threads=2».

## 6. Рекомендация (решение — оркестратору)

1. **Восстановить query path без рестарта снаружи нельзя** — клиентского канала нет, SQL `SET`/cancel недоступны.
2. **Рестарт `serenedb.service` потребуется**, чтобы снова отвечать на `SELECT 1`.
3. 🔴 Перед рестартом учесть правило проекта: ненулевой WAL при убийстве mid-work → риск петли OOM на следующем старте. Факт: WAL **есть** (115 706 байт, застыл 24.08 15:25). Решение «рестартовать / сначала бэкап store+wal / отдельный `--server_directory`» — только оркестратор/владелец.
4. После оживления движка — отдельно разобрать сотни зависших `psql` у `1c-serene-ask@*` (рестарт ask-юнитов *после* живого :7890), иначе клиенты снова забьют пул.
5. Повторить `SELECT 1` и при зелёном — догнать 9 live-замков из `docs/LOCKS_SWEEP_2026-08-25.md`.

**Итог одной строкой:** залип с ~24.08 15:25; CPU/WAL/RSS не растут; **рестарт нужен** для починки ответа; рестарт — решение оркестратора из‑за WAL.
