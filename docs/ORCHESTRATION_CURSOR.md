# Оркестрация: Kimi → cursor-agent

Режим работы, утверждённый владельцем 22.08: **Kimi (k3) — оркестратор**, исполнители —
отдельные процессы `cursor-agent` (модель `auto`, самый дешёвый режим Cursor).
1 задача = 1 свежий вызов `cursor-agent` = 1 чистый контекст исполнителя.

Этот документ — регламент оркестратора. Краткий указатель на него живёт в шапке
`memory_bank/activeContext.md`; постоянная ссылка для долгих сессий — в `AGENTS.md`
(правка владельца).

## 1. Разделение ролей

| Роль | Движок / модель | Чем занимается |
|---|---|---|
| Оркестратор | Kimi Code, `kimi-code/k3-256k` | декомпозиция, промты, контроль логов, замеры, коммиты, доклады владельцу |
| Обёртка | субагент Kimi, модель из `[secondary_model]` (`kimi-code/kimi-for-coding`, force) | только запуск `cursor-agent` и возврат итога |
| Исполнитель | `cursor-agent -p --force --model auto` | правка кода/конфигов, прогоны, замеры в своей задаче |

Решения (что делать, принять ли результат, коммитить ли) — только оркестратор.
Обёртка не разбирает задачу и не чинит ничего сама.

## 2. Команда запуска исполнителя

```bash
cd /srv/1c && timeout 1800 cursor-agent -p "<промт>" \
  --force --model auto --output-format text 2>&1 | tee .claude/state/cursor-run-<id>.log
```

- Запуск — из-под `claudedev` (сессии оркестратора и так идут под ним; `su` не нужен).
- `-p` — неинтерактивный режим: задача выполняется, процесс завершается, код выхода
  показывает итог. Проверено по `cursor-agent --help` 22.08.
- `--force` — разрешение на правки и команды (аналог auto-режима владельца).
- `--model auto` — сверено с `cursor-agent --list-models` 22.08: `auto` есть в списке,
  это текущая модель по умолчанию.
- `timeout 1800` — верхняя граница 30 мин на задачу; код 124 = завис/перерос.
- Лог каждого прогона — в `.claude/state/cursor-run-<id>.log`; оркестратор читает его,
  а не гадает по exit code.
- 🔴 **Промт исполнителю — только из файла** (`-p "$(cat файл)"`), никогда не литералом
  в команде. Живой замер 22.08: если текст промта содержит слова `git add`/`git commit`,
  снайпер срабатывает на саму команду оркестратора (видит «коммит», а индекс пуст) и
  блокирует запуск. Промт-файл кладётся в `.claude/state/prompt-<id>.md` инструментом
  Write — `check-prompt-rules` его пропускает, там нет долженствований в персону бота.

## 3. Правила для промтов исполнителю

Контекст у исполнителя нулевой — промт самодостаточен:

1. Цель и критерий приёмки (число/замер/тест, который должен стать зелёным).
2. Точные файлы для чтения и правки (оркестратор находит их заранее).
3. Что НЕ трогать (файлы, за которые дерутся параллельные задачи; защищённые пути).
4. Напоминание про гейты: коммит — пат-спеком, документы в том же коммите, граф при
   изменении компонента. Гейты Cursor и так остановят нарушение — строка в промте лишь
   экономит прогон.

## 4. Параллельность

- До N независимых задач — `AgentSwarm`: каждый item = одна обёртка = один процесс
  `cursor-agent`. Обёртка вызывает команду из §2 и возвращает: exit code, хвост лога,
  список изменённых файлов.
- Задачи, пересекающиеся по файлам, в один залп не ставятся. Если независимых задач
  много и они правят смежные компоненты — разводятся по `git worktree` (каждой своя
  ветка, merge оркестратором после приёмки).
- Параллельные прогоны делят квоту Cursor: при 403/лимите часть падает — оркестратор
  перезапускает их позже, это штатно.

## 5. Контроль: готов / долго / завис

- **Готов** — процесс завершился, exit code 0, критерий приёмки подтверждён замером
  из лога (не словами агента).
- **Фейл** — ненулевой код: оркестратор читает лог, решает: поправить промт и
  перезапустить (1 раз) или разбирать самому.
- **Завис** — код 124 от `timeout`, либо лог не растёт >10 мин при живом процессе:
  стоп, разбор лога, перезапуск с уточнённым промтом. Второй такой же завис подряд —
  стоп ветки, доклад владельцу.
- Дешёвой обёртке не поручается судить о качестве: приёмка — замером оркестратора
  после завершения (тесты, пробы, md5 — по обычным правилам проекта).

## 6. Дешёвая модель субагентов Kimi (`[secondary_model]`)

Каждый субагент Kimi независимо расходует токены. Привязка к дешёвой модели держится
конфигом, а не памятью оркестратора:

```toml
[secondary_model]
default_model = "kimi-code/kimi-for-coding"   # K2.7 Coding
force = true
```

- Внесено в канон `work/hooks/kimi-config.toml` 22.08; ставится в
  `~/.kimi-code/config.toml` владельцем через `bash work/hooks/install-gates.sh`.
- Фича экспериментальная: требует `KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=1`
  в окружении сессии (профиль `claudedev` — владелец). Без флага секция inert,
  субагенты наследуют модель оркестратора.
- `force = true`: параметр `model` не показывается оркестратору вовсе; каждый спаун
  субагента уходит на `default_model` рантаймом — «забыть» невозможно, в т.ч. после
  компакшна. Явная передача другой модели отклоняется ошибкой.
- Источник: доки Kimi Code, Configuration files → `secondary_model`
  (https://www.kimi.com/code/docs/en/kimi-code-cli/configuration/config-files.html).

## 7. Что за владельцем (один раз)

1. `bash work/hooks/install-gates.sh` — переносит обновлённый канон конфига.
2. `export KIMI_CODE_EXPERIMENTAL_SECONDARY_MODEL=1` — в профиль `claudedev`
   (например `~/.bash_profile`), иначе п. 6 не активируется.
3. Абзац-указатель в `AGENTS.md` (файл root-owned): режим оркестрации + ссылка на
   этот документ — чтобы регламент был в системном промте всю долгую сессию и
   переживал компакшн.

## 8. Границы режима

- Гейты Cursor (`.cursor/hooks.json`, failClosed) и git-гейт действуют на прогоны
  `cursor-agent` без изменений — смыслового снайпера в Cursor нет, поэтому промты
  узкие, а дифф каждого прогона оркестратор смотрит до коммита.
- Правило «не писать свои скрипты для работы с базой» и прочие инварианты проекта
  действуют на исполнителей в полном объёме — это в промте каждой задачи.
- Оркестратор не запускает `cursor-agent` в интерактиве и не резюмит его сессии:
  контекст исполнителя живёт ровно один прогон.
