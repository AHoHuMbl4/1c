# План: поиск по-настоящему штатными средствами SereneDB

Составлен 2026-07-26 после разбора демок и 1653 тестов движка. Причина: владелец —
«мне serene делает быстро очень поиск по базе, где у 1 сущности 45 параметров и все они
пересекаются, и сущностей 500. ты не так делаешь что-то».

Он прав. Ниже — что именно не так, с доказательствами из движка.

---

## 1. Главная ошибка: я склеиваю 45 реквизитов в ОДНУ строку

**Что делаю сейчас** (`serene_search_build.py`, сборка `doc`):

```
"реализациятоваровуслуг | Контрагент: ООО Ромашка | Склад: Основной |
 Организация: Наша организация | Сумма: 791800 | Date: 2025-12-04"
```

Одна текстовая колонка `doc`, один анализатор, один BM25. Всё, что было структурой
(45 отдельных реквизитов), превращается в мешок слов. Отсюда все наши беды:
поиск не отличает «контрагент Ромашка» от «склад Ромашка»; нельзя отфильтровать по
точному значению; нельзя поднять вес нужного поля; приходится вытаскивать смысл
вектором и городить выбор сущности моделью.

**Как штатно** — движок индексирует КАЖДОЕ поле отдельно в ОДНОМ индексе:

```sql
CREATE INDEX machines_idx ON machines
    USING inverted (id, name osb_en, all_text osb_en);
```
`tests/.../cookbook/search/one-search-box.test`. Демка demo6 — шесть полей в одном
индексе: `USING inverted(id, rating, title cf_en, statement cf_en, editorial cf_en, tags cf_en)`.

Проверено на нашей сборке 26.07.3 (таблица `_mf`, снесена после проверки):

```sql
CREATE INDEX _mf_idx ON _mf USING inverted(id, name search_dict, city, inn)
                           INCLUDE (name, city, inn, amount);       -- CREATE INDEX ok

SELECT name, city FROM _mf_idx WHERE city @@ 'Казань';              -- точное поле
SELECT name FROM _mf_idx WHERE name @@ ('ромашка'::tsquery ^ 2.0)   -- буст поля
       ORDER BY bm25(_mf_idx.tableoid) DESC;
```

Три вещи, которых у нас нет и которые появляются бесплатно:
- **колонка без словаря = keyword** (точное совпадение, `exact-value-matching.test`):
  `city`, `inn`, `Ref_Key` ищутся точно, а не как слова в мешке;
- **буст поля** `^ 2.0` — совпадение в наименовании весит больше, чем в примечании;
- **поле «всё вместе»** для широкого запроса (`all_text` в рецепте) — то есть наш
  нынешний `doc` остаётся, но КАК ОДНО ИЗ полей, а не как единственное.

## 2. Второе: вектор нам, возможно, вообще не нужен

Вектор в нашей схеме нужен только чтобы вытащить смысл из мешка слов. Когда поля
разделены и есть буст, значительная часть работы вектора уходит в текстовый индекс.

Отдельно зафиксировано (замеры 26.07):

| Факт | Значение |
|---|---|
| `hnsw` в сборке 26.07.3 | **нет**: `Unknown built-in opclass 'hnsw' (known: included, ivf)` |
| `hnsw` в исходниках коммита 722c929 (26.07) | **нет ни одного упоминания** в `server/` и `libs/` |
| demo4 (100 тыс. строк × 1536 измерений — ровно наш случай) | использует **`hnsw`**, которого в коде нет |
| `ivf` на 1536 измерениях | 10 000 строк, 61 МБ векторов → **30 ГБ памяти**, не достроился за 40 мин (в 500 раз больше полезного объёма) |
| отмена сборки `ivf` | **не работает**: `pg_cancel_backend` → `t`, работа продолжается; снимается только рестартом движка |
| мой прежний диагноз «`row_group_size`» | **опровергнут**: при 10 000 строк row-group ровно одна, а для ivf-колонки параметр обнуляется (`server/catalog/index.cpp:582`) |

**Вывод:** ANN-поиск по 1536 измерениям в этой сборке недоступен. Демка, показывающая
наш случай, написана под опкласс, которого в коде нет. Это вопрос к разработчикам
SereneDB, и идти к ним надо с воспроизведением (лестница по размерности).

Обходные пути, если вектор всё же понадобится:
- размерность 768 или 512 у Qwen вместо 1536 (объём втрое-вчетверо меньше);
- вектор только по НАЗВАНИЯМ сущностей (226 строк вместо 97 тысяч) — для выбора
  сущности этого достаточно, а по строкам искать текстом.

## 3. Порядок работ

### Шаг 1. Многополевой индекс вместо мешка слов
Собирать корпус не как одну строку, а как таблицу с колонками:
`src_table` (keyword), ключевые реквизиты-ссылки (keyword: контрагент, организация,
склад…), текстовые реквизиты (со словарём), `all_text` (склейка — для широкого
запроса), плюс `amount`/`doc_date` в `INCLUDE`.
Состав колонок берётся из `$metadata`, а не задаётся руками.
**Проверка:** «что купила Ромашка» находит строки накладных по полю контрагента,
а не по вхождению слова в мешок.

### Шаг 2. Запрос по полям вместо одного `@@ doc`
`probe()` строит условие по КОНКРЕТНЫМ полям с бустами, а не по `doc`.
Штатные механизмы: `ts_compound(must, must_not, should, k)`, буст `^`,
`ts_dict_agg/_count/_score` для словоформ, `sparse_ngram` для подстроки.
**Проверка:** золотой набор; сравнение с baseline 6/8.

### Шаг 3. Выбор сущности без модели
`src_table` — keyword-колонка в ключах индекса ⇒ доступны фасеты
(`ts_dict_agg`) и фильтр уровня индекса. Отбор кандидатов одним запросом в базе,
`LIMIT` обоснован контекстом модели, а не размером базы.
**Проверка:** 4 585 сущностей не ломают запрос (сейчас ломают на 1 900 — предел argv).

### Шаг 4. Транспорт
`psycopg` с bind-параметрами вместо `psql`-подпроцесса
(`tests/drivers/python/test_search_params.py`). Снимает предел argv, −39 мс на вызов.

### Шаг 5. Вектор — отдельным решением
Либо к разработчикам SereneDB с воспроизведением по `ivf`, либо меньшая размерность,
либо отказ от вектора по строкам в пользу вектора по названиям сущностей.

## 4. Что уже проверено как штатное и переделывать не надо

- агрегаты в базе по всему множеству (`count/sum/min/max/avg`), фильтр проталкивается
  в индекс — подтверждено `EXPLAIN`;
- группировка источников в базе, а не по top-N в Python;
- `ts_phrase` со слопом, `ts_levenshtein`, `ts_highlight`, `ts_compound`;
- обращение `FROM search_idx`, а не `FROM search_corpus`;
- один индекс с колонкой-дискриминатором источника поверх UNION-подобного корпуса —
  это шаблон движка (`examples/demo6/bootstrap.sql`);
- инкремент по `doc_hash` — штатного CDC в движке нет, наше оправдано;
- `ai_embed()` не умеет задавать размерность → наш поход за эмбеддингом из Python
  остаётся своим.

## 5. Ограничения схемы attach, которые надо знать заранее

- **инкрементального обновления индекса нет**: только `DROP INDEX` + `CREATE INDEX`,
  то есть полное вычитывание таблицы с Windows по сети
  (`tests/.../inverted_index_view_attached.test`: «The index is frozen at CREATE INDEX time»);
- **читать можно только `INCLUDE`-колонки**: попытка выбрать любую другую даёт ошибку
  (`postgres_scan` не в реестре fast-path, `server/connector/view_fast_path.cpp:140` — TODO).
  Значит всё, что бот показывает пользователю, физически копируется в индекс на Ubuntu;
- **диапазонный предикат в PG не проталкивается** (`WHERE id > N` → «Unsupported table
  filter type»), дельта-синк оставляем на загрузчике через `DataVersion` OData;
- `ATTACH` не переживает рестарт движка — нужен юнит с повторным `ATTACH` при старте;
- `NUMERIC`/`DECIMAL` не индексируется — в VIEW приводить `amount::DOUBLE`.
