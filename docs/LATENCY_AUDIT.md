# Аудит задержки ответа (~29 с) — 26.08.2026

**Роль:** только измерение и объяснение, без правок кода и без живых `/ask`.

**Вопрос владельца:** «Почему ответ идёт так долго? У нас же вектора, всё должно быть очень быстро.»

**Короткий ответ:** на контуре okna время уходит **не в векторы и не в kNN**. Эмбеддинг вопроса и смысловой отбор — доли секунды. Доминируют (1) блок после сбора кандидатов до выбора сущности (реранкер + детектор развилки + выбор моделью), (2) формулировка ответа моделью (`compose` + гейт), (3) при «холодном» процессе — многократный разбор намерения моделью. Векторный поиск сам по себе гипотезу «должно быть мгновенно» не оправдывает: он уже быстрый.

## 3. Что система уже измеряет

### В ответе (`diag`)

| Поле | Смысл |
|---|---|
| `diag.шаги[]` | `{шаг, мс, …}` — **кумулятивные** мс от `t0` внутри `answer()` (`шаг()` ~11991) |
| `diag.sec` | длительность `answer()` |
| `diag.tokens` | `{calls, in, out[, cache_hit, cache_miss]}` — сумма по `ds_chat` (`_TokenAcc` ~490) |
| `diag.fork.cost_ms` | мс блока детектора от `_t_fork` (~12767); в шаге поле зовётся `счёт_мс` |
| `diag.parse.samples` | сколько прогонов intent вошло в согласие |

При `ASK_TRACE=1` те же шаги пишутся в stderr: `TRACE <rid> service <шаг> <мс> …`; на каждый chat — `TRACE <rid> model TOKENS 0 in=… out=…` (`_trace_write` ~148, `_token_acc_record` ~527).

### В `ask_journal`

Колонки записи (`_ask_journal_write` ~15411): среди прочего  
`tokens_in`, `tokens_out`, `tokens_calls`, `latency_ms`, `rid`, `outcome`, `intent_json`, `atoms`, `doubt`, …  
Текст вопроса — только в `ask_journal_text` (и то без SELECT для `serene_ro`).

**Важно:** `latency_ms` — от `t0` в `answer_checked` (весь HTTP-ответ).  
`diag.шаги` / `diag.sec` — от `t0` **внутри** `answer()`. Если `ASK_ENOUGH` сначала вызывает `parse_intent`, его цена входит в wall/`latency_ms`, но в `шаги` часто видно `разбор вопроса` = **0 мс** (память уже заполнена).

## 6. Гипотеза «время = обращения к модели»

### Сколько раз зовётся chat за один ответ

| Вызов | Когда | Последовательно? |
|---|---|---|
| `_one_intent` × N (обычно 3 при `samples=3`) | разбор | **да, друг за другом** |
| `pick_entity` → `ds_chat` | выбор сущности | после поиска |
| `compose` → `ds_chat` (+ опционально 2-й при гейте) | формулировка | после счёта |
| `question_facts` / `need_say` | enough после/до | да |
| под-`answer` в арбитре × ≤`ASK_ARBITER_MAX`=3 | при сомнении | **каждый** со своим compose |

На успешных okna `answer` в срезе 18.08: **`tokens.calls = 2`** (pick + compose) при wall ≈29 с.  
Intent с `samples=3` в этих дампах **не входит** в `tokens` внутри `answer` (уже в memo) — но на холодном вопросе без memo добавит ещё несколько calls и секунды.

Исторический замер 17.08 (`qwen-latency-20260817.json`): sequential mean **54 с** при **5–7** calls; при меньшем числе calls в parallel-прогоне — десятки секунд ниже. Корреляция calls↔время подтверждает гипотезу качественно.

### Реранкер (не chat, но тоже нейросеть)

`rerank()` (~3501): HTTP на `RERANK_URL` (в `/etc/1c-embed.env` — Qwen3-Reranker-8B), timeout 30 с, до 60 документов. Входит в интервал **до** шага «детектор развилки». Это не векторный kNN корпуса.

### Вердикт по гипотезе

**Подтверждена числами в части «не вектора»:** смысловой отбор ~0.2 с.  
**Уточнена:** при `calls=2` на okna ~29 с делятся примерно на  
- ~7 с compose (модель формулировки),  
- ~10 с блок выбора сущности (в т.ч. 1 chat pick + SQL/алиасы),  
- ~9 с блок реранк+развилка (реранкер + SQL fork ~0.7 с + обвязка).  

То есть дорого и **chat**, и **реранкер/развилка**, а не «медленный индекс».

## 8. Контракт TARGET п. 19 и п. 20

**П. 19 (модель не считает и не ищет):**  
Счёт и индексный отбор — в базе (`aggregate`, `tables_of`, `fork_scan`) — **соблюдается**.  
Модель занята смыслом (intent / pick / compose) — **разрешено**.  
Реранкер для «слово ↔ название» в комментарии кода прямо соотнесён с п. 19 (~204–207).  

**П. 20 (данные внутри движка; эмбеддинг — `ai_embed`):**  
- `fork_scan` / `_measures_by_src` уже заточены под «один SQL, не веер» (~3968–3972, ~4104–4111) — направление верное.  
- **`ASK_EMBED_NATIVE` в env юнитов стенда не задан** → в коде умолчание `"0"` (~297) → эмбеддинг **вопроса** идёт **HTTP-клиентом** `embed_one` (~767–806), не штатным `ai_embed`. Для сборки корпуса `ai_embed` используется отдельно; для ask-пути флаг выката Ф6.4 **выключен**. Это расхождение с формулировкой п. 20 про эмбеддинг текстов — **назвать прямо**: текущий ask-контур эмбеддит вопрос снаружи процесса БД.  
- Оркестрация ответа — процесс Python с серией `psql` + внешние HTTP (chat, embed, rerank). Это не «модель считает», но и не «всё внутри одного SQL».

Время **не** уходит в запрещённый п. 19 «поиск моделью по сырым строкам»; оно уходит в **разрешённые** вызовы смысла/реранка и в тяжёлую обвязку развилки — просто их много и они **последовательны**.

## 10. Три самых дорогих места и что сделать (без внедрения в этом аудите)

### 1) Блок «кандидаты → сущность выбрана» (~9 с + ~10 с ≈ **19 с** на okna)

**Что это:** реранкер по ≤60 меткам + детектор развилки + `pick_entity` (chat).  
**Что сделать, чтобы быстрее:**  
- измерить отдельно TRACE/`шаги` с разнесением rerank vs `fork.cost_ms` vs pick (сейчас склеены соседними шагами);  
- сузить `ASK_RERANK_TOP` или звать реранк только при сомнении;  
- не дублировать тяжёлую работу развилки, если исход уже однозначен каноном продаж;  
- для pick — кэш/детерминизм без повторного chat на том же `(question, cands)`.  
**Чем доказать:** A/B scorer на тех же 25 вопросах + среднее `tokens_calls` и дельты шагов до/после; целевая дельта wall ≥ нескольких секунд при том же hit-rate.

### 2) `compose` + гейт (~**7–10 с**, 1 chat)

**Что это:** генерация прозы 27B (`DEEPSEEK_MODEL=Qwen3.8-27B` в `/etc/1c-serene-ask.env`) после того, как числа уже в `agg`.  
**Что сделать:** шаблонный/`figures` путь без LLM, когда слоты полностью закрыты кодом; укоротить `max_tokens`; запретить лишний retry гейта, если достаточно `kind=figures`.  
**Чем доказать:** те же 25 вопросов, доля `kind=figures` vs `answer`, среднее время и `tokens_out` на compose-шаге (нужен отдельный TRACE вокруг `compose` или journal + `шаги`).

### 3) Многократный intent (~**5–6 с** на новый вопрос; в k3 часто скрыт)

**Что это:** до 5 последовательных chat на согласие полей.

## 11. SQL для оркестратора (journal не снят здесь)

Нужна роль с **SELECT** по колонкам журнала (не `serene_ro` из `ask_journal.sql` — у неё SELECT почти снят). База okna через туннель, например `host=127.0.0.1 port=17890`.

```sql
-- 1) Прогон k3 по rid из лога (префикс ab-20260826T0948 / pid 1838651)
SELECT rid, outcome, latency_ms, tokens_calls, tokens_in, tokens_out,
       q_len, fork_outcome, code_md5, ts
FROM ask_journal
WHERE rid LIKE 'ab-20260826T09%'
   OR rid LIKE '%1838651%'
ORDER BY ts;

-- 2) Сводка по прогону
SELECT count(*) AS n,
       round(avg(latency_ms)/1000.0, 2) AS avg_s,
       round(min(latency_ms)/1000.0, 2) AS min_s,
       round(max(latency_ms)/1000.0, 2) AS max_s,
       round(avg(tokens_calls), 2) AS avg_calls,
       round(avg(tokens_in), 0) AS avg_in,
       round(avg(tokens_out), 0) AS avg_out
FROM ask_journal
WHERE rid LIKE 'ab-20260826T09%'
   OR rid LIKE '%1838651%';

-- 3) Корреляция calls ↔ latency
SELECT tokens_calls,
       count(*) AS n,
       round(avg(latency_ms)/1000.0, 2) AS avg_s
FROM ask_journal
WHERE ts > now() - INTERVAL '2 days'
  AND tokens_calls IS NOT NULL
GROUP BY 1
ORDER BY 1;

-- 4) Сопоставление с текстом (пишет только роль с SELECT на ask_journal_text.q_text)
SELECT j.rid, j.latency_ms, j.tokens_calls, j.outcome,
       left(t.q_text, 80) AS q
FROM ask_journal j
JOIN ask_journal_text t ON t.id = j.id
WHERE j.rid LIKE 'ab-20260826T09%'
ORDER BY j.ts;
```
