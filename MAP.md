## 1. Что делает продукт

Бот отвечает на вопросы по данным 1С. Цепочка:

```
1С (Windows, IIS, OData только на чтение)
  └─ шлюз :6011 — режет всё, кроме GET
      └─ витрина в SereneDB — таблицы 1С как есть
          └─ ПОДГОТОВКА + СБОРКА (внутри движка, SQL): корпус, величины, ссылки, векторы
              └─ индекс `search_idx` (инвертированный, BM25)
                  └─ сервис ответов — ищет индексом, считает базой, формулирует моделью
                      └─ мост MCP `ask_1c` (:6016) → бот OpenClaw в Telegram
```

**Баз 1С бывает несколько, и у каждой свой контур целиком:** свой шлюз OData, своя база
внутри движка, свой сервис ответов. На стенде их две: первая (Бухгалтерия 3.0, база движка
`postgres`, `:8091`) и вторая (УТ 11.4.9, база `ut_test`, `:8099`). **Боевые ответы идут по
второй** — это задано `ASK_URL` в юните `1c-mcp-ask`.

🔴 **02.08 оба сервиса ответов стали шаблонными юнитами** `1c-serene-ask@<база>` с
побазовым `/etc/1c-serene-ask-<база>.env`. До этого боевая конфигурация второй базы жила
ТОЛЬКО в окружении процесса, поднятого руками: `SERENEDB_DSN_RO` не был записан ни в один
файл, журнал уходил в файл под `/tmp` от завершённой сессии, и ребут оставил бы бота без
ответов. Тем же заходом побазовым стал `ASK_SCORER` — и `ab_scorer.py`, который его
переписывает, физически перестал доставать до боевой базы.

**Главный принцип** (п. 20 `TARGET.md`): данные лежат в SereneDB — работа с ними делается
**внутри** SereneDB. Своим кодом остаётся только то, чего у движка нет.

## 2. Файлы, которые работают

### Сборка данных — `ubuntu/serenedb/`, всё на SQL, питона нет

Такт **не ночной**: система обязана отражать изменения в 1С не позднее 20 минут
(п. 17 `TARGET.md`, подтверждено владельцем 28.07). Отсюда замок от наложения запусков,
докатка прерванного прогона и цена такта по числу изменений, а не по размеру базы.

| Файл | Что делает |
|---|---|
| `pipeline.sh` | **точка входа конвейера**: синк-дельта → сборка. Один атомарный такт |
| `serene_sync.py` | синк витрины из 1С: **дельта по `DataVersion`**, перепись схемы раз в час |
| `poc_load_entity.py` | загрузка сущности: полная и **`load_entity_delta`** (только изменения) |
| `build.sh` | сборка поискового слоя. Связывает шаги, держит замок, создаёт/удаляет секреты |
| `corpus_init.sql` | развёртывание с нуля: таблицы, словарь, индекс, **права**. Идемпотентно |
| `corpus_precheck.sql` | проверки ДО такта: индекс, права, источники, живость эмбеддера. Отпечаток «как было» |
| `corpus_build.sql` | сборка корпуса: `$metadata`, классификация колонок, имена, ссылки, даты, величины (`nums`), булевы реквизиты (`flags`), метки сущностей (`search_tables`) |
| `corpus_merge.sql` | перенос в боевой корпус по отпечатку + публикация индекса |
| `corpus_postcheck.sql` | проверки ПОСЛЕ такта: сверка с отпечатком. Код возврата — код сборки |
| `coverage_build.sql` | **перепись полноты** (п. 13): 1С → витрина → корпус → индекс → вектор + причина |
| `resolver_build.sql` | значения измерений для резолвера, инкрементально, одним `MERGE` |
| `embed_missing.sh` | досчёт векторов `ai_embed`: пачки по строкам И символам, докатка, перенос по ключу, `ROWS_WHERE` для очерёдности |
| `classify_entities.py` | разметка сущностей моделью: о чём спрашивают / служебное. Кэш в `search_entity_class`, задаёт **очерёдность** векторизации, ничего не выбрасывает |
| `deploy.sh` | раскладка кода в рабочий каталог, атомарной подменой. Убирает ручной шаг «скопировать в `/opt`». 🔴 **Ни одного `systemctl` в нём нет** — см. врезку ниже |
| `serenedb_backup.sh` | оффлайн-снапшот каталога данных движка: `stop → tar.gz → start`, ротация `KEEP=7`, процедура `RESTORE` в комментарии. Расписания у него нет, зовётся руками |
| `embed_all.sh` | **только досчёт векторов**, без пересборки корпуса. Для продолжения после обрыва и при первой заливке крупной базы |
| `wiki_build.sql` | страницы вики собираются **в базе**: чем сущность отличается от соседей. Ни сумм, ни счётов, ни дат — они бы устаревали и стали готовым неверным ответом |
| `wiki_publish.sh` | пишет страницы в хранилище `memory-wiki` и зовёт `openclaw wiki compile` |
| `wiki_alias.sh` | человеческие слова к сущности — **штатным агентом OpenClaw**, пачками по близости смысла; второй проход разводит слова-столкновения. Сколько сущностей за такт — ручка `WIKI_ALIAS_PER_TACT` (умолчание 100, `build.sh`) |

🔴 **Раскладка кода никого не перезапускает.** `deploy.sh` кладёт в `/opt/1c-mcp-reports` в
том числе `serene_ask.py` (код сервиса ответов), но ни он, ни `pipeline.sh` не делают ни
одного `systemctl restart`: сервис продолжает исполнять версию, загруженную при старте.
Разложенный код вступает в силу только при перезапуске и может копиться днями, ни разу не
проверенный замером — обратная сторона правила «сверить, что исполняется то, что правится».

🔴 **Но ребут сегодня — не выкатка, а остановка бота.** Отвечает процесс вне systemd
(`:8099`, база `ut_test`); после перезагрузки он умрёт, `systemd` поднимет `1c-serene-ask` на
`:8091` по **первой** базе, а мост `ask_1c` продолжит стучаться в `:8099`, где никого нет.
Прежде чем перезагружать — см. `ARCHITECTURE §6`.

⚠ И `/opt/1c-mcp-reports` **не зеркало репозитория**: `deploy.sh` копирует только
`*.sh|*.sql|*.py|*.tsv`, которые отличаются, и **ничего не удаляет**. Поэтому в рабочем
каталоге живут неверсионированные `bench_build.py`, `bench_run.py`, `serene-entities.txt.review`
и каталог `release-42/` с 15 журналами опытов от 26.07. Восстановить каталог из репозитория
«как есть» нельзя, и при разборе аварии непонятно, что из лежащего исполняется.

### Модели — `/etc/1c-embed.env`, одно место на весь продукт

🔴 **02.08 эмбеддер и реранкер переехали в контур владельца** (`Qwen3-Embedding-8B` +
`Qwen3-Reranker-8B`, dim 1024). Причина: [замер 02.08] облачный аккаунт DashScope ответил
`Arrearage` на все 11 ключей, и бот отдавал 503 **на каждый вопрос** — эмбеддинг вопроса
обязателен и отката не имеет. Наружу теперь уходит только модель ответов (DeepSeek).

| Что | Где | Зачем знать |
|---|---|---|
| адрес, ключ, модель, размерность, предел длины, размер пачки | `/etc/1c-embed.env` (600, не в git) | одно место; юниты `1c-serene-ask@` и сборка читают его |
| **две двери** | движок → `/v1/embeddings` (документы), сервис ответов → `/embed` с `is_query=true` (вопрос) | Qwen3 считает вопрос и документ по-разному; звать одинаково — молча потерять качество |
| отметка модели | `emb_model_<таблица>` в `search_quality` | смысловой путь включается только при совпадении с моделью вопроса — иначе несравнимые векторы дают мусор без ошибки |
| проверка модели | `embed_check.sh` (сборка) и `serene_ask.embed_model_live()` (ответ) | спрашивают **`/health`**, а не ответ на запрос: сервисы врут про свою модель — один подставляет свою, другой возвращает эхом запрошенное |
| прибор выбора сущности | `work/acceptance/entity_choice_bench.py` | сравнивает МОДЕЛИ между собой: детерминирован, без вызовов модели ответов, ранжирование делает движок |

### Приёмка — `work/acceptance/`

| Файл | Что делает |
|---|---|
| `run_acceptance.py` | гоняет вопросы из `docs/ACCEPTANCE_UT.md` **через бота**, сверяет величины эталона и **ожидаемое поведение**. Форма вызова: `RUN_TAG=v<N> python3 work/acceptance/run_acceptance.py <от> <до>` — **границы диапазона обязательны** (без них `IndexError`). `RUN_TAG` технически необязателен (без него подставляется метка времени), но **он обязан быть новым на каждый прогон**: при повторе ключа бот помнит прошлый ответ |
| `test_acceptance.py` | 🔴 **проба самого прибора подменой** — без базы, сети и модели. Прибору подсовывают заведомо верный ответ, заведомо неверный, отказ и уточнение, и он обязан назвать все четыре. Гоняется после каждой правки прогонщика |

🔴 **`kind` прибор берёт из стенограммы сессии бота, а не из русских слов ответа** (правка
02.08, кластер Э1). Результат вызова `ask_1c` лежит в `details.structuredContent.result`
файла сессии, а мост ставит туда машинные маркеры `[NO DATA]` / `[CLARIFICATION NEEDED]` /
`[SERVICE ERROR]` — это `kind` сервиса как есть. Отсюда два следствия: прибор не привязан к
языку ответа, и он видит класс, невидимый прежде, — **сервис сказал «нет данных», а модель
назвала число**. Путь к стенограмме спрашивается у движка (`openclaw sessions --json`),
имя файла не собирается догадкой.

[замер 02.08] Что дала правка на настоящем наборе: читается **58 вопросов вместо 54**,
сверяется величиной **47 вместо 26**, поведением 9, и **2** (№20, №53) прибор честно
называет непроверяемыми вместо того, чтобы засчитать любой ответ. 🔴 Прежние отметки
приёмки сняты сломанной линейкой и базой сравнения быть не могут.

Контракт `/ask` для фронта — [`docs/API_ASK.md`](docs/API_ASK.md): адреса, `kind`,
уточнение кнопками, и два ограничения, которые надо знать до начала (loopback без CORS,
токен нельзя класть в браузер).

### 🔴 Чем что запускать — берите САМЫЙ УЗКИЙ инструмент

Дважды за 29.07 я брал инструмент, который делает всё, когда нужно было одно, и терял
часы (`HOW_NOT_TO §3.22`). Таблица, чтобы не соображать заново:

| Задача | Запускать | НЕ запускать |
|---|---|---|
| правка персоны, моста, плагина | `ubuntu/openclaw/deploy_instance.sh` | ничего: без выкатки правка не действует |
| замер качества ответов | `RUN_TAG=v<N> python3 work/acceptance/run_acceptance.py <от> <до>` — через бота | прямой вызов `/ask` — он минует вики и даёт другой ответ. 🔴 Именно ему учит §0 `docs/ACCEPTANCE_UT.md`: тот раздел для замера качества не годится |
| загрузить/обновить **одну сущность** | `poc_load_entity.py <Имя>` — [замер] 4,6 с | `serene_sync.py` (все 1 588, ~40 мин) |
| подтянуть **изменения** из 1С | `serene_sync.py` | `pipeline.sh` |
| **продолжить досчёт векторов** | `embed_all.sh [потоков]` | `build.sh` (пересоберёт корпус) |
| пересобрать корпус после правки `corpus_build.sql` | `build.sh` | — |
| **полный такт** (данные изменились) | `pipeline.sh` или таймер | — |
| посмотреть полноту | `SELECT * FROM search_quality WHERE k LIKE 'cov_%'` | пересборка |

🔴 **У всех перечисленных инструментов умолчание — `dbname=postgres`, то есть ПЕРВАЯ база.**
Бот отвечает по второй (`ut_test`). Задавайте `SERENEDB_DSN` с явным `dbname` в каждой
команде: иначе «посмотреть полноту» молча покажет перепись чужой базы, а `build.sh` /
`embed_all.sh` потратят такт и деньги эмбеддера не на ту базу. Ошибки не будет ни на одном
шаге — числа просто окажутся из другой базы.

Крупный инструмент берётся, когда нужен **весь** его результат, а не когда он «заодно
сделает и это».

### Ответы — `ubuntu/serenedb/serene_ask.py`

Единственный большой файл своего кода в контуре ответа. Что важно: поиск штатными
