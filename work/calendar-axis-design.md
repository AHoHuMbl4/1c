## 1. Данные

### 1.1. Что даёт ось на okna (инвентарь, живая витрина `:7890`)

| Сущность (OData / витрина) | Роль | Замер 24.08 |
|---|---|---|
| `InformationRegister_Календарь` | дни графика: дата + вид дня + часы | **12 085** строк; в `search_tables` label «Календарь» |
| `ChartOfCharacteristicTypes_ДниНедели` | виды дня | **5** строк; join с `День_Key` календаря |
| `Catalog_ГрафикиРаботы` | какой график (пяти-/шестидневка) стоит за строкой | ключи календаря → «Пятидневная…» / «Шестидневная…» |

**Поля календаря (только из инвентаря):** `Дата`, `День_Key`, `Часы`, `Значение`,  
`ГрафикРаботы_Key`.

**Виды дня (значения из join, не список в коде):** Рабочий / Выходной /  
Сокращённый / Праздничный / Предпраздничный.

**Чего нет на okna (и не требуется для оси):**  
`Catalog_ПроизводственныеКалендари`,  
`InformationRegister_ДанныеПроизводственногоКалендаря`,  
`Catalog_Календари`, `InformationRegister_КалендарныеГрафики`,  
`InformationRegister_ПериодыНерабочихДнейКалендаря`, ФИАС / адресный стек.

### 1.2. Как размечается рабочий / выходной / праздничный

Строка `InformationRegister_Календарь` ссылается на вид дня через `День_Key` →  
`ChartOfCharacteristicTypes_ДниНедели`. Рабочий день = вид **Рабочий** (и при  
нужде бизнес-правила — **Сокращённый** / **Предпраздничный** как «всё ещё  
рабочий для фильтра окна»; точное множество рабочих видов — **в данных**  
`search_meta`, не в литералах Python). Выходной / праздничный — остальные виды  
из той же пятёрки.

Несколько графиков (`ГрафикРаботы_Key` → `Catalog_ГрафикиРаботы`): ось по  
умолчанию берёт **объединение дат**, помеченных рабочим видом хотя бы в одном  
графике, либо (если позже понадобится) доминирующий график по числу строк —  
решение данных/метрики, не хардкод имени «Пятидневная».

### 1.3. Один SQL: число рабочих дней в окне `[from, to]`

Счёт — внутри SereneDB (п. 20 TARGET). Имена таблиц ниже — из инвентаря;  
ключ/подпись вида дня подтягиваются структурно при сборке (как `Description` /  
`Ref_Key` уже используются в `corpus_build.sql` для справочников — платформенные  
поля, не имена конфигурации).

Ключ вида дня и подпись — **платформенные** поля OData уже используемые в
`corpus_build.sql` (`Ref_Key`, `Description`; не имена конфигурации). Join:
`Календарь.День_Key` = `ДниНедели.Ref_Key`. Синтаксис list/IN — штатный SereneDB
(проверить `serenedb-docs` + живой 26.08.1 при кодировании; сюда не вшивать).

```sql
-- Эскиз приёмки (один запрос в базе, не Python-цикл).
-- :from / :to — границы окна; :working_keys — список Ref_Key из
-- search_meta.calendar_working_day_keys (csv→list при чтении meta, как
-- balance_registers() в serene_ask.py), не литералы «Рабочий» в ask-коде.
SELECT count(DISTINCT k."Дата") AS working_days
FROM "InformationRegister_Календарь" k
WHERE k."Дата" >= :from
  AND k."Дата" <= :to
  AND k."День_Key" IN (:working_keys);
```

Календарные дни в том же окне — тот же запрос **без** `IN (:working_keys)`  
(или с ним пустым). Предпочтителен счёт по регистру, чтобы дыры в  
`InformationRegister_Календарь` были видны (п. 13 TARGET).

Фильтр фактов «только в рабочие даты» — предикат на дату документа/движения:

```sql
AND doc_date IN (
  SELECT DISTINCT k."Дата"
  FROM "InformationRegister_Календарь" k
  WHERE k."День_Key" IN (:working_keys)
    AND k."Дата" BETWEEN :from AND :to
)
```

### 1.4. Точка вставки в корпус (не новый загрузчик)

Образец — блок `balance_registers` в `ubuntu/serenedb/corpus_build.sql`  
(~стр. 90–101): отбор из `tmp3_ent` / `tmp3_prop` по **структуре** `$metadata`,  
запись в `search_meta`.

| Ключ `search_meta` | Содержимое | Как находят EntitySet |
|---|---|---|
| `calendar_registers` | имена регистров календаря (csv) | entity с полями даты + ссылки на вид дня (структура prop), без литерала `Календарь` в SELECT |
| `calendar_day_kinds` | имя плана видов характеристик дней | entity chartofcharacteristictypes / аналог, join-ключ к `*_Key` даты |
| `calendar_working_day_keys` | Ref_Key видов, чья подпись = рабочий класс | после сборки: join витрины, отбор по подписи вида из **данных** (не python-list); при пустоте — ось выключена |
| опционально карта | рядом с `search_balance_map` | `src_table`, `date_col`, `day_key_col`, `hours_col` — только prop-имена из `$metadata` |

Приёмка шага корпуса: после `corpus_build` на okna  
`search_meta.calendar_registers` непуст, `calendar_working_day_keys` даёт  
`count(DISTINCT Дата)` рабочих за известный месяц > 0 и < числа календарных  
дней того же месяца.

## 2. Детектор

### 2.1. Нужда в оси

Ось нужна, когда одновременно:

1. в `search_meta` есть непустой `calendar_registers` + `calendar_working_day_keys`  
   (иначе ветка «рабочие» = unavailable / не открываем ось — честно по данным);
2. у вопроса есть окно периода (явное / prior / assumed с from|to) — тот же  
   контур, что `period_readings`;
3. **и** либо ось названа в вопросе через словарь (§2.3), либо детектор всегда  
   считает обе ветки на окне (как MTD/full_month раскрываются по **форме**  
   границ, не по лексике).

Рекомендуемый режим (как W): **always-on при наличии карты** — два прочтения  
окна: `calendar_days` (все даты регистра в [from,to]) и `working_days`  
(фильтр по `calendar_working_day_keys`). Числа фактов считаются на каждом  
прочтении; совпали → исход A; разошлись → B/C.

### 2.2. Где в пайплайне

Рядом с W-треком, не отдельный конвейер:

```
parse_intent
  → apply_period_leader / period_readings   # окна mtd|wtd|…
  → [NEW] calendar_axis_readings(intent, period_window, search_meta)
        # 0..2 day-basis readings: calendar_days | working_days
  → fork_scan / fork_scan_readings          # уже умеет readings × src
  → fork_classes* / resolve_fork_outcome
  → fork_outcome_a | fork_outcome_b | fork_outcome_c
  → ask_journal (ticket_variant только при нажатии; _journal_ticket_variant)
```

`interpretation_id` / `window_fp_of` расширять **второй координатой** day-basis  
(или отдельным `day_basis_fp`), не ломая существующие `mtd`/`wtd`/`full_month`/  
`full_week`/`drop_assumed`. Лидер day-basis по умолчанию — см. §2.4.

### 2.3. Без списка слов в Python

Триггеры «за рабочие дни», «в будни», «по рабочим», «календарные дни»,  
«включая выходные» — **не** `frozenset` в `serene_ask.py`.

Варианты (оба допустимы, предпочтителен словарь в базе):

1. **Словарь в данных** — таблица/ключи в `search_meta` или рядом со  
   `search_fork_label` / контуром `wiki_alias.sh` (§7): phrase →  
   `day_basis=working|calendar`. Наполнение — штатным агентом, как подписи  
   развилок; холодный старт без словаря = always-on обе ветки + честный C,  
   если подписей класса ещё нет.
2. **Только форма данных** — ось всегда раскрыта при непустой карте; явная  
   лексика не нужна для открытия люка (люк открывает **разный счёт**, §2  
   контракта). Словарь тогда только для **сдвига лидера** (§2.4), не для  
   детекции.

Запрещено: хардкод русских триггеров в ask-коде; промт «всегда спрашивай про  
рабочие дни».

### 2.4. Лидер day-basis, когда ось не названа

По аналогии с `_WINDOW_LEADER_FORMS = ("mtd", "wtd")`:

| Условие | Лидер day-basis | Люк |
|---|---|---|
| ось не названа (нет hit словаря) | `calendar_days` — текущее поведение окна (все даты from–to), **status quo** | `working_days` |
| словарь / ticket указал рабочие | `working_days` | `calendar_days` |
| словарь / ticket указал календарные | `calendar_days` | `working_days` |

Молчание человека ≠ выбор (§2 контракта). Sticky только через `decision_id` /  
память нажатия.

## 3. Развилка

### 3.1. Класс

Класс развилки: **календарные дни окна vs рабочие дни окна**  
(day-basis × то же E×M×W, что уже считает детектор).  
Отпечаток — через существующий `fork_key_of(src_set, measure_ctx, window_fp=…)`  
с включённым day-basis в fp (иначе B сольёт ветки).

Тот же класс, что MTD vs полный месяц (§7bis): лидер + люк, нажатие в память.

### 3.2. Пары «число + подпись» (B / C)

Человеческие подписи — из словаря развилок §7 (`search_fork_label`), не из  
имён таблиц:

| Ветка (машинный id) | Подпись-кандидат для агента §7 (пример смысла) |
|---|---|
| `calendar_days` | «по календарным дням» |
| `working_days` | «по рабочим дням» |

Агент пишет подписи один раз на `fork_key`; B рендерит  
`render_atom_pair` + `options[]`. Нет подписей → исход **C**: число лидера +  
константа «есть другое прочтение» (`FORK_OTHER_READING` / аналог), ветки не  
называть.

### 3.3. `ask_journal` при нажатии

Пишется **только факт нажатия** (как сейчас клик/`decision_id`):

- `ticket_used` / `ticket_variant` — подпись погашенного варианта  
  (`_journal_ticket_variant`: label/src из trusted);
- `fork_outcome` = `B` (или путь choice);
- `fork_keys` — отпечаток класса с day-basis;
- **не** писать выбор при ненажатии; молчание не обновляет память.

Память выбора (§6 / HOW_IT_WORKS 8a–8b): только явный ticket /  
`memory=remember`, не «пользователь не нажал — значит календарные».

### 3.4. Исход A

Если атом ответа (число + единица + оговорка окна) **совпал** на  
`calendar_days` и `working_days` (например, в окне не было выходных или  
фильтр не изменил сумму) — один класс эквивалентности → **A**: одно число,  
люк не открываем, src/day-basis не запоминаем.

## 4. Ответ лидера

Лидер до разметки day-basis / до клика:

1. **Победитель шага 4 конвейера** — `picked[0]` / класс из  
   `fork_leader_class(picked_src, classes)` (докстринг: «не новая лестница —  
   повторное использование победителя шага 4 до детектора»).
2. Среди нескольких окон одного src — формы `mtd`/`wtd`  
   (`prefer_window_leader` / `_WINDOW_LEADER_FORMS`).
3. Среди day-basis — правило §2.4 (`calendar_days` по умолчанию).

**Не делать:** отдельную лестницу «голова / словарь сущностей / якорь» для  
этой оси; не подменять `fork_leader_class`; не звать `arbitrate` при  
`ASK_FORK_OUTCOMES=1` (как у текущего W).

Ответ человеку: пара лидера; при B — люк с подписанной второй веткой; при C —  
число лидера + «есть другое прочтение».

## Риски (кратко)

1. **Несколько `ГрафикРаботы_Key`** — разные пяти-/шестидневки дадут разный  
   count рабочих; без правила выбора графика ось врёт или плодит третью ветку.
2. **Пустые / дырявые даты в `InformationRegister_Календарь`** — working filter  
   молча выкинет факты в дни без строки регистра (п. 13 TARGET: потеря должна  
   быть видна; иначе дефект).
3. **Лексика в коде** — соблазн зашить «будни»/«рабочие» в Python обойдёт §7bis  
   и снайпер; держать триггеры только в словаре/meta или не требовать их  
   (always-on по разному счёту).
