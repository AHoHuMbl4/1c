## 1. Что ставится на Windows

| Компонент | Откуда | Куда |
|---|---|---|
| `packet-agent.exe` (C#, тот же csc.exe .NET Framework 4, без NuGet — как setup) | комплект | `C:\1c\packet\` |
| `age.exe` | официальный релиз age (шифрование; своих AEAD/X25519 в .NET Framework 4 нет — замер 06.08) | туда же |
| `zstd.exe` | официальный релиз zstd | туда же |
| `agent.ini` | пишет установщик (см. §2) | туда же, права только админам/службе |
| каталог данных (индекс версий, очередь чанков, журналы) | создаёт установщик | `C:\1c\packet\data\` |

Запуск агента: служба Windows (предпочтительно, auto-start) либо задача планировщика —
решение за реализацией; такт задаётся сервером через конфиг (`tact_seconds`), локально
агенту надо уметь «проснуться и сделать такт».

## 2. Комплект установки — что приезжает с Ubuntu

Перед установкой на Ubuntu один раз генерируется комплект базы (скрипт сделаем на стороне
Ubuntu): **base_id, токен Bearer, recipient pubkey (age1…)**. Установщик принимает его
**одним файлом** `packet-setup.json` рядом с exe (или ключом `--packet-setup <путь>`):

```json
{"base_id": "ut", "token": "…", "recipient_pubkey": "age1…",
 "receiver_url": "https://1c-gate.timpul.ru"}
```

**С 06.08 (mTLS, решение владельца)** комплект дополнен клиентским сертификатом
(контракт §8): файлы `client.pfx` + `client.crt` + `client-key.pem`, а в
`packet-setup.json` — поля `client_pfx` (имя файла) и `client_pfx_password`.
Сертификат выдаёт наш CA `1c-packet-ca`, `CN=<base_id>`; без него релей (HAProxy)
не пропускает запрос вовсе. Установщик: импорт `client.pfx` в `LocalMachine\My`
(пароль из `packet-setup.json`), отпечаток — в `agent.ini` полем
`client_cert_thumbprint` (может быть с пробелами/в верхнем регистре — агент
нормализует). Сам `.pfx` после импорта удалить.

🔴 **`recipient_pubkey` — ОБЯЗАТЕЛЕН (решение владельца 07.08: «делаем как надо, с
шифрованием»).** Пилотная оговорка 06.08 («поля может не быть») отменена в тот же
день, не доехав до боя. Комплект всегда несёт pubkey, установщик пишет его в
`agent.ini`, агент шифрует каждый пакет age (zstd → age). Приёмник принимает оба
режима по магии файла (контракт §2) — это совместимость, а не приглашение слать
открытым. Канал дополнительно держат TLS + SSH-туннель + mTLS — то есть шифрование
сквозное: тело нечитаемо и на релее после TLS-терминации, и в карантине на диске.
`age.exe` в комплекте обязателен (префлайт §3).

Из него + параметров OData (ai_reader, уже есть в exe) пишется `agent.ini`:

```
base_id=ut
receiver_url=https://1c-gate.timpul.ru
token=…                    # Bearer, только в файл, в лог как ***
recipient_pubkey=age1…     # только если поле есть в комплекте
client_cert_thumbprint=…   # отпечаток из LocalMachine\My после импорта client.pfx (mTLS)
odata_url=http://localhost/<публикация>/odata/standard.odata
odata_user=ai_reader
odata_password=…           # из существующих параметров exe, в лог как ***
data_dir=C:\1c\packet\data
progress_seconds=60        # (v1.1.0) отчёт хода такта не чаще раза в N секунд;
                           # 0 — выключить. Ключ необязателен: нет — берётся 60
batch_mb=128               # (v1.1.2) порог отправки порции: сжатая очередь достигла
                           # N МБ — пакет уезжает, обход продолжается
batch_seconds=3600         # (v1.1.2) порцию — не реже раза в N секунд, даже если
                           # порог по объёму не набран (чекпоинт долгих обходов)
metadata_file=C:\1c\packet\metadata.xml   # с 11.08 (v2): см. §9 — манифестный режим
```

**`metadata_file` (v2, 11.08):** если ключ задан и файл существует, агент читает
структуру метаданных из этого файла (синтетический `$metadata`, сгенерированный
установщиком через COM — §9) вместо HTTP GET `$metadata`; отпечаток файла пишется
в `state.json` (`metadata_fingerprint`). Ключа нет или файла нет/пуст — прежний
HTTP-режим (агент падает с понятной ошибкой только если ключ задан, а файл
недоступен: `metadata_file задан, но файла нет: …`).

## 3. Префлайт (добавка к существующему блоку, до установки агента)

| Проверка | Если плохо |
|---|---|
| исходящий HTTPS на `receiver_url` (TLS handshake + `GET /health` → `packet-server-ok`) | стоп с текстом: открыть исходящий 443/TCP на домен; входящее на Windows не нужно |
| место на диске под данные агента (очередь чанков ≈ размер базы сжатой + индекс версий) | стоп с цифрами, как в существующем префлайте |
| `age.exe`/`zstd.exe` из комплекта запускаются (`--version`) | стоп: комплект неполный/антивирус |
| `packet-setup.json` валиден (base_id `[a-z0-9_-]+`, токен непуст, pubkey — если есть, то формы `age1…`) | стоп: комплект не от этой установки |
| `client.pfx` из комплекта импортируется в `LocalMachine\My` (пароль из packet-setup.json) | стоп: без клиентского сертификата релей не пропустит ни один запрос (mTLS, контракт §8) |

## 4. Пробная посылка (smoke test) — аналог проверки OData

После установки службы — живая проверка связности **данными, не «запустилось»**:

1. агент собирает тестовый пакет (kind=delta, одна малая сущность или пустой набор по
   указанию приёмника);
2. шлёт по протоколу §8 контракта: manifest → chunk → `status` до `verified`;
3. отчёт в консоль и в лог: `applied`/`verified` или код ошибки приёмника
   (`bad_auth` — неверный токен, `stale_seq` — комплект уже использовался и т.д.);
4. код выхода exe: 0 только при подтверждённой доставке.

## 5. Чего установщик НЕ делает

- не открывает входящие порты на Windows (их нет по построению);
- не настраивает роутер/проброс 443 на Ubuntu (это периметр, отдельный трек);
- не хранит private key (его нет на Windows по построению);
- не трогает существующие шаги канала OData и их коды выхода.

## 6. Журнал и диагностика

- лог агента и установки — `C:\1c\logs\` (там, где уже логи exe), ротация по размеру;
- секреты в лог — как `***` (существующий приём exe с паролем админа);
- понятные строки для типовых сбоев: «нет связи с приёмником», «токен отклонён»,
  «приёмник в карантине — звоните нам».

## 6-бис. Обновление агента НА МЕСТЕ (без переустановки)

Вся личность канала живёт вне exe: `agent.ini` (токен, отпечаток сертификата,
адреса), сертификат в `LocalMachine\My`, задачи планировщика, `data\`
(state.json, индексы) и `metadata.xml`. `state.json` совместим между версиями
(поля не менялись с 1.0.x), новые ключи ini имеют умолчания — поэтому апгрейд =
подмена одного файла `packet-agent.exe`.

Штатный путь — `windows/packet-agent/upgrade-agent.cmd` (лежит и на S3:
`installers/packet-agent/upgrade-agent.cmd`, рядом `packet-agent.exe` всегда
последней версии). Запуск от имени администратора, без параметров. Порядок
внутри продуман под «один шанс»: сначала скачивает и ПРОВЕРЯЕТ новый exe
(`--version`), и только потом глушит сторожа и демона; старый exe остаётся
рядом `.bak`; любой сбой — откат и внятная ошибка, код выхода ненулевой.
`[замер 13.08]` прогнан на стенде: успех (подмена + автозапуск), отказ сети
(«НИЧЕГО НЕ ИЗМЕНЕНО», код 1, файл цел).

⚠ Обновление убивает текущий такт: у 1.0.2 весь несохранённый проход в RAM
пропадает (с 1.1.2 это уже не больно — порции и индекс).

## 7. Контракт CLI `packet-agent.exe` (на него опирается установщик)

Зафиксирован при реализации блока (06.08). Установщик зовёт агент ровно так:

| Вызов | Контракт |
|---|---|
| `packet-agent.exe --version` | печатает версию, код 0. Используется в префлайте (диагностика) |
| `packet-agent.exe --smoke` | пробная посылка по §4: тестовый пакет → `status` до `verified`; **код 0 только при подтверждённой доставке**; при ошибке приёмника печатает его код (`bad_auth`, `stale_seq`, `quarantined`…) — установщик переводит в строку по §6. **Код 3 (v1.0.3, 12.08): смоук НЕ выполнялся — mutex занят демоном.** До 1.0.3 в этом случае возвращался 0, и установщик читал его как подтверждённую доставку — ложно-зелёная установка на живом прогоне ERP (`HOW_NOT_TO §3.63`). Установщик на код 3 гасит демона и повторяет смоук один раз |
| `packet-agent.exe` (без аргументов) | демон: читает `agent.ini` из своего каталога, крутит такты по конфигу сервера (`tact_seconds` из `GET /agent/config`) |
| `packet-agent.exe --send-log <path>` (v2, 11.08; v2.1 — outbox) | копия файла кладётся в `outbox\` рядом с `agent.ini` — этим доставка ГАРАНТИРОВАНА: демон довозит outbox своим тактом (конец `Tact.Run`, лог-пакет тем же кодом, что CLI: служебный чанк `log`, manifest → chunk → status до `verified`; после подтверждения копия удаляется, при неудаче остаётся до следующего такта). Если single-instance mutex свободен — делается и немедленная попытка (код 0 только при `verified`); если занят — печать «поставлено в outbox, демон довезёт», код 0. Файл читается с `FileShare.ReadWrite` (писатель может держать его открытым). Пустой файл не отправляется; незавершённый пакет в очереди — сначала довозка. До v2.1 CLI при живом демоне отказывал по mutex, и установщик гасил демона сам — на живой базе первичная синхронизация держит mutex часами, и лог не уходил никогда (ЗУП 11.08) |
| второй экземпляр | **обязан завершаться сразу с кодом 0** (single-instance): сторож планировщика запускает exe каждые 5 минут |

Автозапуск выбран планировщиком (решение реализации, §1): задача «1C Packet Agent»
(ONSTART, SYSTEM) + «1C Packet Agent Watchdog» (каждые 5 мин). Служба Windows
потребовала бы служебного каркаса в самом exe — агенту это не нужно.

## 9. Установщик v2 (11.08) — что изменилось в поведении exe

Реализован план из ресерча №3 (`CHANGELOG.md`, 11.08 ночь). Существующие шаги
канала OData не тронуты; новое:

1. **Валидатор состава OData — ДО установки состава** (`Steps.cs:2058`).
   COM-обход метаданных ищет три класса ломателей генератора OData: ссылки на
   таблицы внешних источников данных (`ВнешнийИсточникДанныхТаблицаСсылка.*`),
   дубли латинских имён реквизитов внутри объекта, неуправляемый состав
   (режим совместимости ≤ 8.3.4 — тогда блок состава пропускается целиком).
   Найденные объекты **исключаются из состава с явным отчётом**
   `odata-excluded-<дата>.txt` (пишется в `C:\1c\logs\`, уезжает на приёмник
   лог-каналом). Стенд УТ 11: исключён ровно 1 объект (Валюты, дубль
   `DataVersion`), состав 2395, корень → 200.
2. **Health-check тройкой** (корень / `$metadata` / проба сущности). Если
   сущности отвечают 200, а корень и `$metadata` — 500, это **warning, а не
   fail** (соглашение платформы: полная модель строится только корнем и
   $metadata, сущности живут при мёртвом корне). Проверка данных в этом случае
   идёт по манифесту состава (`Steps.cs:2414`).
3. **КС-discovery** (`Steps.cs:2229`, `DiscoverCsBases`): базы кластера через
   COM cluster API (ConnectAgent→GetClusters→ConnectWorkingProcess→
   GetInfoBases); без доступа к кластеру — молчит в лог, в unattended без
   `--base/--connstr` прогон завершается exit 5.
4. **Генератор манифеста метаданных** (`manifest-gen.ps1`, вшит ресурсом;
   вызов — `Program.cs:616`, между шагом 12 и блоком агента). Синтетический
   `$metadata` из COM-метаданных → `C:\1c\packet\metadata.xml`; исключения
   валидатора передаются (`OC1C_EXCLUDE`), в манифест их нет. Мягкий шаг:
   неуспех не валит установку — агент остаётся на HTTP-режиме. Калибровка по
   живой УТ: MATCH 2836/2836; типы чисел — дробные → `Edm.Double`, целые
   ≤ 4 разрядов → `Edm.Int16`, иначе `Edm.Int64` (`Edm.Int32` платформа не
   использует).
5. **autoGate читателя в unattended** (`Packet.cs:246`): при наличии COM и
   кредов администратора ИБ пользователь-читатель (`ai_reader`) создаётся
   автоматически, при повторном прогоне пароль сбрасывается. До v2 прогон на
   чистой машине умирал EXIT_PREREQ.
6. **Автоотправка логов** (`Program.cs`, `SendLogs`; с v2.1 — outbox, §10):
   в конце прогона установщик сам шлёт на приёмник свой лог и отчёт об
   исключениях. В v2 (до v2.1) — через `packet-agent.exe --send-log` с
   остановкой демона на время отправки (`PacketSteps.StopAgent` ждёт
   исчезновения процесса до 20 с — taskkill не равен смерти процесса, named
   mutex освобождается 2–5 с); на живой базе это не работало (mutex занят
   первичной синхронизацией часами) — заменено outbox-ом (§10). Лог
   установщика открывается с `FileShare.ReadWrite` (`Sys.cs:61`) — иначе
   агент не может его прочитать, пока писатель жив.
7. **Пробы ai-ext идут в алиас ЭТОЙ установки**: переменная окружения
   `OC1C_EXT_ALIAS` (`Steps.cs:2496` → `ai-ext.ps1:40`); до v2 алиас /1c был
   захардкожен и шаг 14 падал 401 на публикации с другим именем.

## 10. Установщик v2.1 (11.08) — outbox логов и skipped-only пакеты

Два дефекта наблюдаемости, найденные живым прогоном на ЗУП 11.08 (оба —
«на пустом стенде работало»):

1. **Outbox вместо остановки демона** (`Program.SendLogs`, `Program.cs`;
   агент — `Tact.ProcessOutbox`/`DeliverOutboxFile`/`SendLogBody`,
   `PacketAgent.cs`). Установщик в конце прогона КОПИРУЕТ лог установки и (если
   есть) `odata-excluded-<дата>.txt` в `<packet dir>\outbox\` — демон агента
   не останавливается вообще. Агент в конце каждого такта (`Tact.Run`, все
   ветки выхода) забирает outbox: каждый файл уходит лог-пакетом ТЕМ ЖЕ кодом,
   что CLI `--send-log` (общее тело — `SendLogBody`: построение пакета, seq,
   чанк `log`, `UploadAndFinish`); после `verified/applied` копия удаляется,
   при неудаче остаётся до следующего такта. seq лог-пакетов — тот же
   монотонный `_state.Seq + 1` из того же процесса, что боевые пакеты, —
   монотонность сохраняется сама. До v2.1: `SendLogs` гасила демона и звала
   `--send-log`, который отказывал при занятом mutex, а первичная
   синхронизация на живой базе держит его часами — лог не уходил никогда.
2. **Skipped-only пакет при обнулении пропущенных** (`Tact.Run`,
   `PacketAgent.cs`). Отпечаток набора skipped (sha256 списка «сущность\tошибка»)
   хранится в `state.json` (`skipped_fp`); такт без данных, но с ИЗМЕНИВШИМСЯ
   отпечатком отправляет маленький пакет только с секцией `skipped` — в т.ч.
   при переходе к ПУСТОМУ набору (секция едет пустым массивом; приёмник такой
   пакет принимает: `_validate_manifest` посторонних секций не режет, apply
   работает по наличию секций, kind игнорируется — пакет идёт с kind=meta).
   До v2.1 условие требовало непустой skipped: права починились → пропуски
   исчезли → пакет не отправлялся → сервер годами показывал вчерашний
   `skipped.json` (ЗУП 11.08).
   ⚠ Граница: apply на приёмнике перезаписывает `skipped.json` только по
   НЕПУСТОЙ секции (`packet_apply.py`: `if isinstance(m.get("skipped"), list)
   and m["skipped"]`), поэтому очистка файла при обнулении набора требует
   однострочной правки apply + выката на юниты — решение за владельцем.
