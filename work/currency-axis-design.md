веток. Поэтому **следующая ось — валютная**; гео — после нормализации
справочника или появления адресного классификатора.

## 1. Данные

### 1.1. Что даёт ось на okna

| Сущность (OData / витрина) | Роль | Замер 25.08 |
|---|---|---|
| справочник валют | код / наименование / Ref | **6** |
| регистр курсов | Period, валюта, Курс, Кратность | **3 824** |
| константа валюты учёта | якорь accounting-ветки | **1** (MDL) |
| документы с `Валюта_Key` + `Курс` | факты, на которых считается вилка | **36** EntitySet |

Платформенные / структурные поля (не имена конфигурации в будущем коде):  
`Ref_Key`, `Description`, `Code`, `Period`; у фактов — prop валютной ссылки
(`*_Key` на справочник валют), prop курса, числовая величина суммы
(`Всего` / `Сумма` / аналог из `$metadata` как measure).

### 1.2. Как размечается «валюта документа» и «валюта учёта»

- **Валюта учёта** — значение константы валюты БУ (один Ref).  
- **Валюта документа** — ссылка на справочник валют в шапке/строке факта.  
- **Курс документа** — поле курса на том же факте (на okna у MDL = `1`,  
  у EUR energbank ≈ 19–20). Запасной источник курса — регистр курсов  
  на дату документа (тот же Period/валюта), если prop курса на факте пуст.

Рабочий класс «нужна конвертация» — любые строки, у которых валюта факта  
≠ якорю константы **или** курс ≠ 1. Точное множество — в `search_meta`,  
не литералы `MDL`/`EUR` в Python.

### 1.3. Один SQL: обе ветки суммы на одном источнике

Счёт — внутри SereneDB (п. 20 TARGET). Имена таблиц ниже — из замера;
в коде отбор EntitySet — структурный из `$metadata` / `search_meta`, без
литералов конфигурации. Синтаксис: штатный `SUM` / `CASE` /
`DISTINCT ON` (доки: Sql › Query syntax › SELECT › Aggregates;
DISTINCT ON; Cookbook › Search › Search with Joins and Analytics).

Зерно — **шапка документа** (на okna витрина реализации плоская
«шапка+строки»: `Всего` повторяется на каждой строке; суммировать
line-`Всего` = дефект п. 13).

```sql
-- Эскиз приёмки: обе ветки одним запросом.
-- :acct_key — Ref валюты учёта из search_meta (константа), не литерал.
-- :src — имя источника из карты currency_amount_map (не хардкод).
WITH hdr AS (
  SELECT DISTINCT ON (ref_key)
    ref_key,
    "Валюта_Key" AS curr_key,
    try_cast(nullif("Курс", '') AS DOUBLE) AS rate,
    try_cast("Всего" AS DOUBLE) AS amount
  FROM /* :src */ document_реализациятмц
  WHERE coalesce(posted, 'false') = 'true'
    AND coalesce(deletionmark, 'false') <> 'true'
    -- + тот же match/preds окна, что у fork_scan
  ORDER BY ref_key
)
SELECT
  round(sum(amount), 2) AS doc_amount,
  round(sum(
    CASE
      WHEN curr_key = :acct_key OR rate IS NULL OR rate = 1
        THEN amount
      ELSE amount * rate
    END
  ), 2) AS accounting_amount,
  count(*) AS n_headers,
  count(*) FILTER (
    WHERE curr_key IS DISTINCT FROM :acct_key AND rate IS NOT NULL AND rate <> 1
  ) AS n_fx
FROM hdr;
```

Альтернатива на регистрах/строках без повторённой шапочной суммы —
`sum(line_amount)` и `sum(line_amount * rate)` без `DISTINCT ON`; выбор
зерна пишет карта `currency_amount_map.grain = header|line` из структуры
`$metadata` (наличие header-итога vs только строковых ресурсов).

### 1.4. Точка вставки в корпус (не новый загрузчик)

Образец — `balance_registers` / `calendar_*` в `corpus_build.sql`: отбор из
`tmp3_ent` / `tmp3_prop` по структуре, запись в `search_meta`.

| Ключ `search_meta` | Содержимое | Как находят EntitySet |
|---|---|---|
| `currency_catalogs` | csv имён справочников валют | entity catalog с Code+Description, на который ссылаются currency-props фактов |
| `currency_rate_registers` | csv регистров курсов | entity с Period + currency ref + numeric rate (+ multiplicity) |
| `accounting_currency_constant` | имя константы / её value Ref | constant entity, value → currency catalog |
| `currency_amount_map` | json/csv: src, curr_col, rate_col, amount_col, grain | document/register с currency ref + numeric amount (+ optional rate) |
| опц. `currency_working_keys` | Ref валют, реально встречающихся в фактах | после сборки join витрины; пусто → ось выключена |

Приёмка шага корпуса на okna: `accounting_currency_constant` непуст;
`currency_amount_map` ≥ 1 источника; SQL §1.3 на фиксированном окне с
FX даёт `doc_amount ≠ accounting_amount` и `n_fx > 0` (на 25.08 для
реализации: 40 FX-шапок, суммы 78 789 043,20 vs 79 164 480,23).

## 2. Детектор

### 2.1. Нужда в оси

Ось нужна, когда одновременно:

1. в `search_meta` есть непустые `accounting_currency_constant` +
   `currency_amount_map` (иначе ось не открываем — честно по данным);
2. выбранный источник факта есть в карте (есть curr/amount props);
3. **и** либо в отобранных строках есть FX (`curr ≠ acct` или `rate ≠ 1`),
   либо словарь/ticket назвал валютную ось.

Рекомендуемый режим (как календарная / W): **always-on при наличии карты** —
два measure-прочтения: `doc_amount` и `accounting_amount`. Совпали → A;
разошлись → B/C. Если в выборке все строки в валюте учёта с rate=1 —
числа равны, люк не шумит.

### 2.2. Где в пайплайне

Рядом с W / calendar-axis, не отдельный конвейер:

```
parse_intent
  → apply_period_leader / period_readings
  → calendar_axis_readings          # уже в дереве, флаг
  → [NEW] currency_axis_readings(intent, match, search_meta)
        # 0..2 amount-basis readings: doc_amount | accounting_amount
  → fork_scan / fork_scan_readings
  → fork_classes* / resolve_fork_outcome
  → fork_outcome_a | fork_outcome_b | fork_outcome_c
  → ask_journal (ticket_variant только при нажатии)
```

`interpretation_id` / measure-fp расширять координатой amount-basis
(или `currency_basis_fp`), не ломая day-basis / window_fp. Лидер —
§2.4.

### 2.3. Без списка слов в Python

Триггеры «в валюте документа», «в валюте учёта», «в леях», «в евро» —
не `frozenset` в ask-коде.

1. **Словарь в данных** — phrase → `currency_basis=doc|accounting`
   рядом с `search_fork_label` / wiki-alias (§7). Холодный старт без
   словаря = always-on обе ветки + C без подписей.
2. **Только форма данных** — ось раскрыта при разных числах; лексика
   только сдвигает лидера (§2.4).

Запрещено: хардкод ISO-кодов / «MDL» / «EUR» в ask; промт «всегда
спрашивай про валюту».

### 2.4. Лидер amount-basis, когда ось не названа

| Условие | Лидер | Люк |
|---|---|---|
| ось не названа | `doc_amount` — сумма поля как в документе, **status quo** (сегодня конвейер не умножает на курс) | `accounting_amount` |
| словарь / ticket → учёт | `accounting_amount` | `doc_amount` |
| словарь / ticket → документ | `doc_amount` | `accounting_amount` |

Молчание ≠ выбор. Sticky только через `decision_id` / память нажатия.

Почему лидер = `doc_amount`: на okna 8 200 из 8 240 шапок реализации —
MDL с курсом 1, поэтому status quo численно совпадает с учётом почти
всегда; смена лидера на accounting по умолчанию сдвинула бы ровно те
40 FX-шапок и любые окна, куда они попали, — без явного решения
владельца. Люк предлагает учётную сумму, когда она другая.

## 3. Развилка

### 3.1. Класс

Класс: **сумма в валюте документа vs сумма в валюте учёта**
(amount-basis × то же E×M×W). Отпечаток — через
`fork_key_of(..., measure_ctx=…)` с amount-basis в fp (иначе B сольёт
ветки).

Тот же класс, что MTD vs полный месяц / calendar vs working (§7bis):
лидер + люк, нажатие в память.

### 3.2. Пары «число + подпись» (B / C)

Подписи — из словаря §7 (`search_fork_label`), не из имён таблиц:

| Ветка (машинный id) | Подпись-кандидат для агента §7 |
|---|---|
| `doc_amount` | «в валюте документа» |
| `accounting_amount` | «в валюте учёта» |

Нет подписей → исход **C**: число лидера + константа «есть другое
прочтение», ветки не называть, `options` пуст.

### 3.3. `ask_journal` при нажатии

Только факт нажатия: `ticket_variant`, `fork_outcome`, `fork_keys` с
amount-basis. Не писать выбор при ненажатии.

### 3.4. Исход A

Атом (число + единица) совпал на обеих ветках (нет FX в выборке или
курс=1 всюду) → **A**, люк не открываем.

### 7.3. Какое число «правильное» — исход **B**

Три кандидата (п. 10 TARGET — ошибка, если отдали не то):

| Исход | Суть | Вердикт на okna |
|---|---|---|
| **A** | всегда валюта учёта → умножать на курс | **нет:** 8 197/8 237 шапок MDL с курсом 1; «учётная» ветка = люк, не единственная истина |
| **B** | обе суммы законны → ось amount-basis (§2–§4) | **да:** Δ>0 только где FX; без оси клиент не знает, какую ветку видит |
| **C** | курс везде 1, цена мала | **нет:** в августе Δ **10,3 %** от doc_raw (375 437 / 3 648 295); на FX-доке до **19×** |

Доказательство B: константа БУ = MDL; 40 EUR-отгрузок августа несут сумму
**19 635** (doc) vs **395 072** (acct) — обе из одних строк, обе из SQL.
Вопрос «сколько продали» без оси не имеет одной «правильной» суммы.

**Связь с C3 (document vs register):** на августе register **3 942 014**;
document_raw **3 648 295**; document_acct **4 023 732**. Разрыв register−doc_raw
**293 719** — **не** объясняется курсом (FX даёт +375 437 doc→acct).
Register−doc_acct = **−81 718** — register ближе к doc_raw, чем к acct.
C1 и C3 **пересекаются** (три «истины»), но **не сводятся** друг к другу:
C3 — выбор src (document/register), C1 — amount-basis (doc/acct) внутри
document. Ось валют **не заменяет** structural sales_rank / register fork.

## Риски (кратко)

1. **Плоская витрина шапка+строки** — суммирование повторённого `Всего`
   раздувает обе ветки одинаково или по-разному при фильтрах строк;
   без `grain=header` (DISTINCT ON / отдельная шапка) ось врёт
   (п. 13 TARGET).
2. **Смешение размерностей в `doc_amount`** — при нескольких валютах
   документа в одном ответе «сумма в валюте документа» складывает
   несоизмеримые единицы; при B подпись обязана это не маскировать,
   иначе люк хуже молчания.
3. **Курс на документе vs регистр курсов** — расхождение даст третью
   ветку или тихий сдвиг; правило: сначала prop курса факта, регистр —
   только при пустом prop (и это должно быть видно в статусе ячейки).
