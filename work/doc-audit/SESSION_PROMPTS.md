# Промты сессий наведения порядка: доки → код → граф

Четыре отдельные сессии Claude Fable. Каждая самодостаточна: контекст между сессиями
НЕ переносится, передаётся только закоммиченное. Поэтому каждая сессия обязана
закончиться файлом-результатом, коммитом и push.

## Как запускать (режимы Fable)

| Сессия | Режим | Как включить |
|---|---|---|
| A — аудит-сравнение | **ultracode** | слово `ultracode` в первом сообщении (оно уже стоит в промте) |
| B — план правок | **plan mode**, проверка плана — ultracode | Shift+Tab до `plan`, промт B; после утверждения плана — промт B2 со словом `ultracode` |
| C — внедрение по докам | обычный | просто промт C |
| D — граф зависимостей | plan mode → ultracode на проверку | как B: сначала D, после утверждения — D2 |

Замечания по Fable:
- В ultracode Fable сам разворачивает многоагентные конвейеры; промт задаёт **механику
  недоверия** (независимые слепые аудиторы, адверсариальная проверка, раунды до сухого) —
  Fable её исполнит буквально.
- Штатный потолок конвейера — ~15 агентов. Для сессии A этого мало: перед запуском
  поднять в `/config` пункт «Dynamic workflow size» (или снять ограничение). Можно
  дополнительно задать бюджет прямо в сообщении: `+500k`.
- Основание механики — опыт этого проекта: параллельные аудиторы, не знающие друг о
  друге, находили каждый своё; одному прогону доверять нельзя (владелец, 01.08).

Как промты учитывают устройство Fable 5 (официальный гайд Anthropic по промтингу
Fable 5 + практика Claude Code):
- **правило с «почему»** — модель подменяет своим рассуждением прежде всего те правила,
  причин которых не видит; поэтому у каждого запрета в промте названа причина;
- **протокол несогласия** — явная инструкция «кажется, что правило неверно → останови
  шаг и спроси», против известного отказа «рассуждение верно узко → значит, правило
  можно не исполнять» (случай этого проекта, 31.07). Продублирован в CLAUDE.md —
  файл перечитывается на каждом запросе и, в отличие от промта, не выцветает за
  длинную сессию;
- **доказательный отчёт** — каждое «сделано/проверено» обязано указывать на результат
  инструмента этой сессии; по замерам Anthropic это почти исключает выдуманные статусы;
- **свежие проверяющие вместо самокритики** — верификаторы с чистым контекстом ловят
  больше, чем автор, проверяющий сам себя; отсюда «свежие агенты» во всех перепроверках;
- промты задают ЦЕЛЬ и МЕХАНИКУ проверки, а не пошаговый сценарий — пошаговость
  ограничивает Fable планом составителя.

## Сессия A — аудит: расхождения доков с кодом и живым стендом

Скопировать целиком:

```
ultracode

Задача: полный аудит расхождений между документацией и реальностью (код + живой стенд).
Мы строим фундамент для дальнейших работ — он должен быть точным. Одному прогону не
доверяем: каждый вывод добывается независимо и перепроверяется адверсариально.

Правила этого промта и CLAUDE.md исполняются буквально. Покажется по ходу, что правило
неверно, неприменимо или есть путь лучше, — останови этот кусок работы и вынеси вопрос
владельцу; подменять правило собственным рассуждением запрещено: рассуждение бывает
верным узко, но из него не следует «не делать» — на этом проект уже терял день.
Каждое «сделано/проверено» в отчёте — со ссылкой на конкретный результат инструмента
этой сессии; непроверенное называется непроверенным.

ШАГ 0, до всего: memory_bank/activeContext.md разросся (~900 строк) — перенеси историю
в memory_bank/progress.md по дням, осмысленно, ничего не теряя; в activeContext.md
оставь только живое состояние и «С ЧЕГО НАЧАТЬ». Закоммить отдельным коммитом.

Прочитай сначала: MAP.md, docs/TARGET_STATUS.md, TARGET.md, docs/HOW_NOT_TO.md §0.

МЕТОД (обязательная механика, не пожелание):
1. Извлечение утверждений. Запусти НЕЗАВИСИМЫХ параллельных аудиторов, не знающих друг
   о друге, минимум в четырёх разрезах:
   - по файлам доков: каждый берёт свою долю *.md (README, docs/*, memory_bank/*.md,
     CLAUDE.md, work/*/PLAN*.md) и выписывает ПРОВЕРЯЕМЫЕ утверждения: «сервис X слушает
     порт Y», «скрипт Z делает W», «роль R не имеет доступа к T», «файл F существует»;
   - по подсистемам кода: каждый берёт свою подсистему (ubuntu/serenedb, ubuntu/openclaw,
     ubuntu/1c-gateway, ubuntu/1c-etl, windows/, systemd-юниты) и выписывает, что код
     ДЕЛАЕТ на самом деле — не читая доков об этом;
   - по живому стенду (только чтение!): юниты systemd и их состояние, порты, роли и
     права в SereneDB (через psql, готовыми запросами к duckdb_settings/indexes/functions),
     файлы и таймеры — что РАБОТАЕТ на самом деле;
   - по перекрёстным ссылкам доков: каждый файл — на кого ссылается, существует ли цель,
     не противоречат ли два дока друг другу.
2. Сверка. Каждое утверждение доков сверяется с показаниями кода и стенда. Расхождение —
   находка. Противоречие двух доков между собой — тоже находка.
3. Адверсариальная проверка. Каждую находку проверяют минимум 3 независимых скептика
   с разными линзами (точность цитаты; воспроизводимость на стенде; «а не устарела ли
   сама находка»). Задача скептика — ОПРОВЕРГНУТЬ. Находка живёт при ≥2 подтверждениях.
4. Раунды до сухого. Повторяй раунды поиска новыми разрезами, пока два раунда подряд
   не дадут ничего нового. Счётчик «нашли N — хватит» запрещён.
5. Критик полноты. Отдельный агент в конце отвечает: какой разрез не прогнан, какое
   утверждение осталось непроверенным, где вывод держится на чтении кода там, где
   можно было замерить. Его находки — ещё один раунд.

ВЕРДИКТ каждому расхождению — ровно один из трёх:
  (а) док отстал — править док;
  (б) код/стенд нарушает контракт (TARGET.md) или решение владельца
      (memory_bank/owner-memory/) — это дефект КОДА, править док под код НЕЛЬЗЯ;
  (в) неясно, как задумано — вопрос владельцу.

ЗАПРЕЩЕНО в этой сессии: чинить код; менять состояние серверов; писать свои скрипты
для работы с БД (п. 20 TARGET.md — только готовые одиночные запросы на чтение);
править TARGET.md. Правки разрешены только: activeContext/progress (шаг 0) и
файлы результата.

6. Перепроверка итога. Когда таблица с вердиктами собрана, она перепроверяется
   МИНИМУМ ДВУМЯ полными независимыми проходами: свежие агенты, не участвовавшие в
   аудите, читают итоговый документ целиком и проверяют каждый вердикт по
   первоисточникам. Нашли ошибку → исправить → ещё один полный проход. Готово только
   после двух чистых проходов подряд.

РЕЗУЛЬТАТ — файл work/doc-audit/DISCREPANCIES.md:
таблица: № | утверждение | где в доке (файл:строка) | что на самом деле (файл:строка
или замер) | вердикт а/б/в | чем доказано [замер]/[код] | скептиков за/против.
Отдельными разделами: список (б) — дефекты кода для владельца; список (в) — вопросы
владельцу; отчёт критика полноты — что осталось непроверенным.
Запись в CHANGELOG.md, коммит, push. Промежуточные результаты коммить по ходу.
```

## Сессия B — план приведения доков в порядок

Промт B (в plan mode):

```
Прочитай work/doc-audit/DISCREPANCIES.md (результат аудита), MAP.md, CLAUDE.md,
memory_bank/owner-memory/feedback-details-are-dev-decisions-target-is-judge.md.

ШАГ 1 — разбор вопросов (в). Решение владельца (02.08): нюансы решает разработка,
мерило — TARGET.md; владельцу — только правки контракта и внешний периметр.
Для каждого из 41 пункта work/doc-audit/QUESTIONS_TO_OWNER.md впиши в поле «ОТВЕТ:»:
- TARGET.md или owner-memory дают ответ → «РЕШЕНИЕ (разработка): … Основание:
  TARGET.md п. N / owner-memory файл»;
- контракт молчит, вопрос технический → прими решение разработки, запиши его с
  основанием (что выбрано и почему; выбор должен переживать чужую базу — девиз
  автономности);
- вопрос меняет сам TARGET.md или внешний периметр (деньги, доступы, железо,
  что уходит наружу) → пометь «ВЛАДЕЛЬЦУ» и сформулируй простыми словами, без
  внутренних терминов. Таких должно остаться немного — собери их отдельным коротким
  списком в конце файла.
Решённые пункты разнеси: требует правки доков → в план как (а); требует правки
кода → в список (б) (чинить всё равно нельзя до графа).

ШАГ 2 — план правок доков. Правила:
- в план входят расхождения с вердиктом (а) «док отстал» + решённые в шаге 1;
- вердикты (б) в план правок НЕ входят; проверь, что список (б) полон и внятен;
- правки группируй кластерами по темам (один кластер = один коммит), для каждого
  кластера: какие файлы, что именно меняется, чем подтверждено новое утверждение;
- если правка стирает прежнее ошибочное утверждение, по правилу CLAUDE.md прежняя
  версия не стирается молча: в плане пометь, где нужен разбор «чем была неверна»
  (образец — VECTOR_DECISION.md §0);
- порядок кластеров: сначала то, от чего зависят другие доки (MAP.md, README,
  RUNBOOK_DEPLOY), потом остальное.
Особо про раздел «TARGET.md» в списке (а): сам TARGET.md не правится ни по какому
вердикту. У этих пунктов правится документ, который врёт ОТНОСИТЕЛЬНО контракта
(TARGET_STATUS.md, PLAN_PRIVACY.md и др.). Если же пункт описывает нарушение контракта
реальностью (например F139 — третий ручной шаг установщика, F216 — приёмочный набор
написан руками против п. 15) — это не (а): переквалифицируй в (б) или (в) с пометкой
и вынеси владельцу, в план правок доков не включай.

Несогласие с любым правилом или вердиктом аудита — отдельный вопрос владельцу в плане,
не твоё решение: молча «исправить» вердикт запрещено.
План сохрани в work/doc-audit/FIX_PLAN.md, коммит, push.
```

Промт B2 — проверка плана (новое сообщение или новая сессия):

```
ultracode

Проверь план work/doc-audit/FIX_PLAN.md против work/doc-audit/DISCREPANCIES.md.
Независимые проверяющие, минимум три линзы, каждая своим агентом, не знающим о других:
1) полнота: каждое расхождение (а) попало в план? ничего не потерялось?
2) корректность: ни одна правка не «узаконивает» вердикт (б) — не подгоняет док под
   дефектный код? ни одна не трогает TARGET.md?
3) доказательность: у каждого нового утверждения плана есть подтверждение
   (файл:строка или замер), а не «так логичнее»?
Каждую претензию к плану адверсариально перепроверить (может, неправ проверяющий).
Подтверждённые претензии внести правкой в FIX_PLAN.md с пометкой ревизии.

Проходов — МИНИМУМ ДВА, и оба полные: после внесения правок первого прохода запусти
второй с СВЕЖИМИ агентами (не видевшими первого) по уже исправленному плану. Второй
проход нашёл что-то → исправить → третий. Статус «проверен» ставится только после
двух чистых полных проходов подряд.
Итог: FIX_PLAN.md со статусом «проверен», коммит, push.
```

## Сессия D — граф зависимостей: план и наполнение

Промт D (в plan mode):

```
Прочитай CLAUDE.md (раздел про MCP), MAP.md, docs/ARCHITECTURE.md,
docs/RUNBOOK_DEPLOY.md, work/doc-audit/DISCREPANCIES.md (убедись, что статус
внедрения — завершён; если нет — остановись и скажи об этом).

Задача: спроектировать граф зависимостей проекта в MCP `memory`
(файл memory_bank/mcp-memory.json, коммитится в git) и хук, который делает граф
работающим без дисциплины. Цель графа: «починил одно — сломал другое» должно ловиться
ДО правки, а не после.

Спроектируй и опиши в work/doc-audit/GRAPH_PLAN.md:
1. Онтологию: типы сущностей (сервис, скрипт, индекс, роль БД, документ, замер...)
   и типы связей («зависит от», «пересоздаёт», «читает», «выкатывается через»,
   «проверяется замером»). Мало типов лучше, чем много.
2. Источник каждой связи: связь вносится ТОЛЬКО с доказательством (файл:строка или
   замер) и это доказательство хранится в наблюдении сущности. Связи «по памяти» —
   запрещены.
3. PostToolUse-хук на Edit|Write: правится файл → хук находит его в
   memory_bank/mcp-memory.json (это обычный JSON, читается без MCP) → вбрасывает
   в контекст «правишь X, от него зависят Y, Z; после правки обязателен замер N».
   Хук в стиле существующих (.claude/hooks/*.sh: разбор stdin, пустой {} по умолчанию).
4. Правило поддержки в CLAUDE.md: «изменил зависимость — обнови граф», строка в
   таблицу «Куда что писать».
План сохрани, коммит, push.
```

Промт D2 — наполнение и перепроверка (после утверждения D):

```
ultracode

Выполни work/doc-audit/GRAPH_PLAN.md: наполни граф и напиши хук.

Правила плана исполняются буквально; несогласие — вопрос владельцу, не решение.
Каждое «сделано/проверено» — со ссылкой на результат инструмента этой сессии.

Механика наполнения — как в аудите, одному прогону не доверяем:
1. Независимые сборщики связей по разрезам (по подсистемам кода, по докам, по стенду —
   только чтение), не знающие друг о друге.
2. Каждая связь-кандидат проверяется скептиком по первоисточнику: доказательство
   существует и говорит именно это? Связь без доказательства не вносится.
3. Контрольный опрос готового графа: для 10 известных зависимостей (возьми из
   HOW_NOT_TO — случаи «починил одно, сломал другое») проверь, что граф их ЗНАЕТ.
   Не знает — раунд добора.
4. Хук: написать, прогнать на тестовом stdin (см. как тестировались check-docs.sh и
   check-active-size.sh — через echo JSON | hook), подключить в settings.json.
5. Проверка на себе: правь тестово файл, от которого есть зависимости, — хук обязан
   вброситься. Откати тестовую правку.
6. Перепроверка итога: готовый граф целиком проверяется МИНИМУМ ДВУМЯ полными
   независимыми проходами свежих агентов (каждая связь — по первоисточнику; полнота —
   контрольным опросом по новым случаям из HOW_NOT_TO). Нашли ошибку → исправить →
   ещё полный проход. Готово после двух чистых проходов подряд.
Обнови CLAUDE.md (правило поддержки графа), CHANGELOG.md, коммит, push.
```

## Сквозные правила всех четырёх сессий

- 🔴 **Продуктовый код не чинится ни в одной из сессий A–D — вообще.** Пока нет графа,
  нет основы: неизвестно, что от чего зависит, и починка одного ломает другое. Любой
  дефект кода — только запись в список (б) для владельца. Чинить код будет отдельная
  свежая сессия ПОСЛЕ D, с опорой на граф. Единственное исключение — инфраструктура
  самих сессий (`.claude/hooks/*.sh`, `settings.json`) в сессии D2, по утверждённому
  плану.
- 🔴 **Итоговый документ с вердиктами или планом перепроверяется минимум ДВАЖДЫ** —
  полными независимыми проходами свежих агентов, не участвовавших в его составлении.
  Любая правка по итогам прохода обнуляет счёт: готово только после двух чистых
  проходов подряд (владелец, 01.08).
- Результат сессии — закоммиченный файл; незакоммиченное не существует.
- Сомнение на любом шаге → вопрос владельцу в списке (в), а не «моё правило».
- 1С — только чтение; серверы — состояние не менять; секреты не печатать.
- Хуки проекта будут спрашивать подтверждения (документы в коммите, размер
  activeContext, снайпер) — это штатно, отвечать по существу.
