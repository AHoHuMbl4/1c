## 1. Что за система

Бот в Telegram отвечает на вопросы о данных 1С обычным языком: «сколько у нас
контрагентов», «на какую сумму мы закупили товаров и услуг», «какой ИНН у Ромашки».
Ответ обязан быть **числом или списком, посчитанным базой**, а не пересказом.

Данные: выгрузка конфигурации 1С (учётная система) в аналитическую СУБД **SereneDB**
(движок с инвертированным индексом BM25/tfidf/dfi, векторным типом и `<=>`).

Масштаб боевой базы (`ut_test`, конфигурация «Управление торговлей 11.4.9»), `[замер 03.08]`:

| | |
|---|---|
| сущностей (таблиц 1С в поиске) | **1 502** |
| строк корпуса | **623 565** |
| сущностей со словарём синонимов | 697 |
| строк из 1С всего | 507 500 (корпус больше: табличные части разложены) |

Модели: ответы — DeepSeek v4 pro (снаружи), эмбеддинг — Qwen3-Embedding-8B (dim 1024,
свой контур), реранкер — Qwen3-Reranker-8B (свой контур).

## 2. Ограничения, которые нельзя обойти

Это контракт продукта, а не наши предпочтения. Решение, нарушающее любой пункт, нам не
подходит, даже если работает.

1. **Схема базы никогда не уходит в модель. NL2SQL запрещён.** Модель не видит ни имён
   таблиц, ни колонок, ни данных — только человеческие названия сущностей.
2. **Модель не считает и не ищет.** Считает база одним SQL, отбирает индекс. Модель нужна
   только для языкового сопоставления «слово человека ↔ название сущности».
3. **Объём в модель не растёт с размером базы.** Сейчас 6–20 тыс. символов на вопрос,
   держится кодом (бюджет перечня 8 000 символов, `serene_ask.py:61`).
4. **Никакого хардкода.** Ни имён сущностей, ни списков слов, ни порогов, подобранных под
   нашу базу. Критерий приёмки: на **чужой** базе 1С — другая конфигурация, другой язык —
   работает **без правки кода и без ручной настройки**. Это проверяется: вторая
   конфигурация прошла без единой правки.
5. **Отказ и уточнение — не ошибка. Догадка — ошибка.** Молча выбрать одно из нескольких
   правдоподобных прочтений запрещено; надо переспросить.
6. **Детерминированность.** Один вопрос на неизменных данных обязан давать один ответ.
7. Порядок предпочтений: **ответ → уточняющий вопрос → отказ**. Отказ при живых данных —
   тоже дефект.

## 3. Пайплайн целиком

```
1С (OData, только чтение)
 └─ шлюз, режущий не-GET
     └─ витрина: таблицы 1С как есть
         └─ СБОРКА, целиком внутри СУБД одним SQL-конвейером (такт ≤20 мин):
             ├─ search_corpus   строка = запись; поля: doc (текст), refs (ссылки на
             │                  другие объекты), nums (карта величин), flags, doc_date,
             │                  parent (шапка для табличной части), emb (вектор)
             ├─ search_idx      инвертированный индекс по doc/refs
             ├─ search_tables   ОДНА строка на сущность: src_table, label
             │                  («Реализация Товаров Услуг»), parent, emb (вектор метки)
             ├─ search_entity_alias + alias_idx — синонимы сущности человеческими словами,
             │                  собираются один раз при установке штатным агентом
             ├─ resolver_index  значения измерений (имена контрагентов, складов и т.д.)
             └─ вики (697 страниц): чем сущность отличается от соседей
                 └─ СЕРВИС ОТВЕТОВ (serene_ask.py) ── мост MCP ── бот в Telegram
```

**Путь одного вопроса:**

| # | Шаг | Кто делает |
|---|---|---|
| 0 | перефразирование вопроса по вики — «как это называется в ЭТОЙ базе» | модель бота |
| 1 | разбор намерения: слова с вариантами, период, что просят (сумма/счёт/список) | модель |
| 2 | **разведка**: каждое слово четырьмя способами в одном SQL | база |
| 3 | **кандидаты**: `GROUP BY src_table` по всем совпадениям | база |
| 4 | сито и порядок кандидатов | база + реранкер |
| 5 | **выбор сущности**: модель называет номер из перечня | модель |
| 6 | признак неоднозначности, подтверждение синонимами | база |
| 7 | арбитр между готовыми ответами (до 3) | модель |
| 8 | подсчёт — один SQL | база |
| 9 | формулировка; числа в текст подставляет **код**, не модель | модель + код |
| 10 | гейт: каждое число ответа обязано найтись в данных | код |

## 4. Стадия выбора сущности — по шагам, с кодом

### Шаг A. Кандидаты (recall) — `serene_ask.py:2371`

```python
by = tables_of(match, preds)          # где поиск ЧТО-ТО нашёл
kids, kid_pred = children_by_parent(by, ...)   # + табличные части найденных шапок
if not by and match and emb_ready(CORPUS):     # ← только если буквально НЕ нашлось
    by = <ближайшие по вектору строки корпуса, TOPK=40, GROUP BY src_table>
```

Совпадение считается **самым строгим способом, который дал непустой результат**:
`ts_phrase` (точная фраза) → `ts_phrase` с окном → `ts_levenshtein` (опечатки и
словоформы) → `ts_like` (подстрока, для склеенных имён вроде «ПоступлениеТоваровУслуг»).

🔴 **Буквальный отбор — жёсткий шлюз. Смысловой путь по корпусу включается, только если
буквальный не нашёл НИЧЕГО.** Нашёл хоть что-нибудь — пусть мусор — и вектор не
спрашивается вовсе.

🔴 **Синонимы сущностей в отборе кандидатов не участвуют.** `search_entity_alias`
читается только на шаге F, для проверки уже сделанного выбора (`serene_ask.py:2776`,
`:2802`). Своей поисковой поверхностью словарь синонимов не является.

### Шаг B. Порядок кандидатов — `serene_ask.py:2503`

Два входа **вперемежку**, чтобы ни один в одиночку не мог вытеснить кандидата:
вектор самого вопроса и вектор слова, которое сформулировала модель. Затем голова
списка (не больше `RERANK_TOP=60`) уходит **реранкеру**, который оценивает пары
«вопрос ↔ название сущности».

Так сделано после `[замер 30.07]`: модель на один и тот же вопрос выдаёт то «закупки»,
то «закупка» — шесть вызовов подряд дали 4 отказа и 2 верных ответа, потому что
множественное число дословно совпадало с именем регистра и вытесняло нужный документ.

### Шаг C. Структурные правила — `serene_ask.py:2570`, `:2610`

- **ребёнок не раньше родителя** (при числовом вопросе): итог документа живёт в шапке,
  а не в строках. Родство берётся из составного ключа платформы, а не из имени;
- **у кандидата обязана быть величина**: спрашивают сумму — остаются только сущности,
  у которых заполненная числовая величина вообще есть. Отбор по наличию, не по порогу.

### Шаг D. Выбор — `pick_entity`, `serene_ask.py:1200`

Модель получает **пронумерованный список и больше ничего из базы**. Рядом с каждым
названием:

```
12. Реализация Товаров Услуг — 272 matching records
     quantities recorded here: СуммаДокумента, СуммаВзаиморасчетов, ...
     typical for these records: оптовый склад, расчёты по авансам
```

- **число совпадений** — снимает случай «Банки» на 1 запись против «Классификатор
  Банков» на 680;
- **отличительные термы** — штатный significant-terms движка по полю ссылок;
- **величины** — из данных (`map_keys(nums)`);
- **структурная пометка** «строки внутри такой-то записи».

Бюджет 8 000 символов; что не влезло — видно клиенту как неполнота.

### Шаг E. Признак неоднозначности — `serene_ask.py:2700`

Если вершина по **самому вопросу** (считает база) разошлась с выбором модели — это два
равноправных прочтения, и мы обязаны переспросить, а не выбирать.

### Шаг F. Подтверждение синонимами — `_alias_verdict`, `serene_ask.py:2748`

Подтверждением считается любое из трёх: человек выбрал сам; сущность — вершина по
вектору вопроса; слово вопроса совпало с её синонимом (сравнение по основам слов
штатным словарём движка). Ни одно не выполнилось — уточняем.

Жёсткая форма («подтверждает только лидер ранжирования») **есть, но выключена**:
`[замер 30.07]` она дала 1 улучшение против 3 ухудшений.

### Шаг G. Арбитр — `arbitrate`, `serene_ask.py:382`

До трёх кандидатов доводятся **до готовых ответов**, и модель выбирает между
результатами, а не между названиями.

## 5. Где ломается — на живых числах

### Эталонный отказной случай

«**Сколько всего мы продали?**» / «What is the total amount of all sales?» — неверно в
**4 прогонах из 4**, каждый раз выбран регистр вместо документа реализации, причём в
разных прогонах разный регистр. Верный ответ: `document_реализациятоваровуслуг`
(«Реализация Товаров Услуг»), 272 документа.

Разберём по слоям — всё `[замер 03.08]`, прямыми запросами:

**1) Словарный разрыв.** Слово человека и слово базы не совпадают никогда:

```sql
SELECT src_table, count(*) FROM search_idx WHERE doc @@ ts_phrase('продали') GROUP BY 1;
```
→ **4 строки в 3 сущностях**, и все три — каталоги вариантов отчётов. Чистый шум.

В 1С продажа называется «реализация». Мост через это — только смысловой.

**2) Буквальный отбор находит мусор — и этим гасит смысловой путь.** Ослабляем до
подстроки, как делает код:

```sql
SELECT src_table, count(*) FROM search_idx WHERE doc @@ ts_like('%продаж%') GROUP BY 1
ORDER BY 2 DESC;
```

| сущность | совпадений |
|---|---|
| `accumulationregister_себестоимостьтоваров` | 7 307 |
| `document_планпродаж_товары` | 5 357 |
| `accumulationregister_планыпродаж` | 5 357 |
| `informationregister_сезонныекоэффициенты` | 4 524 |
| `accumulationregister_выручкаисебестоимостьпродаж` | 3 878 |
| … | … |
| **`document_реализациятоваровуслуг`** (верный ответ) | **272** |

Верная сущность **есть** в кандидатах — и проигрывает шуму в 27 раз по тому самому
признаку («сколько совпадений»), который мы даём модели как различающий. Он здесь
работает против нас. А поскольку буквальный отбор что-то нашёл, вектор по корпусу не
спрашивается вовсе.

Слово «продаж» стоит в метках **64 сущностей** из 1 502.

**3) Знание, которое у нас ЕСТЬ, но не используется для отбора.** Словарь синонимов той
самой верной сущности:

```
document_реализациятоваровуслуг → реализация, продажа, отгрузка клиенту, накладная
```

Слово «продажа» там стоит. Но словарь читается **после** выбора, только для проверки, и
на отбор кандидатов не влияет. Проверим его как поисковую поверхность:

```sql
SELECT src_table, tfidf(alias_idx.tableoid) s FROM alias_idx
WHERE aliases @@ ts_phrase('продажа') ORDER BY 2 DESC LIMIT 8;
```

| сущность | оценка |
|---|---|
| `document_реализацияподарочныхсертификатов` | 7,99 |
| `businessprocess_типоваяпродажа` | 6,52 |
| **`document_реализациятоваровуслуг`** | **4,61** |
| `catalog_сделкисклиентами` | 4,61 |
| `accumulationregister_товарыкоформлениюотчетовкомитенту` | 4,61 |
| `document_реализациятоваровуслуг_видызапасов` | 4,61 |

Верная сущность попадает в тройку — заметно лучше, чем буквальный отбор. Но:
**четыре сущности имеют одинаковую оценку 4,61**, а порядок между равными ничем не
задан (у запроса нет разделителя равенства) — то есть на этом самом вопросе выбор между
верным документом и тремя чужими решается порядком исполнения. Это отдельный
зарегистрированный дефект (`F243`), сам по себе он проблему не решает, но показывает,
что даже там, где сигнал есть, он у нас не доведён до детерминированного порядка.

А по фактически заданному слову вопроса («продали», не «продажа») тот же индекс отдаёт
**две** сущности, обе посторонние: анализатор не приводит «продали» к «продажа».

### Второй показательный случай

«**Сколько НДС мы заплатили поставщикам?**» → выбирается регистр «уплаченный НДС»
(2 719 573,23) вместо табличной части документа приобретения (11 036 086,09). В
названии **18 сущностей** есть слово «НДС», а у верной — нет вовсе: она называется
«Приобретение Товаров Услуг_Товары».

### Косвенный признак

`[замер 02.08]` **задержка коррелирует с ошибкой**: верные ответы 10–15 с, неверные
54–60 с, один таймаут 300 с. Долго идут ровно те вопросы, где буквальный отбор пуст или
почти пуст — то есть где всё решает смысловой путь.

### Диагноз в одной фразе

**Когда в вопросе нет слова, буквально совпадающего с данными, множество кандидатов
формируется шумом, и все последующие ступени — реранкер, перечень для модели, арбитр —
работают уже внутри неверного множества.** Ошибок счёта нет ни одной: арифметика верна
всегда, гейт ни разу не пропустил число, которого нет в данных. Ошибается только выбор
места, где считать.

Две различимые половины:

- **(а) recall** — верная сущность либо не попадает в кандидаты, либо попадает с
  заведомо проигрышным весом;
- **(б) precision** — попала, но модель/реранкер берут соседа.

Реранкер лечит (б) и **это его главный вклад**: `[замер 02.08]` без него верная сущность
первой в 14 % случаев, с ним — в 36 %. По (а) он бессилен: он видит только то, что ему
дали.

## 6. Что уже пробовали — и что замер отверг

Важно для экспертов: это не рассуждения, а прогоны. Повторять их не нужно.

| Попытка | Чем кончилось |
|---|---|
| показать модели синонимы сущностей прямо в перечне | **хуже**: 2 верных из 12 против 5 без вставки; попутно ломался шаг выбора величины |
| перегенерировать синонимы с покрытием величин | **хуже**: 2/3/5 против 3/4/3, откачено |
| жёсткое вето «подтверждает только лидер синонимов» | 1 улучшение против 3 ухудшений |
| признак «у кандидата есть спрошенное поле» (по основам слов) | не помог **ни в одной** из трёх форм (отсев / перестановка / поднятие к арбитру); по основам совпадает слишком много названий |
| модель посильнее (v4 pro вместо flash) | 11 плохих исходов против 11 — не влияет |
| индекс синонимов на словаре со стеммингом | ранжирование вырождается в нули |
| сокращение промтов сервиса | пользы не подтвердило |
| прямой вызов сервиса в обход бота и вики | даёт другой ответ — как метод замера негоден |

Отдельно: гипотеза владельца «плохие результаты потому, что реранкер был выключен»
**проверена и не подтвердилась** — с доказанно работающим реранкером результат тот же.

## 7. Чем меряем и почему числам трудно верить

- Приёмочный набор — **58 вопросов** под 12 классов дефектов, у 47 сверяется величина
  против эталона, посчитанного независимым SQL по источнику.
- 🔴 **Разброс замерен: ±1 верный ответ из 8** между прогонами **без единой правки**
  (5, 6, 5, 5). Значит сдвиг на один ответ доказательством не является.
- Прибор приёмки был сломан и переписан 02.08 (засчитывал провал за успех); **все числа
  приёмки, снятые до этого, аннулированы**.
- Числовой гейт (сверка каждого числа ответа с данными) по устройству движка живёт
  только на настоящей доставке в мессенджер, а прогонщик зовёт агента без неё: за всю
  историю журнала он сработал **1 раз из 240**. То есть даже свежие числа сняты с
  выключенной половиной защиты.

Прибор, свободный от всего этого: `work/acceptance/entity_choice_bench.py` — сравнивает
только выбор сущности, детерминирован, ранжирование делает движок, модель ответов не
зовётся.

## 8. Что мы считаем открытыми направлениями

Не решения, а то, куда мы смотрим. Ровно здесь и нужен взгляд со стороны.

1. **Сделать словарь синонимов полноценной поисковой поверхностью на этапе отбора**, а
   не поздней проверкой: сегодня знание «продажа = Реализация Товаров Услуг» у нас
   лежит в базе и в отборе не участвует. Риск известен: раньше синонимы, поданные
   модели в перечне, сделали хуже — но это была другая точка приложения (подсказка
   модели, а не отбор индексом).
2. **Убрать «буквальный отбор гасит смысловой»**: сегодня это взаимоисключающие ветки,
   а нужен, видимо, единый отбор, где оба сигнала складываются (гибридный поиск с
   нормировкой). Ограничение: объём в модель расти не должен, отбор обязан оставаться
   на стороне базы.
3. **Признак «сколько совпадений» вреден в нынешнем виде** — он пропорционален размеру
   сущности, а не относимости. Нужна нормировка, но без подобранного под базу порога.
4. **Отбор со стороны величины, а не слова**: у сущности либо есть искомая величина,
   либо нет — это факт из данных. Мешает объём: по слову «сумма» таких объектов 88, и
   число растёт с базой.
5. **Правило владельца «несколько разных объектов отвечают вопросу → всегда
   переспрашивать»** реализовано наполовину: признак расхождения сигналов есть, но
   уточнение кнопками из данных не доведено. Ограничение: лишний вопрос там, где
   сомнения нет, обесценивает настоящие уточнения.

модели и генерировать SQL; вести отбор моделью; завести список слов-синонимов или
правил в коде; подкрутить пороги так, чтобы «на нашей базе обычно побеждало нужное».
