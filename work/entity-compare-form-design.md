## 0. Общая причина (оба класса)

Детектор §3 всегда включён, но пространство ячеек по факту —

**R₀ = E × P × M × W с операциями только `count`/`sum` по одной `src_table`.**

Эталоны K4/K6 требуют форм, которых в R₀ нет:

| Класс | Форма эталона | Что делает бой сейчас |
|---|---|---|
| K6.1 | `complement` = \|каталог\| − \|DISTINCT ось в продажах окна\| | clarify по чужому регистру / C |
| K6.2 | `distinct_axis` = COUNT DISTINCT ссылки на контрагента в продажах | count карточек справочника + clarify |
| K4 | `compare` = SUM(мера, W₁) − SUM(мера, W₂) | `axis_form=rank` по оси договора |

Пока форма F не входит в атом и в скан детектора, «не та сущность» и
«сравнение не собрано» — **один дефект**: конвейер отвечает чужой формой
атома, а детектор либо не видит нужную ячейку (K6.1), либо видит чужие
count-классы и не удерживает исход (K6.2), либо compare-путь не
включается (K4).

Ответ на развилку владельца про K6 **не один на оба вопроса**:

| Вопрос | Случай | Доказательство (бой 25.08) |
|---|---|---|
| «…не продаётся…» | **(б)** нужные сущности/операция не в живом пространстве | `pool_srcs` без живого регистра продаж по ТМЦ; `catalog_*` → `no_live_cells`; live только книга НДС; `fork_outcome=C` / `uncounted_cell` |
| «…реально покупают?» | **(в)** развилка была, лидер не тот | early `fork.classes=16`, live включают и справочник, и регистр продаж; шага «детектор исходов» нет; `выбрал=модель` → `catalog_*`, `doubt=False` |

Общий класс лечения — **форма F в R** + исходы на полном пуле форм, не
заплатки под три строки gold.

# Раздел A — K6 «не та сущность»

## A.1. Проблема (живые цитаты)

### A.1.1. «сколько позиций совсем не продаётся в этом месяце?»

- Эталон SQL gold: `2384 − 493 = **1891**` (каталог − DISTINCT `ТМЦ` в
  `accumulationregister_*` продаж за MTD) — замер `psql` okna 25.08.
- Ответ боя: `kind=clarify`, текст про **Книгу продаж / НДС**,  
  `fork_outcome=C`, `fork_c_reason=uncounted_cell`.
- `diag.fork.pool_srcs` (исходный arb_pool):  
  `catalog_номенклатура`, `accumulationregister_книгапродаж`,  
  `document_передачатмцврозничнуюторговлю_номенклатура`.
- `live_srcs`: только `accumulationregister_книгапродаж`.
- `excluded`: catalog + document — `no_live_cells` (preds `doc_date` на
  сущностях без даты в корпусе).
- Атомы: два окна MTD/full_month, оба **count=2376** на книге продаж —
  не 1891, не complement.
- Шаги: «детектор исходов» → «исход C».

**Случай (б):** вторая (и третья) нужная клетка формулы не жива / не в
пуле операций. Детектор честно поднял C по непосчитанным, но **не**
открыл развилку «не продаётся vs книга НДС», потому что ячейки
complement в пространстве нет.

### A.1.2. «сколько клиентов реально покупают?»

- Эталон: DISTINCT контрагент в продажах за 12 мес = **141**.
- Ответ: `kind=clarify`, рассуждение по **карточкам** контрагентов
  («Всего в выборке 353…»), `focus=catalog_контрагенты`, `doubt=False`.
- Early fork: `classes=16`, `pool=16`; в `live_srcs` есть и
  `catalog_контрагенты`, и `accumulationregister_реализациятмц`
  (count строк **77901**, не DISTINCT).
- Шаги: «детектор развилки» (16 классов) → сразу «сущность выбрана /
  модель» — **нет** «детектор исходов» / `fork_outcome`.
- Причина пропуска исходов в коде: блок §2 срабатывает при
  `len(arb_pool) > 1` (или window-fork). После выбора модели без
  сомнения `arb_pool = [catalog_*]` → исходы не пересчитываются, хотя
  early-скан уже показал 16 разных атомов.

**Случай (в):** развилка по данным была; лидер и путь ответа — справочник;
нужная форма `distinct_axis` в атомах скана отсутствует (везде
`operation=count` по строкам).

## A.2. Данные

Структурно (из `$metadata` / `search_tables` / `refs_map` / `written_by`),
без имён конфигурации в будущем коде:

| Роль | Как узнать | Роль в формуле |
|---|---|---|
| каталог «позиций» | Edm EntitySet `catalog_*` с товарной семантикой (уже есть канон прайса) | \|E_cat\| |
| регистр/документ продаж | `accumulationregister_*` с `written_by` от документа продажи + меры Количество/Всего | факт продаж |
| ось «ТМЦ / номенклатура» | ключ в `refs_map`, чей `target_src` — товарный каталог | DISTINCT для «продавалось» |
| ось «контрагент / клиент» | ключ в `refs_map` → справочник контрагентов | DISTINCT для «покупают» |
| окно | те же `period_readings` / MTD / rolling 12m из intent | W |

Complement «не продаётся» =  
`count(E_cat) − count(DISTINCT axis_product ON sales IN W)` — один
SQL в движке (`count` / `count(DISTINCT …)` /
`FILTER`, доки: Sql › Functions › Aggregate Functions › Examples).

Distinct «реально покупают» =  
`count(DISTINCT axis_counterparty ON sales IN W)` на каноне продаж,
не `count(*)` справочника.

## A.3. Детектор

Расширение пространства: **R = E × P × M × W × F**, где F для K6:

| `form` | Ячейка | Когда открывать (из данных, не лексики) |
|---|---|---|
| `row_count` | нынешний `fork_scan` count | status quo |
| `distinct_axis` | COUNT DISTINCT по оси ссылки, чей target — каталог вопроса | вопрос `want=count` + kind/ось указывает на справочник **и** в пуле есть sales-register с этой осью |
| `complement` | \|catalog\| − distinct_axis(sales) | в пуле одновременно catalog-кандидат и sales с осью на этот catalog; окно W на sales, catalog **без** date-pred |

Правила без списков слов:

1. Каталог под pred `doc_date` → статус ячейки `not_applicable` /
   скан **без** pred даты (как сейчас match не в WHERE скана), иначе
   ложный `no_live_cells`.
2. Early-скан с `classes > 1` обязан либо дать исход A/B/C на **том же
   пуле**, либо явно записать в diag `fork_outcome_skipped=arb_pool_collapsed`
   и **не** уходить в модельный выбор сущности молча (дыра Q2).
3. Атом distinct/complement входит в `_fork_atom_equiv_fp` через
   `operation` + `form` + `axis` + `exact_value` (без src).

## A.4. Исходы A/B/C

| Ситуация | Исход |
|---|---|
| Один атом (например distinct=141 на всех живых sales-ветках) | A / unique |
| Catalog-count vs distinct-sales дают разные числа + подписи | **B**: лидер = форма, ближе к вопросу (distinct/complement), люк с row_count справочника |
| Нет подписей / непосчитан complement | **C**: число лидера + «есть другое прочтение» или clarify без чужого НДС-регистра как «ответа» |
| Только справочник live, sales нет | C / unavailable по статусу ячейки sales — не clarify «по карточкам» как будто продаж нет |

Лидер при B: **форма из данных вопроса** (ось+каталог vs факт), не
модель. Молчание ≠ выбор (§2).

## A.5. Флаг

`ASK_ENTITY_FORM=0` по умолчанию.

- `0` — поведение боя без F (регрессия).
- `1` — ячейки `distinct_axis` / `complement` + запрет схлопывания
  исходов при early `classes>1`.

Бой не включать без слова владельца; проба на стейджинге.

## A.6. Замки

Оффлайн (новый модуль рядом с `test_fork_detector.py` /
`test_fork_outcomes.py` — имя при внедрении; до создания в дереве нет):

| Замок | Ожидание |
|---|---|
| флаг умолч. 0 | бой-путь без F |
| catalog + date-pred → ячейка catalog не `no_live_cells` из-за даты | A.3.1 |
| distinct_axis на фикстуре sales → атом ≠ row_count | операция |
| complement = cat − distinct | число |
| early classes>1 + arb_pool=1 → исход не unique молча | дыра Q2 |
| нет литералов имён окн/«книгапродаж» как триггеров в diff | снайпер |
| `test_fork_detector`, `test_fork_outcomes`, `test_calendar_axis` | остаются зелёными |

Живые (после флага на стейдже): два вопроса K6 → digits к gold;
остальные 22 okna gold **не краснеют**.

## A.7. Порядок внедрения

1. Оффлайн-замки формы + правка скана (catalog без date-pred; F-ячейки)
   за `ASK_ENTITY_FORM`.
2. Связка early-fork → `resolve_fork_outcome` без схлопывания пула.
3. Подписи §7 для пар «карточки / факт покупок», «все позиции /
   не продавались в окне».
4. Проба стейдж → слово владельца на бой.

# Раздел B — K4 «сравнение: форма не собрана»

## B.1. Проблема (живые цитаты)

Вопрос: «эта неделя лучше прошлой или хуже?»

- Эталон gold: diff сумм продаж двух окон ≈ **−792 128,74** (замер SQL
  okna 25.08 на том же регистре канона продаж).
- Ответ боя:  
  `«Основной договор / 0000000001»: 728 · … · Реализация ТМЦ (регистр) · Всего · Договоры · rank`  
  — `kind=answer`, `axis_form=rank`, `grain=group`, `axis_col=Договор`,
  `sales_canon_locked` на регистре продаж, **`compare_sales` в diag нет**.
- Разбор: `считать=list` / фактически `want=list` → `rank_intent_from`
  истинен; `sales_compare_intent` при rank без «чем» — ложен
  (локальная матрица 25.08: `want=list` → compare=False; `want`∈{,count,sum}
  → compare=True).
- Период assumed `2026-08-17..2026-08-23` (прошлая полная неделя). Даже
  при срабатывании compare `sales_compare_windows` на таком period даёт
  `period2={}` / `form=explicit` — второй половины нет. На WTD с
  `from=понедельник этой недели` окна собираются.

**Где теряется форма:** вопрос **не распознан как compare** (перебит
rank через `want=list`). Счёт двух сумм и renderer compare не
вызывались. Это не «посчитали, но renderer собрал не ту фразу».

Код пути compare уже есть (`sales_compare_intent` →
`aggregate_compare_sales` → `form=compare` → атом/renderer §5) и закрыт
замком `test_compare_sales.py` при `want=sum`. Дыра — **вход в путь** и
согласование периода двух окон, не отсутствие агрегата.

## B.2. Данные

Те же, что канон продаж §6bis: один sales-register, мера денежного
канона, два окна W₁/W₂ из `period_readings` / календарных границ
(неделя/месяц), без лексики имён таблиц.

Счёт — штатный `sum(...) FILTER (WHERE …)` на двух окнах в одном
запросе или два `aggregate` + diff (как сейчас
`aggregate_compare_sales`). Доки: Sql › Functions › Aggregate Functions
› Examples (`sum` + `FILTER`).

## B.3. Детектор

Форма `compare` в F:

1. Триггер формы — **структура вопроса о двух окнах одного measure**, не
   `want=list`. Rank (`top` / суперлатив / одна ось без второго окна)
   остаётся rank; compare «лучше/хуже **чем** / эта vs прошлая» —
   compare даже если парсер выставил `list`.
2. Окна: если intent дал одно окно «прошлая неделя», а форма compare —
   достроить пару (текущее WTD/MTD ↔ prior) из `today` + календаря, не
   оставлять `period2={}`.
3. Ячейка детектора: атом `operation=compare`, `exact_value=diff`,
   `period`+`period2`, measure канона. Разные src с тем же diff → A;
   разные diff → B/C.

## B.4. Исходы A/B/C

| Ситуация | Исход |
|---|---|
| Один diff на каноне продаж | unique / A |
| Документ vs регистр, разные diff | B (лидер = канон регистра §6bis) + люк |
| Окна не собрались / мера NA | C / unavailable, **не** rank по договору |

Renderer: пара «подпись + число» из `build_answer_atom` /
`render_atom_pair` (§5); модель цифры diff не пишет.

## B.5. Флаг

Тот же контур формы: либо общий `ASK_ENTITY_FORM`, либо узкий
`ASK_COMPARE_FORM=0` (умолч. 0), включающий только вход в compare +
достройку окон. Предпочтительно **один флаг F**, чтобы K4/K6 не
разъехались.

## B.6. Замки

| Замок | Ожидание |
|---|---|
| вопрос K4 + `want=list` → compare intent истинен при флаге | вход |
| windows WTD/MTD не пустой `period2` | окна |
| `aggregate_compare_sales` form=compare (уже `test_compare_sales`) | не краснеет |
| ответной фразы с `· rank` на compare-вопросе нет | форма |
| gold K4 digits; прочие 23 не краснеют | скорер |
| `test_fork_*`, `test_fork_detector`, `test_calendar_axis` | зелёные |

## B.7. Порядок внедрения

1. Вход compare независим от ложного `want=list`; достройка окон.
2. Ячейка compare в fork-скане (рядом с F из раздела A).
3. Замки + проба стейдж; бой по флагу после слова владельца.

# Универсальность

На чужой базе без правки кода и без ручного разбора:

- оси и каталоги — из `refs_map` / `search_tables` / `$metadata`;
- sales-register — `written_by` + меры, не имя;
- окна — календарь / period_readings;
- подписи веток — словарь §7, не литералы.

Запрещено в будущем коде: списки слов «не продаётся» / «реально» /
имён `книгапродаж` / городов как единственный вход в форму. Лексика
парсера может подсказывать F, решение — данными и атомом.
